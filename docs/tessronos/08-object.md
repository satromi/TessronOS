# 第8章　実身

## 8.1 基本的な考え方

TessronOSでは、ファイル、共有メモリ、デバイス、プロセス、プロセス間の通信路、ネットワークのソケット、ウインドウとその部品を、すべて実身として同じ基本操作で扱う。実身は128bitのUUIDで識別され、レコードの列、属性(メタデータ)、保護情報を持つ。どの種類の実身も、開いてキーを取得し、レコードを読み書きし、イベントを受け取る、という同じ手順で使える。

この構造はBTRON2の設計にならっている。周辺核は実身の種類ごとのマネージャの集合で、名前マネージャがシステムコールを担当のマネージャへ振り分ける。

| タイプ | サブタイプ | 実体 | 例 |
| --- | --- | --- | --- |
| ストレージ`OB_T_STORAGE` | ファイル`OB_S_FILE` | ボリューム上のレコード(TSFS) | 文書、図形、プログラム、ユーザ |
| ストレージ | メモリ`OB_S_MEMORY` | 主記憶上のレコード。揮発性 | 共有メモリ、グローバル名 |
| デバイス`OB_T_DEVICE` | ディスク`OB_S_DISK`、キャラクタ`OB_S_CHAR`、時計`OB_S_CLOCK`、サウンド`OB_S_SOUND`、一覧`OB_S_DEVLIST`、システム`OB_S_SYSTEM`、入力`OB_S_INPUT`、画面`OB_S_DISPLAY`、GPIO`OB_S_GPIO`、USB`OB_S_USB`、カメラ`OB_S_CAMERA` | ドライバ | SDカード、USBメモリ、時計、キーボード、画面、GPIOのバンク、乱数 |
| プロセス`OB_T_PROCESS` | | 実行中のプロセス | |
| 通信`OB_T_CHANNEL` | キュー`OB_S_QUEUE`、ソケット`OB_S_SOCKET` | 主記憶上のメッセージキュー、ネットワークのソケット | ウインドウのイベントの受信キュー、TCPの接続 |
| ウインドウ`OB_T_WINDOW` | ウインドウ、パネル、メニュー、部品 | ウインドウマネージャ | 文書のウインドウ、ボタン、テキストボックス |

## 8.2 基本操作

| 分類 | システムコール |
| --- | --- |
| 開く、閉じる | `ob_opn_obj`、`ob_cls_obj` |
| 作成、削除、複製 | `ob_cre_obj`、`ob_del_obj`、`ob_cpy_obj` |
| 参照、検索 | `ob_ref_obj`、`ob_lst_obj`、`ob_fnd_nam`、`ob_fnd_lnk`、`ob_lst_lnk` |
| レコード | `ob_rea_rec`、`ob_wri_rec`、`ob_apd_rec`、`ob_trn_rec`、`ob_del_rec`、`ob_lst_rec`、`ob_sch_rec`、`ob_trs_rec` |
| リソース | `ob_rea_res`、`ob_wri_res`、`ob_del_res`、`ob_lst_res` |
| 属性とアイコン | `ob_get_atr`、`ob_set_atr`、`ob_get_ico`、`ob_set_ico` |
| マッピング | `ob_map_rec`、`ob_unm_rec` |
| イベント | `ob_ntf_evt`、`ob_can_evt` |
| 保護 | `ob_get_prt`、`ob_set_prt`、`ob_dup_key`、`ob_acc_obj` |
| ユーザ | `ob_login`、`ob_set_pwd`、`ob_get_crd` |
| ボリューム | `ob_att_vol`、`ob_det_vol`、`ob_ref_vol`、`ob_get_dom`、`ob_set_dom` |
| トランザクション | `ob_beg_trx`、`ob_end_trx` |

実身を開くと実身キーが返る。キーには所有プロセスと許可された操作が記録されており、以後の操作はキーの操作権限で判定する。所有プロセス以外がキーを使うと`E_OACV`になる。`ob_dup_key`で操作権限を絞ったキーを作り、別のプロセスに渡せる。プロセスが終了すると、そのプロセスのキーはすべて閉じられる。

ストレージの実身では、開くときに排他の指定(BTRONの排他モード)を`ob_opn_obj`の`ops`に足せる(`include/ts/ob.h`)。

| 指定 | 開いている間に締め出すもの |
| --- | --- |
| `OB_O_EXCL`(完全な排他) | レコードを読み書きするほかのすべてのキー |
| `OB_O_WEXCL`(書込みの排他) | 書くためのキー(`OB_OP_WRITE`、`OB_OP_RECORD`、`OB_OP_ATRWR`)。読むためのキーは開ける。書くキーが開いていると、このキーも開けない |
| `OB_O_NOEXCL`(排他なし) | だれも締め出さない |
| 指定なし | `OB_O_NOEXCL`と同じ(BTRONの仕様どおり) |

締め出されたキーを開こうとすると`E_BUSY`になる。`OB_OP_ATRRD`だけで開いたキー(属性だけのキー)は、だれにも締め出されず、だれも締め出さない。変更の通知を受けるために開いたままにするキー(設定の実身を監視するカーネルのタスクのキーなど)が書込みを妨げないためで、属性だけのキーはレコードの中身を見ないので、書きかけを見ることもない。TSFSの層の開くモードは`TFO_EXCL`、`TFO_WEXCL`、`TFO_NOEXCL`で、組み合わせの判断は`tsfs.c`の`od_clash`にある。

#### 排他なしの約束

排他の指定のないキーは、ほかの者がどう開いていても、次のように振る舞う。

- 1回の変更(`ob_wri_rec`の1回、`ob_trn_rec`、`ob_apd_rec`、`ob_del_rec`、`ob_rpl_rec`、属性、アイコン、資源の1回の書込み)は、ボリュームのロックの中で行うので、ほかの者の変更と混ざらない。2つのキーが同じレコードを書いても、レコードやボリュームの構造が壊れることはない(TSFSの層は開いたキーごとに確定の番号だけを持ち、レコードの配置や長さは毎回ボリュームから読む)。同じ範囲を2人がその場で書けば、後の書込みが残る。`ob_rpl_rec`どうしなら、後の置き換えが丸ごと残る(Linuxの`rename`による置き換えと同じ)。
- 読む者には、レコードが最後の変更が残したとおりに見える。いくつもの変更を続ける書く者(書いてから切り詰める、部分ごとに書く、いくつものレコードをそろえて書く)の途中も見える。見られて困る書く者は`OB_O_EXCL`で開く。
- 読んで、変えて、書き戻す者は、間にほかの書く者が入ると、その者の変更を消すことがある。そうした者は`OB_O_WEXCL`で開く。
- 1つのレコードを何回かに分けて読む者は、間に置き換えがあると、新旧の中身を混ぜて読むことがある。1つの版として読みたい者は、読むキーを`OB_O_WEXCL`で開く(書く者を締め出す)か、1回で丸ごと読む(`knl_ob_rea_all`、`ui_key_all`は大きさを聞いてから1回で読む)。

TessronOSの中のプログラム(カーネル、アプリ、ライブラリ、POSIXの層、PCM Player、MPEG Player、ブラウザ)は、書き方に応じて次のように開く。

| 書き方 | 直し | 場所 |
| --- | --- | --- |
| 作ったばかりの実身に、いくつものレコードを足して書く | `OB_O_EXCL`で開く | 書庫の展開(`unp_obj.c`)、書庫管理(`arc_pack.c`の書庫のレコード)、バックアップの書出しと戻し(`bk_media.c`、`bk_vol.c`、`bk_rest.c`)、ファイル変換の取込み(`xf.c`の`XF_OPS`、`xfu_imp.c`の`IMP_OPS`、`xfu_obj.c`、`xfc_net.c`)、デスクトップの複製の写し先(`om_copy.c`)、印刷の実身(`ui_prn.c`)、予定表、マイクロカード、システム環境設定が作る実身(`cal_main.c`、`mc_obj.c`、`sysenv.c`)、パッケージの入れ替えで消すレコード(`dtpkg.c`) |
| 読んで、変えて、書き戻す(箱のレコード0に仮身を足す、設定の行を変える、メタデータを変える) | `OB_O_WEXCL`で開き、レコードは`ob_rpl_rec`で置き換える(前は書いてから切り詰める2回の変更) | 箱への仮身の追加と取出し(`xfu_obj.c`、`arc_pack.c`、`bk_vol.c`)、デスクトップのレコードの保存(`om_obj.c`の`om_obj_record_put`、`om.c`の`om_wri_doc`)、トレー(`tray.c`)、カレンダーの属性(`datetime.c`)、ファイル変換の設定と属性(`xfc_net.c`、`xf.c`)、設定の実身(下の段落) |
| 元のレコードを何回かに分けて読んで写す | 読むキーを`OB_O_WEXCL`で開く | デスクトップの複製の写し元(`om_copy.c`) |
| 1回の`ob_rpl_rec`で丸ごと置き換える保存 | 指定なし | 文章、図形、表計算、手帳、単語登録、カレンダーの保存、ブラウザの実身のレコード0(`br_obj.cc`)など |
| ブラウザの保存の場所(別々に開いた窓のブラウザが共有する) | 書いてから途中を書き換えるレコードは`OB_O_EXCL`、記録を足して見出しを最後に書くレコードは`OB_O_WEXCL`。その記録を読むキーも`OB_O_WEXCL`で開き、見出しと記録を同じ時点の中身として読む(書き直しで古いレコードが空になる途中を読まない)。締め出されたら5秒まで待つ | `br_store.cc`、Widevineの実身(`br_widevine.cc`) |
| 装置、窓、通信の実身だけを書く | 指定なし(ストレージの実身でないので排他の指定は効かない) | PCM Player、MPEG Player(音の装置と窓)など |
| POSIXの層(`objfs.c`)とファイルの形の読み書き | 指定なし(1回の`read`、`write`、`ftruncate`ごとに開き、Linuxのファイルと同じく、書く者がいても読め、書く者どうしも開ける) | `objfs.c`、かな漢字変換の学習のファイル(`kconv.c`)、マイクロスクリプトのファイルの命令(`ms_rtlib.c`) |

`OB_O_WEXCL`のキーが書いている間に開いた読むためのキーは、レコードを、最後の変更が残したとおりに読む。`ob_rpl_rec`で置き換えたレコードは古い中身か新しい中身のどちらかで、途中は見えない(新しい場所に書いてから1回の変更で差し替えるため。Linuxのファイルを`rename`で置き換えるのと同じ)。その場で書く`ob_wri_rec`は、書けた所まで見える。

設定の実身(機器の設定、ネットワークの設定、利用者の設定、Ｗｉ－Ｆｉの設定、システムの実身へのリンク)を書く者は、`OB_O_WEXCL`で開き、レコードを`ob_rpl_rec`で丸ごと置き換える。カーネルのウインドウシステム(`uconf.c`の`conf_open`)、Wi-Fi(`wifi.c`の`conf_wopen`)、キー配列の設定(`svc_gate.c`)、アプリのシステム環境設定、ネットワーク設定、ユーザ環境設定(`lib/libui/ui.c`の`ui_conf_open`)がそうする。読む者(アダプタの管理、Wi-Fiの管理、設定の監視)は、書く者がいても読める。書く者どうしは締め出し合うので、あとから来た書く者は、先の者が閉じるのを1秒まで待ってから開き、そのときの中身を読み直して1行を変え、置き換える。各書込みが1つの置き換えになる点は`rename`と同じで、待つので、ほかの者が同じ時に書いた別の行を消すこともない。

## 8.3 ストレージの実身

ファイルの実身はTSFSに格納される(第7章)。レコードは型(RT)とサブタイプを持つ。主な型は次のとおりである。

| 型 | 内容 |
| --- | --- |
| 0 | リンク(ウインドウの実身では、パネルからその部品へのリンク) |
| 1 | xmlTAD。文書、図形、仮身一覧 |
| 7、8 | 付箋 |
| 9 | 実行ファイル(プログラムの実身) |
| 10 | データボックス |
| 11 | フォント |
| 12 | 辞書 |
| 15 | 型を定めていないバイト列(ウインドウの配置など) |

実身「書体」、実身「壁紙」、プログラム箱のような箱は、レコード0のxmlTADにリンク(`<link id="UUID_0.xtad">`)を並べた実身である。`ob_lst_lnk`は箱のリンク先を書かれた順にすべて返し、名前を指定すればその名前のものだけを返す。`ob_fnd_lnk`はその名前の最初のリンク先を返す。名前は実身名か、メタデータの`tessronos.file.name`(ファイルから取り込んだ実身の元のファイル名)と比べ、英字の大文字と小文字を区別せず、拡張子は省略できる(`NotoSansJP-Regular`は`NotoSansJP-Regular.otf`にも一致する)。箱は呼んだプロセスの資格で読み、メタデータを読めない実身は実身名だけで比べる。読めるかどうかは`ob_acc_obj`で先に確かめ、読めない実身のメタデータは開きに行かない。フォントの`ts_face_find`、`ts_face_list`、デスクトップの実身「書体」と実身「壁紙」の読込み、プログラム箱の一覧(デスクトップ、システム環境設定、パッケージの展開、ファイル変換)、`xf_find`は、これで箱を読む。

### ボリュームをまたぐ仮身

仮身の行き先(`<link id>`)は、実身が仮身と同じボリュームにあるときは、これまでどおり実身のUUIDとレコードだけを書く(`実身のUUID_0.xtad`)。別のボリュームの実身を指す仮身は、外側の識別子を実身のUUIDの前に付け、「/」で区切る。

| 行き先 | `id` |
| --- | --- |
| 同じボリュームの実身 | `実身のUUID_0.xtad` |
| 別のボリュームの実身 | `ボリュームのUUID/実身のUUID_0.xtad` |
| 別のマシンの実身 | `マシンのUUID/ボリュームのUUID/実身のUUID_0.xtad` |

ボリュームのUUIDは、ネイティブのTSFSではスーパーブロックのボリュームのUUID(`mktsfs`、`tools/tsfs_py`、ディスク修復が読み書きする所)、FATの上の格納方式では格納先のディレクトリの`TSFSVOL.ID`に書いたUUID(初めて開いたときに作る)である。マシンのUUIDは、そのマシンのシステムのボリュームのUUIDとする。今はマシンの段は書式と読み取りだけで、自分のマシンのUUIDなら無いものとして扱い、ほかのマシンの実身を指す仮身は開かない。

前置きは書き手が付ける。デスクトップが記録を保存するとき(`om_store_save`)と、実身を複製するとき(`om_copy.c`、別のボリュームへの複製を含む)に、各仮身の行き先の実身が今どのボリュームにあるかを調べ、記録の実身と同じボリュームなら前置きを外し、違えばそのボリュームのUUIDを付ける(`om_link_fix`)。レコードを自分で書くアプリケーションのプロセス(基本図形編集、予定表、基本表計算)も、保存の前に同じことをする。ボリュームはSVCの`ob_ref_vid`で調べ、書き換えはデスクトップと同じソース(`tad_lnkvol.c`の`tad_lnk_vol_fix`、`tad_link.c`の`tad_lnk_vol_doc`)で行う。行き先が今どのボリュームにも無い仮身と、ほかのマシンを指す仮身はそのまま残す。仮身を読む所(`tad_link.c`の`T_VOBJ.tvol`と`tmach`、メニュー、TSFSの仮身表、FAT上の格納方式の参照数、ファイル変換、書庫とバックアップの作成と展開、マイクロカード、単語登録、`tools/tsfs_py`)は、どれも前置きを飛ばして実身のUUIDを読む(`ts_lnk_split`)。バックアップに保存するときは前置きを落とす。復元した実身は1つのボリュームに置かれるからである。

実身のUUIDは、取り付けたどのボリュームの間でも重ならない。UUIDを指定して実身を作るとき(`T_OBCRE.uuid`)、ほかのボリュームに同じUUIDの実身があれば`E_OBJ`になる。ボリュームのコピーのように、取り付けてあるボリュームと同じボリュームのUUIDを持つボリュームは取り付けない(7.6)。実身を探す順は取り付けた順で、最初はシステムのボリュームである。

ボリュームをまたぐ仮身は、指す側のボリュームでは数えない。ネイティブのTSFSは仮身表で、ボリュームにない実身を指す仮身を外部の仮身(`LK_F_EXTERNAL`)として持ち、数えない。FATの上の格納方式の数え(`om_store_relink`)も、記録の実身と同じボリュームの行き先だけを数える。その代わりに、指される側のボリュームが「ほかのボリュームからの参照」の記録を持ち、指される実身の参照数にはこの記録を通して数える(`peripheral_kernel/obj/obxref.c`)。ほかのボリュームからしか指されていない実身も、屑実身にはならない。

記録は、指される側のボリュームの実身の1つで、スーパーブロックが指す(`T_TSFSBLK_SB.xref_uuid`、バイト400からの16バイト)。名前は「ほかのボリュームからの参照」で、編集も削除もできない。最上位の実身と同じく、スーパーブロックが指すことを固定1つとして数え、屑実身にならない。記録のレコード0はxmlTADで、ほかのボリュームの仮身1つにつき次の`<link>`を1つ持つ。

```
<link id="指される実身のUUID" xref-volume="指す側のボリュームのUUID" xref-object="指す側の実身のUUID"/>
```

同じ実身から同じ実身への仮身が2つあれば、同じ行が2つ並ぶ。TSFSはこのレコードからも仮身表を作るので、指される実身の参照数は1つずつ増え、ディスク修復の隠れ屑実身の判定ではこの記録からたどり始める(7.5)。参照数の数え方そのものは変わらず、ボリュームの中の仮身表と固定だけから数えるので、ディスク修復の検査と食い違わない。1つの記録が持てる行は、1つの実身の仮身表の上限と同じ1024である。それを超える仮身は記録されず、コンソールにそう示す。この記録の形を知らないバージョンのカーネルがスーパーブロックを書くと、指す欄は0に戻る。そのときは記録の実身は固定のまま残り、次に記録が要るときに新しく作られる。

記録は次のときに動く。

- 仮身の作成と削除、実身の複写と移動、削除と回収: ネイティブのTSFSは、仮身表を作り直すとき(実身を閉じたとき、マウント時)と、削除や回収で実身の仮身を手放すときに、外部の仮身の増減を待ち行列に積む(`ts_obj_xq_take`)。オブジェクト層は、実身を閉じたときと削除したときにこれを取り出し、行き先の実身があるボリュームの記録を1行ずつ増やすか減らす(`knl_obxref_move`)。FATの上の格納方式の実身からの仮身は、`om_store_relink`が直接記録を動かす。行き先が同じボリュームだったと分かった仮身と、記録自身の仮身は動かさない。
- 行き先のボリュームが切り離されている間の変更: 行き先の実身がどのボリュームにも無ければ、記録は動かさない。ボリュームを取り付けたとき(`knl_obfile_attach`)に、そのボリュームと取り付けてあるほかのネイティブのボリュームの組ごとに、指す側の全実身の仮身表から外部の仮身を数え、指される側の記録のうちその指す側のボリュームからの行を、数えたとおりに書き直す(`knl_obxref_sync`)。指す側のボリュームが切り離されている間に、指される側で何かが変わっても、指す側を取り付けたときに同じく合わせる。取り付けていないボリュームからの行は、そのまま残す。待ち行列があふれて増減を失ったときは、取り付けてある全ボリュームについて同じ突き合わせをする。
- ディスク修復: 記録を、取り付けてあるネイティブのボリュームの仮身表と突き合わせ、行き先の無い行、指す側の実身の無い行、数の食い違い、記録の無い仮身を報告し、修復で書き直す(`knl_obxref_check`、7.5)。

記録の更新は、記録の実身のレコードを書き換えて閉じることで行い、参照数はTSFSが仮身表の作り直しで動かす。記録の書換えと指す側の仮身表の変更は1つのトランザクションではないので、その間に電源が切れると食い違いが残るが、次にボリュームを取り付けたときの突き合わせか、ディスク修復が直す。記録はネイティブのTSFSのボリュームにだけ置くので、FATの上の格納方式の実身を指す仮身は記録しない。

ディスクを接続したときにデスクトップに置く仮身が指す最上位の実身(11.26)は、ボリュームが保持するので屑実身にはならない。

行き先の実身が見つからない仮身(虚身)は、薄く描き、開いた仮身の中は斜線にする。開こうとすると、前置きのボリュームが取り付けられていなければ「ボリューム「名前」が接続されていません」と示す。名前は、起動してから取り付けたボリュームのラベルか、知らなければUUIDの先頭と仮身の名前である。別のボリュームの実身を指す仮身は、左上の角を三角に塗る(デバイス間接参照)。

TADjs Desktopは、`id`の拡張子と末尾の`_数字`を除いた残りを実身のUUIDとし、そのUUIDの`.json`をデータのフォルダから読む(`js/real-object-system.js`の`extractRealId`と`loadRealObject`)。前置きの付いた`id`では、「ボリュームのUUID/実身のUUID」がそのまま名前になってフォルダの下の別の場所を指すので、実身が見つからないという誤りになり、その仮身は開けない。仮身の要素と`id`の文字列はそのまま残り、ほかの仮身や記録は壊れない。TessronOSで書き出すTADjs形式(ファイル変換)は、書き出す実身を1つのフォルダに集めるので、同じボリュームの実身として前置きなしで書く。

メモリの実身は揮発性で、共有メモリとグローバル名に使う。`OB_F_GLOBAL`を指定して作成した実身は、`ob_fnd_nam`で名前から検索できる。メモリの実身のレコードを`ob_map_rec`でプロセスの共有メモリ領域にマッピングすると、同じ物理ページが、マッピングしたすべてのプロセスから同じアドレスで見える。

## 8.4 デバイスの実身

デバイスの実身は、登録されたデバイスごとに存在する。レコードの読み書きがデバイスの読み書きになり、属性にはデバイスの種類、容量、マウントの状態が現れる。このほか、次の仮想デバイスがある。

| 実身 | 内容 |
| --- | --- |
| 時計 | 現在時刻 |
| デバイス一覧 | すべてのデバイスへの仮身を持つ。どのデバイスで起きたイベントもここに届くので、これ1つを監視すればすべてのデバイスの接続と切断が分かる |
| システム(`SYSDEF_SYSTEM`) | マシンそのもの。下表のレコードを持つ |

登録されたデバイスの実身の属性には、ドライバが割込みを伝えた装置なら`"irq":{"cpu":名指しのCPU(0はなし),"intno":[割込み番号…],"on":[今受けるCPU…]}`が加わる。属性に`{"irq":{"cpu":2}}`と書くと、その装置の割込みを全部PRC 2に向け、0と書くとシステムの決め方(雑務のCPU)に戻す(4.5.1)。書いた値はデバイス箱の項目(`irqcpu`)に残り、次の起動でも当たる。実時間のCPUを名指しすると`E_OBJ`になる。属性を書くには`OB_OP_ATRWR`が要る。

デバイス管理に登録しないデバイスも、デバイスマネージャが実身として見せる。デバイスを扱うモジュールが名前とレコードの読み書きの関数(`T_OBDVOPS`)を渡して実身を加え(`knl_obdev_add`)、デバイスマネージャがUUIDを与え、デバイス一覧に載せ、保護を付け、接続と切断を`OB_E_ATTACH`、`OB_E_DETACH`で通知する。UUIDは名前ごとにデバイス箱に記録するので、同じポートに差し直したデバイスは同じ実身になる。どの実身もレコード0に説明のxmlTADを持ち、関係する実身への仮身をそこに置く。

| 実身 | サブタイプ | 名前とUUID | レコード |
| --- | --- | --- | --- |
| 乱数 | `OB_S_CHAR` | 固定のUUID(`ob_uuid_random`)、「乱数」 | 1　読むと乱数のバイト列、書くと生成器に混ぜる |
| 入力 | `OB_S_INPUT` | 固定のUUID(`ob_uuid_input`)、「入力」 | 1　イベント(`T_HIDEV`)、2　ポインタの位置と接続数、3　入力の属性(`T_HIDATTR`) |
| キーボード、ポインタ | `OB_S_INPUT` | HIDのインタフェースごと。「hid」とUSBのポート(`hid0-8.3`)。x64ではUSBでないものも:i8042の「ps2kbd」「ps2aux」、HID over I2Cの「hidi2c0」… | 1　そのデバイスのイベント、2　種類、ベンダとプロダクト、ポート、絶対座標か相対座標か |
| 電池、ACアダプタ、蓋、電源ボタン | `OB_S_POWER` | x64のACPI。「battery0」「battery1」「acpower」「lid」「powerbutton」 | 1　状態の「キー 値」の行(電池はPRESENT、STATE(discharging、charging、full、notcharging)、CRITICAL、PERCENT、REMAINING、FULL、DESIGN、RATE、VOLTAGE、UNIT、MODELなど、ACアダプタはONLINE、蓋はOPEN、電源ボタンはPRESSES) |
| 画面 | `OB_S_DISPLAY` | 固定のUUID(`ob_uuid_display`)、「画面」 | 1　モード(`SIZE`、`DEPTH`、`MODES`、`DRIVER`、`SCALE`、`VIEW`、`SCALES`、置き方を選べる画面では`FIT`など)、2　ピクセル |
| GPIOのバンク | `OB_S_GPIO` | Raspberry Pi 5だけ。`gpio-aon0`、`gpio-aon1`、`gpio-rp1-0`〜`gpio-rp1-2` | 1　ピンごとに「ピン 方向 値 プル」の行 |
| USBデバイス | `OB_S_USB` | ハブを含むデバイスごと。「usb」とコントローラ、ルートポート、経由するハブのポート(`usb0-8.3`) | 1　VID、PID、クラス、速度、ポート、製品名 |

入力の実身のレコード1は、読むと、そのキーで前回読んだ後に届いたイベントのコピーを返す。ウインドウマネージャが受け取るイベントを奪わないので、何人が読んでもウインドウには全部が届く。書くと、デバイスが報告したのと同じようにイベントを入れる。試験とデスクトップの操作試験(`dtuitest.c`)は、この書込みで入力を与える。キーボードとポインタの実身は、それぞれ自分のUSBデバイスの実身と入力の実身への仮身を持つ。

画面の実身のレコード1に「幅x高さ」を書くと、画面のドライバを通して解像度を変える。QEMUでは`bochs-display`(x64では標準VGA)のモードを、Raspberry Pi 5ではファームウェアにその大きさのフレームバッファを求め(ファームウェアが断ったときは元の大きさのまま)、x64のIntelの内蔵グラフィックスではプレーンとスケーラを変える(10.2.2)。x64では、選べる大きさ(`MODES`)とドライバの名前(`DRIVER`)をドライバが答え、パネルと縦横の比が違う大きさの置き方を選べる画面では`FIT`の行(`aspect`か`stretch`)が加わる。書くときは「幅x高さ aspect」のように大きさの後に置き方を書ける。「150%」と書くと表示の倍率を変え(大きさの後に書いてもよい)、`SCALE`が使っている倍率、`VIEW`が論理ビューの大きさ、`SCALES`がその解像度で使える倍率を答える(10.2.3)。モードが変わると、画面の実身のレコード1とシステムの実身のレコード3に`OB_E_CHANGE`を通知する。

GPIOのバンクのレコード1に「ピン 方向 値 プル」の行を書くと、そのピンを設定する(`-`の欄は変えない)。方向は`in`、`out`、チップの機能に渡したピンは`alt<番号>`で表す。カーネルのドライバが使うピン(SDカードの挿抜検出、EthernetのPHYのリセット、ヘッダのUART、サウンドが使うI2S)は行末に`kernel`と付き、書き込むと`E_BUSY`になる。入力のピンの値が変わると、レコード1に`OB_E_CHANGE`を通知する。通知の`code`がピン、`x`が値である。基板のLEDも、実身ができた後はカーネルがこのバンクの実身を通して点灯させる。

USBデバイスの実身は、ぶら下がるハブの実身、提供する機能の実身(ディスク、サウンドデバイス`snda`、カメラデバイス`cama`、キーボードとポインタ)への仮身を持ち、ハブはその先のデバイスへの仮身を持つ。

サウンドデバイスの実身(`OB_S_SOUND`)は、レコードがデバイスのデータ番号である。レコード1がPCM(データ番号0。書くと鳴り、読むと録音したものが得られる)、2から23が属性(`OB_SND_INFO`から`OB_SND_VOL`の並び)、24が出力先の一覧(`OB_SND_OUTS`)、25が選んだ出力先と鳴らしている出力先(`OB_SND_OUTSEL`)、26がミキサーの全体とプログラムごとの音量(`OB_SND_MIX`)、27が音量と消音を書く所(`OB_SND_MIXSET`)である。24と25は読むだけで、出力先はシステムの実身のレコード8で選ぶ(6.5.1)。音量はだれでも27に書ける(6.5.6)。

カメラデバイスの実身(`OB_S_CAMERA`、ユニットごと)は、レコードがデバイスのデータ番号である。レコード1がフレーム(`OB_CAM_FRAME`、データ番号0)、2が状態(`OB_CAM_INFO`)、3がモードの一覧(`OB_CAM_MODES`)、4が選んだモード(`OB_CAM_MODE`、書くと選ぶ)、5が流れ(`OB_CAM_STREAM`、1を書くと流し、0で止める)、6が数(`OB_CAM_STAT`)である(6.6)。どれも先頭から丸ごと読み書きする。サウンドデバイスやシリアルポートと同じくプログラムが使うものなので、誰でも読み書きできる(`rw-rw-rw-`)。ブラウザのカメラ(14.4.11)はこれを使う。

システムの実身のレコードは「キー 値」の行からなるテキストである。読み出せばマシンの現在の状態が分かり、書き込めばマシンに指示できる。

| レコード | 読出し | 書込み |
| --- | --- | --- |
| 1　情報 | 名前、バージョン(`VERSION`)、ビルド日時、機種、プロセッサ(`CPU`)、動いているCPUの数(`CPUS`。x64ではコアの数`CPU_CORES`とパッケージの数`CPU_PACKAGES`も)、CPUの役割(`CPU_CHORE`、`CPU_RT`)、割込みを伝えた装置ごとの割込みと受けるCPU(`IRQ`、4.5.1)、メモリ | |
| 2　電源 | 実行できる操作 | `OFF`で電源を切る、`RESTART`で再起動する |
| 3　画面 | 画面の実身のUUIDと、そのレコード1(解像度、色深度、選択できる解像度) | |
| 4 USB | USBデバイスの実身ごとに、そのレコード1から作る行と実身のUUID | |
| 5　配色 | 配色の一覧と現在の配色 | 番号で配色を切り替える |
| 6　壁紙 | 現在の壁紙 | 画像の実身のUUIDと配置方法で壁紙を変える |
| 7　ネットワーク | IPアドレス、サブネットマスク、ゲートウェイ、DNS、リンク状態、使用中のソケット数。IPv6の使い方(`IPV6`)、アドレスごとの種類と有効期間・推奨期間の残り(`ADDRESS6`)、デフォルトルータ(`GATEWAY6`)、DNSサーバ(`DNS6`)(9.3.4) | |
| 8　サウンド | 鳴らしている出力先(`OUTPUT`)、選んだ出力先(`SELECT`)、サンプリングレート、チャネル数、出力先ごとのID、種類、フラグ、名前(`OUT`、`OUT_KIND`、`OUT_FLAGS`、`OUT_NAME`、6.5.1)、出力を止めずに流し続けるか(`KEEP`、6.5.5) | `SELECT`と出力先のIDで出力先を選ぶ。`PLAY`と音の名前でシステムの音を鳴らす。`KEEP 1`か`KEEP 0`で流し続けるかを決める |
| 9　ハードウェアの状態 | SoCの温度(`TEMPERATURE`、`TEMPERATURE_MC`)、ARMのクロック(`ARM_HZ`)、V3Dのクロック(`V3D_HZ`)、Raspberry Pi 5ではファンの強さと駆動の方式(`FAN_LEVEL`、`FAN_DRIVE`、`FAN_SPEED`、3.7)。CPUのクロックの上限とファームウェアが許す範囲とファンによる下げ(`ARM_LIMIT_MHZ`、`ARM_MIN_HZ`、`ARM_MAX_HZ`、`ARM_HEAT_HZ`)、電源とクロックの状態(`THROTTLED`、`UNDERVOLT`、3.9)、ウォッチドッグの秒数と動作(`WATCHDOG_S`、`WATCHDOG_HW`、3.8)。Raspberry Pi 5と4ではファームウェアにメールボックスのプロパティタグ(温度`0x00030006`、クロック`0x00030002`、範囲`0x00030004`と`0x00030007`、状態`0x00030046`)で問い合わせ、QEMUでは温度とクロックを`unknown`とし、上限とウォッチドッグだけを示す | |

## 8.5 プロセスと通信の実身

実行中のプロセスは実身として参照でき、`OB_E_EXIT`で終了を通知する。プロセスの番号は、メタデータの`tessronos.process.pid`で読む(`ob_get_atv`)。実身名「process 番号」は表示のためのもので、番号を名前から読まない(コンソール、マイクロスクリプト)。プロセスの実身のレコード0は状態を表すxmlTADで、実行しているプログラムの実身と、そのプロセスが開いているソケットの実身への仮身を持つ。

通信の実身には、メッセージキュー(`OB_S_QUEUE`)とソケット(`OB_S_SOCKET`)がある。メッセージキューはレコード0の書込みで1つのメッセージを送り、読出しで1つを受け取る。プロセスがウインドウのイベントを受け取る受信キューにも使う。

ソケットは、`so_socket`か`so_accept`で作られてから、`so_close`かプロセスの終了で閉じられるまで実身である(9.2.1)。所有者は作ったプロセスが代理するユーザで、名前は`socket 3 (process 12)`のようになる。レコード0は説明のxmlTADで、所有するプロセスの実身への仮身を持つ。レコード1がデータで、読むと受信し、書くと送信する。メッセージキューのレコード0と同じく、データがないときや送れないときは待ち、キーを`OB_O_NOWAIT`で開いていれば`E_TMOUT`を返す。メタデータの`socket`に、番号、プロセス、ファミリ、種類、プロトコル、両端のアドレスとポート、状態が現れる。実身を削除するとソケットが閉じる。

## 8.6 保護

保護情報はすべての種類の実身に同じ形式で付く。

| 項目 | 内容 |
| --- | --- |
| 所有者、グループ | ユーザとグループのUUID |
| モード | 所有者、グループ、その他のそれぞれにr、w、x |
| 属性 | 書込み禁止、削除禁止 |
| ACL | ユーザかグループごとに許可する操作 |
| レコードマスク | レコードごとに許可する操作を制限する |

rwxは次の操作ビットに展開して判定する。

| ビット | 内容 | rwx |
| --- | --- | --- |
| `OB_OP_READ` | データレコードを読む | r |
| `OB_OP_ATRRD` | 属性を読む、レコードの一覧を取得する | r |
| `OB_OP_WRITE` | データレコードを書く、切り詰める | w |
| `OB_OP_RECORD` | レコードを追加する、削除する | w |
| `OB_OP_ATRWR` | 属性を書く | w |
| `OB_OP_LINK` | 参照数を増減する | w |
| `OB_OP_DELETE` | 実身を削除する、プロセスを終了させる | w |
| `OB_OP_EXEC` | プログラムを実行する、デバイスを制御する | x |
| `OB_OP_PROT` | 保護情報を変更する | 所有者には常に許可 |

判定は次の順で行う。管理者であればすべてを許可する。そうでなければ、所有者、グループ、その他のどれに該当するかでrwxを選び、ACLで許可された操作を加え、属性とレコードマスクで制限する。

レコードマスクに`OB_OP_EXEC`を含むレコードは、`OB_OP_EXEC`を持つキーでなければ読み書きできない。人が見ている画面のピクセルや、人が打ったキーのように、デバイスの制御に等しいレコードに使う。デバイスの実身の既定の保護では、xは管理者だけが持つ。

| 実身 | 所有者、グループ | モード | xが要るレコード |
| --- | --- | --- | --- |
| 乱数 | システム、管理者 | `rw-r--r--` | なし |
| 入力、キーボード、ポインタ | システム、管理者 | `rw-r--r--` | 1(イベントの読み書き) |
| 画面 | システム、管理者 | `rw-rw-r--` | 2(ピクセルの読出し) |
| GPIOのバンク | システム、管理者 | `rw-rw-r--` | なし(グループと管理者が書ける) |
| USBデバイス | システム、管理者 | `r--r--r--` | なし |
| ディスク | システム、管理者。ACLで利用者のグループに属性の読出しを与え、システムが何も使っていないUSBの媒体(`uda`、`uda0`など)は読み書きも与える | `rw-r-----` | なし |
| システム | システム、管理者。ACLで利用者のグループにも書込みを与える(書けるのは配色、壁紙、電源のレコードだけ) | `rw-rw-r--` | なし |
| ソケット | 作ったプロセスのユーザ、その最初のグループ(カーネルのソケットはシステム、管理者) | `rw-------`(変更できない) | なし |

USBの媒体を一般の利用者にも開かせるのは、ファイル変換やバックアップで人が自分の媒体を読み書きするためである。媒体のどこかのパーティションがネイティブのボリュームとして取り付けられているとき、または`/media`の外にマウントされているとき(システムがそこから起動したときなど)は、その媒体のブロックは管理者だけのものに戻る。ネイティブのボリュームの実身は実身ごとの保護を持ち、ブロックを直接読み書きできるとその保護を迂回できるからである。

ボリュームには保護ドメインを設定できる。ドメインの保護は、そのボリュームのすべての実身の保護に重ねて適用される。

秘密を持つ実身は、所有者をシステム、グループを管理者、モードを`rw-------`にし、ACLを付けない。システム(カーネルのタスク)と管理者だけが読み書きでき、ふつうの利用者のプロセスは開けない。管理者は判定で何でも許されるので、グループに読み書きを与えても効き目は変わらない。Wi-Fiの設定の実身「Ｗｉ－Ｆｉの設定」(`SYSDEF_CONF_WIFI`)がこれで、保存したネットワークの鍵を持つ。この実身を書くのはカーネルのWi-Fiの管理だけで、プログラムはWi-Fiのデバイスの実身(wlan0)に依頼を書く。保存したネットワークは保存した利用者のもので、依頼は書いたプロセスの利用者のネットワークにだけ効き、wlan0のレコード1もその利用者のネットワークだけを見せる。鍵はパスフレーズではなくPMKで持ち、どのプロセスにも渡さない(利用者自身のネットワークの鍵も)。LinuxのNetworkManager(rootだけが読める600のファイルと、利用者のキーリング)と比べてこう決めた理由は09章9.6.6にある。

TADjs Desktopから持ってきた実身は保護情報を持たない。その場合は所有者なしとし、メタデータの`readable`、`editable`、`deletable`からモードと属性を決める。

実身を介さずに系全体に効くシステムコール(時刻とタイムゾーン、ネットワークインタフェース、ボリューム、外観設定テーブル、キー配列)も、この保護で判断する。SVCゲートの権限の表(付録A)が、呼出しごとに、管理者であるか、関係する実身(時計、暦、機器の設定)に必要な操作ビットを持つかを`knl_ob_permit_on`で確かめる。たとえば暦の実身のACLで`OB_OP_ATRRD`と`OB_OP_ATRWR`を与えたユーザは、管理者でなくてもタイムゾーンを変えられる。

## 8.7 ユーザとログイン

ユーザとグループはファイルの実身で、メタデータの`tessronos.user`、`tessronos.group`で定義する。パスワードはPBKDF2-HMAC-SHA256のハッシュで保存し、平文は保存しない。ユーザの実身として認めるのは、所有者がシステムかそのユーザ自身のものだけである。プロセスは資格情報(ユーザと所属グループの一覧)を持ち、`ob_login`で資格情報を別のユーザに切り替える。

固定のUUIDを持つユーザとグループは次のとおりである。

| 名前 | UUID | 内容 |
| --- | --- | --- |
| システム | `ob_user_system` | カーネルのタスクとデスクトップ |
| 管理者(グループ) | `ob_group_admin` | このグループに属するユーザは管理者で、すべての操作を許される |
| 利用者 | `ob_user_person` | どの利用者もログインしていないときに、デスクトップから起動したプログラムが代理するユーザ。パスワードを持たず、ログインには使えない |
| 利用者(グループ) | `ob_group_users` | 一般の利用者すべてが属するグループ。系の設定のうち人が自分で変えてよいものは、このグループに書込みを与える |
| 管理者 | `ob_user_admin` | 管理者のパスワードを持つアカウントで、管理者と利用者のグループに属する。初めて必要になったときに、カーネルが実身「システム」と同じボリュームに作る。所有者はシステム、モードは`rw-------` |

プロセスの資格情報は、プロセスを作ったものによって次のように決まる。

| 作ったもの | 資格情報 |
| --- | --- |
| カーネルのタスク(`ts_cre_prc`。初期プロセス、試験) | システム |
| デスクトップ(プロセスの実身を`ob_cre_obj`で作る。カーネルが`TS_PRC_USER`を付ける) | デスクトップにログインしている利用者の資格から管理者のグループを除いたもの。ログインしていなければ利用者 |
| デスクトップが自分の仕事のために動かす、系が信頼するプログラム | システム |
| プロセス | 親の資格情報。親が一時的に得た管理者の権限は受け継がない |

デスクトップ自身と、カーネルのタスクとして動く系の処理(ネットワークの時刻合わせ、デバイスのドライバなど)は、システムの資格のままである。デスクトップへのログインは`knl_ob_session`で行い、それ以降にデスクトップが起動するプログラムがそのユーザの資格で動く。ログインした利用者が管理者のグループに属していても、プログラムには管理者のグループを渡さない。管理者の権限は、必要なときに8.7.2の手順で一時的に得る。

### 8.7.1 系の設定を変えるプログラム

系の設定を変える正当なプログラムは、変えるものに応じて次の3つの方法のどれかで通す。

| 方法 | 使う所 | 理由 |
| --- | --- | --- |
| 一般の利用者に書かせる(実身の保護) | 自分のWi-Fiの接続の保存、変更、削除と、接続と切断(wlan0への依頼をWi-Fiの管理が書いたプロセスの利用者で受ける。鍵はどのプロセスにも渡さない、09章9.6.6)、ユーザ情報(ユーザ環境設定の項目、使用者名)、実身「システムの音」のブザー音・押下音・離し音、暦のタイムゾーン、機器の設定(キー配列、配色、壁紙、画面の解像度、キーボードの種類、CPUのクロックの上限、ウォッチドッグ)、システムの実身の配色・壁紙・電源、実身「ファイル変換」(FTPの接続先の設定)、システムが何も使っていないUSBの媒体 | マシンの前にいる人の使い勝手に関わり、変えても他の利用者のデータやマシンの安全に影響しないもの。毎回パスワードを尋ねると使いにくい。電源は、マシンの前にいる人なら電源スイッチでも切れる |
| 管理者のパスワードを尋ねて一時的に昇格する | 時刻(`dt_settime`など)、ネットワークの設定(IPアドレス、DNS、ゲートウェイ、時刻サーバ)、ネットワークの開始(`so_dhcp_start`)、アプリケーションの追加と削除、USBの媒体以外のディスクを開くこと、ボリュームの取り付けと取り外し、保護ドメイン | ログの時刻、TLSの証明書の検証、名前解決、実行されるプログラム、他の利用者のデータが変わり、系全体の安全に関わるもの |
| 系が信頼するプログラムにシステムの資格を与える | 実時間メディアの補助プログラム(`SYSDEF_PROG_RTMEDIA`) | デスクトップが実時間制御TADの再生のために起動し、デスクトップが作ったチャネルとメモリの実身を使う補助プログラム。人が直接起動するものではない |

一般の利用者に書かせるものは、システムのボリュームの定義実身(`etc/def`)のACLで利用者のグループに操作を与えてある。SVCゲートの権限の表(付録A)は、ユーザ情報、機器の設定、暦の実身に必要な操作ビットを持つかで判断するので、表を変えずにこの保護で通る。外観設定テーブルの書換え(`wm_set_look`)は、ユーザ環境設定の項目ならユーザ情報、ウインドウの見た目の項目なら機器の設定に書き込めることを求め、それ以外の項目は管理者だけに許す。

CPUのクロックの上限(`CPU_MHZ`、3.9)とウォッチドッグ(`WATCHDOG`、3.8)はマシンの安定に関わるが、管理者のパスワードによる昇格を使わず、一般の利用者に書かせる。理由は次のとおりである。上限はファームウェアが許す範囲に丸めるので、定格を超えるクロックにはできず、ファンによる下げとファームウェア自身の保護は上限と関係なく働く。ウォッチドッグを切っても、止まったマシンが自動で再起動しなくなるだけで、データや他の利用者には影響しない。どちらも、マシンの前にいる人なら電源ボタンや電源の抜き差しで同じ結果を得られる。また、高いクロックで落ちるかどうかは使う電源によるので、利用者はクロックを変えては試し、落ちない値を探すことになる。そのたびに管理者のパスワードを尋ねると使いにくい。さらに、この2つの行は配色や壁紙と同じ機器の設定の実身にあり、カーネルは誰が書いたかを区別せずに反映するので、管理者だけに許すには実身を分ける必要があり、すでに配ったマシンの設定と食い違う。

信頼するプログラムは、プログラム実身のメタデータに`tessronos.program.trusted`(`true`)を持ち、実身「システム」と同じボリュームにあり、所有者がシステムで、管理者以外が書き込めず保護も変えられないものに限る(`knl_ob_trusted`)。印だけを持つ実身、別のボリュームにある実身、保護を緩めた実身は信頼されない。システムの所有の実身を作れるのは管理者だけなので、印を付けられるのも管理者だけである。以前はカーネルの中に固定のUUIDの表を持っていたが、実身の側の印と保護で決める形にした。プログラム箱にある小物には使わない。人が起動する小物にシステムの資格を与えると、マシンの前にいる誰もがパスワードなしで時刻やネットワークを変えられるからである。

### 8.7.2 一時的な昇格

デスクトップから起動したプログラムが、管理者だけに許された呼出しで`E_OACV`を受けると、デスクトップに`DT_RQ_ADMIN`を依頼する(`ts_admin_ask`、`lib/libts/ts_admin.c`)。依頼の`name`は行おうとしている操作である。デスクトップは自分のパネルを自分のウインドウの中央に出し、キーボードの入力をそのウインドウに移してから、「「プログラム名」が管理者の権限を求めています」と操作を示して、管理者のパスワードを伏せ字の欄(`WM_PT_SECRET`)で尋ねる。パスワードはデスクトップの中で確かめ(`knl_ob_admin_check`)、プログラムには渡らない。ログインしている利用者が管理者のグループに属していればその利用者のパスワードを、そうでなければ管理者のアカウントのパスワードを求める。

正しければ、カーネルがそのプロセスの資格情報に管理者のグループを加える(`knl_ob_adm_give`)。プログラムは呼出しをやり直し、終わったら`ob_end_adm`で権限を返す。返さなくても`OB_ADM_MS`(2分)で失われ、プロセスが終われば消え、子プロセスには渡らない。3回間違えると`E_OACV`、パネルを取り消すと`E_ABORT`で応答する。権限を得られなかったプログラムは落ちずに、自分のパネルかメッセージ行(`ts_no_right`)で「〜する権限がありません」と示し、ほかの設定はそのまま続ける。アプリケーションの追加と削除の依頼(`DT_RQ_INSTALL`、`DT_RQ_REMOVE`)を管理者でないプロセスから受けたときも、デスクトップが同じパネルで尋ねる。デスクトップが自分のメニューで行う操作のうち管理者だけに許すもの(ディスク操作でシステムのディスクに区画を作る、システムのボリュームを広げる、11.26)も、同じパネルで「「ディスク操作」には管理者の権限が要ります」と尋ねる(`dt_admin_self`)。このときはパスワードを確かめるだけで、どのプロセスにも権限を与えない。

パネルをプログラムのウインドウの上に出さないのは、そのウインドウの部品にもキーが届き、プログラムがパスワードを読めてしまうからである。パネルは、`dt_pn_run`で実際のキーボードとポインタの入力だけを受け、その間はプロセスからの依頼を処理しない。プログラムが依頼(`DT_RQ_TYPE`)でパスワードの欄に文字を入れることはできない。画面のキーボードのキー(`wm_key_put`)は、人がその画面のキーボードを押した直後にしか入らない。

画面の操作は`tools/tests/ui_admin.steps`と`tools/tests/ui_userenv.steps`を`tools/ui_run.py`で実行して確かめる(12.4)。`ui_admin.steps`は、デスクトップから開いたネットワーク設定で自ホスト名を変えて更新し、管理者のパスワードが未設定の試験用ディスクで最初のパスワードを決めるパネルが出て、2回入れると設定が書き込まれること、次に誤ったパスワードが断られて正しいパスワードで書き込まれること、最後にパネルを取り消すと書き込まれないことを見る。`ui_userenv.steps`は、ユーザ環境設定で使用者名とタイムゾーンを変え、時刻サーバも変えて〈更新して終了〉を押し、時刻サーバのパスワードのパネルを取り消しても、使用者名とタイムゾーンは尋ねずに保存され、開き直すと残っていることを見る。

### 8.7.3 管理者のパスワードが未設定のマシン

管理者のアカウントはパスワードなしで作られる。パスワードが未設定のマシンで昇格が求められると、デスクトップのパネルが「管理者のパスワードがまだ決まっていません」と示し、新しいパスワードを2回入力させて設定し(`knl_ob_admin_set`)、そのまま権限を与える。この方法で設定できるのは最初の1回だけで、以後の変更はパスワードを知っている者が行う(`ob_set_pwd`は本人か管理者だけに許される)。最初に昇格を求めた人が管理者のパスワードを決めることになるので、マシンを他人に渡す前にはパスワードを決めておく。

### 8.7.4 デスクトップが作る実身

デスクトップのタスクは、利用者の操作で作る実身(原紙からの新規作成、複製、新版)を利用者のものとして作る(`knl_ob_make_for_person`)。保護を指定せずにファイルの実身を作ると、所有者がログインしている利用者(いなければ利用者)、グループが利用者、モードが`rw-r--r--`になり、利用者の資格で動くプログラムがその実身を開いて書き換えられる。ほかのカーネルのタスクが作る実身はシステムのものである。デスクトップへの依頼を受けるチャネル(`DT_REQ_NAME`)は、どのプログラムも書けるように所有者がシステム、モードが`rw--w--w-`である。

プロセスが作った実身の既定のモードは`rw-r--r--`で、所有者にもxを与えない。プログラムは自分のウインドウやパネルを`OB_OP_R | OB_OP_W`で開き、xを含む`OB_OP_ALL`では開かない。

デスクトップが補助のプロセスに渡すために作るチャネルとメモリの実身(実時間制御TADの再生で、映像を復号するMPEG Playerと実時間メディアに渡す指示と答えのチャネル、フレームと音のメモリ、15.6)は、ログインしている利用者(いなければ利用者)の所有、モード`rw-------`で作る。MPEG Playerはパッケージで入るプログラムで系が信頼するものではなく、利用者の資格で動くからである。実時間メディアはシステムの資格で動くので、利用者のものも開ける。

権限の不足で断られた呼出しを探すために、`UITEST=1`か`OACVLOG=1`でビルドしたカーネルは、プロセスの呼出しが`E_OACV`で断られるたびに、プロセスの名前、実身のUUIDと種類と名前、求めた操作ビットと許されている操作ビットを`!OACV!`で始まる1行でコンソールに出す(`knl_ob_deny_note`)。出すのは、実身を開くとき、キーで許されていない操作をしたとき、実身の削除や参照数の増減、プログラムの起動、保護の変更、ボリュームの取り付けと取り外しと保護ドメイン、SVCゲートの権限の表(付録A)、外観設定テーブルの書換えで断られたときである。同じ行は直前の16件に含まれる間は繰り返さない。`tools/tests/ui_user_apps.steps`(12.4)は、プログラム箱のすべてのプログラムを利用者の資格で起動し、この行が出ないことを確かめる。各プログラムの画面の試験のスクリプトも、最後に`absent !OACV!`で同じことを確かめる。管理者の権限を求める操作を試験する`ui_admin.steps`と`ui_userenv.steps`では、ネットワーク設定の実身を書くための開きが一度断られる行が出るのが正しい。

実身の一覧を作るプログラムは、項目の実身を開いて読めるかを試さない。Unixの`ls`が項目ごとにファイルを開かず、ディレクトリから名前を読み、権限を`stat`のモードで知るのと同じく、名前と種類と大きさは`ob_ref_obj`で、読めるかどうかは`ob_acc_obj`で知る。`ob_acc_obj`は`ob_opn_obj`と同じ判定で、実身を開かずに`E_OK`か`E_OACV`を答える(`access(2)`に当たる)。問い合わせであって断られた操作ではないので、`!OACV!`の行は出さない。読めない実身を開いて断られたときの行は、保護の記録としてそのまま出す。コンソールの`ls`(11.29)と`ob_lst_lnk`の名前での比較は、これで読めない実身を開かずに済ませる。

## 8.8 イベント通知

`ob_ntf_evt`で、ある実身の特定のレコードで起きたイベントを、通信の実身かストレージの実身へ通知させられる。ウインドウの入力、部品の操作、ストレージの実身の変更、デバイスの接続と切断は、すべてこの1つの仕組みで受け取る。

| イベント | 内容 | 発生する実身 |
| --- | --- | --- |
| `OB_E_PRESS`、`OB_E_RELEASE` | ボタンを押した、離した。ほかのウインドウの上や何もない所で離したときは、押したウインドウにも、その作業領域から見た位置(作業領域の外になる)で離したことを通知する。離した先のウインドウには通知しない | ウインドウ、部品 |
| `OB_E_MOVE`、`OB_E_WHEEL` | ポインタが動いた、ホイールが回った | ウインドウ |
| `OB_E_KEY` | キー入力。要求に`OB_N_KEYUP`を付けると、キーを離したことも`mods`に`OB_KEY_UP`を立てて通知する。入力の対象にならないウインドウ(`WM_ATTR_NOFOCUS`)では、要求に`OB_N_KEYSEEN`を付けると、どのウインドウに宛てたキーも押したときと離したときに`mods`に`OB_KEY_SEEN`を立てて通知する(11.15) | ウインドウ |
| `OB_E_ENTER`、`OB_E_LEAVE` | ポインタが入った、出た | ウインドウ |
| `OB_E_REDRAW` | ウインドウの再描画が必要 | ウインドウ |
| `OB_E_CLOSE` | ウインドウを閉じるよう要求された | ウインドウ |
| `OB_E_CHANGE` | レコードや部品の値が変わった | ストレージ、部品、パネル、デバイス(画面のモード、GPIOの入力、キーボードとポインタの数、電源の装置の状態、シリアルポートと擬似端末に読むものが来た、8.8.1、サウンドデバイスのミキサー、ネットワークのアダプタとWi-Fiの状態と走査の結果、9.6.1)、システムの実身(コンソールのログ、音の出力) |
| `OB_E_DELETE` | 実身が削除された | すべて |
| `OB_E_ATTACH`、`OB_E_DETACH` | メディアやデバイスが接続された、切断された | デバイス |
| `OB_E_EXIT` | プロセスが終了した | プロセス |
| `OB_E_DROP` | 仮身がドロップされた | ウインドウ |
| `OB_E_SCROLL` | スクロールバーが操作された(10.4) | ウインドウ |
| `OB_E_PRESSED` | 画面のどこかでボタンかキーが押された。ほかのウインドウ、メニュー、パネル、何もない所で押したときも、そのウインドウで押したときも、押下の通知より先に届く。`code`はボタンかキーで、位置は0。デスクトップが自分のウインドウの選択枠の点滅を押すたびに数え直すのと同じく、プロセスが点滅を数え直すのに使う(11章)。押下の通知とは別の種類なので、ウインドウの押下を待つ所がこれを押下と取り違えることはない | ウインドウ |

### 8.8.1 読むものが来たことの知らせ

読むものが次々に来る実身(コンソールのログ、シリアルポート、擬似端末)は、読み手が読み尽くした後に何かが来たことを`OB_E_CHANGE`で知らせる。読み手はポートで知らせを待ち、来たら何もなくなるまで読み、また待つ。来るたびに知らせると、キューがあふれて取りこぼしの数ばかりが増えるので、知らせは「読み尽くした後に最初に来たもの」に1回だけ出す(`include/ts/ob.h`の`T_OBEDGE`)。

- 読んで何もなかったとき、その読出しが印を立てる(`knl_obedge_arm`)。来たものを入れる側は、印が立っていれば外して知らせを出すことにする(`knl_obedge_came`)。どちらも読むものを守るロックの中で行うので、読み尽くした後に来たものは必ず印を見つける。
- 知らせを出してから読み手が読むまでの間に来たものは、知らせを出し直さない。読み手は知らせを受けると何もなくなるまで読むので、それもいっしょに読む。読み尽くしたところで印が立ち、その後に来たものはまた知らせる。来たものを知らせずに残すことはない。知らせを受けて読んだら何もなかった、ということはありうる。
- 割込みの中やコンソールのロックの中など、知らせを出せない所では、来たことを記すだけにして、知らせを出すカーネルのタスク(`obdev.c`の`obe_task`、優先度8)をイベントフラグで起こす(`knl_ob_edge_kick`)。`tk_set_flg`は割込みの中、ディスパッチ禁止の間、ジャイアントロックの中(同じCPUが入れ子に取れる)からも呼べる。カーネルの細かいロック(x64のKLOCK_MODE 1〜3)を持っている所だけは、フラグのロック(段3)とスケジューラのロック(段4)を後の段のロックの下で取れないので、起こしを溜めておき、そのCPUが最後のロックを離すとき(`knl_klk_unlock`)に必ず起こす。次に何かが来るのを待たない。
- 割込みを持たない装置(Raspberry Pi 5のRP1のUART)だけは、読み手が待っている間に限って、タスクが20msごとに見る。

| --- | --- | --- | --- |
| システムの実身 | `OB_SYS_LOG`(ログの末尾の位置`END`) | `tm_log_read`が新しいものを返さなかったとき | コンソールに書いたとき。起こすのはコンソールのロックを全部離したとき(`tm_out_unlock`) |
| シリアルポート(`sera`など) | 1 | 受信のタイムアウトが`TMO_POL`の読出しが何も返さなかったとき | 受信の割込みでFIFOから環へ移したとき |

`tests/ktest/ktest_devob.c`の`test_edge_log`、`test_edge_locked`、`test_edge_interrupt`、`test_edge_sound`と、`tests/ktest/ktest_ser.c`の`test_edge`が、読み尽くした後の1回目が知らせられること、知らせから読むまでの間に来たものは知らせずに読めること、カーネルの細かいロックを持った区間やジャイアントロックの中で書いてその後に何も足さなくても知らせが届くこと、割込みの中で細かいロックを持ったまま記して最後のロックを離すときに起こしても届くこと、マウスもキーも触らずシリアルに受信だけがあるときに、書いてから知らせまで数ミリ秒であることを確かめる。

## 8.9 設定の実身

マシンの設定は、固定のUUIDを持つ設定用の実身のレコード1に「キー 値」の行として格納する。ネットワーク設定、デバイス設定、ユーザ情報の3つがある。カーネルはこれらのレコードの変更をイベントで監視しており、書き換えられるとすぐに反映する。設定の小物(第11章)は、設定用の実身を書き換えるだけで設定を変える。`WIFI=1`のビルドには、Wi-Fiの設定の実身「Ｗｉ－Ｆｉの設定」(`SYSDEF_CONF_WIFI`)もある。保存したネットワークの鍵を含むので、所有者がシステム、グループが管理者、モードが`rw-------`で、システムと管理者だけが読み書きでき、書くのはカーネルのWi-Fiの管理だけである(8.6、09章9.6.6)。ネットワーク設定にはIPv4の行(自ホスト、DNSサーバ、ゲートウェイ、時刻サーバ)と、IPv6の行(使うかどうかとアドレスの決め方、固定のアドレスとルータ、DNSサーバ)がある(9.3)。デバイス設定には、配色、壁紙、画面の解像度、キーボード、ウインドウの見た目の行のほかに、CPUのクロックの上限(`CPU_MHZ`、MHz、0は最大、行がなければ1800、3.9)とウォッチドッグ(`WATCHDOG`、秒、0は使わない、行がなければ30、3.8)の行がある。CPUの役割の行(`CPU_CHORE`は雑務のCPU、`CPU_RT`は実時間のCPUの番号の並び。行がなければ雑務はPRC 1だけ、実時間はなし、4.5.1)もここにあり、CPUのクロックの上限と同じく利用者のグループが書ける。装置の割込みの向け先が変わるだけで、ほかの利用者のデータやマシンの安全には関わらないからである。この2つは、行がないときに前の値のままにせず既定に戻す。CPUのクロックの上限だけは、デスクトップが起動するのを待たず、実身マネージャの初期化の直後にも読む(`wm_cpu_conf_apply`)。設定の結果としての今の状態は設定の実身には書かず、システムの実身のレコード(8.4)で読む。3つの実身はどれも所有者がシステム、グループが管理者、モードが`rw-r--r--`である。ユーザ情報と機器の設定は、ACLで利用者のグループにも読み書きを与え、ネットワーク設定は管理者だけが書ける(8.7.1)。

`so_fcntl`と送受信の呼出しは実身に触れないので、時間は9.1.4の値と変わらない。実身の分が加わるのはソケットを作るときと閉じるときだけである。

## 8.12 可変長の一覧と大きさの決まり

システムの実身とデバイスの実身のレコード、設定の実身の行には、CPUの並び、割込み、USBデバイス、走査で見つけたWi-Fiのネットワーク、画面の解像度、IPv6のアドレスのように、数も長さも機械によって変わる一覧が入る。これらは長さにも件数にも上限を置かずに読み書きする。固定の大きさのバッファに写して、超えた分を黙って捨てることはしない。

作る側(カーネル)は、レコードを読まれるたびに作る。作る関数は`knl_oj_put`の系統で書き、バッファの端に来ると-1を返す(書けた所まで書き、以後の呼出しも-1になる)。`knl_oj_make`は、最初に4KBの場所で作り、-1なら場所を倍にして作り直す(16MBまで)。読出しは作ったテキストの指定の位置から写し、`ob_lst_rec`の大きさも作った長さを答える。LinuxのseqfileやFreeBSDの`sbuf`(`SBUF_AUTOEXTEND`)と同じ考え方で、作り直すたびにその時の状態から作るので、一度の読出しの中では一つの時点の内容になる。システムの実身のレコード1〜9、デバイス一覧、デバイスの実身のレコード0、時計、USBデバイス、画面、入力、Wi-Fiの状態と走査の結果がこの形である。

読む側は、レコードを丸ごと読む。カーネルは`knl_ob_rea_all`、プロセスは`ui_rec_all`と`ui_key_all`(`lib/libui`)を使う。先頭から読み、用意した場所が満ちたら倍にして先頭から読み直すので、作られるレコードでも途中で切れない。行の値が一覧のとき(`CPU_CHORE`、`CPU_RT`、`IRQ`、`MODES`、`SCALES`、`KBMAP`)は、`cf_find`で値の位置と長さを得て、その長さのまま扱う。値の中の語は`cf_wfind`で長さ付きで取り出す。`cf_get`と`cf_word`は、数、アドレス、名前のように長さが値の種類で決まるものだけに使う(`CF_VAL_MAX`はその場所の大きさで、一覧の長さの決まりではない)。書き込むときは、読んだレコードの長さに足す行の分の場所を足して`cf_put`で書く。

実身の一覧も、数を先に聞いて場所を用意する。`ob_lst_lnk`は`buf`をNULL、`n`を0にすると数だけを答える(sysctlの長さを先に聞く形と同じ)。`ob_lst_obj`は`from`で続きを尋ねられるので、`ui_lst_obj`は256件ずつ尋ねて全部を集める。`knl_int_dev_names`、`ts_usb_lst_dev`、`so_getifaddr6`、`ob_lst_rec`(実身のレコード、`om_obj_records_all`)、`wm_list`のように用意した場所の数までを返す関数は、返った数が場所と同じかそれより多ければ、場所を広げて尋ね直す。リンクの数え直し(`om_store_relink`、`om_store_recount`)も、レコードのリンクを全部読んでから数える。読めないものがあれば数を直さない。数を少なく見て実身を消すことがないようにするためである。

装置や窓を受け持つ表(USBのコントローラと機器、xHCIの流れ、HIDのインタフェース、USB機器とキーボード、ポインタの実身、デスクトップが扱うプログラム)も、来た数だけ伸ばす。表の項目は1つずつ確保して解放しない。そのため、項目を指すポインタ(デバイスの実身の文脈、`dt_prog_find`の答え)は、表が伸びても、読み直されても動かない。表そのものは、大きな表を作り終えてから1回のポインタの書込みで差し替える。割込みやほかのタスクがロックなしで表をたどっていても、前の表は解放しないので壊れない。xHCIのコントローラの並びと流れの表は、作り終えた項目を末尾につなぐリストにした。

保存できるWi-Fiのネットワークと走査の結果に上限は無い。管理のタスクは設定の行の数だけ場所を用意し、走査の結果はnet80211の走査の表を直接たどって数え、場所が足りなければ広げて受け取り直す(9.6.6)。

上限として残すのは、規格やデータの形式で決まるものだけである。

| 上限 | 値 | 根拠 |
| --- | --- | --- |
| 1つのバスのUSB機器 | 127 | USBのアドレスは7ビット(USB 2.0 9.4.6) |
| xHCIの1つのコントローラの機器 | 255 | xHCIのMaxSlotsは8ビット |
| xHCIの1つのコントローラの口 | 255 | xHCIのMaxPortsは8ビット |
| 機器とルートの口の間のハブ | 5 | USB 2.0 4.1.1(7段) |
| ハブの口 | 31 | 状態の変化の地図を32ビットで読む(Linuxの`USB_MAXCHILDREN`も31)。それより多い口のハブは、コンソールに出す |
| USB機器の番号の中の場所 | 65535 | 機器の番号(`T_USBDEV.dev`)の下位16ビット |
| パッケージ(.tpk)の中のファイル | 65535 | 頭の数が16ビット |
| xHCIのスクラッチパッド | 1023 | HCSPARAMS2のMax Scratchpad Buffersは10ビット。配列はコントローラの答えた数だけ取る |
| 1つのデバイス名の小単位(カメラなど) | 255 | T-Kernelのデバイスの小単位は8ビット(`CAM_UNITS_MAX`) |
| USBのディスクの名前 | 約18000 | デバイス名は8バイト(`L_DEVNM`)。`ud`に英字3文字まで |
| 窓の番号 | 2^28-1 | 窓の部品のハンドルが上位4ビットを種類に使う(`WM_WIN_LAST`) |
| メニューの段と項目 | 2048段、各0x80000項目 | メニューのコマンドの値の符号化(`MN_NODES`、`MN_CMD_NODE`) |
| ネイティブのボリュームのメタデータ | 約492KB | ジャーナルの1つのトランザクションに入る大きさ(`TSFSO_META_MAX`) |
| 丸ごと読むレコードとメタデータ | 64MB | 読み直しを止める安全の上限(`REA_ALL_LIMIT`、`OB_META_LIMIT`)。メモリを使い切らないため |
| QEMUのvirtのPL011 | 4 | 機械の作り(`KNL_MAX_PL011`) |
| x64のISAのシリアルポート | 4 | COM1〜COM4のI/Oポートが決まっている |

R1.200で、次の表を数に合わせて伸びる形にした。上限は無く、超えた分を黙って捨てることもない。

- USBオーディオの機器、カメラ、USBのディスクは、表を倍にして伸ばす。項目は1つずつ確保する。カメラは台数が増えるとデバイスを小単位の数を変えて登録し直し、デバイスマネージャに知らせる。
- T-Kernelのデバイスの登録、オープン、要求の表(`CNF_MAX_REGDEV`など)は、始めの数から倍にして伸ばす。制御ブロックに番号を持たせ、番号から引く表を伸ばす。ディスクの数の`CNF_MAX_DISK`は無くした。
- サウンドのチャネルと覚えた音量の表は伸ばす。`DN_SDOUTS`と`DN_SDMIXER`は全部を返す。大きさは`SND_MIX_SIZE`で求め、場所が足りなければ数だけを答える。
- デバイスマネージャの装置と区画、ボリュームの一覧は伸ばす。
- 窓の表と、窓ごとの描画環境の表(`dp.c`)は64から倍にして伸ばす。メニューの項目は`T_WMMENU`の可変長の配列にした(`WM_MENU_SIZE`)。画面より高いメニューは列を分けて並べる。
- ドロップの仮身と文字は`T_OBDROP`の可変長の配列にした(`OB_DROP_SIZE`)。プロセスは`ob_drop_read`(`ts/obdrop.h`)と`ui_drop`で全部を受け取る。
- ACLと保護のマスクは`T_OBPRT`の可変長の配列にした(`OB_PRT_SIZE`)。`ob_get_prt`と`ob_get_dom`は場所の大きさを受け取り、全体の大きさを答える。
- メタデータの16KBの上限(`OB_ATR_MAX`)は無くした。`ob_get_atr`は場所の大きさまで写し、写した長さを答える。場所が満ちたら広げて読み直す。プロセスは`ob_atr_read`(`ts/obatr.h`)で丸ごと読む。ヒープを持たないプロセス(コンソール)は、`ob_get_atv`でメンバを1つずつ読む。レコードの一覧も`ob_rec_read`で全部を読む。
- シリアルポートの表は伸ばす。名前は`sera`〜`serz`の次を`seraa`とする。ヒープを持たないシリアルの小物は、一覧をページに分けて読む。
- バックアップの根、除く実身、媒体、箱の深さは数に合わせて確保する。起動の引数`T_BKARG`は可変長の形にした。
- 関係図の実身と線は数に合わせて確保する。256個を超える図は、格子に分けて近くの実身とだけ反発を計算する。
- xHCIのスクラッチパッドは、コントローラの答えた数だけページを取る。

まだ固定の表として残るものは`docs/private/fixed-buffer-audit.md`の9章にまとめた(窓の部品の表の200、パネルの32、ダイアログの項目の64、キーとハンドルの数など)。超えたときにどうなるかも、そこに書いた。

洗い出した箇所と、それぞれの扱いは`docs/private/fixed-buffer-audit.md`にまとめた。

## 8.13 システムの容れ物の名前

システムが固定のUUIDで持つ容れ物の実身は、中に並ぶものを表す普通の名前にする。「○○箱」と呼ぶのは、BTRONの標準の原紙箱と小物箱、それにプログラム箱だけである。

| UUID | 名前 | 中身 | R1.110までの名前 |
| --- | --- | --- | --- |
| `SYSDEF_SYSTEM_BOX` | システム | システムの資源の根(画面の定義、プログラム箱、小物箱、書体、壁紙、辞書、設定の実身、「/」など) | システム箱 |
| `SYSDEF_BOX` | 画面の定義 | メニューの定義、部品の定義 | 定義箱 |
| (画面の定義の中) | メニューの定義 | メニューの定義の実身 | メニュー箱 |
| (画面の定義の中) | 部品の定義 | パネルの部品の定義の実身 | 部品箱 |
| `SYSDEF_FONT_BOX` | 書体 | 書体の実身 | 書体箱 |
| `SYSDEF_WALL_BOX` | 壁紙 | 壁紙の絵の実身 | 壁紙箱 |
| `SYSDEF_LEARN_BOX` | かな漢字変換の学習 | 学習の実身 | 学習箱 |
| `SYSDEF_DICT_BOX` | 辞書 | 辞書の実身 | 辞書箱 |
| `SYSDEF_SND_BOX` | システムの音 | 音の実身 | 音箱 |

文字箱と数値箱は、容れ物ではなく、パネルの部品(テキストボックスと数値ボックス)の定義の実身の名前なので、そのままにする。コードはこれらの実身を固定のUUIDで開き、名前では探さない。etc/defのメタデータには、言語ごとの名前を`tessronos.names`(`ja`、`en`)に持たせてある。

R1.110以前のシステムボリュームでは、デスクトップが起動するたびに、名前がまだ古い既定の名前のままの実身だけを新しい名前に変える(`desktop.c`の`sysdef_names`、`om_store_rename`)。管理者が付けた名前は変えない。UUID、レコード、仮身は変わらないので、文章や図形の中の仮身も、開くと新しい名前で出る。R1.110で新しい名前のボリュームを起動しても、UUIDで開くので動く。

超漢字はシステムの容れ物を`$$PROGRAM.BOX`、`$$FONT.BOX`、`$$BGSCREEN.BOX`などの名前で持ち、利用者に見せる「箱」は原紙箱と小物箱だけである。`$$`は保護のない1Bと3で名前で隠すための決まりで、TessronOSは実身の保護で守るので、`$$`の名前にはそろえない。

根「システム」(`SYSDEF_SYSTEM_BOX`)の仮身には、それぞれの実身の役目を表す続柄(`system.fonts`、`system.wallpapers`、`system.programs`、`system.conf.dev`など16)を付けてある。カーネルは、システムの実身を固定のUUIDで開く代わりに、根の仮身を続柄でたどる1つの入口`knl_sys_find(続柄, 既定のUUID, &u)`で引く(`outer_kernel/wm/uconf.c`)。仮身が欠けていれば、実身を作ったときのUUIDを既定として使う(Windowsの既知のフォルダが固定のGUIDから場所を引くのと同じ考え)。デスクトップは起動のたびに`knl_sys_mark`で、続柄のない仮身(R1.110までのボリューム)に続柄を付け、欠けた仮身を置き直す。名前は見ないので、名前を変えても、多言語にしても動く。プロセスからは、同じ入口をSVC`ob_fnd_sys(続柄, 既定のUUID, &u)`(クラス7の52)で呼ぶ。続柄の名前は`include/ts/sysdef.h`の`SYSROLE_*`にある。プログラム箱、書体、壁紙、学習、ファイル変換、暦、ネットワークの設定、機器の設定、ユーザ情報、システムの音、ルート証明書、「/」を探す所は、どれもこれで引く(カーネル、デスクトップ、システム環境設定、ユーザ環境設定、音量ミキサー、予定表、パッケージの展開、ファイル変換、コンソール、`ts_face_find`、TLS)。SVCの権利の判断(`TSN_RIGHT_CONF_DEV`など)も、こうして見つけた設定の実身に書けるかで決める。objfsの「/」は、箱の中身と同じく2秒間は覚えておく。ネットワーク設定(`application/netenv`)は、ほかの作業の範囲なので、まだ固定のUUIDで開く。

起動のたびに空にする実身(tmp)は、機器の設定の実身のレコード0に、続柄`tessronos.clearAtStart`の仮身で並べる(起動のたびに空にする実身の一覧)。実身の層は、ボリュームをつなぐたび(起動のときのシステムボリュームと`ob_att_vol`)に、この一覧の仮身のうち、そのボリュームにある実身を指すものだけを見て、指す実身の仮身をすべて外す(`knl_sys_clear_start`、`outer_kernel/wm/uconf.c`)。外された実身は、ほかから結ばれていなければ屑実身になる。一覧だけを見るので、ボリュームの実身の数によらず手間は変わらない。機器の設定に書けるのはシステムと管理者だけなので、ふつうの利用者が自分の実身を一覧に入れて空にさせることはできない。R1.110以前のボリュームの機器の設定には一覧がないので、レコード1に`CLEAR_LIST`の行がないときに1回だけ、tmpへの仮身を一覧に入れ、`CLEAR_LIST 1`の行を書く。行があれば一覧は作り終えたものとして扱い、管理者が一覧からtmpを外していても入れ直さない。テスト:ktest_devobの`test_clear_start`。
