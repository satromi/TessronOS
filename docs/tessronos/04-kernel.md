# 第4章　カーネル

## 4.1 データ型

μT-Kernel 3.0のデータ型は32bitのCPUを前提にしている。TessronOSは`INT`と`UINT`を32bitのまま残し、サイズ、個数、アドレスを表す型を64bitにした。これにより、上流のコードとT-Kernel仕様の引数の意味を変えずに、64bitのアドレス空間を扱える。

| 型 | 幅 | 用途 |
| --- | --- | --- |
| `INT`、`UINT`、`W`、`UW` | 32bit | 仕様どおりの整数 |
| `D`、`UD` | 64bit | 64bitの整数、時刻 |
| `BINT`、`UBINT` | 64bit | プロセッサのワード幅の整数 |
| `SZ` | 64bit | サイズ(`BINT`) |
| ポインタ | 64bit | |

`W`と`UW`は、`<stdint.h>`を使う構成(`config.h`の`USE_STDINC_STDINT`)でも使わない構成でも32bitである。`config.h`を読まないプログラムも`include/tk/typedef.h`で同じ大きさになるので、カーネルと`dp_put_argb`の画素などの大きさが食い違わない。

## 4.2 タスクと同期

タスク、セマフォ、イベントフラグ、メールボックス、ミューテックス、メッセージバッファ、メモリプール、周期ハンドラ、アラームハンドラは、μT-Kernel 3.0の仕様のまま使える。オブジェクト数の上限は`config/config.h`の`CNF_MAX_*`で決まる。数千のプロセスがそれぞれタスクや同期オブジェクトを持てるよう、タスクは32768、セマフォは98304などとしてある。プロセスのタスクのシステムスタックはImallocではなくページアロケータから確保するので、タスク数はImallocの領域サイズに制約されない。タスクの優先度は1から32である(`CNF_MAX_TSKPRI`)。

保護レベル0と1のタスクはEL1(SP_EL1)で、保護レベル2と3のタスクはEL0で動く。EL0のタスクは生成時にユーザスタックを受け取り(`knl_tcb_sysdep_cre`)、確保できなければ`tk_cre_tsk`が`E_NOMEM`を返す。起動用のフレームを作る`knl_setup_context`は、保護レベル2と3のタスクには必ず戻り先をEL0t(`SPSR`のMが0)にする。ユーザスタックを持たない保護レベル2と3のタスクは`tk_sta_tsk`が`E_SYS`で起動を断り、それでもフレームを作る場面に至った場合は、タスク自身のコードではなくカーネルの`knl_task_no_ustack`へ戻るフレームにして、そこでコンソールに`!USTACK!`を出してタスクを終了させる。失敗したときにEL1で動かすことはしない。`tk_set_reg`で与える`SPSR`からは条件フラグ(EL1のフレームでは割込みのマスクも)だけを取り、例外レベルとPAN(4.6.1)はフレームにあるものを残す。カーネルのタスクの`SPSR`はPANを立てた状態で作る。

タスクは生成時に実行プロセッサを指定できる(SMP T-Kernel仕様の`TA_ASSPRC`)。指定しなければどのCPUでも実行される。`T_CTSK.assprc`は`UBINT`(64ビット)で、ビットnがPRC n+1である(仕様の意味のまま)。64を超えるCPUに割り付けるときは、生成した後でTessronOSの拡張の`tk_set_asp(ID tskid, CONST UBINT *assprc, SZ size)`で指定する(4.3.2)。`tk_get_prc`で、呼び出したタスクが動いているプロセッサが分かる。SMP T-Kernel仕様のドメイン(`tk_cre_dom`など)は実装していない。

浮動小数点とSIMDのレジスタは、`TA_FPU`を指定したタスクだけが使える。ディスパッチャは、`TA_FPU`のタスクから切り替えるときと、そのタスクへ切り替えるときだけ、q0〜q31とFPSR、FPCRをそのタスクのシステムスタックの先頭の領域(`FPUContext`)に保存し、復元する。カーネルは`-mgeneral-regs-only`でビルドしてこれらのレジスタを使わないので、割込みの処理やほかのタスクをはさんでも値はおかしくならない。`TA_FPU`を指定していないタスクが使ってもトラップはしないが、レジスタは保存されないので、タスクの切り替えをはさむと値がおかしくなる。カーネルの中でSIMDを使うのは、`TA_FPU`で生成したウインドウマネージャの合成タスクと、その命令列を確かめる試験のタスクだけで、そのための`outer_kernel/wm/compose_simd.c`だけを`-mgeneral-regs-only`なしでビルドする(10.4.4)。

## 4.3 SMP

すべてのCPUが同じカーネルを実行する。Raspberry PiとQEMUのArmは4つ、x64はACPIのMADTで有効とされた論理CPU(ハイパースレッディングのスレッドを含む)をすべて使う(4.3.2)。レディキューは全体で1本で、スケジューラはその先頭から優先度の高い順に、空いているCPUへタスクを割り当てる。実行中のタスクは、実行プロセッサの指定がない限り同じCPUにとどまる。割当てが変わったCPUには、プロセッサ間割込み(IPI)で通知する。

カーネル内の排他制御は、Armでは、μT-Kernel 3.0のクリティカルセクションを「割込みを禁止し、グローバルなスピンロック(大きなカーネルロック)を取得する」処理に置き換えて実現している。x64では大きなロックを使わず、スケジューラのロックと物ごとのロックに分けている(4.3.3)。ドライバや周辺核が自分のリソースを保護するには、スピンロック(`SpinLock`、`ISpinLock`)かミューテックスを使う。割込みを禁止するだけでは他のCPUを止められないので、排他制御にはならない。

待ちに入るシステムコールは、クリティカルセクションの終わりに、ディスパッチするかどうかをカーネルのロックを持ったまま決める(`cpu_status.h`の`END_CRITICAL_SECTION`)。待ちに入ったタスクは必ずディスパッチャを通り、ディスパッチャはタスクを走らせる前にロックを取り直す(`knl_dispatch_pick`)。その間に別のCPUが待ちを解除しても、待ちの結果のエラーコード、メッセージ、メモリブロックなど、そのCPUがタスクに渡すものは書き終わっている。ロックを放してから決めると、解除したCPUがタスクをレディにしてからエラーコードを書くまでの間に、タスクが自分のCPUの割当てを取り戻し、ディスパッチャを通らずに走り続けることがある。タスクはまだ書かれていない結果(時間の指定のない待ちなのに`E_TMOUT`)を読んで戻り、エラーコードは後から、そのときスタックのその位置にあるもの(次に呼んだ関数の戻りアドレスなど)の上に書かれる。rumpカーネルのスレッドが、上位32ビットが0になった戻りアドレスへ戻って止まったのはこれである(9.1.2)。

タスクのスタックは、そのCPUがスタックを離れてから返す。終了するタスクは、ロックを放した後もディスパッチャのための例外フレームを積むまで自分のスタックの上で動き、その間はCPUがタスクのコンテキストを持っている(TCBの`runprc`が0でない)。`tk_del_tsk`は、休止状態のタスクでも`runprc`が0になるまで待ってから削除する。自分を削除するタスク(`tk_exd_tsk`)のスタックとTCBは、ディスパッチャが自分のスタックに移り、コンテキストを手放してから返す(`knl_reap_task`)。先に返すと、そのメモリを受け取った別のタスクのスタックや別のデータが、終わりかけのタスクの積むフレームで書き換えられる。プロセスの終了では、`tk_ext_tsk`で休止状態になったばかりのタスクを別のタスクがすぐに削除するので、この順序が要る。

`tests/ktest/ktest_smp.c`の`test_wait_result`、`test_del_ended`、`test_exd_stack`がこれを確かめる。そのままでは食い違う時間が命令数個分しかないので、試験用のビルド(`KTEST=1`)だけにある待ちの時間(`knl_kt_unlock_spin`、`knl_kt_release_spin`、`knl_kt_exit_spin`、`smp.c`)で、ロックを放した直後、待ちを解除してから結果を書くまで、終了するタスクがロックを放してからディスパッチャに入るまでを長くして、毎回食い違いが起きるようにする。普段は0で、何もしない。

CPUごとのデータ(`T_PCPU`)の欄を、割込みを許したタスクがそのまま読むことはしない。`knl_ctxtsk`は「CPUごとのデータの場所(ArmのTPIDR_EL1、x64のGSベース)を読む」「その欄を読む」の2命令になり、その間に割込みで横取りされて別のCPUで続けると、離れたCPUで今走っている別のタスク(空いていれば無し)を読む。`tk_get_tid`が別のタスクのIDや0を返し、rumpuserのcurlwpの表(9.1.2)を別のタスクの欄で引いてrumpカーネルが止まったのはこれである(R1.110からあった)。自分のタスクは`knl_self_ctxtsk()`(各アーキテクチャの`sysdepend.h`)で1回だけ読む。x64はGS相対の1命令で読み、Armは割込みを止めて読む。次の所がこれを使うか、割込みを止めた中で読む。

| 所 | 読むもの |
| --- | --- |
| `tk_get_tid`、`get_tcb_self`(`TSK_SELF`)、`CHECK_NONSELF`、`in_qtsk` | 自分のタスク |
| `in_indp`、`in_ddsp`(`cpu_status.h`) | `taskindp`、`ctxtsk`、`dispatch_disabled`を割込みを止めた中で。呼出しの入口の`CHECK_INTSK`、`CHECK_DISPATCH`、`CHECK_TSKID`が使う。別のCPUの値では`E_CTX`が誤って返る |
| `tk_dis_dsp`、`tk_ena_dsp` | `dispatch_disabled`の書込みを割込みを止めた中で。移った後に書くと、離れたCPUのディスパッチを止めてしまう |
| `td_set_reg`、`td_get_reg`、`knl_task_no_ustack` | 自分のタスク |
| `proc.c`の`cur_pcb`、`knl_prc_dma`、`knl_psx_intr` | 自分のタスクから自分のプロセス |
| ACPIの`knl_acpi_os_can_wait`、`knl_acpi_os_tid`、x64の`stopat=` | 割込みを止めた中か、`in_indp` |

クリティカルセクションの中、割込みハンドラ、例外の入口(割込みを禁止したまま読むもの)、ディスパッチャ、ほかのCPUの今のタスクを見る所(`knl_sync_cores`、`knl_pt_reclaim`)は、そのままでよい。`T_PCPU`のポインタそのもの(`knl_pcpu()`)は1命令で読むので、自分がいたCPUのどれかを指す。`knl_pt_reclaim`が自分のCPUを飛ばすのは、そこを離れていればそのCPUはディスパッチャを通っているので正しい。`knl_kernel_locked`は割込みを許したまま呼ぶと、離れたCPUがロックを持っているときに真を返すが、呼ぶ所はない。確かめは、`make RUTRACE=1`のrumpuser.cが、`tk_get_tid`の答えを割込みを止めて読み直した値と比べ、食い違えば`rumpuser: CHECK tk_get_tid gave …`と出すことで行う。直す前はx64の負荷試験(9.1.2)で60秒に1回ほど、QEMUのArmを`-accel tcg,one-insn-per-tb=on`で走らせると1回に数回出た(普段のQEMUのArmは割込みを翻訳ブロックの境目でしか入れないので、2命令の間に入らず起きない)。

2つめ以降のCPUは、起動の途中でPSCIの`CPU_ON`(Arm)か、INITとSIPI(x64)で起動する。`config.h`の`USE_SMP`を0にすると1つのCPUだけで動く。

ディスパッチャは、各タスクが走った時間(TCBの`runcyc`)と合わせて、各CPUがタスクを走らせた時間をGeneric Timerのカウント(x64はTSC)で積む。`ts_ref_cpu(T_TSCPU *pk, SZ size)`は、動いているCPUの数、カウントの周波数、今のカウント、各CPUの積んだ時間(今走っているタスクの分も含む)を返す。CPUごとの時間は可変長の`busy[]`で、呼び手が渡した大きさに入るだけ書く(`TS_TSCPU_SIZE(n)`でn個分)。答えは動いているCPUの数である。2回の呼出しの差から、その間のCPUの負荷が分かる。プロセスの`sysconf(_SC_NPROCESSORS_ONLN)`はこのCPUの数を返す(以前は固定の2だった)。ブラウザのCompute Pressure(14.4.8)もこれを使う。

### 4.3.1 実時間の層と時分割の層

優先度(1〜32)を二つの層に分ける。境は`config.h`の`CNF_RT_PRI_LAST`(15)である。

| 優先度 | 層 | 決め方 |
| --- | --- | --- |
| 1〜15 | 実時間 | 厳密な優先度順で、同じ優先度の中は来た順(FIFO)。回り持ちはしない。`tk_chg_slt`で時間を与えたタスクだけが、同じ優先度の間を回る(POSIXの`SCHED_RR`に当たる) |
| 16〜32 | 時分割 | プロセスのタスクとデスクトップのタスクは、同じ優先度のほかのタスクと`CNF_SLICE_MS`(20ms)ずつ回り持ちする |

回り持ちするのは、プロセスのタスク(保護レベル2と3で、プロセスの番号を持つもの)とデスクトップのタスク(開始アドレスがデスクトップのコードにあるもの)だけである。カーネルとドライバのタスクは、どちらの層にあっても回さない。これらはもともと短く動いては待つように作ってあり、途中で譲らせるとかえって応答が遅れる。カーネルのタスクがプロセスのタスクと同じ優先度に並んでいれば、プロセスのタスクが列の後ろへ回るので、カーネルのタスクは遅くとも1回りで動ける。回り持ちは同じ優先度の間だけで、上の優先度は下のタスクに邪魔されない。

調べた例は次のとおりである。いずれも、実時間の層は数値の範囲か方針で分け、資格で入れるものを限っている。

- Linux: `SCHED_FIFO`と`SCHED_RR`は1〜99で、`SCHED_OTHER`より常に上。`RLIMIT_RTPRIO`か`CAP_SYS_NICE`が要る。
- Windows: 16〜31が実時間のクラスで、動的な引き上げは0〜15だけに効く。
- QNX Neutrino: 方針はスレッドごと。64以上の優先度は特別な能力が要る。
- Zephyr: 負の優先度の協調スレッドと、`CONFIG_TIMESLICE_PRIORITY`より上は回さない。
- T-Kernel 2.0: タスクごとの`slicetime`(既定0)を`tk_chg_slt`で決める。

TessronOSでは、実時間の層に入れるプロセスを、管理者の資格で動くものと、カーネルが`TS_PRC_SYSTEM`で起動したもの(initなど)に限る。それ以外のプロセスは、次のことができない。どちらも求めると`E_OACV`になる(`ts_cre_prc`、`ts_spn_prc`)。

- 自分より高い優先度の子を起動すること
- 実時間の層で子を起動すること

プロセスのタスクは、今までどおりプロセスの基の優先度より上に行けない。実時間の処理をするプログラムは、資格のある者が実時間の層で起動する。優先度を指定せずに起動したプロセスは`CNF_PRC_PRI`(20)で、デスクトップと同じ時分割の列に並ぶ。以前の既定は16で、CPUを使い切るプログラムがあると、デスクトップ(20)が動けなかった。

カーネルのおもなタスクの置き場は次のとおりである。

- 実時間の層: rumpの時計 2、強制終了 3、ファン 6、USBの管理と入力 8、GPU 9、画面の合成とrumpのスレッド 10、カードの送信と強制終了の仕事 11、プロセスの回収・POSIXのアラーム・ジョブ 12
- 時分割の層: 実時間制御TADの再生 19、デスクトップ 20、objfs 20、起動とマウス 21、ビープ 25、ミキサーの設定を残すタスク・DHCP・SLAAC・SNTP 30、ジャーナル 31

音を出す処理(I2SやHDMIのDMAのリングを詰めること、USBオーディオの転送)は、USBの管理タスク(8)が数ミリ秒ごとに行っており、もともと実時間の層にある。サウンドデバイスの優先度30のタスクは、ミキサーの設定を1秒後に機器の設定の実身へ書き残すだけのタスクなので、時分割の層のまま低くしてある。

`tk_chg_slt(tskid, slicetime)`(ミリ秒、0〜1000)は、タスクの回り持ちの時間を決める(SVCのクラス0の78番)。

- 実時間の層では、0(既定)がFIFO、0でない値がRRになる。
- 時分割の層では0を認めず、`CNF_SLICE_MS`とみなす。回らないことを選べると、同じ優先度のほかのプログラムとデスクトップを止められるからである。
- 決めた値は、タスクを休止状態にすると消える。
- プロセスは自分のタスクにだけ使える。

POSIXの`pthread_setschedparam`、`pthread_setschedprio`、`sched_setscheduler`は、これに合わせる。`pthread_getschedparam`は層から`SCHED_FIFO`か`SCHED_OTHER`を答える。

| POSIX | TessronOS |
| --- | --- |
| `SCHED_OTHER`(`sched_priority` 0) | 時分割の層。タスクの初めの優先度に戻し、回り持ちの時間は層の既定 |
| `SCHED_FIFO`、`SCHED_RR`(1〜15) | 実時間の層で、優先度は16 − `sched_priority`(大きいほど高い)。FIFOは時間0、RRは`CNF_SLICE_MS` |
| 資格のないプロセスが実時間を求める | `EPERM` |

時計はティックレスのままである。`knl_reschedule`の終わり(カーネルのロックの下)で、次の両方が成り立つときだけ、回り持ちの期限のタイマイベントを1つ置く。すでに置いてあれば何もしない。

- 回り持ちするタスクがCPUを得ている。
- 同じ優先度でそのCPUで動けるreadyのタスクが、CPUを得られずに残っている。

期限は、そうしたタスクの残りの時間のうち最も短いものである。期限が来ると、時間を使い切ったタスクを、待っているタスクの数だけ同じ優先度の列の後ろへ回し、CPUを割り当て直す。待っていたタスクは譲ったタスクのCPUを優先して取るので、走り続けるタスクがほかのCPUへ移ることはない。続けて走り始めた時刻は、ディスパッチャがタスクを取るときに付ける。待ちに入ったタスクは、次に取られたときに付け直されるだけである。競り合いがなければイベントは置かれず、割込みも処理も増えない。判断はすべてロックを持ったまま行う(4.3の待ちの結果の直しと同じ考え)。

試験は`tests/ktest/ktest_prcobj.c`の`test_slice`と`test_slice_rt`である(svcprogの`SP_SLICE`)。

- `test_slice`: 時分割の層の6つの空回りするタスクを4つのCPUで走らせ、進み具合を記録するタスクが数十ミリ秒以内に必ず動くことを確かめる。
- `test_slice_rt`: その横で、実時間の層のタスクが2ミリ秒の眠りから遅れずに起きることを確かめる。

ミューテックスの`TA_INHERIT`と`TA_CEILING`は今までどおり使える。rumpのロック(rumpuser.c)とpthreadのミューテックスは優先度を継承しない。実時間の層のプロセスがそれらを時分割のタスクと取り合うと、遅れることがある。

### 4.3.2 CPUの数

CPUの数に小さい決め打ちを置かない。上限`CNF_MAX_PRCID`は、x64で1024、Armで4である(`config/config.h`)。上限の大きさで持つのは、CPUの集合(ビットの配列)とCPUごとのデータへのポインタの表だけで、CPUごとのデータそのものは見つかった数だけ確保する。

| 物 | 形 |
| --- | --- |
| CPUの集合 | `T_PRCSET`(`kernel/knlinc/prcset.h`)。`UBINT`の配列で、ビットnがPRC n+1。上限に合わせた語の数(x64は16語、Armは1語)。集合を走査するのは、上限まででなく動いているCPUの数(`knl_num_prc`)まで |
| タスクの割付けCPU | TCBの`assprc`は`T_PRCSET`。空はどのCPUでもよい。`T_CTSK.assprc`(`UBINT`)はPRC 1〜64を表し、それ以上は`tk_set_asp`で指定する |
| CPUごとのデータ(x64) | `T_PCPU`、一時スタック、割込みのスタック、3つのISTのスタック、GDT、TSS、計時、スケジューラの選択、ロックアップの記録、持っているスピンロックの記録、TLBとページテーブルの応答の記録。PRC 1の分は静的に持ち、ほかは起動するときにページで確保する。静的に持つのは`knl_pcpu_p[CNF_MAX_PRCID]`のポインタの表だけ |
| 実行中のCPUの番号 | TCBの`runprc`は、上限が255を超えると`UH`になる(`RUNPRC`、x64の`dispatch.S`は16ビットで書く) |
| CPUの情報 | `ts_ref_cpu`は呼び手が大きさを渡す。ロックアップの統計の各CPUのタイマの回数は`knl_lockup_beats(beats, n)` |

TessronOSの拡張の呼出し(SMP T-Kernel仕様には、生成した後で割付けCPUを変える呼出しは無い)。

- `ER tk_set_asp( ID tskid, CONST UBINT *assprc, SZ size )`: `size`バイト(`UBINT`の倍数)のビットの配列で割付けCPUを設定する。配列が届かない所は0、空はどのCPUでもよい。上限を超えるCPU、あるいは動いているCPUを1つも含まない指定は`E_PAR`。すぐにスケジューラに掛け直す。
- `INT tk_ref_asp( ID tskid, UBINT *assprc, SZ size )`: 割付けCPUを`size`バイトに書き、書いた語の数を返す。どのCPUでもよいタスクは、動いているCPUを全部立てて返す。

スケジューラ(`smp.c`の`knl_reschedule`)は、優先度の高い順にタスクを空いたCPUへ割り当てる。タスクがこの回の割当てで選ばれたかどうかは、TCBの`sch_round`(回の番号)で一度に分かるので、CPUを全部たどらない。1回の割当ての手間は、CPUの数nと割り当てるタスクの数Rに対しておよそn + R × n / 64である。

制限:

- Armのカーネルのロックは1つ(4.3の初め)なので、CPUが多いとロックの取り合いが増え、速さはCPUの数に比例しない。x64はスケジューラのロックと物ごとのロックに分けている(4.3.3)が、レディキューを触る処理はスケジューラのロックで直列になる。`make KLOCKSTAT=1`で、場所ごとの回数、待った時間と持った時間の合計と最大、持った時間の分布(1µs未満から16ms以上までの倍々の16区分)を測れる。
- x64の装置の割込み(IOAPIC、MSI、MSI-X)は、既定ではPRC 1に送る。雑務のCPUを複数にすればメッセージの割込みを分け、割込みごとや装置ごとにも受け先を決められる(4.5.1)。255を超えるIDのCPUへ装置の割込みを送るには、IOMMUの割込みの付け替えが要る。
- x64のTLBの撃ち落としは、プロセスの空間のユーザの半分の変更なら、その空間のタスクを走らせたことのあるCPUにだけNMIを送る(4.5.2)。カーネルの半分の変更は全部のCPUに送る。
- MADTが上限を超えるCPUを持つときは、上限まで起こし、起こさなかった数をKERNEL.TXTに出す。ファームウェアが後から入れられる(オンラインにできるだけの)CPUは起こさず、数だけを出す。

試験は`ktest_smp.c`の`test_set_asp`(最後のCPUへの割付けと実行、`tk_ref_asp`の大きさの扱い、拒否)、`test_ref_cpu`(大きさを渡す形、ヘッダだけの大きさで後ろに書かないこと)と、QEMUのq35を`-smp 8,cores=4,threads=2`、`-smp 16`、`-smp 64,sockets=2,cores=16,threads=2`で走らせて行う(3.10.5)。

### 4.3.3 カーネルの排他

x64では、カーネル全体を1つのロックで守るのをやめ、スケジューラのロックと物ごとのロックの2段に分けている。Raspberry PiとQEMU virtのArm(4CPU)は大きなロック1つのままである。CPUの少ないArmでは、分けたときの取り合いの減り方より、1つのロックの単純さと実時間の見積もりやすさを取る。

#### 方式の切り替え

ロックの当て方は`config.h`の`CNF_KLOCK_MODE`で決まり、`make KLOCK=<値>`で替えられる。

| 値 | 入口のロック | 細かいロック | 使う所 |
| --- | --- | --- | --- |
| 0 | 大きなロック | なし | Armの既定 |
| 1 | 大きなロック | スケジューラとタイマ | 外す途中の区切り1(試験) |
| 2 | 大きなロック | 全部 | 外す途中の区切り2(試験。全部のロックを大きなロックの下で取り、順番を検査する) |
| 3 | なし(割込みの禁止だけ) | 全部 | x64の既定。Armの試験(`make KLOCK=3`) |

T-Kernelの各機能のコード(`kernel/tkernel/`)は、どの値でも同じである。ロックを取る所はマクロ(`KLK_LOCK`、`KLK_UNLOCK`、`KLK_SCHED`など、`kernel/knlinc/klk.h`)で書き、値0ではマクロは何もしない。値0のArmでは、細かいロックの欄も作らない(`KLOCK`の型は大きさ0)。機械ごとの違いは`config.h`の既定値だけで、ロックの実装は共通の`kernel/tkernel/klk.c`にある。

#### ロックの種類と守る物

| 順 | ロック | 数 | 守る物 |
| --- | --- | --- | --- |
| 1 | タスク制御のロック(`knl_tctl_klk`) | 1 | すべてのミューテックス(状態と待ち行列)、各タスクの持つミューテックスの列(TCBの`mtxlist`)と基の優先度(`bpriority`)。ほかのタスクの優先度を変える処理と、タスクを終わらせる処理はこの下で行う |
| 2 | ランデブのロック(`knl_por_klk`) | 1 | すべてのランデブのポート。呼出し、受付け、終了の待ち |
| 3 | 物のロック(制御ブロックの`klk`) | 物ごと | セマフォ、イベントフラグ、メールボックス、メッセージバッファ、可変長と固定長のメモリプールの状態と待ち行列。周期ハンドラとアラームハンドラは全部で1つ(`knl_tev_klk`) |
| 4 | スケジューラのロック(`knl_sched_klk`) | 1 | レディキュー、タスクの状態(TCBの`state`、`priority`、`suscnt`、`wupcnt`)、各CPUの`schedtsk`と、ディスパッチャがタスクを取ること(`runprc`)、回り持ちのタイマ、待つ物の無い待ち(起床待ちと時間待ち) |
| 5 | タイマのロック(`knl_tmr_klk`) | 1 | タイマの待ち行列、コンペアレジスタの設定 |
| 6 | 雑多なロック(`knl_misc_klk`) | 1 | 物の空きの列、プロセスごとの物の数、システム時刻の差分、省電力の数、割込みハンドラの表 |

順番は、番号の小さいものから大きいものへ取る。同じ順のロックを2つ持つことはない(物のロックは同時に1つ)。スケジューラのロックだけは、同じCPUが入れ子に取れる(タスクの状態を変える関数がそれぞれ取るため)。どのロックも割込みを禁止して取り、持ったまま割込みを許すことはない。ドライバや周辺核のスピンロック(4.3の初め)は、どのカーネルのロックより内側で、それを持ったままカーネルのロックを取ることはない。

タスクの待ちの情報(TCBの`wspec`、`wid`、`wercd`、`winfo`と、待ち行列の中のつながり)は、そのタスクが待つ物のロックで守る。待ちに入るときと待ちを解くときは、物のロックとスケジューラのロックの両方を持つ。タスクがどの物のロックで待っているかは、待ちの種類(`WSPEC`)の`wlock`がタスクから求める。ミューテックスの待ちはタスク制御のロック、ランデブの待ちはランデブのロックで、待つ物の無い待ちには物のロックは無い。

#### 待ちを解く側の約束

物のロックを放すと、待ちを解かれたタスクはすぐにほかのCPUで走りうる。そのため、待ちを解く側は次の2つを守る。

1. 待っていたタスクに渡すもの(エラーコード、メッセージ、メモリブロック、イベントフラグのパターン)は、タスクをレディにする前に全部書く。タスクをレディにするのはスケジューラのロックの下で、ディスパッチャは同じロックの下でタスクを取る(`knl_dispatch_pick`)ので、取ったタスクはそれを読める。クリティカルセクションの終わりでディスパッチしないと決めたタスク(解かれてすぐ自分のCPUに割り当て直されたもの)も、`schedtsk`を取得の順序(acquire)で読むので同じである。`knl_wait_release_ok`などは、エラーコードを先に書いてからタスクをレディにする。
2. タスクをレディにした後は、そのタスクの待ちの情報(`winfo`、`wid`、`wspec`)を読まない。レディにしたタスクは、次の待ちのためにそれを書き換えうる。`tk_sig_sem`は解くタスクの要求数を解く前に読み、待ちの解除の後始末(`rel_wai_hook`)はタスクをレディにする前に呼ぶ。

#### 外からタスクの待ちを触る処理

待ちの時間切れ、`tk_rel_wai`、`tk_ter_tsk`、`tk_chg_pri`は、対象のタスクがそのとき待つ物のロックを先に取る必要がある。順番の規則のため、スケジューラのロックを持ったまま物のロックは取れない。そこで`knl_lock_wait_of`は、スケジューラのロックの下でタスクの待つ物のロックを求め、スケジューラのロックを放してから物のロックを取り、スケジューラのロックを取り直して、タスクがまだ同じロックの物を待っているかを確かめる。違えばやり直す。ロックが自分の持つもの(ミューテックスの待ちでタスク制御のロックを持っているとき)なら、取らずにそのまま使う。

時間切れは、タイマの割込みが期限の来たイベントをタイマのロックの下で列から外し、イベントの番号(`TMEB`の`seq`)を`fired`に写してから、ロックを放してコールバックを呼ぶ。イベントを入れる、外すたびに`seq`が進むので、待ちの時間切れのコールバックは、物のロックとスケジューラのロックを取った後で`fired`と`seq`が同じかを確かめる。違えば、その間にほかのCPUが待ちを解いた(あるいはタスクが次の待ちに入った)ので、何もしない。周期ハンドラ、アラームハンドラ、回り持ちのタイマも同じ確かめをする。列から外したイベントはつながりを自分に向け直す(`QueInit`)ので、後から外しても列は壊れない。

#### 複数の物やタスクを同時に扱う処理

| 処理 | 解き方 |
| --- | --- |
| タスクの終了でのミューテックスの全解放(`tk_ext_tsk`、`tk_exd_tsk`、`tk_ter_tsk`) | タスク制御のロックの下で行う。ミューテックスは全部このロックで守るので、何個持っていても取るロックは1つである。待っていたタスクに持ち主を移し、上限の優先度を当てる |
| 優先度の継承の連鎖 | 連鎖をたどるのは、タスク制御のロックだけを持った状態で行う。1つのタスクごとに「そのタスクの待つ物のロック、スケジューラのロック」を取って優先度を変え、放してから次のタスクへ進む。待ちの解除や待ち行列の並べ替えの中で持ち主の優先度を求め直す必要が出たときは、持ち主をタスク制御のロックの下の保留の列に積み、タスク制御のロックを放す直前にまとめて求め直す(`knl_tctl_unlock`)。求め直しは「基の優先度、持っている上限付きのミューテックスの上限、継承のミューテックスを待つ先頭のタスク」の最も高いものである |
| 待ちの時間切れ | 前の項。ミューテックスの待ちなら、タスク制御のロックを取り、解いた後の持ち主の優先度の求め直しを保留の列に積む |
| `tk_ter_tsk` | タスク制御のロック、対象の待つ物のロック、スケジューラのロックの順に取り、待ちを解き、ミューテックスを全部放し、休止状態にする。ほかのCPUで走っているタスクは今までどおり`E_OBJ`である |
| `tk_rel_wai` | 対象の待つ物のロック、スケジューラのロックの順に取る。ミューテックスの待ちならそれがタスク制御のロックである |
| `tk_chg_pri` | タスク制御のロックの下で上限と基の優先度を決め、対象の待つ物のロック、スケジューラのロックを取って変える。継承の連鎖は前の項のとおり |
| `tk_sus_tsk`、`tk_rsm_tsk`、`tk_wup_tsk` | スケジューラのロックだけ。強制待ちは待ち行列を触らない。起床待ちには物が無い |
| タスク例外 | μT-Kernel 3.0にもTessronOSにもタスク例外は無い。プロセスのシグナルが待ちを中断するのは`tk_rel_wai`(5章)、プロセスの終了は`tk_ter_tsk`と`tk_sus_tsk`で、前の項のとおりである |
| 待ち行列のある物の削除 | 物のロックの下で、待っているタスクを全部`E_DLT`で解く。ミューテックスの削除は、タスク制御のロックの下で、持ち主の優先度の求め直しを保留の列に積む |
| 周期ハンドラとアラームハンドラ | ハンドラは、タイマの割込みがロックを全部放してから呼ぶ。削除する側は、ほかのCPUでハンドラが走っている間は待つ(ハンドラが自分を削除するときは待たない) |

TOPPERS/FMP3は、タスクの終了やミューテックスの全解放で複数のタスクのロックを取る所のデッドロックの回避が多くなりすぎるとして、細かいロックをやめ、大きなロックだけにした(検討書5.16.8)。TessronOSは、タスクごとのロックを持たない。タスクの状態は全体で1つのスケジューラのロックで、ミューテックスとほかのタスクの優先度の変更は全体で1つのタスク制御のロックで守る。複数のタスクを触る処理はどれもこの2つの下で行うので、タスクのロックを2つ以上取る所は無く、デッドロックの回避そのものが要らない。分けたのは、物ごとの状態(セマフォの数、フラグのパターン、バッファ、メモリ)とその待ち行列だけで、物のロックは同時に1つしか持たない。これはZephyrの形(スケジューラのロック1つと物ごとのロック)に当たる。代わりに、ミューテックスの操作と優先度の変更はCPUの間で直列になり、レディキューを触る処理(待ちに入る、待ちを解く)はスケジューラのロックで直列になる。待たずに済む呼出し(数の足りるセマフォ、待つタスクの無いイベントフラグ、空きのあるバッファなど)は、物のロックだけで終わる。

#### ロックを待つ間の割込み

ロックを1つも持たないCPUが、割込みを許した状態から入ったクリティカルセクションで最初のロックを待つときは、待つ間だけ割込みを許す(検討書5.16.11.1の7)。待つ間はディスパッチを止めておき(`dispatch_disabled`を`DDS_DISABLE_IMPLICIT`にする)、セクションの途中で別のタスクに替わらないようにする。待ち方は「試して、取れなければ割込みを許して空くのを見る」を繰り返し、決まった回数(`KLK_OPEN_TRIES`)取れなければ、割込みを禁止してチケットを取り、順番を待つ。チケットの順番があるので、待ちの上限(公平さ)は失わない。ロックを持ったまま割込みを許すことはないので、割込みのハンドラが同じCPUで同じロックを待って止まることはない。

#### ロックの順番の検査と試験

`KTEST=1`のビルドと`make KLOCKCHECK=1`では、各CPUが持つカーネルのロックを順に記録し、次のことを確かめる(`klk.c`)。違反すると`!KLOCK!`で始まる行に、取ろうとしたロック、持っているロック、それぞれを取った場所を出し、数(`knl_klk_bad`)を数える。

- 取るロックの順が、持っているどのロックより大きいこと(スケジューラのロックの入れ子を除く)
- 割込みを禁止して取ること
- 放すロックが自分の持つものであること
- クリティカルセクションの終わりで、入ったときより多くのロックを持っていないこと
- ディスパッチャに入るときにロックを持っていないこと
- レディキュー、タイマの待ち行列、物の待ち行列を触る所で、そのロックを持っていること

試験の`ktest_klk.c`(kernel群)は、検査が違反を見つけること(わざと逆の順で取る)と、次の負荷をすべてのCPUで重ねたときに、結果が合い、違反も止まりも無いことを確かめる。試験用のビルドでは、ロックを取った直後、`knl_lock_wait_of`のロックを取り直す前、タイマの割込みがイベントを外してからコールバックを呼ぶまでに、わざと待ちを入れて(`knl_kt_klk_spin`)、食い違いの起きる時間を延ばす。

- セマフォの受け渡しと、短い時間切れ、`tk_rel_wai`の競り合い。渡した数と受けた数が合うこと
- 継承のミューテックスの連鎖(3段)の途中の時間切れ、`tk_chg_pri`、`tk_ter_tsk`。全部放した後に優先度が基に戻ること
- 待っている物の削除(`E_DLT`を1回ずつ受けること)
- メッセージバッファの送受信の中身と時間切れ
- 周期ハンドラとアラームハンドラの開始、停止、削除と発火の競り合い。削除した後に呼ばれないこと

#### 計測

取り合いは`make KLOCKSTAT=1`で計る。値3では、ロックの種類ごとに、取った回数、待った回数、待った時間と持った時間の合計と最大、持った時間の分布を数える(物のロックは全部の物をまとめて1つ)。試験は群ごとに`KLOCK suite <群> class <種類>`、最後に`KLOCK class`の行で出す。

再スケジュールで別のタスクを割り当てたCPUへのIPIは、スケジューラのロックを放してから送る(`knl_sched_ipi_flush`)。ロックの中で送ると、仮想機械(WHPX)ではIPIのたびに仮想機械の出口があり、その分だけ持つ時間が延びて、ネットワークの負荷でスケジューラのロックの待った割合が6割を超えた。

外す前(値0)と後(値3)を、QEMUのq35(WHPX)で、kernel群とネットワークの負荷(rump)の群を走らせて比べた。待った割合は、値0は大きなロックの、値3は全部のロックを合わせたものである。ホストは他の作業と同時に動いていたので、時間の絶対値は揺れる。

| 群 | CPU | 値0 待った割合 | 値0 待ち合計 | 値3 待った割合 | 値3 待ち合計 |
| --- | --- | --- | --- | --- | --- |
| proc(プロセスの起動と終了) | 4 | 7.4% | 4.8秒 | 2.1% | 0.6秒 |
| proc | 16 | 17.1% | 32.4秒 | 5.0% | 13.9秒 |
| task | 16 | 22.1% | 6.7秒 | 4.4% | 0.8秒 |
| rump(ネットワークの負荷) | 4 | 65.4% | 18.9秒 | 11.0% | 3.4秒 |
| rump | 8 | 71.9% | 40.6秒 | 8.6% | 3.6秒 |
| rump | 16 | 72.2% | 35.1秒 | 7.9% | 7.1秒 |

値3で残る取り合いの元はスケジューラのロックである。レディキューが変わるたびに全部のCPUの割当てを作り直す`knl_reschedule`が、1つのロックの下で直列になる。1回の待ちの最大は、値3ではスケジューラのロックで5ms(4 CPU)から113ms(16 CPU)だったが、仮想CPUがホストに止められた間の分を含むので、実機の値の根拠にはしない。詳しい値は検討書5.19にある。

## 4.4 時間管理

周期的なタイマ割込みは使わない(ティックレス)。次に期限が来るタイマの時刻だけをGeneric Timerのコンペアレジスタに設定し、実行するタスクがないCPUは割込みが来るまで`wfi`で休止する。ただしNetBSDのネットワークスタック(第9章)は、自分のタイマを1秒に100回の刻みで進めるので、そのスレッドが10ミリ秒ごとに起きる。タイマキューはPRC1が持つ1本で、他のCPUが先頭の期限を変えたときはIPIでPRC1に再設定させる。

| 時刻 | 基準と単位 | 取得方法 |
| --- | --- | --- |
| 単調時刻 | 起動時点、ナノ秒 | `ts_get_mono` |
| システム時刻 | 1985年1月1日0時(UTC)、ミリ秒とマイクロ秒 | `tk_get_tim`、`tk_get_tim_u` |
| カレンダ | システム時刻とタイムゾーン | `dt_localtime`ほか(第9章) |

時刻の基準は、T-Kernelのシステム時刻と同じ1985年1月1日0時(UTC)である。UUIDのversion 7やFATの日付のように、外部の形式が別の基準を定めている場合だけ、その形式に合わせて変換する。

システム時刻は起動時にRTCから読み込む。Raspberry Pi 5で電池がなく、RTCが1985年より前を返す場合は、1985年1月1日から計時を始める。ネットワークに接続していれば、SNTPで時刻を合わせる(第9章)。`tk_set_tim`で時刻を変更するとRTCにも書き戻す。x64のPCでは、RTCをWindowsと同じくローカル時刻として扱うか、UTCとして扱うかを選べ、既定はローカル時刻である(9.5.1)。Raspberry PiのRTCはUTCである。うるう秒は扱わない。

## 4.5 割込み

割込みコントローラはGICv2で、SMP T-Kernel仕様どおり割込み番号にはGICのINTIDをそのまま使う。0〜15番がSGI(プロセッサ間割込み)、16〜31番がPPI(CPUごとのタイマなど)、32番以降がSPI(デバイスの割込み)である。デバイスの割込みは、デフォルトでPRC1に届く。PCIeデバイスのMSIは、GICのSPIに変換して受け付ける。

割込みハンドラは`tk_def_int`で登録し、割込みを受けたCPUのタスク独立部で実行される。タスク独立部からは待ち状態に入るシステムコールを使えない。

### 4.5.1 割込みを受けるCPUとCPUの役割

装置の割込みは、既定ではx64もArmもPRC 1に届く(x64のIOAPIC、MSI、MSI-Xの宛先と、ArmのGICの`GICD_ITARGETSR`)。PRC 1はシステムタイマも受ける。これを変える仕組みとして、CPUの役割と、割込みごとの受け先を持つ(`kernel/tkernel/inttarget.c`、検討書5.16.11.1の1〜5)。

CPUの役割は機器の設定の実身(`SYSDEF_CONF_DEV`)の2つの行で決め、システムは書かれるとすぐに取り入れる(`uconf.c`の`cpu_conf`)。値はPRCの番号の並びで、`2,4-6`のように書く。並びの長さに上限は無く(CPUは1024個まで)、システムは行の値を長さのまま読む(8.12)。システム環境設定は、続く番号を`2-64`のように範囲にまとめて書く。

| 行 | 役割 | 既定 |
| --- | --- | --- |
| `CPU_CHORE` | 雑務のCPU。装置の割込みを受ける。PRC 1はシステムタイマを受けるので、書かなくても常に入る | PRC 1だけ |
| `CPU_RT` | 実時間のCPU。装置の割込みを向けない。雑務のCPUと重なる番号は雑務になる | なし |

システムの実身のレコード1の`CPU_CHORE`と`CPU_RT`の行が、取り入れた結果を示す。実時間の層(優先度1〜15)のタスクを雑務のCPUに割り付けないことは勧めるだけで、強制しない(タスクの割付けCPUは`TA_ASSPRC`と`tk_set_asp`で利用者が決める)。

割込みの受け先は次の順に決まる。

1. `SetIntTarget(intno, prcid)`で割込みに名指ししたCPU
2. 装置の実身の属性`irq.cpu`で、その装置の割込み全部に名指ししたCPU
3. どちらもなければ雑務のCPUの先頭。ただしメッセージの割込み(x64のMSIとMSI-X、ArmのGICv2mの範囲)は、雑務のCPUが複数あれば、割込み番号で順に分ける

名指ししたCPUが実時間のCPUになったり、動いていないCPUだったりするときは、3.の決め方になる。役割を変えると、使っている装置の割込みを全部決め直す。既定(雑務がPRC 1だけ)では今までどおり全部がPRC 1に届く。

TessronOSの拡張の関数(SMP T-Kernel仕様は受け先を実装定義とし、変える関数を持たない)。

- `ER SetIntTarget( UINT intno, ID prcid )`: 割込みを受けるCPUを1つ決める。`prcid`が0なら名指しをやめ、システムが決める。装置の割込みでない番号、動いていないCPUは`E_PAR`、実時間のCPUは`E_OBJ`、そのCPUへ送れないときは`E_NOSPT`。
- `ID GetIntTarget( UINT intno )`: 今その割込みを受けるCPU。

マスクの形(CPUの集合)にしないのは、検討書5.16.6のとおり、x86の最低優先度の配送とGICv2の複数のビットはどちらも1つのCPUに決まらず(受け先が守られない、ほかのCPUに偽の割込みが出る)、CPUの数を問わない形にもなるからである。

ハードウェアの差は`knl_int_route`(x64は`apic.c`、Armは`interrupt.c`)に閉じ込めている。

| 機械 | 割込み | 書き換えるもの |
| --- | --- | --- |
| x64 | IOAPICの入力 | RTEの宛先(上位の8ビット)。書き換える間はマスクし、元のマスクの状態に戻す |
| x64 | MSI-X | 表の項目のアドレス(宛先のAPIC IDは19〜12ビット)。項目をマスクして書き、マスクを戻す。`pcie.c`がどの項目に書いたかを覚えている |
| x64 | MSI | 能力の中のアドレスの下位の語。宛先はこの語だけにあるので、1回の書込みで変わる |
| Arm | SPI(GICv2mのMSIを含む) | `GICD_ITARGETSR`の1バイトに、そのCPUのCPUインタフェースのビット。各CPUは起動時に`GICD_ITARGETSR0`(自分のビットが読める)を読んで覚える(`knl_gic_cpuif_note`) |

xAPICの形式の宛先は8ビットなので、x64でAPIC IDが255以上のCPUには送れない(`E_NOSPT`)。IOMMUの割込みの付け替えは使っていない(4.3.2)。メッセージの割込みは、作るときに受け先のCPUのアドレスで書く(`cpu_msi.h`の`knl_msi_addr`)。

装置の実身の属性`irq.cpu`: ドライバは割込みを登録した後に、それが自分の装置(デバイス名)のものであることを`knl_int_owner(intno, devnm)`で伝える。今は、NVMe(`nvmea`…)、virtioのブロック装置(`vblka`…)、ネットワークのカード(`neta`、virtio-netとIntelのLAN)が伝える。装置の実身の属性を読むと`"irq":{"cpu":名指し(0はなし),"intno":[…],"on":[…]}`が見え、`{"irq":{"cpu":2}}`のように書くと、その装置の割込みを全部PRC 2に向ける。値はデバイス箱の項目(`irqcpu`)に残り、次の起動でもドライバが割込みを伝えたときに当たる。システムの実身のレコード1は、割込みを伝えた装置ごとに`IRQ 名前 実身のUUID 名指し 番号:CPU,…`の行を持つ。

システム環境設定の〈機器情報〉の「プロセッサ」のページで、CPUごとの役割(普通、雑務、実時間)と、装置ごとに割込みを受けるCPUを設定できる(11章)。

### 4.5.2 TLBの無効化を送るCPU(x64)

x86にはほかのCPUのTLBの項目を消す命令がないので、ページの対応を変えるとNMIで頼む(`mmu.c`)。プロセスの空間のユーザの半分の変更は、その空間のタスクを走らせたことのあるCPUにだけ頼む。ディスパッチャは、タスクを走らせる前(CR3を載せる前)に、その空間(PML4の物理アドレス)をCPUごとの表に書く(`knl_tlb_note`)。PCIDがないCPUでは、空間を載せ替えると前の空間の項目は消えるので、表は今の空間だけである。PCIDがあるCPUでは、最後に自分のTLBを全部消してから走らせた空間を並べ、全部を消したら今の空間から並べ直す。表が16を超えたCPUには、空間によらず頼む。頼む側は、ページの表を書き換えてから表を読む(`mfence`)ので、表に載る前のCPUは書き換えた後の表を引く。カーネルの半分の変更、`knl_tlb_flush_va`、空間の削除は今までどおり全部のCPUに頼む。

## 4.6 メモリ

仮想アドレスは48bitで、上位半分(TTBR1)をカーネル、下位半分(TTBR0)をプロセスに使う。プロセスのアドレス空間はそれぞれ16bitのASIDを持つので、プロセスを切り替えてもTLBをフラッシュせずに済む。ASIDは0がカーネルのタスク、1がシステムプロセスで、2から65535をプロセスに割り当てる。プロセッサが8bitのASIDしか持たない場合は255までである。

| 範囲 | 内容 | EL0から | カーネルからの参照 |
| --- | --- | --- | --- |
| `0xFFFF000000000000`から | 物理メモリ全体のリニアマッピング。仮想アドレス = 物理アドレス + `0xFFFF000000000000` | 不可 | 常に可 |
| `0xFFFF800000000000`から | デバイスのレジスタ領域 | 不可 | 常に可 |
| `0xFFFF900000000000`から | カーネルの可変領域(物理的に連続しないページを連続した仮想アドレスに並べる) | 不可 | 常に可 |
| `0x400000`から | プロセスのプログラムイメージ、その上にヒープ | 可 | 確かめた後、PANを外すインタフェースを通してだけ(4.6.1) |
| `0x100000000000`から | プロセスが要求したメモリ(`ts_map_mem`) | 可 | 同上 |
| `0x400000000000`から | 共有メモリの領域(全プロセスで同じアドレス) | 可 | 同上。中身はリニアマッピングかカーネルの可変領域のアドレスで扱う |
| `0xFFFFF0000000`の下 | プロセスのタスクのユーザスタック | 可 | 同上 |

ページサイズは4KBである。物理ページはバディアロケータで割り当てる。カーネルのメモリは`Kmalloc`で確保する。プログラムイメージのコードは読出しと実行のみ、データは読み書きのみを許し、書込みと実行を両方許すページは作らない。プロセスのアドレス0から1MBはマッピングしないので、NULLポインタの参照は必ず失敗する。

プロセスのメモリは、要求されたときにページを割り当ててマッピングする。アクセス時に初めてページを用意するのは、書込みと実行を交互に行う範囲(`TS_MEM_JIT`、5.3)だけで、一般のデマンドページングとスタックの自動拡張の仕組みは持たない。マッピングしていないアドレスにアクセスすると、プロセスは異常終了する。

プロセスのページを実行できるようにするときは、データキャッシュの書き戻しと命令キャッシュの無効化(`knl_icache_sync`)、TLBの無効化(`tlbi vaale1is`)、同じプロセスを実行中の他のプロセッサへのIPIによるコンテキスト同期(`knl_sync_cores`)を行う(5.3)。EL0は`CTR_EL0`の読出しと、アドレスによるキャッシュ操作(`dc cvau`、`ic ivau`)を許されている(`SCTLR_EL1.UCT`、`UCI`)。

デバイスとのDMAには物理アドレスを渡す。リニアマッピング上のバッファはアドレスの差で物理アドレスに変換できるが、可変領域に並べたページは物理的に連続していないので、`ConvPhysicalAddress`で連続する区間ごとに物理アドレスを求める。

`Kmalloc`は、大きさで取り方を分ける。1MB未満は、起動時に頁の割り当てから取っておいた固定の領域(`CNF_IMALLOC_SIZE`、64MB)のヒープから取る。1MB以上は、そのたびに頁を割り当てて可変領域に並べ(`knl_vmap`)、先頭の64バイトに頁の数を書いて、その後ろを返す。`Kfree`と`Krealloc`は、アドレスが可変領域にあるかどうかでどちらかを見分ける。返された大きなものは、8個、合わせて64MBまでを手放さずに残し、次にそれより少し小さい(4分の1以内)ものを求められたら頁を並べ直さずに渡す(文章を編集するたびに同じ大きさで取り直す、記録の写しやモデルのため)。可変領域が足りなくなったら、残したものを先に返す。ハンドラの中と、タスクが走り出す前は、頁の表を変えないよう、大きなものもヒープから取る。可変領域から取れないときも、ヒープから取ってみる。Linuxの`kmalloc`(スラブから取る、物理的に連続した小さなもの)と`vmalloc`(頁を仮想アドレスに並べた大きなもの)の使い分けと同じ考えで、違いは呼び出し側が選ぶのではなく`Kmalloc`が大きさで選ぶことである。デスクトップはカーネルの中で動き、文章のモデルや図形、表、取り消しの写しが`Kmalloc`で取られるので、ヒープの大きさが開ける文章の大きさの上限になっていた(12MBの文章が開けなかった)。いまは機械のメモリの量と、可変領域の大きさ(`CNF_VMAP_SIZE`、1GB)が上限である。大きなものは物理的に連続しないので、装置との転送に使う側は、ほかの可変領域のメモリと同じく`ConvPhysicalAddress`で区間に分ける(SDHCI、vblk、FAT、USBはそうしている)。物理的に連続したメモリが要るときは、`tk_get_smb`で頁を取る。

### 4.6.1 PAN(Privileged Access Never)

ARMv8.1以降のプロセッサ(Raspberry Pi 5のCortex-A76、QEMUの`-cpu cortex-a76`)はPANを持つ。`PSTATE.PAN`が立っている間は、EL1からEL0がアクセスできるページ(ページテーブルの`AP[1]`が1)への読み書きがパーミッションフォールトになる。カーネルはこれを使い、プロセスのメモリへは、システムコールの引数として確かめたものだけを、決まったインタフェースを通して読み書きする。それ以外の場所でカーネルがプロセスのページに触れると例外になり、記録に残る。

起動時に各プロセッサが`ID_AA64MMFR1_EL1`のPANの欄を見て、PANがあれば`SCTLR_EL1.SPAN`を0にし、`PSTATE.PAN`を立てる(`knl_pan_setup`)。`SPAN`が0なので、EL1へ例外が入るたびに`PSTATE.PAN`が立つ。システムコール、割込み、カーネル内の例外のどれから入っても、カーネルのコードはPANが立った状態で始まる。カーネルのタスクも`SPSR`にPANを立てた状態で起動する。PANを持たないプロセッサ(ARMv8.0のRaspberry Pi 4など)では何もせず、カーネルはこれまでどおりプロセスのページに触れる。

プロセスのメモリを読み書きするインタフェースは`kernel/sysdepend/cpu/core/armv8a/cpu_uaccess.h`にある。

| インタフェース | 働き |
| --- | --- |
| `knl_ua_open`、`knl_ua_close` | PANを外し、元に戻す。入れ子にしても外側の`knl_ua_close`だけが戻す |
| `UACCESS(式)`、`UACCESS_DO(文)` | PANを外して式の値を求め、文を実行する |
| `knl_ua_get`、`knl_ua_put` | PANを外してプロセスのメモリからカーネルへ、カーネルからプロセスのメモリへコピーする |

どのインタフェースも、`knl_prc_user_ok`でポインタがプロセス自身のページを指し、書き込む場合は書込み可能であることを確かめた後でだけ使う。システムコールのラッパ(`svc_gate.c`、`svc_tk.c`、`obsvc.c`、`so_prc.c`、`gpu_svc.c`)が、引数の構造体や文字列のコピー、答えの書き戻し、メッセージの受け渡しをこのインタフェースで行う。ファイルや実身のレコードのデータのように、カーネルが中身を見ずに運ぶだけのバッファは、確かめた後、それを使う下の層の呼び出しを`UACCESS`で囲んで、置かれた場所のまま使う。`PSTATE`はタスクの例外フレームの`SPSR`に入って保存されるので、PANを外したまま待ちに入ったりプリエンプトされたりしたシステムコールは、再開したときもPANは外れたままである。その間に入った割込みのハンドラはPANが立った状態で動く。

システムプロセスのEL0のタスク(保護レベル2と3でプロセスに属さないもの)はカーネルの一部として扱い、渡したポインタを確かめない。このタスクのシステムコールは、入口でPANを外して出口で戻す。

カーネルがプロセスのページを自分で用意するときは、EL0から見えるアドレスを使わない。プログラムのロード、起動時の引数のページ、ユーザスタックの確保、`TS_MEM_JIT`のページの切替え、共有メモリのアドレスウインドウにマップするウインドウの面やGPUのBOは、すべてリニアマッピングか可変領域のアドレスで中身を作る。デバイスとの転送でプロセスのページを直接使うときも、`knl_prc_dma`がリニアマッピングのアドレスを返す。PANの対象になるのは、システムコールの処理の中でプロセスのアドレスのまま読み書きする場合だけである。

インタフェースを通さずにプロセスのページに触れると、`knl_kernel_fault`が、PANの立った状態で起きた、EL0からアクセスできるページへのパーミッションフォールトであることを確かめ、コンソールに`!PAN!`とアドレス、`ELR`、`LR`、タスクを表示し、回数(`knl_pan_faults`)を数える。割込みハンドラの中で起きた場合は、ほかのカーネルの例外と同じくそのプロセッサを停止する。タスクで起きた場合は、ボリュームやロックを中途半端な状態で残さないように、例外フレームの`SPSR`のPANを外してそのシステムコールを最後まで実行させる。タスクがプロセスのものであれば、システムコールから戻るところでプロセスを`TS_ABORT_FAULT`で終了させ、例外の記録の種類を`TS_FLT_KPAN`にする(5.5)。カーネルのどこかがプロセスのメモリを確かめずに使った不具合を、プロセスの終了とダイアログで通知するためである。

試験用のカーネル(`KTEST=1`)では、プロセスが`TSN_TM_PAN_PROBE`で自分のページの1ワードをカーネルに読ませられる。確かめてからインタフェースを通して読む場合と、インタフェースを通さずに読む場合を選べ、後者でPANが働くことを`tests/ktest/ktest_pan.c`が確かめる。

### 4.6.2 ユーザスタックの場所とページテーブル

保護レベル2と3のタスクのユーザスタックは、そのタスクの空間(プロセスのタスクならプロセスの空間、カーネルが作るものならシステムプロセス空間)の`0xFFFFF0000000`の下に、ガードページを1つはさんで下へ順に置く。タスクを削除してスタックを返すと、その場所を同じ大きさのスタックのために控え、次に作るタスクに渡す(`space.c`の`stk_take`、`stk_keep`。控えは全体で1024個まで)。空間を削除すると、その空間の控えも消す。控えがなければ下へ延ばす。場所を使い回さないと、タスクを作っては消すプロセスやシステムプロセス空間では、スタックの領域がタスクごとに少しずつ減り、2MBごとにページテーブルが1枚ずつ増えていった。

スタックを返した後で、何もマップしなくなったL3のページテーブルと、それで空になったL2のページテーブルを空間から外す(`knl_pt_prune`)。外すときはページテーブルのロックの下で上の段のエントリを消し、`tlbi vaae1is`で全プロセッサのTLBから落とす。ページを返すのは、その後でほかのすべてのプロセッサがディスパッチャを通ったか、ディスパッチャで休んでいるのを確かめてからである(`knl_pt_reclaim`)。`knl_pt_lookup`、`knl_pt_entry`、`knl_pt_next`はロックを取らずにページテーブルをたどるが、たどる間は割込みを禁止しているので、たどっている途中のプロセッサはディスパッチャを通らない。外したページテーブルは64枚まで待たせ、それを超える分は外さずに残す。返すのは、スタックの確保と解放のたびと、プロセスの回収のタスク(5.5)が起きるたびである。

`tests/ktest/ktest_el0.c`の`test_el0_stack_churn`が、システムプロセス空間で保護レベル3のタスクを作っては消すことを`KT_CHURN_N`回(既定は1000回)繰り返し、スタックの領域の位置と空きページが変わらないことを確かめる。`tests/ktest/ktest_prcobj.c`の`test_task_churn`は、プロセスが自分のタスクを同じ回数作っては消し、どのタスクのスタックも前のタスクと同じ場所に置かれること、プロセスが終わればページがすべて戻ることを確かめる。

## 4.7 停止の検出とウォッチドッグ

システムが止まったときに何も出力されないと、原因を調べる手がかりがない。プロセッサが割込みを禁止したまま回り続けている場合、応答しないデバイスへのアクセスで止まっている場合、ロックが解放されない場合は、例外が起きないので例外の表示も出ない。TessronOSは、各プロセッサが互いを監視してこうした状態を検出し、分かったことを直ちにコンソールに出す(`kernel/sysdepend/cpu/core/armv8a/lockup.c`、`include/ts/lockup.h`)。

### 4.7.1 プロセッサの監視

各プロセッサは自分の仮想タイマ(`CNTV`、PPI 27)を0.5秒ごとに満了させる。カーネルはこのタイマをほかの用途に使わない。その割込みのハンドラは、自分が生きている印として現在の時刻を記録し、割り込んだ場所(`ELR`、`LR`、`SP`、`SPSR`、タスク)を控えてから、ほかのプロセッサを調べる。調べるのは同時に1つのプロセッサだけである。5秒間割込みを受けていないプロセッサは、割込みを禁止したまま動いているか、完了しないアクセスで止まっている。これを見つけると、次の内容をコンソールに出す。

- そのプロセッサの実行中のタスク(番号、開始アドレス、優先度、状態、プロセスの番号とファイル名)、ディスパッチの禁止、割込みの入れ子の深さ
- 最後に割込みを受けたときに割り込んだ場所と、その時刻
- 持っているスピンロックと、それを取った場所と時刻。待っているスピンロック
- ビッグカーネルロックを持っていれば、それを取った場所と時刻

続けて、そのプロセッサにSGI 4番(`SGI_LOCKUP`)を送る。受け付けたプロセッサは、自分が割り込まれた場所とフレームポインタをたどった呼出し元を出す。0.5秒以内に受け付けなければ、割込みが禁止されているか、アクセスで止まっていると出す。最後に、ほかのプロセッサの状態も出す。そのプロセッサが再び割込みを受けるようになったら、そのことも出す。

スピンロックを5秒待っているプロセッサは、待ちながら自分でそのことを出す(`lib/libtk/sysdepend/cpu/core/armv8a/spinlock.c`)。スピンロックは、取ったプロセッサ、場所、時刻を各プロセッサ4つまで記録しているので、どのプロセッサがどこで取ったロックを待っているのかが分かる。待つプロセッサが時刻を確かめられるよう、起動時にGeneric Timerのイベントストリーム(`CNTKCTL_EL1.EVNTEN`、約1ミリ秒ごと)を有効にし、`wfe`で待つプロセッサを定期的に起こす。待ちが続けば30秒ごとに繰り返し、ロックを取れたらそのことを出す。ビッグカーネルロックを一度の取得で5秒持ち続けている場合も、監視する側のプロセッサが出す。

タスクが互いのミューテックスを待ち合って輪になっている場合(デッドロック)は、監視の割込みのたびにタスクの表を2048個ずつ調べて見つけ(割込みを禁止する時間を短くするため、表全体を数秒かけて一巡する)、輪をなすタスク、待っているミューテックス、持っているタスクと、各タスクが待ちに入った場所と呼出し元を出す。1つの輪は、それが続く間に1度だけ出す。

これらの出力は`!LOCKUP!`で始まる。止まったプロセッサがコンソールのロックを持ったままのこともあるので、出力にはコンソールのロックを使わず、UARTへポーリングで直接書く(`tm_printf_urgent`)。その間、ほかのプロセッサの通常の出力は1文字ごとに待ち、行が混ざらないようにする。アドレスはカーネルのマップファイル(`build_make/tessronos*.map`)か`aarch64-none-elf-addr2line`で関数に直す。

監視は初期タスクが`usermain`を呼ぶ直前に始まり(`knl_lockup_arm`)、システムの終了と再起動の初めに止まる(`knl_lockup_stop`)。

### 4.7.2 デスクトップの監視

デスクトップの起動を待つ初期タスクのループ(`ts_desktop`)は、1秒ごとにウォッチドッグをキックする(`knl_wdog_kick`)。初期タスクはすべてのタスクより優先度が高いので、これが20秒止まるのは、タイマかスケジューラが止まったか、すべてのプロセッサが割込みを受けられない状態である。このとき、初期タスクが待っている場所とプロセッサの状態を出す。

デスクトップのタスクの主ループが10秒回ってこない場合も、そのタスクが待っているオブジェクト、待ちに入った場所と呼出し元、ミューテックスの待ちの連鎖を出し、最後にShift+Pauseで回復できることを1行出す。x64では、錠として使うセマフォ(実身のファイルシステムのボリュームの錠と、USBの管理の係の錠。取るときと放すときに`knl_lockup_sem_held`で持ち主を控える)の待ちも連鎖としてたどる。連鎖の各ミューテックスとセマフォの持ち主についても、状態(実行可能か待ちか)、待っているもの、止まった場所と呼出し元を出し、USBの管理の係のロックの持ち主とその長さも出す。主ループがまた回ってきたら、止まっていた長さを1行出す。画面が固まったときの手がかりにするためのもので、こちらではシステムを再起動しない。主ループが入力を待っている間(`wm_read_event`の中で`ts_hid_read`を待っている間)は、何も押されなくても止まったとはみなさない。`wm_read_event`が待つ前後に`knl_wdog_idle`を呼び、待っている間は監視の割込みが主ループの時刻を進める。パネルを操作する間のループもこの関数で入力を待つので、パネルを長く開いていても止まったとはみなさない。止まったかどうかは`knl_wdog_stuck`で問い合わせられる。強制終了のタスクはこれを見て、デスクトップを立ち上げ直すかどうかを決める(5.5.5)。

デスクトップの立ち上げは、主ループに入る前の段階ごとに「`TessronOS desktop: - 段階の名前`」を1行出す(かな漢字変換、壁紙、メッセージ行、入力モード、キャビネット、最初の画面、画面サイズの確認、ディスク修復の結果、システムの更新の続き、ループ)。キックする初期タスクのループ(`ts_desktop`)は、1秒ごとにこれを見張る(`dt_watch`)。最初の30秒は5秒ごとに、今の段階とその長さ、主ループの回数、画面を組み立てた回数(`wm_stat`)、画面へ送った回数(`ts_disp_stat`)、画面を押さえている数と最初に押さえたタスクとその長さ(`knl_disp_hold_note`)、デスクトップのタスクと合成のタスクの状態(待ちの要因と待っているオブジェクト)を1行出す。ループの前の段階が5秒進まないときは、デスクトップのタスクと合成のタスクが待っている場所と連鎖を、画面が3秒押さえられたままのときは、最初に押さえたタスクの待っている場所と連鎖を、それぞれ1回出す(`knl_lockup_tell_task`)。どちらも記録のファイルを2秒後に書かせる。デスクトップのループが回っていて組み立てた回数が増えるのに送った回数が増えなければ、画面が押さえられたままであることが分かる。電源を切るときは、デスクトップのタスクが終わるまでの長さを1行出し、10秒で終わらなければその待っている場所を出す。

カーネルの可変領域(`knl_vmap`)の確保に失敗したときは、最初の8回について、ページ数、理由(アドレスの続きがない、ページがない、ページテーブル)、使っているページ数と最も長い空きを出す。ウインドウマネージャの背景(壁紙を画面の大きさに広げたもの)が確保できずに壁紙なしの机の色で描くときも1回出す。確保の途中でページが取れなかったときは、取ったページを返してから、アドレスの範囲をまとめて1回だけ返す(以前は範囲の一部を先に返してから全体をもう一度返していたので、その間に別のプロセッサが取った範囲を空きにすることがあった)。

### 4.7.3 ウォッチドッグ

Raspberry Pi 5、CM5、Raspberry Pi 4系では、PMのブロックのハードウェアウォッチドッグを使う(3.8)。監視の割込みのたびに、10秒後に全体をリセットするよう設定し直す。割込みを受けないプロセッサ、例外で止まったプロセッサ、持ち続けられたビッグカーネルロック、止まったキックのいずれかがあると、それを出力した時点から数え、設定した時間(既定は30秒)が過ぎたら設定し直すのをやめる。ウォッチドッグはその約10秒後にボードをリセットし、ファームウェアから起動し直す。止まった状態が途中で解消すれば、数えるのをやめる。すべてのプロセッサが止まると誰も設定し直さないので、何も出さずに10秒でリセットされる。

時間はマシンの設定(`SYSDEF_CONF_DEV`)の行`WATCHDOG`で秒単位に指定する。0にするとウォッチドッグを止め、止まったマシンをそのまま残す。検出と出力は続ける。QEMUにはウォッチドッグがないので、検出と出力だけを行う。

### 4.7.4 カーネルの例外

カーネル(EL1)で起きた同期例外、SError、FIQ、登録のない割込み、スタックの溢れ(`!STACK!`)も、同じくコンソールのロックを使わずにUARTへ直接書く。プロセッサの番号、`ESR`、`FAR`、`ELR`、`SPSR`、レジスタ、実行中のタスク(番号、開始アドレス、プロセスの番号とファイル名)、カーネル内で起きた場合はフレームポインタをたどった呼出し元を出し、そのプロセッサを止める。表示の途中でさらに例外が起きた場合は、短い1行だけを出して止まる。ほかのプロセッサは動き続け、止まったプロセッサを4.7.1のとおり報告し、設定した時間の後にウォッチドッグがリセットする。

### 4.7.5 試験

`tests/ktest/ktest_lockup.c`が、時間を1秒に縮めて、わざと止まった状態を作る。プロセッサの割込みを禁止したまま回る(SGIを受け付けないことも確かめる)、タイマの印だけを止める(SGIを受け付ける)、スピンロックとビッグカーネルロックを2秒持つ、2つのタスクが互いのミューテックスを待つ、キックを止める、デスクトップのループを止めたことにする、の各場合について、検出と出力を確かめる。デスクトップのループを本当に止めたときの検出と、その後の強制終了と立ち上げ直しは`tests/ktest/ktest_fq.c`が確かめる(5.5.6)。

### 4.7.6 走っていないタスクのスタックの監視

`make STKWATCH=1`でビルドすると、ディスパッチャが、走っていないタスクのスタックの書き換えを見つける。CPUがタスクのコンテキストを手放す直前(`dispatch.S`、ほかのCPUがそのタスクを取る前)に、例外フレームのx29からフレームポインタをたどり、カーネルのコードを指す戻りアドレスを最大12個、場所と値をTCBに控える(`knl_stk_snap`)。CPUがそのタスクを取るときに読み直し(`knl_dispatch_pick`)、違っていれば、走っていない間に誰かがそのスタックに書いたことになる。そのタスクが戻って例外を起こす前に、`!STKWATCH!`で始まる行に、場所、元の値と今の値、どのCPUが何マイクロ秒前に手放したか、その前後の16ワード、待ちの結果をその近くに書くことになっているタスク、各CPUが走らせているタスクを出し、すべてのCPUを止める。デバッガで調べられるよう、マシンはそのまま残る。EL0のフレームと、カーネルのコードを指さないワードは見ない。TCBが1つあたり約200バイト大きくなるので、普段のビルドには入れない。

### 4.7.7 カーネルのタスクのスタックの大きさ

カーネルのタスク(プロセスに属さないもの)のシステムスタックは、可変領域(4.6)のページに取り(`knl_vmap_stack`)、その下の8ページ(`TASK_STK_GUARD_PAGES`、32KB)をマップしない。スタックはページの倍数に切り上げ、足元がマップしないページのすぐ上に来るようにする。ガードを1ページより広くしたのは、大きなフレームの関数がガードを飛び越えないようにするためである(次の段落の`-Wframe-larger-than`の対象外のFreeTypeが25KBのフレームを持つ)。ページの物理アドレスは連続しないので、スタック上のバッファをデバイスに渡すときは`ConvPhysicalAddress`で引く。`VA2PA`を使う所(SDの転送とメールボックス)を調べ、SDは線形マップにないバッファをデータポートで転送し、メールボックスの呼び手はスタックのバッファを渡さないことを確かめた。プロセスのタスクのシステムスタックは今までどおりページアロケータの連続ページで、ガードを置かない。ユーザが`TA_USERBUF`で渡したスタックと、ページアロケータの初期化の前に作るタスクのスタック(Imalloc)にもガードはない。

スタックからはみ出すと、その場でフォールトになる。x86-64では、ガードに当たったページフォールトのフレームも積めないので、ダブルフォールトになってISTのスタックに入り、CR2がガードの中なら`!STACK!`の行を出してから例外の報告(4.7.4)を続ける。スタックに余地があるままガードに書いたときは、ページフォールトの中で同じ行を出す。AArch64では、例外のフレームを積めないとベクタの中で同じ例外を繰り返すので、EL1のデータアボートについてベクタの入口で`at s1e1w`によりフレームの場所が書けるかを尋ねる。書けなければ、そのプロセッサの割込みスタック(タスクのスタックで走っている間は使っていない)に移り、`knl_stack_out`から`!STACK!`の行と報告を出す。x0はこの間`CONTEXTIDR_EL1`に置く(カーネルは他に使わず、EL0からは読めない)。行には、タスク、スタックの大きさ、当たったアドレス、そのときのPC(`RIP`、`ELR`)とスタックポインタを出す。報告はレジスタと呼出し元を続けて出し、そのプロセッサを止める。

スタックの最も下の8バイトの決まった値(`TASK_STK_MAGIC`)は残す。ディスパッチャはタスクを走らせる前にこれを確かめて、違えば`!STACK!`を出して止める(4.7.4)。ガードのないスタックと、スタックの外からの書込みはこれで捕まえる。

返されたスタックはその場ではマップを外さない。タスクが自分で終わるときはディスパッチャが割込みを禁止したまま返すので、そこでTLBの無効化を待ちたくないからである。リストに置いてマップしたまま持ち(`knl_sstk_free`)、次に同じページ数のタスクを作るときはそれをそのまま使う。16個を超えた分は、次のタスクの作成と削除のときに外す(`knl_sstk_trim`)。ページが足りないときはリストのものをすべて外してから取り直す。

試験は`tests/ktest/ktest_stkg.c`(`make KTEST=1 KTONLY=stkg`)である。スタックの配置とガードがマップされないこと、足元の近くまで使えること、1MBのスタックの2000回の作成と削除でスタックが再利用されること、はみ出して押し込んだときとスタックの下へ直接書いたときに`!STACK!`が出てそのタスクとアドレスが正しいことを確かめる。後の2つはプロセッサを1つずつ止めるので、名指ししたときだけ走る。

ガードを置く前の話として、R1.200の開発中には、図形の線の端を押したときの処理(`application/desktop/dtftool.c`の`df_end_press`)が、線の経路の8272点(66KB)を局所変数に取っていた。デスクトップのタスクのスタックは、求めた64KBにシステムの分(AArch64では4KB、x86-64では8KB、`DEFAULT_SYS_STKSZ`)を足した大きさである。AArch64ではこれを呼ぶだけで全体からはみ出し、隣に置かれていたジャーナルの確定したコピー(7.3)の後ろの方を、自分のフレームのレコードで書き換えた。このコピーはチェックポイントでそのまま媒体に書かれるので、システムボリュームのオブジェクトブロックのCRCの誤りとして現れ、ボリュームは読出し専用になった。何が壊れるかはヒープの配置しだいで、調べるための記録を足すと再現しなくなった。

そこで、カーネルのイメージに入るCのコードは`-Wframe-larger-than=4096`でビルドし、4096バイトを超えるフレームを警告にする(`build_make/common.mk`の`CFLAGS_COMMON`)。大きな作業域は`Kmalloc`で取るか、ヒープに取った構造体に持たせる。カーネル内の試験は1つずつ順に走るので、大きな作業域を`static`にしてかまわない。移植したライブラリ(FreeType)は上流のままにして、その分だけ警告を外す。FreeTypeのラスタライザ(`ftraster.c`、`ftgrays.c`)とCFFの解釈(`psintrp.c`)は16KBから25KBのフレームを持つので、それを呼ぶタスクには、それを足しても余る大きさのスタックを与える。

`KTEST=1`と`UITEST=1`のビルドでは、タスクを作るときにスタックの全体を決まった値(`STK_FILL`)で埋め、足元から上へその値が残っている所までを、一度も使われなかった所とみなす(`CNF_STK_USAGE`、`kernel/tkernel/task_manage.c`)。LinuxのCONFIG_DEBUG_STACK_USAGEと同じ考え方である。削除したタスクの分は、開始アドレスとスタックの大きさの組ごとに、最も深い使用量を控える。UIの試験の`stkuse`(12.4)と、カーネル内の試験の終わり(`KTEST SUMMARY`の前)で、今あるタスクと削除したタスクの組ごとに、スタックの大きさ、最も深い使用量とその割合をコンソールに出し、残りが4分の1を切るものに`LOW`を付ける。

## 4.8 アーキテクチャの層

CPUのアーキテクチャに依存するものは、コア依存の置き場(`kernel/sysdepend/cpu/core/armv8a/`、`include/sys/sysdepend/cpu/core/armv8a/`、`include/tk/sysdepend/cpu/core/armv8a/`、`lib/libtk/sysdepend/cpu/core/armv8a/`)に置く。ドライバ、`sysman`、プロセス、ELFのローダ、PCIeなどの共通部は、AArch64の命令やレジスタを直接書かず、次の関数とマクロを使う。どれもインライン関数かマクロなので、AArch64では以前と同じ命令になる。別のアーキテクチャを足すときは、同じ名前で中身の違うヘッダを置き場ごとに足す。

makefileは`TARGET`からアーキテクチャ`ARCH`(Raspberry PiとQEMU virtは`aarch64`、`_X64_`は`x86_64`)を決め、そこからコア依存の置き場の名前`ARCH_CORE`(`armv8a`、`x86_64`)を決める。`toolchain.mk`はコンパイラの名前の頭とQEMUを、`common.mk`はインクルードパスのコア依存の置き場と命令セットの基準を、`sources.mk`はコア依存のソースの一覧(`SRCS_CORE_armv8a`)を、これで選ぶ(12.2)。

AArch64のまま共通部に残っているものは次のとおりである。

- `include/ts/proc.h`の`T_PRCFLT`と`T_TSFLT`はプロセスに見えるAPIで、AArch64のレジスタの並びのままにしてある。x86-64では`T_TSFLT`だけを`__x86_64__`のときの別の形にし、AArch64の形は変えていない。`T_PRCFLT`は項目の名前(`esr`、`far`、`elr`、`lr`)をそのまま使い、x86-64ではベクタとエラーコード、CR2、`rip`、`rbp`を入れる。
- 共通部の変数や項目の名前の`ttbr0`(`CTXB.ttbr0`、`T_SPACE.ttbr0`、`knl_sync_cores`の引数など)は、プロセスの空間の根を表す値の名前として残している。中身は`knl_mmu_space_root`が作る。
- `outer_kernel/wm/compose_simd.c`はNEONで書いた合成のループで、AArch64でしか翻訳できない。x86-64では`outer_kernel/wm/x86_64/compose_simd.c`(SSEとAVX2、3.10.3)を使う。`peripheral_kernel/fs/crc32c.c`は`__aarch64__`のときだけ`crc32c`の命令を使い、ほかではソフトウェアで計算する。
- `device/gpu/`以下と`lib/libgl/gl_drm.c`は、ほかの作業と並行しているためまだ置き換えていない(キャッシュの直書きなど)。
- `tests/ktest/`の試験のうちレジスタを直接見るもの(`ktest_el0.c`、`ktest_pan.c`、`ktest_smp.c`、`ktest_lockup.c`、`ktest_task.c`、`ktest_mem.c`、`ktest_cxx.c`、`ktest_fault.c`など)は、`CPU_CORE_X86_64`で書き分けている。Armの機器だけの試験(`ktest_board.c`、`ktest_sd.c`、`ktest_gpu.c`、`ktest_gl.c`)はx64では翻訳しない(3.10.5)。

## 4.9 マシンの終了

〈電源を切る〉、〈再起動〉、システムの更新の後の再起動、最初のウインドウを閉じたときの終了は、どれも同じ順番で進む。x64、Raspberry Pi 4、Raspberry Pi 5、QEMU virtで違うのは、最後に機器を止める部分だけである。

1. プログラムのウインドウに閉じる要求を送る(`wm_obj_close_programs`)。閉じるボタンを押したときと同じ`OB_E_CLOSE`である。ポップアップ(パネルやメニュー)には送らない。デスクトップはこの間も入力を読み続けるので、プログラムの保存の確認に答えられる。
2. 5秒たってもウインドウが残っているプログラムがあれば、その名前の一覧と〈取消〉〈強制的に終了〉をパネルで出す。〈取消〉なら終了をやめてデスクトップに戻る。すでに終わったプログラムは終わったままである。〈強制的に終了〉なら保存せずに進む。パネルを出している間にウインドウがすべて閉じれば、パネルを消してそのまま進む。パネルに3分答えがなければ、保存していない内容を失わないように終了をやめる。ウインドウが閉じて保存だけが残っているプログラムは終了を止められず、ブラウザのCookieなどの保存は要求から20秒までの間に行う。
3. 残ったプログラムの名前をログに出し、システムのプロセス(`TS_PRC_SYSTEM`)を除くすべてのプロセスに`SIGTERM`を送る(`knl_prc_end_all`)。ウインドウのないプロセスもここで終わる。プロセスの数に上限はない。10秒待っても(〈強制的に終了〉のときは1秒)残るものは名前をログに出して強制終了し(`knl_prc_kill`)、さらに3秒待つ。
4. デスクトップのタスクが自分のウインドウを保存して閉じ、終わる。このタスクが60秒動かなくなったら、ログを出して待つのをやめ、3を代わりに行う。
5. すべてのプロセスが終わった後で、ファイルシステムを書き出す(`knl_fs_sync_report`)。マウントごとと実身のボリュームごとに結果をログに出す。ディスクが外れていたものも、書き込まなかったと出す。失敗したら1回やり直す。それでも失敗したときはメッセージ行に3秒出して、止まらずに進む。デバイスのキャッシュも`TDN_FLUSH`で書き出す。
6. カーネルの`shutdown_system`から機種ごとの`knl_finish_device`を呼ぶ。Wi-Fiの接続を切った後で、どの機種でも`knl_fs_finish`を通る。
7. `knl_fs_finish`は、まず実身のボリュームを閉じる(`knl_obfile_shut`、`ts_finish_vol_blk`)。システムボリュームはカーネルが実身を開いたままなので外せない。そこでトランザクションを止めてジャーナルの内容を本来の場所に書き、スーパーブロックに`TSFSBLK_ST_CLEAN`を立て、デバイスのキャッシュまで書き出してから、読み取り専用にする。これより後に書き込もうとしても拒まれ、印は壊れない。次の起動では、ボリュームを開くときに`taken down properly the last time`か`not taken down properly`をログに出す。ジャーナルを戻す処理は印によらず毎回行う。印が付いていなくても起動時に検査は自動で走らない。NTFSのdirtyビットのように起動時に検査する形にはしていない。fsck.tsfsは印がなければ警告を出す。
8. 続いて、書き込めるマウントのうちデバイスを持つものを外す(`mount_free`)。FATやexFATの使用中の印が消え、その書込みもデバイスのキャッシュから書き出す。ファイルが開いたままのマウントは書き出すだけで残し、開いているファイルの数をログに出す。次の起動で検査される。x64では`/boot`と`/tslog`を後回しにし、記録を書いてから外す(3.10)。
9. 機器を止める。NVMeはコントローラをシャットダウンする。SDカードは書込みの完了を待って返すのでキャッシュがなく(`sdhci.c`)、Pi 5では1.8Vのカードの電源を切る(`knl_sd_finish`)。AHCIとUSBストレージのキャッシュは7と8の`TDN_FLUSH`で書き出している。

固まっても電源が切れないままにならないように、終了には時間の上限がある(`knl_off_limit`)。優先度の高いタスクが時刻を見ていて、段階ごとに90秒を過ぎると`NOT FINISHED IN TIME`とログに出し、残りを飛ばして電源を切るか再起動する。確定した変更はジャーナルにあるので、次の起動では停電の後と同じようにジャーナルから戻す。

スリープ(`pm.c`)は`fs_sync`を使い、ボリュームを読み取り専用にしない。停電の試験(`make KTONLY=tsfscut powercut`)は機械を外から止めるので、この順番を通らない。

ログの行は`shutdown:`で始まる。確かめるには`tools/tests/ui_shutdown1.steps`を`--keep-disk`で流し、残ったディスクで`ui_shutdown2.steps`を流す。〈取消〉、保存の確認への回答、閉じると書き込むプログラム、ウインドウのないプロセス、`SIGTERM`を無視するプロセスを通し、次の起動で読めることを見る。`ui_shutdown4.steps`は〈強制的に終了〉を通す。
