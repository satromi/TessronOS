# 第7章　ファイルシステム

## 7.1 2つのファイルシステム

TessronOSは2つのファイルシステムを持つ。システムの実身を格納するTSFSと、ブートパーティションと外部メディアに使うFATである。

| | TSFS | FAT |
| --- | --- | --- |
| 用途 | 実身の格納 | ブートパーティション、PCとデータをやり取りするメディア |
| 名前 | 実身はUUIDで開く。ディレクトリツリーはない | パスで開く |
| 形式 | TessronOS独自。ジャーナルとチェックサムを持つ | FAT12、FAT16、FAT32。長いファイル名に対応 |
| API | 実身の基本操作`ob_`(第8章) | T2EX互換の`fs_` |

## 7.2 fs_

`fs_`はT2EXのファイル管理の関数である。`fs_open`、`fs_read`、`fs_write`、`fs_close`、`fs_mkdir`、`fs_rename`、`fs_stat`などでFATのボリュームを扱う。マウントテーブルは全体で1つで、`/boot`にSDカードの第1パーティション(QEMUでは試験用ディスクのFATパーティション)がマウントされる。USBメモリは、デバイスの実身を通して要求すると`/media`の下にマウントされる(6.1)。マウントに使うfimpは、区画の先頭の中身から見分けて選ぶ(7.6)。

ファイルディスクリプタはプロセスごとに持ち、プロセスが終了すると閉じる。プロセスの`fs_read`と`fs_write`は256KBずつに分割して実行する。

FATは、電源断の後にマウントしたとき、クラスタチェーンとディレクトリエントリのサイズの不一致など、書込み途中で残った不整合を検査して修復する。

FATのファイルの大きさはディレクトリエントリの32ビットで決まるので、4GB-1バイトを越える書込みと切り詰めは`EX_FBIG`で断る。越える位置をまたぐ書込みは、入る分だけ書いてその長さを答える。前は検査がなく、越えて書くと大きさの欄が桁あふれして、ファイルの中身とクラスタチェーンが食い違った。切り詰めでファイルを伸ばすときは、クラスタチェーンを伸ばし、足したクラスタと、前の終わりから最後のクラスタの終わりまでを0にする(前は大きさだけを変え、伸ばした所を読むと`EX_NOENT`になった)。終わりより先に書くときも、前の終わりから最後のクラスタの終わりまでを0にする。`fs_read`と`fs_write`は答えがINTなので、1回に動かすのは0x7FFFF000バイト(LinuxのMAX_RW_COUNTと同じ)までとし、それより大きな要求には短く答える。

### ディスクの実身の鍵から開く

利用者が差したディスクの中のファイルは、ディスクのデバイスの実身を開いた鍵から開く。パスの木(`/media`)にはつながず、パスはファイル層の中とディスクの中の道だけになる。Linuxのfsopenとfsmount(マウントをパスの木につながずに記述子で扱う)と、openat2の`RESOLVE_BENEATH`(記述子のディレクトリの下から出ない)と同じ考え方である。

| 関数 | 働き |
| --- | --- |
| `fs_opn_vol(devkey, fimpnm, flags)` | ディスクのファイルシステムの根のディレクトリを記述子(vd)として返す。`fimpnm`がNULLなら中身から見分ける。`flags`は`FS_MNT_RDONLY`だけ |
| `fs_openat(vd, path, oflags)` | ディスクの中のファイルを開く。返すのは普通の記述子で、`fs_read`などがそのまま使える |
| `fs_statat`、`fs_mkdirat`、`fs_rmdirat`、`fs_unlinkat`、`fs_utimeat`、`fs_renameat` | ディスクの中の道の操作。名前を変えるのは同じディスクの中だけ |
| `fs_fstatvfs(vd, st)` | 空き容量など |

vd自身も記述子なので、`fs_getdents`で根の一覧を読め、`fs_close`で閉じる。プロセスが終わると閉じる。

権利は、マウントの権利と記述子の権利を分ける。

- マウントの権利は、そのディスクを開いている者のうち、書く者が1人でもいれば書ける形である。読むだけのマウントに書ける形の要求が来たとき、そのマウントで開いているファイルがなければ、マウントを書ける形でつなぎ直す(FATの不整合の検査と修復は、書ける形でつなぐときに行うため)。開いているファイルがあれば`EX_BUSY`で断る。
- 記述子の権利は、`fs_opn_vol`のときの`flags`と鍵の権利で決まり、マウントが書ける形になっても変わらない。読むだけのvdからは、書くための`fs_openat`と、ディスクの中を変える操作が`EX_ROFS`になる。vdから開いた記述子は、vdの権利を越えない。書くには、鍵に`OB_OP_WRITE`が要る(今の`fs_attach_dev`と同じ)。

道は、vdのディスクの根から下だけをたどる。先頭の`/`はディスクの根を指す。`.`と`..`はファイル層が道を渡す前に字面で畳み、根より上に出る`..`は`EX_ACCES`で断る。道はvdのマウントのfimpだけに渡すので、パスの木のほかのマウントには届かない。シンボリックリンクを持つfimpは、そのボリュームの中だけで解き、根より上や別のボリュームを指すリンクはたどらない。KTESTで、`..`、`../..`、`/../x`、根より上を指すリンクで、vdの外のファイルを開けないことを確かめる。

ディスクが抜かれたときは、今のパスのマウントと同じく、マウントに`gone`の印が付き(`knl_fs_revoke`)、vdとそこから開いた記述子は、読み書きと道の操作に`EX_IO`で答える。`fs_close`は通り、最後の記述子が閉じたときにマウントが片付く。KTESTで、USBのディスクをQEMUのモニタで抜き、vdとファイルの記述子が落ちずに`EX_IO`で答え、閉じられることを確かめる。

`/media`のパスの木から同じディスクを使う形(`fs_attach_dev`)は、バックアップとファイル変換が移り終えるまで残す。その間、1つのディスクのマウントは1つだけにする。`fs_opn_vol`は、そのディスクのマウントがあれば(`/media`にあっても)それを共に使う。`fs_attach_dev`は、`fs_opn_vol`がパスなしで作ったマウントがあれば、それに`/media`の道を付ける。`fs_detach_dev`は、vdが残っていれば道だけを外し、マウントは最後の記述子が閉じたときに片付く。移り終えたら、`fs_attach_dev`と`/media`の名前をプロセスから見える所から外す。

## 7.3 TSFS

TSFSは、実身の構造をそのままディスク上の形式にしたファイルシステムである。GPTのパーティションに置き、パーティションタイプGUIDは`54465331-0000-4000-8000-5446532d5631`である。

実身は次の要素からなる。

- 管理用セグメント。名前、日時、保護情報、レコードの並びと型、アプリケーションが格納する設定(`applist`、`window`、`tessronos.*`など)を持つJSONである。
- アイコン。ICOかPNGで、64KBまで。
- レコードの列。レコードは型(0〜31)とサブタイプを持つバイト列で、任意の位置に挿入と削除ができる。型1はxmlTADで、その中の`<link>`が仮身である。1つの実身のレコードは256まで(`TSFS_MAX_REC`)である。ネイティブの形式では、配置表(1レコード48バイト)は数を32ビットで持つ管理用の部分である。小さいうちは実身ブロックのインライン領域(3584バイト)に置き、入りきらなくなると共通の頭を持つブロックの連続(1ブロックに約84レコード分)に移して、ジャーナルを通して書く。仮身表やメタデータと同じ置き方で、索引の段は増えない。256レコードの配置表は12KBで、4ブロックの連続になる。したがって上限は形式ではなく、管理用セグメントが持つレコードの並び(`records`)の大きさで決めている。256レコードの並びは約10KBで、ネイティブのボリュームのメタデータの上限(約492KB、8.12)に十分収まる。上限を64から256に広げたときに実身ブロックの形は変えていないので、それ以前のボリュームはそのまま読める。ただし、65以上のレコードを持つ実身を作ったボリュームは、上限が64のカーネルと検査のツールでは形が壊れていると判断される。カーネルの検査(`tsfsck.c`)とホストのツール(`tools/tsfs_py`、`mktsfs`、`fsck.tsfs`)の上限も256にした。`tests/ktest/ktest_tsfsobj.c`の`test_many_records`は、256のレコードを型とサブタイプを変えながら作り、257個目が断られること、マウントし直しても中身と型が保たれること、途中を消すと後が詰まること、ボリューム全体の検査が実身について何も見つけないことを確かめる。
- レコードのバイトが置かれるブロックの連なり(エクステント、ラン)。1つのランなら置き場そのものに(`F_RUN`)、165まで(`TSFSO_MAX_EXTENTS`)なら1つの葉のブロックに(`F_TREE`)、それより多ければ、葉の番号を並べた索引のブロックと、165ずつのランを持つ葉に(`F_TREE2`、2段の木)置く。2段の木は165×165=27225のランまで持てる。前は1つの葉までで、空きが細切れのボリュームでは大きなレコードが`E_NOMEM`で書けなかった。2段の木は1つの葉に収まらないレコードのときだけ使い、収まるまで短くなれば1つの葉に戻す。書き足すときは、変わったランを持つ葉から後と索引だけを書き直すので、1回の変更で書くブロックは少ない。
  - 2段の木を初めて書いたボリュームは、スーパーブロックの非互換の機能に`TSFSBLK_INCOMPAT_XT2`(0x0002)の印を付ける(R1.200から)。印は、2段の木がなくなっても外さない。R1.110までのカーネルは、知らない非互換の機能の印があるボリュームをつながず(`ts_opn_vol_blk`が`E_NOSPT`)、スーパーブロックを読む以外は何も書かないので、ボリュームを壊さない。R1.110の`fsck.tsfs`は、検査では「incompatible features 0x2: the kernel will not open it」の誤りを出す。ただし`--fix`を付けると、印は残したままスーパーブロックと予備を書き直し、2段の木を知らずに直そうとするので、R1.200のボリュームにR1.110の`fsck.tsfs --fix`を使ってはいけない。R1.200からの`fsck.tsfs`は、知らない非互換の機能の印があるボリュームには`--fix`と`--relink`で何も書かず、終了コード2で戻る(R1.110の`fsck.tsfs`は0x2の印を立てたボリュームで、R1.200の`fsck.tsfs`は知らない0x100の印を立てたボリュームで確かめた)。R1.200のカーネルの検査(`tsfsck.c`)と`tools/tsfs_py`は2段の木を読み、印のないボリュームの2段の木は誤りとして報告する。`ktest_tsfsobj`の`test_many_runs`は、2つのレコードを1ブロックずつ交互に伸ばして400を越えるランにし、印が付くこと、つなぎ直しても全部読めること、検査が何も見つけないこと、短くすると1つの葉に戻ることを確かめる。
- リソース。レコードに付随する画像、音声、動画である。
- 仮身表。この実身が含む仮身の一覧で、TSFSが型1のレコードから生成する。

実身はUUIDのversion 7で識別し、B+木でUUIDから検索する。時計が設定される前(電池のないマシンで、SNTPで時刻を合わせる前)に作る実身は、時刻を含まない乱数だけのversion 4のUUIDで識別する。キャビネットは仮身を並べた実身であり、ファイルシステム側にディレクトリはない。

TSFSは仮身表から、各実身を指している同じボリュームの仮身の数(参照数)を自動で数える。ほかのボリュームの実身を指す仮身は、指す側のボリュームでは数えず、指される側のボリュームが持つ「ほかのボリュームからの参照」の記録を通して、指される実身の参照数に数える(8.3)。アプリケーションは参照数を操作しない。参照数が0になった実身は屑実身になり、空き領域が減ったとき、または要求されたときに回収される。

### 格納方式

TSFSには2種類の格納方式がある。

| 格納方式 | 形式 |
| --- | --- |
| ネイティブ | GPTのパーティションをTSFSの形式で使う。システムボリュームはこの方式 |
| FAT上 | FATのディレクトリに、実身を1つずつTADjs Desktopと同じ形式のファイル群で格納する |

FAT上の格納方式のファイル群は次の形式である。この形式で書き出せば、TADjs Desktopで開ける。

| ファイル | 内容 |
| --- | --- |
| `{UUID}.json` | 管理用セグメント |
| `{UUID}_0.xtad` | 位置0のレコード(xmlTAD) |
| `{UUID}_N.xtad`、`{UUID}_N.bin` | 位置Nのレコード(`.bin`は型1以外) |
| `{UUID}.ico` | アイコン |
| `{UUID}_N_M.png`など | 位置Nのレコードのリソース |

### 障害耐性

ネイティブのTSFSは、電源断が起きても管理構造が壊れないように設計してある。

- 管理ブロックはすべてチェックサム(CRC32C)を持つ。読み込んだブロックのチェックサムが合わなければ、ボリュームを読取り専用に切り替え、以後は書き込まない。最初の誤りは、その種類とブロックをコンソールに出す(`tsfs: 装置: ERROR kind ...`)。
- 変更はジャーナルに書いてから本来の位置に書く。マウント時にジャーナルを再生するので、途中で中断した変更は、すべて反映されるか、まったく反映されないかのどちらかになる。
- 誤りが記録されたボリュームは、マウントのときにジャーナルを再生せず、読取り専用で開く(誤りの種類、ブロック、最初と最後の時刻をコンソールに出す)。ジャーナルは検査(7.5)のときに再生する。それまでは、変更のトランザクションを始めようとしても`E_RONLY`で断る(`ts_jrnl_begin`)。以前は断らずにトランザクションを受け付け、ジャーナルのリングの長さが0のままコミットして、0での割り算の例外で止まっていた(ThinkPad X1 Yoga 第3世代で、起動中の時計の帯の書込み)。
- ジャーナルは本来の位置に置き終えた後も、前に書いたブロックのコピーを、リングが一周して上書きされるまで残す。秘密を含んでいたレコードを書き直したプログラムは、`ob_wip_vol`で、その実身のあるボリュームのジャーナルを0で書きつぶせる(`ts_jrnl_wipe`)。走っているトランザクションが終わるのを待ち、すべてを本来の位置に置いてから、リングの全体を0で書き、デバイスのキャッシュを空にする。リングには再生するトランザクションが残っていないので、再生は何もしない。その実身のレコードを書ける者だけが呼べる。ブラウザが、平文で保存されていたパスワードを暗号化し直した後に使う(14.4.7.1)。
- スーパーブロックは2つを交互に書き、さらにバックアップを持つ。
- 区画とボリュームを広げる途中で電源が切れても、元のまま使えるか、次に開くときに広げ終える(7.7)。
- 開いたまま削除された実身や、仮身表を再構築している途中の実身は孤児リストに登録し、マウント時とアンマウント時に後処理する。

`tools/fsck.tsfs`がボリュームを検査し、`tools/mktsfs`がボリュームを作成する。どちらもPythonで書かれ、ホストで動く。マシンの上での検査と修復は7.5で述べる。

### ジャーナルの確定とボリュームのロック

ジャーナルのトランザクションは、作る、閉じる、確定させる、の3つの段階を通る(`tsfsjrnl.c`)。

1. 作る。変更する操作がハンドルを取り(`ts_jrnl_begin`)、管理ブロックの新しい内容をメモリのトランザクションに入れる。データのブロックは本来の位置にそのまま書く(ordered)。
2. 閉じる。最後のハンドルを離した呼び手が、空きビットマップ、群の見出し、スーパーブロックの変更をトランザクションに加え、トランザクションを待ち行列に入れる(`ts_jrnl_close`)。その写しはこの時から、すべての読込みに見える。デバイスには何も書かない。リングに待ち行列の後ろの空きが足りないときだけ、ここで待ち行列を書き、チェックポイントをする。
3. 確定させる。`ts_jrnl_durable`を最初に呼んだ者が、その時の待ち行列をすべてリングに書く。まずデバイスのキャッシュを空にし(待ち行列のトランザクションが指すデータを媒体に置くため)、待ち行列のすべてのトランザクションを記述ブロックから確定ブロックまで1つのバッファに並べて1回の要求で書き(リングの端で折り返すときは2回)、最後にもう一度キャッシュを空にする。デバイスがFUAの書込み(`TDN_FUAWRITE`、6.8)を受けるときは、リングへの書込みをFUAで行い、最後のキャッシュを空にする要求は省く。受けないデバイスは最初の1回で`E_PAR`を返し、そのボリュームはそれからふつうに書いて空にする(`knl_tsfsblk_raw_writes_fua`)。書込みのキャッシュを持たないと言うUSBの大容量記憶(多くのカードリーダとUSBメモリ)は、Linuxのsdと同じく、キャッシュを空にする要求に命令を送らずに成功で答え、FUAも受けない(6.3.0)。そのため、USBでは確定は、装置が書込みを終えたと答えたことだけに頼る。トランザクションが指すデータの書込みがすべて終わったと答えてから、リングへの書込みを出す。リングへの1回の書込みの中の順序は、ほかのデバイスでFUAで書くときと同じく、装置に任せる。答えた後も自分のキャッシュに持っている(それをキャッシュのページで言わない)装置では、電源を切る直前の確定が失われることがある。これはLinuxでも同じである。書いている間に来た者はそれを待ち、多くはそれで確定する(group commit)。

`tsfs.c`の操作は、ボリュームのロックを持ったまま操作を行ってトランザクションを閉じ、ロックを放す。ロックを持つ間にデバイスへ書くのは、データのブロックと、トランザクションの外で本来の位置に書くブロックだけになる。確定をいつ待つかは、次の「確定の約束」のとおりである。`ts_end_trx`で終えるトランザクションは、戻る前に確定させる。

#### 確定の約束

開いている実身のレコードを書く、足す、切り詰める、取り除く、並べ替える、型を変える操作(`ob_wri_rec`、`ob_apd_rec`、`ob_trn_rec`、`ob_del_rec`、`ts_ins_rec`、`ts_mov_rec`、`ts_set_rtp`)は、トランザクションを閉じて待ち行列に入れたところで戻る。媒体に置くのは、次のどれかが最初に起きたときである(`tsfs.c`の`vol_lazy`)。

- その鍵を閉じたとき(`ob_cls_obj`)。閉じる操作は、その鍵で変えたものが媒体に置かれるまで待ち、置けなければ誤りを返す。
- 同期のAPIを呼んだとき(`ob_syn_obj`。POSIXの層の`fsync`と`fdatasync`は`fs_fsync`を通してこれにあたる。`sync`は全部のボリューム)。
- チェックポイントのタスクが動いたとき(5秒ごと、`CNF_TSFS_FLUSH_MS`)と、ほかの者が確定させたとき。待ち行列はまとめて1回でリングに書くので、いくつの操作があっても、キャッシュを空にする要求は2回(FUAで書けるデバイスでは1回)である。

レコードを丸ごと置き換える操作(`ob_rpl_rec`)、メタデータ、アイコン、資源の書込み、実身を作る、消す操作は、これまでどおり戻る前に媒体に置く。

同じ実身を、書くキーと読むキーが同時に開いていることがある(排他を指定しない書く者と、書込みの排他`OB_O_WEXCL`で開いた書く者は、読む者を締め出さない。開くときの排他の指定は8.3)。TSFSの層は、実身の開き方を開いたキーごと(`TSFSOBJ`)に持ち、レコードの読み書きはボリュームのロックの中で行う。`ob_rpl_rec`は新しい場所に書いてから1つの変更で差し替えるので、読む者に見えるのは古いレコードか新しいレコードで、混ざったものは見えない。その場で上書きする`ob_wri_rec`は、操作の途中の中身も見えうる。設定の実身の書込みは`ob_rpl_rec`を使う。

電源が切れたときは、次のようになる。

- 確定していない操作は失われる。ボリュームは壊れない(再生は確定ブロックの検査に通った最も長い先頭の部分だけを戻す)。
- レコードに書き足した分と、`ob_rpl_rec`で置き換えたレコードは、確定した時点の中身か、それより前の中身のどちらかになる。書き足すブロックは新しく取り、置き換えは新しい場所に書いてから1回の変更で差し替えるからである。
- すでにあるブロックを上書きした範囲は、確定していなければ新旧が混ざることがある。データのブロックは本来の位置にそのまま書く(Linuxのext4の`data=ordered`と同じ)。混ざるのを避けたいプログラムは、`ob_rpl_rec`で丸ごと置き換えるか、同期のAPIを呼ぶ。

アプリの保存は、デスクトップ(`om_obj_record_put`、`tad_write`)、表計算、カレンダー、手帳、単語登録、システム環境設定、ネットワーク設定、ユーザ環境設定、外観と機器の設定(`uconf.c`)、トレーが`ob_rpl_rec`を使い、保存が終わったと見せる前に媒体に置く。書庫管理、バックアップ、展開、ファイル変換の取込みのように新しい実身に書いていくものは、書き終えて鍵を閉じたときに媒体に置く。

書き込みの区切りは、確定が1回ごとでなくなった後も、システムの道具では4MBにしてある(`arc_pack.c`、`bk_util.c`、`bk_rest.c`、`bk_vol.c`、`unp_obj.c`、`xfu_in.h`の`XFU_CHUNK`、`xf.c`の`XF_CHUNK`)。1回の書込みの手間(実身ブロックと配置表を読み直すこと)が少ないほど速い。

1つのトランザクションの書き方は、これまでの「写しを書く、キャッシュを空にする、確定ブロックを書く、キャッシュを空にする」から、「キャッシュを空にする、写しと確定ブロックを書く、キャッシュを空にする」に変えた。キャッシュを空にする回数は同じ2回で、それが待ち行列のトランザクションの数によらなくなる。確定ブロックが写しより先に媒体に届いても、再生は各写しを記述ブロックが持つCRCと比べ、合わないところで止まるので、半端なトランザクションを戻すことはない。リングの形式と再生は変えていないので、前のカーネルで作ったボリュームもそのまま使え、`tools/tsfs_py`と`fsck.tsfs`も変わらない。

閉じたが確定していないトランザクションが解放したブロックは、そのトランザクションが確定するまで割り当てない(`tsfsblk.c`の`busy_add`、`knl_tsfsblk_unbusy`)。媒体の上ではまだ前の持ち主のものなので、次の持ち主のデータが先に書かれてから電源が切れると、前の持ち主の中身が他人のデータになってしまう。ボリュームが満杯で、空きがこのブロックだけのときは、閉じたトランザクションを確定させてから探し直す。Linuxのext4もXFSも、確定前に解放したブロックを同じ理由で使わない。

チェックポイントは、写しの一覧を取るときと後片付けのときだけジャーナルのロックを持ち、本来の位置への書込みはロックを放して行う。前は書き終えるまでロックを持っていたので、その間、管理ブロックを読む操作はすべて待っていた。チェックポイントの最中に置き換えられた写しは次の回に回し、書いている最中の写しのバッファは書き終えるまで放さない。書いている最中のブロックを本来の位置に書こうとする者は、チェックポイントが終わるのを待つ(`knl_jrnl_forget_blk`)。チェックポイントのタスクは5秒ごとのほか、写しが512ブロックを超えたとき、リングが半分埋まったときに起こされる。

#### このようにした理由

ThinkPad X1 Yoga 第3世代で、USBメモリのシステムボリュームから起動すると、デスクトップが最初のウインドウを出したところで10〜14秒止まった。デスクトップはボリュームのロックを待ち、ロックはかな漢字変換のタスクが、ジャーナルのリングへの書込みとSYNCHRONIZE CACHEの途中で持っていた。その起動ではUSBメモリへの書込みが4766回(合わせて15.8秒)、キャッシュを空にする要求が1807回(3.8秒)あった。原因は次の4つの重なりであった。

- 1つの操作が1つのトランザクションで、操作ごとに確定させ、そのたびにデバイスのキャッシュを2回空にしていた。リングへは1ブロックずつ要求していたので、小さな書込み1回でデバイスへの要求が8回ほどになった。
- その間ずっとボリュームのロックを持っていた。デスクトップは仮身を描くたびに実身を開いて閉じ、閉じるとき(`ts_cls_obj`)にロックを占有で取るので、変換のタスクの1回ごとの確定を待った。
- チェックポイントがジャーナルのロックを持ったまま本来の位置に書いていたので、その間は管理ブロックの読込みも待った。
- かな漢字変換(mozc)は最初の起動で学習のファイル`segment.db`(320KB)と`boundary.db`(80KB)を作る。C++のストリームが1KBずつ`write`するので、`ob_wri_rec`が782回、トランザクションも782になった。QEMUで数えると、変換器の起動の間にトランザクションが854、デバイスへの書込みが4002回、キャッシュを空にする要求が1730回で、実機の数と合う。USBのディスクを1秒300要求に絞ったQEMUのx64でも、変換器の起動に12.5秒かかった。

変換器のプロファイルが毎回作り直されているのではない。同じイメージで2回目に起動すると、学習のファイルは残っていて、変換器の起動は0.13秒で終わる。KERNEL.TXTの`user_dictionary.db`が無いという行は、書き込んだばかりのイメージの最初の起動だから出る。`.history.db`と`config1.db`が無いという行は、変換の履歴と設定を変えるまでmozcがそれらを作らないためで、2回目以降も出る。誤りではない。

かな漢字変換は、エンジンが続けて書いたものを`kconv.c`で256KBまでためて1回の`ob_wri_rec`にする(`KC_WBUF`)。ファイルを読む前、大きさを聞く前、名前で探す、名前を変える、消す前、閉じる前に書き出す。学習のファイルを作るときの`ob_wri_rec`は782回から3回になる。

ほかのOSのジャーナルと比べて、次のように決めた。

| OS | トランザクションのまとめ方 | 媒体に置く時機 | 書いている間のロック |
| --- | --- | --- | --- |
| Linux ext4(jbd2) | 走っているトランザクション1つに、その間のすべての操作が入る | 5秒ごと(`commit=`)か満杯のとき。`fsync`はそれを待つ | 確定は専用のスレッドが書き、その間に次のトランザクションが走る |
| FreeBSD UFS+SU | ジャーナルを持たず、書く順序の依存を追う(SU+Jはfsckを省くための補助のジャーナル) | syncerが30秒ごと。`fsync`はそのファイルの依存を書く | バッファごとのロック |
| ZFS | 5秒ごとのトランザクション群(txg) | txgごと。`fsync`はZILに書く | txgの書き出しは別のスレッド |
| NetBSD WAPBL | すべての操作を1つのログに入れる | ログが満杯のときかsyncerのとき。`fsync`はログを書く | ログの書き出しはロック(`wl_rwlock`)を占有で取り、その間は操作が止まる |
| TessronOS | 1つの操作が1つのトランザクション | レコードの書込みなどは、鍵を閉じたとき、同期のAPI、5秒ごと。置き換え、メタデータ、作ると消すは操作が戻る前。待ち行列をまとめて書く | ボリュームのロックを放してから書く |

- 前は、すべての操作が戻るときに媒体にある、という約束だった。1回の`ob_wri_rec`ごとにキャッシュを空にする要求が2回入り、64KBずつ書くと生の書込みの18分の1、1KBずつの追記は0.11MB/sだった(`docs/private/io-limits-audit.md`)。2026年10月にユーザが、上の「確定の約束」に変えると決めた。保存の操作は`ob_rpl_rec`で戻る前に確定するので、アプリが「保存した」と見せた後に電源が切れても、保存した中身は残る。
- 1つの操作を1つのトランザクションにするのも変えない。操作が途中で失敗したとき、そのトランザクションを捨てて元に戻している(`ts_jrnl_abort`)。jbd2のように複数の操作を1つにまとめると、失敗した操作だけを戻すことができない(jbd2では操作は失敗せず、失敗すればジャーナル全体を止める)。
- 書いている間にロックを持たないのは、jbd2の、確定中のトランザクションと走っているトランザクションを分ける作りにならった。WAPBLのように書き出しの間に操作を止めると、今回と同じく、デスクトップが他のタスクの書込みを待つことになる。
- 電源断の安全性は落ちない。再生は前と同じで、確定ブロックの検査に通った最も長い先頭の部分だけを戻す。トランザクションは閉じた順にリングに入るので、どこで電源が切れても、各操作はすべて反映されるか、まったく反映されないかのどちらかで、後の操作だけが残ることはない。`ktest_tsfsjrnl`、`ktest_tsfsobj`の電源断の掃引(`test_cut_sweep`)、`make KTEST=1 KTONLY=tsfscut powercut`で確かめた。

テストは次のとおりである。

- `ktest_tsfsjrnl`の`test_queue`: 閉じた3つのトランザクションはリングに書かれないまま読込みに見え、1つを待つと3つともが1回でリングに入り(`batches`が1増える)、その後の電源断で3つとも戻る。
- `ktest_tsfsjrnl`の`test_busy`: 閉じて確定していないトランザクションが解放したブロックは`ts_alloc_ext_at`で取れず、確定した後は取れる。
- `ktest_tsfsobj`の`test_unlocked`: リングの書き手を止めた状態(`TSFSJ_FAULT_HOLD`)で別のタスクが`ts_wri_rec`をすると、その操作は確定を待って戻らないが、その間に同じボリュームのほかの実身を開いて読んで閉じることができ、書いた実身の新しい大きさも見える。書き手を放すと操作は戻る。

### デバイスに1回に読み書きする量

ネイティブのTSFSは、レコードの中身のうちディスク上で続いている部分を、1回の要求にまとめてデバイスに読み書きする。その大きさはデバイスが属性`TDN_IOMAX`(`include/ts/blk.h`)で答えるバイト数で決め(`tsfsblk.c`の`io_open`がボリュームを開くときに聞き、`tsfsobj.c`の`run_io_max`が使う)、答えないデバイスは32ブロック(128KB、`RUN_IO_BLOCKS`)のままにする。上限は1024ブロック(4MB)である。要求を通すカーネルのバッファは64バイトの境界に置き(`run_io_buf`)、SDHCIのドライバが中継のバッファ(64KB)を通さずにDMAで直接読み書きできるようにする。

SDカードの値は、Raspberry Pi 5で動くLinux(github.com/raspberrypi/linuxのrpi-6.12.y、Raspberry Pi OSの既定)が同じカードに使う値に合わせる。Linuxでは次のように決まる。

| 項目 | 値 | 出典 |
| --- | --- | --- |
| 1要求の最大(ホスト) | `max_req_size` 4MB(ADMAのとき。ADMAがなければ512KB) | `drivers/mmc/host/sdhci.c`の`sdhci_setup_host`(「4MiB is preferred for multi-descriptor DMA」の注記。カードが順に書く速さを保証するのは4MB単位の書き込みだから) |
| 1要求のブロック数の最大 | `max_blk_count` 65535 | 同じ関数 |
| セグメント | `max_segs` 128(`SDHCI_MAX_SEGS`)、`max_seg_size` 64KB | 同じ関数(ADMAの記述子1つが運ぶのは長さの16ビットで表せる64KBまで、`max_adma` 65536) |
| ADMA2の記述子 | 64ビットのアドレスで12バイト(v4のモードで16バイト) | `drivers/mmc/host/sdhci.h`の`SDHCI_ADMA2_64_DESC_SZ` |
| ブロック層のハードウェアの上限 | `max_hw_sectors` = min(65535, 4MB÷512) = 8192セクタ(`max_hw_sectors_kb` 4096) | `drivers/mmc/core/queue.c`の`mmc_alloc_disk`(`lim.max_hw_sectors = min(host->max_blk_count, host->max_req_size / 512)`) |
| ブロック層の1要求の上限 | `max_sectors_kb` = min(4096、`BLK_DEF_MAX_SECTORS_CAP` 2560セクタ) = 1280KB | `block/blk-settings.c`の`blk_validate_limits`、`include/linux/blkdev.h` |
| 先読み | `read_ahead_kb` 128KB(`VM_READAHEAD_PAGES`。mmcは`io_opt`を示さないので、その2倍との大きいほうでも128KB)。Raspberry Pi OSのudevの規則(raspberrypi-sys-mods)はこれを変えていない | `block/blk-settings.c`の`blk_apply_bdi_limits`、`include/linux/pagemap.h` |
| 書き込み | ページキャッシュにためてから1要求1280KBまでまとめる。カードのSCRがCMD23に対応していれば(`SD_SCR_CMD23_SUPPORT`)ブロック数を先に告げる(SET_BLOCK_COUNT)。SDHCIの仕様3.00以上でADMAならコントローラが自動で出すAuto-CMD23を使い、対応しないときはCMD12で止める | `drivers/mmc/core/block.c`の`mmc_blk_alloc_req`と`mmc_blk_rw_rq_prep`、`sdhci.c`の`SDHCI_AUTO_CMD23` |

TessronOSのSDHCIのドライバは、`TDN_IOMAX`に1280KB(`SD_IO_MAX`)と答える。1280KBの要求は、コマンド1つ(1コマンドの上限`SD_XFER_MAX`は8192セクタ)で、ADMAの記述子40個(1つ32KB、`ADMA_MAX_LEN`。表は256個まで)になる。データポートのときは同じ大きさを1ブロックずつ運び、SDMAのときは512KBの境界で分けて出す。バッファが64バイトに揃っていない、またはコントローラが届かないときは、これまでどおり64KBの中継のバッファで分けて運ぶ。NVMeは2MB(MDTSがそれより小さければMDTS)、AHCIは4MBと答え、呼び手のバッファがカーネルのメモリなら中継のバッファを通さない(6.8)。USBの大容量記憶とvirtio-blkは`TDN_IOMAX`に答えず、128KBのままである。

プログラムのローダは1280KBずつレコードを読む(`elf.c`の`ELF_PIECE`)。書き込みは、デバイスへの要求を同じく1280KBまでにするが、ブラウザのストアは256KBずつ`ob_wri_rec`を呼ぶ(`br_store.cc`の`kChunk`)。TessronOSの書き込みは、データのブロックがデバイスに届くまでボリュームを持ったままで、その間はほかのスレッドの同じボリュームの読み出し(エンジンのスレッドがページの実身やフォントを読むなど)が待つ。そのため`tsfs.c`の`ts_wri_rec`は、256KB(`WRI_PIECE`)を越える書込みを256KBずつに分け、その間にボリュームを放す。分けたそれぞれが1つの変更で、媒体に置くのは「確定の約束」のとおりまとめて行う。Linuxは書き込みをページキャッシュから非同期に出し、読み出しを間に入れられるが、TessronOSはそうでないので、1回の書き込みを短くして待ちを短くする。実機のSDカードの書き込みは約3MB/sで、256KBなら約85ミリ秒、1280KBなら約0.4秒になる。QEMUのSDカードの経路(実機よりずっと遅い)で12.6MBを書いたとき、エンジンのスレッドが止まったのは、1280KBずつでは7秒と14秒、256KBずつでは5.5秒の1回であった。TSFSにはページキャッシュがない。読み込みは、レコードのエクステントを見つけるまでに、実身ブロック、配置表、エクステントの葉を読み、メタデータの`records`の並びを解くので、小さく区切って読むと1回ごとの手間が効いた(64KBずつで1MBずつの半分の速さ)。そこで、読んだレコードのエクステントを、ボリュームごとに16件まで持つ(`tsfsobj.c`の`rc_*`)。持ったものは、そのボリュームの世代(変更のトランザクションの始めと終わりで1つ進む)が同じ間だけ使うので、どの実身が変わっても古い場所を読むことはない。持っているレコードを、前の読込みが終わった所から512KBより小さく読むときは、512KBを先に読んでおき(`RA_BYTES`)、続く読込みはそこから渡す(Linuxの先読みのウインドウにあたる)。`iob`の群の`test_kept`が、小さく順に読んでいる途中で、別の鍵で上書き、切り詰め、伸ばす、置き換えをして、どの後も新しい中身が読めることを確かめる。プログラムのローダは1280KBずつ読むので、先読みはしない。

複数ブロックの転送の止め方は、Linuxと同じ条件で決める(`drivers/mmc/core/block.c`の`mmc_blk_alloc_req`と`mmc_blk_rw_rq_prep`、`drivers/mmc/host/sdhci.c`の`sdhci_setup_host`と`sdhci_auto_cmd_select`、`sdhci_set_transfer_mode`)。

1. カードのSCRのCMD_SUPPORTにCMD23(ビット1)があれば、CMD18とCMD25の前にブロック数をCMD23(SET_BLOCK_COUNT)で告げ、成功した転送の後にCMD12を送らない。CMD_SUPPORTは、SD_SPECが2でSD_SPEC3(ビット47)が立つカードにあり、SD_SPEC4(ビット42)が立てば4ビット(ビット35〜32)、そうでなければ2ビット(ビット33〜32)である(`sd.c`の`mmc_decode_scr`)。対応しないカードは、これまでどおりAuto-CMD12で止める。
2. SDHCIの仕様のバージョンが3.00以上のコントローラでは、CMD23をコントローラが出すAuto-CMD23にする。転送モードのビット3を立て、ブロック数をARGUMENT2(0x00)に書く。ARGUMENT2はSDMAのアドレスのレジスタと同じなので、SDMAで動かすときと、3.00より古いコントローラでは、CMD23をコマンドとして先に送る。ADMAとデータポートではAuto-CMD23を使う。
3. 転送が失敗したときは、CMD23を使っていてもCMD12を送ってカードを転送の状態に戻す(`sd_recover`、Linuxの`sdhci_finish_data`)。
4. 起動時のDMAの検査(`sd_dma_check`)は、データポートとCMD12で読んだ32KBと、選んだ方式と止め方で読んだものを比べる。違えば、選んだ方式をCMD12で読み直し、それが合えばCMD23を使わず、合わなければその方式を使わない。決まった止め方は`TessronOS: sda ...`の行に`CMD12`、`CMD23`、`Auto-CMD23`と出す。

eMMCは、LinuxではCSDのSPEC_VERSが3以上ならCMD23を使うが、TessronOSではCMD12のままにする。QEMUのsdhci-pciはAuto-CMD23を持たず(`hw/sd/sdhci.c`が扱う自動のコマンドはAuto-CMD12だけ。9.2と2026年10月のバージョンで確認)、QEMUのeMMCで試せず、CM5のeMMCは実機で確かめていないためである。QEMUのsd-cardはCMD23を受け付けるが、SCRのCMD_SUPPORTを0と答えるので、ふだんはCMD12で止める。`ktest_sd`の`test_cmd23`は、CMD12とCMD23(コマンドとして送る)を強制して書いて読み、Auto-CMD23は実機でだけ試す。

ほかのOSも同じ考え方で決めている。NetBSDは1回の転送を`MAXPHYS`(64KB)に限り、FreeBSDは13.0から既定1MBの`maxphys`、Windowsはストレージのドライバが示す最大転送長、macOSはIOKitの装置が示す最大の量を上限にし、どれも順に読まれると先読みのウインドウを広げる。実行ファイルはページキャッシュ(Windowsはイメージのセクション)で共有し、同じプログラムの2つ目のプロセスはデバイスから読まない。TessronOSの共有は5.1のとおりである。

QEMUのsdhci-pciは、コマンドごとの待ち時間や帯域を実機のように再現しないので、要求の大きさによる速さの違いはQEMUでは判断しない。QEMUでは、1280KBの要求で読み書きした中身が正しいことだけを確かめる(`ktest_sd`の`test_read_size`と、システムボリュームをSDカードに置いたブラウザの試験)。

## 7.4 システムボリューム

システムボリュームはTSFSのネイティブのパーティションで、起動時に実身の格納先としてマウントされる。フォント、壁紙、定義実身、小物のプログラム、かな漢字変換の辞書、サンプルの実身を格納する。イメージは`etc/`以下のファイル群から`tools/mktsfs`で作成する。

利用者が作る実身もここに置くので、載せる中身の大きさぎりぎりで作ると、原紙から実身を作れなくなる(R1.100の実機では空きが114688ブロック中1ブロックで、「実身を作れませんでした」となった)。Raspberry Piのカードのイメージでは、システムボリュームを2GBで作る(`build_make/makefile`の`SYS_VOL_SIZE`、3.3)。最初の起動で、区画とボリュームを8GB(`CNF_SYSVOL_GROW_MB`)まで広げる。カードが8GBより小さければ、カードの終わりまで広げる(7.7)。

## 7.5 ディスクの検査と修復

ネイティブのTSFSのボリュームは、マシンの上で検査し、修復できる(`peripheral_kernel/fs/tsfsck.c`、`include/ts/tsfsck.h`)。小物「ディスク修復」(11.25)がこれを使う。ホストの`tools/fsck.tsfs`とは別の実装で、同じ形式をカーネルの中から読む。実身ブロックとB+木の節の配置は`peripheral_kernel/fs/tsfsfmt.h`にまとめてあり、書く側(`tsfsobj.c`、`tsfsbtree.c`)と検査する側が同じ定義を使う。

### 検査の項目

検査はボリュームの構造に沿って、次の順に進む。項目の名前は超漢字Vのディスク修復小物の検査項目に合わせてある。

| 項目 | 見るもの |
| --- | --- |
| ボリュームの管理情報 | スーパーブロックの2面とバックアップ、割当て群のヘッダ、空きビットマップのチェックサム、群の空きブロック数とビットマップの一致、スーパーブロックに記録された異常 |
| リンクインデックス | 実身索引、屑実身の木、孤児の木の全節。ヘッダとチェックサム、木の番号、キーの順序と親が分けた範囲、段、葉のつながり |
| ファイルヘッダー | 索引が指す実身ブロック。ヘッダとチェックサム、UUIDが索引のキーと同じこと、表の項目数とフラグが範囲に収まること |
| 通常インデックスと接続インデックス | 管理用セグメント、アイコン、置き場表、リソース表、仮身表。置き場の形、内蔵領域の重なり、ブロックの連なりのヘッダ、項目数、ridの順、種別、バイト数、仮身表の順 |
| フラグメント・区切り・レコードサイズ | レコードとリソースの置き場。エクステントの木の葉、連なりの続き方、ブロック数とバイト数の一致 |
| ファイルヘッダー情報 | 管理用セグメントがJSONのオブジェクトであること、`records`と置き場表の一致、参照数と仮身表・固定の数の一致、壊れたリンク、屑実身の木と実身のフラグ、孤児の木と実身のフラグ、スーパーブロックが指す実身 |
| 領域の割当て | 空きビットマップと実際に使われているブロックの一致 |
| 空き領域 | 完全のときだけ。空きブロックをデバイスから読む |
| 隠れ屑実身 | 生きている実身から仮身でたどれない実身 |
| ほかのボリュームからの参照 | ボリュームが持つ参照の記録(8.3)と、取り付けてあるほかのボリュームの仮身表との一致。行き先の実身が無い記録、指す側の実身が無い記録、数の食い違い、記録の無い仮身、スーパーブロックが指す記録の実身が無いこと |

使われているブロックは、ボリューム全体のビットの表に印を付けながら数える。同じブロックに2度目の印を付けようとした所で、二重割当てとして報告する。管理ブロックの検査はブロック層の`ts_blk_good`で行い、異常を記録しない。普段の読み出しで使う`ts_blk_check`は、異常を記録してボリュームを読込専用にするためである。壊れたリンクは、仮身表で数える対象になっている項目のうち、同じボリュームの索引に無い実身を指すものである。

隠れ屑実身は、参照数が0でないのに、生きている実身から仮身をたどっても届かない実身である。たどり始めるのは、スーパーブロックが指す実身(根の実身、実身「システム」、保護区画、ほかのボリュームからの参照の記録)、固定のある実身、参照数が0の実身(屑実身。回収されるまではその仮身も数えられる)、開いたまま削除された実身である。自分自身を指す実身や、互いに指し合う実身の組がこれに当たる。

処理方式の簡易は、フラグメント・区切り・レコードサイズと領域の割当てを調べない。レコードの置き場をたどらないと使用中のブロックが分からないので、ビットマップとの突き合わせもしない。完全は、空き領域に加えて、レコードとリソースのブロックもデバイスから読み、読めないブロックを報告する。データはチェックサムを持たないので、読めることだけを確かめる。

### 修復

修復は、到達できるものを失わない操作に限る。最初の検査で、デバイスから読めないブロックや、壊れた管理の部分、置き場の食い違い、二重割当てなど、ボリュームの全体像が欠ける障害が見つかったときは、何も書かない。全体像が欠けたまま書くと、使用中のブロックが空きに見えたり、参照数が少なく数えられたりするためである。木の節と空きビットマップは、ほかの所から作り直せるので、全体像が取れていれば作り直す(下の2と4)。木とビットマップが同時に壊れていても、すべてのブロックを読んで実身を集めて作り直す(下の4)。読めるがチェックサムの合わない実身ブロックは、読めるものを救い出す(下の1)。修復できる障害だけのときは、次の順に行う。

1. 壊れた実身ブロック: デバイスから読めるがヘッダかチェックサムが合わない実身ブロックは、ブロックの中身をそのまま手がかりにして、読めるものを新しい実身に移す(`ts_obj_salvage`)。管理用セグメントと置き場表の置き場は、形、範囲、大きさを確かめてからたどり、別のブロックにある管理の部分はそれ自身のチェックサムが合うものだけを使う。管理用セグメントが読めれば名前を引き継いで「救出: 名前」とし、レコードは置き場表とレコードの並びに沿って、全体が読めたものだけを同じ型とサブタイプで書く。リソースと仮身表は引き継がない(仮身表はレコードから作り直される)。新しい実身は、隠れ屑実身と同じくTRASHを作ってそこに集める。元の実身は木から外し、そのUUIDは何も指さなくなる。元の実身を指していた仮身は壊れたリンクとして4で外部のフラグが付き、元の実身のブロックは何にも使われないブロックとして6で解放する。ビットマップを作り直す前に行うのは、元の実身のブロックがまだ使用中のうちに読み出すためである。この段階の後に検査をやり直す。
2. 空きビットマップ: 群のヘッダが持つチェックサムに合わないビットマップのブロックを、検査で使用中と分かったブロック(群が自分で使うブロック、群の終わりより後のビット、何かが指すブロック)から作り直す(`ts_blk_map_put`)。ほかの段階がその群からブロックを取る前に行う。群の空きブロック数もそれに従う。
3. 割当て漏れ: 使用中なのに空きになっているブロックを、使用中にする。ほかの段階がブロックを取る前に行う。後にすると、修復が新しく取ったブロックが使用中のレコードと重なる。
4. 木: たどれなかった実身索引、屑実身の木、孤児の木を、実身ブロックから作り直す。実身索引か孤児の木がたどれないときは、ビットマップが使用中とするブロックのうち、ヘッダとチェックサムの正しい実身ブロックを読み出して実身を知る(解放されたブロックは前の中身を残しているので、使用中のブロックだけを見る)。同じ実身が2つのブロックに見つかれば、後のトランザクションが書いた方を採り、同じトランザクションのものなら全体像が欠けるとする。ビットマップのブロックも壊れていれば、そのブロックが受け持つ範囲はすべてのブロックを読む。このとき、削除されて解放された実身の古い実身ブロックも見つかるので、検査の本番の前に、見つけた実身のブロックと管理の部分とレコードの置き場に印を付けることを報告せずに繰り返し(`sift`)、2つの実身が同じブロックを使えば、実身ブロックを書いたトランザクションの古い方を古いコピーとして外す。ボリュームが自分で使うブロック(木の節、ジャーナル)を使う実身も古いコピーである。古いコピーが無くなるまで8回まで繰り返し、収まらなければ全体像が欠けるとする。ほかの実身とブロックが重ならない古いコピーは区別できないので、屑実身として残る。何も失わない方を選んだ扱いである。外した古いコピーのブロックは、何にも使われないブロックとして6で解放する。レコードの置き場をたどらないとビットマップを作り直せないので、ビットマップが壊れているときは、簡易の処理方式でもレコードの置き場まで調べる。実身索引には孤児のフラグの無い実身を、孤児の木には孤児か作り直しのフラグのある実身を、屑実身の木には屑実身のフラグのある実身を入れる。古い根を忘れて全部のキーを入れるまでを1つのトランザクションで行うので、途中で電源が切れても、古い木か新しい木のどちらかが残り、空の木は残らない。古い木の節は何にも使われないブロックになり、6で解放する。
5. 仮身表、参照数、隠れ屑実身: 壊れたリンクを持つ実身と、作り直しのフラグが残る実身の仮身表を、xmlTADのレコードから作り直す(`ts_obj_mark_relink`、`ts_obj_relink`)。無い実身への仮身は外部のフラグが付き、数えられなくなる。孤児の木と屑実身の木から、余分な項目を除く。誰も開いていないボリュームでは、開いたまま削除された実身をマウント時と同じく回収する。参照数は、仮身表と固定から数えた値にし、屑実身の木と実身のフラグをそれに合わせる(`ts_obj_set_ref`)。隠れ屑実身は、新しいキャビネット実身「TRASH」を作って、そこへの仮身を並べる。TRASHは参照数が0の屑実身で、実身ブロックにTRASHのフラグ(`TSFSO_F_TRASH`)を持つ。屑実身操作で見られ、ウインドウに移すと普通の実身に戻る。
6. 使われていない領域: 何にも使われていないのに使用中になっているブロックを解放する。続けて、群の空きブロック数をビットマップから数え直し、壊れたスーパーブロックのコピー、バックアップ、群のヘッダを、メモリにある正しい内容で書き直す(`ts_blk_mend`)。

各段階はボリュームのトランザクションとして書き、段階ごとに検査をやり直して、次の段階はその結果から始める。途中で電源が切れても、次の検査がその続きから直す。最後にもう一度検査し、何も残らなければ、スーパーブロックの異常の記録を消して、ボリュームを書き込める状態に戻す(`ts_blk_checked`)。異常が記録されたボリュームは読込専用でマウントされ、ジャーナルを再適用していない。誰も開いていないボリュームでは、検査の前にジャーナルを再適用する(`ts_blk_replay`)。取り付け済みでジャーナルを再適用していないボリュームは、修復しない。

TRASHのフラグを持つ実身を削除するか屑実身として回収すると、それが指していた実身のうち、生きている実身から届かなくなったものと、それらだけが届くものも回収する(`ts_obj_drop_cycles`)。互いに指し合う実身の組は参照数が0にならないので、普段の回収では残る。この組を見つけるのは修復と同じ隠れ屑実身の判定で、TRASHが無くなった後のボリュームで行う。見つけた実身は、まず参照数を0にして屑実身の木に入れ、それから1つずつ回収する。回収は仮身を手放すが、相手の参照数は0より下がらないので、組がまとめて消える。生きている実身から届く実身は残る。ボリュームの全体像が取れないときは何もしない。

検査と修復の間は、そのボリュームを変える呼び出しを止める(`ts_chk_vol`がボリュームのロックを排他的に取る)。呼び出し元が自分のトランザクションを開いたままにしていれば、それが終わるのを待つ。

ボリュームの検査の後に、ほかのボリュームからの参照の記録を、取り付けてあるネイティブのボリュームの仮身表と突き合わせる(`knl_obxref_check`、8.3)。行き先の実身がボリュームに無い記録、指す側のボリュームが取り付けてあるのにその実身が無い記録、仮身表の数と食い違う記録、記録の無い仮身を見つける。修復では、記録を見つけたとおりに書き直す。参照数は記録の実身の仮身表から数えられるので、記録に合わせて動く。取り付けていないボリュームからの記録は確かめられないので、そのまま残す。ボリュームの検査が全体像の欠けで修復を断ったときは、記録も書き換えない。

### ボリュームの選び方とシステムのボリューム

`ob_chk_list`は、デバイス管理にあるディスクの全区画のスーパーブロックを読み、TSFSのボリュームを一覧にする(`peripheral_kernel/obj/obfsck.c`)。取り付け済みのボリュームは、検査はそのまま行う。修復するときは、システムのボリュームでなければ一度取り外し(`knl_obfile_detach`)、検査のためだけに開いて修復し、終わったら取り付け直す。取り外しは、そのボリュームの実身を開いている者がいれば断られる(`ts_cls_vol`が`E_OBJ`を返す)。そのときは取り付けたまま修復する。ただし、異常が記録されて取り付けられたボリュームはジャーナルを再適用していないので、取り付けたままでは修復できず、結果にそう示す(`T_TSFSCK`の`inuse`と`refused`)。取り付けていないボリュームは検査のためだけに開く。その間は、そのボリュームの取り付けを断る(`knl_ob_chk_busy`)。

システムのボリュームは、起動から終了まで書体やプログラムの読み出しに使われ続ける。そのため、動いている間は検査だけを行い、修復は断る。修復の依頼は、起動ボリュームのファイル`/boot/DISKFIX.REQ`に「デバイス名 処理方式」の1行で書き(`ob_chk_request`)、システムを再起動する。次の起動では、システムのボリュームを取り付ける前に依頼を読んで消し、ボリュームを修復のためだけに開いて修復する(`knl_ob_chk_boot`)。依頼を先に消すので、修復が終わらなくても起動のたびに繰り返すことはない。結果と報告はメモリに残し、デスクトップが起動したときにディスク修復のウインドウに出す(`ob_chk_boot_result`)。

### 報告

検査と修復は、進むにつれてイベントを呼び出し元の関数に渡す(`FP_TSFSCK`)。項目の始まり、見つけたもの(種類、実身のUUID、ブロック、種類ごとの数値)、修復したものである。修復の後の検査は、残ったものを種類ごとに1つのイベントで渡す。結果(`T_TSFSCK`)は、種類ごとの見つかった数、修復した数、残った数と、実身、レコード、仮身、ブロックの数を持つ。

### 試験

カーネルの試験(`tests/ktest/ktest_dfix.c`、`dfix`の群)は、作業用の区画にボリュームを作って行う。

- `test_clean`: 根の実身が固定するキャビネット、2つの文書(1つは3ブロックのレコードを持ち、もう1つを指す)からなるボリュームを、検査、簡易、完全のどれでも障害なしとし、修復しても何も書かないこと。
- `test_repair`: 互いに指し合う2つの文書と、屑実身の木から外した屑実身を足し、ストアの下から、参照数を3増やし、何にも使わない3ブロックを取り、レコードのブロックを1つ空きにし、仮身表の項目を無い実身に向け、異常を記録して読込専用にする。検査がそれぞれを見つけ(書き換えないこと)、修復がそれぞれを直し、修復後の検査で何も残らないこと。完全の検査でも障害なしとなり、もう一度修復しても何も書かないこと。レコードの中身が書いたときのままで、TRASHが2つの仮身を持つ参照数0の実身であること。ボリュームに再び書き込めること。
- `test_refused`: レコードの置き場をボリュームの外に向けると、置き場の障害として見つかり、修復は何も書かないこと。
- `test_system`: 一覧に作業用の区画とシステムのボリュームがあり、使用中のシステムのボリュームを検査して、すべての実身について障害がないこと。修復は`E_BUSY`で断ること。
- `test_boot`: 参照数を狂わせたボリュームに修復の依頼を書き、起動時の処理を呼ぶと、依頼のファイルが消え、参照数が直り、結果が残ること。

- `test_index`: 実身索引の根の節のチェックサムを壊すと、リンクインデックスの障害として見つかり、修復できない障害は無いとされ、実身ブロックから4つの実身が見つかること。修復で索引が作り直され、古い節が解放され、修復後の検査で何も残らないこと。レコードの中身と参照数が保たれ、屑実身は屑実身の木に戻ること。
- `test_map`: 実身のブロックのビットを含む空きビットマップのブロックを壊すと、割当て群の障害として見つかり、修復で作り直されること。修復後に作った実身が、使用中のレコードのブロックを取らないこと。
- `test_both`: 長いレコードを持つ実身を削除した後に別の実身を作り、さらにAの実身ブロックをコピーしてUUIDを変えた古いコピーを空きブロックに置いて、Aを書き直す。そのうえで実身索引の根の節と空きビットマップのブロックを両方壊すと、修復できない障害は無いとされ、古いコピーが外されて5つの実身が見つかること。修復で索引とビットマップが作り直され、修復後の検査と完全の検査で何も残らず、古いコピーのUUIDの実身が無く、レコードの中身と参照数が保たれ、修復後に作った実身が使用中のブロックを取らないこと。
- `test_salvage`: 2つのレコードを持つ実身の実身ブロックで、ヘッダが使っていないバイトを変えてチェックサムを合わなくすると、ファイルヘッダーの障害として見つかり、修復できない障害は無いとされること。修復でTRASHが作られ、元のUUIDの実身は無くなり、TRASHが指す新しい実身の2つのレコードが元と同じで、元の実身が指していた実身の参照数が新しい実身の仮身で数えられること。
- `test_cycles`: 互いに指し合う2つの実身(片方は生きている実身からも届く実身を指す)を修復でTRASHに集め、TRASHにTRASHのフラグがあること。TRASHを削除すると、2つの実身も消え、生きている実身から届く実身は残り、空きブロック数が2つの実身を作る前に戻ること。
- `test_attached`: 異常を記録したデータのボリュームを取り付け、その実身を開いている間は、修復が取り外せず書き換えないこと(`inuse`)。実身を閉じると、取り外して修復し、取り付け直し、参照数と異常の記録が直り、実身を開けること。

`make TARGET=_QEMU_VIRT_ KTEST=1 KTONLY=dfix BUILD_ID=dfx SD_CARD_SECTORS=1048576 test`で11件が通る。

## 7.6 多くのディスクとボリューム

USBのディスクを何本も挿し、それぞれが複数の区画を持つときにも、すべての区画を同時にマウントまたは取り付けられる。固定の小さな表(マウント8、fimp 4、実身のボリューム4、TSFSのブロック層のボリューム4、同時に開けるデバイス32)はやめ、表の上限はディスクの数と区画の数で決まる大きさにした。

| 表 | 上限 | 持ち方 |
| --- | --- | --- |
| ディスク | 表の上限は無い。virtio-blk、NVMe、SATAのディスクも、見つけたときに表を伸ばす(6.1)。USBのディスクの名前は`uda`から`udz`の次が`udaa`、`udab`と続く(6.1)。名前はデバイス名の8バイトに収まる`ud`と英字3文字までで、約18000台。USBの機器の数に表の上限は無く、xHCIのスロットはコントローラごとに255まで | USBのディスクの記述は、挿されたときに作り、抜かれても捨てずに次に使う。表は8から倍にして伸ばす |
| 1台の区画 | 255(`BLK_MAX_PART`)。GPTは区画表の項目の数(4096まで)を読み、使われている項目を数える。MBRは基本区画と拡張区画の中の論理区画で、論理区画はEBRの連なりをたどる(256個まで、後ろへ進まない連なりは切る) | |
| マウント(`fs_`) | 4096(`FS_MAX_MOUNT`) | 要るときに1つずつ作り、外しても捨てずに次に使う |
| 実身のボリューム(`obfile.c`)、TSFSの層(`tsfs.c`)、ブロック層(`tsfsblk.c`) | `CNF_MAX_VOL`(4096) | 同じ。ジャーナルとトランザクションの保留の表はボリュームの番号の位置に、初めて要るときに作る |
| fimp | 16 | 固定 |
| 同時に開けるデバイス、デバイスへの要求、登録できるデバイス | 上限は無い(`CNF_MAX_OPNDEV`、`CNF_MAX_REQDEV`、`CNF_MAX_REGDEV`は始めの数) | μT-Kernelの表。足りなくなると倍にして伸ばし、制御ブロックは番号から表で引く |
| デバイスの実身 | 上限は無い | 項目は1つずつ確保して表を伸ばし、使ったことのある所まで(`obd_hi`)を見る。デバイス箱に書く名前とUUIDは、全部を書く |
| 開いている実身 | 1024(`TSFS_MAX_OD`) | 固定 |

表の項目を要るときに作って捨てないのは、ロックを取らずに番号から項目を引く所(TSFSの層の`vol_of`など)と、マウントを指したまま残る記述子があるからである。項目の場所が変わらず、メモリも返さないので、取り外しと同時に番号で引いても、使い終えたメモリには触れない。同時に使った数だけメモリが要り、抜き差しを繰り返しても増えない。項目を作るのは、表のミューテックスを取ってからで、作った項目は`__atomic_store_n`(解放の順序)で表に置き、ロックを取らずに読む所は`__atomic_load_n`(取得の順序)で読む。DI/EIだけの排他は4コアでは効かないので使わない。

ブロック層のキャッシュは、ボリュームごとに最大32MB(`CNF_TSFS_CACHE`)で、全ボリュームの合計が128MB(`CNF_TSFS_CACHE_ALL`)を超えると、256ブロック(1MB)より多く持つボリュームは新しいブロックを取らずに自分の最も古いブロックを入れ替える。デバイスごとの読み書きの回数は、デバイスの記述子の番号の位置に数える。

### 区画の中身の見分け

区画を何の形式でマウントするかは、プログラムが名指す形式ではなく、区画の先頭の中身から決める(`peripheral_kernel/fs/fsprobe.c`、`knl_fs_probe`)。先頭の64KBを読み、次の順に見る。

| 形式 | 見分け方 | 扱い |
| --- | --- | --- |
| TSFS | ブロック0か1に`TFSVOL02`。チェックサムの合う、世代の新しい方からラベル、ボリュームのUUID、最上位の実身を読む | 実身のボリュームとして取り付ける(`ob_att_vol`、11.26) |
| exFAT | 起動セクタのOEM名。ラベルはルートディレクトリの先頭のセクタから読む | `exfatfs`でマウントする |
| NTFS | 起動セクタのOEM名 | `ntfsfs`でマウントする |
| FAT12、FAT16、FAT32 | FATのfimpと同じ条件の起動セクタ。種類はクラスタ数で決める | `fatfs`でマウントする |
| ext2、ext3、ext4 | バイト1024からのスーパーブロックのマジックナンバー0xEF53 | 扱えない |
| BTRONのCD-ROM、ISO 9660 | セクタ16からのボリューム記述子。システムIDが`BTRON SPECIFIED FILE SYSTEM`の区画記述子があればBTRON | BTRONはファイル変換がマウントせずに読む(11.9)。ISO 9660は扱えない |
| BTRONのファイルシステム | 先頭64KBの512バイトごとに、TRONディスクIDとディスク形式ID | ファイル変換が読む |
| 区画表 | 区画をサブユニットに持つディスク全体の、0xAA55で終わるセクタ0 | ボリュームは区画にある |
| 空 | 読んだ範囲がすべて0 | 扱えない |

`fs_attach_dev`にfimpの名前を渡さない(`NULL`)と、見分けた形式のfimpでマウントし、マウントするfimpの無い形式には`EX_NOTSUP`を返す。ディスクの実身の属性には`tessronos.format`(`kind`、`label`、`fs`)として現れる。ファイル変換とバックアップは名前を渡さずにマウントし、ファイル変換はメディアの一覧に形式を示して、扱えない形式は「この形式は扱えません」と通知する。

### exFAT

`peripheral_kernel/fs/exfatfs.c`。読み書きとも、ファイルと名前について`fatfs`と同じ呼び方ができる。マウントはデバイスの実身(`fs_attach_dev`、`fs_opn_vol`)を通すので、ファイル変換、バックアップ、`/media`からそのまま使える。

ファイルのクラスタは、続いたクラスタの列(NoFatChain)で持ち、次のクラスタが使用中のときに初めてクラスタの表に鎖を書く。ValidDataLengthより後ろは0として読み、ファイルを長くするだけでは書かない。名前の比較とNameHashはボリュームのアップケース表を使う。知らない副エントリを持つファイルは、そのエントリがクラスタを持つかもしれないので、削除と改名を`EX_NOTSUP`で断る。

媒体への書き順は、データ、ビットマップ、クラスタの表、ディレクトリのエントリとする。解放するときはエントリを先に書く。最初の変更の前に起動セクタのVolumeDirtyを立て、変更がすべて媒体に届き、書込みで開いたファイルが無くなって5秒たつと消す。このとき使用率も書く。この2つは起動領域のチェックサムの対象外である。バックアップの起動領域は変えない。

次のボリュームは読むだけで、書込みは`EX_ROFS`にする。VolumeDirtyかMediaFailureが立っている、クラスタの表が2つある(TexFAT)、主版数が1でない、アップケース表のチェックサムが合わない。ここで修復はしない(Windowsか`fsck.exfat`に任せる)。起動領域のチェックサムが合わないときはマウントしない。セクタは512バイトだけを扱う。

### NTFS

`peripheral_kernel/fs/ntfsfs.c`。読むのは名前、ディレクトリの索引(レコードの中とブロック)、属性リストで別レコードへ続く属性、レコードの中のデータ、クラスタの列、スパース、圧縮(LZNT1)である。暗号化されたファイルは一覧に出るが、データは読めない(`EX_NOTSUP`)。`$`で始まるボリュームのファイルは一覧に出さない。媒体の長さとオフセットはすべて確かめてからたどる。

書くのは、すでに場所のあるファイルのバイトを同じ場所で置き換えることと、そのファイルの時刻だけである。NTFSはファイルのデータをジャーナルに入れないので、この書込みはジャーナルと構造に触れない。ファイルの作成、削除、改名、大きさの変更、圧縮・スパース・暗号化されたファイルと未初期化の部分への書込みは、`EX_NOTSUP`で断る。これらはレコードと索引とビットマップを、ジャーナルを通さずに一度に変えることになり、途中で電源が切れるとWindowsの`chkdsk`に頼ることになるからである。

次のボリュームは読むだけにする。NTFS 3.xでない、`$Volume`にdirtyの印がある、`$LogFile`の再開領域に再生すべき内容が残っている、`hiberfil.sys`に中身がある(休止状態、高速スタートアップ)。Windowsが中身を消した`hiberfil.sys`は問題にしない。

### 試験(exFAT、NTFS)

カーネルの外で動かす試験を`tools/tests/hostfs/`に置く。fimpのソースをそのままホストのコンパイラ(AddressSanitizerとUBSan付き)でビルドし、イメージファイルをデバイスとして動かす。`hostfs.sh exfat`は`mkfs.exfat`のイメージ(クラスタ512バイト、4KB、128KB)に、作成、1MBごとの書込み、部分セクタ、飛び越えた書込み、切詰めと伸長、2つのファイルを交互に伸ばす断片化、2階層の移動を含む改名、1つのクラスタに収まらないディレクトリ、満杯になるまでの書込み、VolumeDirtyのボリュームの読取り専用を行い、終わったイメージを`fsck.exfat -n`で確かめる。`hostfs.sh ntfs`(rootで`ntfs-3g`のループマウントを使う)は、`ntfs-3g`が作ったファイルを全部読んでハッシュを比べ、同じ場所での書込みの結果を`ntfs-3g`で読み返し、`ntfsfix -n`を通し、dirtyの印、再生の残ったジャーナル、休止状態の各ボリュームが読取り専用になることを確かめ、MFTの先頭をランダムに壊したイメージ200個で落ちないことを確かめる。exFATのカーネル内の試験は`vols`の群の`test_all_on`で、`tools/tests/mkvoldisk.py`が作る本物のexFATの区画に書いて読み返し、読取り専用でマウントし直して読む。

### 取り外しと抜き取り

ボリュームの取り外し(`ob_det_vol`)は、そのボリュームの実身を開いているキーがあれば`E_BUSY`で断り、何も変えない。同じボリュームのUUIDを持つボリュームがすでに取り付けてあるときの取り付けは`E_OBJ`で断る(1つのボリュームをコピーした区画を並べると、同じ実身が2か所に見えるため)。

媒体やディスクが抜かれると、デバイスの実身の層(`obdev.c`)が、そのデバイスと区画のマウントと実身のボリュームを、去ったもの(gone)にする(`knl_fs_revoke`、`knl_obfile_revoke`)。去ったボリュームの実身はもう見つからず、開いていたキーと記述子は誤りを返し、最後のキーが閉じたときにボリュームを閉じて表の項目を空ける。同じ媒体を挿し直すと、空いた項目に取り付け直せる。デスクトップはこの変化を見て、そのボリュームの実身のウインドウを閉じ、仮身を虚身として描き直す(11.26)。システムのボリュームも同じに去り、カーネルは止まらない。デスクトップは初期ウィンドウだけを、持っている記録で残し、同じボリュームが挿されると取り付け直す(11.26)。起動のときから一度取り付けたことのあるボリュームを取り付け直したときは、起動のたびに空にする実身を空にしない(`knl_obfile_again`)。

## 7.7 区画の作成と拡張

TSFSの区画とボリュームは、後ろに空き領域があれば、作った後で広げられる。カードに書いたイメージの区画はイメージの大きさしかないので、システムボリュームは起動時に広げる。ディスク操作の〈区画作成〉と〈拡張〉(11.26)も同じ処理を使う。区画表(GPT)を書くのは`peripheral_kernel/sysman/gpt.c`、TSFSの区画とボリュームをまとめて扱うのは`peripheral_kernel/fs/tsfspart.c`、ボリュームを広げるのは`peripheral_kernel/fs/tsfsblk.c`である(`include/ts/gpt.h`)。

### 区画表の読み書き

区画表はディスク全体のデバイス(`sda`、`uda`など)から読む。プライマリのヘッダ(セクタ1)とその区画表の項目をCRCで確かめ、合わなければディスクの最後のセクタにあるバックアップのヘッダと項目を使う。どちらも合わないディスクには書かない。先頭の2セクタが0のディスクは区画表の無いディスクとし、区画を作るときに保護MBRと128項目の区画表を新しく作る。MBRのディスクは扱わない。

空き領域は、どの区画にも使われていない範囲を1MB単位に切りそろえて数える。ディスクの終わりは、バックアップの区画表をディスクの最後の33セクタに置いたときの位置とする。イメージを書いたカードではバックアップの区画表がイメージの終わり、つまりカードの途中にあるが、そこも空き領域に含め、最初に区画表を書くときにカードの終わりへ移す。元のバックアップはそのまま残り、後で区画を広げたり作ったりしたときに上書きされる。

区画表を書くときは、毎回、プライマリとバックアップの両方を書き、CRCを計算し直す。順番は次のとおりで、それぞれを書いた後でデバイスのキャッシュを空にする(`TDN_FLUSH`)。

1. バックアップの区画表の項目をディスクの終わりに書き、続けてバックアップのヘッダを最後のセクタに書く。
2. プライマリの区画表の項目を書き、続けてプライマリのヘッダをセクタ1に書く。
3. 保護MBRの大きさがディスクより小さければ直す。

電源が切れたときの扱いは次のとおりである。1の途中で切れたなら、プライマリのヘッダとその項目は元のままで、元のバックアップも元の場所に残るので、元の区画表として読める。2で項目を書き終えてヘッダを書く前に切れると、プライマリのヘッダのCRCが項目と合わなくなる。CRCを確かめる読み手(`gpt.c`、ほかのOS)は、1で書いたバックアップ、つまり新しい区画表を使う。ドライバが区画を数える処理(`part.c`)はCRCを見ずにプライマリのヘッダが指す項目を読むので、やはり新しい区画表になる。どの場合も、読めるのは元の区画表か新しい区画表のどちらかで、両者が混ざることはない。

新しい区画は、使われている最後の項目の次の項目に置く。区画の番号(サブユニット、`sda1`の1)は使われている項目の順で決まるので、すでにある区画の番号は変わらない。

書いた後は、ディスク全体のデバイスに属性`TDN_PARTSCAN`を書き込む。SD、virtio-blk、USBのディスクのドライバは区画表を読み直し(`knl_part_rescan`)、すでにある区画の開始位置が変わっていないことを確かめてから大きさを更新し、新しい区画を後ろに足し、サブユニットの数を変えてデバイスを登録し直す(`tk_def_dev`)。開いている区画はそのまま使い続けられる。開始位置の変わった区画や無くなった区画があれば、読み直しは何も変えずに`E_OBJ`を返す。最後に`knl_obdev_changed`でデバイスの一覧に変化を知らせる。

### ボリュームの拡張

ボリュームを広げても、ジャーナルの大きさと割当て群の大きさは作ったときのままにする。最後の群を群の大きさまで(新しい終わりがそれより手前ならそこまで)伸ばし、その後ろに群を足す。最後の群が64ブロック(`AG_MIN_TAIL`)より短くなるときに群にしない規則は変えない。スーパーブロックの総ブロック数、群の数、空きブロック数を新しい値にする。

こうして広げたボリュームの群の配置は、総ブロック数から決まる配置(`layout()`)とは異なる。そこでスーパーブロックの互換の機能に`GROWN`(compatのビット0)を付ける。カーネルはもともと群の配置をスーパーブロックの値から求めるので、カーネルの側に変える所はない。ホストの検査(`tools/tsfs_py/check.py`)は、`GROWN`のあるボリュームについては、群の大きさが2の累乗で範囲内であることと、ジャーナルと群の大きさから求めた群の数が一致することを確かめ、`layout()`との違いを警告しない。

群の大きさが32768ブロックを超えると、最後の群を伸ばしたときに空きブロックのビットマップのブロックが増えることがある。増えるブロックは最後の群のデータ領域なので、そこが使われていれば広げずに`E_LIMIT`を返す。

ボリュームは使用中のまま広げられる(`ts_grow_vol_blk`)。まずジャーナルを止める(`knl_jrnl_freeze`)。走っているトランザクションが終わるのを5秒まで待ち、確定したものをすべて本来の位置に置き、それ以降は新しいトランザクションを始めさせない。ジャーナルに残った群のヘッダやスーパーブロックの古いコピーが拡張の後に再生され、広げた内容が元に戻るのを防ぐためである。その後、ボリュームのロックを持ったまま、次の順に書く。

1. スーパーブロック。非互換の機能`GROWING`(incompatのビット0)を付け、広げる先の総ブロック数を416バイト目(`grow_to`)に書く。
2. 足す群のそれぞれについて、空きブロックのビットマップ、続けて群のヘッダ。すべて元のボリュームの終わりより後ろにある。
3. 最後の群のビットマップ、続けてヘッダ。
4. すべてのバックアップのスーパーブロック。新しい大きさで書く。
5. 新しい大きさと`GROWN`を持ち、`GROWING`を外したスーパーブロック。続けてもう一方のコピーにも書く。

5が媒体に届くまでは、開いたときに読むスーパーブロックは1のものである。`GROWING`のあるボリュームを開くと(`ts_opn_vol_blk`)、カーネルは2から5をやり直して拡張を終える(コンソールに`tsfs: デバイス名: a grow cut short finished, ブロック数 blocks`)。最後の群のヘッダは新旧どちらが書かれているかわからないので、開くときには確かめない。最後の群のビットマップはCRCを確かめずに読み、元の群の範囲のビットだけを使って作り直す。元の範囲のビットは、増えるビットマップのブロックに当たるビット(拡張の前は空き、後は使用中)を除いて新旧で同じなので、どちらが読めても同じものができる。1が媒体に届く前に切れたときは、元のボリュームのままである。`GROWING`を知らないカーネルはこのボリュームを開かない。ホストの検査は、`GROWING`のあるボリュームについて、拡張が途中で切れたことを警告する。

広げた後は、群の表を新しく作り直す。データの読み書きの一部はロックを取らずに群の表を読むので、古い表はボリュームを閉じるまで残す。

2の書込みをデバイスが断ったときは、拡張をやめる。2が書くのは元の終わりより後ろのブロックだけで、ボリュームのどこからも指されていないので、ボリュームは元の大きさのまま書ける。スーパーブロックから`GROWING`と`grow_to`を外して書き、次に開くときにやり直さない。次の起動(システムボリューム)か次の〈拡張〉で、区画の大きさまで広げ直す。3から5の書込みが断られたときは、ボリュームの中の群とスーパーブロックに触れているので、これまでどおり誤りを記録し、検査まで読込み専用にする。どちらのときも、断られたブロックとデバイスの答えをコンソールに出す(`tsfs: デバイス名: the grow could not write block ブロック (誤り)`)。記録する誤りのブロックも、断られたブロックである(前は最初の群の位置を記録していた)。

前は2の失敗も誤りとして記録していたので、拡張のための1回の書込みの失敗で、システムボリュームが読込み専用になり、設定がすべて保存できなくなった(2026年10月、ThinkPad X1 Yoga 第3世代、USBのカード読み取り器のSDカードから起動したとき。誤りのブロック770は最初の群の位置で、失敗したブロックではなかった)。QEMUでは、USBのディスクの、新しい群の地図にあたるセクタへの書込みが失敗するようにし(`blkdebug`)、前は誤りの記録と読込み専用になること、今は拡張をやめて元の大きさで使い続け、次の起動で広げ直せることを確かめた。

USBの大容量記憶のドライバは、失敗した読み書きを、ディスクごとに最初の16回まで、命令の状態とセンスデータ(キー、ASC、ASCQ)とともにコンソールに出す(`usb: uda: write of 8 blocks at 1513528 failed: status 1, sense 0b/00/06, 4096 bytes moved`)。失敗の数は`USB.TXT`にも出る。SYNCHRONIZE CACHEを断る装置は、そのことを1回だけ出す。起動のときの`sysvol:`の行は、区画表の区画の範囲、区画のデバイスのブロック数を出し、ボリュームを広げる前にはその大きさと状態を出す。

### 区画とボリュームの順

区画とボリュームをまとめて広げるときは(`knl_tsfs_part_grow`)、区画表を先に、ボリュームを後に広げる。区画がボリュームより大きくても使っていない領域ができるだけだが、ボリュームが区画より大きいと開けないためである。区画を広げた後、ボリュームを広げる前に電源が切れると、区画だけが大きいボリュームが残る。区画がボリュームより1MB以上大きいときは、次の起動(システムボリューム)か次の〈拡張〉で、ボリュームを区画の大きさまで広げる。

区画を作るときは(`knl_tsfs_part_make`)、区画表に区画を足してから、その区画にボリュームを作る(`ts_format_blk`)。区画の大きさは1MB単位で、4MB以上(TSFSの最小のボリューム)でなければならない。

### システムボリュームの自動拡張

起動時、システムボリュームを取り付ける前に(`knl_sysvol_grow`、`peripheral_kernel/obj/obname.c`)、次の条件をすべて満たせば区画とボリュームを広げる。

- 区画がTSFSの型である。
- ディスクの最後の区画で、後ろに空き領域がある。
- 区画が`CNF_SYSVOL_GROW_MB`(8192MB、`config/config.h`)より小さい。

広げる先は8GBと、ディスクの終わり(バックアップの区画表の分を残し、1MB単位に切り下げた位置)の小さいほうである。広げたかどうかをコンソールに1行で出す。広げたときは`sysvol: grown 2048 MB -> 8192 MB`、広げなかったときは`sysvol: 2048 MB, not grown (理由)`で、理由は`at its limit`(すでに上限)、`not the last partition`(後ろに区画がある)、`no room after it`(後ろに空きがない)、`not a TSFS partition`である。条件を満たさなくても、区画がボリュームより大きければボリュームだけを広げる。

Raspberry Pi 5と4のカードのイメージ(`tools/mksd.py`)は、区画2がシステムボリュームで、最後の区画である。カーネル内の試験のイメージ(`KTEST=1`)は後ろに作業用の区画3があるので、広げない。2GBから8GBに広げるときに書くブロックは、足す24個の群のヘッダとビットマップ、バックアップのスーパーブロックなど百ほどのブロックで、時間はかからない。

### 試験

`tests/ktest/ktest_grow.c`(`grow`の群)は、`tools/tests/mkvoldisk.py`が作る96MBの空のUSBのディスク(`volg.img`)をQMPを通してハブに挿す。前の実行が残したものを消すため、先頭と末尾のセクタを0にしてから挿し直す。

- `test_fresh`: 区画表の無いディスクの空き領域が1つであること。そこに16MBのTSFSの区画を作ると、プライマリとバックアップの区画表がどちらもCRCを満たし、バックアップがディスクの終わりにあり、区画にラベルの付いたボリュームがあること。
- `test_image`: 36MBのイメージを書いたカードと同じくバックアップをディスクの途中に置いた区画表を書き、区画に実身を書いてから、区画とボリュームを48MBに広げる。バックアップがディスクの終わりに移ること、デバイスとボリュームが48MBになること、検査(`ob_chk_run`)で障害が無いこと、実身を読み返せること、元のボリュームより大きい20MBの実身を書けること。
- `test_live`: ボリュームを開いたまま64MBに広げ、開いているボリュームの大きさが変わり、続けて書けること。空きの無い所でもう一度広げると`E_LIMIT`になること。
- `test_cut_volume`: 8MBのボリュームを24MBに広げる書込みの数を数え、1つ目から最後までの各書込みの後で、電源が切れたことにする(`ts_cut_blk`)。開き直したボリュームが元の大きさか新しい大きさで、異常の記録も`GROWING`も無く、実身を読み返せ、4MBの実身を書け、検査で障害が無いこと。
- `test_cut_table`: バックアップがディスクの途中にある区画表で区画を広げる書込みの数を数え(5回)、そのそれぞれの後で電源が切れたことにする(`knl_gpt_cut`)。CRCを満たす区画表が必ずあり、区画の終わりが元か新しいかのどちらかであること。元のままの場合と広がった場合の両方が現れること。
- `test_sysvol`: 起動時のシステムボリュームの拡張の結果が、区画の大きさと合っていること。
- `test_out`: ディスクを抜く。

`make TARGET=_QEMU_VIRT_ KTEST=1 KTONLY=grow BUILD_ID=<名前> test`で走らせる。起動時の自動拡張は、`TEST_DISK_MB=384 TEST_DISK_ROOM=96`を付けて試験用ディスクを作り直すと確かめられる。`tools/mkdisk.py --sys-room N`が、区画表をディスクの終わりのN MB手前で終わらせ(イメージを書いたカードと同じくバックアップがディスクの途中に来る)、システムボリュームの区画3を最後に置くので、起動時に`sysvol: grown 144 MB -> 240 MB`となる。その後`python3 tools/fsck.tsfs --partition 3 <試験用ディスク>`で、広げたボリュームに障害が無いことを確かめる。

ホストのツールでは、`tools/tests/test_tsfs_py.py`の`TestGrow`が、`Volume.grow`(カーネルと同じ手順で広げる)で広げたボリュームを検査して障害も警告も無いこと、`GROWN`を外すと配置の警告が出ること、`GROWING`を付けると途中で切れた警告が出ることを確かめる。

## 7.8 システムボリュームの暗号化(未実装、将来の検討)

システムボリュームの暗号化は実装していない。実装するかどうかも決めていない。この節は将来検討するときのための設計の案で、ここに書いたものはどれもTessronOSにはまだ無い。実装するときは、まず末尾の表の方針を決める。

### 守るものと守らないもの

電源の切れたディスクやカードを持ち去られたときに、利用者の実身と設定を読まれないようにする。起動中のマシンの攻撃、メモリの読取り、起動区画の改ざん(カーネルをすり替えてパスワードを盗む)は守らない。ESPとRaspberry Piの第1パーティションは暗号化できず(ファームウェアが読む)、カーネルはここに平文で置くので、改ざんを防ぐにはセキュアブートが要る。今のローダはセキュアブートに対応していない。

### 層

TSFSとディスクの間に、暗号化デバイス(`crypt`の層)を置く。ディスクの区画`nvmeaN`に対して、復号した内容を見せるブロックデバイスを登録し、TSFSはこちらをマウントする(`ob_att_vol`)。TSFSとジャーナル(7.3)は暗号化を知らない。カーネルの中で行い、復号の前後を別のページに持つ。読むときはDMAのあと同じバッファの上で復号でき、書くときは平文のバッファを壊さないよう別のページに暗号化してから渡す。TSFSのブロック(4KB)ごとに、ブロック番号をIVにする。ブロックより小さいセクタの部分書込みの扱いが要らないので、電源断の性質はTSFSの今の前提(ブロックの書込みが途中で切れてもCRCで分かる)から変わらない。

暗号はAES-256-XTSを既定にする(x64のAES-NI、Pi 5のCortex-A76の暗号拡張)。Pi 4、Pi 400のCortex-A72(BCM2711)には暗号拡張が無いので、AESはソフトウェアで遅い。暗号拡張の無いCPU向けの選択肢としてAdiantumがある(下の表の2)。乱数はx64のRDRANDとUEFIの種、PiのRNGブロックを既存の`knl_rng`からとる。

カーネルは今`mbedtls`を`WIFI=1`のときだけ結ぶ。暗号化では、AESの部分(AES-NIと暗号拡張の命令を含む)とSHA-512、Argon2idを小さく取り込むか、Mbed TLSの該当のファイルをカーネルのビルドに常に入れる。

### 鍵の持ち方

区画の先頭に見出しを置き、そのブロック(と末尾の控え)にマスター鍵を暗号化して持つ。マスター鍵は乱数で作り、パスワードはArgon2idで作った鍵でこれを包む。パスワードの変更は包み直すだけで、全体を暗号化し直さない。見出しには複数のスロットを持ち、回復用の鍵(登録のときに表示して控えてもらう)を別のスロットに入れる。マスター鍵はカーネルのメモリにだけ置き、スリープ(3.10.11)の間も持つ。電源を切るときと再起動で消す。プロセスからは読めない。

### 起動時の尋ね方

カーネルの`devinit`の、起動ディスクを見つけた直後に尋ねるのが、x64とPiで同じコードになる。画面はカーネルのコンソール(fbcon)で、キーはUSBのHIDとI2CのHIDとシリアルのドライバが上がった後なので、この段階では`ts_hid_read`がまだ使えない機種がある(BluetoothキーボードやSurfaceのキーボードカバーの準備は遅い)。この段階でのキー入力の経路を作る必要がある。日本語の配列を考えて、英数字だけを受け付ける。かな漢字変換は無い。

x64ではUEFIのローダがブートサービスの間にConInで尋ねる方法もある。ファームウェアのキーボードのドライバが使えるので確実で、外付けのキーボードも内蔵も動く。ただしPiでは使えず、コードが2つになる。

### 起動とシステム登録との関係

- 起動の流れ: x64はローダがカーネルをESPから読み、カーネルが尋ねて、システムボリュームを開く(3.10.1)。Piはファームウェアが第1パーティションからカーネルを読み、カーネルが尋ねる(3.2)。
- システム登録(`application/sysinst`、11.32、3.10.10): 〈暗号化する〉の選択を足し、パスワードを部品の入力欄で受ける。写しのときに区画に見出しを作り、ボリュームを暗号化しながら写す。今の登録は「読み返し」と「ボリュームの拡張」を行うので、どちらも復号した側のデバイスに対して行う。回復用の鍵はパネルに表示する。
- 区画の拡張(7.7)は復号した側のデバイスの大きさが広がる形にする。見出しの控えを末尾に置くと、拡張で移す必要がある。
- ディスク修復(11.25、7.5)はパスワードが通ってからでなければ動かない。
- システムのバージョンアップ(.tpk)はカーネルとローダとシステムの実身を替えるので、見出しの形式はこのバージョンをまたいで読める必要がある。
- 記録の区画`TSLOG`(FAT)とESPの`bootlog`には起動の記録が平文で残る。実身の名前が記録に出ないことを確かめる。

### 実装するときに決める必要のあること

| 項目 | 選択肢 | 勧め |
| --- | --- | --- |
| 1 対象 | (a)x64の内蔵NVMeへの登録だけ。(b)PiのカードとUSBのボリュームも | (a)から。Piのカードのイメージはパスワードを持てないので、初回起動で全体を暗号化する別の仕組みが要る |
| 2 暗号 | (a)AES-256-XTSだけ(Pi 4が遅い)。(b)AES-XTSとAdiantumの両方 | (1)が(a)ならAES-XTSだけで足りる |
| 3 見出しの形式 | (a)LUKS2互換(Linuxから開ける。形式が大きい)。(b)TessronOSの独自形式(小さい。独自の暗号の形式を検証する責任を自分で持つ) | (a)。回復と検証に`cryptsetup`が使える |
| 4 パスワードの尋ね方 | (a)カーネルで共通(起動の早い段階のキー入力の経路を作る)。(b)x64はUEFIのローダ、Piはカーネル | (1)が(a)なら(b)が確実で早い |

他に、これを入れるならセキュアブートを合わせて扱うか、TPMで自動的に開く形を入れるか(今回は入れない案)も、決める必要がある。
