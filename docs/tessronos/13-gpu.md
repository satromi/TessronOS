# 第13章　GPU

## 13.1 目的と現状

Raspberry Pi 5のGPU(VideoCore VII、3DブロックはV3D 7.1)を、プロセスのOpenGL ES、EGL、そして将来のVulkanから使えるようにする。最初の利用者はブラウザ(Chromium/Blinkの移植)のWebGLで、その後にページの合成とウインドウの合成が続く。

## 13.2 BCM2712のV3D

### 13.2.1 アドレスと割込み

V3Dの資源はデバイスツリー(`bcm2712-rpi-5-b.dtb`)の`/axi/v3d@2000000`(`compatible = "brcm,2712-v3d"`)に書かれている。`/axi`のアドレス変換は恒等なので、`reg`の値がそのまま物理アドレスになる。

| 資源 | 値 | 内容 |
| --- | --- | --- |
| `reg`の`hub` | `0x10_0200_0000`から16KB | ハブ。MMU、テクスチャフォーマットユニット(TFU)、ハブの割込み |
| `reg`の`core0` | `0x10_0200_8000`から24KB | コア0。制御リストの実行器(CLE)、タイルのビニング(PTB)、キャッシュ、コアの割込み |
| `reg`の`sms` | `0x10_0203_0800`から0x700バイト | 電源状態の管理(SMS) |
| `interrupts` | SPI 250(INTID 282)、SPI 249(INTID 281)、レベル | 1つ目がハブ、2つ目がコア0(バインディングの定義による) |
| `power-domains` | `<&pm 1>` | PMブロック(`0x10_7d20_0000`、`brcm,bcm2712-pm`)の電源ドメイン1 |
| `resets` | `<&pm 0>` | 同じPMブロックのリセット0 |
| `clocks` | `<&firmware_clocks 5>` | ファームウェアが管理するクロックの5番(V3D) |

配布されているデバイスツリーでは、このノードは`status = "disabled"`である。Linuxではオーバーレイ(`vc4-kms-v3d-pi5`)が有効にするが、TessronOSはデバイスツリーの状態に関係なく、ビルドの指定(13.3.1)で使うかどうかを決める。アドレスと割込み番号は`include/sys/sysdepend/cpu/bcm2712/sysdef.h`の`V3D_HUB_PA`、`V3D_CORE0_PA`、`V3D_SMS_PA`、`V3D_HUB_INTNO`、`V3D_CORE0_INTNO`にある。

### 13.2.2 電源とクロック

クロックはファームウェアのメールボックスのプロパティインタフェースで操作する。使うタグは公開されている次のものである。クロックの番号5がV3Dである。

| タグ | 機能 |
| --- | --- |
| `0x00030001` | クロックの状態を取得する(ビット0がオン、ビット1が「存在しない」) |
| `0x00038001` | クロックをオンにする |
| `0x00030004` | 最大周波数を取得する |
| `0x00038002` | 周波数を設定する |
| `0x00030002` | 現在の周波数を取得する |

電源ドメインはPMブロックが持つ。ファームウェアがV3Dの電源を入れたままカーネルに渡すかどうかは公開された資料になく、実機で確かめる(13.8)。ドライバは、コアの識別レジスタ`IDENT0`が「V3D」と読めることを最初に確かめ、読めなければ他のレジスタには触れずに止まる。SMSのウインドウには何も書かない。

### 13.2.3 構成とMMU

V3Dはハブと1つ以上のコアからなる。コアはシェーダプロセッサ(QPU)を束ねたスライスを持ち、スライスの数とスライスあたりのQPUの数は`IDENT1`で分かる。バージョンは`IDENT0`の上位8bit(メジャー)と`IDENT1`の下位4bit(マイナー)で、Raspberry Pi 5では71になるはずである。

GPUは自分のMMUを通してメモリを読み書きする。GPUのアドレスは32bitで、4KBのページごとに32bitのエントリを持つ1段のページテーブルで物理アドレスに変換する。4GB全体では100万エントリ、4MBのテーブルになり、ハードウェアにはその先頭だけを渡すので、テーブルは物理的に連続していなければならない。エントリの下位28bitが物理ページ番号で、1TBまでの物理アドレスを指せる。実際に届く物理アドレスの幅は、MMUのデバッグ情報のレジスタで分かる。無効なエントリへのアクセスは、指定したページ(スクラッチページ)に振り向けられ、割込みで報告される。

GPUはCPUのキャッシュを見ないものとして扱う。GPUが読むメモリはCPUのキャッシュから追い出してから使い、その後はキャッシュしないマッピングでだけ触る。これが正しいかどうか(GPUとCPUの間にコヒーレンシがあるかどうか)も実機で確かめる。

ページテーブルは1つしかないので、GPUのアドレス空間はすべての利用者で共有になる。プロセスの間の分離は、プロセスが自分の持つバッファオブジェクトしか指定できないこと(13.5)で保つ。ジョブは1つずつ順に実行するので、将来はジョブごとにプロセス専用のページテーブルに切り替えることもできる。

### 13.2.4 ジョブの種類

| 種類 | 実行する部分 | 終わりを知る方法 |
| --- | --- | --- |
| ビニング(制御リスト0) | CLEのスレッド0。頂点を処理し、タイルごとのリストをタイル割当てメモリに書く | コアの割込み「ビニングのフラッシュ完了」、カウンタ`BFC` |
| レンダリング(制御リスト1) | CLEのスレッド1。タイルごとにフラグメントを処理し、メモリに書き出す | コアの割込み「フレーム完了」、カウンタ`RFC` |
| TFU | ハブのTFU。テクスチャのレイアウト変換とミップマップの生成 | ハブの割込み「TFU完了」 |
| コンピュート(CSD) | コアのディスパッチャ。コンピュートシェーダのワークグループ | コアの割込み「CSD完了」、完了数のカウンタ |
| キャッシュのクリーン | テクスチャのL2キャッシュとTMUのライトコンバイナ | 制御レジスタのビットが0に戻るのをポーリングする |

ビニング中にタイル割当てメモリが足りなくなると、コアが「メモリ不足」の割込みを上げる。カーネルはオーバーフロー用のメモリを`BPOA`、`BPOS`に渡して続けさせる。

制御リストはGPUのメモリに置いたコマンド(パケット)の並びで、形式はMesaの`src/broadcom/cle/v3d_packet.xml`に記述がある(13.6.4)。

### 13.2.5 レジスタの資料

V3D 4以降のレジスタの配置を記した公開の仕様書はない。`device/gpu/v3d/v3d_regs.h`では、項目ごとに次の印を付けている。

| 印 | 意味 | 該当するもの |
| --- | --- | --- |
| `[doc]` | 公開された資料に配置がある | 識別レジスタ`IDENT0`〜`IDENT2`、CLEの`CTnCS`〜`RFC`、PTBの`BPCA`〜`BPOS`(BroadcomのVideoCore IV 3D Architecture Reference Guideに同名のレジスタがあり、後の世代も同じ位置に残している)。識別ワードの各フィールドの意味(Mesaの`v3d_device_info.c`が読み解く) |
| `[hw]` | 公開された配置がない | ハブの識別と割込み、MMUとそのキャッシュ、コアの割込みとキャッシュ、キュー形式のCLEの開始レジスタ、ページテーブルのエントリのビット |

`[hw]`の項目は、実機で1つずつ読み出して確かめてから使う(13.8)。ドライバはビルドの指定`V3D=1`ではこれらに一切書き込まない。TFUとCSDは7.1での位置が未確認なので、第1段階では実装していない。ジョブの実行手順(キャッシュの無効化、キューのレジスタに開始と終了のアドレスを書く順序、完了の判定、MMUの割込みの処理)は、Mesaに含まれるシミュレータ用のコード(`src/broadcom/simulator/v3dx_simulator.c`、MIT)が示す手順に合わせた。

### 13.3.1 ファイルと段階

| `device/gpu/v3d/v3d.h`、`v3d_mmu.c` | GPUのアドレス空間。ハードウェアに依存しないので両方のマシンでビルドし、QEMUで試験する |
| `device/gpu/v3d/v3d.c` | Raspberry Pi 5のV3D。`rpi5.mk`だけがビルドする |

| `include/ts/gpu.h` | カーネル内の利用者とSVCが使う定義 |

起動時、`kernel/sysdepend/rpi5/devinit.c`が乱数の初期化の後で`knl_v3d_init()`を呼ぶ。ドライバがどこまで動くかは、ビルド時の`V3D`で決まる(`CNF_V3D`)。

| 指定 | 動作 |
| --- | --- |
| なし(既定) | 何もしない |
| `make TARGET=_RPI5_ V3D=1` | メールボックスでクロックを入れ、識別レジスタとMMUのアドレス幅を読んでコンソールに表示して終わる。V3Dには書き込まない |
| `make TARGET=_RPI5_ V3D=2` | さらにMMUと割込みを設定し、GPUとして共通層に登録し、自己試験(MMUに入れたバッファオブジェクトの確認とキャッシュのクリーンのジョブ)をする。起動の後で、実機の試験(13.8.2)をまとめて行い、最後にウインドウの合成の確認(13.10.6)をする |
| `make TARGET=_RPI5_ V3D=3` | `V3D=2`と同じく設定して登録するが、実機の試験はしない。起動の2秒後にウインドウの合成の確認だけを行い、通ればGPUで合成する。GPUを使うときの普段の指定である |

QEMUではV3Dのドライバはビルドもされず、呼ばれもしない。

### 13.3.2 起動の手順

1. クロック5の状態を取得し、オフならオンにして、最大周波数に設定する。
2. コアの`IDENT0`を読み、下位24bitが「V3D」(`0x443356`)でなければ終わる。
3. ハブとコアの識別レジスタを読み、ハブの`IDENT0`が「VHUB」(`0x42554856`)でなければ終わる。続けてMMUのデバッグ情報を読み、バージョン、リビジョン、コア数、QPU数、GPUの仮想アドレスと物理アドレスの幅を表示する。`V3D=1`なら、V3Dに何も書き込まないことを表示してここで終わる。`V3D=2`では、以下の手順ごとに、その前に`v3d: - 手順名`を表示する。実機で止まったときに、どの書込みで止まったかが分かる。
4. バージョンが71でなければ終わる。物理アドレスの幅から、バッファオブジェクトのページを取る上限を決める。
5. 4MBの連続したページテーブルを確保し、スクラッチページを用意して、MMUに設定する(13.3.3)。
6. コアの割込み(フレーム完了、ビニングのフラッシュ完了、メモリ不足)とハブの割込み(MMUの書込み違反、無効なエントリ、上限超え)だけを許可し、INTID 281と282にハンドラを登録する。
7. 共通層に登録し、オーバーフロー用のメモリ(512KB)を確保して、自己試験をする。
8. 合成の準備(13.10)の後で、コンピュートのディスパッチを確かめる(`v3d_csd_check`、`v3d_compose.c`)。確認用の計算シェーダ(`tools/mesa/gen_cp_shaders.c`の`csd`。16の起動のワークグループを4つ。起動nはバッファのn番目のワードに3n+1を書く)を、プロセスのジョブと同じくキューを通して1回走らせ、64ワードがすべて合ったときだけ、共通層にコンピュートのジョブを受け付けると伝える(`GPU_FEAT_CSD`、`v3d_csd_offer`)。合わなければ受け付けず、v3dドライバはこれまでどおりOpenGL ES 3.0になる。

### 13.3.3 GPUのアドレス空間

`v3d_mmu.c`はページテーブルとGPUアドレスの割当てを受け持つ。ページテーブルはバディアロケータの最大の次数(4MB)の1ブロックで、起動の早い時期に確保する。テーブルの線形マッピング上のキャッシュラインを一度クリーンしてから、キャッシュしないマッピング(`knl_vmap_pa`の`VMAP_NOCACHE`)を通してだけ書く。

GPUアドレスは、ページ単位のビットマップから、前回の割当ての続きを探して割り当てる。解放したアドレスはすぐには使い回さず、探索が末尾から先頭へ一巡したときに再び使う。アドレスで引くGPUのキャッシュに、解放前の内容が残っていても読まれないようにするためである。64KB未満のアドレスは割り当てないので、0は「アドレスなし」を意味し、リストが下端を越えれば無効なページに当たる。エントリを書き換えた後は、コールバックで、先にMMUのキャッシュ(ページテーブルのエントリのキャッシュ)を、次にTLBを消去させる。MMUは、無効なエントリ、書込みが許されないページ、アドレスの上限を越えるアクセスをいずれも中止して割込みで通知する設定で有効にする。中止させないと、そうしたアクセスをしたGPUのスレッドは止まったままになる。ハードウェアがない試験ではコールバックの回数を数える。

### 13.3.4 ジョブの実行

共通層はジョブを1つずつ`kick`でバックエンドに渡す。制御リストのジョブは、ハードウェアでは2段階である。`kick`がキャッシュを無効化してビニングのリストを始め、コアの割込みで「ビニングのフラッシュ完了」が来ると、割込みハンドラがレンダリングのリストを始める。「フレーム完了」が来たら、必要ならキャッシュをクリーンして、共通層にジョブの終わりを通知する。ビニングのリストが空のジョブ(タイルを描くだけのブリット)は、すぐにレンダリングから始める。キャッシュのクリーンのジョブは割込みがないので、`kick`の中でポーリングして終える。

コンピュートのジョブ(CSD)は、`kick`がジョブの表に切り替えた後、キャッシュを無効化し(コード、ユニフォーム、読むバッファがプロセッサか前のジョブで書かれていることがある)、完了したディスパッチの数(`CSD_STATUS`のビット11〜4)を控えてから、キューのディスパッチの設定`CFG1`〜`CFG6`(7.1では0x934〜0x948)を書き、`CFG7`(0x94c)を0にし、最後に`CFG0`(0x930)を書く。`CFG0`を書くとディスパッチがキューに入る。終わりはコアの割込み「CSD完了」(7.1ではビット6)で知り、割込みが来なくても1msごとの監視で完了数の変化から知る。終わったら、シェーダがTMUで書いたものをライトコンバイナとL2Tからメモリに書き出してから、共通層にジョブの終わりを通知する。v3dドライバがSSBOを使うのに要る「キャッシュの書き出し」(`DRM_V3D_PARAM_SUPPORTS_CACHE_FLUSH`)は、この書き出しで満たす。

ドライバは、制御リストのジョブの各段階の時間をシステムカウンタ(`cntvct_el0`)で測り、終わったジョブについて合計する(`v3d_jobt_take`、`T_V3DJOBT`)。段階は、キャッシュを無効化してビニングを始めるまで、ビニング(終わりを割込みハンドラで見るまで)、キャッシュを無効化してレンダリングを始めるまで、レンダリング(同じく終わりを見るまで)、終わった後のキャッシュのクリーンの5つで、最初のジョブの開始と最後のジョブの終わりの時刻も持つ。ビニングとレンダリングの時間には割込みの遅れが含まれる。合成(13.10.7)がこの値を読んで表示する。

MMUの違反の割込みが来たら、違反したアドレスとクライアントを記録し、1つのジョブにつき4回まで表示する。違反したアクセスはスクラッチページに向かうので、ジョブはそのまま最後まで進み、「フレーム完了」のときに失敗として終える。1つのジョブで割込みが1000回を超えたら、消去できずに出続けているものとみなして、その割込みを禁止し、ジョブを失敗として終える。割込みが出続けてシステムが止まるのを防ぐためである。2秒以内に終わらないジョブは、共通層が`reset`を呼んでGPUを止め、失敗として扱う。リセットは現在、CLEの両スレッドをリセットし、割込みを消去し、MMUを消去するだけである。PMブロックによるブロック全体のリセットは未実装である。

### 13.3.5 未実装のもの

TFUのジョブ、ビニングとレンダリングの並行実行(前のジョブのレンダリング中に次のジョブのビニングを進める)、パフォーマンスカウンタ、アイドル時のクロックの停止、ブロック全体のリセット、GMP(メモリ保護)である。ウインドウの合成(13.10)は描画のジョブだけで行うので、これらを必要としない。

## 13.4 共通層

### 13.4.1 バッファオブジェクト

バッファオブジェクト(BO)は、GPUが自分のMMUを通して読み書きするメモリである。ページアロケータから1ページずつ取るので、大きなBOでも連続した物理メモリを必要としない。ページはキャッシュを通して0で埋めた後、一度キャッシュからクリーンして追い出す。その後、CPUはキャッシュしないマッピングでだけ触る。バックエンドが物理アドレスの上限(`pa_limit`)を示せば、その範囲のページだけを使う(4GB以下なら32bitのゾーンから取る)。

| 関数 | 機能 |
| --- | --- |
| `knl_gpu_bo_create` | BOを作る。バックエンドがあればそのMMUに入れてGPUアドレスを得る。`GPU_BO_NOGPU`ならMMUには入れない |
| `knl_gpu_bo_get`、`knl_gpu_bo_put` | 参照を増やす、減らす。最後の参照がなくなるとMMUから外してページを解放する |
| `knl_gpu_bo_map`、`knl_gpu_bo_unmap` | プロセスのアドレス空間にマッピングする、解除する |
| `knl_gpu_bo_ref` | サイズ、GPUアドレス、プロセスでのアドレス、参照数、使用中のジョブの数 |
| `knl_gpu_bo_wait` | そのBOを使うジョブがすべて終わるまで待つ |
| `knl_gpu_bo_wrap` | ほかの持ち主のページ(バックバッファ、ウインドウのピクセルなど)の物理アドレスの列から、MMUに入れたBOを作る。ページは持ち主のままで、BOを手放してもMMUから外すだけで解放しない。CPUのキャッシュの操作と、ジョブの間ページを手放さないことは持ち主の役目である(13.10.5) |

プロセスには共有メモリの領域(4.6、5.3)にマッピングする。アドレスは最初にマッピングしたときに決まり、以後どのプロセスにマッピングしても同じアドレスになる。あるプロセスがGPUで描いたバッファを、ウインドウシステムが同じアドレスでコピーなしに読める。共有メモリの領域のページはアドレス空間を破棄しても解放されないので、BOのページはBO自身が管理できる。マッピングは読み書き可能、実行不可、キャッシュしない(Normal Non-cacheable)属性である。マッピングは参照を1つ持ち、解除すると返す。プロセスの終了時にこれを返すのはSVCの層の役目である(13.5)。

共有メモリの領域のアドレスは再利用しないので、BOを作っては捨てるプログラムは領域(64TB)を少しずつ消費する。Mesaはバッファを再利用するので実用上は問題にならないが、長時間動かすブラウザで問題になれば、BOのアドレスを再利用する仕組みを加える。

### 13.4.2 ジョブとフェンス

ジョブは`knl_gpu_submit`で1本のキューに入り、次のフェンス番号を受け取る。専用のタスク(優先度9)がキューから1つずつ取り出してバックエンドで実行する。この順序により、フェンス番号nが終わったことは、それより前のジョブがすべて終わったことを意味する。ジョブは使うBOを列挙し、終わるまでそれらの参照を持つので、ジョブの途中でBOが解放されることはない。ジョブは待つべきフェンス(`after`)を指定できるが、現在はジョブを順に実行するので、それは常に満たされている。

| 関数 | 機能 |
| --- | --- |
| `knl_gpu_submit` | ジョブを投入し、フェンス番号を返す |
| `knl_gpu_wait` | フェンスが終わるまで待つ。成功なら`E_OK`、ジョブが失敗したかGPUをリセットしたなら`E_IO`、時間切れなら`E_TMOUT` |
| `knl_gpu_done` | 終わった最後のフェンス番号 |
| `knl_gpu_ref` | GPUの種類、バージョン、QPU数、機能、識別レジスタの値 |

待つ側は、「フェンスが終わった」のイベントフラグのビットをクリアしてから終わった番号を確かめ、その後で待つ。タスクは番号を更新してからビットを立てるので、確かめてから待つまでの間に終わったフェンスも取りこぼさない。

### 13.4.3 バックエンド

バックエンドは`T_GPUOPS`(種類、実行できるジョブ、物理アドレスの上限、`info`、`bo_bind`、`bo_unbind`、`kick`、`reset`と、プロセスのアドレス空間の`as_create`、`as_destroy`、`as_bind`、`as_unbind`)を`knl_gpu_register`で登録する。アドレス空間は自分のページテーブルで、そこで走らせるジョブは`knl_gpu_submit_as`で投入し、`kick`がその表を受け取る(13.5.1)。アドレス空間を持たないバックエンドは4つを空にする。ジョブの終わりは`knl_gpu_job_end`で通知し、割込みハンドラからも`kick`の中からも呼べる。同時に登録できるバックエンドは1つである。予定しているバックエンドは、Raspberry Pi 5のV3D(13.3)、x64のIntelのGPU(13.11)、QEMUのvirtio-gpu(13.7.2)、試験用のもの(13.7.3)である。x64では`T_GPUOPS`に、空間の利用者が選んだアドレスにBOを置く`as_bind_at`、`as_unbind_at`と、プロセスのBOのマッピングをキャッシュする印`coherent`が加わる。

## 13.5 プロセスからの利用

プロセスはSVCのクラス10(`gp_`、`include/ts/gpuapp.h`)でGPUを使う。関数はMesaのドライバがカーネルに出す要求(DRMのV3D用のインタフェース)と1対1に対応させ、ユーザ空間の変換(DRMシム、13.6.2)を薄くする。カーネル側は`device/gpu/gpu_svc.c`で、GPUの共通層(13.4)の関数を呼ぶ。

| 関数 | 対応するDRMの要求 | 機能 |
| --- | --- | --- |
| `gp_opn_gpu`、`gp_cls_gpu` | デバイスを開く、閉じる | GPUのコンテキストを作る、破棄する。コンテキストはBOの番号の表を持つ |
| `gp_ref_gpu` | `GET_PARAM` | GPUの種類、識別レジスタの値と機能。GPUのないマシンでは`E_NOEXS` |
| `gp_cre_bo`、`gp_del_bo` | `CREATE_BO`、`GEM_CLOSE` | BOを作り、番号、GPUアドレス、大きさを返す。番号を削除する |
| `gp_ref_bo` | `GET_BO_OFFSET` | 番号のBOのGPUアドレスと大きさ |
| `gp_map_bo` | `MMAP_BO`と`mmap` | BOを自分のアドレス空間にマッピングし、アドレスを返す |
| `gp_sub_job` | `SUBMIT_CL`、`SUBMIT_TFU`、`SUBMIT_CSD` | ジョブを投入し、フェンス番号を返す。BOは番号で指定する(1つのジョブで1024個まで) |
| `gp_wai_fen` | 同期オブジェクトの待ち | フェンスを待つ |
| `gp_wai_bo` | `WAIT_BO` | BOを使うジョブが終わるのを待つ |
| `gp_shr_bo`、`gp_imp_bo` | `GEM_FLINK`と`GEM_OPEN`、PRIMEのエクスポートとインポート | BOに名前を付けて他のプロセスに渡す、名前から受け取る |
| `gp_bnd_bo`(x64) | i915の`EXECBUFFER2`の一覧のアドレス(softpin) | BOをコンテキストの空間の、プロセスが選んだ48ビットのアドレスに置く(13.11.3) |

コンテキストは開いたプロセスのもので、全体で32個まで開ける。表は64個の番号から始まり、足りなくなると倍にして16384個まで伸びる。表の各項目がBOの参照を1つ持ち、プロセスへのマッピングがもう1つ持つ(13.4.1)。プロセスは自分のコンテキストの表にある番号しか指定できず、他のコンテキストの番号、削除した番号、他のプロセスのコンテキストは`E_ID`になる。カーネルはジョブを投入するとき、番号から引いたBOの参照をジョブに持たせる。表はスピンロックで守り、BOを作る、マッピングする、待つといった時間のかかる処理はロックを放してから行う。その間に同じプロセスの他のタスクが番号を削除したときは、後で表を見直して、作ったマッピングを外す。プロセスの空間へのマッピングとその解除は、プロセス表のロックの下で行う(`knl_prc_space_call`)。終了しかけたプロセスの空間が途中で消えないようにするためである。

マッピングは番号ごとに一度作り、番号を削除するまで残す。2度目の`gp_map_bo`は同じアドレスを返す。名前は`gp_shr_bo`のときに作られ、BOの参照を1つ持ち、元の番号が削除されるかコンテキストが閉じられるまで有効である。名前の下位8ビットが名前の表の位置、上位が世代で、位置を使い回しても古い名前は`E_NOEXS`になる。

プロセスが終了すると、`prc_close_all`が`knl_gpu_prc_end`を呼び、そのプロセスのコンテキストをすべて閉じて、表のBO、マッピング、名前の参照を返す。実行中のジョブは最後まで実行され、BOはそのジョブが終わってから解放される。クラス10の呼出しはファイルやウインドウと同じく、プロセスの終了で途中から切られない呼出しとして扱う(9.7)。そのため、フェンスとBOの待ちは50msずつに区切り、区切りごとにプロセスが終了しかけていないかを見て、終了しかけていれば`E_DISWAI`で戻る。待っていたタスクはSVCを出るところで終わり、プログラムには戻らない。一方、終了しかけたプロセスのタスクが新しくクラス10を呼ぶと、SVCの入口(`knl_prc_call_enter`)が`E_DISWAI`を返し、タスクはプログラムに戻る。ブラウザが`_exit`したときに、GPUでラスタ化するスレッドやWebGLのスレッドがまだMesaの中で動いているのがこの場合である。DRMシムは`E_DISWAI`を受けると、エラーを返さずにそのスレッドを止めておき、プロセスとともにシステムが終わらせるのを待つ(13.6.2)。Linuxでは、終了するプロセスのほかのスレッドは`ioctl`からプログラムに戻らずに終わるので、Mesaのv3dドライバは`ETIME`以外の待ちの失敗を想定せず、ログ(`wait failed: -4`)を出して`abort`する。2026年10月17日まで、DRMシムは`E_DISWAI`を`EINTR`にして返していたので、実機でブラウザを閉じるとコンソールにこの行が出た。

BOがコンテキストの表に入ること、ジョブの数の上限、プロセスのジョブが他のメモリに触れないことの根拠は13.5.1に書く。

フェンスの終わりを実身のイベント(8.8)として受け取る仕組みは、まだない。GPUをデバイスの実身として見せ、`ob_ntf_evt`でフェンスの終了を通信の実身に通知させる予定である。ブラウザのように1つのメッセージループですべてのイベントを待つプログラムは、GPUを待つためだけにスレッドを使わずに済む。

試験の群`gl`(`tests/ktest/ktest_gl.c`)は、試験用のプロセス`tests/uprog/gpprog.c`(`/boot`の`GPPROG.ELF`、`lib/libts`で作る小さなプログラム)でクラス10を確かめる。

| 試験 | 内容 |
| --- | --- |
| `gl_gp_bo` | コンテキストとBOを作り、マッピング(0で埋まっていること、書いて読めること、2度目に同じアドレス)、大きさの切上げ、引数の誤り、名前で別のコンテキストに渡すと同じページが同じアドレスに見えること、他のコンテキストの番号の拒否、GPUのないマシンでジョブが`E_NOEXS`になること、元の番号の削除で名前が消えること。終わった後にコンテキストが残らず、空きページが元に戻ること |
| `gl_gp_job` | 試験がジョブをすぐに終える試験用のバックエンドを登録し、プロセスから何もしないジョブと制御リストのジョブを投入する。フェンスの順序、フェンスとBOの待ち、表にない番号と多すぎる番号の拒否。バックエンドはコンテキストごとにV3Dと同じ形のページテーブルを与え、ジョブを始めるたびにその表を引く。どのジョブも自分のコンテキストの表で走ること、2つのコンテキストの同じアドレスが別のページであること、カーネルのBOのアドレスがどちらの表でも無効であること、コンテキストを閉じると表がなくなること |
| `gl_gp_hold` | 2つのコンテキストに70個のBOを作って一部をマッピングし、名前を付けたまま終了する。カーネルがすべてを返し、空きページが元に戻ること |

### 13.5.1 GPUの共有とアドレス空間

V3Dは、カーネルのウインドウの合成(13.10)と、プロセスのOpenGL ES(Mesaのv3dドライバ、13.6)の両方が使う。2つは次のように分ける。

ジョブの順番は共通層の1本のキュー(13.4.2)で決まる。合成のジョブもプロセスのジョブも、投入された順に1つずつ実行する。合成が待たされる時間を抑えるため、1つのコンテキストがキューに置けるジョブは4つまでとし、5つ目の`gp_sub_job`はそのコンテキストの最も古いジョブが終わるまで待つ。1つのジョブは2秒で打ち切られる(13.3.4)ので、合成のジョブの前に並ぶのは、GPUを使うプロセスの数の4倍のジョブまでである。

MMUのページテーブルは、1つの表の中で範囲を分けるのではなく、プロセスのコンテキストごとに別の表を持ち、ジョブごとに切り替える。1つの表の中で範囲を分けても、GPUはジョブが渡したアドレスを表のどこへでも引けるので、範囲の外へのアクセスを止められないからである。

| 表 | 中身 | 使うジョブ |
| --- | --- | --- |
| カーネルの表(起動時に作る4MB) | カーネルのBO(合成のコマンド、ウインドウのピクセルとバックバッファを包んだBO、試験のBO、カーネルのオーバーフローのメモリ) | 合成と試験のジョブ |
| コンテキストの表(`gp_opn_gpu`のときに作る4MB) | そのコンテキストが作った、または名前で受け取ったBOと、そのコンテキストのオーバーフローのメモリ(512KB)だけ | そのコンテキストの`gp_sub_job`のジョブ |

プロセスのBOはカーネルの表に入れない(`GPU_BO_NOGPU`で作り、コンテキストの表にだけ入れる)。BOのGPUアドレスは表ごとに割り当て、`gp_cre_bo`と`gp_ref_bo`はコンテキストの表でのアドレスを答える。2つのコンテキストで同じアドレスが別のページを指すことがある。

ジョブを始めるとき(`kick`)、ドライバは前のジョブと表が違えば、まず前の表のままGPUのキャッシュをメモリに書き出し(`caches_clean`)、`MMU_PT_PA_BASE`に新しい表を書き、MMUのエントリのキャッシュとTLBを消してから、制御リストを始める。切り替えはジョブの間、両方の制御リストのスレッドが止まっているときだけである。ジョブを始めるときには、従来どおりL2T、テクスチャ、ユニフォーム、命令のキャッシュを無効にする(13.3.4)。

コンテキストの表は、BOを使うジョブより長く残す。キューに入ったジョブが表の参照を持ち、コンテキストを閉じても(プロセスが終わっても)、表とオーバーフローのメモリはそのコンテキストの最後のジョブが終わってから解放する。BOの番号を削除したときは、表からそのエントリを外してTLBを消し、BOの参照を返す。そのBOを使うジョブがまだ残っていれば、ページはジョブが終わるまで残るが、ジョブからは見えなくなる(そのプロセス自身のジョブが失敗するだけである)。

#### プロセスのジョブが他のメモリに触れないことの根拠

1. プロセスのジョブは必ずコンテキストの表で走る。`gp_sub_job`はジョブの記述をカーネルにコピーした後、表を自分で付けてキューに入れる(`knl_gpu_submit_as`)。プロセスは表を選べない。ドライバは、表を付けたジョブを、カーネルの表に切り替えずには走らせない。プロセスが自分の表を持てないとき(起動時の確認が通らなかったとき)は`gp_opn_gpu`が失敗し、そのプロセスのジョブはGPUで走らない。
2. コンテキストの表のエントリは、そのコンテキストが参照を持つBOのページと、そのコンテキストのオーバーフローのメモリのページだけである。BOのページは作るときに0で埋めるので、前の持ち主のデータも見えない。ほかのエントリはすべて無効で、MMUは無効なエントリ、書込みの禁じられたページ、上限を超えるアドレスへのアクセスを中止し、スクラッチページに向けて割込みで通知する設定である(13.3.3)。
3. 表は32ビットのアドレス空間全体(4MB)を覆う。小さな表にすると、表より上のアドレスのエントリを表の後ろのメモリから読むおそれがある。アドレスの上限(`MMU_ADDR_CAP`)の意味は公開の資料にないので、それに頼らない。
4. カーネルがプロセスのために書くレジスタ(制御リストの開始と終了`CT0QBA`〜`CT1QEA`、タイルの割当てメモリ`CT0QMA`と`CT0QMS`、タイルの状態`CT0QTS`、オーバーフローのメモリ`BPOA`と`BPOS`)はどれもGPUのアドレスで、コンテキストの表で引かれる。オーバーフローのメモリはそのコンテキストのものを渡すので、別のプロセスのジョブやカーネルのジョブが読むメモリに、プロセスのジョブが書くことはない。
5. TFUのジョブは受け付けない(`E_NOSPT`)。v3dドライバにもTFUを持たないと答える。コンピュートのジョブは、制御リストのジョブと同じくジョブの表に切り替えてから走らせる。カーネルが書く`CFG5`(シェーダのコード)と`CFG6`(ユニフォーム)はGPUのアドレスで、コンテキストの表で引かれる。
6. GPUのキャッシュの中身が別の表の下で書き出されないよう、表を切り替える前に前の表のままキャッシュを書き出す。次のジョブの前にはキャッシュを無効にするので、前のジョブのデータを読むこともない。
7. スクラッチページはすべての表で共通で、無効なアクセスの書込み先になる。中身はジョブを越えて残るので、2つのプロセスが故意に無効なアドレスを使えば、わずかな情報をやりとりできる。カーネルのデータやほかのプロセスのBOはここに入らない。
8. これらは、V3DのすべてのメモリのアクセスがMMUを通ることを前提にしている。起動時の確認(13.8.3)は、コンテキストの表のジョブがカーネルのBOのアドレスに書いても、MMUが中止してBOが変わらないことを実機で確かめ、通らなければプロセスに表を与えない。

## 13.6 ユーザ空間: Mesa

### 13.6.1 バージョンと構成

Mesa 26.2.3(2026年9月16日リリースの安定版、MITライセンス)を使う。ChromiumはMesaを同梱せず、WebGLはANGLEがOpenGL ES(EGL経由)かVulkanの上に実装する。したがってMesaのバージョンはChromiumのバージョンに縛られず、ANGLEのOpenGL ESのバックエンドが必要とするEGL 1.4以上と、WebGL 2に必要なOpenGL ES 3.0以上を満たせばよい。V3D 7.1に対するMesaのv3dドライバはOpenGL ES 3.1を提供する。以後のバージョンの更新は26.2系のポイントリリースに追従する。

| 部分 | 場所 | 規模(行) | 用途 |
| --- | --- | --- | --- |

### 13.6.2 OSに求めるものと対応

Mesaの`src/util`、EGL、ドライバがLinuxに求めるものを、次のように与える。Mesaのファイルを変える必要のあるものだけをパッチ(`tools/mesa/patches`、13.6.5)にし、それ以外はTessronOSの側(`lib/libcxxrt`、`lib/libgl`、`tools/mesa/shim`)で受ける。`tools/mesa/shim`はLinuxのライブラリのヘッダの代わりで、mesonの検査とコンパイルが読み、その実体は`lib/libgl`にある。

| Mesaが使うもの | TessronOSでの対応 |
| --- | --- |
| OSの判定(`util/detect_os.h`) | パッチで`DETECT_OS_TESSRONOS`を加え、POSIXの一つとする(`DETECT_OS_POSIX`)。コンパイラに`-D__TESSRONOS__`を渡す |
| スレッド(C11の`threads.h`、pthread) | Mesaの`c11/impl/threads_posix.c`を`lib/libpthread`の上で使う |
| スレッドローカル変数 | `lib/libpthread`のemutls |
| 時刻と待ち(`os_time.c`) | POSIXの経路のまま、`lib/libcxxrt`の`clock_gettime`、`usleep`で動く |
| メモリの大きさとページの大きさ(`os_misc.c`) | `lib/libcxxrt`の`sysconf`。パッチは`unistd.h`を読ませるだけ |
| スレッドのCPU時間(`u_thread.c`の`pthread_getcpuclockid`) | ないので0を返す(パッチ)。HUDとトレースだけが使う |
| ログ(`log.c`の`syslog`、プロセス名) | `syslog`はコンソールに書く(`lib/libgl/gl_os.c`)。プロセス名は持たない |
| バイト順(`util/u_endian.h`の`endian.h`) | `tools/mesa/shim/endian.h`がnewlibの`machine/endian.h`の名前で定義する |
| DRMの`ioctl`(`DRM_IOCTL_V3D_*`、`GEM_CLOSE`、`GEM_FLINK`、`GEM_OPEN`) | DRMシム(`lib/libgl/gl_drm.c`)が要求の番号で振り分け、`gp_`のSVC(13.5)を呼ぶ。`gp_`のエラーは`errno`に直す。プロセスの終了で断られた呼出し(`E_DISWAI`、13.5)だけはドライバに返さず、スレッドをそこで止めておく |
| `mmap`によるBOのマッピング | `lib/libcxxrt`の`mmap`がGPUの記述子(0x3400から)をDRMシムに回し、DRMシムが`gp_map_bo`を呼ぶ。マッピングはBOがある間残るので、`munmap`は何もしない。`close`と`fcntl`の複製もDRMシムに回る |
| 同期オブジェクト(`drmSyncobj*`) | DRMシムがフェンス番号を保持するオブジェクトとして実装し、待ちは`gp_wai_fen`にする。タイムラインは持たない |
| PRIMEのエクスポートとインポート | DRMシムが`gp_shr_bo`の名前を持つ記述子(0x3440から)を作る、受け取る |
| デバイスの列挙(`drmGetDevices2`) | 何も見つからないと答える。GPUはEGLのプラットフォーム`tessronos`が自分で開く(13.6.3) |
| 記述子のデバイスの情報(`drmGetDevice2`) | GPUの記述子には、レンダーノード(`/dev/dri/renderD128`)だけを持つplatformバスのデバイスとして答える。デバイスツリーの名前と`compatible`の`brcm,2712-v3d`を入れる。ローダはPCIのデバイスでないのでPCIの番号での選択をやめ、`drmGetVersion`の名前`v3d`でドライバを選ぶ |
| 記述子の複製(`fcntl`の`F_DUPFD_CLOEXEC`) | Galliumのローダは画面を作る前に記述子を複製する。newlibの`fcntl`は`HAVE_FCNTL`なしで作られていて、どの要求にも`ENOSYS`を返し`_fcntl`を呼ばないので、`lib/libcxxrt`が`fcntl`そのものを持ち`_fcntl`に渡す。GPUの記述子ならDRMシムが同じコンテキストの新しい記述子を返す |
| sync_fileの記述子(`drmSyncobjExportSyncFile`、`drmSyncobjImportSyncFile`、`libsync.h`) | v3dドライバはフレームのフェンスをsync_fileの記述子で持つ。DRMシムが同期オブジェクトのその時点のフェンス番号を持つ記述子(0x3480から)を作り、取り込みでは同期オブジェクトにその番号を戻す。待ちは`gp_wai_fen`、併合は番号の大きい方を残す(ジョブは番号の順に走る)。記述子はプロセスの中だけのもので、ほかのプロセスには渡せない |
| 共有ライブラリの動的な読込み(`dlfcn.h`) | 使わない。EGL、OpenGL ES、Gallium、ドライバを1つの静的ライブラリにしてプログラムにリンクする。`dlopen`は何も開けないと答える(`gl_os.c`)。`gl_os.c`の関数はどれも弱い名前で、自分の`dlopen`を持つプログラム(ANGLEにMesaのEGLを渡すブラウザ、第14章14.6.1)ではそちらが使われる |
| ドライバの設定ファイル(driconf) | 静的な既定値だけを使う(`-Dxmlconfig=disabled`)。プログラム名で選ぶ設定は、newlibに正規表現の実装がないので使わない(`NO_REGEX`) |
| ディスクのシェーダキャッシュ | 無効(`-Dshader-cache=disabled`)。後で実身に置く |
| zlib | 使わない。V3Dの制御リストを表示するデバッグ用のデコーダだけが使い、展開できないと答える(`gl_os.c`) |
| `memfd_create`の封印(`F_ADD_SEALS`) | `tools/mesa/shim/fcntl.h`が番号を定義し、`lib/libcxxrt`は知らない命令を何もせずに受ける |
| シグナル(HUDの表示の切替え) | ないので、その処理を入れない(パッチ) |
| `getuid`、`getgid`、`getegid`、`sync` | `lib/libcxxrt`(利用者は1人)と`gl_os.c`(待つものがない) |
| TFUのジョブ(`DRM_IOCTL_V3D_SUBMIT_TFU`) | カーネルはまだTFUを持たず、`GET_PARAM`の`SUPPORTS_TFU`に0を答える。Linuxのv3dドライバはいつも1を答えるので、Mesaのv3dドライバはこれを見ずにblitでTFUのジョブを出し、失敗して`MESA: error: Failed to submit TFU job: -1`を出す。パッチ(`v3d-tfu.patch`)で、画面を作るときに`SUPPORTS_TFU`を読み、0ならTFUを使わずにほかのblitの方法と描画によるミップマップに回す |

プロセスの記述子の番号は、`lib/libcxxrt`と`lib/libgl`が範囲を分けて持つ。ファイルの層の記述子は3から、`eventfd`と`epoll`は0x3000から0x303f、DRMシムのGPUの記述子は0x3400から0x343f、PRIMEの記述子は0x3440から0x347f、sync_fileの記述子は0x3480から0x357f、`/dev/urandom`(開くときに実身の木で「/」からdevの文字デバイスをたどって確かめ、読むのは実身「乱数」の鍵から)は0x3800から0x380f、`memfd_create`のメモリのオブジェクトは0x3c00から0x3fff、ソケットは0x4000からである。`lib/libcxxrt`の`close`、`fcntl`、`mmap`はメモリのオブジェクトの範囲をDRMシムより先に調べるので、2つの範囲が重なるとGPUの記述子はDRMシムに届かない。DRMシムの範囲が乱数の範囲に届けばコンパイルで止まる(`gl_drm.c`の`#error`)。

### 13.6.3 ウインドウシステムとEGL

EGLに新しいプラットフォーム`tessronos`を加えた(`tools/mesa/src/egl/drivers/dri2/platform_tessronos.c`。Mesaのコピーに足してlibEGLと一緒にコンパイルする)。プラットフォームはMesaのヘッダだけを読み、TessronOSの呼出しは`tools/mesa/shim/ts_glport.h`の関数(`lib/libgl/gl_win.c`、`gl_drm.c`)を通す。Mesaのソースの名前とTessronOSのヘッダの名前を一つのファイルで混ぜないためである。プログラムが読むのは`include/ts/glapp.h`である。

- `EGLDisplay`は`eglGetPlatformDisplay(EGL_PLATFORM_TESSRONOS, NULL, NULL)`で得る。`EGL_PLATFORM_TESSRONOS`は仮の値`0x3FD0`である。TessronOSのプロセスでは`eglGetDisplay(EGL_DEFAULT_DISPLAY)`も同じプラットフォームになる(既定のプラットフォームをパッチで`tessronos`にした)。プログラムは`EGL_NO_PLATFORM_SPECIFIC_TYPES`を定義して`<EGL/egl.h>`を読み、ネイティブの型はすべて`void *`になる。
- ドライバは、マシンにV3Dがあり、カーネルがプロセスにアドレス空間を与えるとき(13.5.1)はv3d、そうでなければsoftpipe(ローダの`swrast`)である。環境変数`TS_GL_DRIVER=softpipe`ならV3Dがあってもsoftpipeにする。v3dにするときは、DRMシムでGPUを開き(`ts_gl_drm_open`、`gp_opn_gpu`)、ローダにv3dドライバを選ばせ、画面を作った後で64×64のフレームをGPUで消して読み戻す(`ts_gpu_check`)。合わなければ画面を壊してsoftpipeに戻る。選んだものと理由はコンソールに出す(13.8.3)。v3dでは、ピクセルバッファを1枚のイメージ(前のバッファ)で描く。
- ウインドウのサーフェスは、ウインドウの実身のキー(書込みの権利で開いたもの)を入れた`TS_EGLWINDOW`をネイティブのウインドウとして作る。そのピクセルは、プロセスにマッピングされた作業領域の面(`wm_obj_surf`、10.2)である。softpipeはフレームを自分のバックバッファに描き、`eglSwapBuffers`でソフトウェア描画のローダの拡張(`putImage2`)を通してプラットフォームに渡す。プラットフォームは行ごとに面と比べながらコピーし(ウインドウが使わない最上位のバイトは0にする)、変わった行の帯を最大16個の長方形にまとめて`wm_obj_put`でウインドウに出す。`eglSwapBuffersWithDamageKHR`で長方形を指定されたときは、その長方形だけをコピーして出す。
- フレームごとに、ドライバがサーフェスの大きさを尋ねるたびに`wm_obj_surf`を呼ぶ。ウインドウの大きさが変わると新しい大きさの面が返り、バックバッファもそれに合わせて作り直される。構成はウインドウの0x00rrggbbと同じ並び(赤・緑・青が16、8、0ビット目から8ビットずつ、アルファは24ビット目からか、なし)のものにウインドウとピクセルバッファの両方の種類を付け、ほかの形式はピクセルバッファだけにする。フレームは出すとすぐに画面に出るので、待つべき表示の間隔はなく、スワップの間隔は0を既定にした。
- ピクセルバッファのサーフェス(pbuffer)とサーフェスなしのコンテキスト(`EGL_KHR_surfaceless_context`)も持つ。ChromiumのWebGLはANGLEが自分でフレームバッファオブジェクトを使うので、最初はこれだけで動き、結果は`glReadPixels`でSkiaのCPUのラスタに渡せる。ブラウザのGPUでのラスタ化(第14章14.7.2)も、ピクセルバッファのコンテキストの上でSkiaのGaneshが自分のレンダーターゲットに描き、`glReadPixels`で作業領域の面に読み戻す。
- v3dで描くウインドウでは、後ろのバッファを線形のイメージ(v3dのBO)にする。イメージのローダがウインドウの大きさのものを1枚渡し、`eglSwapBuffers`は描画を流してからそれをマッピングし(GPUの終わりを待つ)、softpipeのフレームと同じく行ごとに比べてウインドウの面にコピーし、変わった帯を`wm_obj_put`で出す。後ろのバッファはそのまま残るので、次のフレームはこのフレームから始まる。ウインドウの大きさが変わると、次のフレームで新しい大きさのイメージを作る。BOはキャッシュしないマッピングなので、CPUでの読出しは速くない。次の段階では、BOをウインドウシステムに渡し、GPUでウインドウを合成する(13.10)。

### 13.6.4 ツールチェーンでの試し

`tools/mesa/probe.sh`は、Mesa 26.2.3を取得し(SHA-256を検査する)、必要な生成物をMesaのPythonスクリプトで作り、TessronOSのプロセス用のコンパイラの設定(`build_make/cxxrt.mk`と同じ`include/tsposix`、newlib、`-march=armv8.2-a -O2`)でコンパイルする。生成物は作業ディレクトリ(既定は`/tmp/tsmesa`)にだけ置く。2026年9月29日、12並列で実行した結果は次のとおりである。

| 対象 | 結果 | コード量(.text) | 時間 |
| --- | --- | --- | --- |
| V3D 7.1のパケットの詰め込み(`cle_probe.c`) | 生成した5439行のヘッダでホスト用に実行し、パケットを詰めて読み戻せることを確認。TessronOSのプロセスとしてもリンクできた | 95KB(プログラム全体) | 数秒 |
| NIR(生成物を含む) | 239ファイルすべてコンパイルできた | 9.7MB | 58秒 |
| V3Dのシェーダコンパイラ、QPU | 31ファイルすべて | 182KB | 6秒 |
| `src/util`、`src/util/format` | 89ファイル中83。失敗は`os_time.c`(OSの判定)、`os_misc.c`(同)、`log.c`(プロセス名)、`u_thread.c`(`pthread_getcpuclockid`)、`u_sync_provider.c`(libdrm)、`xmlconfig.c`(driconfの生成物) | 3.7MB | 24秒 |

### 13.6.5 ビルドの仕組み

`make GL=1`のとき、`build_make/cxxrt.mk`が`tools/mesa/build.sh all`を呼び、静的ライブラリ`~/tsmesa/libtsgl.a`(置き場は`GL_DIR`)を作る。ライブラリは移植層、パッチ、シム、スクリプトが変わったときだけ作り直し、`build.sh`は変わったものだけをコンパイルする。x64(`TARGET=_X64_`)では`tools/x64/mesa/build.sh`が同じMesaとパッチ、移植層をx86_64-elfで作り、置き場の既定は`~/tsmesa-x64`、ドライバはsoftpipeとIntelのiris(13.11.9)である(3.10.5)。`GL`を指定しないときは、Mesaに触れず今までどおりにビルドでき、小物「歯車」のレコード1は作り方を言うだけの小さなプログラムになる。

| 段 | 内容 |
| --- | --- |
| `fetch` | Mesa 26.2.3を`~/mesa`に取得し、SHA-256を検査して展開する。meson(1.4以降)、ninja、Pythonのmakoとyamlがあることを確かめる |
| `tree` | 展開したソースをハードリンクで`~/tsmesa/src`に複製し、パッチを当てる。パッチが当たるファイルだけはコピーを別のファイルにしてから書き換えるので、取得したソースは変わらない。パッチが変わったときだけ作り直し、当てた結果が前と同じファイルは前の時刻を保つ。`tools/mesa/src`のファイルは、Mesaの`src`の同じ場所に、中身が違うときだけコピーする |
| `setup` | ホストのmesonを本番のオプションで実行する。コンパイラはTessronOSのプロセス用のもの(`aarch64-none-elf-gcc`、`include/tsposix`、`include/tscxx`、`tools/mesa/shim`)で、mesonの関数の検査は`lib/libcxxrt`と`lib/libpthread`に対してリンクするので、プログラムが実際に持つ関数だけが見つかる(`sysconf`、`clock_gettime`、`memfd_create`はある、`dlopen`、`getrandom`、`secure_getenv`はない)。libdrmはバージョンと`tools/mesa/shim`だけを示す`pkg-config`の記述で見せる |
| `gen` | mesonが書いた生成のコマンド(86個)をninjaで走らせる。NIRの表、フォーマットの表、GLSLの字句と構文の解析器(ホストのflexとBison)、glapiの表などで、クロスコンパイルしたプログラムを走らせるものはない。作り直した生成物のうち中身が前と同じものは前の時刻を保つ |
| `compile` | `tools/mesa/translate.py`が`build.ninja`をたどり、libEGL、libGLESv2、Galliumのライブラリ(`libgallium-26.2.3.so`)にリンクされるオブジェクトファイルを選び、その`compile_commands.json`のコマンドを書き換えてコンパイルする。位置独立のコードと`-pthread`、`-Werror`を外し、言語の水準を`gnu11`、`gnu++17`にし(newlibが厳密な水準では`alloca`やPOSIXの名前を隠すため)、関数ごとのセクション(`-ffunction-sections`)と`-O2 -g0`にする。コマンドと依存のファイルが変わらないオブジェクトファイルはコンパイルし直さない |
| `port`、`lib` | 移植層(`lib/libgl`)をコンパイルし、全部を`libtsgl.a`にまとめ、プログラムが読むKhronosのヘッダ(`EGL`、`GLES2`、`GLES3`、`KHR`)を`~/tsmesa/include`に置く |

mesonのオプションは次のとおりである。プラットフォームはLinuxのもの(X11、Wayland、GBM)を持たず、EGLのプラットフォーム`tessronos`を足す。GLX、glvnd、LLVM、ディスクのシェーダキャッシュ、driconfのXML、zlib、zstd、Valgrind、libunwind、lm-sensors、VA-APIは使わない。

```sh
-Dplatforms= -Degl=enabled -Dgles1=disabled -Dgles2=enabled -Dopengl=true
-Dglx=disabled -Dgbm=disabled -Dglvnd=disabled -Dllvm=disabled -Dvulkan-drivers=
-Dgallium-drivers=softpipe,v3d -Dshader-cache=disabled -Dxmlconfig=disabled
-Dexpat=disabled -Dzstd=disabled -Dzlib=disabled -Doptimization=2 -Db_ndebug=true
```

結果は次のとおりである(2026年10月3日)。

| 項目 | 値 |
| --- | --- |

M5からM8に向けて残っていることは次のとおりである。

- DRMシムのV3Dの要求(`SUBMIT_CL`、`WAIT_BO`、`GET_PARAM`)を実機で確かめる(13.8.3の行)。`GET_PARAM`は識別レジスタをドライバが読んだ値のまま返し、TFU、性能カウンタ、複数の同期オブジェクトを持たないと答える。コンピュートは、起動時の確認が通ったときだけ持つと答える。`GLOBAL_RESET_COUNTER`は0のままである。v3dドライバのBOの読出し(キャッシュしないマッピング)の速さを測る。
- TFUのジョブ(13.3.5)。v3dドライバはTFUがなければミップマップを描画で作る(パッチ`v3d-tfu.patch`でblitもTFUを避ける、13.6.2)。コンピュートのジョブは2026年10月18日に足した(13.3.4)。v3dドライバはコンピュートがなければOpenGL ES 3.0になり、あればRaspberry Pi OSと同じOpenGL ES 3.1になる。WebGL 2はOpenGL ES 3.0で足りるが、WebGPU(DawnのOpenGL ESのバックエンド)は3.1が要る(14.6.5)。コンピュートは実機の起動時の確認(13.3.2)の結果を見てから使う。TFUのレジスタは、Raspberry Pi OSのカーネル(`drivers/gpu/drm/v3d`の`v3d_regs.h`)ではV3D 7.1でハブの0x700から(4.2では0x400から)に移り、出力の設定の`IOC`(0x71c)が加わる。実機で読んで確かめてから足す。
- v3dで描いたウインドウを、CPUでコピーせずにBOのままウインドウシステムに渡し、GPUで合成する(13.6.3)。
- フェンスの終わりを実身のイベントとして受け取る仕組み(13.5)。
- 同期オブジェクトの複数待ち(`DRM_V3D_EXT_ID_MULTI_SYNC`)と性能カウンタは持たない。Vulkanが要るなら足す。sync_fileは、プロセスの中だけの記述子として持つ(13.6.2)。
- ブラウザのWebGLの色のバッファを、読み戻さずにBOのままウインドウシステムに渡す(14.6.1)。
- ブラウザがGPUでラスタ化したページを、読み戻さずにBOのままウインドウシステムに渡し、GPUで合成する(14.7.2)。今は変わった矩形を`glReadPixels`で作業領域の面に読み戻すので、v3dではキャッシュしないマッピングの読出しになる。レンダーターゲットをMesaのBOのEGLイメージにして`gp_shr_bo`の名前で渡せば、ウインドウマネージャのGPUの合成(13.10)がそのまま読める。
- softpipeの速さ。描画はプロセスの1つのタスクで行う。llvmpipeは使わない方針(13.6.1)なので、速くするにはGPUを使うしかない。
- `EGL_PLATFORM_TESSRONOS`の値(`0x3FD0`)は仮のものである。
- ライブラリを`-Os`で作ったときの大きさと速さを比べる。

### 13.6.7 Vulkanという別の道

ANGLEはVulkanの上でも動く。Mesaのv3dvはV3D 7.1でVulkan 1.3を提供する。この道では、OpenGLの状態管理(20万行)、GLSLコンパイラ(8万行)、Galliumの補助(19万行)が不要になり、代わりにv3dv(4万行)、Vulkanの共通部分(9万行)、SPIR-VからNIRへの変換(3万行)が要る。規模はほぼ半分になり、ANGLEが自分のシェーダ変換器を持つのでGLSLの互換性の問題もANGLE側で閉じる。一方、QEMUでの開発にはvirgl(OpenGL)ではなくVenus(Vulkan)が必要で、Windows版のQEMUが持つvirglrendererがVenusを含むかどうかは未確認である。M4まで(カーネルのSVC、DRMシム、ビルドの仕組み)はどちらの道でも共通なので、M5の前にどちらを先にするか決める。

## 13.7 QEMUでの開発

### 13.7.1 使えるQEMU

QEMUはV3Dをエミュレートしないので、V3Dのドライバとv3dドライバの生成するコードは実機でしか確かめられない。QEMUで確かめられるのは、共通層、MMUのページテーブル、SVC、Mesaの全体、EGLとウインドウシステムの結合である。3Dの描画そのものはvirtio-gpuとvirgl(ホストのOpenGLでゲストのOpenGLのコマンドを実行する仕組み)で確かめる。

| QEMU | virtio-gpuの3D | GLを持つ表示 | 判定 |
| --- | --- | --- | --- |
| WSLのxPack QEMU 9.2.4 | `virtio-gpu-pci`(2Dのみ)と`vhost-user-gpu-pci`だけで、`virtio-gpu-gl`がない | なし(`none`、`sdl`、`curses`、`dbus`) | virglは使えない |
| Windows版QEMU 11.0.50(`C:\Program Files\qemu`) | `virtio-gpu-gl-pci`、`virtio-gpu-gl-device`(virtio-mmio)。属性に`blob`、`venus`、`drm_native_context`、`hostmem` | `egl-headless`、`gtk`、`sdl`、`spice-app`、`dbus`。virglrendererとANGLEのDLLを同梱 | virglが使える見込み |

Windows版のQEMUで`-device virtio-gpu-gl-pci -display egl-headless`とすると、デバイスが作られてマシンが起動する(`-display none`では「表示のバックエンドがOpenGLを持たない」として起動しない)。`egl-headless`はウインドウを開かずにホストのGPU(ANGLE経由)で描くので、自動試験に向く。ゲストのドライバがまだないので、virglの3Dコマンドが実際に実行されることはまだ確かめていない。

### 13.7.2 virtio-gpuのバックエンド

TessronOSのvirtioのドライバ(`device/vblk`、`device/vnet`)と同じvirtio-mmioの転送で`virtio-gpu-gl-device`を扱い、共通層のバックエンド(`GPU_KIND_VIRTIO`)にする。

- 初期化で`GET_CAPSET_INFO`と`GET_CAPSET`を発行し、virglのcapsetが返ることを確かめる。これが最初の確認項目になる。
- BOは、ゲストのページ(共通層のBOのページ)をバッキングにしたホストの3Dリソース(`RESOURCE_CREATE_3D`、`ATTACH_BACKING`)に対応させる。V3DのようなGPUアドレスはないので、`bo_bind`はリソース番号を割り当てる。
- ジョブは`SUBMIT_3D`のコマンド列で、フェンス付きで発行する。ホストがフェンスを返したら`knl_gpu_job_end`を呼ぶ。
- ユーザ空間はMesaのvirglドライバとvirglのDRM用winsysを、V3Dと同じDRMシム(`DRM_IOCTL_VIRTGPU_*`の振り分けを加える)で動かす。

試験はネットワークの試験と同じく、WindowsのPythonからWindows版のQEMUで実行する(12.4)。WSLのQEMUで実行する通常の試験には影響しない。

## 13.8 実機で確かめること

1. `V3D=1`で、クロックのタグが応答すること、`IDENT0`が「V3D」と読めること、バージョンが71であること、ハブの識別、コア数、QPU数、MMUの仮想アドレスと物理アドレスの幅。`IDENT0`が読めない場合は、PMブロックの電源ドメイン1を入れる手順を調べる。
2. `V3D=2`で、MMUの設定(`PT_PA_BASE`、`ILLEGAL_ADDR`、`MMU_CTL`の有効ビットとTLBの消去のビット、MMUのキャッシュ)、割込みがINTID 281と282に届くこと、キャッシュのクリーンのジョブが終わること。
3. 最初の描画のジョブとして、ビニングなしのレンダリングのリストで64×64のバッファを1色で塗り、CPUで読み出して確かめる。リストはMesaのパケットの定義から生成したコード(13.6.4)で作る。
4. GPUがCPUのキャッシュを見るかどうか。見るなら、BOをキャッシュするマッピングにしてCPUでの読出しを速くできる。
5. 物理アドレスの幅と、4GBより上のページをBOに使えること。
6. TFUとCSDのレジスタの位置、MMUのエラーを割込みにするビット、ハブの割込みの各ビット。
7. ブロック全体のリセット(PMブロックのリセット0)。

### 13.8.1 実機で読んだ値

2026年9月29日、Raspberry Pi 5で`V3D=1`のイメージを起動して読んだ値は次のとおりである。クロックはファームウェアへの要求で入り、そのままでコアとハブのレジスタが読めた。電源ドメインを別に入れる必要はなかった。

| レジスタ | 値 | 解釈 |
| --- | --- | --- |
| クロック5 | 960MHz(最大960MHz) | 最大周波数で動く |
| コアの`IDENT0` | `07443356` | 下位24bitが「V3D」、上位8bitがメジャーバージョン7 |
| コアの`IDENT1` | `81001441` | マイナーバージョン1、スライス4、スライスあたりのQPU 4(QPUは16)、31:28が8(VPMは64KB) |
| コアの`IDENT2` | `c0078101` | 未解釈 |
| ハブの`IDENT0` | `42554856` | 「VHUB」。ハブのレジスタの位置が正しいことが分かる |
| ハブの`IDENT1` | `00081117` | 3:0と7:4がコアのメジャーとマイナー(7と1)に一致するので、11:8がコア数(1)である。15:12の1と19bitは未解釈 |
| ハブの`IDENT2` | `00001900` | 8bitが立っている(MMUを持つ) |
| ハブの`IDENT3` | `00000700` | 15:8がリビジョン7 |
| MMUのデバッグ情報 | `20804664` | 7:4と11:8がともに6。30を足してアドレスの幅とする解釈では、仮想アドレス、物理アドレスとも36bit(解釈は未確認) |

最初のドライバはハブの`IDENT1`の19:16をコア数として読み、8と表示していた。上の値に合わせて11:8に直し、ハブの`IDENT0`が「VHUB」でなければ終わるようにした。

続けて`V3D=2`のイメージで、MMUの設定と自己試験まで止まらずに進んだ。

| 表示 | 分かったこと |
| --- | --- |
| `page table at a000000, invalid accesses to 9d56000` | 4MBの連続したページテーブルを4GBより下に確保できた。`PT_PA_BASE`、`ILLEGAL_ADDR`、`MMU_CTL`、MMUのキャッシュの制御レジスタへの書込みでバスが止まらない。TLBの消去とMMUのキャッシュのフラッシュは、待つビットが時間内に0に戻った |
| `self test: BO at GPU 00090000, entry 30100879 for page 100879000` | BOのページが4GBより上(`0x1_0087_9000`)から取られ、有効と書込み可のビットと物理ページ番号を持つエントリになった |
| `self test: cache clean job ended (0)` | L2Tのキャッシュのクリーンで、待つビット(`TMUWCF`、`L2TFLS`)が0に戻った |

待つビットが0に戻ったことは、そのビットが一度も立たなかった場合と区別できないので、ビットの位置の確認としては弱い。GPUがMMUを通して実際にメモリを読み書きすること、割込みがINTID 281と282に届くこと、MMUのエラーの報告は、まだ確かめていない。これらは次の描画のジョブ(13.8の3)で確かめる。

### 13.8.2 実機の試験(`V3D=2`)

SDカードに書き込む回数を減らすため、`V3D=2`のイメージは、確かめられることを1回の起動でまとめて試す(`device/gpu/v3d/v3d_test.c`)。試験は起動の3秒後に優先度30の専用のタスクで始まり、1件ごとに`v3d test:`で始まる行をコンソールに出力する。どのジョブにも時間の上限があり、終わらないジョブは共通層がGPUをリセットするので、試験が失敗しても次の試験に進み、システムの起動も止まらない。GPUを悪い状態にするおそれのある試験(オーバーフローとMMUの違反)は後に回し、その後にもう一度描画して、GPUが回復したかどうかを確かめる。最後に割込みの回数と、成功した件数と失敗した試験の名前を出力する。

ジョブは、ハードウェアが実行できる最小のフレームである。ビニングのリストは描画を1つも含まず、レンダリングのリストはタイルバッファを1色でクリアする(またはメモリから読み込む)だけで、すべてのタイルをメモリ上のラスタ形式のバッファに書き出す。描画の対象は1つ(RGBA8UI、1ピクセル32bit)で、タイルは64×64である。パケットの並び、タイルとスーパータイルの大きさ、タイルの割当てメモリの大きさは、Mesaのv3dvがバッファを1色で埋めるとき、およびバッファをコピーするときと同じにした。試験はBOを線形マッピング(キャッシュする)を通して読み書きし、キャッシュの操作を明示的に行う。

| 試験 | 内容 | 成功の条件 |
| --- | --- | --- |
| `fill` | 64×64を1色で埋める | ジョブが`E_OK`で終わり、全ピクセルがその色で、バッファの直後の1ページが0のまま |
| `fill uneven` | 100×37(タイルの大きさの倍数でない) | 同上。タイルの端の切り取りを確かめる |
| `fill large` | 1920×1080 | 同上。スーパータイルが複数になる構成を確かめ、所要時間と書込みの速さ(MB/s)を出す |
| `copy` | CPUが書いた256×256のラスタを読み込んで、別のバッファに書き出す | 全ピクセルが一致する |
| `queue of 4` | 64×64のジョブを4つ続けて投入し、最後のフェンスを待つ | 4つとも正しい色で、フェンスの番号が投入の順 |
| `coherence` | コピー元のメモリにはA、CPUのキャッシュにだけBを置き、コピー先のキャッシュラインを読み込んでからコピーする | ジョブが終わり、メモリ上の結果がすべてAかすべてB。GPUがCPUのキャッシュを読んだか(B)、CPUが無効化せずにGPUの書込みを見られたかを出力する |
| `overflow` | 1920×1080で、タイルの割当てメモリを実際より少なく伝える | ジョブが`E_OK`で終わり、全ピクセルが正しい。メモリ不足の割込みの回数を出す |
| `MMU fault` | MMUにないアドレス(`0x8000`)へ書き出す | ジョブが`E_IO`で終わり、違反が報告される。違反の状態、アドレス、クライアント、スクラッチページに届いたワード数を出す |
| `after fault` | 違反の後にもう一度64×64を埋める | `fill`と同じ |
| `interrupts` | ここまでの割込みの回数 | フレーム完了とビニングのフラッシュ完了が1回以上あり、禁止した割込みがない |
| `compose` | ウインドウの合成の確認(13.10.6)。出力は`v3d compose:`で始まる行 | すべての場面がCPUの合成と一致する |

2026年10月の実機の起動で、`compose`より前の10件はすべて通った。`coherence`では、CPUはキャッシュを無効化しないとGPUの書込みのほとんどを古い値で読んだ(new 16、stale 4080)。GPUとCPUの間にコヒーレンシはないので、GPUが読むメモリはジョブの前にクリーンし、GPUが書いたメモリはジョブの後に無効化してから読む。

出力の例を次に示す(数値は例である)。

```text
v3d test: start
v3d test: fill 64x64 ok: job E_OK, 0 of 4096 pixels wrong, 0 written past the end, 180 us, 91 MB/s, first page 100879000
...
v3d test: interrupts: core 22 (frames 11, flushes 11, out of memory 1), hub 1 (MMU faults 1), turned off 0
v3d test: summary 11/11 passed
```

### 13.8.3 OpenGL ESをV3Dで描く(M6)

QEMUにはV3Dがないので、プロセスのOpenGL ESがV3Dで描けるかは実機でしか確かめられない。実機では次の2か所で自分で確かめ、結果をUARTに出し、通らなければsoftpipeに戻る。

1. 起動時(`V3D=2`と`V3D=3`)。`knl_v3d_init`が自己試験の後で`v3d_as_check`(`v3d_test.c`)を呼ぶ。プロセスと同じ作りのアドレス空間を1つ作り、(a)その表の中のBOに64×64のフレームを描いて読み戻す、(b)その表からカーネルのBOのあるアドレスに書くフレームを走らせ、MMUの違反でジョブが失敗し、カーネルのBOが変わらないことを確かめる、(c)カーネルの表に戻ってもう一度描く。3つとも通ったときだけ、プロセスにアドレス空間を与える(`gp_opn_gpu`が成功する)。`V3D=2`の試験の一覧にも「address spaces」として入る。
2. OpenGL ESのプログラムの起動時。EGLのプラットフォームが、v3dドライバの画面を作った後で、GPUで64×64のフレームを消して読み戻す(`ts_gpu_check`)。全画素が合えばv3dで描き、合わなければsoftpipeで描く。

| 行 | 意味 |
| --- | --- |
| `v3d: - address spaces` | 起動時の確認を始めた |
| `v3d: address spaces: a frame in a table of its own ok: job ok, 0 pixels wrong, N us` | (a)。コンテキストの表への切替えとオーバーフローのメモリの設定が働いた |
| `v3d: address spaces: a store to the kernel's BO at XXXXXXXX ok: job E_IO, 1 fault(s), last at XXXXXXXX, 0 words changed` | (b)。違反が割込みで報告され、カーネルのBOは書かれなかった。プロセスの分離の根拠(13.5.1の8)になる行である |
| `v3d: address spaces: a frame in the kernel's table after ok: ...` | (c)。カーネルの表に戻った |
| `v3d: address spaces ok: processes draw on the V3D` | 3つとも通った。`FAIL`なら`processes do not draw on the V3D`で、プロセスはsoftpipeで描く |
| `v3d: - compute dispatch` | コンピュートのディスパッチの確認を始めた(13.3.2の8) |
| `v3d: compute dispatch: 64 of 64 words right in N us; offered (OpenGL ES 3.1)` | 確認の計算シェーダが全ワードを正しく書いた。プロセスのv3dドライバはOpenGL ES 3.1になる |
| `v3d: compute dispatch: word N is XXXXXXXX, not YYYYYYYY` | 違ったワード(4つまで)。続く行は`not offered`で、OpenGL ES 3.0のまま |
| `v3d: compute dispatch: the check's job failed (E)` | ジョブが時間内に終わらなかった、または失敗した。`not offered`と同じ扱い |
| `v3d: the dispatch at the reset: status XXXXXXXX, cfg ...` | 共通層の時間切れでリセットしたとき、走っていたディスパッチの状態と設定 |
| `egl: the V3D (v3d), a frame cleared and read back in N ms` | プログラムの起動時の確認が通り、v3dで描く |
| `egl: the V3D did not draw (理由), softpipe` | 確認が通らず、softpipeで描く。理由は段階の順に「no driver named for the descriptor」(`drmGetVersion`の名前からドライバを決められない)、「the loader of the driver v3d did not take the descriptor (errno N)」(記述子の複製など、Galliumのローダの段階)、「the driver v3d did not make its screen」(v3dドライバがレジスタの値を受け付けないなど。直前に`MESA: error:`の行が出る)、「the frame did not end」「N pixels wrong (...)」(画面はできたが、GPUで消したフレームが合わない)。x64のirisでは、次の行に断ったi915の要求の一覧(`egl: i915 (iris): ...`、13.11.9)が出る |
| `egl: the V3D is not open to this process (no address space), softpipe` | 起動時の確認が通らなかったか、4MBの表を取れなかった |
| `glgears: V3D 7.1...`で始まる行 | 小物「歯車」がv3dで描いている(softpipeなら`glgears: softpipe, ...`)。続く`glgears: N frames in 5.0 seconds = F fps`が速さで、その行の`drawing`と`eglSwapBuffers`の時間と、同じころの`wm: frames:`と`disp: frames:`の行(10.4.5)で、60フレーム毎秒に届かないときにどこで1フレームを越えたかが分かる |
| `v3d: MMU fault ...` | プロセスのジョブが自分の表にないアドレスに触れた。ジョブは`E_IO`で終わり、ほかには影響しない |

`TS_GL_DRIVER=softpipe`を与えればV3Dがあってもsoftpipeで描く(比べるとき)。

最初の実機の試験では、ローダが記述子を複製できず(newlibの`fcntl`が`ENOSYS`を返した)、`MESA-LOADER: failed to retrieve device information`と`egl: failed to create dri2 screen`の後でsoftpipeに戻った。v3dドライバはフレームのフェンスをsync_fileの記述子で持つので、そこを越えても確認のフレームは終わらなかった。どちらも直した(13.6.2)。ローダからv3dドライバの画面までの道筋はQEMUで確かめる。DRMシムに、Raspberry Pi 5のV3Dを模擬するインタフェース(`ts_gl_drm_fake`)を置いた。模擬したV3DはGET_PARAMに実機のレジスタの値(13.8.1)を答え、BOをプロセスのメモリに取り、ジョブは走らせずにすぐ終わったことにする。カーネルの試験の`gl_v3dpath`(`glprog v3dpath`)がこれを使い、プラットフォームがドライバ`v3d`を選び、画面を作り、確認のフレームの提出と待ちまで進むこと(フレームの中身は描かれないので、読み戻しで合わないところで止まる)を確かめる。プラットフォームがどこまで進んだかは`ts_gl_probe_result`で読める。

2026年10月8日の実機では、ブラウザが`egl: the V3D (v3d), a frame cleared and read back in 2 ms`を出し、ページのラスタ化とWebGLがV3Dで動いた(`browser: webgl: WebGL 1 on ANGLE, ANGLE (Broadcom, V3D 7.1.7.0, OpenGL ES 3.0)`)。その後、`memfd_create`の記述子を1024に増やして範囲が0x3c00から0x3fffになり、DRMシムの記述子(当時は0x3e00から)と重なった。`lib/libcxxrt`の`fcntl`はメモリのオブジェクトの範囲を先に調べるので、ローダの記述子の複製が`EBADF`で失敗し、10月11日から後の実機ではどのプログラムも`egl: the V3D did not draw (the loader of the driver v3d did not take the descriptor (errno 9)), softpipe`を出してsoftpipeで描いていた。DRMシムの範囲を0x3400からに移した(13.6.2)。QEMUの`gl_v3dpath`は同じ`lib/libcxxrt`を使うので、この重なりがあると手順4(`TS_GL_PROBE_NOPROBE`)で止まり、失敗する。ブラウザの試験`test_blink_v3dfall`(第14章14.10)は、ブラウザの起動の行`gpufake=`で同じ模擬したV3Dを使い、ブラウザのプログラムでもローダがv3dを選んで画面を作り、確認のフレームが合わずにsoftpipeに戻ること(手順6)と、その後もWebGLとページが描けることを確かめる。

### 13.10.1 ジョブの種類

レンダリングのジョブ(ビニングとレンダリングの制御リスト)で、長方形を描く。コンピュート(CSD)は使わない。理由は次のとおりである。

- ドライバは制御リストのジョブを実機で動かしている(13.8.2の試験が全件通った)。CSDはプロセスのOpenGL ES 3.1のために足したもので(13.3.4)、合成の確認より後で確かめる。
- タイルバッファが画面の読み書きを受け持つ。フレームの各タイルを背景からロードし、ウインドウの段階を順に描き、バックバッファにストアする。重なりの順序はハードウェアが描画の順に保つ。
- フラグメントシェーダは、タイルバッファにあるそのピクセルの背後の値を読める(フレームバッファフェッチ)。混ぜる計算をシェーダの整数演算で行えるので、固定機能のブレンドの丸めに頼らず、CPUと同じ結果になる。ブレンドは使わない。
- ウインドウのピクセルはTMUの汎用のロード(アドレスを指定する32bitの読出し)で読む。V3DのTMUは2次元のテクスチャをラスタ形式のままサンプリングできないが、汎用のロードならウインドウのピクセルバッファをそのまま読める。ウインドウが覆い切るタイルは、タイルバッファへのロードでウインドウのピクセルを直接読む(13.10.5)。
- ぼかし(10.4.1)は、縮小、平滑化、拡大のどの段でも、画素が1つ前の段の数画素だけから決まる。そこで段ごとに1つのジョブとし、その段のレベルの1画素を1つのフラグメントで求める。すべての画素が並列に動き、前の段の結果はTMUの汎用のロードで読み、結果はタイルからメモリにストアするので、TMUでの書込みもコンピュートのジョブも要らない。

### 13.10.2 シェーダ

頂点シェーダは1つで、クリップ空間に変換済みの長方形の頂点を受け取ってそのまま出す。ビューポートは画面の大きさによらず固定で、中心4096、幅の半分4096ピクセルとする。ピクセルの境界pはクリップ空間で(p−4096)/4096になり、2のべき乗で割るので浮動小数点数で正確に表せる。カーネルは浮動小数点のレジスタを使わずにビルドするので、頂点の座標は整数の演算でこの値のビット列を作る。ビューポートとクリッパの設定など浮動小数点数を含むパケットは、固定なのでホストで詰めておく。

フラグメントシェーダは次の10個である。座標は`gl_FragCoord`から整数のピクセル位置を求め、フレームの位置を足して画面の座標にする。

| シェーダ | 内容 | 命令数 |
| --- | --- | --- |
| `piece` | ウインドウの部分(ワークエリアと4本の枠の帯、`cp_blend`)。角の被覆率、色の重ね、背後(またはぼかした背後)との混合 | 154 |
| `shadow` | 影(`cp_shadow`)。影の濃さの計算の平方根は、浮動小数点数の平方根を整数で補正して`isqrt`と一致させる | 168 |
| `halve` | ぼかしの縮小。1つ下のレベルの4×4画素(16ワード)を読む | 127 |
| `smooth3`、`smooth5` | ぼかしの平滑化。最も深いレベルの3×3画素(9ワード)か5×5画素(25ワード)を読む。外側の重みが0なら`smooth3`を使う | 109、253 |
| `double` | ぼかしの拡大。1つ上のレベルの2×2画素(4ワード)を読む | 87 |
| `moving` | 開閉中のウインドウ(`cp_moving`) | 191 |
| `copy` | 不透明で、色を重ねず、角にかからない部分(ワークエリアの大部分)。ウインドウのピクセルを1ワード読んでそのまま書く。起動時の確認の診断にも使う | 32 |
| `fill`、`invert` | 起動時の確認の診断用。パラメータの色、背後の反転 | 16、42 |

ぼかしの3つのシェーダは、CPUの`compose.c`と同じく、チャネルごとの重み付きの和を一度だけ丸める。`halve`と`double`は、1ワードの青と赤を0x00FF00FFのマスクで下位と上位の16ビットに分けたまま同時に足し、緑は別に足す。和は16×255以下なので16ビットの区画からあふれず、丸めて右にずらしたときに上の区画から下りたビットはマスクで落とす。`halve`の重みは定数(1、3、9)、`double`の重みは座標の奇偶で決まる1か3である。`smooth3`、`smooth5`は和が4096×255に達するので、チャネルごとに足し、重みはパラメータで受け取る。どのシェーダも、読むレベルの画素(x, y)を、そのレベルの先頭のアドレスにy×ピッチ+4xを加えた所から読み、読む位置は組み立てる範囲に掛かるそのレベルの画素(パラメータ)に収める。2×2の組の補助のピクセルが読むのもその中である。

どれも4スレッドで、レジスタのスピルはない。V3D 7.1のQPUは1命令で16ピクセルを4サイクルかけて処理するので、16個のQPUが960MHzで動くとき、`piece`は1ピクセルあたり約2.5ns、`copy`は約0.5nsの命令の実行時間になる。`piece`はどのピクセルでもウインドウ、ぼかした背後、角の表の3ワードをTMUで読み、タイルバッファの背後も読むので、画面の大部分を占める不透明な部分を`copy`で描く(13.10.5)。座標を読むアドレスは対象のバッファの中に収めてから使う。2×2の組で描くための補助のピクセル(三角形の外側)が、バッファの外を読まないようにするためである。

シェーダの入力は、ドローごとのパラメータ(32bitのワード、最大32個)と3つのバッファのGPUアドレス(ウインドウのピクセル、ぼかした背後、角の被覆率の表)である。ユニフォームストリームの各ワードは、定数、パラメータの番号、バッファの番号のどれかで、生成したヘッダがワードごとに種類と値を持つ。カーネルはドローごとにこれを埋めてストリームを作る。

### 13.10.3 シェーダの生成

`tools/mesa/shaders.sh`がWSLのホストで次を行う。Mesaはカーネルにリンクせず、カーネルに入るのは生成したヘッダだけである。

1. Mesa 26.2.3のリリースを`~/mesa`に取得して展開する(SHA-256を検査する)。
2. NIRと`src/util`の生成物をMesaのPythonスクリプトで作り、NIR、V3Dのシェーダコンパイラ、QPU、`src/util`をホスト向けの静的ライブラリにする。12並列で約30秒、置き場は約0.6GBである。DRMの模擬のヘッダ(`tools/mesa/shim`)からは、libdrmの宣言(`xf86drm.h`など)だけを作業の場所に写して使う(残りはnewlibの代わりで、ホストのCライブラリと重なるため)。ホスト向けの`compose.c`が呼ぶx64のベクトルのループ(`cps_*`)とタスクの番号は、`tools/mesa/hostshim`が呼ばれない形で持つ。
3. `gen_cp_shaders.c`をリンクして実行する。シェーダをNIRのビルダで書き、GLのドライバがコンパイラに渡す前と同じ準備(入出力の変換、最適化)をして、Raspberry Pi 5のV3D(7.1、ハブのリビジョン7、QPU 16、VPM 64KB)向けに`v3d_compile`でコンパイルする。
4. QPUのコード、ユニフォームの種類と値、シェーダステートレコード(ドローインデックスを持つリビジョン10以降の形と、それより前の形の2つ)とその中のアドレスの位置、頂点属性のレコード、VCMのキャッシュの大きさ、ビニングの前置きのパケット、レンダターゲットのストライド、パラメータの番号、TMUでメモリに書くシェーダの一覧(`CP_FS_TMU_WRITES`)を`device/gpu/v3d/mesa/v3d_cp_shaders.h`に書く。レコードのアドレスの位置は、アドレスだけを変えて2回詰めた差から求め、1ワードに収まることを確かめる。QPUのコードを命令の名前で書き表したものはWORKの`v3d_cp_shaders.dis`に書く。
5. `test`(13.10.4)を実行する。

```sh
tools/mesa/shaders.sh          # build、gen、test
NSCENE=3000 tools/mesa/shaders.sh test
```

カーネルは、ヘッダの対象(バージョン71、リビジョン7以上)と`knl_gpu_ref`の値が合わなければ合成を準備しない。

### 13.10.4 ホストでの確かめ

`test_cp_shaders.c`は、生成に使うのと同じNIRのシェーダを、コンパイルの直前の形のまま解釈して実行する。ALUの演算はNIRの定数畳込みと同じ関数で評価する。パラメータとバッファは試験が与え、タイルバッファからの読出しは8bitの値を半精度浮動小数点数に通した値、書出しは半精度浮動小数点数を通して8bitに戻した値とし、TMUでの書込みはメモリに書く。乱数で作った場面(128×96の画面、1〜3個のウインドウ、透明度、色の重ね、角の丸み、影、1〜16ドットのぼかし、開閉中、画面の一部だけの組立て)を、ホスト向けにビルドした`compose.c`と、シェーダとで組み立て、全ピクセルを比べる。

シェーダの側は`v3d_compose.c`と同じ順序とパラメータでドローをジョブに集め、カーネルと同じ`device/gpu/v3d/v3d_cp_split.h`で、影と部分を長方形に分け、ドローを見える所に切り詰め、スーパータイルを分類し、最初のジョブの空いたスーパータイルをCPUと分ける(13.10.5)。そのうえでジョブをGPUが行うように実行する。描くスーパータイルを背景、バックバッファ、ウインドウのピクセルのどれかからロードし、ドローを順に描き、ストアする。CPUの分担の背景のコピーは全部のジョブの後に行うので、GPUがその範囲を読めば違いになって現れ、書けば誤りとして数える。カーネルが切り替えられる使い方(見える所への切り詰め、必要なスーパータイルだけの描画とCPUの分担、ウインドウのピクセルからのロード)の有無、タイルの大きさ(8、16、32)、スーパータイルの数の上限、1つのジョブのドローとロード元のウインドウの数の上限は、場面ごとに乱数で選ぶ。シェーダの読出しがバッファの外に出た回数、書込みが書いてよい所(T1、T2)の外に出た回数、描かないスーパータイルにドローがかかった回数も数える。

ぼかしを縮小、平滑化、拡大で求めるようにした後の2026年10月2日の時点で、3000場面すべてで、最上位のバイトまで含めて一致し、バッファの外の読出し、書いてよい所の外への書込み、描かないスーパータイルへのドローはなかった。CPUのぼかし自体も、Pythonで2次元のまま書いた同じ定義と、乱数の画像、1〜16ドット、画面の一部の組立てで120通り比べ、すべて一致した。試験の中のCPUの分担を、ぼかしの読む範囲やほかのジョブのフレームを避けずに決めるように壊すと、200場面のうち54場面が違いになることも確かめた。確かめられないのは、V3Dのコンパイラによるコンパイルとハードウェアの動作であり、それは起動時の確認が受け持つ。

### 13.10.5 ジョブの組み立て

GPUで組み立てる範囲(フレーム)は、ウインドウマネージャが`align`(16ピクセル)に合わせた範囲である。左端が64バイトの境界になり、バックバッファと背景のラスタのロードとストアのアドレスが揃う。バックバッファと背景の1行のバイト数も64の倍数でなければならない。

1. メモリ。バックバッファ、背景、ウインドウのピクセルバッファは`knl_vmap`で取った不連続なページなので、ページの物理アドレスを引いて、そのままGPUのMMUに登録する(`knl_gpu_bo_wrap`、13.4.1)。登録は96個まで表に残して使い回す。`lay`に渡すウインドウは64個までなので、バックバッファと背景を合わせても入れ替えは起きない。登録は初めて使う組立てで一度だけ行い、カーネルが`knl_vunmap`でその範囲を手放すと`knl_vunmap_hook`で通知され、次の組立てのときにMMUから外す。ぼかしに使うT1とT2(画面か確認の場面の大きい方のバックバッファの1.5倍の大きさのBO、9.)は、準備のときに取る。
2. リスト。制御リスト、シェーダステートレコード、ユニフォーム、頂点、角の被覆率の表は、起動時に取った1MBの物理的に連続したメモリに組み立てる。先頭の4KBは0のまま残し(半径0の角の表として読ませる)、末尾の8KBは使わない(制御リストの実行器は1KB先まで読む)。シェーダのコードと頂点シェーダのユニフォームは別の32KBのバッファに起動時に置く。
3. 最初のジョブは、フレームの各タイルを背景からロードし、ウインドウを奥から順に描き、バックバッファにストアする。1つのウインドウは、影、ぼかし、5つの部分の順に描く。開閉中のウインドウは1つの長方形である。
4. シェーダの費用は描く長方形のピクセルごとにかかるので、影と部分は仕事のある所だけの長方形に分けて描く(`device/gpu/v3d/v3d_cp_split.h`、ホストの試験と共有)。影は、影の範囲からウインドウの立つ所を除いた上、下、左、右の4つと、丸い角の4つの正方形(ウインドウが一部しか覆わない)の最大8個である。CPUの`cp_shadow`が計算しない所を描かないだけなので、結果は変わらない。不透明で、枠の色(`tint_str`)も重ねる色(`wash_str`、`bar_str`)も重ねない部分は`copy`で描き、角の行のうち角の正方形だけを`piece`で描く(1つの部分で最大7個)。CPUの`lay_piece`が行をコピーする所に当たる。
5. 見える所への切り詰め。ジョブのドローがそろった後、各ドローの長方形から、同じジョブで後に描く`copy`の長方形を除く(`cp_cull`)。`copy`は背後を読まずにすべてのピクセルを書くので、その前に同じピクセルに描いた結果は残らない。手前のウインドウに覆われた奥のウインドウの部分や影は描かない。1つのドローは最大16個の長方形になり、それを超えるドローは元の長方形のまま描く。ドローは長方形ごとに2つの三角形(三角形のリスト)にして、1つのシェーダステートレコードで描く。
6. スーパータイルの分類。ジョブのフレームを、タイル1枚から始めて数が256以下になるまで大きくしたスーパータイルに分け、それぞれを次のどれかにする(`cp_classify`)。どのドローもかからないもの、ドローがかかり、ジョブのロード元(背景かバックバッファ)からロードするもの、ウインドウのピクセルからロードするもの(8.)、CPUが背景をコピーするもの(7.)である。レンダリングの制御リストは、描くスーパータイルの座標だけを並べ、種類ごとに作った汎用タイルリスト(ロードの有無とロード元だけが違う)を、種類が変わる所で切り替える。バックバッファからロードしてバックバッファにストアするジョブでは、どのドローもかからないスーパータイルは描かない。バックバッファがすでにその値だからである。
7. CPUの分担。最初のジョブのスーパータイルのうちどのドローもかからないものは、ほかのジョブが読み書きしない所(ぼかしが読むバックバッファの範囲と、後のジョブのフレームを避ける)に限り、GPUが働いている間にCPUが背景をコピーする(`cp_share`)。CPUとGPUの見積りの時間(1ピクセルあたりの重み`CP_CW_*`、ジョブ1つの固定の時間)を比べ、CPUの分担がGPUより重ければ、分担の後ろから順にGPUに戻す。ウインドウのない画面では、ほぼ半分ずつになる。スーパータイルの境界は64バイトに揃うので、CPUが書くキャッシュラインとGPUが書く範囲は重ならない。
8. ウインドウのピクセルからのロード。スーパータイルのすべてを1つのウインドウの`copy`が書き、それより前のドローがそのスーパータイルにかからない(5.で切り詰められている)とき、そのスーパータイルはウインドウのピクセルバッファからロードし、その`copy`はそのスーパータイルから除く(`cp_cut_bases`)。ロードのアドレスは、フレームの最初のピクセルに当たるウインドウの中の位置(ウインドウの外を指すこともある)で、ハードウェアがタイルの位置を足すとウインドウの中を指す。その値が32bitに収まらないときと、1つのジョブで16個を超えるウインドウからはロードしない。ウインドウの左端は16ピクセルに揃っていないので、このロードのアドレスは4バイトにしか揃わない。
9. 透ける部分をぼかすウインドウでは、それまでのフレームをストアしてジョブを閉じ、ぼかしの段(10.4.1)ごとにジョブを加え、バックバッファからロードする新しいジョブで続ける。深さdのぼかしは、縮小d回、平滑化1回、拡大d回の2d+1個のジョブになる。各ジョブのフレームはそのレベルの座標で表し、透ける部分ごとにそのレベルで求める範囲(`cp_spread_plan`、CPUと同じもの)をドローとし、フレームはそれらを囲む範囲(左端は16ピクセルの倍数に下げる)とする。タイルはロードせず、描いたタイルをそのレベルの置き場所にストアする。置き場所はどれもバックバッファと同じピッチで、レベル1〜3はT1に上から順に重ね(`cp_lv_row`)、平滑化したレベルはT2の画面の行より下に、拡大の最後(レベル0)はT2の画面と同じ位置に置く。拡大の途中のレベルは、もう読まない縮小のときの同じレベルの上に書く。フレームのうちドローの外の画素もストアされるが、そこは後のジョブが読まない所である。最初の縮小(深さ0なら平滑化)が読むバックバッファの範囲は、CPUの分担から外す。1つのジョブのドローは128までで、超えたらジョブを分ける。1つの範囲のドローは2048まで、ジョブは128までで、超えたらその範囲はCPUで組み立てる。
10. バックバッファからロードしてバックバッファにストアするジョブ(最初のジョブより後のもの)のフレームは、ドローがすべて決まってから、ドローの長方形を囲む範囲に縮める(左端は16ピクセルの倍数に下げる)。その外のバックバッファは前のジョブがストアした値のままでよいからである。ドローが1つもなくなったジョブと、描くスーパータイルが1つもないジョブは投入しない。このため、ドローの頂点とユニフォームの中のフレームの位置は、ジョブのフレームが決まってから書く。
11. タイル割当てメモリは画面の大きさのフレームに対して、各タイルの最初のブロック、ビナーが最初に取る8KB、リストが伸びる余裕の2MBを取る。タイルの状態は1タイル256バイトである。
12. CPUのキャッシュ。ジョブの前に、GPUが読むウインドウのピクセルを、各ドローの見える所の長方形とウインドウからロードするスーパータイルの分だけクリーンする(2×2の組の補助のピクセルが隣を読んでも、その値は使われない)。開閉中のウインドウは拡大縮小して読むので全体をクリーンする。リストのメモリもクリーンし、背景は作り直されたとき(ポインタと世代で判定)で、かつ背景からロードするスーパータイルがあるときに一度だけクリーンする。バックバッファのGPUが書く範囲(CPUの分担を除いたスーパータイル)の行は、書き戻さずに無効化する(`dc ivac`。行の端で一部だけ範囲にかかるキャッシュラインは、範囲の外の部分を残すためにクリーンしてから無効化する)。GPUが範囲のすべてのピクセルを書くのでCPUのキャッシュにある値は要らず、書きかけの行が残っていると後で追い出されたときにGPUの結果を上書きするからである。ジョブが組み立てられずにCPUに戻すときは、範囲を背景からすべて組み立て直すので、捨てた値は要らない。ジョブの後で同じ範囲を無効化し、CPUがGPUの書いた値を読むようにする。CPUの分担の範囲はCPUが書くので触らない。ジョブの前と後の操作は、それぞれ全部の行を1続きのキャッシュラインの操作として行い、完了を待つバリア(`dsb sy`)は前後に1回ずつだけ置く。ジョブの間は、ウインドウマネージャのロックにより、CPUはGPUが書く範囲に書かない。
13. GPUのキャッシュ。どのシェーダもTMUで読むだけで書かず、タイルはタイルバッファからメモリに書くので、ジョブの後のTMUのキャッシュのクリーンは求めない。TMUで書くシェーダ(`CP_FS_TMU_WRITES`、今は1つもない)を含むジョブにだけクリーンを求める仕組みは残してある。後のジョブがTMUで読むT1、T2、バックバッファは、ドライバがビニングとレンダリングの前にTMUのキャッシュを無効化するので、前のジョブがストアした値が読まれる。
14. すべてのジョブを続けて投入し、CPUの分担の背景をコピーしてから、最後のフェンスを4秒まで待ち、各フェンスの結果を確かめる。

### 13.10.6 起動時の確認と切り替え

`V3D=2`では実機の試験(13.8.2)の最後に、`V3D=3`では起動の2秒後に優先度30のタスクで、合成の確認(`v3d_compose_check`)を行う。1024×768の画面を想定した背景とウインドウのピクセルを作り、次の場面を、CPUで1つのバックバッファに、GPUでもう1つのバックバッファに組み立てて、全ピクセルを比べる。CPUの段階はウインドウマネージャと共有する作業領域を使うので、場面ごとにウインドウマネージャのロックを取る(`knl_wm_hold`)。場面のメモリは、場面の前にGPUのMMUに登録しておく。使用中のウインドウマネージャのメモリも最初の組立ての後は登録済みなので、場面の時間に登録の時間は入らない。

| 場面 | 確かめること |
| --- | --- |
| `ground`、`ground in a part` | ウインドウなし。背景のCPUとGPUの分担、タイルのロードとストア(全体と一部の範囲) |
| `fill` | 1つの長方形をパラメータの色で塗る。描画が届くか、届いた場所 |
| `copy` | 1つの長方形にウインドウのピクセルをコピーする。TMUでのメモリの読出しと、ウインドウのピクセルからのタイルのロード(アドレスが4バイトにしか揃わない) |
| `invert` | 1つの長方形で背後を反転する。タイルバッファの読出し |
| `one window`、`plain` | 不透明で角も影もないウインドウ1つと2つ。2つでは奥のウインドウの覆われた部分を描かない |
| `washed` | 枠とタイトルバーに色を重ね、プログラムの色を掛ける |
| `see-through` | 枠を透かし、1つはウインドウ全体を透かす |
| `corners` | 角の丸みと影 |
| `spread`、`spread in a part` | 3つの重なったウインドウの背後のぼかし(全体と、端でぼかしが切れる一部の範囲) |
| `opening` | 開く途中のウインドウ |
| `many` | 24個のウインドウ。ドローが1つのジョブに収まらない |

すべての場面で、RGBの各チャネルの差が1以内で、GPUがすべてのウインドウ(ぼかしをGPUで行わない使い方では、最初にぼかすウインドウの手前まで)を重ねたときに確認に通る。計算は同じなので差は0になるはずで、差が1の画素があれば数を報告する。最上位のバイト(画面には出ない)の違いも数えて報告する。

場面は、まず13.10.5のすべての使い方(見える所への切り詰め、必要なスーパータイルだけの描画とCPUの分担、ウインドウのピクセルからのロード、GPUでのぼかし)で組み立てる。違う場面があれば、ウインドウのピクセルからのロードを外して、次にGPUでのぼかしを外して(ロードは戻す)、次に両方を外して、次に切り詰めだけにして、最後にどれも使わない元のジョブで、場面をすべて組み立て直し、最初にすべての場面が一致した使い方を使う。GPUでのぼかしを外した使い方では、ぼかすウインドウがあれば、その手前までをGPUが重ね、そこから後をCPUが重ねる。ウインドウのピクセルからのロードはアドレスが64バイトに揃わず、ぼかしの縮小、平滑化、拡大のシェーダとレベルの置き場所はまだ実機で動かしていないので、実機で確かめていない使い方のうちでこの2つを先に疑う。ジョブが時間切れになって共通層がGPUをリセットしても、次の使い方で確かめ続ける。

確認に通ったら、ウインドウ2つの場面を、64×64、256×256、1024×768の範囲で、CPUとGPUそれぞれ3回組み立てて最短の時間を測る。見た目の効果なしと、効果あり(枠の透過、角、影)の2通りで、64×64と全体の時間を直線で結んでGPUのほうが速くなる画素数を求め、`wants`の閾値にする。全体でもGPUが速くなければ、その場合はGPUを使わない。透けて見える背後をぼかす設定のときは、確認の場面「spread」(画面全体、透過とぼかしのあるウインドウ3つ)でGPUのほうが速かった場合だけGPUを使い、そうでなければ範囲の大きさにかかわらずCPUで組み立てる(`wants`に渡す`CP_FX_BLUR`)。ランで求めていたころのぼかしは、GPUで並列に動く数が少なく、実機ではCPUより遅かった(GPU 15.0ms、CPU 7.1ms)。GPUでのぼかしを外した使い方で通ったときも、ぼかすときはCPUで組み立てる。どちらにしたかは確認の最後の行に`a spread on the GPU`か`a spread on the processor`と出る。各大きさについて、3回のうち最短だったGPUの組立ての時間の内訳(13.10.7)も1行ずつ出す。

2026年10月の最初の実機の計測(CPU 2.4GHz、V3D 960MHz)では、14場面すべてが一致したが、どの大きさでもCPUのほうが速く、合成はCPUのままだった。1024×768で見た目の効果なしの2つのウインドウはGPU 2824µs、CPU 2134µs、64×64はGPU 79µs、CPU 18µs、ぼかしのある3つのウインドウ(10ジョブ)はGPU 14820µs、CPU 6530µsである。コードから見た時間のかかる所は次のとおりで、それぞれ手を入れた。

- どのピクセルも154命令の`piece`で描いていた。命令の実行だけで1ピクセル約2.5nsになり、測った値(重ねたピクセルあたり約3.5ns)に近い。不透明な部分を`copy`(32命令、TMUの読出し1ワード、タイルバッファの読出しなし)で描くようにした。
- 影をウインドウの範囲全体に描き、ウインドウの内側ではシェーダが角の表を読んでから捨てていた。内側を描かないようにした。
- ぼかしの後の新しいジョブが範囲全体をロードしてストアしていた(1024×768で6MBの読み書き)。ドローを囲む範囲に縮めた。
- CPUのキャッシュの操作で、範囲が画面の幅より狭いとき、行ごとに前後2回のバリアを置いていた(256×256では1000回余り)。全体で前後1回にし、ジョブの前のバックバッファはクリーンせずに無効化するようにした。
- ジョブごとに、終わった後にTMUのキャッシュの全体をクリーンして完了をポーリングしていた。合成のジョブでは求めないようにした。

2回目の計測では、見た目の効果なしの1024×768はGPU 2227µs、CPU 1994µs、効果ありはGPU 1954µs、CPU 2914µsで、効果ありでは4096画素以上をGPUで合成するようになった。ぼかしのある場面はGPU 16032µs、CPU 12070µsだった。内訳から次のことが分かった。

- ウインドウのない背景だけの1024×768でも、タイルのロードとストアだけでレンダリングが1064µsかかり、CPUのコピー(934µs)と変わらない。ドローがなくても、タイルの読み書きだけでCPUの合成の時間を使い切る。
- ぼかしのある場面ではレンダリングが12671µsで、TMUの読出しが558万ワードあった。1ピクセルについて半径の2倍+1ワードを、行と列で2回読むためである。
- ぼかしのある場面の`build`が2645µsあった。その場面で初めて使うT1とT2(各3MB)を取り、0で埋めてキャッシュをクリーンする時間と、初めて使うウインドウのピクセルのMMUへの登録の時間で、使用中は一度しか起きない。

これに対して次のようにした(13.10.5)。

- タイルのロードとストアを減らした。どのドローもかからない所は、バックバッファからロードするジョブでは描かず、最初のジョブではGPUが働く間にCPUが背景をコピーする。ウインドウの`copy`が覆い切るスーパータイルは、ウインドウのピクセルからロードし、`copy`を描かない。後の`copy`が書く所には、前のドローを描かない。
- ぼかしをランで求め、TMUの読出しを1ピクセルあたり約2.4ワードにした。
- T1とT2を準備のときに取り、確認の場面のメモリも場面の前にMMUに登録するようにした。

見込みは、背景だけの1024×768ではCPUとGPUでほぼ半分ずつを受け持ってCPUだけのときの3分の2ほど、見た目の効果なしの2つのウインドウではCPUの約半分、ぼかしのある場面ではレンダリングが3分の1以下である。次の実機の起動では、13.10.7の内訳の行の`ground by the processor`、`tiles`の括弧、`left out under copies`、`K TMU reads`で、それぞれが働いているかを確かめる。

3回目の計測では、ぼかしのない場面はどれもGPUがCPUの1.5〜2倍速くなったが、ぼかしのある場面(10ジョブ)はGPU 14956µs、CPU 7096µsで、レンダリングが14.5ms、TMUの読出しが180万ワードだった。ランでは1つのフラグメントが32画素を順に求めるので、同時に動くフラグメントが少なく、読出しの待ちが隠れないことが遅さの元である。そこでぼかしを、縮小、平滑化、拡大の段に分け、どの画素も1つ前の段の数画素(4×4、3×3か5×5、2×2)から独立に求めるものに改めた(10.4.1)。CPUとGPUは同じ整数の計算を行う。段ごとにジョブが1つ要るので、ぼかすウインドウ1つのジョブは、深さdに対して2d+1個と、続きの新しいフレームの1個である。場面`spread`(半径6、深さ2)では、最初のジョブと合わせて19ジョブになる。透ける部分の画素数をNとすると、TMUの読出しは、縮小が16×N/4+16×N/16、平滑化が9×N/16、拡大が4×N/4+4×Nで、合わせて約11Nワードである。ワード数はランのときと同じ程度だが、すべての画素が独立に動くので、読出しの待ちはほかのフラグメントの計算で隠れる。見込みは、ジョブの固定の時間(1つ約25µs、`CP_CW_JOB`)の合計が約0.5ms、レンダリングが数ms以下で、CPUより速くなることである。速くなれば確認の最後の行が`a spread on the GPU`になり、ぼかしのある範囲もGPUで組み立てる。次の実機の起動では、`phases spread`の行の`jobs`、`render`、`K TMU reads`と、`time`の行を見る。

実行中は、システム環境設定の「GPUで合成」(`LK_GPU`、10.4.2、11章)を切るとCPUだけで合成する。GPUのジョブが失敗するか時間切れになったら、その起動の間はGPUを使わず、その旨を一度だけ表示する。リストのメモリが足りないなどでジョブを組み立てられない範囲は、その回だけCPUで組み立てる(「fell back」として数える)。

### 13.10.7 実機のログの読み方

行はすべて`v3d compose:`で始まる。

```text
v3d compose: ready: code 11264 bytes at GPU 00010000, lists 1024 KB at GPU 00030000, tile memory 2944 KB, spread 4612 KB twice, plain records
v3d compose: check start, with cut to what shows, supertiles as needed, tiles from windows, spread on the GPU
v3d compose: check ground, 0 windows in 1024x768 at (0,0): same; 0 of 786432 pixels differ, by 0 at most, top bytes 0; GPU 0 window(s) in 1 job(s) 600 us, processor 930 us
v3d compose: check fill: the colour is in 60000 pixels within (100,60)-(399,259), meant for (100,60)-(399,259)
v3d compose: check fill, 0 windows in 1024x768 at (0,0): same; ...
...
v3d compose: time plain: 64x64 GPU 60 us / processor 20 us, 256x256 ..., 1024x768 1100 / 2000 us (1 / 2 ns a pixel); the GPU from 20000 pixels
v3d compose: time with a look: ...
v3d compose: check passed (14/14) with cut to what shows, supertiles as needed, tiles from windows, spread on the GPU: to the GPU, parts of 20000 pixels and more without a look, 4096 with one (0: never); a spread on the GPU
v3d compose: in 60 s: 40 parts on the GPU (52 jobs, 60 Mpx, 160000 us), 2000 on the processor (3 Mpx, 90000 us); fell back 0, partly 0
v3d compose: whole screen: GPU 12 times, 4100 us each; processor 0 times, 0 us each
```

(数値は例である。)ある使い方で違う場面があれば、`check with 〜: n of 14 scenes the same`の後に、次の使い方の`check start, with 〜`が続く。どの使い方でも違えば`check FAILED`になる。確認に通らなかった場面は、その行が`DIFFERENT`になり、最初の3つの違うピクセル(位置、GPUの値、CPUの値)と、違うピクセルの範囲、そのうち組み立てる前の値のまま残ったもの(ストアされていない)と背景のままのもの(描画されていない)の数が続く。場面の順に、どこがおかしいかを次のように切り分ける。

| 最初に失敗する場面 | 疑うところ |
| --- | --- |
| `ground` | RGBA8のラスタのロードとストア、フレームの位置のアドレス、バックバッファと背景のMMUへの登録、スーパータイルごとの汎用タイルリストの切替え、CPUの分担の範囲とキャッシュの操作 |
| `fill` | 描画が届かない(色の画素数が0)なら、シェーダステートレコード、頂点、ビューポートとクリップウインドウ、ビニング。届いた範囲がずれていれば座標の変換(上下が逆ならY方向) |
| `copy`(`fill`は通る) | TMUの汎用のロード、バッファのアドレスのユニフォーム、ウインドウのピクセルのMMUへの登録とキャッシュのクリーン。ウインドウのピクセルを外した使い方で通れば、揃わないアドレスからのタイルのロード |
| `invert`(`fill`は通る) | タイルバッファの読出し(スコアボードとスレッドの切替えの設定) |
| `one window`以降 | `piece`などの各シェーダ。ホストの確かめ(13.10.4)は通っているので、コンパイラによるコンパイルかハードウェアの違い |
| `spread` | ジョブを分けたときの順序、T1とT2のレベルの置き場所、前のジョブがストアしたレベルをTMUで読むこと、縮小、平滑化、拡大の各シェーダ。GPUでのぼかしを外した使い方で通れば、このどれか |

ほかに、ドライバの`v3d: MMU fault 〜 at 〜 (client 〜)`(MMUの違反のアドレス)と、共通層の`gpu: job of fence 〜 did not end; resetting the GPU`(ジョブが終わらない)が手がかりになる。`check passed`の後は、使用中に60秒ごとに統計の行が出る。1行目は期間中にGPUとCPUで組み立てた範囲の数、ジョブの数、画素数、時間の合計と、GPUを使えずCPUに戻した回数、GPUが一部のウインドウだけを重ねた回数、2行目は画面全体の組立ての1回あたりの時間、3行目はGPUで組み立てた範囲の1回あたりの時間の内訳(`phases of a part on the GPU, on average`、次の形の平均)である。

時間の内訳は、確認の各場面の行の後、閾値を求める各大きさ(`phases time plain 64x64`など)、使用中の統計に、次の形の1行で出る。

```text
v3d compose: phases plain: build 40, caches 150 (rows read 60), hand over 10, ground by the processor 380, to start 15, GPU 750 (ready-bin 5, bin 25, ready-render 5, render 700, clean 0), wake 20, after 70 us; 1 jobs, 113 tiles (69 from windows, 0 left out), 30 draws, 140 Kpx drawn, 120 copied, 330 left out under copies, 150 K TMU reads, 320 Kpx of ground by the processor
```

(数値は例である。)時間はµsで、左から順に起きる。`ground by the processor`は`to start`以降と同時に進む。

| 欄 | 内容 | 大きいときに見るところ |
| --- | --- | --- |
| `build` | ドローとリストを作るCPUの時間。見える所への切り詰めとスーパータイルの分類、初めて使うメモリのMMUへの登録(`wrap_of`)もここに入る | ドローの数。場面の初回だけ大きければ登録 |
| `caches` | ジョブの前のCPUのキャッシュの操作の全体。括弧の`rows read`はそのうちGPUが読む所(ウインドウの見える所と、作り直されたときの背景)のクリーンで、残りはバックバッファのGPUが書く行の無効化とリストのクリーン | キャッシュラインの操作の速さ。1024×768の全体で、バックバッファだけで4万9千回 |
| `hand over` | 共通層へのジョブの投入 | ジョブの数 |
| `ground by the processor` | GPUが働く間にCPUが背景をコピーした時間 | `GPU`より大きければ、分担の重み(`CP_CW_*`)をCPUに重くする |
| `to start` | 最初のジョブの投入から、ドライバがそれを始めるまで | 共通層のタスクへの切替え |
| `GPU` | 最初のジョブの開始から最後のジョブの終わりまで。括弧はドライバが測った各段階のジョブ全体の合計(13.3.4)。`GPU`と括弧の合計の差は、ジョブとジョブの間の共通層の切替え | 下の各段階 |
| `ready-bin`、`ready-render` | ビニング、レンダリングの前のGPUのキャッシュの無効化と完了の待ち | ジョブの数 |
| `bin` | ビニング | ドローと長方形の数 |
| `render` | レンダリング。各タイルのロード、シェーダ、ストア | 描いたタイル、画素数、`piece`と`copy`の割合 |
| `clean` | ジョブの後のGPUのキャッシュのクリーン。TMUでメモリに書くシェーダを含むジョブだけで、今の合成では0になる | |
| `wake` | 最後のジョブの終わり(割込み)から、待っていたタスクが動き出すまで | 割込みから共通層のタスク、待つタスクへの切替え |
| `after` | ジョブの後のバックバッファのGPUが書いた行の無効化 | キャッシュラインの操作の速さ |
| `jobs`、`tiles`、`draws` | 投入したジョブ、全ジョブの描いたタイル(括弧はそのうちウインドウのピクセルからロードしたものと、描かずに飛ばしたもの)、ドローの数 | |
| `Kpx drawn`、`copied`、`left out under copies` | シェーダが描いたピクセル(千)、そのうち`copy`が描いたもの、後の`copy`が書くので描かなかったもの | |
| `K TMU reads` | シェーダがTMUで読んだワード数(千、描いた長方形の面積からの見積り) | |
| `Kpx of ground by the processor` | CPUがコピーした背景のピクセル(千) | |

CPUより遅いときは、`caches`と`after`の合計、`render`、`ground by the processor`、それ以外(`build`、`hand over`、`to start`、`wake`と、ジョブの間)のどれが大きいかで、次に手を入れる所を決める。キャッシュが大きければCPUが書いた範囲を覚えて操作を減らすこと、`render`が大きくて`copied`が小さければシェーダ、ジョブの数あたりの固定の時間が大きければジョブを減らすことになる。`ground by the processor`と`GPU`の差が大きければ、分担の重みを合わせる。

### 13.10.8 未実装のもの

- 描画(`outer_kernel/dp/dp.c`)の大きな塗り、コピー、拡大縮小のGPUへの移行。合成が実機で確かめられてから、同じジョブの仕組み(`fill`、`copy`のシェーダ)で行う。
- ポップアップ、メッセージ行、閉じつつあるウインドウ、独自の外形を持つウインドウのGPUでの合成。今はGPUが重ねた後でCPUが重ねる。
- フレームバッファへの直接の書出し(バックバッファからのコピーの省略)は、調べたうえで行わないことにした。GPUで組み立てた範囲は、ジョブのストアでバックバッファ(キャッシュする通常のメモリ)に直接書かれ、間に別のバッファはない。フレームバッファへの書込みは、画面ドライバが損傷の矩形をバックバッファからコピーする1回だけである。バックバッファは、GPUの後でCPUが重ねるもの(メッセージ行、ポップアップ、閉じつつあるウインドウ、ドラッグ中の枠線、ポインタ)、ぼかしのために広げた縁の保存と復元(`cp_margin_keep`)、バックバッファからロードする後のジョブ、ポインタの下の画素、試験とスクリーンショットが読む元なので、GPUの結果はバックバッファにも要る。フレームバッファにも書くには、GPUに同じタイルを2回ストアさせることになる。背景だけの1024×768ではタイルのロードとストアだけでレンダリングが1064µsかかり(13.10.6)、ストアをもう1回足すとその半分程度が増えると見積もられる。これで省けるCPUのコピーも同じ程度の時間で、合成タスクは両方を順に待つので、1フレームの時間はほとんど変わらない。さらに、ストアした範囲のうちCPUが後で何かを重ねた所を送り直し、残りを損傷の矩形から差し引く管理が要り、ぼかしの縁(組み立て直したが元に戻す所)はタイル単位のストアでは除けない。最上位のバイトを0xFFにする必要のある画面(デバイスツリーのノードの`a8r8g8b8`)ではそもそも直接書けない。2面の切り替え(10.2.1)では、裏の面に前回の矩形もコピーする必要があり、その分はGPUが書いてもCPUのコピーが残る。実機の`disp: flip: whole screen`の行のコピーの時間が、`phases`の行の`render`に比べて大きいと分かったら改めて考える。
- 変化しない部分のリストの再利用、ビニングとレンダリングの並行実行。
- CPUがバックバッファに書いた範囲を覚えて、ジョブの前のキャッシュの無効化をその範囲だけにすること。
- CPUとGPUの背景の分担の重み(`CP_CW_*`)は、これまでの実機の内訳から見積もった値である。実機の`ground by the processor`と`GPU`から合わせ直す。CPUの分担は1つのCPUでコピーしているので、複数のCPUで分けることもできる。
- ウインドウのピクセルからのタイルのロードと、縮小、平滑化、拡大によるぼかしのジョブは、まだ実機で確かめていない。確かめられなければ起動時の確認がその使い方を外す(13.10.6)。

## 13.11 IntelのGPU(x64)

x64のPC(`TARGET=_X64_`)のIntelの内蔵GPU(第9世代。ThinkPad X1 Yoga 第3世代のUHD 620 8086:5917、Surface Go 2のUHD 615 8086:591C)のレンダーとコピー(BLT)のエンジンを、V3Dと同じGPUの共通層(13.4)のバックエンドとして動かす。表示のエンジン(パイプ、プレーン、解像度の変更)は表示の係のドライバで、この節は描画の側である。両者が共有するGGTTの割当てと装置の情報は、どちらにも属さない共有の部品`kernel/sysdepend/x64/igt_ggtt.c`が持つ(分け方は検討書`docs/private/x64_surface_go2_study.md`の5.13と5.14)。QEMUにはIntelのGPUが無いので、ハードウェアの動作は実機の起動時の自己試験で確かめ、ハードウェアに依らない部分はQEMUのカーネル内の試験(13.11.8)で確かめる。

### 13.11.1 ファイル

### 13.11.2 起動の手順

`kernel/sysdepend/x64/devinit.c`の段階「GPU」(画面とウインドウの後)が`knl_igt_init()`を呼ぶ。ここでは装置を見つけて読むだけで、GPUに書く処理は専用のタスク(優先度30)が後で行う。どこまで行うかは起動の設定`cmdline.txt`の`igt=`で決める。

| 指定 | 動作 |
| --- | --- |
| `igt=0` | 何もしない |
| `igt=1` | 装置、リビジョン、GGTTとstolenの大きさを読んで出すだけ。GPUに書かない |
| `igt=2`(今の既定) | 試しの立ち上げ。起動の30秒後に記録のファイル(`KERNEL.TXT`ほか、3.10.7)を書かせてから立ち上げ、段階の区切りごとに記録を書き直させる。GPUで機械が止まっても、どこまで進んだかが残る。続けて自己試験(13.11.5)と合成の確認(13.11.7) |
| `igt=3` | 普段の使い方。起動の2秒後に立ち上げ、合成の確認だけをする |

立ち上げは次の順で、各段階の前に`igt: - 段階の名前`を出す。

1. forcewake。render、GT(blitter)、mediaの3つの領域を取り、立ち上げが終わるまで持つ(13.11.13)。要求はマスクつきのビットで、確認が来ないときは2つ目のビットを切り替えて促す(ハードウェア自身の起床と重なって確認が失われることがあるため)。
2. 電源を切った状態から始める。RC6とパワーゲーティングと周波数の制御を切る(`RC_CONTROL`、`PG_ENABLE`、`RP_CONTROL`を0)。`RP_STATE_CAP`からRP0、RP1、RPnを読み、RP1を求めて、実際の周波数(`RPSTAT1`)を出す。
3. 構成。`FUSE2`と`EU_DISABLE0`からスライス、サブスライス、EUの数を求め、スライスごとのレジスタの読出しを最初にあるサブスライスへ向ける(`MCR_SELECTOR`)。
4. 回避策(13.11.6)、PPAT、PPGTTのスクラッチの表、カーネルのアドレス空間。
5. エンジン(RCSとBCS)。状態のページ(GGTTに置く)、execlistsの有効化(`RING_MODE`の`RUN_LIST_ENABLE`)、割込みのマスク(`RING_IMR`。第9世代では、各エンジンの`RING_IMR`のビットはGTの割込みレジスタ0でのそのエンジンのビットと同じ位置にある。RCSはビット0から、BCSはビット16からで、BCSの下位16bitには何もなく1が読める。以前はBCSにもビット0からの値`fffffef6`を書いていたので、BCSの割込みがすべて止まったままになり、BCSのジョブは1msの見回りでしか終わらなかった(Surface Go 2で`reads ffffffff`)。今はBCSに`fef6ffff`を書く。書いた直後と、各エンジンの最初のコンテキストが走った後に読み返して記録に出す)、コンテキストの状態のバッファ(CSB)のポインタ、MOCS、バッチが書いてよいレジスタ(`FORCE_TO_NONPRIV`)、RCSのエンジンの回避策。
6. 割込み。GPUはMSIだけを持つので、`ts_pcie_msi_plain_alloc`(`pcie.c`にx64だけ足した、MSI-Xでない形のメッセージ)で1つ取る。マスタ(0x44200)のハンドラはGTの割込み(ユーザの割込み、コンテキストの切替え、コマンドの誤り)を処理し、表示の分が立っていれば表示の係が登録した関数(`knl_igt_irq_display`)を呼ぶ。登録が無いまま表示の割込みが100回を超えたら、マスタを戻さずに1msの見回りだけで続ける。割込みとは別に、1msごとの周期ハンドラがジョブの終わりを見る。
7. 各エンジンの最初のコンテキスト。エンジンの状態を読み込まない印(restore inhibit)を立てたコンテキストで、コンテキストの回避策をリングから書き、エンジンが保存したイメージを控える。以後の新しいコンテキストはこのイメージから作る。
8. RC6とRPS(13.11.13)。起動の設定の`igtrc6=0`、`igtrps=0`で切れる。
9. 共通層への登録。続けて範囲の一覧(`igt: GGTT ...`)。ここで立ち上げの分のforcewakeを放し、以後はジョブの間だけ持つ。続けて自己試験、合成の確認。

最後に`igt: ready: render and copy engines, N execution units, interrupts`が出る。立ち上げに失敗したら`igt: the GPU is NOT used (エラー)`で、GPUを使わずに続く(プロセスのOpenGL ESはsoftpipe、合成はCPU)。

GPUはデバイスの実身「gpu0」(`OB_S_GPU`、デバイス箱)になる。レコード1は状態の「キー 値」の行で、`DEVICE`、`REVISION`、`STATE`(starting、running、not used)、`EU`、`RP0_MHZ`〜`RPN_MHZ`、`RPE_MHZ`(効率のよい周波数)、`RC6`と`RPS`(onかoff)、エンジンごとのジョブとリセットの数、`INTERRUPT`(messageかpolled)、`COMPOSE`(render engine、copy engine、processor)を持ち、立ち上げの段階が進むたびに変化を通知する。

### 13.11.3 アドレス空間とGGTT

すべてのジョブはPPGTT(4段のページテーブル、48ビット、4KBのページ)の中で走る。カーネルの空間(合成と試験のBO、32ビットのアドレスをビットマップで割り当てる)と、プロセスのコンテキストごとの空間がある。どの空間も、何も無いエントリは下の段のスクラッチの表を指し、最後はゼロのスクラッチのページに行き着く。範囲の外への書込みはスクラッチのページに行き、止まらない(この世代のエンジンはページフォールトで止まるため)。スクラッチの表はすべての空間で共通で、変えない。ページのエントリはPPATの4番(LLCとeLLCで書き戻し)、表のエントリは0番(LLCで書き戻し)を指す。CPUとGPUはLLCを共有するので、BOのキャッシュの操作は要らない(自己試験の`coherence`で確かめる)。ページテーブルはCPUのキャッシュを通して書き、書いた行を`clflush`で書き戻してからGPUに見せる。

GGTTに置くのは、コンテキストのイメージとリング(1つの連続した領域)、エンジンの状態のページだけで、共有の部品から取る(mappableの外を先に使う)。プロセスのBOもカーネルのBO(合成のバッファを含む)もGGTTに置かない。

プロセスのBOは、プロセスが選んだアドレスに置く(`gp_bnd_bo`、SVCのクラス10の13番、x64だけ)。irisはBOのアドレスを自分で決める(softpin)ので、カーネルはアドレスを割り当てず、i915がexecbufferの一覧のアドレスにBOを置くのと同じく、DRMの模擬がバッチの前に置き直す。アドレスは48ビットで、正規形の上位のビットは捨てる。番号を消すかコンテキストを閉じると表から外す。

置く所が同じコンテキストの別のBOの所と重なるときは、その別のBOを先に丸ごと表から外し、置かれていないものとする。i915がsoftpinで重なるVMAを追い出すのと同じである。irisは使い終えたBOを番号ごと手元に残し(BOのキャッシュ)、別のメモリの区域で使い直すときはそのアドレスを返してから新しいアドレスを付ける(`alloc_bo_from_cache`)。返したアドレスは、前のBOが新しい所に移る前に別のBOに付くことがある。前のBOを移すか消すときに前の所を外すと、そこにある新しいBOのエントリまでスクラッチに戻り、新しいBOはゼロを読み、書込みは捨てられる。DRMの模擬は置いたつもりのままなので置き直さず、エラーにもならない。追い出したときは、最初の8回を`gpu: number 番号 placed at アドレス (Nページ) over number 番号 at アドレス (Nページ), which is taken out of the space (N so far)`の行でコンソールに出す。

### 13.11.4 コンテキストと投入

エンジンごと、アドレス空間ごとに論理リングコンテキスト(LRC)を持つ。イメージ(RCSは22ページ、BCSは2ページ、先頭がコンテキストごとの状態のページ)の後ろに16KBのリングを続けて1つの連続した領域にし、GGTTに写す。1つの空間は16個までのハードウェアコンテキスト(`GPU_HWC_MAX`)を持ち、ジョブ(`GPU_JOB_BATCH`、`T_GPUBATCH`)が番号で選ぶ。i915のGEMコンテキストのエンジンの表の1項目が1つに当たる(13.11.9)。初めて使うときと`GPU_BATCH_FRESH`の印のときは、最初のイメージから作り直す。

1つのジョブのリングのコマンドは次のとおりである(RCS)。

1. コンテキストが入るときの回避策: L3の書き出しとSLMの消去のパイプコントロール、`COMMON_SLICE_CHICKEN2`、`FF_SLICE_CHICKEN`、`3D_CHICKEN3`の書込み(i915が間接のコンテキストのバッチで行うもの)。
2. 頂点のキャッシュの無効化の前の空のパイプコントロールと、TLBと各キャッシュの無効化。
3. `MI_BATCH_BUFFER_START`(PPGTT)。
4. キャッシュの書き出し、状態のページへのシーケンス番号の書込み(GGTTのアドレス、パイプコントロールの書込み)、`MI_USER_INTERRUPT`。

BCSは`MI_FLUSH_DW`(TLBの無効化と、シーケンス番号の書込み)で同じことをする。書いた後、イメージのリングの末尾(`CTX_RING_TAIL`)を書き換え、コンテキストの記述子(イメージのGGTTのアドレス、48ビットのアドレスの形、有効、特権、上位にコンテキストの番号)をELSPの0番の口に書く(1番の口は空)。GuCとHuCは使わない。

ジョブの終わりは、シーケンス番号が書かれ、かつCSBに「動作中から休止へ」の記録が来たときである(イメージの保存が済み、次のジョブがイメージを書き換えてよい)。割込みか1msの見回りが気づき、共通層に終わりを伝える。番号が書かれてから20msたってもCSBの記録が来なければ終わりとみなし、その回数を数える(`without word of idle`)。コマンドの誤りの割込み(`GT_CS_ERROR`)が来たジョブは`E_IO`で終える。

共通層の時間切れ(2秒)では、走っていたエンジンだけをリセットする。リングを止め(`MI_MODE`の`STOP_RING`)、`RESET_CTL`でリセットの準備を求め、`GDRST`のそのエンジンのビット(RENDERかBLT)を2回立てて戻るのを待つ。その後、エンジンを起こし直し(状態のページ、execlists、割込み、CSBのポインタ、MOCS、whitelist、回避策)、走っていたコンテキストを作り直す印を付ける。前後にエンジンのレジスタ(HEAD、TAIL、ACTHD、BBADDR、INSTDONE、IPEHR、EIR、ESR、CSBのポインタ、フォールトのレジスタ)を出す。GDRSTのFULLは使わない(表示を止めない)。

### 13.11.5 起動時の自己試験(`igt=2`)

1回の起動で分かるように、試験は1件ごとに`igt test:`で始まる行を出し、`KERNEL.TXT`に残る。どのジョブにも時間の上限があり、終わらなければ共通層がエンジンをリセットするので、失敗しても次に進む。止まりを起こす試験は後に置き、その後にもう一度書いて回復を確かめる。

| 試験 | 内容 | 成功の条件 |
| --- | --- | --- |
| `store bcs`、`store rcs` | `MI_STORE_DATA_IMM`のバッチで16語をPPGTTのBOに書く | ジョブが`E_OK`、16語が正しく、間の語は書かれない |
| `fill`、`fill uneven`、`fill large` | `XY_COLOR_BLT`で64×64、100×37、1920×1080を塗る(行の長さは幅より長い) | 全画素が色、範囲の外とBOの残りは元のまま。時間とMB/sを出す |
| `copy`、`copy unaligned` | `XY_SRC_COPY_BLT`で256×256、173×61(読む位置と書く位置、行の長さが揃わない) | 全画素が一致し、範囲の外は元のまま |
| `queue of 4 on both engines` | BCSとRCSに交互に4つのジョブを続けて投入し、最後のフェンスを待つ | 4つとも書かれ、フェンスが投入の順 |
| `coherence` | CPUのキャッシュにだけ書いた元をBLTで写し、写し先の行をCPUのキャッシュに持ったまま読み戻す | 全語が新しい値(GPUがCPUのキャッシュを読み、CPUがGPUの書込みを見た)。新しい値、古い値、それ以外の数を出す |
| `spaces` | プロセスと同じ作りの空間で、その空間のBOと、カーネルのBOのアドレスに書くバッチを走らせる | 空間のBOは書かれ、カーネルのBOは1語も変わらない(そのアドレスはスクラッチのページに行く)。プロセスの分離の根拠になる行 |
| `hang bcs`、`hang rcs` | 自分へ飛び続けるバッチ | 約2秒で`E_IO`、エンジンのリセットが1回増える |
| `after hang` | 止まりの後に`store`をもう一度 | `store`と同じ |
| `interrupts` | エンジンごとのジョブ、ユーザの割込み、コンテキストの切替えの割込み、誤り、見回りで終えた数、CSBの記録なしで終えた数、リセット | 割込みを取れたときはBCSのユーザの割込みが1回以上 |

最後に`igt test: summary 通った数/件数`と、失敗した試験の名前が出る。

### 13.11.7 BLTのエンジンでの合成

ウインドウの合成は、まずレンダーのエンジン(13.11.14)で試し、起動時の確認に通ればそれを使う。通らなかったときと`igtrc=0`のときに、次のBLTのエンジンでの合成を使う。

BLTのエンジンは矩形の写しと塗りしかできない(混ぜることも角の被覆率もない)ので、CPUの段階(`compose.c`)がただ写すだけのものを受け持つ。背景と、奥から順に、不透明で(`a_frame`と`a_work`が255)、角が丸くなく、影も色の重ね(wash、tint)もなく、キーの透過も外形も開閉中でもないウインドウである。CPUの`lay_piece`はそのようなウインドウの画素をそのまま写すので、結果はビット単位で同じになる。見た目の効果のあるウインドウに当たったらそこで止め、それまでの数を答える(`T_CPGPU`の`lay`)。残りはCPUがいつもどおり重ねる。

写すものは、まずカーネルのメモリの間の写しの一覧(`igt_cp_plan`、`CP_OP`)として決め、次にそれを、メモリのGPUのアドレスを使った`XY_SRC_COPY_BLT`の並びにしてBCSで実行し、終わるのを待つ。一覧の段階はQEMUの試験(13.11.8の`igt_plan`)がCPUの写しで実行してCPUの段階と突き合わせ、コマンドの段階は実機の起動時の確認が突き合わせる。BLTのエンジンは面を元のアドレス、行の長さ、座標で指すので、元のアドレスを最初の画素のあるページとし、ページの中の位置を座標にする。行の長さは32767バイトまでである。

バックバッファ、背景、ウインドウの画素はカーネルのメモリ(`knl_vmap`など)のままで、初めて使うときにその物理ページをカーネルの空間に写し(`knl_gpu_bo_wrap`、96個まで覚える)、カーネルがその範囲を手放したら(`knl_vunmap_hook`)外す。CPUとGPUはLLCで一貫するのでキャッシュの操作はしない。起動時の確認で違いが出たときだけ、写す前と後に`clflush`をする形でもう一度確かめ、通ればその形で使う。

起動時の確認(`igt compose:`の行)は、1024×768の画面を想定し、次の場面をCPUだけとBLTとCPUの組で別々のバックバッファに組み立て、最上位のバイトまで全画素を比べる。

| 場面 | 確かめること |
| --- | --- |
| `ground`、`ground in a part` | 背景の写し(全体と一部) |
| `one window` | 不透明なウインドウ1つ |
| `two, one past the edge`、`two in a part` | 画面の右と下の外に出るウインドウ、一部の範囲 |
| `past the left and top` | 画面の左と上の外に出るウインドウ |
| `many` | 24個のウインドウ |
| `plain, then a look` | 不透明な2つの後に角と影のあるウインドウ。BLTは2つまで重ね、残りをCPUが重ねる |
| `a look first` | 最初のウインドウに効果がある。BLTは背景だけ |

全部が一致したら、64×64と1024×768の2つのウインドウの場面でBLTとCPUの時間を測り、BLTのほうが速くなる画素数を求めて閾値にする(`wants`)。全体でもCPUのほうが速ければ使わない。レンダーのエンジンの確認(13.11.14)の後で、使うエンジンを決めて`cp_gpu_set`で使い始める(`igt compose: the windows are composited by ...`の行)。結果はデバイスの実身「gpu0」の`COMPOSE`にも出る。ジョブが失敗したら、その起動の間はCPUに戻す。使用中は60秒ごとに`igt compose: in N s:`の統計の行が出る。

### 13.11.9 Mesaのirisとi915の要求

`tools/x64/mesa/build.sh`は、`GALLIUM_DRIVERS`に`iris`を含むとき、irisとIntelのコンパイラ(第9世代以降のもの。第8世代のELKは入れない)を建てる。Intelのドライバの内部のシェーダはOpenCL Cで書かれ、Mesaの`mesa_clc`(LLVMとclangが要る)と`vtn_bindgen2`で作るが、ホストにLLVMを用意せずに済むよう、`tools/x64/mesa/clcstub`の代わりの道具を使う(`-Dmesa-clc=system -Dprecomp-compiler=system`)。代わりの`vtn_bindgen2`は、blorpが使う`blorp_check_in_bounds`(元のOpenCL Cと同じ符号なしの範囲の判定)をNIRの命令で直に書き、使わないもの(間接描画の生成、クエリの写し、Vulkanの関数)は呼ばれたら止まる関数にする。irisが間接描画の生成を使わないよう、パッチ`tools/x64/mesa/patches/iris-no-generation.patch`で閾値の既定を最大にする。`iris-tessronos-port.patch`は、装置のファイルの番号(`major`、`minor`)と`DT_LNK`の無いことに合わせる。2026年10月19日の時点で、1181のソースがすべて翻訳でき、ライブラリは55MBになった。

irisはDRMの要求を`drmIoctl`ではなくCライブラリの`ioctl`で出す(`intel_ioctl`)。そこで`gl_drm_i915.c`が、GPUの記述子の要求を`drmIoctl`に渡す`ts_gpu_fd_ioctl`と、それを呼ぶ弱い名前の`ioctl`を持つ。自分の`ioctl`を持つプログラムは、そこからGPUの記述子の要求を`ts_gpu_fd_ioctl`に回さなければならない。ブラウザ(`port/compat/ts_linux.c`)は、どの記述子にも`ENOTTY`を返す強い名前の`ioctl`を持っていたので、弱い名前の`ioctl`は使われず、irisの要求はすべて`ENOTTY`で断られていた(下の2026年10月23日の実機の例)。irisは記述子を`fstat`して装置を見分けるので、`lib/libcxxrt`の`_fstat`がx64ではGPUの記述子を`ts_gpu_fd_fstat`に回し、DRMのレンダーノードの文字装置(226:128)として答える。名前付きのパイプ(`mkfifoat`、Intelのバッチの計測の道具だけが使う)は無いと答える。記述子は`gp_`のコンテキストで、i915のVM(アドレス空間)1つに当たる。模擬のGPU(`ts_gl_drm_fake(2)`)では、失敗した要求を`i915 (pretended): request 番号 of 大きさ bytes: errno`の行で出す。

2026年10月19日、QEMUの`test_igt_irispath`で、模擬のKaby Lakeに対してローダが`iris`を選び、irisが装置の情報(`GETPARAM`、`QUERY`)を読み、画面とコンテキストを作り、確認のフレームを消すバッチを`EXECBUFFER2`で出して終わりを待つところまで進んだ(194ms)。模擬ではGPUが描かないので、読み戻しで4096画素が合わずにsoftpipeに戻る。失敗した要求は、持たないと答えた`GEM_USERPTR`、知らないパラメータの`GETPARAM`と`CONTEXT_GETPARAM`だけだった。

2026年10月23日、ThinkPad X1 Yoga(第3世代、UHD 620 8086:5917)の実機でブラウザを起動すると、カーネルのGPUの自己テストと合成の確認は通ったのに、`MESA: warning: Kernel 4.1 required to properly query GPU properties.`の後に`egl: the GPU did not draw (the driver iris did not make its screen), softpipe`が出た。Mesaの`intel_device_info_i915_get_info_from_fd`は、`QUERY`の`TOPOLOGY_INFO`が得られず、続く`GETPARAM`の`SLICE_MASK`、`EU_TOTAL`、`SUBSLICE_MASK`も得られないときにこの警告を出す。ローダの段(`drmGetVersion`、`drmGetDevice2`)はDRMシムの関数を直に呼ぶので通り、`intel_ioctl`を通る要求だけが、上に書いたブラウザの`ioctl`で`ENOTTY`になっていた。`GETPARAM`の`HAS_CONTEXT_ISOLATION`も得られないので、`iris_screen_create`は「カーネルが古い」として画面を作らない。`GLPROG.ELF`は自分の`ioctl`を持たないので、`test_igt_irispath`ではこれが見えなかった。ブラウザの`ioctl`が`ts_gpu_fd_ioctl`に回すように直し、`test_blink_v3dfall`をx64でも走らせて、ブラウザのプロセスで模擬のKaby Lakeに対してirisが画面を作る(`driver=iris step=6`)ことを確かめるようにした。

次に同じことが起きたときに原因が分かるように、DRMシムはi915の要求の数と、断った要求の種類(要求の名前、`GETPARAM`と`CONTEXT_GETPARAM`、`CONTEXT_SETPARAM`ではパラメータの番号、`QUERY`では負の長さを答えた項目の番号)ごとの`errno`と回数を覚えておく。あわせて、エンジンごとのバッチの数とバイト数、ジョブがエラー(`E_IO`、エンジンが命令を断ったかリセットされた)で終わっていたのを待ちで見つけた数を数える。待ちはこれまでどおり`E_IO`を終わったものとして扱うので、ドライバには見えない。プラットフォームはirisで描けなかったとき(画面が作れない、確認のフレームが合わない)に、`egl: the GPU did not draw (...)`の次の行にそれを出す(`ts_gl_drm_tell`)。

```text
egl: i915 (iris): 167 requests, batches 6 render 0 copy (5760 bytes), 0 waits found a job ended in an error; 8 refused: QUERY 5 errno 22 (1) GEM_USERPTR errno 19 (1) GETPARAM 1 errno 22 (1) QUERY 7 errno 22 (1) c3 errno 62 (1) GETPARAM 58 errno 19 (1) GETPARAM 54 errno 22 (1) GEM_CONTEXT_GETPARAM 7 errno 22 (1)
```

これは同じ日にQEMUの`test_blink_v3dfall`で、ブラウザのプロセスが模擬のKaby Lakeに対して出したもので、irisは画面を作り、確認のフレームの段まで進んだ(`driver=iris step=6`)。断ったのはどれもirisが無くても進むもの(`QUERY`の`HWCONFIG_BLOB`(5)と`GUC_SUBMISSION_VERSION`(7)、`GEM_USERPTR`、`GETPARAM`の`IRQ_ACTIVE`(1)、`PERF_REVISION`(54)、`PXP_STATUS`(58)、`CONTEXT_GETPARAM`の`SSEU`(7)、`SYNCOBJ_WAIT`(c3)の時間切れ)である。実機でirisの要求がすべて`ENOTTY`(25)で断られると、ここに`GETPARAM`の多くの番号が`errno 25`で並ぶ。`SYNCOBJ_WAIT`の時間切れは、irisがBOの忙しさを待ち時間0の`SYNCOBJ_WAIT`で確かめるためで(`iris_bo_busy_syncobj`)、Linuxのi915も同じく`ETIME`を返す。

DRMシムは、プロセスの最初の24個のバッチを読み、1つ1行でコンソールに出す。描画(`3DPRIMITIVE`)の種類を直前の`3DSTATE_PS`で分けた記号(Dは描画、Cは速いクリア、Pは部分的なresolve、Rは全体のresolve)、Wはコンピュートのウォーカー、`PIPE_CONTROL`(`|`はレンダーターゲットのフラッシュ、`i`はキャッシュの無効化、`s`は待ちだけ)、Lはレジスタの書込み、`>`は別のBOへの続き、をバッチの順に並べ、書いたレジスタを添える。描画ごとに、ピクセルシェーダのバインディングテーブルの0番(レンダーターゲット)と1番(読む面)のSURFACE_STATEから、形式、タイリング、補助の面のモード、アドレス、そこに入っているクリア色の赤を出す。STATE_BASE_ADDRESSはハードウェアのコンテキストに残るので、それを出さない2つ目以降のバッチでは、バインディングテーブルを引けない(`no binding table`)。カーネルは、ジョブがエンジンにエラー(命令の拒否)を起こしたとき、割込みでEIR、IPEHR、IPEIR、INSTDONE、ACTHD、BBADDRを読んでおき、次のジョブを出すときに`igt: rcs: a job ended in an error ...`の行で出す(最初の16回)。

確認のフレームが合わないときは、プラットフォームがさらに1行で、フレームの語の並び(最初の4語、最後の語、異なる語の種類)、100ms後にもう一度読んだ結果、タイリングも圧縮も速いクリアもない線形のフレームでの結果を出す。irisでは、色の圧縮(CCS)と速いクリアを一時的に切って(`INTEL_DEBUG`の`noccs`、`nofc`と同じビット)もう一度確かめた結果も出す。これは原因を絞るための記録だけで、合ってもGPUは使わない。

```text
i915: batch 1 (render, context 0, 1520 bytes, 1 pieces, to the end): 1 draws |iL|iLL|si|iC||; registers 7034 20d8 7004
i915:   draw 1 (C): target format 0c0 tiling 3 aux 5 at fffefff40000 clear 3e808081; source format 000 tiling 0 aux 0 at bffff080 clear 00000000;
```

同じ日の2回目の実機では、irisは画面を作ったが、確認のフレームが合わなかった(`egl: the GPU did not draw (4096 pixels wrong (first row 81 80 80 3e)), softpipe`)。0x3e808081は64/255の浮動小数点数で、クリアの赤0.25を8ビットに丸めた値そのものである。バッチの記録を足してQEMUで模擬のKaby Lakeに対して動かすと、確認のクリアの描画のレンダーターゲットが`format 000`(R32G32B32A32_FLOAT)になっていた。確認は`pipe->clear_render_target`に、自分で作った`pipe_surface`を渡していた。Mesa 26.2.3のirisの`iris_clear_render_target`は、受け取った`pipe_surface`を自分の`struct iris_surface`(先頭が`isl_view`で、`pipe_surface`を含まない)として扱い、ビューの形式を`pipe_surface`の`first_layer`と`last_layer`の位置、つまり0から読む。そのためblorpは、クリア色の浮動小数点数をそのまま1画素16バイトで、フレームの外まで書いていた。GPU、カーネル、DRMシムの答えの違いではない。glClear(ANGLEの道)は`pipe->clear`を通り、irisが`set_framebuffer_state`で作った`iris_surface`を使うので、これに当たらない。確認を`set_framebuffer_state`と`pipe->clear`に替えると、QEMUの記録で、クリアがB8G8R8A8_UNORMのCCS_Eへの速いクリアになった(`format 0c0 tiling 3 aux 5`、上の例)。

2026年10月30日、x64の実機で、起動直後に開いた小物「歯車」は描けたのに、時間が経ってから開くとウインドウの中が黒いままになり、もう一度開くと一瞬だけ歯車が見えてから黒くなった。起動直後はGPUがまだ準備できておらず、`gp_ref_gpu`が失敗してsoftpipeで描いていた(microSDからの起動のログでは`glgears: softpipe, ...`の行が`igt: - forcewake`より前にある)。黒くなるのはirisの道で、確認のフレームは通り、最初の数フレームは描け、その後の描画だけが消えていた。カーネルとirisのソースを突き合わせると、13.11.3の置き直しで、カーネルが前の所を外すときに、その所に後から置かれた別のBOのエントリまでスクラッチに戻していた(`test_igt_place`の新しい場面で、直す前は移したBOの前の所が外れることを確かめた)。irisのBOのキャッシュは数フレームのうちに別の区域で使い直されるので、頂点のバッファ、シェーダ、状態のBOのどれかがゼロのページを読むようになり、クリアだけが残って黒くなる。エラーもリセットも起きないので、これまでのログには出ない。i915と同じく、重なるBOを先に追い出すように直した。実機ではまだ確かめていない。次に実機で歯車を開いたときは、`gpu: number ... over number ...`の行が出て、歯車が描かれ続けることを確かめる。

### 13.11.11 実機で確かめること

1. `igt=2`(既定)のイメージで起動し、`KERNEL.TXT`の`igt:`の行。最初に止まった段階(`igt: - 段階`の最後の行)、forcewakeの確認、RC6を切る前の`RC_CONTROL`、RP0〜RPnと実際の周波数、フューズとEUの数、割込みの番号と前の値、各エンジンの最初のコンテキストの時間と保存したイメージの値、コンテキストの回避策を読み返した値、GGTTの範囲の一覧。
2. `igt test:`の各行と`summary`。失敗したら、その行の値と、リセットの前後のエンジンのレジスタの行。
3. `igt: power:`の行(13.11.13)。立ち上げ前の`RC_CONTROL`、RC6の`RC6_CTX_INFO`、効率のよい周波数とpcodeの答え、リングの周波数の表の書込み、RPSを始めたときの周波数、60秒ごとの状態(RC6にいた割合、パークと起こしの回数、周波数の上げ下げの回数、forcewakeの促しと下りなかった数)。止まりやおかしな動きがあれば、次の起動で`igtrc6=0`か`igtrps=0`で切り分ける。
4. `igt compose:`と`igt rcompose:`の行。BLTとレンダーのエンジンのそれぞれの場面の`same`、長方形とグループの数、時間、どのエンジンで合成するか(13.11.14)。レンダーのエンジンで違いが出たら、次の起動で`igtrc=0`にすればBLTかCPUで合成する。
5. デスクトップの小物「歯車」(`make GL=1`)が`egl: the GPU (iris), ...`を出してGPUで描くか。出なければ、その理由の行と`MESA:`で始まる行。
6. 止まった場合は、次の起動で`igt=1`(読むだけ)か`igt=0`にすれば、GPUに触れずに起動できる。

### 13.11.13 GTの電源(forcewake、RC6、RPS)

`device/gpu/intel/igt_pm.c`が、GTの電源の3つを受け持つ。レジスタの意味はIntelのPRMで、設定の値と手順の順はLinuxのi915(`gt/intel_rc6.c`、`gt/intel_rps.c`、`gt/intel_llc.c`、`gt/intel_gt_pm_irq.c`)で確かめた。コードは写していない。

forcewakeは参照数で持つ。エンジンとGTの電源のレジスタはGTが起きている間しか読み書きできないので、レジスタに触れる処理は`igt_fw_get`で参照を取り、`igt_fw_put`で返す。ジョブは投入の前に取り(`igt_kick`)、終わったとき(割込みか1msの見回り)か、エンジンのリセットで取り上げたときに返す。立ち上げは最初に3つの領域を取ってから終わるまで1つの参照を持つ。参照が0になってから10ms(`IDLE_US`)たつと、1msの見回りの周期ハンドラがGTをパークし、forcewakeの要求を下ろす。GTはそこからRC6で眠れる。次の`igt_fw_get`が3つの領域の要求を上げ(前の確認が下りるのを待ってから)、それがGTをRC6から起こす。確認を待ち、パークを解いてから戻る。確認が下りないまま次の要求になった回数(stuck)と、2つ目のビットで促した回数は数えて記録に出す。

| 段階 | 処理 |
| --- | --- |
| 立ち上げの最初(`igt_pm_init`) | RC6、パワーゲーティング、周波数の制御を切る。`RP_STATE_CAP`からRP0、RP1、RPn(50MHz単位)を読み、内部では3倍の50/3MHz単位で持つ。RP1を求める |
| エンジンの後(`igt_pm_start`) | RC6の設定、RPSの設定、PMの割込みのタスク(優先度12)を作る |
| パーク | RPS: PMの割込みを止め(`PMINTRMSK`、`GT_IER(2)`、`GT_IMR(2)`)、RPnを求める。次に起きたときの周波数を、今より少し低く(下げる向きが続けば倍)するが、効率のよい周波数(RPe)より下にはしない。RC6: `RC6_CTX_INFO`が0ならRC6のコンテキストが壊れたとみなしてRC6を以後切り、forcewakeを放さない。そうでなければ`RC_CONTROL`にRC6の有効だけを書き、`RC_STATE`の目標をRC6(4)にして、手動でRC6に入れる。そのあとforcewakeの要求を下ろす |
| 起こし | RC6: `RC_CONTROL`を0に戻す(忙しい間は自動で入らない)。RPS: パークの前の周波数(RPnとRP0の間に収める)を求め、PMの割込みを有効にする |

RC6の設定は次のとおりである。第9世代では、忙しい間にハードウェアのタイマーでRC6に入ると、RC6が保存するコンテキストが壊れることがある。そのためタイマーによる自動の入りは使わず、パークのときだけ手動で入れる。設定のときとパークのたびに`RC6_CTX_INFO`を見て、0なら破損としてRC6を切る。

| レジスタ | 値 |
| --- | --- |
| `RC6_WAKE_RATE_LIMIT` | 54<<16(Kaby Lake。Skylakeの108ではない) |
| `RC_EVALUATION_INTERVAL`、`RC_IDLE_HYSTERSIS` | 125000、25 |
| 各エンジン(RCS、BCS、VCS、VECS)の`RING_MAX_IDLE` | 10 |
| `GUC_MAX_IDLE_COUNT`、`RC_SLEEP` | 0xA、0 |
| `MEDIA_PG_IDLE_HYSTERESIS`、`RENDER_PG_IDLE_HYSTERESIS` | 250、250 |
| `RC6_THRESHOLD` | 37500 |
| `PG_ENABLE` | レンダーとメディアのパワーゲーティング(Skylake GT3、GT4の回避策の対象外) |
| `RC_CONTROL` | 忙しい間は0、パークでRC6の有効だけ |

RPSは、GTが評価区間ごとに測る忙しさで周波数を上げ下げする。

- 効率のよい周波数(RPe)は、電源の制御装置(pcode)に`DYNAMIC_DUTY_CYCLE`(0x1A)で聞き、答えのビット15:8(50MHz単位)をRPnとRP0の間に収める。答えが無ければRP1とする。
- リング(LLC)の周波数の表を、GTの周波数(50MHz単位)ごとに、リングを同じ値、CPUの周波数の目安を0として、`WRITE_MIN_FREQ_TABLE`(0x8)でpcodeに書く(第9世代の決め方)。
- pcodeへの要求は、表示の係と共有する部品`kernel/sysdepend/x64/igt_pcode.c`の`knl_igt_pcode_rw`だけを通す。
- `RC_VIDEO_FREQ`にRP1、`RP_IDLE_HYSTERSIS`に10を書く。RPnから始める。
- 評価区間と閾値は周波数の高さで3つの段(低、中間、高)を切り替える。上げの区間は16ms、13ms、10ms、下げの区間はどれも32msで、上げの閾値は区間の95%、下げは85%忙しいときとする。値は12MHzの時刻の16刻みの単位である。`RP_CONTROL`はメディアのturbo、通常の動作、GFXの扱い、有効、上げは忙しさの平均、下げはアイドルの平均。
- 割込みは`UP_THRESHOLD`と`DOWN_THRESHOLD`だけを使う(GTの割込みの2番、マスタの0x30)。割込みは`GT_IMR(2)`で止めてタスクを起こし、タスクが段を1つ上げ下げする(同じ向きが続けば段を倍にする)。周波数を書くたびに、`RP_INTERRUPT_LIMITS`(最高と、最低にいるときだけ最低)と、`PMINTRMSK`(動ける向きの割込みだけ通す。ビット31は0)を書き直し、止めた割込みを戻す。メッセージの割込みが無いときと止めたときは、1msの見回りが`GT_IIR(2)`を読む。

起動の設定(`cmdline.txt`)で切れる。実機で問題が出たときの切り分け用である。

| 指定 | 動作 |
| --- | --- |
| `igtrc6=0` | RC6とパワーゲーティングを使わない。forcewakeを放さない(これまでと同じ) |
| `igtrps=0` | RPSを使わない。RP1に固定し、pcodeにも聞かない |

`KERNEL.TXT`には、各段階で次の行が出る。

| 行 | 内容 |
| --- | --- |
| `igt: power: as found: RC_CONTROL ..., RC_STATE ..., PG_ENABLE ...; both off now; RP0 ... RP1 ... RPn ...` | 立ち上げ前の状態、周波数の範囲、RP1を求めた後の実際の周波数 |
| `igt: power: RC6 asked for, RPS asked for (...)` | 起動の設定 |
| `igt: power: RC6 set up (RC6_CTX_INFO ..., in RC6 so far ... ms); ...`か`RC6 NOT used: ...` | RC6の設定と、壊れていたときの断り |
| `igt: power: efficient frequency ... MHz (pcode ..., ...)` | RPeとpcodeの答え |
| `igt: power: the ring's frequency table: N entries written, M refused` | リングの周波数の表 |
| `igt: power: RPS on: asked ... MHz, running at ... MHz (RPSTAT1 ...), RP_CONTROL ..., PMINTRMSK ..., GT IER/IMR 2 ...` | RPSを始めたときのレジスタ |
| `igt: power: RC6 on, RPS on, busy, asked ... MHz (RPn ..., RPe ..., RP1 ..., RP0 ...); parked N times, woken N, steps up N down N; N jobs, in RC6 N% of the last N s, N PM interrupts, N forcewake kicks, N stuck` | GPUが動いている間、60秒ごと |
| `igt: power: the context RC6 saved was found corrupted (RC6_CTX_INFO 0): RC6 off from now on, ...` | パークで破損に気づいたとき |

QEMUの試験`test_igt_pm`(13.11.8)が、メモリをレジスタに見立ててこの流れを確かめる。

### 13.11.14 レンダーのエンジンでの合成

ウインドウの角、影、半透明、色の重ね、ぼかし、開閉中の拡大と縮小を、CPU(`compose.c`)の代わりにレンダーのエンジンで計算する。BLTのエンジン(13.11.7)と同じく`T_CPGPU`のバックエンドで、組み立てた画面はCPUのものとビット単位で一致し、起動時の確認で一致を確かめたときだけ使う。

#### 作り方の決め方

irisで描く形と、カーネルの固定のシェーダで描く形を比べ、V3D(13.10)と同じ後者にした。

| 比べる点 | irisで描く形 | カーネルの固定のシェーダ(採用) |
| --- | --- | --- |
| 合成のある所 | 合成はカーネルのウインドウマネージャの中にあり、バックバッファ、背景、ウインドウのピクセルはカーネルのメモリである。irisはプロセスで動くライブラリ(Cライブラリ、スレッド、DRMの模擬の上、55MB)で、カーネルには結べない。合成をプロセスに移し、毎回の場面とバッファを渡して終わりを待つ形になり、遅れが増え、そのプロセスが止まると画面が止まる | カーネルが直にバッチを作って投入する。V3Dの合成と同じ流れで、失敗したらその起動の間はCPUに戻せる |
| CPUとの一致 | GLSLとirisの丸め、ブレンドの固定機能に頼ることになり、一致を確かめる手段を別に作る必要がある | 段階の計算はV3Dと同じNIR(`tools/mesa/cp_stages.h`)で、CPUと同じ整数の計算。ホストでNIRのまま解釈して`compose.c`と突き合わせる仕組みもV3Dと同じ形にできる |
| 生成物 | 実行時にGLSLを翻訳する | ホストでMesaのIntelのコンパイラ(brw)に翻訳させたコードをヘッダにして入れる。カーネルにMesaは入らない |

パイプラインは、3Dでなく、レンダーのエンジンのGPGPU(計算)のパイプラインにした。V3Dではタイルバッファが背後の画素を保ち、フラグメントシェーダがそれを読めるが、IntelのGPUで背後を読むにはレンダーターゲットの読出しのメッセージと、3Dの固定機能の状態(頂点、セットアップ、ピクセルシェーダ、URB、ブレンド、深度)を一式組む必要がある。計算シェーダなら背後をメモリから直に読み書きでき、組む状態は`STATE_BASE_ADDRESS`、`MEDIA_VFE_STATE`、インタフェース記述子、プッシュ定数だけで、irisの計算のディスパッチと同じ命令の並びになる。

#### シェーダ

`tools/mesa/cp_stages.h`の10個のフラグメントシェーダ(13.10.2)を、`tools/x64/mesa/gen_igt_shaders.c`が計算シェーダにしてから翻訳する。V3Dの生成器とこのファイルを共有するために、シェーダの計算を`gen_cp_shaders.c`から`cp_stages.h`に移した。移した後もV3Dの生成物(`v3d_cp_shaders.h`)は1バイトも変わらず、V3Dのホストの試験(13.10.4)も200場面で一致したことを確かめた。

| フラグメントシェーダの形 | 計算シェーダの形 |
| --- | --- |
| `gl_FragCoord`とフレームの位置から画素を求める | スレッドグループ(1行の16画素)とその中の位置から、長方形の左端を16に切り下げた所を起点に画素を求める。長方形の左右の外の位置は何も書かない |
| タイルバッファから背後を読む | 書き先(バックバッファかぼかしのレベル)のメモリから読む |
| タイルバッファに書く。フラグメントを捨てる(`discard`)と書かない | 書き先のメモリに書く。捨てる代わりに印を立て、印が無いときだけ書く |
| ユニフォームのパラメータ | プッシュ定数(CURBE)の64ワード。0〜31がV3Dと同じパラメータ(フレームの位置は0)、32〜33が書き先のアドレス、34が行の長さ、35〜38が長方形、40〜45が3つのバッファのアドレス |
| バッファの番号と位置で読む | 64ビットのアドレスで読む(A64のuntypedの読出しと書込み) |

翻訳はKaby Lake GT2(8086:5917)向けで、第9世代のどの部品にも同じコードを使う。SIMD16だけで、スクラッチ、共有メモリ、バリア、スレッドごとのプッシュ定数、コードの後ろの定数データは無いこと、プッシュ定数が8レジスタであることを生成器が確かめ、外れたら止まる。

| シェーダ | バイト数 |
| --- | --- |
| `piece`、`shadow` | 3104、2400 |
| `halve`、`smooth3`、`smooth5`、`double` | 3616、3072、6736、1920 |
| `moving` | 3456 |
| `fill`、`copy`、`invert` | 480、816、752 |

コードは合わせて26688バイトで、各シェーダを64バイトの境界に置き、最後に128バイトの0を付ける。

#### 生成(`tools/x64/mesa/igt_shaders.sh`)

1. `build`。x64のMesaの建て(`tools/x64/mesa/build.sh`の`~/tsmesa-x64/build`)の`compile_commands.json`から、NIR、`src/util`、`src/c11`、Intelのコンパイラ(brw)と装置の情報と`src/intel/mda`、islを、`tools/x64/mesa/hostcc.py`がホストのgcc、g++で翻訳し直して静的ライブラリにする。TessronOSのプロセス向けの指定(`include/tscxx`、`include/tsposix`、DRMの模擬のヘッダ)は外し、libdrmの宣言だけを置いた場所に替える。同じ建ての生成物(NIRの表、Intelの命令の表、genxml)をそのまま使う。C23の`enum`の型の指定を使う新しいバックエンド(`jay`)はホストのgcc 11で翻訳できず、第9世代では使わないので入れない。`MESA_DEBUG=1`ではMesaの`assert`とシェーダの検証を入れて`-O0`で建てる(作業の場所を分ける)。
2. `gen`。`gen_igt_shaders`を走らせ、`device/gpu/intel/mesa/igt_cp_shaders.h`を書く。`INTEL_DEBUG=cs`でコンパイラが出す逆アセンブルとその検証を作業の場所の`igt_cp_shaders.dis`に残し、検証の誤り(ハードウェアが受け付けない命令)があればヘッダを書き換えずに止まる。
3. `test`。次の項のホストの確かめ。

生成器には、Mesaの検査を入れた建てで見つかったことを2つ直してある。パラメータの読出しは、brwがプッシュ定数として受け付ける`load_push_data_intel`にする(`load_uniform`のままでは検査を入れない建てで誤ったコードになり、スレッドの終わりの送信が決まったレジスタを使わなかった)。`STATE_BASE_ADDRESS`のMOCSは0にできないので、欄の位置を調べるときも入れる。直した後は、検査を入れた建てと入れない建ての生成物が1バイトも違わない。

ヘッダの中身は、パラメータの番号(V3Dと同じ名前、v3d_cp_split.hがそのまま使える)とプッシュ定数の番号、`IGT_CP_WANT_CODE`を定義したときだけ、コード、シェーダごとのインタフェース記述子(コードの位置、プッシュ定数のレジスタ数、1スレッドのグループ)、コマンドの雛形である。雛形はMesaのgenxmlの第9世代の詰め込みで作り、カーネルが埋める欄は、値を0と最大にして2回詰めた差から語と位置とマスクを求めて書く(アドレスは0と48ビットの値で求め、下位と上位の2語に収まることを確かめる)。

| 雛形 | 内容 | カーネルが埋める欄 |
| --- | --- | --- |
| `sync_flush` | パイプの終わりの同期。RT、深度、データのキャッシュの書出し、コマンドストリーマの停止、即値の書込み | 書込みのアドレス |
| `invalidate` | 読むだけのキャッシュ(テクスチャ、定数、状態、命令)の無効化と停止 | なし |
| `barrier` | グループの境。データのキャッシュの書出しとコマンドストリーマの停止 | なし |
| `cc_pointers`、`select_gpgpu` | GPGPUに切り替える前のカラー計算の状態のポインタの消去(第9世代の回避策)、`PIPELINE_SELECT`(GPGPU) | なし |
| `base` | `STATE_BASE_ADDRESS`。MOCSは書き戻し(2番)、大きさは最大 | 面、動的な状態、命令、bindlessの各基点 |
| `vfe` | `MEDIA_VFE_STATE`。URBの項目2つ、CURBEは8レジスタ、ゲートウェイのタイマーのリセット | スレッドの最大数 |
| `idl`、`curbe` | `MEDIA_INTERFACE_DESCRIPTOR_LOAD`、`MEDIA_CURBE_LOAD` | 長さと動的な状態からの位置 |
| `walker`、`msf` | `GPGPU_WALKER`(SIMD16、グループは1スレッド、奥行1、マスクはすべて)、`MEDIA_STATE_FLUSH` | インタフェース記述子の番号、グループの横と縦の数 |

#### ホストでの確かめ(`test_igt_shaders.c`)

V3Dの`test_cp_shaders.c`と同じ考え方で、生成に使うのと同じ計算シェーダ(brwに渡す直前のNIR)を解釈して実行する。起動ごとに、スレッドグループ、グループの中の位置、プッシュ定数、64ビットのアドレスのメモリを与える。試験のバッファは4GBより上のアドレスに置き、アドレスの上位の半分の計算も確かめる。乱数の場面(150×100の画面、行の長さは画面より64バイト長い、0〜3個のウインドウ、透明度、色の重ね、角の丸み、影、1〜16ドットのぼかし、開閉中、画面の一部だけの組立て)を、ホスト向けにビルドした`compose.c`と、カーネルと同じ計画(`device/gpu/intel/igt_rplan.c`をホストの型で翻訳したもの)で組み立て、最上位のバイトまで全画素を比べる。

GPUでは、1つのグループ(バリアのある長方形から次のバリアの前まで)の長方形は、どの順序でも、同時にも動きうる。試験では、グループの中の読出しはグループの始めの時点のメモリを見るようにし、同じ語にグループの中で違う値を2回書いたら誤りとして数える。計画が頼んでいない順序に頼っていれば違いになって現れる。読出しがバッファの外に出た回数と、書込みが自分の長方形の自分の画素の外に出た回数も数える。

2026年10月19日の時点で、400場面すべてで最上位のバイトまで一致し、バッファの外の読出し、外への書込み、グループの中の食い違う書込みはなかった(3331個の長方形、1323のグループ)。計画からぼかしの段の境のバリアを抜くと、40場面のうち6場面が違いになり、グループの中の食い違う書込みも2659回数えられることを確かめた。確かめられないのは、brwによる翻訳とハードウェアの動作で、それは起動時の確認が受け持つ。

#### 計画(`igt_rplan.c`)

部分を、計算シェーダを走らせる長方形の並びにする。

1. 背景。背景のメモリから部分全体に`copy`。
2. 奥から順に各ウインドウ。影はウインドウの周りと丸い角の長方形に`shadow`(`v3d_cp_split.h`の`cp_split_shadow`)。ぼかしがあれば、部分ごとに、縮小(`halve`)をレベルごとにT1へ、最も深いレベルの平滑化(`smooth3`か`smooth5`)をT2の画面の行の下へ、拡大(`double`)をT1へ戻し、最後をT2へ(`compose.c`の`cp_spread_plan`)。最後に部分を背後と混ぜ(`piece`)、不透明で色を重ねない部分はピクセルをそのまま写す(`copy`、`cp_split_piece`)。開閉中のウインドウは`moving`の長方形1つ。外形を持つウインドウ、キーの透過、ピクセルをGPUの空間に写せないウインドウ、ぼかしのレベルの置き場が無いときのぼかすウインドウに当たったらそこで止め、それまでの数を答える。残りはCPUが重ねる。

1つの段階(影、ぼかしの1段、部分)の長方形は互いに重ならず、どれも自分の画素の背後と、前の段階が書き終えたものしか読まないので、各段階の最初の長方形にだけバリアを付ける。パラメータはV3Dの`v3d_compose.c`と同じで、フレームの位置を0にする。長方形は1つの部分で2048個まで(`IGT_RD_MAX`)で、越えたらその部分はCPUで組み立てる。

#### バッチとメモリ(`igt_rcompose.c`)

バッチは、パイプの終わりの同期、読むだけのキャッシュの無効化、カラー計算の状態のポインタの消去、`PIPELINE_SELECT`(GPGPU)、同期、`STATE_BASE_ADDRESS`、無効化、`MEDIA_VFE_STATE`、全シェーダのインタフェース記述子の読込みで始まり、長方形ごとに(グループの始めならバリア、)そのプッシュ定数の読込み、`GPGPU_WALKER`、`MEDIA_STATE_FLUSH`を並べ、最後に同期と`MI_BATCH_BUFFER_END`を置く。1つの部分が1つのジョブで、カーネルの空間のRCSのハードウェアコンテキストに投入し、終わりを待つ。スレッドの最大数は、フューズに残ったサブスライスの数×56とする。

| メモリ | 内容 |
| --- | --- |
| コード(26688バイト) | 起動時に1回写す。命令の基点 |
| 動的な状態(576KB) | 0からインタフェース記述子、512に同期の書込み先、1024から角の被覆率の表(半径1〜32)、64KBから長方形ごとのプッシュ定数(256バイト) |
| バッチ(256KB) | 部分ごとに作る |
| T1、T2 | ぼかしのレベル。V3Dと同じ並び(`cp_spread_bytes`)で、使うときに取る |

コード、動的な状態、バッチはカーネルのメモリ(`knl_vmap`)をGPUの空間に写したもので、CPUが書いた後に`clflush`する(コマンドストリーマと固定機能はCPUのキャッシュを見ないことがあるため)。バックバッファ、背景、ウインドウのピクセルはBLTのエンジンと同じ写しの表(`igt_cp_wrap`)で写す。BLTの確認がキャッシュの書出しを要した場合は、ここでも部分の前後に同じ書出しをする。

#### 起動時の確認と切り替え

BLTのエンジンの確認の後で、`igt rcompose:`の行を出して準備し、次の場面をCPUとレンダーのエンジンでそれぞれのバックバッファに組み立てて全画素を比べる。行は`igt compose: check r ...`で、長方形とグループの数も出す。

| 場面 | 確かめること |
| --- | --- |
| `r ground`、`r ground in a part` | 背景の写し(全体と、16に揃わない一部) |
| `r one window`、`r plain` | 不透明で四角いウインドウ(`copy`) |
| `r washed` | 枠の色の重ね(`piece`) |
| `r see-through` | 半透明の枠とワークエリア |
| `r corners` | 丸い角と影 |
| `r spread`、`r spread in a part` | 3つの重なったウインドウのぼかし(縮小、平滑化、拡大) |
| `r opening` | 開きかけのウインドウ(`moving`) |
| `r many` | 16個のウインドウ。ぼかし、角、影の混ざったもの |

全部が一致したら、効果の無い2つのウインドウと、角、影、ぼかしのある2つのウインドウで、64×64と1024×768の時間をCPUと比べ、それぞれでレンダーのエンジンのほうが速くなる画素数を閾値にする(`wants`は見た目の効果やぼかしのある部分に後者を使う)。レンダーのエンジンが確認に通り、どちらかの閾値があればレンダーのエンジンで、無ければBLTのエンジン(確認に通り、速いとき)、どちらでもなければCPUで合成する(`igt compose: the windows are composited by ...`)。起動の設定`igtrc=0`でレンダーのエンジンを試さない。ジョブが失敗したら、その起動の間はCPUに戻す。結果はデバイスの実身「gpu0」の`COMPOSE`にも出る。

QEMUの試験では、`test_igt_rcmd`が長方形のコマンドを、`test_igt_rplan`が計画を確かめる(13.11.8)。

### 13.11.15 irisのための同期オブジェクトの待ちと時刻の読出し

DRMの模擬(`lib/libgl/gl_drm_i915.c`)の`SYNCOBJ_WAIT`と`SYNCOBJ_TIMELINE_WAIT`は、Linuxの意味で待つ。

- フェンスがまだ付いていない(何も投入されていない)同期オブジェクトは、`WAIT_FOR_SUBMIT`(タイムラインでは`WAIT_AVAILABLE`も)が無ければ`EINVAL`、あればジョブが付くまで1msごとに見直して待つ。
- `WAIT_ALL`が無ければ、知らされたものが1つでもあれば終わり、その番号を`first_signaled`に答える。あればすべてを待つ。
- 投入済みのフェンスは、ジョブが1つずつ順に走るので、最も早いものを待つ。失敗したジョブのフェンスも終わったものとみなす(Linuxでも待ちはフェンスの誤りを返さない)。
- 期限(単調な時計の絶対時刻)が過ぎれば`ETIME`。

`REG_READ`は、i915がこの世代に許すレジスタ、レンダーのエンジンの時刻(`RING_TIMESTAMP`、0x2358、64ビット)だけに答える。i915と同じく、2つの半分を読む印(`I915_REG_READ_8B_WA`、位置の下位ビット)の有無のどちらも受け付け、ほかの位置と印は`EINVAL`にする。値は、記述子ごとに作る専用の空間(`gp_opn_gpu`)のバッチが、レンダーのエンジン自身に`MI_STORE_REGISTER_MEM`で書かせて読む。上位の半分を下位の前と後に読み、両方の上位が一致すればその組、違えば後の組を使う(下位があふれる間に読んだ場合)。専用の空間を使うので、irisが自分で決めるBOのアドレスには触れず、カーネルの共通のファイルも変えない。模擬のGPUでは単調な時計を12MHzの刻みにして答える。

QEMUの試験`test_igt_i915sync`(13.11.8)が、模擬のKaby Lakeに対してこれらを確かめる。
