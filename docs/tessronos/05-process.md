# 第5章　プロセスとシステムコール

## 5.1 プロセス

プロセスは固有のアドレス空間と、その中で動く1つ以上のタスクからなる。タスクはすべて保護レベル3(EL0)で実行される。

プロセスはELF64のプログラムから生成する。プログラムは`0x400000`にリンクした静的なELFで、パスで指定する(`ts_cre_prc`)か、実身とそのレコードで指定する(`ts_cre_prc_obj`)。TessronOSでは、プログラム実身のレコード1に実行ファイルを格納するのが標準の形で、仮身を開くとデスクトップがこれを使ってプロセスを起動する(第11章)。

| システムコール | 機能 |
| --- | --- |
| `ts_cre_prc`、`ts_cre_prc_obj` | プログラムをロードし、メインタスクを生成して実行する。起動時の引数を渡せる |
| `ts_get_arg` | 起動時の引数を受け取る |
| `ts_ext_prc` | 自プロセスを終了する |
| `ts_ter_prc` | 別のプロセスを強制終了する |
| `ts_wai_prc` | プロセスの終了を待ち、後処理をする |
| `ts_ref_prc`、`ts_get_pid` | プロセスの状態とプロセスIDを取得する |

プロセスは同時に32000個まで生成できる(`CNF_MAX_PRC`)。実際にはその前にメモリが不足する。プロセスにはタスクごとに64KBのシステムスタックとユーザスタック、アドレス空間のページテーブル、プログラムイメージが必要なので、何もしない小さなプログラムでもおよそ200KBを使う。メモリ2GBのマシンでは数千のプロセスが同時に動く。プロセスIDは1から32767までを順に使い、一巡したら空いている番号を再利用する(`CNF_PID_MAX`)。

起動時、呼出し元はプロセスの優先度と、渡す引数を指定する。優先度を指定しなければ`CNF_PRC_PRI`(20)である。プロセスは自分より高い優先度の子を起動できず、実時間の層(1〜15)で子を起動できるのは管理者とシステムのプロセスだけである(4.3.1)。メインタスクはプログラムのエントリ`_start`から実行を始め、`main`を呼ぶ。`main`から戻るか、いずれかのタスクが`ts_ext_prc`を呼ぶと、プロセス全体が終了する。

プログラムのロードでは、新しいアドレス空間を作り、ELFの`PT_LOAD`セグメントをそこへ読み込み、起動時の引数のページを置く。ここまでは、プロセスの表を守るロック(`proc.c`の`prc_mtxid`)を持たずに行う。このロックはプロセスの生成、終了、メモリの範囲の変更などで取られるので、読込みの間これを持っていると、100MBを超えるプログラムを読む数秒のあいだ、ほかのプロセスの生成や終了が止まる。システムコールの入口と出口ではこのロックを取らない(5.6.1)。読み終えてから、ロックの中でプロセスIDと制御ブロックを割り当て、空間を制御ブロックに渡してメインタスクを生成する。それまで新しい空間はどこからも見えない。プロセスの数が上限に達しているときは、読む前に`E_LIMIT`を返す。

実行ファイルは1280KBずつ(SDカードの1回の要求のサイズ、7.3。以前は256KB)カーネルのバッファに読み、そこからアドレス空間のページへコピーする。ページは物理的に連続していないので、直接は読み込めない。1ページずつ読むと4KBごとに実身とレコードを探し直すことになり、118MBのブラウザのロードにQEMUで8〜12秒かかっていた。256KBずつ読むと約1.4秒である。

各`PT_LOAD`セグメントのページは、最初から最終の属性(実行できるものは読出しと実行、書き込めるものは読み書き、ほかは読出しのみ)でマッピングしてから中身をコピーする。コピーはカーネルのリニアマッピングを通して書き、プロセスのマッピングを通さないので、ページを書き込める属性にしておく必要はなく、書込みと実行を同時に許すページはこの間も無い。まだどのプロセッサも使っていない空間に初めてマッピングするのでTLBの無効化は要らない。以前は書き込める属性でマッピングし、コピーの後で属性を変えていた。その変更はページごとに`tlbi vaale1is`で全プロセッサのTLBを無効にするので、GL=1のブラウザ(約190MB)ではQEMUで約3.4秒かかり、その間すべてのプロセッサが止まっていた。いまのブラウザの起動は約3.1秒で、その内訳は読込みが約2.7秒(うちデバイスの読出しが約1500回で約2.3秒)、ページの割当てとマッピングが約0.3秒、コピーが約0.1秒である。

実身のレコードから起動したプログラムは、そのプロセスが動いている間、カーネルがイメージとして持ち続け、同じプログラムの次のプロセスはプログラムを読み直さない(`elf.c`の「shared images」)。最初のロードは読出し専用のセグメント(コードと読出し専用のデータ)のページを、ページテーブルのソフトウェアのビット`PTE_SW_SHARED`(ビット55)を付けてマッピングし、そのページをイメージのものとして記録する。書込みのできるセグメントは、プログラムが動き出す前に、ファイルの中身のあるページだけをイメージにコピーしておく。同じボリューム、同じ実身、同じレコードで、ELFヘッダとプログラムヘッダのバイト列が同じロードは、ヘッダだけを読み、読出し専用のページはイメージのページをそのままマッピングし、書込みのできるページはイメージからコピーする(物理アドレスの連続するページはまとめてマッピングする)。`PTE_SW_SHARED`の付いたページは空間のものではないので、空間を破棄するとき(`free_level`)も、カーネルが不正なアドレスの代わりに空のページを置くとき(`knl_space_sink`)も解放しない。イメージはそれをマッピングするプロセスの数を持ち、最後のプロセスの空間を破棄した後に(`prc_release`の`knl_elf_img_put`)ページを解放する。実身を書込みのために開いたとき(`ts_opn_obj`の`TFO_WRITE`か`TFO_EXCL`)とボリュームを閉じたときは、その実身(ボリューム)のイメージを使わないことにし(`knl_elf_forget`)、書き直したプログラムは次の起動で読み直す。セグメントが同じページを共有するプログラムと、パスで起動したプログラムは共有しない。読出し専用のページはプロセスから書き込めず(5.3)、カーネルもシステムコールのバッファとしての書込みをページテーブルの属性で拒否する(`knl_prc_user_ok`、`knl_prc_dma`)ので、共有したページが書き換えられることはない。

ブラウザ(読出し専用のページが約190MB、書込みのできるセグメントのファイルの部分が約1MB)では、動いているブラウザが別のプロセスのブラウザを起動するとき(14.7.8)、デバイスから読むのはヘッダだけになる。8MB以上のイメージはロードのたびにコンソールに`elf: a program of N MB read`か`shared`と、プロセスを作るのにかかった時間を出す。QEMUで、システムボリュームをSDカード(sdhci-pci)に置いて測ると(`CNF_OB_SYSVOL`を`"sda1"`にしたビルド)、最初のブラウザのロードは184MBを読んで約300秒、2つ目のブラウザのプロセスの生成は13ミリ秒であった。QEMUのSDカードの経路は実機のSDカード(25MHzで約12MB/s)よりずっと遅い(約0.5MB/s)が、2つ目以降が読まなくなることは同じである。

## 5.2 プロセスのタスクとオブジェクト

プロセスは`tk_cre_tsk`で自分のタスクを生成できる。タスクは必ず保護レベル3でプロセスのアドレス空間に置かれ、浮動小数点演算を使える。ユーザスタックはデフォルトで64KB、最大1MBで、プロセスのアドレス空間に確保する。

プロセスが生成したセマフォ、イベントフラグ、ミューテックス、メッセージバッファ、タスクは、そのプロセスの中でだけ有効である。別のプロセスやカーネルのオブジェクトのIDを渡すと`E_ID`になる。プロセス間の通信には、プロセスメッセージ(5.4)、通信用の実身、共有メモリ、イベント通知を使う(第8章)。

1つのプロセスが持てるオブジェクト数は、タスクとイベントフラグが256、セマフォとミューテックスが1024、メッセージバッファが64である(`include/ts/proc.h`の`TS_PRC_*_MAX`)。これを超えるか、カーネルのテーブルがカーネル自身の予約分を残して埋まると、生成のシステムコールが`E_LIMIT`を返す。

POSIXスレッドは`lib/libpthread`が提供する。スレッドはプロセスのタスクとして実装し、ミューテックスや条件変数は競合がなければユーザ空間のアトミック操作だけで処理する。ミューテックスの解放は、待つスレッドがいるとき、その1つを待ち行列から外してから状態を「空き」にし、それより後はミューテックスに触れない。POSIXでは解放したミューテックスをすぐ破棄してよく、待っていた側はスタックの上のミューテックスを取った直後にその関数から戻ることが多い。空きにしてから待ち行列を読むと、別のものになったメモリを読んで、そこから得たポインタに書き込む(ブラウザのレンダラが`pth_deq`で異常終了した原因。glibcでも同じ種類の不具合が修正されている)。待ち行列はグローバルなロックの下でしか変えないので、状態を書くまでそのロックを持てば、その間に待ちに入るスレッドを見落とさない。

## 5.3 メモリ

プロセスのアドレス空間の配置は4.6のとおりである。プログラムイメージはロード時にマッピングし、ヒープはその上に伸ばす。それ以外のメモリは`ts_map_mem`でアドレス範囲を予約し、使う部分をコミットして確保する。

| システムコール | 機能 |
| --- | --- |
| `ts_map_mem` | アドレス範囲を予約する。保護属性に`TS_MEM_READ`、`TS_MEM_EXEC`を指定すれば、ただちに0で初期化したページをマッピングする。`TS_MEM_RW`と`TS_MEM_JIT`は、ページを触れたときに作る(下記)。`TS_MEM_NONE`ならアドレス範囲だけを予約する |
| `ts_ctl_mem` | 予約範囲内のページをコミットする、保護属性を変える、解放する |
| `ts_unm_mem` | ページを解放し、予約を解除する |

保護属性は次の5つである。POSIXの`mmap`と`mprotect`(`lib/libcxxrt/ts_mman.c`)は`PROT_READ`、`PROT_WRITE`、`PROT_EXEC`の組をこれに対応付ける。

| 保護属性 | ページテーブルの属性 | 内容 |
| --- | --- | --- |
| `TS_MEM_NONE` | なし | アドレスだけを予約する。ページがあれば解放する |
| `TS_MEM_READ` | `AP`=EL0読出し専用、`UXN`=1 | 読出しのみ |
| `TS_MEM_RW` | `AP`=EL0読み書き、`UXN`=1 | 読み書き |
| `TS_MEM_EXEC`(`TS_MEM_READ`との組も同じ) | `AP`=EL0読出し専用、`UXN`=0 | 読出しと実行 |
| `TS_MEM_JIT`(`TS_MEM_RW`と`TS_MEM_EXEC`の組) | ページごとに上の読み書きか読出しと実行のどちらか | 書込みと実行を交互に行う |

書込みと実行を同時に許すページは作らない(W^X)。カーネルは`SCTLR_EL1.WXN`も立てており、書き込めるページはハードウェアの上でも実行できない。どの属性でも`PXN`は1で、カーネルがプロセスのページを実行することはない。

ページを実行できるようにするときは、ページテーブルを書き換える前に、そのページの物理アドレスのリニアマッピングで、データキャッシュの各ラインをPoUまで書き戻し(`dc cvau`)、`dsb ish`の後に命令キャッシュの各ラインを無効にして(`ic ivau`)、`dsb ish`と`isb`を行う(`knl_icache_sync`)。キャッシュラインのサイズと要否は`CTR_EL0`で決める。`IDC`か`DIC`が1なら該当する操作を省き、`CLIDR_EL1`の`LoUIS`と`LoUU`がともに0か`LoC`が0のときも`IDC`が1のときと同じく書き戻しを省く(QEMUのCortex-A76は`CTR_EL0`が0x8444C004で`IDC`が0、`CLIDR_EL1`が0x82000023で`LoUU`と`LoUIS`が0。実機のRaspberry Pi 5のLinuxも、データキャッシュの書き戻しが要らないと判定している)。命令キャッシュが物理アドレスで索引付けとタグ付けをする方式(PIPT)でなければ、別の仮想アドレスのラインが残りうるので`ic ialluis`で全体を無効にする。アドレスによるキャッシュ操作はInner Shareableの全プロセッサのキャッシュに及ぶ。ページテーブルの書換えはbreak-before-makeで行い、古いエントリは`tlbi vaale1is`で全プロセッサのTLBから消す。

キャッシュを無効にしても、他のプロセッサが古い命令をすでに取り込んでいることがある。それを捨てるにはそのプロセッサでコンテキスト同期(例外の発生か復帰、`isb`)が要る。そこで、ページを実行できるようにした後、同じプロセスのタスクを実行中の他のプロセッサにIPI(`SGI_DISPATCH`)を送り、それぞれが割込みを受け付けたことを受信の回数で確認してから戻る(`knl_sync_cores`)。割込みの受付は例外の発生なので、そのプロセッサが取り込んだ命令は捨てられる。後からそのプロセスのタスクを実行し始めるプロセッサは、例外からの復帰でEL0に入るので、同じく同期している。

`TS_MEM_JIT`の範囲は、実行時にコードを生成するプログラム(V8、第14章)のためのものである。V8はコードの領域を読み書きと実行の両方の属性で求め、書き込んだ直後に実行する。カーネルは範囲をプロセスごとの一覧に記録し、ページは触れたときに0で初期化して作る(書込みか読出しなら読み書き、実行なら読出しと実行)。読み書きのページを実行するとインストラクションアボート、読出しと実行のページに書き込むとデータアボートになり、例外ハンドラ(`knl_el0_fault`)が、システムコールと同じく割込みを許し、タスクをカーネルの中にいる扱い(`svcdepth`)にして`knl_prc_ufault`を呼ぶ。そこでプロセス表のロックを取り、ページを逆の属性に切り替えて(実行にするときは上のキャッシュ操作とプロセッサの同期をする)、同じ命令をやり直させる。各ページはどの時点でも書込みか実行のどちらか一方しか許さない。別のスレッドが実行しているページに書き込むと、両者の例外でページが行き来するが、書き込まれた命令は必ず実行の前にキャッシュから見えるようになっている。

同じ例外ハンドラは、別のタスクが保護属性を変えている途中(break-before-makeでエントリが一時的に無い)のページに触れた場合も、ロックを取った後にエントリがそのアクセスを許していれば、やり直させる。これ以外の変換フォルトと許可フォルトは、従来どおりプロセスを異常終了させる(5.5.2)。

プロセスはキャッシュの操作を自分でも行える。`SCTLR_EL1.UCT`と`UCI`を立てているので、EL0から`CTR_EL0`を読み、`dc cvau`と`ic ivau`を実行できる(gccの`__builtin___clear_cache`、V8の`FlushInstructionCache`)。

`TS_MEM_RW`の範囲(`ts_map_mem`か`ts_ctl_mem`で読み書きにした範囲)も、ページをその時には作らない。カーネルは範囲をプロセスごとのもう1つの一覧(`lazy`)に記録し、プロセスが初めて触れたときに例外ハンドラ(`knl_prc_ufault`から`knl_umem_fault`)が0で初期化した読み書きのページを作って、同じ命令をやり直させる。無名のマッピングのデマンドページングに当たる。そのため、newlibのヒープの64GBの予約、partition_allocやV8の予約の中のコミット、`memfd_create`のメモリオブジェクトは、使ったページの分しかメモリを使わない。使う前のページをシステムコールに渡したときは、カーネルがそのページに触れる前に、アドレスを確認する`knl_prc_user_ok`がプロセス表のロックの中でページを作る(`knl_umem_touch`)。作るのは最初に欠けたページからで、プロセスのものでないページに当たったところで止める。そのため、システムコールに実際のメモリより大きな長さを渡されても、ロックを持つ時間はプロセスのページの数を超えない。カーネル自身のアクセスの例外ではページを作らない(割込みを禁止した例外ハンドラの中で、どのロックを持っているか分からないため)ので、プロセスのメモリに触れるシステムコールは必ず先に`knl_prc_user_ok`を通す(5.6)。ページを作るときにマシンの空きが16MB(`UMEM_FLOOR`)を切っていれば、プロセスは異常終了する。予約の時点では拒否しない(Linuxのオーバーコミットに当たる)。

`ts_ctl_mem`に`TS_MEM_DISCARD`だけを与えると、保護属性はそのままにページの中身を捨てる。`TS_MEM_JIT`と`TS_MEM_RW`の範囲のページは解放してシステムに返し(次に触れたときに0で作り直す)、それ以外のページはその場で0で埋める(実行できるページなら上のキャッシュ操作も行う)。`madvise`の`MADV_DONTNEED`、`MADV_FREE`、`MADV_REMOVE`はこれを使う。ブラウザでは、V8がコードの領域を確保した直後にpartition_allocの`DiscardSystemPages`がこれを呼ぶので、以前のように読み書きのページに作り直すと、コードの領域が実行できなくなる。

`TS_MEM_JIT`の範囲のページをシステムコールに渡してはならない。カーネルがそこに読み書きするときは属性を切り替えず、ページが無いか書き込めなければ、システムコールに渡した不正なアドレスとして扱う(5.5.2)。

プロセス間で共有するメモリは、揮発性のメモリの実身のレコードを`ob_map_rec`で共有メモリ領域にマッピングして作る(8.3)。共有メモリはどのプロセスからも同じアドレスに見える。名前のないメモリの実身(`OB_F_TRANSIENT`)は、キーを渡されたプロセスだけが使え、最後のキーとマッピングがなくなると消える。`lib/libcxxrt`の`memfd_create`はこれを作る(5.7)。

### 5.3.1 メモリの使用量の記録

カーネルのタスク(`prc_memlog`、`peripheral_kernel/sysman/proc.c`)が30秒ごとにプロセスの表を見て、メモリを64MB以上使っているプロセスについて、1行ずつコンソールに出す。Linuxの`/proc/<pid>/status`の`VmRSS`などに当たる。実機で長く動かしたときに、何が増えているかを後からログで見分けるためである。

```text
mem: pid 21 browser.elf: image 210MB asked 830MB (writable 2900MB) held 0MB gpu 412MB (950 BOs) shared 96MB calls 2 lent 0; free 3120MB of 7680MB
mem: shared memory: 840 objects 180MB, 150MB of them mapped; window 260MB in use
```

| 項目 | 内容 |
| --- | --- |
| `image` | プログラムイメージとスタックのマッピング(`memsz`) |
| `asked` | `ts_map_mem`と`ts_ctl_mem`の範囲で、今あるページ(ヒープ、`mmap`、V8やpartition_allocの予約の中のコミット)。読み書きの範囲のページは触れてから数える(`VmRSS`に当たる) |
| `writable` | 読み書きの範囲(`TS_MEM_RW`)のサイズ。ページが有っても無くても数える(`VmSize`に当たる) |
| `held` | プロセスが外したが、デバイスに貸した呼出しのために保留しているページ(5.6.1)。プロセスのものでも空きでもない |
| `gpu` | プロセスのGPUのコンテキストが持つBOのページとBOの数(`knl_gpu_prc_pages`) |
| `shared` | プロセスにマッピングしているメモリの実身のレコードのページ(`knl_obmem_stat`)。同じページを複数のプロセスがマッピングしていれば、それぞれに数える |
| `calls`、`lent` | 呼出しの中にいるタスクの数(`incall`)と、そのうちページをデバイスに貸している数(`indma`) |
| `free` | マシン全体の空きのページと、全部のページ |

値は表のロックの中でコピーし、ロックを外してから出す。64MBに満たないプロセスは出さないので、通常はほとんど出ない。`shared`はメモリの実身のロックで数えるので、プロセスの表のロックを外してから求める(メモリの実身はマッピングのときに、自分のロックの中でプロセスの表のロックを取るため、逆の順に取るとデッドロックする)。

メモリの実身のレコードのページが合わせて64MB以上あれば、プロセスの行の後に`mem: shared memory`の行を出す。実身の数、レコードのページの合計、そのうちどこかのプロセスにマッピングしているもの、共有メモリの領域で使っているアドレスの量(解放したアドレスを除く。`knl_shm_va_used`)である。ページは、何プロセスがマッピングしていても1回だけ数える。ブラウザを複数のプロセスに分けると、プロセスの行の`shared`の和は実際のページより大きくなるので、こちらで全体を見る。

64MB以上の範囲を、`TS_MEM_NONE`以外の保護属性で`ts_map_mem`で予約するか`ts_ctl_mem`で変えると、そのたびに1行出す(`umem_tell`)。大きな確保をどこが求めたかを、前後のログと突き合わせて見分けるためである。最後の数は結果のエラーコードで、`asked`はその後のプロセスのページである。

```text
mem: pid 3 maps 256MB at 100004a00000 prot 3: 0, asked 1260MB
mem: pid 3 changes 128MB at 100010000000 prot 3: 0, asked 1262MB
```

2026年11月9日、Surface Go 2でYouTubeを見ていると、ブラウザの`asked`が30秒で1.2GB増え、その後は減らなかった。当時は、読み書きの範囲のページを予約やコミットの時点で全部作っていた。さらに、`TS_MEM_DISCARD`(`madvise`の`MADV_DONTNEED`)は読み書きのページをその場で0で埋めるだけで、`_sbrk`がヒープを縮めてもページは残った。partition_allocは空いたスロットスパンを`MADV_DONTNEED`で返す(`PageAccessibilityDisposition::kAllowKeepForPerf`)ので、Blinkのパーティション(ArrayBufferの中身など)とV8のヒープが一度使ったページは、プロセスが終わるまで残っていた。`asked`は、それまでに一度でも使ったメモリの最大のところを示していたことになる。今は上のとおり、読み書きのページは触れたときに作り、捨てたページはシステムに返す。

## 5.4 プロセスメッセージ

プロセスはそれぞれメッセージの受信キューを1つ持つ。`ts_snd_msg`でプロセスIDを指定して送信し、`ts_rcv_msg`で受信する。1通は256バイトまでで、8通までキューにためられる。キューが満杯のときの送信と、空のときの受信は、指定した時間まで待つ。

子プロセスが終了すると、親プロセスに`TS_MSG_CHILD_EXIT`が届く。

## 5.5 プロセスの終了

プロセスは次のいずれかで終了する。

- `main`から戻る、または`ts_ext_prc`を呼ぶ。
- 別のプロセスが`ts_ter_prc`を呼ぶ。デスクトップでShift+Pauseを押したときも、同じ処理で終了する(5.5.1)。終了コードは`ts_ter_prc`に渡した値で、Shift+Pauseでは`TS_ABORT_TERM`である。
- EL0で例外を起こす。未定義命令(例外クラス`0x00`。`UDF`と割り当てのない命令)と不正な実行状態(`0x0e`)では`TS_ABORT_ILL`、それ以外の例外(データアボート、命令アボート、アライメント例外など)では`TS_ABORT_FAULT`が終了コードになる。データアボートは、プログラムがハンドラを決めていればそこで受け取れる(5.5.2)。コンソールには例外の種類、アドレス、`ELR`とともに`LR`(x30)も表示する。アドレス0へ分岐した例外では、呼び出した場所は`LR`にしか残らないためである。
- システムコールに渡したアドレスで、カーネルがデータアボートを起こす。そのアドレスがプロセスの空間内にあり、マッピングされていないか書き込めないときは、そこに中身のないページを割り当ててシステムコールを最後まで実行させ、戻るところでプロセスを`TS_ABORT_FAULT`で終了させる。
- システムコールの処理の中で、カーネルが確認せずにプロセスのページに触れ、PANがそれを拒否する(4.6.1)。システムコールは最後まで実行し、戻るところでプロセスを`TS_ABORT_FAULT`で終了させる。プロセスの誤りではなくカーネルの不具合だが、カーネルが確認していないものを受け取ったプロセスをそのまま続けさせない。

終了時、カーネルはプロセスのタスクとオブジェクトを削除し、開いていたファイル、ソケット、実身のキーを閉じ(ストリームの端も閉じるので、相手の端は終わりを読む、8.5.1)、プロセスが作ったウインドウ(従属ウインドウを含む)を閉じ、アドレス空間を破棄する。タスクがファイルや実身のシステムコールの処理中にあるときは、途中で止めるとボリュームやロックが不整合な状態で残るので、システムコールから戻るところまで進めてから止める。長い読み書きは256KBごとに区切り、区切りごとに終了要求の有無を確認する。

終了を求められてから終了を通知するまで(待っている者と親に通知し、`ts_wai_prc`が待てるようになるまで)、プロセスの状態(`ts_ref_prc`の`state`)は`PS_EXITING`である。通知し終えると、カーネルのタスク`prc_reaper`(優先度12)が、終了を進めたタスクが休止状態になったものから順に(5ミリ秒ごとに見直し、2秒たっても休止状態にならなければそのまま)、残ったタスクを削除してアドレス空間とページを解放し、状態を`PS_ZOMBIE`(プロセスの実身では「ended」)にする。後に残るのはプロセスの管理ブロックと終了コードだけで、`ts_wai_prc`で回収したときに消える。カーネルが起動したプロセス(デスクトップから起動したプログラムなど)は回収されないことがあるので、空間とページを回収まで持たせない。以前は回収のときに初めて空間を解放し、状態を変えていたので、回収されないプロセスは`PS_EXITING`のまま空間を持ち続け、プロセスの終わりを状態で見るもの(サウンドデバイスの音量のチャネルなど)が先へ進まなかった。`tests/ktest/ktest_proc.c`の`test_end_uncollected`が、回収する前に状態が`PS_ZOMBIE`になり、タスクもマッピングも残らないこと、回収で終了コードを受け取れ、そのとき解放するページが残っていないことを確認する。

回収する者のいないプロセスの管理ブロックは、一定の時間で消す。回収できるのは、動いている親のプロセス(initを除く)と、`ts_wai_prc`でそのプロセスを待っている者である。プロセスの`ts_wai_prc`は自分の子しか待てない(`svc_gate.c`)ので、カーネルが起動したプロセス(親が0)、親が終わったプロセス、initの子は、カーネルの中で`ts_wai_prc`を呼ぶ者がいなければ回収されない。カーネルの中で終了コードを使うのは、試験(`ts_wai_prc`)、プロセスの実身のレコード(`ts_ref_prc`で状態と終了コードを読む)だけで、デスクトップは使わない。例外で終わったことの記録(5.5.2)は管理ブロックとは別に持つ。そこで`prc_reaper`は、回収する者のない`PS_ZOMBIE`の管理ブロックを、`PS_ZOMBIE`になってから60秒(`knl_prc_orphan_ms`)で消す。60秒たたなくても、そうした管理ブロックが512を超えたら、2秒以上たったものから古い順に消す。`ts_wai_prc`で待っている者がいる間(`waiters`)は消さない。消すときは回収と同じく、子をinitの子にし、開いていたものと資格を片付ける。消した後に`ts_ref_prc`や`ts_wai_prc`で問い合わせると`E_NOEXS`になる。`prc_reaper`は、そうした管理ブロックがある間は1秒ごとにウェイクアップして調べる。`tests/ktest/ktest_proc.c`の`test_churn_uncollected`が、時間を0.1秒に縮めて、回収しないプロセスを`KT_CHURN_N`回(既定は1000回)起動して終わらせ、管理ブロックの数と空きページが元に戻ること、待っている者には終了コードが渡ることを確認する。

### 5.5.1 キーボードからの強制終了

Shift+Pauseを押すと、最前面のウインドウを作ったプロセスを強制終了する。最前面のウインドウとは、入力フォーカスを持つウインドウ、どのウインドウも入力フォーカスを持たなければ、ポップアップを除いて最も手前にあるウインドウである。ただし、入力フォーカスを持つウインドウより手前に普通のウインドウ(ポップアップ、浮かぶウインドウ`WM_ATTR_FLOAT`、入力フォーカスを持たないウインドウ`WM_ATTR_NOFOCUS`を除く)があれば、そのうち最も手前のものを最前面のウインドウとする(`knl_wm_front_pick`)。入力フォーカスを持つウインドウがカーネルのもので終わらせるプロセスがないときは、ポップアップを除いて最も手前にあるウインドウも同じように調べる。プロセスのウインドウは、押しただけでは入力フォーカスを得ず(プログラムが求めたときに得る)、手前に見えていても入力フォーカスは後ろの別のウインドウにあることがあるためである。デスクトップの最初のウインドウは仮身一覧のプロセスのウインドウなので、入力フォーカスだけで決めると、手前に見えているプログラムではなく仮身一覧のプロセスが終わる。スクリーンキーボードや道具のパレットは入力フォーカスを持つウインドウの手前に立つものなので、最前面のウインドウにしない。ウインドウを作ったプロセスは、ウインドウの実身が生成時に記録したプロセスID(`wmobj.c`の`maker`)でわかる。終了は`knl_prc_force_end`が`ts_ter_prc(pid, TS_ABORT_TERM)`で行うので、システムコールの処理中のタスクの扱いも、ウインドウを閉じる処理も`ts_ter_prc`と同じである。結果はメッセージ行に「<プログラム名>(pid N)を強制終了しました」と表示し、コンソールにも1行出力する。プログラム名は、起動したプログラムの実身の名前、実身から起動していなければプログラムのファイル名である。

デスクトップがプロセスの依頼で開いたウインドウは、依頼したプロセスのものとして扱う。管理者のパスワードを尋ねるパネル(`DT_RQ_ADMIN`)、印刷の設定や画面表示のウインドウ(`DT_RQ_PRINT`)など、デスクトップは依頼を処理する間に自分のタスクでウインドウを開く。作成元はカーネルなので、そのままでは強制終了できない。そこでデスクトップは依頼を1件処理する間、依頼を書いたプロセス(`knl_obchan_last_from`)を`knl_wmobj_act_for`で通知し、その間に同じタスクが開いたウインドウには、`wmobj.c`が作成元とは別にそのプロセスのIDを記録する(`forpid`)。Shift+Pauseは、入力フォーカスを持つウインドウより手前に出ているポップアップのうち`forpid`を持つ最初のもの、なければ入力フォーカスを持つウインドウの作成元、作成元がカーネルならその`forpid`を対象にする。パネルはデスクトップのウインドウの上にポップアップで出し、入力フォーカスはデスクトップのウインドウに置いたままなので、ポップアップを先に調べる。依頼したプロセスが終わっても、パネルはデスクトップが閉じるまで残る(〈取消〉かEscで閉じる)。

キーはUSBの入力のレイヤ(`device/usb/hid.c`)が受け取る。キーボードの報告から押下と解放のイベントを作り、キー配列の割り当ての変更(`km_remap`)をした後、リングに入れる前に`knl_fq_input`(`outer_kernel/wm/fquit.c`)に渡す。Shift+PauseとCtrl+Shift+Pauseはそこで取り、リングには入れない。リングを読むのはデスクトップのタスクなので、ウインドウマネージャの`wm_read_event`で処理していた以前の実装では、デスクトップがプログラムの応答を待っている間、大きな保存やコピーの間、デスクトップ自身が止まったときにShift+Pauseが機能しなかった。入力のレイヤの手前で取れば、デスクトップが何をしていても受け取れる。

受け取った後の処理は、強制終了専用の2つのカーネルのタスクが行う。`fq_task`は優先度3で、入力のタスク(8)より上で動く。キーの意味を決め、対象のプロセスを調べる。ウインドウの重なり順と作成元を調べるロック(ウインドウマネージャの`wm_mtxid`と`wmobj.c`のロック)は0.3秒しか待たない(`knl_wm_front_pick`、`knl_wmobj_who`)。止まったタスクがロックを持ったままでも、最後の手段であるキーが止まらないようにするためである。調べられなかったときは「ウインドウの状態がわからないため、強制終了できません」と出す。`fq_task`はこのほかの待ちには入らない。`fq_work`は優先度11で、デスクトップ(20)より上、画面を組み立てるタスク(10)より下で動き、プロセスの終了、メッセージ行への表示、強制終了のウインドウ(5.5.3)、デスクトップの立ち上げ直しの後始末(5.5.5)のように、時間がかかるか待つことのある処理を行う。デスクトップが書体やウインドウのロックを持ったまま止まると`fq_work`もそこで待つが、`fq_task`は動き続け、デスクトップを立ち上げ直せばロックは解放される。

結果は`fq_task`がすぐにコンソールへ出し、`fq_work`がメッセージ行に表示する。デスクトップが止まっていても、メッセージ行は`fq_work`が描き、画面を組み立てるタスクが画面に重ねるので表示される。メッセージ行がない(デスクトップが一度も起動していない)ときは、コンソールだけに出す。

キーを押し続けたときの繰り返しは、リングを読む側(`ts_hid_read`)が作るので、リングの手前で取るShift+Pauseには繰り返しが起きない。キーボードの報告は押した時点で1度だけ押下を作る。ただし、手で入れたイベント(試験、リモートの入力)は押下を繰り返すことがあるので、前の押下から解放のないまま2秒以内に来た押下は押し続けとみなして無視し、2秒を過ぎた押下は新しい押下として扱う。キーボードを抜くなどして解放のイベントが失われても、以後のShift+Pauseは機能する。以前は押しているフラグを解放のイベントでしか消さなかったので、解放が失われると以後のShift+Pauseがすべて無視された。

Shift+Pauseで終了を求めたプロセスが1秒たっても終わらないとき(タスクがシステムコールの中で止まっている)は、「<プログラム名>(pid N)は終了の途中です。止まったままなら、もう一度強制終了すると強制的に終わらせます」と出す。もう一度押すと5.5.4の方法で終わらせる。

次の場合は何も終了させず、メッセージ行にその旨を表示する。

| 場合 | 表示 |
| --- | --- |
| 最前面のウインドウがカーネルのもの(デスクトップ、キャビネット、基本文章編集、基本図形編集などカーネルのタスクとして動くもの)で、プロセスの依頼で開いたものでもない、またはウインドウがない | 強制終了できるプロセスがありません(デスクトップが止まっているときは5.5.5) |
| システムに必要なプロセス | <プログラム名>(pid N)はシステムのプロセスなので強制終了できません |
| 終了を求めてから1秒たっていないプロセス | <プログラム名>(pid N)は終了の途中です。… |

システムに必要なプロセスは、initと、属性`TS_PRC_SYSTEM`を指定して起動したプロセスである。initは`knl_start_init`がこの属性で起動する。この属性は、プロセスでない呼出し元(カーネルのタスク)が`ts_cre_prc`に指定したときだけ有効で、プロセスが子プロセスに指定しても無視する。プログラムが自分の子プロセスを強制終了から保護できないようにするためである。

### 5.5.2 例外による終了の通知

プロセスが例外で終了すると、デスクトップがダイアログ「プログラムの異常終了」で通知する(11.1)。例外ハンドラは画面を操作しない。プロセスを終了させるときに、プロセスID、例外を起こしたタスク、プログラムの実身とファイル名、`ESR`、`FAR`、`ELR`、`LR`、終了コードを記録するだけである(`include/ts/proc.h`の`T_PRCFLT`)。EL0の例外では、`ELR`の16バイト前からの32バイトを、プロセス自身のマッピングを通して読んで記録し(`code`、読めた4バイトごとのビット`codeok`)、`ELR`の物理アドレス(`codepa`)とともにコンソールにも表示する(`TessronOS: task N code at ...`)。プロセッサが報告した命令とプログラムのファイルのその位置の内容を比べ、実行中にページの中身が変わったのか、キャッシュから古い命令を取り出したのかを見分けるためである。ARMでは、EL0の例外の行に`CTR_EL0`と`CLIDR_EL1`の値も表示する。x64では、プロセスが例外で終了する経路で1回だけ、汎用レジスタの全部、`rip`、`rflags`、`cs`、`ss`、エラーコード、FSのベース、`rip`からの命令バイト16個、`rsp`からの8ワードをコンソールに表示する。命令バイトとスタックは、プロセスの空間にマッピングされている範囲だけを読み、読めないときは`unreadable`と表示する。EL0の例外は`knl_prc_abort`で、システムコールに渡したアドレスによる例外とPANが拒否したアクセスは、プロセスが終了するシステムコールの出口(`knl_prc_call_leave`)で記録する。後者の`ELR`と`LR`はカーネル内の値である。記録の種類(`kind`)は、EL0の例外が`TS_FLT_EL0`、渡したアドレスによる例外が`TS_FLT_KCALL`、PANが拒否したアクセスが`TS_FLT_KPAN`で、ダイアログの見出しはそれぞれ「プログラムがプロセッサの例外を起こしたため、終了しました」「プログラムがシステムコールに不正なアドレスを渡したため、終了しました」「カーネルがプログラムのメモリに確かめずに触れたため、プログラムを終了しました」である。

記録はカーネル内の4件のキューに入れ、デスクトップのタスクが主ループのたびに`knl_prc_fault_take`で取り出す。キューが満杯のときは最も古い記録を捨て、捨てた件数を数える。記録するのはプロセスを終了させた例外だけで、すでに終了処理中のプロセスの別のタスクが起こした例外は記録しない。そのため、例外が続けて起きても記録とダイアログが際限なく増えることはない。デスクトップが起動する前に起きた例外は、コンソールへの表示だけになる。

x64のIDTのゲートは、どれもカーネルの特権(DPL 0)の割込みゲートである。ただし、ブレークポイント(ベクタ3、`int3`)とオーバーフロー(ベクタ4、`into`)の2つだけはDPL 3にしている。DPL 0のままだと、プログラムの`int3`はゲートの特権の検査で一般保護例外になる。エラーコードはゲートの番号を8倍して2を足した値で、ベクタ3なら0x1aである。ChromiumやV8は回復できない誤りで止まるときに`int3`を実行する(`IMMEDIATE_CRASH`)ので、ダイアログに「一般保護例外」と出て、本当の原因が分からなくなっていた。今は「ブレークポイント」と出る。#BPはトラップなので、プロセッサが報告するRIPは`int3`の次の命令を指す。記録の`ELR`はその1バイト前、つまり`int3`そのものにする。ほかのゲートはDPL 0のままで、プログラムが`int n`で起こすと一般保護例外になる。試験は`cxx`のグループの`test_breakpoint`である。

プログラムは、自分のデータアボートを受け取るハンドラを`ts_def_flt`で決められる。プロセスのメモリで対処できないデータアボート(何もないアドレス、そのように触れてはいけないページ)が起きると、カーネルは例外のエントリのフレームをそのハンドラに向ける。タスクのスタックの、それまでの位置より下に、その時点の状態(`T_TSFLT`。x0からx18とx29、x30、SP、PC、NZCV、`FAR`、`ESR`、FP/SIMDのレジスタq0からq31と`FPSR`、`FPCR`)を書き、x0をそのアドレスにしてハンドラから続けさせる。状態は`T_TSFLT`のアライメント(16バイト)で置く。x64ではタスクのrspが8の倍数でしかないことがあり、さらにSystem V ABIのレッドゾーン(rspの下の128バイト。関数がrspを動かさずに使う)を上書きしないよう、その下に置く。ハンドラの入口のrspは、関数を呼んだ直後と同じく16の倍数より8小さい。カーネルは、エントリへ渡したデータアボートを、プロセスごとに最初の8件だけコンソールに出す(`TessronOS: pid N task N: fault handed to the program, syndrome ... address ... pc ... sp ...`)。ハンドラが対処できずにプロセスが終わったときや、ハンドラ自身が例外を起こしたときに、元の例外が何だったかを残すためである。syndromeはx64では例外のベクタ(ビット39から32)とエラーコード、ARMでは`ESR_EL1`の値である。ハンドラは戻らずに`ts_flt_ret`を呼ぶ。カーネルはそのシステムコールのエントリのフレームを状態の内容に書き換え、FP/SIMDのレジスタを戻して、状態の示す所へ戻る。PCを変えなければ同じアクセスをやり直し、変えればそこから続く。x19からx28(x64ではrbxとr12からr15)はカーネルが状態に含めず、`ts_flt_ret`も変えない。ハンドラが関数と同じくこれらを保つ。ハンドラは`ts_flt_ret`を呼んで戻らないので、Cの関数のまま書くと、その関数が使った値のまま例外の時点へ戻ってしまう。そこでブラウザの入口(`ts_flt_entry`)は、入ってすぐにこれらを状態の`regs`の該当する位置に書いてからCの処理を呼び、`ts_flt_ret`の直前に状態から読み戻す(`ts_flt_back`)。ハンドラを決めていないプロセス、ハンドラを`NULL`にしたプロセス、スタックに状態を書けないときは、これまでどおり終了する。

ブラウザは、これをPOSIXの`SIGSEGV`(アライメント例外は`SIGBUS`)として受け取る(`port/compat/ts_signal.c`)。`sigaction`で登録したハンドラを`siginfo_t`と`ucontext_t`で呼び、ハンドラがコンテキストに残したレジスタ(x19からx28も含む)とPCへ戻る。V8のWebAssemblyのtrap handlerがこれを使う。モジュールのメモリの前後にアクセスできないページを置き、範囲外のロードとストアをそこで例外にして、モジュールのトラップに変える。生成するコードは範囲を確認する命令を持たない(14.4.1)。

カーネルのタスクがEL1で例外を起こしたとき(`!EXCEPTION!`)は、例外の種類とレジスタをコンソールに表示し、そのプロセッサを割込み禁止のまま停止する(x64では、記録のファイルを書き終えるまでそのタスクだけをスリープさせ、書き終えたら全プロセッサを止める。3.10)。カーネルのデータがおかしくなっている可能性があり、処理の継続を前提にしていないので、ダイアログは表示しない。SError、FIQ、タスクのスタックオーバーフロー(`!STACK!`)も同じく停止する。例外として扱わずに処理を続けるのは、上に述べた、システムコールに渡されたプロセスのアドレスによるデータアボートとタスクの中でPANが拒否したアクセス、`TS_MEM_JIT`の範囲のページの切替えなど`knl_prc_ufault`が対処できるEL0のアボート(5.3)だけである。

### 5.5.3 強制終了のウインドウ

Ctrl+Shift+Pause、またはデスクトップの〈小物〉の「強制終了」(組込みのプログラム`force-quit`、プログラム箱にある)で、プロセスの一覧のウインドウ「強制終了」を開く。ウインドウを持たないプロセス(バックグラウンドで動き続けるもの、実時間メディアや動画の補助プログラム)もここから終わらせられる。

ウインドウは、データボックスの実身(`SYSDEF_BOX_FQUIT`「強制終了のデータボックス」)のパネルを配置したウインドウである。`fq_work`がウインドウとパネルを実身として作り(`OB_T_WINDOW`の`OB_S_WINDOW`と`OB_S_PANEL`)、パネルをウインドウに配置し、部品の実身を開く。部品の描画と操作はウインドウマネージャが行い、`fq_work`は部品の番号で状態のレコードを読み書きし、チャネルに届く通知(`OB_E_CHANGE`、`OB_E_KEY`、`OB_E_CLOSE`)を受けるだけである。パネルの部品は次のとおりである。

| 番号 | 部品 | 内容 |
| --- | --- | --- |
| 10 | スクロールする一覧 | プロセス1つが1行で、「プログラム名 (pid N)」。終了の途中のものには「終了の途中」、強制的に終わらせたものには「強制的に終了」を後に付ける |
| 21〜24 | 操作できない文字の箱 | 選んだプロセスの状態(実行中、終了の途中、システムコールの中で止まっている、システムのプロセス、強制的に終了)、作ったウインドウの数、CPU時間、マップしたメモリの量 |
| 25 | 操作できない文字の箱 | 最後に行ったことの結果 |
| 31 | 押しボタン | 〈デスクトップを立ち上げ直す〉 |
| 32 | 押しボタン | 〈強制終了〉。システムのプロセスと、強制的に終わらせたプロセスを選んでいるときは操作できない |
| 33 | 押しボタン | 〈取消〉。既定のボタン(太い枠、Enterで押される)で、ウインドウを閉じる |

既定のボタンは安全な方の〈取消〉にする。Enterを押しただけでプロセスが終わることはない。プロセスを選ぶのは、一覧の行の押下、↑↓、PageUp、PageDown、Home、End(一覧の部品がキーを取らないので、ウインドウに届いたキーの通知から`fq_work`が選ぶ)である。〈強制終了〉か、開いている間のShift+Pauseで、選んだプロセスを5.5.1と同じ処理で終わらせる。終了の途中のものには5.5.4の方法を使う。〈デスクトップを立ち上げ直す〉は、警告のパネル(データボックスの10番、`WM_PNL_WARN`)をウインドウの中央に出して尋ねる。パネルは立ち上げ直すこと、保存していない文書と、失われる変更、プロセスはそのまま残ることを示し、〈立ち上げ直す〉と既定の〈取消〉を持つ。

ウインドウは普通のウインドウである。タイトルバーの絵文字には組込みのプログラム「強制終了」の実身のアイコンを付ける。枠での移動、絵文字の2度押しで閉じること、右ボタンのメニュー(`SYSDEF_MENU_FQUIT`「強制終了のメニュー」:共通の「閉じる」、「強制終了」「デスクトップを立ち上げ直す」、末尾の共通の「ウインドウ」「小物」「実行」)が使える。メニューはウインドウに開き、ウインドウマネージャの実身のレイヤが入力に応じて操作し、選ばれるのを待つ(`mn_opn_men`、`knl_wmobj_menu_run`)。Esc、Ctrl+E、〈取消〉、Ctrl+Shift+Pauseで閉じ、入力フォーカスを開く前のウインドウに戻す。一覧は1秒ごとに作り直し、名前が変わったときだけ部品に書き込み、選んだ行はpidで保つ。終了を通知し終えて回収を待つだけのプロセスは並べない。デスクトップを立ち上げ直した後は、新しいデスクトップが開くウインドウより手前に6秒間保つ。

デスクトップが動いているとき、入力はデスクトップの`wm_read_event`から`knl_wmobj_event`を通ってこのウインドウに届き、ほかのプログラムのウインドウと同じに扱われる。デスクトップが止まっているときは誰も入力を読まないので、ウインドウが開いている間は入力のレイヤの手前でイベントをすべて取り(`knl_fq_input`)、`fq_work`が`wm_read_event`と同じく宛先のウインドウと作業領域の中の位置を決めて`knl_wmobj_event`に渡す(`fw_feed`)。パネルの部品は同じ仕組みで操作でき、見た目も同じである。開く前に押していたキーやボタンの解放はリングへ、取っている間に押したものの解放はウインドウへ渡し、デスクトップが押下のない解放や解放のない押下を受け取ることはない。ポインタは入力のレイヤが位置を更新し、画面を組み立てるタスクが描くので、取っている間も動く。

デスクトップが止まっている間の扱いには例外が2つある。枠での移動と大きさの変更、右ボタンのメニューは使えない。枠の操作はデスクトップの主ループが行うもので、メニューは選ばれるのを`fq_work`自身が待つ間に、入力を渡す役も`fq_work`なので、待ちが終わらなくなるためである。閉じるには〈取消〉かEscを使う。また、ウインドウとパネルを作るには実身とウインドウのロックが要る。デスクトップがそれを持ったまま止まっていると`fq_work`も待ち、ウインドウは出ない。そのとき`fq_task`は、`fq_work`が1秒以上処理を終えられずにいることを見て、プロセスの一覧をロックを使わずにコンソールへ出す(pid、ファイル名、システムか、終了の途中か、CPU時間)。Shift+Pauseを2度押してデスクトップを立ち上げ直せば(5.5.5)ロックは解放され、ウインドウも出る。結果の文はメッセージ行とコンソールに出す。メッセージ行がない(デスクトップが一度も起動していない)ときは、標準の部品でない表示を新たに作らず、コンソールだけに出す。

CPU時間は、各タスクがプロセッサを使った時間の合計である。ディスパッチャがタスクを取るとき(`knl_dispatch_pick`)にそのプロセッサのカウンタ(`CNTPCT_EL0`)を記録し、タスクのコンテキストを手放して一時スタックに移るとき(`dispatch.S`から`knl_acct_leave`)に差を`TCB`の`runcyc`に足す。タスクが動いている間に受けた割込みの時間もそのタスクに数える。`knl_prc_info`が、プロセスのタスクの`runcyc`をミリ秒に換算して合計する。

### 5.5.4 終了の途中で止まったプロセス

`ts_ter_prc`は、タスクがファイル、ソケット、実身、描画、ウインドウのシステムコールの中にいるとき、プロセスにフラグを立てるだけで、タスクが呼出しから出たところで終わらせる(5.5)。長い呼出しは区切りごとに、待ちは一定の時間ごとにフラグを見て抜けるが、そうなっていない待ちに入ったまま返らないタスクがあると、プロセスは「終了の途中」のまま残る。応答しないデバイスへの要求、誰も解放しないロックの待ちがそれにあたる。

終了を求めてから1秒以上たったプロセスにもう一度強制終了を求めると、`knl_prc_kill`で2段階に終わらせる。

1. 待ちを解除する。プロセスのタスクのうち、イベントを待っているだけの待ち(イベントフラグ、メッセージバッファ、メールボックス、起床待ち、時間待ち)にあるものを`tk_rel_wai`で解き、呼出しに`E_RLWAI`を返す。セマフォとミューテックスの待ちは解かない。カーネルのレイヤの中には、セマフォをロックに使い、待ちが解けるとロックを得たものとして先へ進むものがあり(TSFSのボリュームの書込みのロックなど)、解くと2つのタスクがロックの中に入ってしまうためである。解いた後1秒の間、50ミリ秒ごとに終わったかを見て、0.2秒ごとに待ちを解除し直す。シリアルポートの読出しは、待ちが解除されると読めた分だけで戻る(`device/ser/ser.c`)。
2. その場で止める。1秒たっても終わらなければ、プロセスのタスクを呼出しの中にいてもそのまま休止状態にし(`tk_ter_tsk`。別のプロセッサで動いているものは先に`tk_sus_tsk`でそのプロセッサから外す)、呼出しの数を0にして、通常の終了と同じく開いていたものを閉じ、終了を通知する(`prc_finish`)。タスクが持っていたミューテックスはカーネルの中心核が解放する。

2段目はカーネルのレイヤの状態を中途半端に残すおそれがある。止めたタスクが持っていたミューテックスが守っていたデータは、変更の途中のまま次のタスクに渡る。コンソールには、解除した待ちの数、呼出しの中で止めたタスクの数、そのうちミューテックスを持っていたものの数を出す。呼出しの中で止めたタスクがあったプロセスは、回収するときにアドレス空間とページを解放しない(`keep_space`)。呼出しが始めたデバイスの転送が後からそのページに書き込むことがあり、解放したページがほかに使われていると、その内容を上書きしてしまうためである。そのページは失われる。こうした代償があるので、2段目は強制終了を2度求めたときにだけ使う。システムに必要なプロセスは、2段目でも終わらせない(`E_OACV`)。

### 5.5.5 デスクトップの立ち上げ直し

基本文章編集、基本図形編集、キャビネット、仮身一覧、ディスク修復、スライドなどはプロセスではなく、デスクトップのカーネルのタスクの中で動く。これらが止まるとデスクトップごと止まり、プロセスとしては終わらせられない。そこで、止まったデスクトップを立ち上げ直す手段を設ける。

デスクトップが止まったことは、主ループの監視(4.7.2)で知る。主ループが10秒回ってこないと、コンソールにタスクが止まっている場所を出す。この状態でShift+Pauseを押し、対象のプロセスがないとき(最前面がデスクトップのウインドウ)は、「デスクトップがN秒応答していません。もう一度Shift+Pauseを押すと立ち上げ直します。保存していないM個の文書(名前、…)の変更は失われます」と出す。保存していない文書は、デスクトップのウインドウの変更のフラグ(`dirty`)を、ロックを使わずに読んで数える。15秒以内にもう一度押すと立ち上げ直す。画面に出せないとき(5.5.3)もこの文はコンソールに出るので、2度押しで確定できる。強制終了のウインドウの〈デスクトップを立ち上げ直す〉は、同じ内容を警告のパネルで尋ね、〈立ち上げ直す〉で立ち上げ直す(5.5.3)。こちらはデスクトップが止まっていなくても使える。

立ち上げ直しは次の順に行う。

1. `fq_task`が、デスクトップのタスクと、デスクトップのコードから始まるカーネルのタスク(プログラムを起動するタスク、ディスクの検査、実時間制御TADの再生部など)を休止状態にする。デスクトップのコードは、リンカスクリプトがまとめて置いた範囲(`__dt_text_start`から`__dt_text_end`)で見分ける。タスクが持っていたミューテックスは中心核が解放する。主ループの監視も止める。
2. `fq_work`が、それらのタスクが開いたウインドウ(ウインドウマネージャが開いたタスクを`mktsk`に記録している)を、その中のパネルとメニューとともに閉じ(`knl_wm_tsk_end`、`knl_pn_wins_gone`)、作ったメニュー(`knl_mn_tsk_end`)と開いた実身のキー(`knl_ob_tsk_end`。実身のレイヤがカーネルのキーを開いたタスクを記録している)を閉じる。ドラッグ中の枠、拡大鏡、ポインタの形も元に戻す。デスクトップのタスク以外は削除し、デスクトップのタスクは次の立ち上げ直しまで休止状態のまま残す。デスクトップがほかのタスクに依頼した処理の応答が、後からそのスタックに書き込まれることがあるためである。
3. デスクトップがメモリに持っていた文書(`om_store`)を捨てる。保存していない変更はここで失われる。
4. デスクトップの変数を、マシンが起動したときの値に戻す。リンカスクリプトは、デスクトップの各ファイル(`application/desktop`、`cab`、`doc`、`fig`、`lib/librtad`)の初期値のある変数と0で始まる変数を、それぞれ1か所にまとめて置く。強制終了は、ウインドウの初期化の時(デスクトップがまだ動いていない時)に初期値のある変数のコピーを取っておき、ここで書き戻し、0で始まる変数を0にする。画面の試験の駆動(`dtuitest.c`)は範囲に入れず、立ち上げ直しをまたいで動き続ける。かな漢字変換(`application/kconv`)と単語辞書(`lib/libudic`)も範囲に入れない。変換エンジンは起動に時間がかかり、大きなメモリを持つので、立ち上げ直しても止めずに使い続ける。変換エンジンへの依頼の順番はミューテックスで取り、止めたタスクが持ったままにならないようにする。止めたタスクの依頼への応答が後から来ても、依頼ごとのトークンで今の依頼の応答と見分ける(`kc_call`)。
5. `dt_start`でデスクトップを起動する。デスクトップは最初のキャビネットと、自動で開く設定のウインドウを開き直す。起動時のディスク修復の結果の表示は、立ち上げ直した後には出さない(`knl_fq_restarts`)。

プロセスは止めず、そのまま残す。プロセスのウインドウはプロセスのタスクが開いたものなので閉じない。描画の記録を持つウインドウの描画も、新しいデスクトップが描画のコールバック関数(`wm_obj_painter`)を設定し直した後は続く。プロセスがデスクトップに依頼を書く実身(依頼のキュー)は名前で探すので(`DT_REQ_NAME`)、新しいデスクトップが同じ実身を開き直せば依頼は届く。ただし、止まる前にデスクトップへ出した依頼の応答を待っているプロセスには応答が返らない。そのプロセスは強制終了で終わらせる。

立ち上げ直しで戻らないものがある。デスクトップの変数が指していたヒープ上のメモリ(編集中の文書の取消し用のコピーなど)と、デスクトップが開いた描画環境は解放しない。止まった時点で中身が整っている保証がないので、たどって解放するとおかしくなったデータに触れるおそれがあるためである。立ち上げ直すたびにその分のメモリが失われる。かな漢字変換のセッションも、止めたデスクトップが開いていたものは閉じない。また、デスクトップがTSFSのボリュームの書込みのロック(セマフォ)を持ったまま止まっていた場合、中心核はセマフォを解放しないので、そのボリュームは使えないままになる。デスクトップの変数を書き戻す瞬間に、別のタスクがデスクトップのコード(描画のコールバック関数など)を実行していると、その処理は初期値に戻った変数を見る。

### 5.5.6 試験

`tests/ktest/ktest_fq.c`(グループ`fq`)が、デスクトップを動かした状態で、キーとポインタを入力のレイヤに入れて次を確認する。プロセスのウインドウが最前面のときのShift+Pause。解放のイベントが失われた押下が2秒間は押し続けとみなされ、その後は新しい押下になること。デスクトップの主ループを止めた状態でのShift+Pauseとメッセージ行の表示。デスクトップを止めたままCtrl+Shift+Pauseでウインドウを開き、入力がウインドウに渡ること、キーで選んだシステムのプロセスはShift+Pauseでも拒否し、ウインドウのないプロセスは〈強制終了〉で終わらせ、Escで閉じること。試験が実身のレイヤのロックを持ち、その待ちでシステムコールの中に止まったプロセスが、1度目のShift+Pauseでは「終了の途中」になり、2度目にその場で止められること。シリアルポートの読出しの待ちが解除されて戻ること。デスクトップが管理者のパスワードのパネルを出している間のShift+Pauseが依頼したプロセスを終わらせること、依頼の処理中に開いたウインドウが依頼したプロセスのものになること。システムのプロセスを拒否すること。デスクトップを止めてShift+Pauseを2度押すと立ち上げ直り、プロセスとそのウインドウが残り、立ち上げ直した後もShift+Pauseが機能すること。ウインドウの〈デスクトップを立ち上げ直す〉と、尋ねるパネルの〈立ち上げ直す〉で立ち上げ直し、ウインドウが残ること。画面の操作は`tools/tests/ui_fq.steps`(`tools/ui_run.py`)で、Shift+Pause、一覧からの終了、右ボタンのメニュー、尋ねるパネル、立ち上げ直しをスクリーンショットとともに確認する。試験の間、デスクトップの主ループを止めるフラグ(`dt_test_stall`)を試験だけが立て、止まったとみなす時間を1.5秒に縮める。「前面にプログラムが無い」場面は、試験が自分で開いたシステムのウインドウ(どのプロセスも作っていないもの)を前に出して作る。デスクトップの最初のウインドウは仮身一覧のプロセスのウインドウなので、この場面には使えない。管理者のパスワードのパネルの試験だけは、パネルが載る最初のウインドウを前に出す(`dtadmin.c`の`admin_host`)。デスクトップの起動のあとと立ち上げ直しのあとは、起動時に自動で開いたものが描き終わった知らせ(コンソールの`TessronOS desktop: settled`。デスクトップはループを始めるたびに一度出す)を待ってから、ウインドウを前に出す。それより前に出したウインドウは、あとから開く最初のウインドウや自動起動のウインドウの後ろになるためである。ほかに非同期に起きることも、時間で待たずにイベントを待つ。例外のダイアログは、デスクトップがそのウインドウを自分のダイアログとして持つまで(`dt_fault_wid`)待つ。パネルを閉じたことは、`desktop: the administrator's rights for process N: not asked`の行と、その後にループが1周進んだこと(依頼の処理の最後の`knl_wmobj_act_for(0)`が済んだこと)で確認する。終わったプロセスのウインドウは、消えるまで待つ。

### 5.5.7 親と一緒に終わるプロセス

子のプロセスは、親が終わっても終わらない(親の`TS_MSG_CHILD_EXIT`と、プロセスの実身の`OB_E_EXIT`で知るだけである)。ブラウザのレンダラのように、親がいなくなったら意味のない子は、親と一緒に終わるように指定する。LinuxのPR_SET_PDEATHSIGに当たる。

指定のしかたは次の3つで、どれも同じフラグ(`withpar`)を立てる。

| 方法 | 指定 |
| --- | --- |
| 作るとき(`ts_cre_prc`、`ts_cre_prc_obj`) | `T_CPRC.prcatr`に`TS_PRC_WITHPARENT` |
| 作るとき(POSIXのプロセス、`ts_spn_prc`、`ts_spn_obj`) | `T_SPAWN.flags`に`TS_SPN_WITHPARENT` |
| プロセスの実身として作るとき(`ob_cre_obj`) | メタデータ`{"tessronos":{"process":{"withParent":true}}}` |
| 作った後 | プロセスの実身のキー(`OB_OP_ATRWR`)で`ob_set_atr`に同じメタデータを渡す。`false`で外す |

プロセスの実身の属性(`ob_get_atr`)には、`tessronos.process.withParent`として今の値が出る。フラグは親がプロセスのときだけ意味を持つ。カーネルが作ったプロセスでは無視し、作った後の指定は`E_OBJ`になる。親が回収されてinitの子になった後の指定も`E_OBJ`である。

フラグを立てると、そのときの親の番号と世代(`par_pid`、`par_gen`)を覚える。親が終わると(`prc_finish`)、親を終わらせたタスクがカーネルのタスク`prc_reaper`をウェイクアップさせ、`prc_reaper`が、覚えた親が終了を求められたか、もういない子をすべて`ts_ter_prc`(`TS_ABORT_TERM`)で終わらせる(`prc_end_with_parents`)。コンソールには`TessronOS: pid 子 ends with its parent pid 親`と出す。親を終わらせたタスクの上で子を続けて終わらせると、孫まで続くときにそのタスクのスタックの上で終了の処理が入れ子になるので、`prc_reaper`に任せる。子が終わればまた`prc_reaper`がウェイクアップし、孫が終わる。フラグを立てたときに親がすでに終了を求められていれば、すぐに`prc_reaper`をウェイクアップさせる。

終わらせ方は`ts_ter_prc`と同じなので、子がシステムコールの中にいれば、呼出しから出たところで終わる。終了コードは`TS_ABORT_TERM`で、`lib/libcxxrt`の`waitpid`ではSIGKILLで終わったことになる。

`lib/libcxxrt`は、ChromiumのPOSIXの`base::Process`が使う呼出しを次のように対応させる。シグナルの番号はLinuxと同じである。

| 呼出し | 対応 |
| --- | --- |
| `kill(pid, 0)` | `ts_ref_prc`で有無を返す(無ければ`ESRCH`) |
| `kill(pid, SIGKILL)`など | SIGKILL、SIGTERM、SIGINT、SIGHUP、SIGQUIT、SIGABRTは`ts_ter_prc`(`TS_ABORT_TERM`)。終了の途中のものは0を返す。ゲートが、プロセスの実身を削除できる者か親にだけ許す(`E_OACV`は`EPERM`)。ほかのシグナルは`EINVAL` |
| `waitpid(pid, &st, opt)` | 子を番号で`ts_wai_prc`で待って回収する。`WNOHANG`では待たず、動いていれば0を返す。`pid`が-1と0以下(どの子か、グループ)は`EINVAL`。`ts_wai_prc`はどの子だったかを返さないためである |
| 状態の値 | 終了コードが0以上なら`code << 8`、`TS_ABORT_TERM`などの負の値はSIGKILL、`TS_ABORT_FAULT`はSIGSEGV、`TS_ABORT_ILL`はSIGILLとして`WIFSIGNALED`で読める |
| `getppid` | `ts_ref_prc`の`ppid` |

`tests/ktest/ktest_shm2.c`(グループ`shm2`)の`test_with_parent`が、`tests/uprog/cxxprog.cc`の`pdp`の動作で確認する。親は4つの子を作り、1つは`TS_PRC_WITHPARENT`で、1つは作った後にプロセスの実身の属性でフラグを立て、1つは`kill`と`waitpid`で終わらせて回収し(`WNOHANG`で0が返ること、状態がSIGKILLで読めること、回収した後の`kill(pid, 0)`が`ESRCH`になること)、1つは何もしない。親が終わるとフラグを立てた2つが`TS_ABORT_TERM`で終わり、残りの1つは動き続ける。

### 5.5.8 プロセスの役割

ひとつのプログラムがいくつものプロセスで動くとき(ブラウザのレンダラ、ネットワークのプロセス、GPUのプロセス)、プロセスの名前はどれもプログラムの実身の名前になり、見分けられない。そこで作る側は、プロセスの役割を付けられる。プロセスの実身として作るときのメタデータ`{"tessronos":{"process":{"role":"レンダラ"}}}`か、作った後の`ob_set_atr`で同じメタデータを渡す。空の文字列で外す。役割はUTF-8で31バイトまで持つ(`TS_PRC_ROLE`、文字の途中では切らない)。

人に見せるプロセスの名前(`knl_prc_name`、`knl_prc_name_dup`、`knl_prc_flt_name`)は、役割があればプログラムの名前の後に括弧で付けて「ブラウザ(レンダラ)」とする。名前が長いときは、役割が入るように名前の方を切る。異常終了の記録(`T_PRCFLT`)は終わったときの役割を`role`にコピーするので、「プログラムの異常終了」のパネルにも役割が出る。カーネルの中からは`knl_prc_set_role`で付ける。

## 5.6 システムコール

EL0からカーネルを呼ぶにはSVC命令を使う。レジスタ`x8`に機能コード、`x0`から`x7`に引数を置いて`svc #0`を実行すると、`x0`に戻り値が返る。x64では`syscall`命令を使い、機能コードを`rax`に置く(4.8)。機能コードは上位16bitがクラス、下位16bitがクラス内の番号である。

| クラス | 接頭辞 | 内容 |
| --- | --- | --- |
| 0 | `tk_` | T-Kernelのシステムコールのうち、プロセスに許可するもの |
| 1 | `ts_` | プロセス、メモリ、プロセスメッセージ、単調時刻、UUID、乱数 |
| 2 | `fs_` | ファイル |
| 3 | `dt_` | カレンダ |
| 5 | `so_` | ソケット |
| 6 | `tm_` | デバッグ用のコンソール出力 |
| 7 | `ob_` | 実身 |
| 8 | `dp_` | 自分のウインドウへの描画 |
| 9 | `wm_`、`mn_`、`kc_` | ウインドウ、メニュー、かな漢字変換、外観設定テーブル |
| 10 | `gp_` | GPU(13.5) |
| 11 | `sr_` | シリアルポート |
| 12 | `us_` | プログラムのUSBデバイス |

クラス4(プログラムのロード`pm_`)は番号だけを予約してあり、まだ使っていない。

ポインタを受け取るシステムコールは、どのクラスでもクラスごとのラッパを通る。ラッパはまず、ポインタがプロセス自身のページを指し、カーネルが書き込むものは書込み可能であることを`knl_prc_user_ok`で確認し、満たさなければ`E_MACV`(`fs_`では`EX_FAULT`)を返す。カーネルが中身を見て判断するもの(構造体、名前、パス、パスワード、保護情報など)はカーネルのメモリへコピーしてから使い、プロセスが途中で書き換えても判断が変わらないようにする。戻り値はカーネルのメモリで作ってから書き戻す。カーネルが運ぶだけのデータ(ファイルや実身のレコード、ソケットで送受信するバイト列)は、確認した後、置かれた場所のまま使う。プロセスのメモリの読み書きは、コピーも置かれた場所のままの使用も、PANを外すインタフェース(4.6.1)を通してだけ行う。

制限付きのプロセス(5.9)は、使えなくしたグループの呼出しを、SVCゲートが表を引いて呼び出す前に拒否する。

システム全体に影響するシステムコール(時刻とタイムゾーンの変更、ネットワークインタフェースの設定、ボリュームの取り付けと取り外し、外観設定テーブル、キー配列)は、付録Aの権限の表が求める権限を持つプロセスだけが呼べる。SVCゲートが呼び出す前に表を引き、権限がなければ`E_OACV`を返す。管理者はすべての権限を持つ。システムプロセスのタスクは表を引かない。

プロセス側の呼出しのインタフェースは`lib/libts`にある。`svc_stub.S`が各システムコールのスタブを、`crt0.S`がプログラムのスタートアップを受け持つ。一覧は付録Aにある。

### 5.6.1 入口と出口でロックを取らない

システムコールの入口と出口では、システム全体のロックを取らない。以前は、プロセスの表のロック(`prc_mtxid`、T-Kernelのミューテックス)を、呼出しごとに3〜4回取っていた。ファイル、実身、描画、ウインドウの呼出しの入口と出口(`knl_prc_call_enter`、`knl_prc_call_leave`)、ポインタの確認(`knl_prc_user_ok`)、呼出し元のプロセスIDを調べる`ts_get_pid`である。プログラムを18個ほど起動し、それぞれが20msごとに通知をポーリングする状態では、ほとんどの呼出しがこのロックを待った。QEMU virtの4コアで10秒間に、システムコールが4288回、ロックを取った回数が3261回で、そのうち3254回が待った。システム環境設定を開いてから準備ができるまでに110秒かかった。

今は次のようにしている。

- 呼出し元のプロセスとその制御ブロックは、呼び出したタスクが動いている間は消えない。制御ブロックを解放するのは、そのプロセスのタスクと空間を片付けた後だからである。そこで`ts_get_pid`と`knl_prc_ending`は、タスクの`TTBR0`から制御ブロックを求めるだけで、ロックを取らない。
- `knl_prc_user_ok`は、自分のプロセスのアドレスを確認するとき(システムコールのラッパが使うのは常にこれ)はロックを取らず、ページテーブルを`knl_pt_entry`と同じく割込みを止めてたどる。ほかのプロセスのアドレスを確認するときだけ、その制御ブロックが消えないようにロックを取る。
- 呼出しの中にいるタスクの数(`incall`)と、終わりかけているかどうか(`ending`)は、アトミック操作(順序は`SEQ_CST`)で読み書きする。入口は数を1つ増やしてから`ending`を見る。終わらせる側(`prc_mark`)は`ending`を立ててから数を見る。同時に起きても、どちらかが必ず相手に気づく。入口が`ending`に気づいたときは、数を戻して`E_DISWAI`を返す。数を戻して0になり、終わらせる側がその呼出しに終わりを任せていたときは、そのタスクが終わりを進めて終わる。出口は数を減らしてから`ending`を見る。ロックを取るのは、終わりかけているとき、カーネルがプロセスの不正なアドレスに出会ったとき、保留したページを解放するときだけである。
- メモリの範囲の変更(`ts_map_mem`、`ts_unm_mem`、`ts_ctl_mem`)は、外したページを必ず保留する。ページテーブルを変えたあと全体のバリアを置いてから、ページをデバイスに貸している呼出しの数(`indma`)を見て、0なら保留したページを解放する。ファイルのレイヤがプロセスのページの物理アドレスをディスクに渡すとき(`knl_prc_dma`)は、呼出しごとに最初の1回で数を増やし、全体のバリアを置いてからページテーブルを読む。ページが外れたのを見るか、数で見つかるかのどちらかになる。後者のページは、貸した最後の呼出しが出るとき(`knl_prc_call_leave`)に解放する。DMAが途中のページに書き込むことはない。タスクのフラグは`svcdma`で、呼出しから出て`svcin`が0になるときに外す。
- 以前は、`indma`でなく`incall`、つまりファイル、ソケット、実身、描画、ウインドウ、GPUのどれかの呼出しの中にいるタスクの数を見ていた。ソケットを`poll`で待つ呼出しやイベントを待つ呼出しもページを保持することになり、そうしたタスクがいつもどれか中にいるプロセスでは、外したページがプロセスの動いている間ずっと解放されなかった。ページをデバイスに貸さない呼出しは、プロセスのメモリにプロセス自身のマッピングを通して触れる。外れたページに触れれば、渡されたアドレスの誤りとして扱う(5.5.2)。残すのは貸したページだけでよい(Linuxで`get_user_pages`で固定したページだけが`munmap`の後も残るのに当たる)。試験は`cxx`のグループの`test_churn`で、別のタスクが`poll`で待ち続ける間に、64MBの範囲のページを128回作っては外す(合わせて8GB)。

修正した後、同じ18個の状態の10秒間で、システムコールは25767回(ロックを待たなくなったので同じ時間に多く進む)、ロックは20回、待ちは0回になった。システム環境設定の準備は3.8秒になった。x64ではKLOCK_MODE 3でロックの順番の検査を入れ、4コアで`proc`、`prcobj`、`pan`、`psx`、`smp`、`klk`、`el0`、`svcio`のグループを通した。順番の誤りは0件だった。

アプリケーションも、通知を20msごとにポーリングするのをやめ、通知が来るまでスリープする(11.30)。

| `lib/libbpk`、`libbtbk`、`libtxc`、`libxfu`、`libftp` | 書庫、文字コード、ファイルと実身の変換、FTP |

### 5.7.1 ローカルソケットと記述子の受け渡し

`lib/libcxxrt`の`socketpair(AF_UNIX, SOCK_STREAM)`は、ストリームの対(8.5.1)を作り、両端を開く(`ts_chan.c`)。記述子は`0x3880`からの範囲(512個)で、それぞれが端のキーを持つ。`SOCK_NONBLOCK`、`SOCK_CLOEXEC`、`fcntl`の`O_NONBLOCK`と`FD_CLOEXEC`を覚える。キーは待たない開き方で開き、呼出しごとに待つかを決める。`read`、`write`、`send`、`recv`はレコード1を、`sendmsg`、`recvmsg`はレコード3を使う。`shutdown`は`SHUT_WR`と`SHUT_RDWR`を端の書込みの終わりにし、`SHUT_RD`は何もしない。相手がいなくなった後の書込みは`EPIPE`である(シグナルは出さない)。`AF_UNIX`の`socket`、`bind`、`connect`(名前のついたローカルソケット)はない。`SOCK_SEQPACKET`、`SOCK_DGRAM`の対もまだない(`EPROTONOSUPPORT`)。

`SCM_RIGHTS`で送れる記述子は、実身のキーである記述子だけである。ストリームの端、`memfd_create`のメモリの実身(`ts_memfd_key`)、GPUのPRIMEの記述子(`ts_gpu_fd_key`、BOの実身、8.5.1)、受け取ったキーから作った記述子がそれにあたる。ファイルとネットワークのソケットは送れない(`EBADF`)。受け取ったキーは、何の実身のキーかに応じて記述子にする(`ts_fd_from_key`)。ストリームの端は端の記述子、メモリの実身は`ts_memfd_from_key`、BOはPRIMEの記述子で、ほかの実身はキーを持つだけの記述子になる(さらに送れる)。制御の領域に入りきらなかったキーは閉じ、`MSG_CTRUNC`を立てる。`sys/socket.h`の`CMSG_NXTHDR`は2つ目以降の制御メッセージを返さないが、`sendmsg`はすべての`SCM_RIGHTS`を読む。

Linuxでは`fork`と`exec`で子に記述子が引き継がれる。ここではプロセスを作った後に渡す。

| 方法 | 使い方 |
| --- | --- |
| キーを子に渡す | 親が子を作った後に`ts_chan_give(pid, fds, n)`を呼ぶ。記述子のキーを`ob_dup_key`で子のキーにし、その番号と種類をプロセスメッセージ(`TS_MSG_MAX`に入る20個まで)で送る。子は`ts_chan_take(fds, max, ms)`で受け取る。保護に関係なく渡せるので、段階4のサンドボックスでも使える |
| UUIDで開く | 親が`ts_chan_uuid(fd, uuid)`で端のUUIDを起動の引数に書き、子が`ts_chan_open(uuid)`で開く。同じユーザのプロセスしか開けない(端の保護が`rw-------`)。子が開くまで親は自分の記述子を閉じない |

`epoll_wait`と`poll`の待ち方(`ts_evfd.c`)は次のとおりである。

- 端はカーネルのポールセット(`OB_S_POLL`、8.5.2)で待つ。端を監視する`epoll`は、最初の端を足したときに自分のポールセットを1つ作り、`epoll_ctl`の追加、変更、削除をそのままポールセットへ書く(登録はカーネルが持ち、待つたびに渡し直さない)。ポールセットに渡す値は、記述子の番号と監視ごとの通し番号で、受け取った側は今の監視と照らし合わせ、その間に外した監視の知らせは捨てる。`poll`は、プロセスが持ついくつかのポールセットから1つを借り、全部を外してから今回の端を入れる1回の書込みの後で待つ。
- 端の準備の状態は端の側が変わったときにポールセットのレディリストに入るので、待つ側は1回の`ob_rea_tmo`で、準備のできた端とイベントを受け取る。以前は、端ごとに状態を読み(`ob_rea_rec`)、ポートの知らせでスリープし、ポートを読み尽くし(`TMO_POL`の繰返し)、状態を読み直していた。
- 端のほかのもの、つまり`eventfd`とプロセス内のパイプ(表を見る)、キーを持つだけの記述子、ネットワークのソケット(`so_poll`を待たずに呼ぶ)、ファイルは、スリープする前にプロセスの中で見る。端のない待ちは今までどおり条件変数でスリープする。端のある待ちはポールセットでスリープし、スリープしている間はプロセスの一覧(`kwaits`)に載る。`eventfd`とパイプへの書込みは、それを監視している待ちのポールセットに`OB_PL_WAKE`を書いてウェイクアップさせ、ウェイクアップした側はプロセスの中のものを見直す。`epoll_ctl`と`epoll`を閉じることも、その`epoll`でスリープしている待ちをウェイクアップさせる。ポールセットを作る、ウェイクアップさせる、閉じることは、どれもプロセスのロックの中で行うので、閉じたキーの番号が別の実身に使い回された後に、そのキーを使うことはない。
- レベルトリガが既定で、`EPOLLONESHOT`(1度知らせたら`EPOLL_CTL_MOD`まで知らせない)と、端だけは`EPOLLET`も使える。ChromiumのMessagePumpEpollは、一度きりの監視に`EPOLLONESHOT`を付け、知らせを受けた後に`EPOLL_CTL_MOD`で監視を設定し直す。以前の実装は`EPOLLONESHOT`を無視していたので、設定し直すまでの間も知らせ続けていた。
- 記述子を閉じると、その記述子をすべての`epoll`から外す(Linuxで最後の記述子を閉じたファイルがepollから外れるのに当たる)。端はキーを閉じる前にポールセットから外す。キーを閉じても、別のプロセスへ運んだ端は残るので、外さないと閉じた記述子の知らせが届いてしまうためである。
- ネットワークのスタックはソケットの変化を知らせないので、ソケットとほかのものを一緒に待つときは10ミリ秒(`SOCK_SLICE_MS`)ごとにソケットを見る(ソケットのマネージャは`pol`を持たず、ポールセットに入れられない)。`poll`でソケットだけを待つときは、今までどおりスタックの中で待つ。ソケットの変化をポールセットへ知らせるには、ネットワークのレイヤの変化の知らせ(lwIPの`event_callback`に当たるところ)から`knl_obpoll_tell`を呼ぶ形にする。
- `epoll`の監視の数の上限はなく、倍にして拡張する。1回の`epoll_wait`が端について返すのは32個まで(`OB_PL_MAXEV`)。準備のできた端がそれより多ければ、残りは次の待ちで返る。

試験は`tests/ktest/ktest_chan2.c`(グループ`chan2`)で、カーネルの呼出しで端の作成、読み書き、待たない読み書き、相手の終わり、キーの受け渡しと許可、読まれないキーの解放、知らせを確認し、ポールセット(`test_poll`、`test_poll_wake`)で、レベルトリガ、`OB_PL_ONESHOT`、`OB_PL_ET`、`OB_PL_MOD`、`OB_PL_DEL`、2つのポールセットに入れた1つの端、`OB_PL_WAKE`、相手がなくなったときの`OB_PL_HUP`と`OB_PL_RDHUP`、閉じた端が何も知らせないこと、登録できないキーと許可のないキー、閉じたポールセットが端に何も残さないこと、別のタスクの書込みと`OB_PL_WAKE`で待ちがウェイクアップすることを確認する。その後、`tests/uprog/chanprog.cc`(`/boot/CHANPROG.ELF`)の2つのプロセスで、`socketpair`、`ts_chan_give`、待たない読出し、端と`eventfd`の`epoll_wait`、`SCM_RIGHTS`で運んだ端の読み書き、子が受け取らずに終わった端の解放、子の終わりでの`POLLHUP`、`EPIPE`、`EPOLLHUP`を確認する。子は端を受け取る前に、自分の対で、1つの端を2つの`epoll`に入れたとき、レベルトリガ、`EPOLLONESHOT`、`EPOLLOUT`、`EPOLL_CTL_DEL`、待っている間に別のスレッドが端を足すこと、監視している端を閉じること(何も知らせない)、`epoll`を閉じること(`EBADF`)、`shutdown(SHUT_WR)`での`EPOLLRDHUP`と相手を閉じたときの`EPOLLHUP`、端と`eventfd`の`poll`を確認する(`local_waits`)。終わったときに端もポールセットも1つも残らないことを確認する。

## 5.8 起動の引数と標準入出力

起動の引数は、呼出し元が決める1ページまでのバイト列で、プログラムは`ts_get_arg`で受け取る。中身の形はプログラムと呼出し元の取り決めで、次の2つがある。

| 起動する側 | 引数 |
| --- | --- |
| デスクトップ(仮身を開く、実行メニュー、小物メニュー) | 開く実身のUUID(16バイト)。開く実身がなければ引数なし。コマンド(11.29)を開いたときは、コンソールを起動してコマンドの実身のUUIDを渡す。プログラム実身のメタデータの`tessronos.program.openArg`が`"link"`のプログラムには、開く実身のUUIDに続けて、開いた元の仮身を渡す(`T_PRCOPEN`、下記) |
| コンソール(11.29)、マイクロスクリプトの`PROCESS` | 命令の名前の後ろの単語を空白1つで区切って並べたUTF-8の1行と、終わりの0。単語がなければ引数なし |

`T_PRCOPEN`(`include/ts/dtreq.h`)は、開く実身のUUID(`target`)、元の仮身を持つ実身のUUID(`parent`)、その仮身の識別子(`vobjid`)、開くレコード(`recno`、-1は最初)を並べた構造体である。先頭は16バイトの引数と同じなので、引数のサイズが`sizeof(TS_UUID)`以上かを確認するプログラムはそのまま読める。デスクトップのウインドウの仮身から開いたときと、プロセスのウインドウの仮身から`DT_F_LINK`を付けた依頼(`DT_RQ_OPEN`、11.4)で開いたときに`parent`と`vobjid`が入り、ウインドウ一覧や`DT_F_LINK`のない依頼から開いたときは0である。仮身から開いたときは`fromlink`を立て、その仮身の今の指定(`bgcol`、`wordwrap`、`viewmode`)を入れる。今の指定とは、閉じたウインドウが書き戻した後のもので、親の記録をまだ保存していなくても書き戻した後の形になる。プログラムはこれで、デスクトップのウインドウと同じく、仮身の背景色を用紙にし、文章なら仮身の表示の形と折り返しで開く。構造体の後ろには、起動するプログラムの`applist`の項目の固有データ(11.3)が、終わりの0付きで長さのまま続く。仮身の`applist`の項目のものを先に、なければ実身のものを入れ、どちらにもなければ続かない(引数のサイズが`sizeof(T_PRCOPEN)`のまま)。プログラムは`ts_get_arg(NULL, 0)`で引数のサイズを知ってから読み、`dt_prcopen_data`で取り出す。開く実身がない起動(プログラム実身への仮身を開いたとき)でも固有データがあれば、`target`を0にして渡す。構造体のサイズは変えていないので、前のプログラムも同じに読める。

起動の引数の上限は、どの起動の方法でも`TS_SPN_ARG_MAX`(256KB)で、超えると`E_LIMIT`で起動しない。引数は新しいプロセスの空間のページにコピーするので、そのコピーに使うページの数をリソースとして抑える値である。以前の`ob_cre_obj`の経路は1ページ(4KB)で、固有データのように長さの決まらないものを運べなかった。全部のプログラムに渡さないのは、引数がちょうど16バイトであることを確認するプログラム(コンソールなど)があるためである。開く実身を後から依頼で問い合わせる形にせず起動の引数で渡すのは、起動と問い合わせの間に元の仮身が変わる競合を避け(Linux/BSDのexecに当たる)、デスクトップが起動の時に知っていることをそのまま渡すためである。プログラムは、新たな実身に保存(`DT_RQ_SAVE_NEW`)と、閉じるときのスクロール位置、倍率、折り返しの書き戻し(`DT_RQ_LINK_VIEW`)で、この仮身をデスクトップに示す(11.3)。以前は、原紙箱と小物箱の実身を仮身一覧のプロセスに開かせるための`as`(何として開くか)もあったが、原紙箱と小物箱をそれぞれのプログラムにしたので外した(11.2.1、11.2.2)。

単語のない起動で引数を渡さないのは、デスクトップから起動されるプログラムが、引数があればUUIDとして読むためである。`lib/libcxxrt`の`main`には、引数を単語に分けた`argv`はまだ渡らない(`argv[0]`だけ)。引数を使うプログラムは`ts_get_arg`で読む。

標準出力と標準エラー(記述子1と2)に書いたものは、`lib/libts`、newlibのシステムコールのスタブ、`lib/libcxxrt`のどれでも`tm_putstring`でシステムのコンソールに出る。標準入力(記述子0)を読むと、すぐにファイルの終わりになる。コンソールの小物(11.29)は、コンソールの記録(`tm_log_read`)からこれを読んでウインドウに出す。この形は暫定である。プログラムの出力が、カーネルやほかのプロセスの出力と同じ出力に混ざり、シリアルにも出る。プロセスごとの端末(パイプと擬似端末)ができたら、コンソールの小物はプログラムの標準入出力をそちらにつなぎ替える。コンソールの側で起動、出力、待ち、停止を扱うのは`application/console/con_job.c`だけで、つなぎ替えはこのファイルの中で済む。

POSIXのプロセスを起動する呼出しは2つある。`ts_spn_prc`はパスで指し、objfs(「/」から仮身をたどるツリー)でプログラムの実身を求めてから起動する。POSIXのプログラムが`execve`や`posix_spawn`で使う。`ts_spn_obj`はプログラムの実身(仮身の指す先のUUID)をそのまま起動する。コンソールは、いまいる実身やbinの中で仮身から見つけたプログラムをこれで起動する。パスに変換して求め直すと、いまいる実身がbinでないとき、同じ名前が並んで`名前~2`になるとき、ファイル名(`tessronos.file.name`)が実身名と違うときに、別のプログラムを起動するか、起動できなくなるためである。どちらも、呼んだプロセスの資格で実行の権利(`OB_OP_EXEC`)を調べる。

コンソールから起動するPOSIXのプログラムは、環境の`HOME`を`/home`(キャビネットを仮身で持つ実身「home」)とし、コンソールがいまいる実身から始める。コンソールのいる所は実身(と「/」からたどった実身の並び)で、パスは実身の名前を並べて作る。ファイルのレイヤは、ファイル名を持つ実身をその名前で、同じ名前が並ぶと`名前~2`のように見せるので、作ったパスが同じ実身に届くとは限らない。そこで`ts_lkp_obj`でパスの指す実身を求め、いまいる実身と同じときだけそのパスで始め、違えば`/home`から始める。`getpwuid`の`pw_dir`も`/home`である。以前は`/home/BTRON`で、キャビネットの名前が「BTRON」であることを前提にしていた。

## 5.9 制限付きのプロセス

ブラウザのレンダラのように、信用できないコード(ページのスクリプト)を動かすプロセスは、乗っ取られても利用者の実身、ネットワーク、機器、ほかのプロセスに手を出せないように、システムコールの一部を使えなくする。これをカーネルのSVCゲートで行う(LinuxのChromiumのseccomp-bpfと名前空間に当たる)。定義は`include/ts/sbx.h`、表と判定は`peripheral_kernel/sysman/svc_gate.c`、プロセスの持つ値は`proc.c`にある。

制限は、使えなくするグループの組(ビットの集合)で表す。プロセスは`ts_set_sbx(groups, how)`で自分にグループを追加する。一度追加したグループは外せない(呼んでも追加するだけで、減らす呼出しはない)。制限はプロセスのもので、そのときから全部のタスクに適用される。Linuxのseccompはスレッドごとで、全部のスレッドにそろえるには`SECCOMP_FILTER_FLAG_TSYNC`が要るが、ここでは初めからプロセスの全体である。制限されたプロセスが作った子は、親の組を持って始まる(最初の命令から制限されている)。子はさらに追加できるが、外せない。LinuxのPR_SET_NO_NEW_PRIVSに当たる、制限を持ったまま権限を増やす方法(setuidのような)はTessronOSにないので、別のフラグは要らない。資格(ユーザ)は今までどおりで、制限はそれとは別に、資格が許すことのうち、さらにグループの分を拒否する。

| グループ | 使えなくなるもの |
| --- | --- |
| `TS_SBX_OBJ` | UUIDや名前で実身に届く呼出し。開く(`ob_opn_obj`)、作る(`ob_cre_obj`)、削除、参照、一覧、リンク、UUIDでの保護、名前やシステムの続柄での検索、コピー、ボリュームの参照、`ts_lkp_obj`。パスで指すファイルとフォルダ(`fs_open`、`fs_stat`、`fs_openat`など) |
| `TS_SBX_NET` | ネットワーク(クラス5の`so_`のすべて)と、ソケットの実身を開くこと |
| `TS_SBX_DEV` | 機器。シリアル(クラス11)、USB(クラス12)、デバイスの実身を開くこと(音、カメラ、マイク、入力、ディスク、乱数など) |
| `TS_SBX_GPU` | GPU(クラス10の`gp_`)と、GPUのデバイスの実身を開くこと |
| `TS_SBX_PROC` | ほかのプロセス。作る(`ts_spn_prc`、`ts_spn_obj`、プロセスの実身の作成)、終わらせる、シグナル、待つ、問い合わせる、プロセスメッセージとキーを送る、一覧、プロセスグループとセッションを変える。プロセスの実身を開くこと。自分に向けたもの(`kill(getpid(), 0)`、自分の`ts_ref_prc`など)は使える |
| `TS_SBX_WIN` | ウインドウのレイヤ。描画(クラス8、書体を含む)、ウインドウ、メニュー、かな漢字変換、トレー(クラス9)。ウインドウの実身を開くこと |
| `TS_SBX_SYS` | システムのもの。時刻とタイムゾーンを変える、ボリュームの取り付け、ログインとパスワード、コンソールの記録を読む(`tm_log_read`) |

どのグループにも入らず、制限されても使えるのは、すでに持っているものと自分のものへの呼出しである。メモリの確保と解放(`ts_map_mem`など)、自分のタスクと同期オブジェクト(`tk_`、pthreadのミューテックスと条件変数。競合のない間はカーネルを呼ばない)、時刻、乱数(開いておいた乱数のキー)、持っている実身のキー(渡されたストリームの端、メモリの実身、BOの実身)への読み書き、マッピング、通知、閉じること、開いておいたファイルの記述子への読み書き、自分のプロセスメッセージを受けること、コンソールへの出力である。

名前のない実身(ストリームの対、メッセージキュー、ポールセット、`OB_F_TRANSIENT`のメモリ)は、作って開く1つの呼出し`ob_cre_key`で作る。以前の`lib/libcxxrt`は`ob_cre_obj`でUUIDを受け取ってから`ob_opn_obj`で開いていたので、UUIDで開くことを拒否すると`memfd_create`も`socketpair`もできなかった。Linuxの`memfd_create`と`socketpair`が名前でなく記述子を返すのと同じく、`ob_cre_key`は名前のない種類だけを受け付け(名前、メタデータ、保護、ボリュームの指定、固定のUUIDのあるものは`E_PAR`)、キーを返す。ストリームの対は両端のキーを返す。`lib/libcxxrt`の`memfd_create`、`socketpair`、`epoll`と`poll`のポールセットはこれを使う。ポールセットへの登録と待ちは持っているキーへの読み書きなので、制限付きのプロセスでもグループに関係なく使える。

グループの外の呼出しを判定するのは、SVCゲート(`knl_svc_gateway`)である。クラスの全体が1つのグループのもの(`so_`、`dp_`、`wm_`、`gp_`、`sr_`、`us_`)はクラスで決め、ほかは機能コードの表(`sbx_calls`)を引く。表を引くのは制限のあるプロセスだけで、制限のないプロセスの呼出しは、制御ブロックの1ワードを読むだけである。実身を開くことと作ることを許した組(下のネットワークのプロセス)では、開く実身の種類で`ob_opn_obj`と`ob_cre_obj`をさらに分ける(`obsvc.c`、`knl_sbx_may`)。デバイスは`TS_SBX_DEV`(GPUのデバイスは`TS_SBX_GPU`)、プロセスは`TS_SBX_PROC`、ウインドウは`TS_SBX_WIN`、ソケットは`TS_SBX_NET`のものである。

使えないグループの呼出しは、プロセスを終わらせる。終了コードは`TS_ABORT_SBX`で、`lib/libcxxrt`の`waitpid`ではSIGSYSで終わったことになる(Linuxのseccompの`SECCOMP_RET_KILL_PROCESS`に当たる)。コンソールには`TessronOS: pid 12 breaks its sandbox (7f): ob_1 (call 70001, group 1), and ends`のように、組、クラスの接頭辞と番号、機能コード、グループを出す。`how`に`TS_SBX_REFUSE`を与えると、終わらせずに`E_OACV`(ファイルでは`EX_PERM`、POSIXの関数では`EPERM`)で拒否し、`OB_DENY_LOG`のビルドではコンソールに`!OACV! pid=12 "プログラム名" sandbox want=機能コード may=グループ`の行を、プロセスと呼出しごとに1度出す(`SECCOMP_RET_ERRNO`に当たる)。試験と、プログラムが何を呼ぶかを調べるためのものである。拒否する形から終わらせる形には変えられるが、終わらせる形で制限したプロセスは、拒否する形に戻せない(`E_OACV`)。

制限は`ts_get_sbx`で読める(グループと、拒否する形なら`TS_SBX_REFUSE << 16`)。プロセスの実身の属性(`ob_get_atr`)にも`tessronos.process.sandbox`としてグループが出る。

拒否した呼出しの回数は、どのビルドでも数える。制御ブロックに、拒否した合計、グループごとの回数(7つ)、最後に拒否した呼出しの機能コードを持ち、拒否するたびにアトミックに加算する(`knl_prc_sbx_count`)。終わらせる形で、終わらせた呼出しも数える。子には引き継がず、0から始まる。回数は属性`tessronos.process.sandbox_refused`で読める。値は文字列で、`total=3 obj=1 net=0 dev=2 gpu=0 proc=0 win=0 sys=0 last=70001`のように、合計、グループごとの数、最後の機能コード(16進)を並べる。終わったプロセスも、回収されるまでは読める(`knl_prc_sbx_refused_of`)。

拒否する形では、`OB_DENY_LOG`でない通常のビルドでも、コンソールに次の行を出す。プロセスごとに、グループが初めて拒否されたときだけ1行ずつ(最大7行)で、そのあとは数えるだけである。

`TessronOS: pid 12 "プログラム名" is refused by its sandbox (7f): ob_1 (call 70001, group 1); further refusals are counted`

プロセスが終わるときは、拒否した回数が0でなければ、合計とグループごとの数を1行出す(`TessronOS: pid 12 "プログラム名" ended with 3 calls refused by its sandbox (obj 1, net 0, ...)`)。実機で、終わらせる形に切り替える前に、拒否された回数が0であることを確認するためのものである。
プロセスの種類ごとの組は、`include/ts/sbx.h`に名前を付けて置く(14.13.9)。

| 組 | 使えないグループ | 使えるもの |
| --- | --- | --- |
| `TS_SBX_RENDERER` | すべて | 持っているキー、名前のない実身、メモリ、スレッド、時刻 |
| `TS_SBX_RENDERER_GPU` | GPUの他すべて | 上に加えて`gp_`。GPUのプロセスができるまでの移行用 |
| `TS_SBX_RENDERER_STORE` | ほかのプロセス、システム | 上に加えて、UUIDや名前で実身を開くこと、機器、GPU、ウインドウ、ネットワーク。ページの保存域のストア、音・マイク・カメラのデバイスの実身、画面やウインドウの共有とトレイ、ピア接続などのソケットをレンダラが自分で開く間の移行用。グループは、その処理がレンダラの外に出るたびに組へ戻す(14.13.9) |
| `TS_SBX_GPUPROC` | GPUの他すべて | `gp_`と、渡されたメモリの実身 |
| `TS_SBX_NETWORK` | 機器、GPU、ほかのプロセス、ウインドウ、システム | ソケット、ストレージの実身(ストア) |

`TS_SBX_RENDERER_GPU`と`TS_SBX_GPUPROC`は今は同じグループだが、使う側の意図が違うので名前を分けてある。ネットワークのプロセスは、資格が許すストレージの実身をすべて開ける。ストアの実身の下だけに絞ること(Linuxのlandlockや、`openat`の起点を絞る形に当たる)は、まだない。

`lib/libcxxrt`の`ts_sandbox_enter(groups, how)`は、初めて使うときに名前で開くもの(`getrandom`が読む乱数の実身のキー)を先に開いてから`ts_set_sbx`を呼ぶ。

試験は`tests/ktest/ktest_sbx.c`(グループ`sbx`)で、`tests/uprog/cxxprog.cc`の`sbx`の動作を使う。レンダラの組では、メモリ、スレッドとその待ち、時刻、乱数、名前のないメモリの実身とストリームの対の作成と読み書き、制限の前に開いたものが使えること、UUIDと名前での実身、パスでのファイル、ソケット、シリアル、USB、GPU、ウインドウ、ほかのプロセスへのシグナルとキー、コンソールの記録、時刻の設定が拒否されること、組が減らないことを確認する。ネットワークの組では、ストレージの実身を作って開いて書いて消せること、ソケットを作れること、デバイスの実身、GPU、USB、ほかのプロセスへのシグナル、プロセスの作成が拒否されることを確認する。終わらせる形では、UUIDで開いたプロセスが`TS_ABORT_SBX`で終わること、拒否する形に戻せないことを確認する。引き継ぎでは、制限した親の子が親の組で始まり(属性の`sandbox`)、追加できて外せず、拒否された呼出しで終わり、親の`waitpid`でSIGSYSと読めることを確認する。拒否した回数は、レンダラの組で全グループが数えられること、終わらせる形で終わらせた呼出しが1回と機能コードで数えられること、引き継ぎで子の属性`sandbox_refused`が0から始まり1回の拒否で`net=1`になることを確認する。
