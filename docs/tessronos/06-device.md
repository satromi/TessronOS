# 第6章　デバイス

## 6.1 デバイス管理

デバイスは、μT-Kernel 3.0のデバイス管理機能で扱う。ドライバは`tk_def_dev`でデバイスを名前で登録し、利用側は`tk_opn_dev`で開いて`tk_rea_dev`、`tk_wri_dev`で読み書きする。パーティションを持つディスクは、パーティションをサブユニットとして見せる(`sda`がデバイス全体、`sda0`が第1パーティション)。パーティションはGPTの項目か、MBRの基本区画と拡張区画の中の論理区画(EBRの連なり)である。GPTは区画表の項目の数(4096まで)を見て、使われている項目を1台に255まで、MBRは基本区画と論理区画を合わせて255まで持つ(`BLK_MAX_PART`)。サブユニットの番号は0から254で、名前は`uda254`のようになる。区画表の無いディスク(スーパーフロッピー)は全体が1つのボリュームである。区画表を書き換えた後で、ディスク全体のデバイスに属性`TDN_PARTSCAN`を書き込むと、SD、virtio-blk、USBのディスクのドライバが区画表を読み直す。ドライバは、広がった区画の大きさと足された区画を、すでにある区画の番号を変えずに反映し、デバイスを登録し直す(7.7)。登録できるデバイスは192、同時に開けるデバイスは4096、同時の要求は256、同時に扱うディスクは160である(7.6)。

登録するデバイスは次のとおりである。

| 名前 | 種類 | ハードウェア |
| --- | --- | --- |
| `sda` | ディスク | SDカードかeMMC(SDHCI) |
| `vblka`、`vblkb` … | ディスク | virtio-blk(QEMU) |
| `nvmea`、`nvmeb` … | ディスク | NVMe(x64) |
| `sataa`、`satab` … | ディスク | AHCIの先のSATAのディスク(x64) |

virtio-blk、NVMe、SATAのディスクは、見つけた順に名前が付き、`z`の次は`vblkaa`、`nvmeaa`、`sataaa`のように2文字目が付く。ドライバの表は見つけたときに1つずつ作り、満ちたら倍にして伸ばすので、台数の上限は無い(前はvirtio-blkとNVMeが4台、SATAが6台までで、それより後のディスクは見えなかった)。
| `uda`、`udb` … `udz`、`udaa` … | ディスク | USBマスストレージ。接続した順に、空いている一番小さい番号で名前が付く。`udz`の次は`udaa`、`udab` … `udaz`、`udba`のように、表計算の列の名前と同じ付け方で続く。表の上限は無く、名前がデバイス名の8バイトに収まる`ud`と英字3文字まで(約18000台) |
| `neta` | ネットワーク | Ethernet、virtio-net、USBのLAN、Wi-Fiのうち、使うと選んだもの(`netsel.c`)。1回の読み書きが1フレーム |
| `snda` | サウンド | USBオーディオ、RP1のI2S、HDMI(Raspberry Pi 5)、Intel HDA(x64) |
| `sera`、`serb` … | シリアル | PL011とRP1のUART(Arm)、16550のCOM1〜COM4(x64)。コンソールのポートが`sera`。プロセスはSVCのクラス11で使う(6.2の終わり) |
| `cama` | カメラ | USBビデオクラスのカメラ。`cama0`から`cama3`が来た順のカメラ |

次のものはデバイス管理には登録しない。このうち実身があるものは、デバイスマネージャが実身として見せ、プログラムは実身を通して使う(8.4)。

| もの | 扱い | 実身 |
| --- | --- | --- |
| コンソールのUART | カーネル内の関数(`tm_`) | なし(起動の最初から使う) |
| RTC | カーネル内の関数。時刻は時計の実身で見せる | 時計 |
| 乱数 | 実身。カーネル内の利用者は`ts_get_random` | 乱数(`OB_S_CHAR`) |
| 画面 | 実身。描画の層は`ts_disp_`を直接使う | 画面(`OB_S_DISPLAY`) |
| USBのキーボードとマウス | 実身。ウインドウマネージャは`ts_hid_read`で受け取る | インタフェースごとのキーボード、ポインタと、入力(`OB_S_INPUT`) |
| GPIOのバンク(Raspberry Pi 5、4) | 実身。ドライバがピンを機能に割り当てる処理は`gpio_`、`rp1_gpio_`を直接使う | バンクごと(`OB_S_GPIO`) |
| USBデバイス(ハブを含む) | 実身 | デバイスごと(`OB_S_USB`) |

デバイスは実身としても扱える。デバイスの実身に対するレコードの読み書きが、そのままデバイスの読み書きになる(第8章)。デバイスのUUIDは最初に検出したときに生成してデバイス箱に記録するので、次回の起動でも同じ実身として見つかる。USBメモリのように抜き差しのあるデバイスの接続・切断、メディアの挿入・取出しは、そのデバイスの実身とデバイス一覧の実身へのイベントとして通知される。ディスクのボリュームは、デバイスの実身を通して`fs_attach_dev`で要求すると`/media`の下にデバイス名でマウントされ、デバイスが切断されるとアンマウントされる。fimpの名前を渡さなければ、区画の先頭の中身から形式を見分けてマウントする。ディスクの実身の属性`tessronos.format`に、見分けた形式(`kind`)、ラベル、マウントするfimpが現れる(7.6)。媒体が抜かれると、その区画に取り付けてあった実身のボリュームも去ったものになる。

PCIeのコンフィギュレーション空間はECAMで読み、列挙時にBARを割り当てる。Raspberry Pi 5では、RP1が接続されたPCIeのルートコンプレックスをカーネルが自前で初期化し、RP1のアドレスウインドウを通してUSB、Ethernet、GPIO、UARTにアクセスする。PCIeデバイスのMSIはエッジトリガで受け付ける。Raspberry Pi 4系のルートコンプレックスは、コンフィギュレーション空間を索引のレジスタと4KBのウインドウで見せるので、`pcie_rc.c`が読み書きの関数を共通の列挙(`kernel/sysman/pcie.c`、`PCIE_CFG_BOARD`)に渡す。BARのPCIeのアドレスとCPUから見たアドレスは外向きのアドレスウインドウの分だけずれる(`PCIE_BAR_CPU_OFFSET`)。MSIは使わず、INTAをレベルトリガで受け付ける。x64では、構成空間をACPIのMCFGが言うECAMで読み、バス番号とBARはファームウェアが割り当てたものをそのまま使う(`PCIE_KEEP_FW_BARS`)。MSIとMSI-XはLocal APICに送らせる(3.10.3)。

装置の割込みは`ts_pcie_irq_alloc`で1つ取る。MSI-X、MSI(x64だけ。`ts_pcie_msi_plain_alloc`)、装置の割込みの線(INTx)の順に試し、取れたものを返す。どれも取れなければ0を返し、ドライバはポーリングで動く。LinuxやBSDと同じ順である。x64のINTxは、ACPIの`_PRT`が示すGSIを使う。ルートバスから装置までのブリッジの道筋をたどり、`_PRT`を持つブリッジがあればその表を引く。持たないブリッジでは、PCIのブリッジの規格どおりにスロットの番号でピンをずらして、1つ上のバスで引く。リンクの装置(`\_SB_.LNKA`など)を指す項は、そのリンクの今の`_CRS`の割込みを使う。ファームウェアが設定していないリンクは設定しない。INTxはレベル、アクティブローとし、ほかのハンドラか装置がすでに持つGSIは取らない(ドライバのハンドラは自分の装置だけを見るので、共有しない)。Raspberry Pi 4系は、メッセージの送り先が無いのでINTAを使う。どの方式になったかと、手前の方式が取れなかった理由(`E_NOSPT`はその能力が無い)を、`pcie: 00:14.0 8086:9d2f: interrupt by MSI (83); MSI-X -9, MSI 0`の形でコンソールに出す。どの方式でも、割込みの受け先(`SetIntTarget`、装置の実身の`irq.cpu`、MSIの振り分け、4.5)はほかの割込みと同じに効く。MSIは能力のアドレスの下位の語を、MSI-Xは表の項を、INTxはIOAPICの項を書き換える。xHCI(`usbman.c`)とIntelのLAN(`e1k.c`)がこれを使う。ThinkPad X1 Yoga 第3世代のチップセットのxHCI(8086:9D2F)、ThunderboltのxHCI(8086:15D4)、I219(8086:15D7)はMSIしか持たないので、前はポーリングで動いていた。ドライバは、来た割込みの数を、最初の1回とその後10倍ごとに`usb: controller 0: 100 interrupts arrived (MSI, interrupt 83, PRC 1)`、`e1k: 100 interrupts arrived (...)`の行でコンソールに出す。割込みを持つのに起動から10秒たっても1回も来なければ、`no interrupt arrived in 10 s`の行を出す。QEMUのq35で、MSI-X(e1000e)、MSI(`qemu-xhci`の`msix=off,msi=on`)、INTx(`msix=off`の`qemu-xhci`とe1000。q35の`_PRT`はリンクの`GSIA`〜`GSIH`を指す)を確かめた(試験`pcdev`の`test_irq`)。

ドライバが装置を使い始めるときの入口は`ts_pcie_enable`の1つだけである。装置のメモリの応答とバスマスタを有効にし、あわせて、ホストからその装置までの間のブリッジ(ルートポートとスイッチ)のメモリの応答とバスマスタを有効にする。ブリッジのバスマスタが切れていると、その先の装置のDMAも、メモリへの書込みとして届くMSIも、そこで止まる。ファームウェアは自分が使わなかったポートのバスマスタを切ったまま渡すことがある(ThinkPad X1 Yoga 第3世代のWi-Fiのポート)。ブリッジを扱うのは`pcie.c`だけで、ドライバはブリッジに触れない。NetBSDのドライバをrumpで動かすWi-Fiも、カードを渡す前に`ts_pcie_enable`を呼ぶ。ブリッジは起動時の走査でまとめて有効にはせず、ドライバが有効にした装置の上の道だけを開く。使っていないポート(Thunderboltのポートなど)の先からはDMAが通らない。有効にしたブリッジは、`pcie: bridge`の行でコンソールに出る。

x64のネットワークのカード(`neta`)は、virtio-net、Intelのカード、USBのLANのアダプタ、Wi-Fiの中から`netsel.c`が選ぶ。起動の直後はあるものの最初を使い、アダプタの管理(`netadp.c`)が動き出した後は、利用者の選択(機器の設定の`NET_ADAPTER`)か、自動ならリンクが上がっている有線、無ければ接続しているWi-Fiを使う(09章9.6.1)。Raspberry Pi 5(`WIFI=1`)も同じ`netsel.c`と`netadp.c`で、ボードのEthernet(機器の設定では`eth`)とWi-Fiから選ぶ(09章9.6.8)。

IntelのチップセットのLAN(I219など)の初期化は次の順である。PHYの構成を止め(EXTCNF_CTRLのGATE_PHY_CFG)、PHYの超低電力の状態(ULP)を解く。MEがあれば(FWSMのFW_VALID)MEに頼み(H2MEのULPを消し、ENFORCE_SETTINGSを立てて、FWSMのULP_CFG_DONEが落ちるのを待つ)、なければPHYのレジスタで解く(LANPHYPCの切替え、SMBusの強制を外す、K1を立てる、ULP_CONFIG1を消してSTART)。次に、MDIOでPHYの識別子が読めるかを確かめ、読めなければSMBusを強制して、さらにだめならLANPHYPCでPHYの電源を入れ直す。PHYを読み書きする間は、MAC、ME、PHYの構成が共有する旗(EXTCNF_CTRLのSWFLAG)を持つ。リセットの前に、チップセットが求めていれば(PCI構成空間0xE4のビット8)受信のリングを空ける。マスタのアクセスを止め、送受信を止め、MEが許せばPHYも一緒に(CTRLのPHY_RST)リセットし、LANの初期化の終わり(STATUSのLAN_INIT_DONE)を待つ。リセットの後に、MACのアドレスをRAL0とRAH0から読み、PCHのMACの設定(CTRL_EXT、TXDCTL、TARC、RFCTL、ECC)をし、ドライバが持つことを示す(CTRL_EXTのDRV_LOAD)。SkylakeのPCHでは、送信の設定の後にIOSFPCとTARC0の誤りの回避を入れる。リンクが変わるたびに、送信の間隔(TIPG)、PHYのクロックゲート、Skylakeでは速さによるPHYの設定(776,20)、K1を止めるかどうか(PCIEANACFGに従う)を設定する。受信は割込み(`ts_pcie_irq_alloc`。I219はMSIだけを持つ)で知り、割込みが取れなければ1msごとに見る。

x64のvirtio-netは、virtioのPCIの転送(構成空間のケーパビリティが言う共通の設定、通知、デバイスの設定の領域)を使う。`vio_pci.c`はその領域の読み書きを、virtio-mmioのレジスタのオフセットで呼べるように読み替える。このため`vnet.c`のキューの扱いはQEMU virtと同じである。

Raspberry Pi 5とCM5で配線が違うところ(SDHCIの先がSDカードかeMMCか、カード検出線の有無、ボードが使う常時オンのGPIO、EthernetのPHYのアドレス、コンソールのポート)は、ドライバがボードの表(`include/ts/board.h`の`knl_board`)を見て切り替える。表は起動時にデバイスツリーとファームウェアのボードのリビジョンから選ぶ(3.5.1)。Raspberry Pi 4、400、CM4も同じ表で見分ける(3.6.1)。

シリアルポートは、ポートごとのデバイス`sera`、`serb`…(種類`TDK_SERIAL`、サブユニットなし)である。プロセスは、デバイスを直接開かず、SVCのクラス11(`sr_`、付録A、`device/ser/ser_svc.c`)で使う。`sr_lst_prt`がポートの一覧を返し、`sr_opn_prt`で開いたポートはプロセスの中の番号で指定する。デバイスはカーネルがプロセスに代わって開いて持ち(全体で8つまで)、プロセスが終わると閉じる。読み書きのバイト列はカーネルのメモリを通して受け渡す。読出しの待ち時間は呼出しごとに指定し、ポートの受信の待ち時間をそれに設定してから読む。ブラウザのWeb Serial(14.4.9)がこれを使う。

### 6.2.1 NVMe

NVMeのドライバ(`device/nvme/nvme.c`)は、PCIのクラス01h、サブクラス08h、インタフェース02hの制御器ごとに、名前空間1を`nvmea`、`nvmeb`…として登録する。キューは管理のキューと入出力のキューを1組ずつ(どちらも32項)持ち、1つのキューにコマンドは1つずつ送る。

初期化は次の順である。

- CAPかCSTSが全ビット1なら、装置がバスに無いとして、待たずにやめる。CAP.MQESが32未満の制御器、NVMのコマンドセットを持たない制御器、最小のページ(CAP.MPSMIN)が4KBより大きい制御器は使わない。
- 割込みは`ts_pcie_irq_alloc`でMSI-X、なければMSIを1つ取る。管理のキューはベクタ0を使い、入出力の完了のキューにも同じベクタを渡す。どちらも取れなければ、PCIのコマンドのINTx Disableで割込みの線を止め、制御器の割込みをINTMSで全部覆って、完了をポーリングする。
- CC.ENを1から0にして制御器をリセットする。前のOSやファームウェアが残したキューとホストメモリバッファは、ここで外れる。CC.ENが1でCSTS.RDYがまだ0の制御器は、RDYが1になるのを待ってからENに0を書く(RDYが0のうちにENを0にしたときの動きは、仕様で決まっていない)。RDYを待つ時間はCAP.TOで、システムの時計(`tk_get_otm`)で数える。
- Identify Controllerで、型番、ファームウェアのバージョン、MDTS、名前空間の数(NN)、RTD3E、ホストメモリバッファの大きさ(HMPRE、HMMIN、HMMINDS、HMMAXD)を読み、`nvme: nvmea: "..." firmware ..., NVMe 1.4, MDTS 5, 1 namespaces, ...`の行でコンソールに出す。NNが0の制御器は使わない。MDTSは最小のページ(4KB)の2のべき乗で、1回のコマンドの上限にする。0は上限なしで、20以上も上限なしとして扱い、どちらもPRPの表のページ1枚が名指せる2MBで止める。前は`1U << MDTS`をそのまま計算していたので、32以上の値で桁があふれた。
- Identify Namespaceで名前空間1の大きさ(NSZE)とLBAの形式(FLBAS)を読む。論理ブロックが512〜4096バイト(LBADSが9〜12)で、メタデータの無い形式だけを使う。NSZEが0の名前空間(作られていないもの)は使わない。
- ホストメモリバッファを渡し(下)、入出力の完了のキュー、送るキューの順に作る。

名前空間の論理ブロックが、そのままデバイスのブロックになる。`DiskInfo`の`blocksize`、`T_DDEV`の`blksz`、要求の開始番号と大きさ、`TDN_IOMAX`、`TDN_FUAWRITE`は、どれも論理ブロックで数える。前は512バイトの名前空間しか受け付けなかった。4096バイトのときは区画の表を読まず、デバイスの全体(サブユニット0)だけを見せ、`TDN_PARTSCAN`には`E_NOSPT`を返す(USBの大容量記憶の512バイトでない装置と同じ扱い)。4096バイトのブロックに上の層がまだ対応していないところは次のとおりで、4096バイトのNVMeのディスクの上には今はボリュームを置けない。

- GPTとMBRの読み(`peripheral_kernel/sysman/part.c`)は、512バイトの緩衝に1セクタずつ読み、表の項の数も512バイトで数える。GPTの書込み(`gpt.c`)は512バイトでない装置を断る。
- TSFS(`tsfsblk.c`、`tsfspart.c`、`obfsck.c`)は、4KBのブロックの番号をデバイスのブロックの8つ分(`TSFSBLK_SECT_PER_BLK`)として計算する。4096バイトの装置では、位置が8倍にずれ、容量の8分の1しか使わない。
- FAT(`fatfs.c`、`fsprobe.c`)は512バイトのセクタだけを受け付ける。
- x64の起動ディスクの探索(`bootdisk.c`)は512〜4096バイトのブロックを扱える。

Surface Go 2とThinkPad X1 YogaのSSD(KIOXIA BG4、SK hynix BC501)は512バイトの形式で出荷されるので、今の実機ではこの制限は効かない。対応するには、区画の読み書き、TSFS、FATのそれぞれでブロックの大きさを`DiskInfo`から取るように直す必要がある。

コマンドの完了は割込みで待つ。10ミリ秒たっても割込みが来なければ完了のキューを見直し、そこに完了があれば「割込みの来なかった完了」として数え、最初の1回を`nvme: nvmea: a completion was there with no interrupt for it after 10 ms ...`の行で出す。前は数えなかったので、MSI-Xが届かない機械でも10ミリ秒ごとの見直しで遅いまま動き、気付けなかった。待つ時間は、待った回数ではなくシステムの時計で数える。前は割込みの無い道で1ミリ秒の待ちを10ミリ秒として数えていたので、10秒のタイムアウトが約1秒になっていた。

10ミリ秒ごとの見直しのたびにCSTSを読む。全ビット1なら制御器がバスから消えたとし、CFSが立っていれば制御器が壊れたとして、タイムアウトを待たずにやめる。完了の項が言う送るキューの頭(SQHD)を覚えておき、送るキューが満ちていればコマンドを送らない。10秒(`NV_TMO_MS`)答えの無いコマンド、CFS、満ちたキューのどれでも、要求を`E_IO`で失敗にする前に、制御器をリセットする(`nv_recover`)。入出力のキューと管理のキューの両方のロックを持ったまま、CFSでなければホストメモリバッファを外し(1秒まで待つ)、CC.ENを0にしてRDYが0になるのを待ち、キューを空にして作り直し、ホストメモリバッファを渡し直す。制御器は、リセットが終わるまでは、答えていないコマンドが名指したメモリ(ドライバの緩衝か、呼び手のメモリ)に後から書くことがある。そのため、リセットが終わるまで要求を呼び手に返さない。前は答えの無いコマンドを制御器に残したまま次の要求に進んだので、遅れて来たDMAが使い回した緩衝を書き換えるおそれがあり、送るキューの頭も見ていなかったので、31回のタイムアウトで送るキューがあふれた。リセットの後に戻らない制御器と、消えた制御器は、CC.ENを0にしたまま残し、その後の要求はすぐ`E_IO`で失敗にする。

数えるものは、来た割込み、答えたコマンド、割込みの来なかった完了、答えの無かったコマンド、リセットの数である。来た割込みは、最初の1回とその後10倍ごとに`nvme: nvmea: 100 interrupts arrived (MSI-X, interrupt 80, PRC 1); 120 commands, 0 of them found without their interrupt`の行でコンソールに(したがって`KERNEL.TXT`に)出す。割込みを持つのに100回のコマンドで1回も来なければ、`no interrupt arrived in 100 commands`の行を出す。電源を切るときは、記録のファイルを書く前に全部の数を1行に出す(`knl_nvme_report`)。装置の実身の属性の`irq`には、割込みの数`count`を足した(`"irq":{"cpu":0,"intno":[34],"on":[1],"count":[1234]}`)。ドライバがハンドラで増やす数を`knl_int_count_at`(`kernel/tkernel/inttarget.c`)で名指したときに出る。今はNVMeだけが名指す。

ホストメモリバッファ(HMB)は、HMPREが0でない制御器(DRAMを持たないBG4やBC501)に渡す。HMPRE(128MBまで)を2MBの塊で、足りなければ小さな塊で確保し(HMMINDSより小さくせず、HMMAXD個まで)、記述子の表(4KBのページ1枚、256項まで)を付けてSet Features(FID 0Dh)のEHMで渡す。HMMINに届かなければ渡さない。確保したメモリは手放さない。答えなくなった制御器がそこに書いても、ほかに使われていないからである。リセットの後は、同じメモリを中身に触れずにMRを立てて渡し直す。リセットとシャットダウンの前にはEHMを0にして外す。起動の行に`host memory buffer of 32768 KB in 16 pieces given`か`no host memory buffer`が出る。初期化でCC.ENを1から0にするので、前のOSが渡したHMBは外れてから新しく渡すことになる。

電源を切るときと再起動するときは、`knl_finish_device`(x64、`kernel/sysdepend/x64/devinit.c`)が、記録のファイルを書いた後に`knl_nvme_shutdown`を呼ぶ。NVMe 1.4の7.6.2のとおり、制御器ごとに次を行う。

1. 緩衝のロックと両方のキューのロックを取り、それ以降の要求を`E_IO`で断る。
2. Flushで揮発の書込みキャッシュを媒体に書く。
3. 入出力の送るキュー、完了のキューの順に消す(Delete I/O Submission Queue、Delete I/O Completion Queue)。
4. ホストメモリバッファを外す(EHMを0)。
5. CC.ENを1のまま、CC.SHNに01b(普通のシャットダウン)を書き、CSTS.SHSTが10b(完了)になるのを待つ。

待つ時間は、RTD3Eが5秒より長ければRTD3E(60秒まで)、そうでなければ5秒である。RTD3Eは典型の時間で、それより長くかかる装置もあるので、RTD3Eで短く切らない。SHSTが10bになればすぐ次へ進む。結果は`nvme: nvmea: shutdown complete in 3 ms (of 5000; CSTS 00000009): flush 0, I/O queues deleted 0, host memory buffer taken back 0`の行で出す。この行は記録のファイルを書いた後なので、ファイルには残らず、シリアルのコンソールにだけ出る。前はシャットダウンの通知もFlushもせずに電源を切っていたので(`CC_SHN_NORMAL`は定義だけで、`nv_event`も`E_NOSPT`を返すだけだった)、SSDは電源を切るたびに安全でない電源断として数えていたはずである。

電源を切るまでの順は次のとおりである。デスクトップがウインドウを保存して閉じ、ファイルシステムを書き出し(`fs_sync`)、`usermain`が戻る。`knl_finish_device`が、`\_TTS(5)`、Wi-Fiの切断、PCIの装置の起動の解除、電源の切り方の表示、NVMeの数の行の順に行い、記録のファイル(ESPと`/tslog`。NVMeにもUSBメモリにもある)を書いて`fs_sync`する。NVMeを止めるのはその後で、これより後にディスクに書くものはない。USBの大容量記憶とネットワークは、ここでは止めない。

試験は`pcdev`の群で行う。`test_irq`はNVMeの制御器がMSI-Xを取ることを、`test_nvme`は64KBの読込み16回で割込みが16回来て、割込みの来なかった完了が0で、装置の実身の`irq`に`count`が出ることを確かめる。`test_nvme_lost`は、`knl_nvme_test_drop`で失わせた読込みが10047ミリ秒後に`E_IO`で返り、リセットが1回で、同じブロックをもう一度読めることを確かめる。`test_nvme_4k`は、`ktest64.sh`の`NVME4K`で挿した4096バイトのブロックのディスク(`nvmeb`)で、直接の読み書き、ダブルワードにそろわないメモリ(ドライバの緩衝を通る)、3MBの複数のコマンド、FUA、ブロックの一部の要求の拒否、最後のブロック、区画が無いことを確かめる。QEMUの`nvme`はCC.SHNに答えるので、`OFFWAIT=1`の記録で、6台の制御器がどれも`shutdown complete in 0 ms (of 5000; CSTS 00000009)`となり、Flush、キューの削除が0(成功)で返ることを見た。Windowsのハイパーバイザで`iob`の大きな書込みをしている間は、割込みの来なかった完了がまれに数えられた(30774回のコマンドのうち29回など)。割込みは後から来ており、待ちが10ミリ秒延びただけである。

ThinkPad X1 Yoga 第3世代のSK hynix BC501(1c5c:1327、バス3)は、USBメモリから起動したときに(2026-10-27、`C:\tmp\x1yoga3`の記録)、MSI-X(割込み80)で取れ、Windowsの入ったGPTの4つの区画(500118192セクタ、244198MB)を読めた。割込みの数とHMBは、この直しの後の実機でまだ確かめていない。

MSI-Xの有効にする順(`peripheral_kernel/sysman/pcie.c`の`ts_pcie_msi_alloc`)も直した。前は表の項を書いてからMSI-Xを有効にしていたが、MSI-Xを有効にするまで表に答えない装置がある。今は、能力のMSI-X EnableとFunction Maskを同時に立て、表の項を覆ったまま書いてから覆いを外し、最後にFunction Maskを外す。初めて有効にするときは、表の0番以外の項もすべて覆う(ファームウェアが残した項から割込みが送られないように)。

## 6.3 USB

USBスタックは、xHCIホストコントローラの上に、ハブ、HID、マスストレージ、オーディオ、ビデオのクラスドライバを載せたものである。Low、Full、High、Superのすべての速度と、コントロール、バルク、インタラプト、アイソクロナスの各転送を扱う。デバイスの抜き差しは、専用の管理タスクがハブの状態変化を受けて処理する。管理タスクは、デバイスが来たり去ったりすると、ロックを放した後でUSBデバイスとキーボード、ポインタの実身を一覧に合わせる(`knl_obusb_changed`)。コントローラと機器の表は来た数だけ伸ばし、xHCIのスロットはコントローラが持つ数(255まで)、ルートの口はコントローラが持つ数(255まで)を使う(8.12)。

| クラス | 機能 |
| --- | --- |
| HID | キーボードとマウス。レポートディスクリプタを解析し、相対座標と絶対座標のどちらも扱う |
| マスストレージ | Bulk-Only TransportとSCSI。パーティションテーブルを読み、パーティションをサブユニットにする。CD-ROMドライブ(INQUIRYの周辺機器の種類5)も同じ名前の付け方のディスクにし、ブロックは2048バイト、読み取り専用、取り外せるものとして扱い、パーティションは読まない(ディスクの属性は`TDK_DISK_CDROM`)。BTRONのCD-ROMはファイル変換が読む(11.9) |
| オーディオ | UAC 1.0。アイソクロナス転送で再生と録音をする |
| ビデオ | UVC 1.0から1.5。カメラデバイス`cama`のカメラにする(6.6) |
| ハブ | USB 2.0とSuperSpeed |

### 6.3.0 マスストレージの命令の時間と回復

マスストレージの1つの命令(CBW、データ、CSWの3つの段)は、合わせて30秒(`MSC_CMD_TMO`)まで待つ。前は、CBWとCSWを1秒、データを5秒で打ち切っていた。SDカードは書込みの後しばらく次の命令を受けないことがあり、1秒で打ち切ると、命令の途中でリセットすることになっていた。30秒は、Linuxのディスクの命令の時間(`SD_TIMEOUT`)と同じである。

転送が失敗したとき(時間切れ、CBWやCSWのSTALLが解けない、CSWが壊れている、フェーズの誤り)は、デバイスを次の順で戻し、その命令を送り直す。送り直しは5回まで(Linuxの`SD_MAX_RETRIES`と同じ)である。

1. ポートのリセット(`knl_usb_reset_device`)。デバイスにアドレスを付け直して元の構成にする。
2. 1ができなかったときは、Bulk-Only Mass Storage Reset。クラスの要求(5秒まで)を送り、6秒待ってから、バルクのINとOUTのエンドポイントの停止を解く。

順番と時間は、Linuxのusb-storage(`usb_stor_invoke_transport`、`usb_stor_port_reset`、`usb_stor_Bulk_reset`)と同じにした。前は、時間切れのたびにクラスの要求と停止の解除をすぐ送るだけで、命令は送り直さず、ポートのリセットもしなかった。

リセットの後、装置はリセットで起きたことをUNIT ATTENTIONとして、命令1つに1つずつ答える。電源投入やリセット(29/xx)のほかに、カードリーダはカードを見つけ直したこと(28/00、媒体が変わったかもしれない)も答える。命令を送り直す前に、TEST UNIT READYとREQUEST SENSEで、これらを5回まで受け取っておく(`msc_settle`)。準備中(02/04/01)なら100ミリ秒待つ。28/00が来たときは容量を読み直し、前と同じなら同じ媒体とする。違えば前の媒体は抜かれたとし、媒体の見回りで新しい媒体として取り込む。Linuxも、リセットの後はエラー処理のTEST UNIT READY(`scsi_eh_tur`)でUNIT ATTENTIONを受け取ってから命令を送り直す。前は、送り直した命令に来た最初のUNIT ATTENTIONだけをリセットによるものとして許していた。X1 Yogaのカードリーダ(05e3:0749)はリセットの後に2つ答えるので、2つ目の06/28/00で読み書きが失敗し、`/boot`の書込みが-5で止まっていた。ここで受け取りきれずに残ったUNIT ATTENTIONも、1つはリセットによるものとして命令を送り直す。

USB 3の転送でパケットがバスの上で続けて失敗すると(コントローラはエンドポイントの誤りの数CErr=3まで送り直す)、xHCIはTransaction Error(完了コード4)でエンドポイントを止める。デバイスの側のエンドポイントはそのままなので、Reset Endpointを転送の状態を保つ形(TSP)で送り、ドアベルを鳴らして同じTDの続きから再開する(`xhci.c`の`soft_retry`)。順番の番号はコントローラとデバイスで食い違わず、TDも失われない。成功を挟まずに3回までとし、トランザクショントランスレータを通る装置には行わない。それを超えたときだけ、エンドポイントを戻して転送の誤り(`E_IO`)とし、上のポートのリセットに進む。Linuxのxhci(`process_bulk_intr_td`の`EP_SOFT_RESET`、`MAX_SOFT_RETRY`)と同じ形である。前は、1回のTransaction Errorで転送を失敗とし、そのたびにポートのリセットをしていた。X1 Yogaでは、READ(10)の512バイトが数百回通った後に1つが1〜4ミリ秒で-57(`E_IO`。時間切れではなく、STALL以外の完了コードかCSWのフェーズの誤り)になり、10〜20秒ごとにポートのリセットとカードの見つけ直しが起きていた。STALL以外の完了コードで転送が終わったときは、コンソールに完了コードを出す(`usb: slot 5 endpoint 81: bulk of 512 bytes ended with completion code 4 (taken up again 3 times)`)。CSWのフェーズの誤りも出す。

エンドポイントの停止を解く(`knl_usb_clear_halt`、CLEAR_FEATURE(ENDPOINT_HALT))と、デバイスはそのエンドポイントのデータトグル(SuperSpeedでは順番の番号)を最初から数え直す。前は、コントローラの側を数え直していなかった。STALLの後はReset Endpointで数え直されるが、時間切れの後はStop Endpointで止めるだけなので、停止を解いた後はデバイスとコントローラの数が食い違い、それからの転送がすべて通らなくなりえた。今は、停止を解いた後に、コントローラの側のエンドポイントも数え直す(ホストコントローラの`ep_reset`。xHCIでは、Configure Endpointで同じエンドポイントを外して加え直し、リングは書いている所から読ませる。Linuxの`usb_clear_halt`と`xhci_endpoint_reset`と同じ形)。

書込み禁止を調べるMODE SENSE(6)は、Linuxと同じく、全部のページを192バイトの長さで求める(短い長さを嫌う装置がある)。その前に、媒体の最初のブロックを1つ読む(Linuxの`read_before_ms`と同じ)。

書込みのキャッシュも、この同じ答えで決める。Linuxのusb-storageはUSBの大容量記憶にキャッシュのモードのページ(ページ8)だけを求めない(`drivers/usb/storage/scsiglue.c`の`slave_configure`で`skip_ms_page_8`)。sdは代わりに全部のページの答えの中からキャッシュのページを探し、ページ8のWCE(またはRBCのページ6の書込みキャッシュ禁止のビットが0)があるときだけ書込みのキャッシュがあるとし、見つからないか答えがないときは書込みのキャッシュがないもの(write through)とする(`drivers/scsi/sd.c`の`sd_read_cache_type`)。FUAは、書込みのキャッシュがあり、DPOFUAが立つときだけ使う(`sd_set_flush_flag`)。ここも同じにした(`msc.c`の`scsi_protected`)。書込みのキャッシュのない装置には、SYNCHRONIZE CACHEを送らず、FUAも使わない。`TDN_FLUSH`はそのまま成功で答え(書いた中身は、装置が書き終えたと答えた時点で媒体にある)、`TDN_FUAWRITE`は`E_PAR`で答える。多くのカードリーダとUSBメモリはキャッシュのページを答えないので、こちらになる。前は、どの装置にも`TDN_FLUSH`のたびにSYNCHRONIZE CACHEを送り、DPOFUAだけでFUAを使っていた(X1 Yogaの起動では、キャッシュを空にする要求が1807回、3.8秒あった、7.3)。装置を見つけたときの行に、書込みのキャッシュがあるかどうかを出す(`usb: uda: ... 3 partitions, write cache taken as off`)。QEMUのUSBのディスク(`scsi-hd`)は、既定でページ8にWCEを立てて答えるので、キャッシュがありFUAを使う装置になる。

転送が失敗したときは、そのデバイスの直前の8つの命令(命令、ブロック、バイト数、答え、ミリ秒)をコンソールに出し、続けて回復の結果を出す(`usb: uda: the transport failed (-50): the port reset (0)`)。回復の回数は`USB.TXT`に出る。

試験`usb`の`test_msc_recover`は、USBのディスクの命令をわざと2回失敗させ(命令を送らずにCSWを求めると、QEMUのデバイスはSTALLで答える)、ポートのリセットとBulk-Only resetのそれぞれで戻って同じ中身が読めること、その後も両方のエンドポイントで読み書きできることを確かめる。QEMUのデバイスはデータトグルと順番の番号を見ないので、数え直しが効くことは実機でしか確かめられない。本当の時間切れ(Stop Endpointの道)も、QEMUでは起こせなかった。

### 6.3.1 プログラムのUSBデバイス

クラスドライバが取らなかったデバイス(役割が`USB_ROLE_NONE`で、ハブでないもの)は、プログラムが使える(SVCのクラス12、`us_`、`device/usb/uusb.c`、付録A)。プログラムはデバイスの一覧と記述子を読み、そのようなデバイスを開く。開けるのは一度に1つのプロセスだけで、クラスドライバのデバイスや別のプロセスが開いているデバイスは`E_BUSY`になる。開いたデバイスには、プロセスの中の番号が与えられる。プログラムはその番号で、コントロールエンドポイントに要求を出し、インタフェースの代替設定を選び、エンドポイントの停止を解き、デバイスをリセットし、選んだ設定のバルク、インタラプト、アイソクロナスのエンドポイントでデータを送受する。デバイスが抜かれると、以後の呼出しは`E_NOEXS`になる。プロセスが終わると、開いていたデバイスは閉じる。

コントロールの要求とOUTの転送は、管理タスクのロックを持ったまま、その時間切れ(最長10秒)まで行う。INのエンドポイントは、ロックを持ったまま待たない。最初のINの転送でそのエンドポイントにストリームを開き、管理タスクが転送の完了を受けるたびに、そのバイト列を1つのチャンクとしてエンドポイントのリング(64KB)に入れる。INの転送は一番古いチャンクを取り出す。チャンクがなければ、ロックの外で時間切れまで待つ。求めた長さより長いチャンクは切り詰め、残りは捨てる。リングがあふれると古いチャンクから捨てる。アイソクロナスのINも同じ作りで、1サービス間隔のパケットが1つのチャンクになる。アイソクロナスのOUTにもストリームを開き、コントローラがサービス間隔ごとにパケットを求める。OUTの転送はバイト列を1つのパケットとしてリングに入れて戻り、リングが満ちているときだけ空くまで待つ。送るパケットのないサービス間隔は何も送らない。代替設定を選ぶとき、停止を解くとき、リセットのときはストリームを閉じ、次の転送で開き直す。リセット(`us_rst_dev`)は、デバイスのスロットを手放し、ポートをリセットし、デバイスにアドレスを付け直して元の構成にする(`knl_usb_reset_device`)。デバイスはツリーの中の場所と番号と記述子を保ち、プロセスは開いたまま使い続けられる。プログラムのストリームが開いている間は、管理タスクは4ミリ秒ごとにコントローラを見る。

HIDのクラスドライバはキーボードかポインタのインタフェースだけを取る。それ以外のHIDの機器(ゲームパッド、FIDOのキーなど)は役割が`USB_ROLE_NONE`のまま残り、プログラムが使える。ブラウザのWebHIDはそれを使う。バイト列はカーネルのバッファを通し、`knl_ua_get`と`knl_ua_put`で受け渡す(PAN)。ブラウザのWebUSB(14.4.8)がこれを使う。

### 6.3.2 試験のソフトウェアのUSBコントローラ

試験のマシン(QEMU)にない種類のUSBの機器(ゲームパッド、MIDIの機器)を、管理タスク、クラスドライバ、プログラムのUSBデバイス(6.3.1)を通して端から端まで試すために、`KTEST=1`のQEMUのビルドだけにソフトウェアのUSBコントローラがある(`device/usb/vhc.c`、`vhc.h`)。ポートは2つで、試験が`knl_vhc_plug`で機器を挿すと、初めのときにコントローラを管理タスクに足し(`knl_usb_add_hc`)、ポートを見直させる。機器は、デバイス、コンフィギュレーション、文字列、HIDのインタフェースのレポートの記述子と、OUTのエンドポイントに送られたものを受ける関数、クラス要求に答える関数で表す。標準の要求(アドレス、コンフィギュレーション、代替設定、停止)とHIDの答えの要らないクラス要求はコントローラが受ける。試験が`knl_vhc_in`で置いたINのエンドポイントのデータは、管理タスクがコントローラを回すときに、そのエンドポイントのストリームに1回の転送ずつ渡る。ブラウザの試験`test_blink_pad`と`test_blink_midi`が使う(14.10)。

### 6.3.3 x64のPCのxHCI

x64では、PCI Expressの先のxHCIごとに、`device/usb/x86_64/xhci_pc.c`が`knl_xhci_attach`の前後の手順を足す。xHCIの本体(`xhci.c`)のx64だけの処理は`#ifdef X64`の中にあり、Armの動きは変わらない。

1. 取り付けの前に、コントローラのPCIのベンダとデバイスをコンソールに出す。Intelのコントローラなら、構成空間のポートの組合せのレジスタ(0xD0 XUSB2PR、0xD4 XUSB2PRM、0xD8 USB3_PSSEN、0xDC USB3PRM)を読んで記録し、IntelのEHCIが同じバスにあるときだけ、USB3PRMの値をUSB3_PSSENに、XUSB2PRMの値をXUSB2PRに書いて、EHCIのポートをxHCIに渡す。SkylakeからはEHCIが無いので読むだけである。
2. 割込みを割り当てる(`ts_pcie_irq_alloc`)前に、`knl_xhci_quiesce`でコントローラを静かにする。ファームウェアからの引き継ぎ(USBLEGSUPのOS所有を立ててBIOS所有が落ちるのを最大5秒待ち、落ちなければ取る。USBLEGCTLSTSのSMIの許可を消し、残った要因を消す)をし、CNRが落ちるのを最大5秒待ってから、USBCMDのRS、INTE、HSEE、EWEを消してHCHを待ち、USBSTSの要因とインタラプタ0のIMANのIPとIEを消す。ファームウェアが割込みを有効にしたまま動かしていたコントローラは、保留の割込みを持っていることがあり、MSIを有効にした途端に、ハンドラを定義する前にメッセージを送るためである。LinuxもPCIのバスを見るときの回避策(USBのハンドオフ)で、ドライバがベクタを割り当てて割込みを登録する前に同じことをする。引き継ぎの前後のレジスタの値と、見つけたときと静かにした後のUSBCMD、USBSTS、IMANをコンソールに出す。
3. CNRが落ちるのを最大5秒待ってから止め、リセットし、メモリを割り当てて動かす(6.3と同じ)。ハンドラを定義してから、IMANのIEとUSBCMDのINTEを立てる。開始したときに、バージョン、ポートとスロットとスクラッチのページの数、ポートの電源をソフトウェアが入れるかをコンソールに出す。
4. 取り付けの後、Intelのコントローラでは、等時転送のTDごとに完了の割込みを起こす(ほかのコントローラは8つに1つで、残りはBEIで割込みを止める)。チップセットのSunrise Point(8086:9D2F、A12F。Skylake、Kaby Lake、Amber Lake)では、IntelのベンダーのxHCI拡張機能(192)にあるType-Cの口の役割のレジスタ(DUAL_ROLE_CFG0とCFG1)を読んで記録する。ホストの役割でなく、起動の設定(`cmdline.txt`)に`usbrole=host`があるときだけ、IDピンを0、VBUSを0、ソフトウェアのIDピンを使うにして、CFG1がホストを示すのを最大1秒待つ。

USB 3のポートのリンクがSS.InactiveかComplianceで止まっているときは、ポートのリセットの代わりにPORTSCのWPRで温かいリセットをし、WRCを待つ(x64だけ)。USB 2のLPM、USB 3のU1とU2、D3の眠りは使わない。

切断の原因を実機で決められるように、管理タスクが装置を外すと決めたときに、そのポートの状態をコンソール(KERNEL.TXTにも残る)に出す。ルートポートなら、走査で読んだPORTSC(消す前の変化のビットを含む)とリンクの状態、その前の別の状態とそれを読んだ時刻、決めた理由(CCSが0か、CCSが1のままCSCが立ったか)の1行と、今のPORTSC、PORTPMSC、PORTLI(USB 3のリンクのエラーの数)、最後のPort Status Change Eventで読んだPORTSCとその時刻の1行を出す。Sunrise PointではType-Cの役割のレジスタ(DUAL_ROLE_CFG0とCFG1)の今の値と起動のときの値も2行目に足す(`xhci.c`の`knl_xhci_port_say`、`x86_64/xhci_pc.c`の`knl_xhci_pc_role`)。ハブのポートなら、ハブのwPortStatusとwPortChange、SuperSpeedのハブならリンクの状態を1行に出す。Port Status Change Eventを受けたときも、PORTSCが前のイベントのときから変わっていれば1行出す。出しすぎないように、1つのポートで10秒に8行までとする。arm64でも同じに出す。

ルートポートとハブのポートは、同じ手順で扱う(`usbman.c`の`port_event`。LinuxのUSBのハブのドライバ`drivers/usb/core/hub.c`の`port_event`、`hub_port_connect_change`、`hub_port_debounce`、`hub_port_warm_reset_required`と同じにした)。ルートポートのPORTSCは、コントローラのドライバがハブのGET_STATUSと同じ形(状態の16ビットと、その上の変化の16ビット)に直して渡す(操作の表の`port_status`)。

- 接続の変化(CSC、C_PORT_CONNECTION)は、装置がつながったまま有効で、装置の記述子と構成の記述子を読み直して前と同じなら、その装置をそのまま残す(USB 3のポートはリンクを自分で張り直すので、同じ装置のことがある)。違えば外し、つなぎ直す。前は、CCSが1のままのCSCでも、外してつなぎ直していた。
- つなぐ前に、接続が100ミリ秒続けて変わらないことを25ミリ秒ごとに確かめる(デバウンス、2秒まで)。続かなければつながない。前は100ミリ秒待つだけだった。
- ポートが装置を残したまま無効になった(PEC、C_PORT_ENABLE)ときは、電気の雑音でハブが切ったとみなして、つなぎ直す。
- 過電流の変化(OCC)は、100ミリ秒待ってポートの電源を入れ直し、まだ過電流なら出す。
- USB 3のリンクがSS.Inactiveか互換モードになったときは、装置を抜いたときの途中のことが多いので、20ミリ秒ごとに5回まで切断を待つ。それでも残れば、装置がなければポートだけをウォームリセットし、装置がつながっていれば装置をリセットする(`knl_usb_reset_device`。ポートのリセットの前にウォームリセットする)。ハブのポートは`BH_PORT_RESET`で、ルートポートはPORTSCのWPRで行う。前は、ウォームリセットをx64のルートポートでだけ行い、リンクの状態の変化は見ていなかった。
- リンクの状態の変化(PLC)、リセットとウォームリセットの終わり(PRC、WRC)、構成の失敗(CEC)は、消すだけにする。

この手順は、x64とRaspberry Pi 5のRP1のxHCIの両方で同じに動く。

起動から20秒後に書くUSB.TXT(3.10)には、コントローラごとのPCI ID、Intelのポートの組合せと役割のレジスタ、ルートポートごとのPORTSC(つながっているか、有効か、電源、リンクの状態、速さ)と、装置ごとの速さとハブの段数を残す。

ThinkPad X1 Yoga 第3世代の実機で、Sunrise Point-LPのxHCI(8086:9D2F、ルートポート18、ポートの電源はコントローラが入れる)の初期化、ハブの列挙、装置の実身までを確かめた。ファームウェアからの引き継ぎで待ちは起きず、Type-Cの役割はファームウェアがホストにしていた(CFG1 20000000)。EHCIが無いのでポートの組合せのレジスタは書かず(XUSB2PR 00000001、USB3_PSSEN 00000000のまま)、USB 3のポートはSuperSpeedで動いた。内蔵の装置(Bluetooth、カメラ、指紋センサ、Wacomのペンとタッチ、SDカードリーダー)は、どれも本来の速さでつながった。Thunderbolt 3のUSBのコントローラ(8086:15D4)も取り付けた。チップセットのものではないので、Intelのポートの組合せのレジスタは記録しても意味が無く、書かない。

## 6.4 キーボードとポインタ

キーボードとマウスの入力は、USBのHIDから入力キューに入り、ウインドウマネージャが読み出す。同じイベントのコピーを、インタフェースごとの実身と入力の実身がレコード1で見せる。コピーを読んでもキューからは取り出さない。試験などが与える入力は、入力の実身のレコード1に書き込み、キューに入る(8.4)。ユーザ環境設定で変更できる入力の属性、たとえばキー入力の受付時間、キーリピート、ポインタの速度と加速度、主ボタンの左右の入れ替え、中ボタンのダブルクリック割当て、一時シフトは、このレイヤで適用する。ホイールは縦と横の回転量として通知される。

音量のキー(キーボードのページの使用法のVolume Up 0x80とVolume Down 0x81、`HID_KEY_VOLUP`と`HID_KEY_VOLDOWN`)はシステムのキーで、ウインドウマネージャが読み出したところで受け取り、ウインドウには渡さない(6.5.6)。押している間は、ほかのキーと同じくキーリピートの設定のとおりに繰り返す。Windowsでも音量のキーやタブレットの音量のボタンを押し続けると音量が変わり続けるので、それに合わせた。USB以外の機器の音量のボタンも、このキーとして入る。x64のSurface Go 2の本体のボタンは、ACPIのHIDイベントフィルタの5ボタンの配列から「acpibtn」というキーボードとして入る(3.10.6)。USBのキーボードの音量のキーは、多くはキーボードとは別のインタフェースのConsumerのページ(0xE9、0xEA)で送られるが、そのインタフェースはまだ扱わない。

HIDのインタフェースは次のように準備する。ブートサブクラスのキーボードは、SET_PROTOCOLでブートプロトコルに切り替え、SET_IDLE(0)を送り、SET_REPORTでLEDをすべて消す。LEDが一度設定されるまでレポートを送らないキーボードがあるためである。8バイトのブート形式のレポートを読み、キーの配列にErrorRollOverなどの誤り(値1から3)があるときは、キーの状態を前のレポートのままとし、修飾キーだけを更新する。同時押しが多すぎたときに、押されているキーを離して押し直したことにしないためである。

ポインタは、レポートディスクリプタ(4096バイトまで。失敗したら20ms置いて3回まで要求する)を解析する。解析は、Push/Popを含むグローバル項目、4バイト形式のUsage、レポートIDごとのビット位置を扱い、X、Y、ホイール、AC Pan、ボタンの変数フィールドだけを保持する。保持しないフィールドも、後に続くフィールドの位置には長さをすべて加える。相対のX、Yは、Logical Minimumが0以上と書かれていても符号付きとして読む。移動量は両方向にあり、符号なしとして読むと左や上への小さな移動が画面の端まで飛ぶためである。X、Yは同じレポートのものを組にし、相対のものを絶対のものより優先する。ディスクリプタが使えないブートサブクラスのマウスは、ブートプロトコルに切り替えて3から4バイトのレポートを読む。

ディスクリプタどおりに読むブートサブクラスのマウスは、レポートプロトコルで使う。HID 1.11の7.2.6では、バスリセットの後はレポートプロトコルになるが、ホストは機器の状態を仮定せずに設定するべきとしている。そこで、まずGET_PROTOCOL(7.2.5)で今のプロトコルを問い合わせる。レポートプロトコルと答えたときはSET_PROTOCOLを送らない。SET_PROTOCOLを送らないホストではバスリセットの後の状態のまま使われるので、機器もその使い方で最もよく確かめられているためである。それ以外の答えのとき、または答えがないときは、SET_PROTOCOL(1)を送り、もう一度GET_PROTOCOLで確かめる。最後の答えがブートプロトコルなら、SET_PROTOCOLの成否によらずブート形式で読む。答えがないときはディスクリプタどおりに読み、次の段落のレポートの形で見分ける。同じ機器にブートサブクラスのキーボードがあるときは、すべてのインタフェースを準備した後に、ポインタへもう一度GET_PROTOCOLを送る。インタフェースごとでなく機器全体で1つのプロトコルを持つ機器では、キーボードをブートプロトコルにするとポインタもブートプロトコルになるためで、ブートプロトコルと答えたらブート形式で読む。問い合わせの答え、SET_PROTOCOLの結果、ブート形式に切り替えた理由は、シリアルに出力する(`usb: hid: interface N says ...`)。

それでもブート形式のレポートが来る機器のために、レポートの形でも見分ける。3から4バイトのレポートで、ディスクリプタにないレポートIDで始まるもの、またはディスクリプタのX、Yがその長さに収まらないものが来たら、以後はブート形式として読む。ブート形式のレポートを、ディスクリプタのレポートの長さまで0で埋めて送る機器もある(先頭からボタン、Xの1バイト、Yの1バイトで、残りは0)。レポートIDがなく、X、Yが8ビットより広いディスクリプタでは、このレポートはXとYの2バイトが16ビットのXとして読まれ、たとえば`00 09 f9`はXが0xf909(左へ1783)になってカーソルが飛ぶ。このためレポートごとに次のように数える。5バイト目以降に0でないバイトがあれば、ブート形式ではないので、以後は数えない(16ビットのYが上へ動けばすぐにこうなる)。XかYの値が-128から127に収まらず、4バイト目が0なら、ブート形式でも説明できるので1票とする。収まらず4バイト目が0でなければ、ディスクリプタのYが動いた速い移動とみなし、票を0に戻す。収まるレポートは数えない。3票でブート形式に切り替え、シリアルに出力する(`usb: hid: N sends the boot protocol's reports padded to 8 bytes`)。切り替えるまでの票のレポートは、移動を0として扱い、ボタンはそのまま渡す。高解像度のマウスを速く真横に動かし、Yがちょうど0のレポートが3回続くと誤って切り替わり得るが、その間にYも動いている速い移動が1回でもあれば票は0に戻り、上へ一度でも動けば以後は数えないので、まず起きない。この判定はブートサブクラスで、レポートIDがないマウスだけに行う。

インタラプト転送の長さは、ふつうはwMaxPacketSizeとする。ポインタのレポートがそれより長いときは、ディスクリプタにある最長の入力レポートの長さ(64バイトまで)とし、複数のパケットに分かれたレポートを1回の転送で受け取る。ポーリング間隔は、LowとFull SpeedではbIntervalをミリ秒として2のべき乗に切り捨て、High Speed以上では2^(bInterval-1)マイクロフレームとする。転送の誤りでエンドポイントが停止したら、Reset EndpointとCLEAR_FEATURE(ENDPOINT_HALT)で再開する。正常な転送を挟まずに8回を超えて停止したら、再開をやめる。ポインタは、ディスクリプタから読み取った配置と最初の12個のレポートをシリアルに出力する(`usb: hid:`)。

### 6.4.1 ペンとタッチスクリーン

HIDのデジタイザ(Usage Page 0x0D)は、押したことをボタンのページではなく、Tip Switch(0x42)で伝える。ThinkPad X1 Yoga 第3世代のWacomの「Pen and multitouch sensor」(056a:5145)は、インタフェース0がタッチスクリーン(レポートID 12、40バイト)、インタフェース1がペン(レポートID 6、18バイト)で、どちらもボタンのページのフィールドを持たない。以前の入力の層はX、Yとボタンのページしか見ていなかったので、触るとポインタは動くが、クリックにならなかった。Linuxでは、この機器はWacomのドライバの汎用の道(`drivers/hid/wacom_wac.c`のHID_GENERIC。056a:5145は機種の表になく、`HID_ANY_ID`の項で拾われる)で読まれ、Windowsのタッチスクリーンの形のフィールドをそのまま読む。TessronOSも同じ読み方をする。

解析は、Collectionの入れ子をたどり、フィールドごとに、それが入っているApplicationのコレクションの用途と、Finger(0x22)またはStylus(0x20)のコレクションの番号を覚える。Windowsのタッチスクリーンの形では、1つのレポートに複数の指が入り、指ごとにFingerのコレクションがあるので、コレクションの番号で指を分ける。ペンかタッチスクリーンかは、LinuxのWacomのドライバ(`WACOM_PEN_FIELD`、`WACOM_FINGER_FIELD`)と同じに決める。StylusのコレクションかPenまたはDigitizerのApplicationにあればペン、FingerのコレクションかTouch ScreenのApplicationにあればタッチスクリーンである。Touch Pad(0x05)のApplicationはどちらにもせず、今までどおりそのマウスのレポートで読む。Precision Touchpadの読み方(ジェスチャで相対の動きにする)は別の作業とする。Wacomの機器(VID 0x056a)の独自のページ0xFF0Dと0xFF00は、Linuxの`wacom_equivalent_usage`と同じ規則で、標準の用途に読み替える(0x00nnはデジタイザのページのnn、0x01nnはGeneric Desktopのnn)。

ペンとタッチスクリーンは、それぞれ1つの入力レポートで、X、Yと、Tip SwitchかIn Range(0x32)を持つものだけを取る。1つのインタフェースで2つまで(ペンとタッチスクリーン)、1つのレポートの指は10本まで扱う。ディスクリプタにデジタイザのページがあるとき、またはポインタが見つからないときは、ディスクリプタの全体を16バイトずつシリアルに出力し(`usb: hid: interface N report descriptor`)、読み取った配置を出す(`usb: hid: interface N touch screen, report id ...`、`... pen, ...`)。ペンとタッチスクリーンのレポートは、最初の64個を全部のバイトで出力する。実機の1回の起動で、記述子とレポートの形を確かめられるようにするためである。

Windowsのタッチスクリーンの形(高精度のタッチ)の機器は、Device Configuration(0x0E)のApplicationのInput Mode(0x52)のFeature Reportが設定されるまで、マウスのレポートしか送らないか、何も送らないことがある。そこで、ペンかタッチスクリーンが見つかり、Touch PadのApplicationがない機器には、ディスクリプタにある最初のInput Modeを2(マルチ入力の機器)にしたFeature Reportを、SET_REPORT(HID 1.11の7.2.2、レポートの種類3)で送る。同じレポートの他のフィールドは0とし、Surface Switch(0x57)とButton Switch(0x58)は1、Latency Mode(0x60)は0(通常)とする。LinuxのhidのマルチタッチのドライバのMT_INPUTMODE_TOUCHSCREENとmt_set_modes、Wacomのドライバのwacom_hid_set_device_modeと同じ値である。結果はシリアルに出力する(`usb: hid: interface N input mode: feature report R (...) set (er)`)。Touch Padには送らない。送るとPrecision Touchpadの形に切り替わり、今のマウスとしての読み方ができなくなるためである。HID over I2Cのタッチスクリーンにも、同じFeature Reportを送る。HIDの層が`knl_hid_ext_attach_dg`でレポートを作り、`hid_i2c.c`がHID over I2CのSET_REPORT(コマンドレジスタ、種類3とレポートIDとオペコード3、データレジスタ、長さとレポート)で送り、GET_REPORTで読み返した値と一緒にシリアルに出力する(`hidi2c: hidi2c0: input mode: feature report R (...) set (er); read back (n): ...`)。その後のレポートはUSBと同じ処理(Tip Switch、Confidence、Contact Identifier、長押しの右クリック)を通る。

タッチスクリーンのレポートは、Linuxのhid-multitouchのMT_QUIRK_CONTACT_CNT_ACCURATEと同じに読む。Contact Count(0x54)が0でないレポートがフレームの始まりで、その数の指を、このレポートと続くレポート(Contact Countが0のもの。Windowsの形のハイブリッドモード)から読む。Contact Countがない機器では、レポートごとに全部の指を読む。指は、Tip Switchが立ち、Confidence(0x47)が0でないときに触れているとする。Confidenceが0の指は手のひらとして扱う。

ポインタになるのは1本目の指だけで、Contact Identifier(0x51)で追う。前のフレームに触れている指が1本もないときに触れた指を1本目とする。Windowsの主の接触(primary contact)と同じ決め方で、1本目の指が離れた後に残った2本目の指はポインタにならない。2本目の指が触れたときは、下の「二本指のスクロール」のとおり、2本をまとめて扱う。1本目の指がフレームにないか、Tip Switchが落ちたら離したとする。1本目の指はポインタの主ボタン(コード0)として入力のキューに入れ、座標はユーザ環境設定の絶対・相対の設定によらず、触れた所の画面の位置とする。直接触れる機器では、指の下にポインタがあることが意味を持つためである。主ボタンの左右の入れ替えと、中ボタンのダブルクリック割当ては、タッチスクリーンとペンには働かせない(Windowsのタッチのタップも主ボタンのまま)。ペンが範囲内にある間は、タッチスクリーンの指を取らない。ペンで書くときに画面に置いた手を、クリックにしないためである。Linuxも、ペンが近い間はタッチを止める(Wacomのドライバの`touch_arbitration`)。

ペンは、In Rangeの間ポインタを動かし(ボタンなし)、Tip Switch(またはペンの逆の端のEraser)が触れている間ボタンを押す。触れたときにBarrel Switch(0x44)が押されていれば副ボタン(コード1)、押されていなければ主ボタンとし、触れている間は変えない。Windowsのペンのボタンの既定(ボタンを押しながら触れると右クリック)と同じである。ペンのボタンだけを押してもクリックにはしない。範囲から出たら押していたボタンを離す。ペンの座標は、マウスやタブレットと同じに、ユーザ環境設定の絶対・相対の設定に従う。ペンの押下は、ほかのポインタと同じにボタンの受付時間の設定を通る。

#### 長押しで副ボタン

タッチスクリーンの指の長押しは、副ボタンのクリックとして扱う。BTRONの操作では副ボタン(右ボタン)がメニューで、指には副ボタンがないためである。Windowsも、タッチの長押しを右クリックにする(既定で有効)。扱いは次のとおりとする。

| 指の動き | 入力のキューに入るもの |
| --- | --- |
| 触れた | 触れた所へポインタの移動。主ボタンの押下は、何になるか分かるまで出さない |
| 1秒より前に、動かさずに離した | 触れた所で主ボタンの押下と解放(クリック) |
| 1秒より前に、許容の幅より大きく動かした | 触れた所で主ボタンの押下、その後の移動。離したら解放(ドラッグ) |
| 動かさずに長押し時間(既定1秒)触れている | その時点で、触れた所で副ボタンの押下。メニューは指が触れたまま開く。ポインタの形をメニューの形(`WM_PT_MENU`)にする |
| その後、動かした | 副ボタンを押したままの移動(メニューの上のドラッグ) |
| その後、離した | 離した所で副ボタンの解放。ポインタの形を戻す |
| 手のひら、ペンが近づいた、機器を抜いた | クリックを出さない。押しているボタンがあれば解放 |
| タップから0.5秒以内に、その近く(位置許容度（タッチ）、既定5mm)をタップした | 2回目のクリックを、1回目のタップの所で出す。タッチ操作補正が切りのときは寄せない |

指は触れるたびに数mmずれ、マウスのダブルクリックの許容の幅(`LK_DBL_W`、既定10ドット)を超えやすい。そこでタッチスクリーンに限り、2回目のタップを1回目の所に寄せ、ダブルクリックかどうかはマウスと同じ判定にかける。許容の幅は、ユーザ環境設定の〈ＰＤ属性〉の「位置許容度（タッチ）」(`LK_TCH_DBL`、0.1mm単位、1〜15mm、既定5mm)で、マウスの「位置許容度（マウス）」(`LK_DBL_W`、ドット)とは別に持つ。マウスの値を変えても、タッチの寄せの範囲は変わらない。長さは画面の上のmmで決め、触れた画面の大きさで画素に直す(下の「画面の大きさとタッチ操作補正」)。X1 Yogaの14型(309.9×174.3mm)で倍率200%(論理ビュー1280×720)なら、5mmは20画素である。寄せるのはクリックの座標だけで、動いたかどうか(許容の幅を超えたらドラッグ)は指の実際の位置で判定する。ウインドウマネージャやプログラムの判定には手を入れず、どの機器かを知っている入力の層で行う。

長押しの時間は「長押し時間（タッチ）」(`LK_TCH_HOLD`、0.3〜3秒、既定1秒)、動かしていないとみなす許容の幅は、画面の幅の1/128(8画素以上)とする。2560画素の画面で20画素(X1 Yogaの14型で約2.4mm)、1920画素で15画素である。指の位置は触れている間に少しずつ揺れるので、マウスのドラッグの閾値より広くとる。許容の幅の中の動きは入力のキューに入れないが、ポインタの位置(`ts_hid_pointer`)は指に合わせて動く。クリックと副ボタンのクリックは、触れた所の座標で出す。副ボタンは、離したときでなく長押し時間に達した時点で押す。マウスの副ボタンを押したときと同じく、指が触れたままメニューが開き、そのまま指を動かして項目を選べる。動かさずに離したときは、メニューは開いたまま残る(10.8)。副ボタンを押している間の印は、BTRONの標準のポインタの形の、メニューを出しているときの形とし、専用の絵や窓は描かない。

長押しの判定は入力の層(`device/usb/hid.c`の`ts_hid_read`の中の整形、`touch_shape`)で行い、ウインドウマネージャでもHIDのレポートの読み取りでも行わない。理由は次のとおりである。

- タッチスクリーンの指であることを知っているのは入力の層だけである。ウインドウマネージャが受け取るイベント(`T_HIDEV`)には、どの機器から来たかがない。ウインドウマネージャで行うと、マウスの主ボタンの長押しまで副ボタンになってしまい、マウスとTrackPointの動きが変わる。
- 時間で決まる判定は、キーの受付時間やキーリピートと同じに、入力の層の整形(`shape`)が持つ時刻の仕組み(`shape_due`)で待てる。レポートの読み取り(USBの管理タスク)で行うと、指を動かさずにいる間にレポートが来ない機器では、1秒たっても判定できない。
- BTRONでは、ポインティングデバイスの入力を、プログラムには機器によらない主ボタンと副ボタンの事象として渡す。指をマウスの事象に置き換えるのは、その抽象化の内側の仕事である。WindowsもタッチをマウスのメッセージにするのはOSの入力の層で、アプリケーションには主と副のボタンとして届く。

触れたことの印は、入力のキューの中の内部の印(`TCH_TOUCH`、`TCH_CANCEL`)で整形に渡す。`T_HIDEV`の形は変えない。ポインタの形は、入力の層が`knl_pt_hold`(`outer_kernel/wm/pointer.c`)を呼んで切り替え、プログラムが`wm_set_pointer`で設定した形は変えずに、その上に重ねて表示する。

#### 画面の大きさとタッチ操作補正

指に与える長さ(ダブルタップの寄せの範囲、つまみの当たりを広げる幅、10.4.6)は、画面の上のmmで決め、触れたタッチスクリーンの大きさで論理ビューの画素に直す。指の太さとずれは画面の画素の細かさによらず、mmで決まるからである。以前は画面の幅の1/48を約5mmとしていたが、それは14型の画面にだけ当てはまり、3.5型の液晶では1.5mmにしかならなかった。

大きさは、HIDのディスクリプタのX、YのフィールドのPhysical Minimum、Physical Maximum、Unit、Unit Exponentから読む(`phys_ext10`)。Unitがセンチメートル(0x11)かインチ(0x13)のときだけ長さとし、Physicalが無いときは論理の範囲を使う。Unit Exponentは4ビットの2の補数で書く機器が多いので、4ビットに収まる値はそう読む。Linuxの`hidinput_calc_abs_res`(入力の機器の分解能を単位あたりの数にする)と同じ読み方である。Windowsもタッチスクリーンの機器に、物理の大きさを書くことを求めている。画面との対応は、XとYの長さから対角線の長さ(0.1mm単位)を求め、論理ビューの対角線の画素の数で割る(`touch_px`、100mmあたりの画素の数)。対角線で比べるので、タッチの面と画面の縦横比が少し違っても同じ値になる。HIDを話さないGT911は、ボードの表(`tpanel.c`)の液晶の対角線(3.5型で88.9mm)を`knl_hid_mt_size`で渡す。大きさが分からない機器は、幅を240mm(画面の幅の1/48を5mmとしていた今までの決め方)、1mmあたり4画素以上として扱う。

ポインタのイベントに、触れた画面の大きさを付けて入力の層から外へ出す。リングと整形の出口の列に、イベントごとに100mmあたりの画素の数を持ち(指でないものは0)、`ts_hid_read`が返したイベントの値を`knl_hid_taken_touch`で答える。`T_HIDEV`の形は変えない。ウインドウマネージャは押下を読むたびにこれを尋ねて覚え(10.4.6)、指の押下だけ、つまみの当たりを広げる。

ユーザ環境設定の〈ＰＤ属性〉の「タッチ操作補正」(`LK_TCH_ON`、既定は入り)を切ると、つまみの当たりをマウスと同じにし、ダブルタップの2回目を寄せない。部品の「位置許容度（タッチ）」と「つまみ範囲（タッチ）」は、切りのときは灰色にして操作できなくする。長押しの右ボタンは、切りのときも働かせる。指には副ボタンがほかに無く、切るとメニューを指で開けなくなるからである。長押しの時間は入りでも切りでも「長押し時間（タッチ）」で変えられる。値は外観設定テーブルの項目(`LK_TCH_ON`、`LK_TCH_DBL`、`LK_TCH_HIT`、`LK_TCH_HOLD`)で、ユーザ情報の実身に`TOUCH_ADJUST`、`TOUCH_TOLERANCE`、`TOUCH_HANDLE`、`TOUCH_HOLD`として保存する(`lib/libconf/conf.c`の表)。ウインドウマネージャはほかのポインタの属性と同じく`T_HIDATTR`の`tch_off`、`tch_dbl`、`tch_hold`にして入力の層へ渡す(`knl_input_sync`)。既定の値は今までの動き(5mm、1秒)と同じである。

#### 二本指のスクロール

タッチスクリーンの2本の指を同じ向きに動かすと、ホイールのイベント(`HID_EV_WHEEL`)にする。ウインドウマネージャもプログラムもマウスのホイールと同じに受けるので、仮身一覧、文章、表計算、パネルの一覧などは手を入れずに二本指で動く。判定は長押しと同じく入力の層で行う。フレームを読む側(`dg_frame`、`dg_multi`)が2本の指の中点と間の距離を内部の印(`TCH_TWO`、イベントの種類`HID_EV_TWO`)で整形に渡し、整形(`two_shape`)がホイールの段にする。この内部のイベントは`ts_hid_read`から出さず、入力の実身が見せるコピーにも入れない。`T_HIDEV`の形は変えない。

| 指の動き | 入力のキューに入るもの |
| --- | --- |
| 1本目が触れているところに2本目が触れた | 1本目の、まだ出していない押下(タップ待ち、長押し待ち)を取り消す。クリックも副ボタンも出さない。ドラッグしていたら主ボタンを、長押しで副ボタンを押していたら副ボタンを、そこで離す |
| 2本が同じフレームで触れた | 何も出さない |
| 2本の中点が3mm動いた(距離の変化より大きく) | スクロールとする。動いた向きの大きいほう(縦か横)に決め、2本が触れている間は変えない。中点が「1段の動き」(既定10mm)動くごとにホイールを1段 |
| 2本の距離が3mm変わり、その変化が中点の動きより大きい | ピンチとする。スクロールにしない |
| 動いている途中で離した | 離す前0.1秒の速さでスクロールを続け、ゆるやかに止める(慣性) |
| 動かさずに、触れてから0.5秒以内に2本とも離した | 2本が触れた所で副ボタンのクリック |
| 3本目が触れた | 2本の組をやめる。タップにもしない。2本に戻れば新しい組としてやり直す |
| 1本が離れ、1本が残った | スクロールを止める。残った指はポインタにも、ドラッグにもしない。すべての指が離れるまで続く |

向きは、Windowsのタッチと同じく、画面に見えている内容が指に付いてくる向きとする。指を下へ動かすと内容が下へ動く。これは、マウスのホイールを奥へ回した(`HID_WHEEL_V`で`dz`が正、上の内容を見せる)のと同じ向きである。横は、指を左へ動かすと内容が左へ動き、横のホイール(`HID_WHEEL_H`、AC Pan)を右へ回した(`dz`が正)のと同じになる。横のホイールのイベントは前からあり、チルトホイールのマウスのAC Panと同じ形で出すので、新しい形は作らない。マウスのホイールの向きの設定は無いので、指の向きはこの1つに決まる。macOSのトラックパッドの「ナチュラルスクロール」に当たる向きで、マウスの向きとは逆に見えるが、指で画面の内容をつかんで動かす形なので、これが自然である。

横のホイールを受ける側は、イベントの`code`(`HID_WHEEL_V`か`HID_WHEEL_H`)を見る。横のスクロールを持つもの(仮身一覧と文章、表計算、マイクロカードの一覧)は横に動かし、持たないもの(パネルの一覧とタブの中身、`lib/libui`の小物、スライド、トレーの表示、マイクロカードのカード、端末)は横のホイールを捨てて、縦に読み替えない。以前はパネルの一覧などが`code`を見ずに縦として受けていたので、チルトホイールのマウスを横に倒すと一覧が縦に動いた。

強制終了のウインドウがすべての入力を取っている間(デスクトップが入力を読まない間、5.5.3)は、二本指の操作を入力の層で捨てる(`knl_fq_grabbing`)。整形はデスクトップが読むときに行うので、取っておくと、読み始めたときに裏のウインドウへホイールが行くためである。終わりの印だけは取消(`TW_CANCEL`)にして渡し、整形が持っていた状態を捨てさせる。慣性で流れている途中で0.2秒より長く読まれなかったときも、そこで止める。

ホイールの1段に当たる指の動きは、画面の上のmmで決める。長さは触れたタッチスクリーンの大きさで論理ビューの画素に直す(`touch_px`)。既定の10mmは、仮身一覧の1段(48画素)が、X1 Yogaの14型を倍率200%で使うとき約11.6mm、Surface Go 2の10.5型を150%で使うとき約8.3mmなので、その間に取った。速さはユーザ環境設定の〈ＰＤ属性〉の「スクロール速度」(`LK_TCH_STEP`、0.1mm単位、3〜30mm)で変える。1段の画素の量はプログラムが決めるので、指と内容がぴったり同じ量だけ動くとは限らない。

スクロールにするか、ピンチにするか、タップのままかは、2本の中点の動きか距離の変化のどちらかが3mmに達したときに一度だけ決める。指の位置は触れている間に揺れるので、1本目の指の許容の幅と同じく、揺れで決まらないようにするためである。決まったら、2本が触れている間は変えない。縦か横かも、決めたときの動きの大きいほうに固定する。斜めの動きで縦と横の段が混ざると、横のホイールを縦のスクロールとして受けるプログラムで、内容が逆に動くためである。

指を離した後の惰性(慣性スクロール)は入れる。Windows、Android、iOSのタッチの操作では、はじいた後に内容が流れて止まるのが当たり前で、無いと長い一覧を何度もなでることになるためである。離す前の0.1秒の中点の速さが50mm/秒以上なら、その速さで16msごとにホイールの段を出し、16msごとに速さを245/256にする(約0.36秒で1/eになる)。速さが15mm/秒を下回ったら止める。速さは1500mm/秒までとする。たとえば200mm/秒で離すと約73mm分、既定の換算で7段ほど流れる。次に指が触れたら、そこで止める。時間で進むものなので、長押しと同じく整形の時刻の仕組み(`shape_due`)で待つ。

2本の指のタップは、副ボタンのクリックにする。Windowsでは、タッチパッド(高精度タッチパッド)の二本指タップが右クリックで、タッチスクリーンの二本指タップはアプリケーションに渡すジェスチャ(`GID_TWOFINGERTAP`)である。TessronOSでは、副ボタンがメニューで、指で副ボタンを出す方法が1秒の長押ししか無いので、タッチスクリーンでも二本指タップを副ボタンにする。長押しとは次のように矛盾しない。2本目が触れた時点で1本目の長押しの待ちは取り消すので、二本指タップの後に長押しの副ボタンが重ねて出ることはない。1本目がすでに長押しで副ボタンを押していたら(メニューが開いている)、2本目が触れたときに副ボタンを離し、その後の二本指タップは副ボタンのクリックにしない。1本目がドラッグしていたときも、タップにしない。クリックの位置は、2本が初めてそろって触れたときの中点とする。ホイールのイベントも同じ位置で出すので、ウインドウマネージャは、指を置いた所のウインドウに渡す。

手のひら(Confidenceが0)の接触は、1本目の指と同じく数えない。2本目の指にも、3本目にもならない。ペンが近づいたら、2本の指の操作も取り消し、何も出さない。機器を抜いたときも同じである。

ピンチ(2本の距離が大きく変わる動き)は、今はスクロールにしないだけで、拡大縮小は作らない。将来は、ピンチと決まった後の距離の比を、Ctrlを押しながらのホイールと同じ拡大縮小の段にするか(ブラウザはCtrl+ホイールで拡大する)、別のイベントの種類(`HID_EV_ZOOM`、`dz`に倍率の千分率)をウインドウマネージャとプログラムの通知(`OB_E_WHEEL`と並ぶもの)に足すかのどちらかとする。整形はピンチと決めた時点の距離(`tw_d0`)を持っているので、その口はここに足す。

二本指の操作は、ユーザ環境設定の〈ＰＤ属性〉の「二本指スクロール」(`LK_TCH_SCR`、既定は入り)で切れる。切ると今までの動きに戻り、2本目の指は何もせず(1本目のタップはクリックのまま)、二本指タップも無い。「スクロール速度」は、切りのときは灰色にして操作できなくする。値はユーザ情報の実身に`TOUCH_SCROLL`、`TOUCH_SCROLL_STEP`として保存し(`lib/libconf/conf.c`の表)、ウインドウマネージャが`T_HIDATTR`の`tch_noscr`、`tch_scr`にして入力の層へ渡す(`knl_input_sync`)。タッチ操作補正とは別に持つ。補正を切っても、二本指のスクロールは働く。

試験は、試験のソフトウェアのUSBコントローラ(6.3.2)に、ペンとタッチスクリーンの2つのインタフェースを持つ機器を差して行う(`tests/ktest/ktest_digi.c`、`make KTEST=1 KTONLY=digi`)。Input ModeのFeature Reportが送られること、タップがクリックになること、1秒に達した時点で副ボタンが押され、離すまでポインタがメニューの形になること、動かすとドラッグになること、2本目の指、2つのレポートに分かれたフレーム、手のひら、二本指の操作、ペンのTip SwitchとBarrel Switch、ペンが近い間のタッチ、触れたまま抜いた機器を確かめる。試験の機器のタッチスクリーンは309.9×174.3mmとディスクリプタに書いてあり、`test_digi_reach`が、指の押下で100mmあたりの画素の数がその大きさと画面から求めた値になること、つまみの当たりを広げる幅が設定の4mmと8mmに従うこと、タッチ操作補正を切ると0になること、ペンの押下と入れた押下は指でないこと、約3.8mm離れた2回のタップが既定で寄り、マウスの位置許容度を4ドットにしても24ドットにしても寄り、タッチの位置許容度を1mmにすると寄らず、タッチ操作補正を切ると寄らないこと、長押し時間を0.5秒にすると補正が切りでも0.5秒で副ボタンになることを確かめる。`test_digi_two`は、二本指の操作を既定の設定で確かめる。2本の指をゆっくり2.5段分下へ動かすとホイールが奥へ2段(`dz`の和が2)、上へ動かすと手前へ2段、左へ動かすと横のホイールが右へ2段になり、ホイールのイベントは2本が触れた所の中点で出ること、2本の指を長押しの時間より長く置いてもクリックも副ボタンも出ないこと、1本が離れた後に残った指を大きく動かしてもポインタもドラッグも出ないこと、速く動かして離すと動いた分より多く流れて止まること、両方を広げるピンチと1本を止めたピンチでは何も出ないこと、2本を同時に触れて離すと中点で副ボタンのクリックになり、1本目の後に2本目が触れて順に離しても同じであること、長押しで副ボタンを押している所に2本目が触れると副ボタンを離してその後のタップは出ないこと、ドラッグ中に2本目が触れると主ボタンを離し、その後の1本目だけの動きはドラッグにならないこと、3本の指では何も出ないことを確かめる。今までの2本目の指と2つのレポートに分かれたフレームの確かめは、二本指スクロールを切って流し、今までの動き(1本目のタップがクリックになる)を確かめる。ディスクリプタの解析は、Wacomの独自のページとTouch Padも含めて確かめる。


### 6.4.2 I2Cのタッチパネルのコントローラ(GT911)

HIDを話さないタッチパネルのコントローラとして、GoodixのGT911とその系統(GT9110、GT912、GT927、GT928、GT967など)を扱う(`device/i2c/gt911.c`)。Raspberry Pi 4の3.5インチの液晶(3.6.7)が載せている。レジスタとその読み方は、Linuxの`drivers/input/touchscreen/goodix.c`と同じにした。

| レジスタ | 内容 |
| --- | --- |
| `0x8140` | 製品の番号(4文字、"911"と0)、続く2バイトがファームウェアのバージョン |
| `0x8047` | 設定。バージョン、Xの範囲とYの範囲(2バイトずつ、下位が先)、報告する接触の数の上限(下位4ビット)、Module_Switch1(下位2ビットがINTの出し方。0が立上り、1が立下り、2がLow、3がHigh) |
| `0x814E` | 座標の状態。ビット7がフレームの用意ができたこと、下位4ビットが接触の数。続く`0x814F`から1つの接触が8バイト(追跡の番号、X、Y、大きさ、予備) |

レジスタのアドレスは16ビットで、上位のバイトから送る。I2Cのアドレスは、リセットが終わるときのINTのレベルで0x5Dか0x14に決まる。リセットのピンを動かさない基板では、基板が決めたほうになるので、両方を試す。製品の番号が「9」で始まるものを、この系統とする。

INTが来たら、状態と最初の接触を1回で読み、接触が2つ以上なら残りをもう1回で読む。用意ができていなければ、1ミリ秒ごとに20ミリ秒まで読み直す。読んだら`0x814E`に0を書いて、バッファをコントローラに返す。触れている間は走査のたびにフレームが来て、最後の指が離れると接触のないフレームが来る。

接触は、入力の層の口(`knl_hid_mt_attach`、`knl_hid_mt_contact`、`knl_hid_mt_sync`、`device/usb/hid.c`)に渡す。Linuxのinputのマルチタッチの「スロット」の形(type B)にならい、フレームの中で触れている接触を追跡の番号と位置で1つずつ渡し、最後にフレームの終わりを渡す。フレームに無い接触は離れたものとする。入力の層は、HIDのタッチスクリーンのフレームと同じ処理(1本目の指がポインタ、6.4.1の長押しの右クリックとダブルタップの寄せ、二本指のスクロール)に通す。HIDのレポートの形に作り直して渡すことはしない。

座標は、コントローラの設定のXとYの範囲で読む。基板の取り付けの向きで反転し(DPIの液晶はX)、コントローラの長い辺が画面の長い辺と違えば(480×640のパネルに640×480の画面)XとYを入れ替える。Linuxの`touchscreen_apply_prop_to_x_y`と同じく、反転はコントローラの軸で行ってから入れ替える。

INTは基板の側が届ける。Raspberry Pi 4では、GPIOの検出(GPREN、GPFEN、GPHEN、GPLEN)をコントローラの設定の出し方に合わせ、GPIOのブロックの最初の割込み(SPI 113)で受ける(`gpio_irq_set`、`device/gpio/gpio_bcm2711.c`)。レベルの検出は受けたときに止め、読んだ後に掛け直す。割込みが1秒来ないときも1回読み、その読み出しでフレームが見つかることが3回続いたら、INTが届いていないとして、10ミリ秒ごとに読む形に変える。

I2Cは、2本のピンをソフトウェアで動かす(`device/i2c/i2c_gpio.c`)。どちらの線もオープンドレインで、出力の0にして引き下げ、入力にして放す。クロックは約100kHzで、装置がSCLを引き下げたまま待たせること(クロックストレッチ)にも従う。バイトの途中で止まった装置がSDAを引き下げたままのときは、SCLを9回まで打って放させ、ストップを作る(I2Cの仕様書の3.1.16)。

試験は、偽のピンと、その上で線のレベルを1つずつ追ってGT911のように振る舞う偽の装置で行う(`tests/ktest/ktest_tpanel.c`、`make KTEST=1 KTONLY=tpanel`)。スタートとストップ、アドレスと書いたバイト、応答、レジスタの読み出し、クロックストレッチ、SDAを引き下げたまま残った装置を作り、I2Cの読み書き、答えないアドレス、待ちの時間切れ、バスの解放を確かめる。GT911としては、0x5Dに装置が無いときに0x14で見つかること、設定の読み取り、INTで届いたフレームがタップでクリック、1秒の長押しで副ボタン、動かしてドラッグになること、2本目の指がポインタにならないこと、フレームのたびにバッファが返されることを確かめる。2本目の指は、既定ではドラッグ中に触れるとそこで主ボタンを離し、二本指スクロールを切ると今までどおり1本目が離れるまでドラッグが続く。二本指の操作は`test_tpanel_two`で、2本の指を2.5段分上へ動かすとホイールが手前へ2段になり、1本目の押下も、1本が離れた後の残りの指の動きも出ないこと、ピンチでは何も出ないことを確かめる。480×640の設定のコントローラが、横長の画面でXとYを入れ替え、Xを反転すること、INTが無いときに一定の間隔で読むことも確かめる。

## 6.5 サウンド

サウンドデバイス`snda`は、B-right/Vのサウンドデバイスの仕様(データ番号と構造体、`include/ts/snd.h`)に従う。その仕様向けに書かれたプログラムはそのまま使える。

| データ番号 | 内容 |
| --- | --- |
| 0、1 | 再生するPCMを書き込む。録音したPCMを読み出す |
| `DN_SDPCMMODE` | サンプリングレート(8kHzから48kHz)、形式(μ-law、8bit、16bit)、モノラルとステレオ |
| `DN_SDPCMCTL` | 停止、再生、録音、繰り返し再生 |
| `DN_SDPCMCNT`、`DN_SDPCMENDCNT` | 処理したバイト数と、停止するバイト数 |
| `DN_SDPCMBUFSZ` | PCMバッファのサイズ(デフォルト32KB、最大1MB) |
| `DN_SDGAININ`から`DN_SDVOLAUX2` | 入力と出力の音量 |
| `DN_SDSTAT` | TessronOSの追加。再生している出力先の種類、標本化周波数、チャネル数、渡したフレームの数など(`SDStat`) |
| `DN_SDOUTS` | TessronOSの追加。出力先の一覧(`SDOut`の並び。先頭は自動) |
| `DN_SDOUTSEL` | TessronOSの追加。選んだ出力先と、いま鳴らしている出力先(`SDOutSel`) |
| `DN_SDMIXER`、`DN_SDMIXSET` | TessronOSの追加。ミキサーの全体とプログラムごとの音量と消音を読む、設定する(6.5.6) |

チャネルはプロセスとユニットの組ごとに1つ持ち、複数のプログラムが同時に鳴らした音はミキシングして出力する。

### 6.5.1 出力先

サウンドデバイスは、そのとき使える出力先の1つで鳴らす。出力先はIDで呼び、IDは起動をまたいで変わらない。

| ID | 出力先 |
| --- | --- |
| `auto` | 自動。次の順で、そのとき音を出せる最初の出力先 |
| `usb:VVVV:PPPP@C-R.h` | USBオーディオの機能。VIDとPID(16進)と挿した場所(コントローラの番号、ルートポート、ハブのポート) |
| `i2s` | Raspberry Pi 5のI2S0(GPIO 18〜21)のDAC |
| `hdmi0`、`hdmi1` | Raspberry Pi 5のHDMIのポート |

自動の順は、USBオーディオの機能(来た順)、I2S、HDMI0、HDMI1である。I2SのDACはつながっているかどうかを確かめる手段がなく、I2Sはいつも出力先として出るので、Raspberry Pi 5で自動の出力先がHDMIになることはない。HDMIで鳴らすには選ぶ。

出力先は、システムの実身のレコード8に`SELECT ID`を書くと選べ、すぐに切り替わる。機器の設定の実身に`SOUND_OUT ID`の行を書くと、カーネルが起動時とその実身が書き換えられたときに読み(`outer_kernel/wm/uconf.c`)、次の起動からも使う。システム環境設定は両方を書く(11.6)。選んだ出力先がないとき(USBの機器を抜いた、HDMIの画面が音を受けない)は、自動の順で選んだ先で鳴らす。再生中は0.5秒ごとに出力先を選び直し、選んだ出力先が戻れば(挿し直せば)そこへ移る。USBの機能は、同じIDのものがなければ、同じVIDとPIDのものを別の場所に挿したものとみなす。

切り替えは再生中でもできる。今のバックエンドを止め、新しい出力先で始め直す。チャネルは止めず、次のフレームから新しい出力先の標本化周波数に変換して続ける。鳴らしている出力先の機器が去ったときも、すぐに次の出力先へ移る。行き先がないときだけチャネルを止める。移ったことはコンソールに出す(`snd: the stream moves from A to B`)。

プログラムは、出力先の一覧を`DN_SDOUTS`で、選んだものと鳴らしているものを`DN_SDOUTSEL`で読む。一覧の各項目(`SDOut`)は、ID、つながっている機器の名前(USBの機能の製品名、HDMIの画面のEDIDの名前)、種類、フラグ(選ばれている、鳴らしている、いまは音を出せない、音量がある)、鳴らしている間の標本化周波数とチャネル数である。サウンドデバイスの実身ではレコード24と25にあたる(8.4)が、実身からは選べない(`E_RONLY`)。出力先はシステム全体の設定なので、保護されたシステムの実身のレコード8で選ぶ(付録Aの権限の表)。レコード8は、`OUTPUT`(鳴らしている出力先のID、ないときは`none`)、`SELECT`(選んだ出力先)、`RATE`、`CHANNELS`の行と、出力先ごとの`OUT`、`OUT_KIND`(`usb`、`i2s`、`hdmi`。自動は`none`)、`OUT_FLAGS`(`SND_OF_*`)、`OUT_NAME`の組を持つ。

### 6.5.2 RP1のI2S

Raspberry Pi 5は、ヘッダのGPIO 18〜21につないだDACボード(PCM5102Aの類)に、RP1のI2S0から出す(`device/snd/snd_rp1.c`)。音声のPLLを1536MHz(50MHzの水晶の30.72倍)にして25で割った61.44MHzを作り、clk_i2sでさらに20で割って3.072MHzのビットクロックにする。48kHzで1フレーム64クロック(32ビットのスロットが2つ)である。DMAは、256フレームのブロック16個(85ミリ秒)のリングを、I2S0の要求に合わせて送信のFIFOに運ぶ。割込みは使わず、USBの管理タスクが数ミリ秒ごとにDMAの位置を見て、終わったブロックに次の音を詰める。

I2S0のステレオの組ごとの送信と受信の許可(TERとRER)は、リセットの後に有効になっている。DMAのレジスタに書いたワードは有効な送信の組に順に配られるので、4組とも有効のままだと1フレームに8ワードを取り、音が4倍の速さで進む。設定の前に4組すべてを無効にし、第1組だけを有効にする。2026年10月8日の実機の記録では、ブロックが毎秒700ほど(48kHzの約3.7倍)進み、動画が早回しになった。この直しはその原因と見ているが、実機で未確認である。

確かめるために、流れを始めた直後に次の行をコンソールに出す。

| 行 | 内容 |
| --- | --- |
| `i2s0 clocks:` | RP1の周波数計で数えたpll_audio、pll_audio_sec、clk_i2sの周波数(clk_i2sは3072kHzになるはず)と、PLLのレジスタから計算したpll_audio_core、clk_i2sのレジスタ |
| `i2s0 interface:` | I2S0の送信の組の数、CCR、TERの今の値と最初に見つけたときの値、TCR、TFCR、DMACR |
| `i2s0: N blocks in M ms, X a second` | リングの進み。始めてから30秒は5秒ごと、その後は60秒ごと。48kHzなら毎秒187.5ブロック |

PLLがすでに同じ設定でロックしていれば作り直さない。比べるのは、ロック、参照の分周(REFDIV)が1であること、電源のレジスタ(PWR)がすべて動作中(端数を使うのでDSMPDも0)であること、FBDIVの整数と端数、PRIMの2つの分周である。

### 6.5.3 HDMIの音(Raspberry Pi 5)

画面はファームウェアが出し続け(10.2)、カーネルはHDMIの映像の設定に触れない。音に要るものはHDMIのコントローラの中にあり、`device/snd/snd_hdmi.c`だけが扱う。

| もの | 内容 |
| --- | --- |
| MAI | コントローラごとの音声の入力。2つのコントローラが共有する`hd`のブロックにある。IEC 60958のサブフレームのFIFOと、DVPの108MHzから作る標本化のクロック(2250で割って48kHz)、形式(48kHz、PCM、2チャネル) |
| HDMIの本体 | 音声パケットの設定(使うチャネル、平坦なサンプルを0にする)、音声クロックの再生のNとCTS(Nは6144、CTSは画素クロックのkHzの値)、パケットRAMのAUDIO InfoFrame(2チャネル、ほかは流れのとおり) |
| DMA | 40ビットのDMA(`dma40`)のチャネル6。256フレームのブロック16個のリングの制御ブロックを回し、MAIの要求(HDMI0はDREQ 10、HDMI1は17)に合わせてFIFOに運ぶ |

サンプルは1フレーム2ワードのIEC 60958のサブフレームにする。下位4ビットがプリアンブル(192フレームごとの先頭の左が8、ほかの左が2、右が4)、24ビットの音声の欄の上位16ビット(ビット12〜27)がサンプル、ビット30がチャネルの状態、ビット31がビット4〜30の偶数パリティである。チャネルの状態は、民生用、PCM、著作権の主張なし、48kHz、16ビットを表す。DMAは止まらずにリングを回るので、管理タスクが見に来るのがリングの4分の3より遅れたときは、リングを一周したものとして、DMAがいるブロックのほかをすべて詰め直す(古い音が繰り返して聞こえる)。

どのポートを使えるかは、起動時にファームウェアに尋ねる。ファームウェアが駆動している画面とその番号(2がHDMI0、7がHDMI1)、画面のEDID(名前の記述子と、CEAの拡張の基本の音声のフラグか音声データブロック)、画素クロック(画面の表示のタイミング)である。ファームウェアが駆動していないポートのレジスタには触れない(クロックが入っていないことがある)。流している間は1秒ごとにポートを見て、ホットプラグの線が抜けた、DVIになった、表示のタイミングのレジスタ(HORZA、VERTA0、VERTB0)が変わった(モードが変わった)ときは流れを終える。サウンドデバイスはそれを出力先が去ったものとして選び直し、HDMIがまだ音を出せれば、その時の画素クロックでCTSを作り直して始め直す。ファームウェアが画面の一覧に答えないときは、どのポートが画面を出しているか分からないので、HDMIの音を扱わない。DVIで出している画面、EDIDにCEAの拡張がないか音の記述がない画面、ホットプラグの線が抜けているポートは、「いまは音を出せない」出力先として一覧に出し、選んでも鳴らさない。MAIの閾値のレジスタは、BCM2712のD0のステッピング(表示のハードウェアHVSのバージョンが0x54)で配置が違うので、バージョンを見て書き分ける。

流れを始めると`hdmiN plays at 48000 Hz`の行に画素クロック、MAIの制御、HDMIの方式、パケットの設定を出し、リングの進みをI2Sと同じ形で出す(`hdmiN: N blocks in M ms`)。`config/config.h`の`CNF_SND_HDMI`を0にすると、HDMIの音を扱わない(レジスタに触れない)。実機で未確認である。

### 6.5.4 実機での確認

QEMUにはI2SもHDMIの音もないので、出力先の選択と切替えはUSBオーディオの機能でカーネル内の試験(`ktest_snd`の`test_outputs`。2つ目の機能をQEMUのモニタで挿し、選び、再生中に切り替え、選んだ機能を抜いて自動の先に移ることと、挿し直して戻ることを見る)で確かめ、I2SとHDMIは実機で確かめる。`make SNDTEST=1`を付けたRaspberry Pi 5のイメージは、起動の25秒後に次の確認を順に行い、コンソールに`sndtest:`の行を出す(`kernel/sysdepend/rpi5/sndtest.c`、build-and-run.mdの4.6.1)。どれも小さな440Hzの音を鳴らし、時間の上限を持ち、失敗しても次に進む。

| 確認 | 合格の条件 |
| --- | --- |
| `outputs` | 出力先が自動を含めて2つ以上あり、`i2s`がある |
| `i2s` | clk_i2sの実測が3072kHzの1%以内、リングの進みが2秒間で毎秒187.5ブロックの3%以内 |
| `hdmi0`、`hdmi1` | リングの進みが毎秒187.5ブロックの3%以内。音を出せないポートは飛ばす |
| `usb` | USBオーディオの機能が毎秒48000フレームの5%以内を取る。機能がなければ飛ばす |
| `move` | 1つのチャネルを鳴らしたまま、音を出せる出力先を順に選び、どれでもチャネルが鳴り続け、処理したバイト数が進む |

### 6.5.5 システムの音を鳴らすインタフェース

システムの音(ブザー、押下音、離し音、画面印刷の秒読み、設定の小物の〈試聴〉)は、すべてウインドウマネージャの音のモジュール(`outer_kernel/wm/beep.c`)が鳴らす。このモジュールは自分のタスクでサウンドデバイスの実身を開き、1つのチャネルとして書くので、どれも選んだ出力先(6.5.1)で鳴る。音ごとにチャネルを一度止めてから書き直すので、前の音が途中で切られても次の音は断られない。

| 呼び方 | 待つか | 内容 |
| --- | --- | --- |
| `wm_beep(what)` | 待たない | ウインドウ層とデスクトップのクリック音、ブザー、秒読み。スピーカーを切っている(`LK_SPEAKER`が0)ときは鳴らさない。最後に頼まれたものを鳴らす |
| `wm_beep_try(what)` | 鳴り始めるまで待つ(3秒まで) | 〈試聴〉。スピーカーを切っていても鳴らし、鳴り始めたら`E_OK`、音を出せる出力先がなければ`E_NOSPT`を返す |
| システムの実身のレコード8に`PLAY 音 [tone]` | 同上 | プロセスから`wm_beep_try`を呼ぶインタフェース。音は`buzzer`、`press`、`release`、`tick`、`long`、`test`(880Hzを0.5秒)。`tone`を付けると、レコード1にWAVがあっても、メタデータの高さと長さの音を鳴らす(ユーザ環境設定が設定中の音を聞かせるため)。書込みの戻り値が鳴ったかどうかである |

音の流れの止め方は、既定ではLinuxのPipeWireやPulseAudioと同じにする。鳴り始めに無音を足さず(`SNDHW`の`lead_ms`はどの出力先も0)、音は遅れない。最後のチャネルが止まっても、しばらくは無音を送り続けてから流れを止める(`tail_ms`)。HDMIは5秒、I2Sは2秒、USBオーディオは0である。その間に次の音が来れば、流れは続いているので欠けない。止まった後の次の音は、無音を足さずにすぐ流れを開き直して鳴らす。

HDMIの画面やテレビは、音のパケットが始まってから数百ミリ秒たってから音を出し始めることが多く、流れを開き直した直後の短い音(100ミリ秒のブザー)は欠けることがある。そのため、システム環境設定のサウンドのページに「出力を止めずに流し続ける」のスイッチを置く(11.6、既定は切)。入れると(`knl_snd_keep`、システムの実身のレコード8に`KEEP 1`、機器の設定の`SOUND_KEEP 1`で次の起動にも残る)、選んだ出力先の流れを、鳴らすものがなくても止めずに無音を送り続ける。鳴らすものが何もないときにも流れを始め、止めるのは、出力先を替えたとき、出力先が去ったとき(USBの機器を抜いた、HDMIの画面が抜かれたかDVIになったか表示のモードが変わった)だけで、その後すぐ選び直した先でまた始める。流れが止まっている間も0.5秒ごとに出力先を探し、来たら始める。

このスイッチはどの出力先にも効かせる。I2SのDAC(PCM5102Aの類)は、ビットクロックとフレームクロックが入り続け、0のサンプルが続いても困らない(続く0は自分で消音にする)。止めて開き直すたびに出ることのあるクロックの切れ目の雑音が無くなる分、むしろ良い。USBオーディオの機器も、無音のアイソクロナス転送が続くだけである。代わりに、流れている間はUSBの管理タスクが数ミリ秒ごとに起きてリングを満たすので、そのわずかな処理がずっと続く。既定を切にしているのはそのためである。

試験は`ktest_snd`の`test_keep`で、既定では音が終わると流れが止まること、`KEEP 1`で鳴らすものがないまま流れが始まり、音が終わった後も流れ続けること、`KEEP 0`で止まること、機器の設定の`SOUND_KEEP`から入ることを確かめる。画面は`tools/tests/ui_sound.steps`で、スイッチを入れると流れが始まり、切ると止まることを見る。QEMUにはHDMIとI2Sがないので、HDMIの5秒の続きと画面の変化による止まり方は実機で確かめる。

### 6.5.6 ミキサー

いくつものプログラムが同時にサウンドデバイスを開いて鳴らすと、それぞれのチャネルの音を混ぜて1つの流れにする。チャネルはプロセスとユニットの組(`snda`、`snda0`から`snda3`)ごとに1つで、同時に16まで持つ。1つのプロセスがいくつもの流れを持つとき(ブラウザ)は、ユニットを分けて開く。カーネルのタスク(ブザーとクリック音のタスク)はタスクごとのチャネルを持つ。

| 段 | すること |
| --- | --- |
| プログラムの音量 | チャネルのサンプルに、そのプログラムの音量の2乗を掛ける(50なら4分の1、12dB下がる)。消音なら0を掛ける |
| 混ぜる | 鳴っているチャネルを足す |
| 全体の音量 | 足したものに、左と右それぞれの全体の音量の2乗を掛ける。消音なら0 |
| ソフトリミッタ | 16ビットに収める。絶対値が24576(0.75)までは、そのまま、それを超えた分`e`は`24576 + 8191 × e / (e + 8191)`に曲げる。32767に近づくが届かず、境目で傾きが1のまま続くので、切ったときのような濁った音にならない |

プログラムは、プログラムの実身で区別する。同じ実身から起こしたプロセスは同じ音量に従い、その音量は次にそのプログラムが鳴らすときと、次の起動でも効く。プログラムの実身を持たないプロセス(ファイルから起こしたもの)は、プロセスごとに音量を持ち、プロセスが終わると忘れる。カーネルのタスクの音はまとめて「システムの音」(番号0)である。

全体の音量はソフトウェアで掛け、I2S、HDMI、USBオーディオのどの出力先でも同じに効く。USBオーディオの機器が自分の音量(フィーチャーユニット)を持っていても、全体の音量はそれを動かさない。機器の音量は機器を挿したときのままで、プログラムは`DN_SDVOLMAIN`で別に変えられる。こうしておくと、出力先を切り替えても聞こえる大きさが変わらない。

| データ番号 | 実身のレコード | 内容 |
| --- | --- | --- |
| `DN_SDMIXER` | 26 `OB_SND_MIX` | 読む。全体の音量(左と右)と消音、最近の大きさ、音のデバイスで鳴らしたことがあるプログラムの一覧(`SDMixApp`。プログラムの実身のUUID、プロセスの番号、名前、音量、消音、チャネルの数、鳴っているチャネルの数、最近の大きさ)。読むか設定するだけのチャネル(ミキサー自身のもの)は一覧に出さない |
| `DN_SDMIXSET` | 27 `OB_SND_MIXSET` | 書く。`SND_MIX_ALL`で全体の左と右と消音、`SND_MIX_APP`でプログラム(実身のUUID、なければプロセスの番号)の音量と消音 |

書かれた設定は、最後の変更から1秒たつと、サウンドデバイスのタスクが機器の設定の実身に残す(`SOUND_VOL 左 右 消音`の行と、プログラムの実身ごとの`SOUND_APP UUID 音量 消音`の行)。起動時と機器の設定の実身が書き換えられたときに、カーネル(`uconf.c`)がそれを読んでミキサーに入れる。ただし、書き換えを見張るタスクは、ミキサーの行が最後に残したか読んだものと同じなら入れ直さない(ほかの行の書込みや、ミキサー自身が残した書込み)。その行は少し前のミキサーの値で、その後に変えた音量や消音を前の値に戻してしまい、戻した値は残し直されないからである。起動時や`wm_dev_conf_apply`で明示的に読むときは、同じでも入れる。ボリュームを引いている間の細かな変更は1回の書込みにまとまる。

音量のキー(6.4)を押すと、ウインドウマネージャ(`outer_kernel/wm/beep.c`の`knl_wm_volume_key`)が全体の音量を1回につき5変える。もとにするのは左と右の大きい方で、変えた値を左と右の両方に設定し、0から100の範囲に切り詰める。消音は解く。設定は`DN_SDMIXSET`の書込みと同じく機器の設定の実身に残り、ミキサーの変化の通知(`OB_SND_MIX`の`OB_E_CHANGE`)で音量ミキサーの表示も変わる。メッセージ行には「音量 45%」のように2秒間出し、その後はプログラムのメッセージに戻す(`knl_msg_note`。その間にプログラムが書いたメッセージは、注記が消えてから出る)。試験は`ktest_wm`の`test_volume_keys`で、入力の注入(`knl_hid_inject`)で音量のキーを押し、40と50で消音のときに上げると左右とも55で消音が解けること、下げる、100と0で止まること、ウインドウにキーが届かないこと、メッセージ行の文字と、2秒後にプログラムのメッセージに戻ることを確かめる。

これらの構造体は`INT`と`UINT`で作る。プログラムを`config.h`を先に読まずにビルドすると`W`と`UW`は64ビットになり、カーネルの構造体と大きさが食い違うためである。

試験は`ktest_snd`の`test_mixer`で、2つのプログラムとして扱う2つのチャネルに一定の値(4000と4000、2000と-2000)を鳴らし、ミキサーが出したサンプル(`knl_snd_tap`)で、和(6000と2000)、プログラムの音量50(4分の1)、消音、全体の左だけ50、全体の消音、和が16ビットを超えたときに32767の手前に曲げられること、設定が機器の設定に残り、読み戻されることを確かめる。

ブザーとキーやボタンのクリック音は、実身「システムの音」にある音の実身(ブザー音、押下音、離し音)をサウンドデバイスで再生したものである。音の実身のレコード1にWAVがあればそれを、なければメタデータにある音の高さと長さから生成した音を再生する。ブザー音の高さで長さだけを変えた短い音(100ミリ秒、`WM_BEEP_TICK`)と長い音(600ミリ秒、`WM_BEEP_LONG`)もあり、画面印刷の秒読みが使う(11.24)。鳴らし方は6.5.5のとおりである。

### 6.5.7 Intel HDAの録音(x64)

x64のPCの録音は、USBオーディオの機能がなければIntel HDAのコーデックから行う(`device/snd/x86_64/snd_hda.c`)。入力の道筋は、ピンからではなく入力のコンバータ(ADC)の側から接続の一覧をたどって組む。ピンは入力の向きに接続の一覧を持たないためである。

| 手順 | 内容 |
| --- | --- |
| ピンを選ぶ | 入力ができ、配線されたピンのうち、既定の構成の機器がマイクのもの。ポートの接続性が固定(内蔵)のものを内蔵のマイク、ジャック(と両方)のものをジャックのマイクとし、それぞれ最初の1本を取る。マイクがなければライン入力を同じ形で取る |
| 道筋を組む | それぞれのピンへ、ADCからミキサと選択器を通る最短の道筋を探す。長さ2から順に、まずもう一方のマイクの道筋のADCを試し、次にほかのADCを番号の順に試す。両方のマイクが1つのADCとその前のミキサ(または選択器)を共有でき、切替えはその入力を替えるだけになる |
| 増幅器 | ADCの前のミキサは道筋の入力だけを録音の音量で開け、ほかの入力(ほかのピン、ループバックのミキサ)は消音にする。選択器は道筋の入力を選ぶ。ピンの入力の増幅器(マイクのブースト)とADCの入力の増幅器は、録音の音量(`DN_SDVOLMIC`、`DN_SDGAININ`)を各増幅器の段に割り当てる(中央の0x8000が0dB) |
| ピンの制御 | 入力(PIN_IN)にする。ジャックのアナログのマイクには、ピンが出せるなら80%(なければ50%か100%)のバイアス(VREF)を与える。内蔵のマイクとデジタルのマイクには与えない |
| ジャックの切替え | 録音している間、ジャックのピンが何か挿さっていると感じればジャックのマイク、感じなければ内蔵のマイクに切り替える。ピンが非要求応答を持てば、録音の始めに非要求応答をタグ付きで有効にし(コントローラはGCTLのUNSOLで非要求応答をRIRBに入れる)、RIRBの中で動詞の答えと分けて受け、来たらピンの検出(GET_PIN_SENSEのビット31)を読み直す。持たなければ0.5秒ごとに読む。ジャックのピンが挿さっていることを感じられないときは、内蔵のマイクだけを使う |

Surface Go 2のRealtek ALC298(10ec:0298)では、内蔵のマイクはピン0x12(既定の構成90a60130。固定、内蔵、マイク、接続の種類6でデジタル)、ジャックのマイクはヘッドセットのピン0x18(04a11040)である。以前のドライバは、入力のピンをADCからの深さ優先の探索で最初に見つかったマイクに決めていたため、ミキサの接続の一覧で先に来る0x18への道筋だけを組んだ(2026年10月の実機の記録の`hda: input path: converter 8 ... pin 24`)。ヘッドセットを挿していなければ何も録れず、内蔵のマイクは使えなかった。ジャックのピンにバイアスを与えておらず、ピンの入力の増幅器も設定していなかった。ALC298の内蔵のデジタルマイクは、ほかの入力のピンと同じ扱いで録れ、係数などの機種固有の設定は要らない(`hda_quirks()`は空のまま)。もう1つの原因は音の層にあった。HDAの入力の流れは、USBの管理タスクが数ミリ秒ごとに回すサウンドデバイスの見回り(`knl_snd_poll`)で読まれるが、録音を始めても管理タスクを起こしていなかった(再生の始めだけが`knl_usb_kick`で起こしていた)。USBの転送がなければ管理タスクは眠ったままで、録った音はチャネルに届かなかった(QEMUで0.5秒に0フレーム)。録音の始めにも管理タスクを起こすようにした。I2Sの録音も同じ形で読まれる。ヘッドセットの4極のジャックの種類の判定(CTIAとOMTP)は行わないので、3極のヘッドホンを挿すと、ジャックのマイクに切り替わって無音になる。

実機で1回で確かめられるように、次の行をコンソール(KERNEL.TXT)に出す。

| 行 | 内容 |
| --- | --- |
| `hda: input converter N:`、`hda:   mixer N:` | 起動時。ADCとその前のミキサや選択器のウィジェットの能力、入力と出力の増幅器の能力、接続の一覧 |
| `hda: input pin N:` | 起動時。入力のピンのウィジェットの能力(デジタルかアナログか、挿したことを感じるか、非要求応答で知らせるか)と入力の増幅器 |
| `hda: input path (built in)`、`(jack, ...)` | 起動時。組んだ道筋(ADCからピンまでのウィジェット) |
| `hda: records:` | 起動から3回目までの録音の始め。使うピンとADC、ジャックの状態、録音の音量、道筋の増幅器ごとの段(段/最大、0dBの段) |
| `hda: plugged in:`、`hda: unplugged:` | 録音中にジャックのマイクと内蔵のマイクを切り替えたとき |
| `hda: recorded peaks` | 起動から3回目までの録音の、ブロック0、1、2、3、50、100、200、400(約2.1秒)の左右の最大振幅 |

試験は`ktest_snd`の`test_hda_record`で、QEMUのIntel HDA(`EXTRA="-audiodev none,id=a0 -device intel-hda -device hda-duplex,audiodev=a0"`、12.3)で、録音を始めると出力先の種類がHDAになり、48kHzの2チャネルで録り、0.5秒で12000フレーム以上が届いて読めること、録音の音量を書いて読み戻せることを確かめる。QEMUのコーデックはADCがライン入力のピンに直接つながるだけなので、ミキサの入力の消音、2つのマイクの道筋、ジャックの切替えは実機で確かめる。Intel HDAがない機械では飛ばす。

## 6.6 カメラ

カメラデバイス`cama`は、カメラごとのサブユニット`cama0`から`cama3`(`cama`は`cama0`と同じ)を持つ(`include/ts/cam.h`、`device/cam/cam.c`)。カメラは来た順に空いているユニットに入り、いる間はそのユニットのままである。

| データ番号 | 内容 |
| --- | --- |
| 0 `DN_CAMFRAME` | フレームを読む。そのプログラムがまだ読んでいない一番新しいフレームを、ヘッダ(`T_CAMFRAME`、番号、形式、大きさ、時刻、カメラのPTS)に続けて返す。無ければ0バイト。待たない。サイズ0で読むと、ヘッダを含めた大きさが分かる |
| -1 `DN_CAMINFO` | カメラの状態、VIDとPID、UVCのバージョン、製品名、モードの数、選んだモード |
| -2 `DN_CAMMODES` | モード(`T_CAMMODE`)の一覧。形式(YUY2、NV12、UYVY、MJPEG)、幅と高さ、最大のフレームの大きさ、フレームの間隔 |
| -3 `DN_CAMMODE` | 書くとモードを選び、カメラと取り決めた値(間隔、ペイロードとフレームの大きさ、代替設定)を返す |
| -4 `DN_CAMSTREAM` | `CAM_START`で流し始め、`CAM_STOP`で止める。モードを選ぶ前は`E_OBJ` |
| -5 `DN_CAMSTAT` | 完成したフレーム、捨てたフレーム、プログラムが読んだフレームの数 |

フレームは3つのバッファを回して受け取る。一番新しいフレーム、プログラムがコピーしている最中のもの、次に入れるものである。バッファはカメラのスピンロックの下で選んで目印を付け、ロックの外でコピーする。クラスドライバはUSBの管理タスクのロックを持ったままフレームを渡すが、読む側を待たない。空きの無いときに来たフレームは捨てた数に数える。プログラムごとに最後に読んだフレームの番号を覚え、同じフレームを2度返さない。バッファの大きさは選んだモードの最大のフレームで、モードを選んだとき、流していない間に作る。最後に閉じたプログラムが流れを止める。

UVCのクラスドライバ(`device/usb/uvc.c`)は、VideoControlのインタフェースからUVCのバージョンを、最初のVideoStreamingのインタフェースから形式、フレームの大きさと間隔、アイソクロナスの代替設定と帯域(またはバルクのエンドポイント)を読む。H.264のようなフレームベースの形式は使わない。モードは`VS_PROBE`の`SET_CUR`と`GET_CUR`、続く`VS_COMMIT`で取り決め、取り決めたペイロードの大きさを1サービス間隔のバイト数で賄える一番小さい代替設定を選ぶ。アイソクロナスでは1トランザクションが1ペイロードで、バルクでは短いパケットで終わる転送か、取り決めた大きさに達したところがペイロードの終わりである。ペイロードのヘッダ(FID、EOF、PTS、ERR)を読んで中身を自前のバッファに組み立て、EOFかFIDの切替わりでフレームを閉じる。形式に合う大きさ(YUY2とUYVYは幅×高さ×2、NV12は1.5倍)のもの、MJPEGはJPEGの始まり(`FF D8`)で始まるものだけをカメラデバイスに渡し、誤りのあったもの、大きさの違うもの、バッファに収まらないものは捨てた数に数える。

USBの管理タスクは、ロックを持ったままカメラのドライバを付けたり外したりし、カメラデバイスに通知するのはロックを放した後である(`knl_uvc_notify`)。カメラデバイスの要求は自分のロックを持ったまま管理タスクのロックを取るので、逆の順に取らないためである。去ったカメラのスロットは、カメラデバイスが手放すまで次のカメラに使わない。カメラが流している間、管理タスクはサウンドと同じく4ミリ秒ごとにコントローラを見る。

デバイスの実身(サブタイプ`OB_S_CAMERA`)のレコードは、レコード1がフレーム、2から6が上の表の-1から-5である(8.4)。x64のPCの内蔵カメラも、同じカメラデバイスの1台として見える(6.6.1)。試験のために、カーネル自身のカメラ(`knl_cam_loopback`、YUY2とMJPEGの64×48。`knl_cam_loopback_formats`で片方だけにもできる)があり、試験が渡したフレームを流す。UVCのクラスドライバは、構成の記述子とペイロードを与えて組立てを確かめるエントリ(`knl_uvc_probe_*`、カーネルの試験のときだけ)で試す。本物のカメラは実機で`test_uvc_board`が確かめる。挿したカメラの形式ごとに一番小さいモードを3秒、一番大きいモードを2秒流し、フレームの数と、大きさ(無圧縮)またはJPEGの始まり(MJPEG)を見る。カメラがなければ飛ばす。

### 6.6.1 x64のPCの内蔵カメラ(IPU3)

Surface Go 2の前面のカメラ(OmniVisionのOV5693)を、カメラデバイスの1台(製品名「Front camera (OV5693)」)として見せる。USBのカメラと同じモードの一覧、フレームの読み方なので、ブラウザ(14章)の側は変えずに使える。ドライバは`device/cam/x86_64/`にあり、`kernel/sysdepend/x64/devinit.c`が起動時のI2Cの段階の後(段階の表示「camera: IPU3」)で`knl_cio2_init`を呼ぶ。

| 部分 | ファイル | 内容 |
| --- | --- | --- |
| CSI-2の受け口 | `cio2.c` | IPU3のCIO2(PCI 8086:9D32)。ImgU(8086:1919)は使わない |
| センサーと電源の組立て | `cio2.c` | ACPIの名前空間から、センサー、その電源の制御器、I2Cのバスを結び付ける |
| 電源の制御器 | `int3472.c` | ACPIのINT3472。discrete(チップセットのGPIO)を駆動し、TPS68470は見つけて記録に出すだけ |
| GPIO | `device/gpio/x86_64/gpio_pch.c` | IntelのPCH(INT344B、Sunrise Point-LP)のパッドを出力として駆動する |
| センサー | `ov5693.c` | OV5693。I2Cでレジスタを書く |
| 現像 | `device/cam/cam_isp.c` | 10ビットのrawからNV12とYUY2を作る。ARMとx64で共通のCのコード |

#### センサーの見つけ方

センサーはACPIのデバイスで、IDがINT33BE(前面、OV5693)、INT347A(背面、OV8865)、INT347E(赤外線、OV7251)である。駆動するのはOV5693だけで、ほかは見つけたことを記録に出す。センサーの`SSDB`(108バイト)のバイト28がつながるCIO2のポート、29がレーン数、84が筐体での向き、86からの4バイトが入力のクロック(MCLK)、90が電源の制御器の番号である。`_CRS`のI2cSerialBusがI2Cのアドレスとバス、`_DEP`が電源の制御器とI2Cのバスを指す。`_DEP`に電源の制御器が無いときは、`CLDB`の制御器の番号がSSDBのものと同じINT3472を使う。SSDBもGPIOの番号も、ファームウェアが起動時にACPIの変数の領域に置く値から作られるので、表の上では決まらない。起動のたびにACPICAで読み、記録に出す。Surface Go 2では、前面のセンサーはI2C4(PCIの19.2)のアドレス0x36にあり、電源の制御器は`\_SB_.PCI0.DSC1`(discrete、GPIO 4本)である。背面のセンサーの電源は`\_SB_.PCI0.CLP0`(TPS68470、I2C2の0x4D)である。これはACPIの表で確かめた。

#### 電源

INT3472の`CLDB`(32バイト)のバイト1が種類で、1がdiscrete、2以上がTPS68470である。discreteは`_CRS`のGpioIoが1本ずつの線で、`_DSM`(79234640-9E10-4FEA-A5C1-B5AA8B19756F)の関数`i+2`が`i`番目の線の種類(ビット7:0。0がreset、1がpowerdown、2がストロボ、8がデジタルの電源、0x0Bがアナログの電源、0x0Cがクロック、0x0Dがプライバシーの表示灯、0x10がI/Oの電源、0x12がハンドシェイク)と、センサーが動く側のレベル(ビット31:24、0以外がHigh)を返す。GpioIoの極性は使わない。電源を入れる順は、resetとpowerdownを止める側にする、クロックを入れる、電源をセンサーの順(アナログ、I/O、デジタル)に1つ入れるごとに2ミリ秒待つ(ハンドシェイクの線は、その先の制御器がセンサーに電源を入れるので200ミリ秒)、表示灯を点ける、resetとpowerdownを放す、7.5ミリ秒待つ(データシートの、クロックを入れたままreset解除から5ミリ秒以上)、である。切るときは逆の順である。起動時に一度電源を入れてチップIDを読み、答えが無ければresetとpowerdownのレベルを逆にしてもう一度だけ読む。どちらで答えたかを記録に出し、答えた方を使う。TPS68470は、制御器のレビジョンを読んで記録に出すが、レギュレータとクロックは駆動しないので、その先のセンサー(背面と赤外線)は使えない。

#### GPIOのパッド

INT344Bの`_CRS`のメモリは、パッドのコミュニティ(0から47、48から119、120から151)の順である。名前空間のピン番号は24本ずつのグループを通しで数えたもので、このPCHではパッドの番号と同じである。パッドのDW0(PADBARからパッドごとに8バイト)のビット0が出力のレベル、ビット8が出力を止める、ビット13:10がファンクションである。ファンクションがGPIOでないパッド、MEが持つパッドには書かない。出力のロック(PADCFGLOCKTX)が掛かっていれば記録に出す。

#### センサー

OV5693はI2Cのレジスタ(16ビットのアドレス、8ビットの値。複数バイトの値は上位から)で設定する。チップIDはレジスタ0x300Aの0x5690である。モードは1つで、2592×1944の有効画素を2×2でビニングした1296×972、10ビットのraw、毎秒30フレームである。MCLKの19.2MHzから、PLLでレーンあたり838.4Mbit/s(リンク周波数419.2MHz)、画素レート167.68MHzを作る。1行は2688クロック、1フレームは2079行である。ミラーとフリップは使わず、画素の並びはBGGRである。露光(0x3500、行数)とアナログの利得(0x350A、8で1倍)は手動で、後に書く自動露光が決める。センサー自身のホワイトバランスの利得は1倍のままにする。黒レベルはセンサーの補正で64(10ビット)に保たれる。起動の設定`cam=bars`でセンサーのカラーバー(0x5E00)を絵の代わりに出せる。

#### CIO2

4つのポート(それぞれCSI-2の受け口とMIPIのバックエンド、0x400ごと)と20のDMAのチャネルがあり、チャネル0を使う。チャネルはFBPTを通してフレームを書く。FBPTは32個のフレームのバッファの輪で、1つのバッファに16バイトのエントリが8つある(合わせて1ページ)。最初のエントリには制御語(VALID、完了と開始の割込み)、フレームの番号、最初のページの中のデータの始まりがある。2番目には書いたバイト数、ページ数、最後のページで書いてよいバイト数がある。どのエントリにも、ページのリスト(LOP、1024個のページ番号を持つ1ページ)のページ番号がある。フレームが入るとハードウェアがVALIDを落とす。ここでは輪の32個のバッファに4つのフレームのバッファ(2MBずつ、物理的に連続、4GB未満)を順に割り当てる。終わったバッファはすぐにハードウェアに返し、一番新しいものを絵にする。同じフレームのバッファが次に書かれるのは4フレーム後なので、絵にする間に上書きされない。バッファの後のLOPのエントリはダミーのページのLOPを指す。

フレームはIPU3の詰めた10ビットのrawで、32バイトに25画素(各画素のビットを最初のバイトの最下位ビットから順に並べる)、1行は`DIV_ROUND_UP(幅, 50) * 64`バイトである。1296画素では1664バイト、1フレームは1,617,408バイト(395ページ)になる。ポートの受け口は、レーン数と、センサーのリンク周波数から求めたsettleとterminationの値(1/16ナノ秒単位で`16 * (A + B * UI)`、UIは`1 / (2 * リンク周波数)`。クロックレーンのsettleはAが95、Bが-8、データレーンは85と-2、terminationはどちらも0と0)で設定する。419.2MHzではクロックレーンが1368、データレーンが1322になる。バックエンドはバーチャルチャネル0のRAW10(データタイプ0x2B)だけを通し、ポートのピクセルフォーマッタは1画素10ビット、64バイトに詰める形にする。割込みはMSIで、ハンドラは来たもの(INT_STS、出力の誤りと受け口の誤りはそれぞれの状態のレジスタ)を受け付けて消し、ビットと数を残してカメラのタスクを起こす。

#### 現像

生のBayerを、`cam_isp.c`がソフトウェアで現像する。詰めた形を戻し、隣の画素から足りない色を作り(元の大きさでは双一次の補間、半分の大きさでは2×2の1組から1画素)、黒レベルを引いてホワイトバランスの利得を掛け、ガンマ0.5を掛ける(この3つは色ごとの1つの表)。それをBT.601のY'CbCr(スタジオレンジ)にしてNV12かYUY2にする。補間はセンサーが測った10ビットの値で行い、8ビットにするのは表を引くときである。絵を作る間に、使った部分の4組おきの統計(各色の平均、緑のヒストグラム、飽和した組の数)を取る。次のフレームのホワイトバランスは灰色仮説で、赤と青を緑の平均に4分の1ずつ近づける(利得は0.5倍から4倍)。黒レベルは、千組に1組がそれより暗い値がセンサーの値より低ければ、そこまで下げる(上げない)。露光は、緑の平均が黒レベルより上の範囲の6分の1になるように、求めた比の半分だけ動かす(飽和した組が50組に1組を超えれば減らす)。露光の行数を先に、最大(1フレームの行数-8)に達したら利得を上げる。変化が32分の1未満のとき、前に変えてから3フレームの間は書かない。整数だけで計算するので、カーネルの中で動く。

モードはNV12とYUY2の640×480(1296×972の中央の1280×960を半分にする)、1280×720と1280×960(中央を切り出す)で、どれも毎秒30フレームである。起動の設定`cam=off`で内蔵カメラを使わない。`cam_bayer=rggb`(`grbg`、`gbrg`、`bggr`)で画素の並びを替えられる。

#### 記録

実機で一度動かせば原因が分かるように、各段階をコンソールに出す(起動時のコンソールは`KERNEL.TXT`に残る)。出し続けないように、フレームの記録は1枚目、30枚目、300枚目だけ、誤りは1回の流れで8回までにする。

| 行の始まり | 内容 |
| --- | --- |
| `cio2: \_SB_.PCI0.LNK1 INT33BE (OV5693)` | 名前空間で見つけたセンサー |
| `cio2: ... SSDB 0-35`、`36-71`、`72-107` | SSDBのバイト列 |
| `cio2: ... version ..., CSI-2 port ..., ... lanes` | SSDBの読み、ポート、レーン数、MCLK、向き、電源の制御器の番号 |
| `cio2: ...: I2C 36 on \_SB.PCI0.I2C4`、`_DEP` | I2Cのアドレスとバス、依存先 |
| `campwr: ...: CLDB`、`kind` | 電源の制御器の種類 |
| `campwr: ...: line N: pin ... _DSM ...` | GPIOの線ごとのピン、`_DSM`の値、種類、動く側のレベル |
| `gpio: ... community`、`gpio: before/powered, ...: pin ... DW0` | GPIOのコミュニティの番地、パッドの設定とレベル(電源の前と後) |
| `ov5693: on i2c25.2 at 36: chip ID` | チップID(0x5690なら正しい)。答えが無ければ`ffff` |
| `TessronOS: cio2 8086:9d32`、`TessronOS: cio2: ... unit` | CIO2のレジスタの番地と割込み、カメラのユニット |
| `cio2: ring:` | FBPTとバッファの番地、1行と1フレームのバイト数 |
| `cio2: port ..., lanes, link ... settle` | 受け口の設定(流し始めたとき) |
| `ov5693: streaming:` | センサーのPLL、窓、ビニング、HTSとVTS、露光と利得を読み返したもの |
| `cio2: frame N after ... ms` | 受けたフレーム、バイト数、先頭の8画素、色の平均、黒レベル、露光、ホワイトバランス |
| `cio2: errors at frame` | 出力の誤り、受け口の誤り(ECC、D-PHY、CRC、パケットの長さ)のビット |
| `cio2: no frame in a second`、`still no frame` | 1秒経ってもフレームが来ないときの受け口とDMAの状態(2回まで) |
| `cio2: stopped:` | 止めたときのフレームと割込みの数 |

試験は`ktest_camisp`(x64)が、ここで作ったフレームで現像を確かめる。詰めた形の展開が正確であること、灰色の絵が両方の大きさと両方の形式で灰色になり、黒レベルで黒、最大で白に近いこと、赤い絵が赤くなり、画素の並びを替えると青になること、合わない大きさを断ること、ホワイトバランスと露光が正しい向きに動くことである。QEMUにはIPU3が無いので、CIO2とセンサーと電源は実機で確かめる。

## 6.7 動画の復号器

Raspberry Pi 5のBCM2712には、HEVC(H.265)のMainプロファイルとMain10プロファイルを復号する回路がある。これをデバイスの実身「動画の復号器」(サブタイプ`OB_S_VIDEODEC`、`include/ts/hevc.h`、`device/hevc/hevc.c`)として見せる。QEMUとRaspberry Pi 4には無く、実身も作らない。

復号器はストリームを自分では解析しない。プログラムが解析した結果、つまりシーケンスとピクチャのパラメータ、スライスのヘッダ、参照ピクチャの一覧と、スライスのバイト列(エミュレーション防止バイトを含んだまま)を1枚ごとのジョブとして渡す。復号したピクチャを入れる場所(スロット)と、参照ピクチャがどのスロットにあるかもプログラムが決める。ブラウザはChromiumのH265Decoderに解析と参照の管理を任せ、そのアクセラレータがジョブを組み立てる(14.6.7)。

| レコード | 内容 |
| --- | --- |
| 1 | 書くと1枚を復号する。`T_HEVCJOB`、`T_HEVCSLICE`をスライスの数だけ、スライスのバイト列の順。復号を終えて(または失敗して)から戻る。最大4MB |
| 2 | スロットのピクチャを読む。8ビットはNV12(輝度が幅×高さ、続いてUとVが交互に幅×高さ/2)、10ビットはP010(同じ並びで1サンプル16ビットのリトルエンディアン、10ビットを上に詰め下の6ビットは0)。オフセットの上位32ビットがスロット、下位がバイトの位置 |
| 3 | `T_HEVCCONF`(ピクチャの幅と高さ、ビット深度8か10、スロットの数1から17)。書くとスロットを作り直す |
| 4 | `T_HEVCINFO`(バージョン、クロック、復号した枚数、失敗の数、最後の失敗の状態、最後の1枚にかかった時間) |

扱うのは8ビット(Main)と10ビット(Main10)の4:2:0で輝度と色差のビット深度が等しいもの、1920×1088まで、タイルとWPPを同時に使わないストリームである。ジョブのビット深度は`T_HEVCCONF`のものと同じでなければならない。CTBの大きさは16、32、64のいずれでもよい。

復号器は1枚を2つの段で処理する。

1. 第1段はスライスのバイト列のエントロピー復号(CABAC)で、結果を予測単位(PU)と係数の2つのメモリに書く。この段は、メモリに置いた(レジスタ、値)の対の列、コマンドリストで動かす。リストには、パラメータのレジスタ、文脈変数の初期値(スライスの種類と量子化パラメータから求める)、スケーリングリストの係数、スライスごとのメッセージ(種類、参照とその重み、デブロッキングの指定)、タイルやWPPの行の始まりと終わりの位置を入れる。PUや係数のメモリが足りないと第1段はそう言って止まるので、倍の大きさにして第1段をやり直す。
2. 第2段はPUと係数と参照からピクチャを組み立ててループフィルタをかけ、スロットに書く。レジスタに直接書いて動かす。時間方向の動きベクトルを使うストリームでは、スロットごとに動きベクトルのメモリを持ち、後のピクチャがそれを参照する。

各段の終わりは復号器の割込みコントローラから通知される(SPI 98)。ジョブは実身の書込みの中で1枚ずつ処理し、ミューテックスで他の書込みを待たせる。

復号器が触れるメモリ(コマンドリスト、バイト列、PU、係数、スロット)は、4GB未満の物理的に連続したページ(`KAF_DMA32`)から取る。復号器はアドレスを64バイト単位で受け取る。プロセッサが書いたものは復号器に渡す前にキャッシュから追い出し、復号器が書いたスロットは読む前にキャッシュを無効にする。取ったページはゼロで埋めた直後にキャッシュから追い出し、ダーティな行が後で復号器の書いたピクチャの上に書き戻らないようにする。復号器の前のIOMMU(iommu2)が有効でバイパスでないときはバイパスにする。クロックはファームウェアのクロック11を最大にする。

スロットのピクチャは復号器が書いたまま持つ。128バイト幅の列が並び、輝度は1枚のメモリに各列がピクチャの高さ(8の倍数に切り上げ)の行を、色差はUとVを交互にもう1枚のメモリに各列が半分の高さの行を持つ。8ビットでは列の1行が1バイトのサンプル128個である。10ビットでは列の1行が32ビットのリトルエンディアンのワード32個で、1ワードにサンプル3個をビット0、10、20から置き、上の2ビットは使わない。このため列の幅は96サンプルになり、列の数は幅を96で割って切り上げた数になる。色差のワードはU、V、Uと次のワードのV、U、Vのように交互に続く。列と列の間隔(1列のバイト数)と、第1段・第2段のレジスタの設定は8ビットと同じで、ビット深度はSPSのレジスタと第2段の設定のワード(ビット深度の欄と、8ビットでないことを示すビット)、量子化パラメータの初期値に足すQpBdOffset(6×(ビット深度−8))に表れる。重み付き予測のオフセットは8ビットの値のまま渡し、ビット深度に合わせた拡大は復号器が行う。レコード2の読出しで行の並びのNV12またはP010に直す。

### 6.7.1 実機での確認

QEMUには復号器が無いので、実機の確認を`make HEVCTEST=1`でカーネルに入れる(`kernel/sysdepend/rpi5/hevctest.c`)。起動の20秒後に、`tools/hevc/mkjobs.py`がlibx265で作った小さなストリームのジョブ(`tools/hevc/hevc_jobs.bin`)をカーネルのエントリ(`knl_hevc_conf`、`knl_hevc_decode`、`knl_hevc_picture`)で復号し、ピクチャごとのNV12(10ビットはP010)のハッシュ(FNV-1a)をffmpegの復号の結果と比べて、`hevctest:`の行をコンソールに出す。ストリームは5つで、8ビットが1スライスでCTBが32の64×64、2スライスでWPPを使いCTBが64の320×240、CTBが16の128×96、10ビット(Main10)が1スライスでCTBが32の64×64と、2スライスでWPPを使いCTBが64の208×120である。208×120は輝度も色差も10ビットの列(96サンプル)を3つにまたがり、最後の列が途中で終わる。どれもIピクチャに続くPピクチャで、重み付き予測と時間方向の動きベクトルを含む。期待するハッシュは、`mkjobs.py`がffmpeg(libx265が`yuv420p10le`を受け付けるもの)で同じストリームを`nv12`または`p010le`に復号して求める。`mkjobs.py`はffmpegのビットストリームフィルタ`trace_headers`の出力からジョブを作るので、ブラウザとは別の道でジョブの形を確かめることにもなる。

## 6.8 ドライバの規約

- デバイスに渡すアドレスは物理アドレスである。リニアマッピングの外にあるバッファは、`ConvPhysicalAddress`で連続する区間ごとに物理アドレスを求める(4.6)。デバイスから見たメモリが物理アドレスとずれるとき(RP1、Raspberry Pi 4系のEMMC2とPCIe)は、そのずれを足したバスアドレスを渡し、届かないバッファはDMAのゾーン(`KAF_DMA32`)から取ったバッファを通す。
- キャッシュの書き戻しと無効化、デバイスとの間のバリア、待つループの休みは、`DCacheFlushRange`、`DeviceBarrier`、`SmpWriteBarrier`、`CpuRelax`などのアーキテクチャの層の関数(4.8)で書き、`dsb`や`dc civac`などの命令を直接書かない。
- 割込みハンドラが参照するデータは、割込みを許可する前に用意しておく。
- ドライバ内の排他制御はスピンロックかミューテックスで行う。割込みを禁止するだけでは他のCPUを止められない。
- 期限を過ぎた時刻をコンペアレジスタに残すと割込みが連続して発生するので、設定する前に確認する。
- 割込みのハンドラは、どのCPUで動いてもよいように書く。装置の割込みは既定ではPRC 1に届くが、CPUの役割(機器の設定の`CPU_CHORE`、`CPU_RT`)、`SetIntTarget`、装置の実身の属性`irq.cpu`でほかのCPUに向けられる(4.5.1)。割込みを登録して許可した後に`knl_int_owner(intno, デバイス名)`で、その割込みがどの装置のものかを伝えると、装置の実身の属性が当たる。今伝えるのは、NVMe、virtioのブロック装置、ネットワークのカード(`neta`)である。
- ドライバのタスクは割付けCPUを指定しない。割込みを受けたCPUに近いCPUで動かすこと(キャッシュの局所性)は、まだ狙っていない。
- ブロック装置の要求の開始番号(`T_DEVREQ.start`)は64ビット(`D`)で、セクタの番号を2^31より先まで持てる。開始番号を`W`で渡す`tk_srea_dev`、`tk_swri_dev`は2^31セクタ(512バイトで1TB)までで、それより先はT-Kernel 2.0と同じ`tk_srea_dev_d`、`tk_swri_dev_d`(非同期は`tk_rea_dev_du`、`tk_wri_dev_du`)で頼む。TSFS、FAT、GPT、x64の起動ディスクの読み、ディスクの実身のレコードの読み書きは、こちらを使う。ディスクの大きさ(`TDN_DISKINFO`の`DiskInfo`)は`blockcont_d`(`D`)に全部を入れ、`W`の`blockcont`は2^31-1で止める。前は`blockcont`だけで、1TBを越えるディスクの大きさが負になり、後ろの方を読み書きできなかった。`iob`の群の`test_huge`が、3TBのディスクの2^31と2^32の前後のセクタを読み書きし、そのディスクの全体にTSFSのボリュームを作ってつなぐ。
- 1回に運べる量は`TDN_IOMAX`で答える(7.3)。NVMeとAHCIは、呼び手のバッファがカーネルのメモリなら、中継のバッファを通さずに、そのページを直接渡す(NVMeはPRPの表、AHCIは物理領域の表)。プロセスのメモリ、DMAで届かないメモリ(AHCIの32ビットの制御器での4GBより上)は、これまでどおり128KBの中継のバッファを通す。NVMeは1つの表のページが名指せる2MB(MDTSがそれより小さければMDTS)、AHCIは4MBを`TDN_IOMAX`に答える。
- 装置のキャッシュを通さずに媒体に書く(Force Unit Access)ときは、属性`TDN_FUAWRITE`に、書く場所、中身、大きさを持つ`T_DEVFUA`を書き込む(`include/ts/blk.h`)。できない装置は`E_PAR`を返し、何も書かない。呼び手はふつうに書いてからキャッシュを空にする(`TDN_FLUSH`)。できるかどうかは装置が言うことで決める。NVMeはすべての制御器がFUAを持つ。SATAは、IDENTIFYの語84が有効(ビット15〜14が01)で、そのビット6(WRITE DMA FUA EXT)が立つディスクで、48ビットのコマンドを持つもの。USBの大容量記憶は、MODE SENSE(6)の答えに書込みのキャッシュ(ページ8のWCE)があり、装置固有の引数のDPOFUA(ビット4)が立つ装置で、WRITE(10)とWRITE(16)のFUAのビットを立てる(Linuxのsdと同じ。6.3.0)。書込みのキャッシュのない装置とMODE SENSEに答えない装置はFUAを使わず、`TDN_FLUSH`には命令を送らずに成功で答える。virtio-blkとSDカードは持たない。TSFSのジャーナルが、確定のときのリングの書込みに使う(7.3)。起動のときのSATAのディスクの行と、USBの大容量記憶の報告(`USB.TXT`)に、FUAを使うかどうかが出る。`iob`の群の`test_fua`が、`KT_IOB_FUA`で名指したディスク(既定は無し。ほかの試験のUSBのディスクを消さないため、`KT_IOB_CFLAGS`で渡す)で、FUAを持つ装置では書いた中身が読み戻せること、持たない装置では`E_PAR`で何も書かれないこと、どちらでもその上のTSFSのボリュームのレコードがつなぎ直した後に残ることを確かめる。QEMUのSATAのディスク(`ide-hd`)はFUAを持たないと言う。QEMUのUSBのディスクは`scsi-hd`の`dpofua`の設定に従い(QEMU 11の既定はon。`usb-storage`もこれを使う)、`usb-bot`の先に`scsi-hd,dpofua=off`をつなぐと持たない装置になる。

## 6.9 x64のIntelの内蔵グラフィックスの表示

x64のPCで、Intelの内蔵グラフィックスの第9世代(Skylake、Kaby Lake、Amber Lake、Coffee Lake。UHD 620 8086:5917、UHD 615 8086:591C)が内蔵のパネルを表示しているときは、再起動せずに解像度を変える(`device/disp/x86_64/disp_igfx.c`、10.2.2)。参照したのはIntelのPRM(Vol 2cのレジスタ、Vol 12の表示のウォーターマーク)の意味と、i915の手順の順だけで、コードは写していない。

ファームウェアは、eDPのトランスコーダでパイプAからパネルを本来の大きさで点け、パイプAのプライマリプレーンにGOPのフレームバッファ(GGTTの0番地、stolen memory)を表示させている。GOPのモードがパネルより小さいときは、パイプのスケーラで引き伸ばしている。ThinkPad X1 Yoga 第3世代では、パネルは2560×1440(HTOTAL 2720、VTOTAL 1481)、パイプの大きさは1600×1200で、スケーラがパネル全体に広げていた(DISPLAY.TXT、3.10.7)。

ドライバは、トランスコーダ、DDI、PLLに触れない。パネルは常に本来の大きさで動かし、変えるのはプレーン(大きさ、行の長さ、面のアドレス)、パイプの大きさ(PIPE_SRC)、スケーラの窓だけである。リンクを張り直さないので、パネルの電源とバックライトはそのままで、失敗しても画面は消えない。起動時に次の条件を確かめ、満たさなければ解像度を変えない(GOPのモードのまま)。

- GGTTの共有の部品(`kernel/sysdepend/x64/igt_ggtt.c`)がIntelの第9世代の機能を見つけた
- GOPのフレームバッファが2つ目のBAR(GMADR)の先頭にある
- eDPのトランスコーダとパイプが有効で、入力がパイプAである。パイプBとCは止まっている
- プライマリプレーンが有効で、XRGB8888、線形、面のアドレスが0である

面は、GGTTの中のCPUから見える範囲(mappable)に2つの置き場を取り、交互に使う。置き場0はGGTTの0から16MBで、ファームウェアがstolen memoryの先頭を写した範囲(GOPの画面)を起動時にファームウェアから引き継ぐ。置き場1は共有の部品が空きから取る16MBで、系のメモリの4MBの塊を4つ写す。mappableな範囲に16MBの空きが無いときは、0番地以外のファームウェアの範囲の上に取る(13.11の共有の部品。GGTTのメモリに電源投入時のごみが残る機械のため)。どちらかの置き場が取れなければ、起動時に`the GOP's screen could not be taken over`か`no second place`の行を出して解像度を変えず、システム環境設定の変更は-9(E_NOSPT)になる。新しい大きさの面を、表示していない方の置き場に作って黒で埋め、それから切り替える。CPUはどちらの置き場にも、2つ目のBARを書き込み結合で写して書く。GGTTのPTEは共有の部品(`knl_igt_ggtt_set`)で書き、部品がGFX_FLSH_CNTLでGPUのGGTTのキャッシュを捨てる。

DDBとウォーターマークは、PRMの方法1と方法2で、新しいプレーンの幅について計算し直す。メモリの遅延はpcodeのメールボックスで読む(`knl_igt_pcode_rw`、`kernel/sysdepend/x64/igt_pcode.c`。表示と描画で共有し、中で全CPUにまたがるロックを取る)。画素のクロックは、eDPのトランスコーダのLINK M/NとDPLL0のリンクの速さから求める。今のプレーンについて計算した値がファームウェアの値と違うときは、大きい方を使う。レベル1〜7と移行用のウォーターマークは無効にする。DDBは、ファームウェアがプレーンに割り当てたブロックで足りなければ、その大きさを断る。

更新は垂直帰線に合わせる。パイプAの走査中の行(PIPEDSL)が帰線の始まりの64行より前にあるときに、割込みを止めて、PIPE_SRC、スケーラ(PS_CTRL、PS_WIN_POS、PS_WIN_SZ)、ウォーターマークとDDB、プレーン(STRIDE、POS、SIZE、OFFSET、CTL)の順に書き、最後にPLANE_SURFを書く。プレーンの値はPLANE_SURFの書込みで、スケーラの値はPS_WIN_SZの書込みで準備され、同じ帰線で反映される。書いた後、プレーンが表示している面(PLANE_SURFLIVE)が新しいアドレスになるのを最大100ms待ち(比べるのはアドレスのビット31〜12だけ。下位のビットには状態の印が立ち、ThinkPad X1 Yoga 第3世代では0x20が読めた。以前は下位のビットまで比べていたので、新しい面が表示されていても待ちが時間切れになり、どの大きさも書き戻して-9になっていた)、50ms後にパイプAのFIFOのアンダーラン(GEN8_DE_PIPE_IIR(A)のビット31。変更の前に消し、IMRで隠れていれば変更の間だけ見えるようにする。割込みは有効にしない)を見る。どちらかがだめなら、控えておいた変更の前の値を同じ手順で書き戻し、その大きさを断る。

スケーラの窓は、大きさの縦横の比がパネルと同じならパネル全体、違えば置き方(比を保つ、全体に広げる)で決める。比を保つときは、パネルの中央に、比を保ったまま入る一番大きい窓を置き、残りはパイプの下地の黒になる。パネルの本来の大きさのときはスケーラを止め、また使うときはファームウェアが有効にしていた値(係数を書き込む形のフィルタ)で有効にする。ファームウェアがスケーラを使っていなかったときは、係数の要らない中間のフィルタで有効にする。

変更の各段階(計算した値、書く前と書く値、反映を待った時間、アンダーランの有無、書き戻し)はコンソールに出し(KERNEL.TXTに残る)、DISPLAY.TXTの最後の節にも並べる。変更の2秒後に記録のファイルを書き直す(3.10.7)。

描画のエンジンの係との共通の資源(GGTT、stolen、レジスタの範囲、forcewake、割込み、PPAT、圧縮のハッシュ)の分け方は、x64の検討書の5.13と5.14で決めた。表示が書くのは0x40000〜0x7ffffの表示のレジスタだけで、forcewakeと割込みは使わない。外付けの画面(DDI B、C、Type-CのDisplayPort)はまだ扱わない。
