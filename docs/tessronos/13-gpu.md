# 第13章　GPU

## 13.1 目的と現状

Raspberry Pi 5のGPU(VideoCore VII、3DブロックはV3D 7.1)を、プロセスのOpenGL ES、EGL、そして将来のVulkanから使えるようにする。最初の利用者はブラウザ(Chromium/Blinkの移植)のWebGLで、その後にページの合成とウインドウの合成が続く。

第1段階(本章の時点)で済んでいるのは次のことである。

| 項目 | 状態 |
| --- | --- |
| V3D 7.1のアドレス、割込み、クロック、MMU、ジョブの種類の調査 | 13.2 |
| GPUの共通層(バッファオブジェクト、ジョブの列、フェンス) | 実装済み。QEMUの試験`gpu`で確認(13.7.3) |
| V3DのMMUのページテーブルとGPUアドレスの割当て | 実装済み。QEMUの試験`gpu`で確認 |
| V3Dのドライバ(クロック、識別、MMU、割込み、制御リストとキャッシュのジョブ) | クロック、識別、MMUの設定、キャッシュのジョブは実機で確認(13.8.1)。描画のジョブと割込みは未確認 |
| プロセスからの呼出し(SVC) | 設計のみ(13.5) |
| Mesaの移植 | 計画と、一部をTessronOSのツールチェーンでコンパイルした結果(13.6) |

## 13.2 BCM2712のV3D

### 13.2.1 アドレスと割込み

V3Dの資源はデバイスツリー(`bcm2712-rpi-5-b.dtb`)の`/axi/v3d@2000000`(`compatible = "brcm,2712-v3d"`)に書かれている。`/axi`のアドレス変換は恒等なので、`reg`の値がそのまま物理アドレスになる。

| 資源 | 値 | 内容 |
| --- | --- | --- |
| `reg`の`hub` | `0x10_0200_0000`から16KB | ハブ。MMU、テクスチャフォーマットユニット(TFU)、ハブの割込み |
| `reg`の`core0` | `0x10_0200_8000`から24KB | コア0。制御リストの実行器(CLE)、タイルのビニング(PTB)、キャッシュ、コアの割込み |
| `reg`の`sms` | `0x10_0203_0800`から0x700バイト | 電源状態の管理(SMS) |
| `interrupts` | SPI 250(INTID 282)、SPI 249(INTID 281)、レベル | 1つ目がハブ、2つ目がコア0(バインディングの定義による) |
| `power-domains` | `<&pm 1>` | PMブロック(`0x10_7d20_0000`、`brcm,bcm2712-pm`)の電源ドメイン1 |
| `resets` | `<&pm 0>` | 同じPMブロックのリセット0 |
| `clocks` | `<&firmware_clocks 5>` | ファームウェアが管理するクロックの5番(V3D) |

配布されているデバイスツリーでは、このノードは`status = "disabled"`である。Linuxではオーバーレイ(`vc4-kms-v3d-pi5`)が有効にするが、TessronOSはデバイスツリーの状態に関係なく、ビルドの指定(13.3.1)で使うかどうかを決める。アドレスと割込み番号は`include/sys/sysdepend/cpu/bcm2712/sysdef.h`の`V3D_HUB_PA`、`V3D_CORE0_PA`、`V3D_SMS_PA`、`V3D_HUB_INTNO`、`V3D_CORE0_INTNO`にある。

### 13.2.2 電源とクロック

クロックはファームウェアのメールボックスのプロパティインタフェースで操作する。使うタグは公開されている次のものである。クロックの番号5がV3Dである。

| タグ | 機能 |
| --- | --- |
| `0x00030001` | クロックの状態を取得する(ビット0がオン、ビット1が「存在しない」) |
| `0x00038001` | クロックをオンにする |
| `0x00030004` | 最大周波数を取得する |
| `0x00038002` | 周波数を設定する |
| `0x00030002` | 現在の周波数を取得する |

電源ドメインはPMブロックが持つ。ファームウェアがV3Dの電源を入れたままカーネルに渡すかどうかは公開された資料になく、実機で確かめる(13.8)。ドライバは、コアの識別レジスタ`IDENT0`が「V3D」と読めることを最初に確かめ、読めなければ他のレジスタには触れずに止まる。SMSのウインドウには何も書かない。

### 13.2.3 構成とMMU

V3Dはハブと1つ以上のコアからなる。コアはシェーダプロセッサ(QPU)を束ねたスライスを持ち、スライスの数とスライスあたりのQPUの数は`IDENT1`で分かる。バージョンは`IDENT0`の上位8bit(メジャー)と`IDENT1`の下位4bit(マイナー)で、Raspberry Pi 5では71になるはずである。

GPUは自分のMMUを通してメモリを読み書きする。GPUのアドレスは32bitで、4KBのページごとに32bitのエントリを持つ1段のページテーブルで物理アドレスに変換する。4GB全体では100万エントリ、4MBのテーブルになり、ハードウェアにはその先頭だけを渡すので、テーブルは物理的に連続していなければならない。エントリの下位28bitが物理ページ番号で、1TBまでの物理アドレスを指せる。実際に届く物理アドレスの幅は、MMUのデバッグ情報のレジスタで分かる。無効なエントリへのアクセスは、指定したページ(スクラッチページ)に振り向けられ、割込みで報告される。

GPUはCPUのキャッシュを見ないものとして扱う。GPUが読むメモリはCPUのキャッシュから追い出してから使い、その後はキャッシュしないマッピングでだけ触る。これが正しいかどうか(GPUとCPUの間にコヒーレンシがあるかどうか)も実機で確かめる。

ページテーブルは1つしかないので、GPUのアドレス空間はすべての利用者で共有になる。プロセスの間の分離は、プロセスが自分の持つバッファオブジェクトしか指定できないこと(13.5)で保つ。ジョブは1つずつ順に実行するので、将来はジョブごとにプロセス専用のページテーブルに切り替えることもできる。

### 13.2.4 ジョブの種類

| 種類 | 実行する部分 | 終わりを知る方法 |
| --- | --- | --- |
| ビニング(制御リスト0) | CLEのスレッド0。頂点を処理し、タイルごとのリストをタイル割当てメモリに書く | コアの割込み「ビニングのフラッシュ完了」、カウンタ`BFC` |
| レンダリング(制御リスト1) | CLEのスレッド1。タイルごとにフラグメントを処理し、メモリに書き出す | コアの割込み「フレーム完了」、カウンタ`RFC` |
| TFU | ハブのTFU。テクスチャのレイアウト変換とミップマップの生成 | ハブの割込み「TFU完了」 |
| コンピュート(CSD) | コアのディスパッチャ。コンピュートシェーダのワークグループ | コアの割込み「CSD完了」、完了数のカウンタ |
| キャッシュのクリーン | テクスチャのL2キャッシュとTMUのライトコンバイナ | 制御レジスタのビットが0に戻るのをポーリングする |

ビニング中にタイル割当てメモリが足りなくなると、コアが「メモリ不足」の割込みを上げる。カーネルはオーバーフロー用のメモリを`BPOA`、`BPOS`に渡して続けさせる。

制御リストはGPUのメモリに置いたコマンド(パケット)の並びで、形式はMesaの`src/broadcom/cle/v3d_packet.xml`に記述がある(13.6.4)。

### 13.2.5 レジスタの資料

V3D 4以降のレジスタの配置を記した公開の仕様書はない。`device/gpu/v3d/v3d_regs.h`では、項目ごとに次の印を付けている。

| 印 | 意味 | 該当するもの |
| --- | --- | --- |
| `[doc]` | 公開された資料に配置がある | 識別レジスタ`IDENT0`〜`IDENT2`、CLEの`CTnCS`〜`RFC`、PTBの`BPCA`〜`BPOS`(BroadcomのVideoCore IV 3D Architecture Reference Guideに同名のレジスタがあり、後の世代も同じ位置に残している)。識別ワードの各フィールドの意味(Mesaの`v3d_device_info.c`が読み解く) |
| `[hw]` | 公開された配置がない | ハブの識別と割込み、MMUとそのキャッシュ、コアの割込みとキャッシュ、キュー形式のCLEの開始レジスタ、ページテーブルのエントリのビット |

`[hw]`の項目は、実機で1つずつ読み出して確かめてから使う(13.8)。ドライバはビルドの指定`V3D=1`ではこれらに一切書き込まない。TFUとCSDは7.1での位置が未確認なので、第1段階では実装していない。ジョブの実行手順(キャッシュの無効化、キューのレジスタに開始と終了のアドレスを書く順序、完了の判定、MMUの割込みの処理)は、Mesaに含まれるシミュレータ用のコード(`src/broadcom/simulator/v3dx_simulator.c`、MIT)が示す手順に合わせた。

## 13.3 V3Dのドライバ

### 13.3.1 ファイルと段階

| ファイル | 内容 |
| --- | --- |
| `device/gpu/gpudev.h` | バックエンドが共通層に渡す口(`T_GPUOPS`)と、共通層の関数 |
| `device/gpu/gpu.c` | 共通層(13.4) |
| `device/gpu/v3d/v3d_regs.h` | V3Dのレジスタ(13.2.5) |
| `device/gpu/v3d/v3d.h`、`v3d_mmu.c` | GPUのアドレス空間。ハードウェアに依存しないので両方のマシンでビルドし、QEMUで試験する |
| `device/gpu/v3d/v3d.c` | Raspberry Pi 5のV3D。`rpi5.mk`だけがビルドする |
| `include/ts/gpu.h` | カーネル内の利用者と、将来のSVCが使う定義 |

起動時、`kernel/sysdepend/rpi5/devinit.c`が乱数の初期化の後で`knl_v3d_init()`を呼ぶ。ドライバがどこまで動くかは、ビルド時の`V3D`で決まる(`CNF_V3D`)。

| 指定 | 動作 |
| --- | --- |
| なし(既定) | 何もしない |
| `make TARGET=_RPI5_ V3D=1` | メールボックスでクロックを入れ、識別レジスタとMMUのアドレス幅を読んでコンソールに表示して終わる。V3Dには書き込まない |
| `make TARGET=_RPI5_ V3D=2` | さらにMMUと割込みを設定し、GPUとして共通層に登録し、自己試験(MMUに入れたバッファオブジェクトの確認とキャッシュのクリーンのジョブ)をする。起動の後で、実機の試験(13.8.2)をまとめて行う |

QEMUではV3Dのドライバはビルドもされず、呼ばれもしない。

### 13.3.2 起動の手順

1. クロック5の状態を取得し、オフならオンにして、最大周波数に設定する。
2. コアの`IDENT0`を読み、下位24bitが「V3D」(`0x443356`)でなければ終わる。
3. ハブとコアの識別レジスタを読み、ハブの`IDENT0`が「VHUB」(`0x42554856`)でなければ終わる。続けてMMUのデバッグ情報を読み、バージョン、リビジョン、コア数、QPU数、GPUの仮想アドレスと物理アドレスの幅を表示する。`V3D=1`なら、V3Dに何も書き込まないことを表示してここで終わる。`V3D=2`では、以下の手順ごとに、その前に`v3d: - 手順名`を表示する。実機で止まったときに、どの書込みで止まったかが分かる。
4. バージョンが71でなければ終わる。物理アドレスの幅から、バッファオブジェクトのページを取る上限を決める。
5. 4MBの連続したページテーブルを確保し、スクラッチページを用意して、MMUに設定する(13.3.3)。
6. コアの割込み(フレーム完了、ビニングのフラッシュ完了、メモリ不足)とハブの割込み(MMUの書込み違反、無効なエントリ、上限超え)だけを許可し、INTID 281と282にハンドラを登録する。
7. 共通層に登録し、オーバーフロー用のメモリ(512KB)を確保して、自己試験をする。

### 13.3.3 GPUのアドレス空間

`v3d_mmu.c`はページテーブルとGPUアドレスの割当てを受け持つ。ページテーブルはバディアロケータの最大の次数(4MB)の1ブロックで、起動の早い時期に確保する。テーブルの線形マッピング上のキャッシュラインを一度クリーンしてから、キャッシュしないマッピング(`knl_vmap_pa`の`VMAP_NOCACHE`)を通してだけ書く。

GPUアドレスは、ページ単位のビットマップから先頭一致で割り当てる。64KB未満のアドレスは割り当てないので、0は「アドレスなし」を意味し、リストが下端を越えれば無効なページに当たる。エントリを書き換えた後は、コールバックでハードウェアのTLBとMMUのキャッシュを消去させる。ハードウェアがない試験ではコールバックの回数を数える。

### 13.3.4 ジョブの実行

共通層はジョブを1つずつ`kick`でバックエンドに渡す。制御リストのジョブは、ハードウェアでは2段階である。`kick`がキャッシュを無効化してビニングのリストを始め、コアの割込みで「ビニングのフラッシュ完了」が来ると、割込みハンドラがレンダリングのリストを始める。「フレーム完了」が来たら、必要ならキャッシュをクリーンして、共通層にジョブの終わりを知らせる。ビニングのリストが空のジョブ(タイルを描くだけのブリット)は、すぐにレンダリングから始める。キャッシュのクリーンのジョブは割込みがないので、`kick`の中でポーリングして終える。

MMUの違反の割込みが来たら、違反したアドレスとクライアントを記録し、1つのジョブにつき4回まで表示する。違反したアクセスはスクラッチページに向かうので、ジョブはそのまま最後まで進み、「フレーム完了」のときに失敗として終える。1つのジョブで割込みが1000回を超えたら、消去できずに出続けているものとみなして、その割込みを禁止し、ジョブを失敗として終える。割込みが出続けてシステムが止まるのを防ぐためである。2秒以内に終わらないジョブは、共通層が`reset`を呼んでGPUを止め、失敗として扱う。リセットは現在、CLEの両スレッドをリセットし、割込みを消去し、MMUを消去するだけである。PMブロックによるブロック全体のリセットは未実装である。

### 13.3.5 未実装のもの

TFUとコンピュートのジョブ、ビニングとレンダリングの並行実行(前のジョブのレンダリング中に次のジョブのビニングを進める)、パフォーマンスカウンタ、アイドル時のクロックの停止、ブロック全体のリセット、GMP(メモリ保護)である。

## 13.4 共通層

### 13.4.1 バッファオブジェクト

バッファオブジェクト(BO)は、GPUが自分のMMUを通して読み書きするメモリである。ページアロケータから1ページずつ取るので、大きなBOでも連続した物理メモリを必要としない。ページはキャッシュを通して0で埋めた後、一度キャッシュからクリーンして追い出す。その後、CPUはキャッシュしないマッピングでだけ触る。バックエンドが物理アドレスの上限(`pa_limit`)を示せば、その範囲のページだけを使う(4GB以下なら32bitのゾーンから取る)。

| 関数 | 機能 |
| --- | --- |
| `knl_gpu_bo_create` | BOを作る。バックエンドがあればそのMMUに入れてGPUアドレスを得る。`GPU_BO_NOGPU`ならMMUには入れない |
| `knl_gpu_bo_get`、`knl_gpu_bo_put` | 参照を増やす、減らす。最後の参照がなくなるとMMUから外してページを解放する |
| `knl_gpu_bo_map`、`knl_gpu_bo_unmap` | プロセスのアドレス空間にマッピングする、解除する |
| `knl_gpu_bo_ref` | サイズ、GPUアドレス、プロセスでのアドレス、参照数、使用中のジョブの数 |
| `knl_gpu_bo_wait` | そのBOを使うジョブがすべて終わるまで待つ |

プロセスには共有メモリの領域(4.6、5.3)にマッピングする。アドレスは最初にマッピングしたときに決まり、以後どのプロセスにマッピングしても同じアドレスになる。あるプロセスがGPUで描いたバッファを、ウインドウシステムが同じアドレスでコピーなしに読める。共有メモリの領域のページはアドレス空間を破棄しても解放されないので、BOのページはBO自身が管理できる。マッピングは読み書き可能、実行不可、キャッシュしない(Normal Non-cacheable)属性である。マッピングは参照を1つ持ち、解除すると返す。プロセスの終了時にこれを返すのはSVCの層の役目である(13.5)。

共有メモリの領域のアドレスは再利用しないので、BOを作っては捨てるプログラムは領域(64TB)を少しずつ消費する。Mesaはバッファを再利用するので実用上は問題にならないが、長時間動かすブラウザで問題になれば、BOのアドレスを再利用する仕組みを加える。

### 13.4.2 ジョブとフェンス

ジョブは`knl_gpu_submit`で1本のキューに入り、次のフェンス番号を受け取る。専用のタスク(優先度9)がキューから1つずつ取り出してバックエンドで実行する。この順序により、フェンス番号nが終わったことは、それより前のジョブがすべて終わったことを意味する。ジョブは使うBOを列挙し、終わるまでそれらの参照を持つので、ジョブの途中でBOが解放されることはない。ジョブは待つべきフェンス(`after`)を指定できるが、現在はジョブを順に実行するので、それは常に満たされている。

| 関数 | 機能 |
| --- | --- |
| `knl_gpu_submit` | ジョブを投入し、フェンス番号を返す |
| `knl_gpu_wait` | フェンスが終わるまで待つ。成功なら`E_OK`、ジョブが失敗したかGPUをリセットしたなら`E_IO`、時間切れなら`E_TMOUT` |
| `knl_gpu_done` | 終わった最後のフェンス番号 |
| `knl_gpu_ref` | GPUの種類、バージョン、QPU数、機能、識別レジスタの値 |

待つ側は、「フェンスが終わった」のイベントフラグのビットをクリアしてから終わった番号を確かめ、その後で待つ。タスクは番号を更新してからビットを立てるので、確かめてから待つまでの間に終わったフェンスも取りこぼさない。

### 13.4.3 バックエンド

バックエンドは`T_GPUOPS`(種類、実行できるジョブ、物理アドレスの上限、`info`、`bo_bind`、`bo_unbind`、`kick`、`reset`)を`knl_gpu_register`で登録する。ジョブの終わりは`knl_gpu_job_end`で知らせ、割込みハンドラからも`kick`の中からも呼べる。同時に登録できるバックエンドは1つである。予定しているバックエンドは、Raspberry Pi 5のV3D(13.3)、QEMUのvirtio-gpu(13.7.2)、試験用のもの(13.7.3)の3つである。

## 13.5 プロセスからの利用(予定)

プロセスはSVCのクラス10(`gp_`)でGPUを使う。関数はMesaのドライバがカーネルに出す要求(DRMのV3D用のインタフェース)と1対1に対応させ、ユーザ空間の変換を薄くする。

| 関数 | 対応するDRMの要求 | 機能 |
| --- | --- | --- |
| `gp_opn_gpu`、`gp_cls_gpu` | デバイスを開く、閉じる | GPUのコンテキストを作る、破棄する。コンテキストはBOの番号の表を持つ |
| `gp_ref_gpu` | `GET_PARAM` | 識別レジスタの値と機能 |
| `gp_cre_bo`、`gp_del_bo` | `CREATE_BO`、`GEM_CLOSE` | BOを作り、番号とGPUアドレスを返す。番号を削除する |
| `gp_map_bo` | `MMAP_BO`と`mmap` | BOを自分のアドレス空間にマッピングし、アドレスを返す |
| `gp_sub_job` | `SUBMIT_CL`、`SUBMIT_TFU`、`SUBMIT_CSD` | ジョブを投入し、フェンス番号を返す。BOは番号で指定する |
| `gp_wai_fen` | 同期オブジェクトの待ち | フェンスを待つ |
| `gp_wai_bo` | `WAIT_BO` | BOを使うジョブが終わるのを待つ |
| `gp_shr_bo`、`gp_imp_bo` | PRIMEのエクスポートとインポート | BOを他のプロセス(ウインドウシステム)に渡す、受け取る |

プロセスは自分のコンテキストの表にあるBOしか指定できない。カーネルはジョブを投入するとき、プロセスが指定したBOの参照をジョブに持たせる。プロセスが終了すると、コンテキストを閉じ、表のBOとマッピングの参照を返す。実行中のジョブは最後まで実行され、BOはそのジョブが終わってから解放される。

フェンスの終わりは待つだけでなく、実身のイベント(8.8)としても受け取れるようにする。GPUをデバイスの実身として見せ、`ob_ntf_evt`でフェンスの終了を通信の実身に通知させる。ブラウザのように1つのメッセージループですべてのイベントを待つプログラムは、GPUを待つためだけにスレッドを使わずに済む。

## 13.6 ユーザ空間: Mesa

### 13.6.1 版と構成

Mesa 26.2.3(2026年9月16日リリースの安定版、MITライセンス)を使う。ChromiumはMesaを同梱せず、WebGLはANGLEがOpenGL ES(EGL経由)かVulkanの上に実装する。したがってMesaの版はChromiumの版に縛られず、ANGLEのOpenGL ESのバックエンドが必要とするEGL 1.4以上と、WebGL 2に必要なOpenGL ES 3.0以上を満たせばよい。V3D 7.1に対するMesaのv3dドライバはOpenGL ES 3.1を提供する。以後の版の更新は26.2系のポイントリリースに追従する。

### 13.6.3 ウインドウシステムとEGL

EGLに新しいプラットフォーム`tessronos`を加える。Mesaの`src/egl/drivers/dri2`のプラットフォームのうち、ウインドウシステムを持たない`platform_surfaceless.c`を元にする。

- `EGLDisplay`は`EGL_PLATFORM_TESSRONOS`(仮の値)と`NULL`で得る。ドライバは`gp_ref_gpu`の種類でv3d、virgl、softpipeから選ぶ。
- ウインドウのサーフェスは、TessronOSのウインドウの描画環境を`EGLNativeWindowType`として作る。サーフェスは2つ以上のカラーバッファ(線形のフォーマットのBO)を持つ。`eglSwapBuffers`は描き終えたBOをウインドウシステムに渡し、次のBOに切り替える。
- ウインドウシステムは、渡されたBOの内容をそのウインドウの描画環境のピクセルバッファにコピーし、ウインドウが見えている部分を画面に送る。BOは共有メモリの領域にあるのでアドレスをそのまま使える。BOはキャッシュしないマッピングなのでCPUでの読出しは遅い。最初はこれでよしとし、次にGPUでウインドウを合成する(第10章のウインドウマネージャの合成の置き換え)。
- ピクセルバッファのサーフェス(pbuffer)とサーフェスなしのコンテキスト(`EGL_KHR_surfaceless_context`)も持つ。ChromiumのWebGLはANGLEが自分でフレームバッファオブジェクトを使うので、最初はこれだけで動き、結果は`glReadPixels`でSkiaのCPUのラスタに渡せる。

### 13.6.6 Vulkanという別の道

ANGLEはVulkanの上でも動く。Mesaのv3dvはV3D 7.1でVulkan 1.3を提供する。この道では、OpenGLの状態管理(20万行)、GLSLコンパイラ(8万行)、Galliumの補助(19万行)が不要になり、代わりにv3dv(4万行)、Vulkanの共通部分(9万行)、SPIR-VからNIRへの変換(3万行)が要る。規模はほぼ半分になり、ANGLEが自分のシェーダ変換器を持つのでGLSLの互換性の問題もANGLE側で閉じる。一方、QEMUでの開発にはvirgl(OpenGL)ではなくVenus(Vulkan)が必要で、Windows版のQEMUが持つvirglrendererがVenusを含むかどうかは未確認である。M4まではどちらの道でも共通なので、M5の前にどちらを先にするか決める。

## 13.7 QEMUでの開発

### 13.7.1 使えるQEMU

QEMUはV3Dをエミュレートしないので、V3Dのドライバとv3dドライバの生成するコードは実機でしか確かめられない。QEMUで確かめられるのは、共通層、MMUのページテーブル、SVC、Mesaの全体、EGLとウインドウシステムの結合である。3Dの描画そのものはvirtio-gpuとvirgl(ホストのOpenGLでゲストのOpenGLのコマンドを実行する仕組み)で確かめる。

| QEMU | virtio-gpuの3D | GLを持つ表示 | 判定 |
| --- | --- | --- | --- |
| WSLのxPack QEMU 9.2.4 | `virtio-gpu-pci`(2Dのみ)と`vhost-user-gpu-pci`だけで、`virtio-gpu-gl`がない | なし(`none`、`sdl`、`curses`、`dbus`) | virglは使えない |
| Windows版QEMU 11.0.50(`C:\Program Files\qemu`) | `virtio-gpu-gl-pci`、`virtio-gpu-gl-device`(virtio-mmio)。属性に`blob`、`venus`、`drm_native_context`、`hostmem` | `egl-headless`、`gtk`、`sdl`、`spice-app`、`dbus`。virglrendererとANGLEのDLLを同梱 | virglが使える見込み |

Windows版のQEMUで`-device virtio-gpu-gl-pci -display egl-headless`とすると、デバイスが作られてマシンが起動する(`-display none`では「表示のバックエンドがOpenGLを持たない」として起動しない)。`egl-headless`はウインドウを開かずにホストのGPU(ANGLE経由)で描くので、自動試験に向く。ゲストのドライバがまだないので、virglの3Dコマンドが実際に実行されることはまだ確かめていない。

### 13.7.2 virtio-gpuのバックエンド

TessronOSのvirtioのドライバ(`device/vblk`、`device/vnet`)と同じvirtio-mmioの転送で`virtio-gpu-gl-device`を扱い、共通層のバックエンド(`GPU_KIND_VIRTIO`)にする。

- 初期化で`GET_CAPSET_INFO`と`GET_CAPSET`を発行し、virglのcapsetが返ることを確かめる。これが最初の確認項目になる。
- BOは、ゲストのページ(共通層のBOのページ)をバッキングにしたホストの3Dリソース(`RESOURCE_CREATE_3D`、`ATTACH_BACKING`)に対応させる。V3DのようなGPUアドレスはないので、`bo_bind`はリソース番号を割り当てる。
- ジョブは`SUBMIT_3D`のコマンド列で、フェンス付きで発行する。ホストがフェンスを返したら`knl_gpu_job_end`を呼ぶ。
- ユーザ空間はMesaのvirglドライバとvirglのDRM用winsysを、V3Dと同じDRMシム(`DRM_IOCTL_VIRTGPU_*`の振り分けを加える)で動かす。

試験はネットワークの試験と同じく、WindowsのPythonからWindows版のQEMUで実行する(12.4)。WSLのQEMUで実行する通常の試験には影響しない。

## 13.8 実機で確かめること

1. `V3D=1`で、クロックのタグが応答すること、`IDENT0`が「V3D」と読めること、バージョンが71であること、ハブの識別、コア数、QPU数、MMUの仮想アドレスと物理アドレスの幅。`IDENT0`が読めない場合は、PMブロックの電源ドメイン1を入れる手順を調べる。
2. `V3D=2`で、MMUの設定(`PT_PA_BASE`、`ILLEGAL_ADDR`、`MMU_CTL`の有効ビットとTLBの消去のビット、MMUのキャッシュ)、割込みがINTID 281と282に届くこと、キャッシュのクリーンのジョブが終わること。
3. 最初の描画のジョブとして、ビニングなしのレンダリングのリストで64×64のバッファを1色で塗り、CPUで読み出して確かめる。リストはMesaのパケットの定義から生成したコード(13.6.4)で作る。
4. GPUがCPUのキャッシュを見るかどうか。見るなら、BOをキャッシュするマッピングにしてCPUでの読出しを速くできる。
5. 物理アドレスの幅と、4GBより上のページをBOに使えること。
6. TFUとCSDのレジスタの位置、MMUのエラーを割込みにするビット、ハブの割込みの各ビット。
7. ブロック全体のリセット(PMブロックのリセット0)。

### 13.8.1 実機で読んだ値

2026年9月29日、Raspberry Pi 5で`V3D=1`のイメージを起動して読んだ値は次のとおりである。クロックはファームウェアへの要求で入り、そのままでコアとハブのレジスタが読めた。電源ドメインを別に入れる必要はなかった。

| レジスタ | 値 | 解釈 |
| --- | --- | --- |
| クロック5 | 960MHz(最大960MHz) | 最大周波数で動く |
| コアの`IDENT0` | `07443356` | 下位24bitが「V3D」、上位8bitがメジャーバージョン7 |
| コアの`IDENT1` | `81001441` | マイナーバージョン1、スライス4、スライスあたりのQPU 4(QPUは16)、31:28が8(VPMは64KB) |
| コアの`IDENT2` | `c0078101` | 未解釈 |
| ハブの`IDENT0` | `42554856` | 「VHUB」。ハブのレジスタの位置が正しいことが分かる |
| ハブの`IDENT1` | `00081117` | 3:0と7:4がコアのメジャーとマイナー(7と1)に一致するので、11:8がコア数(1)である。15:12の1と19bitは未解釈 |
| ハブの`IDENT2` | `00001900` | 8bitが立っている(MMUを持つ) |
| ハブの`IDENT3` | `00000700` | 15:8がリビジョン7 |
| MMUのデバッグ情報 | `20804664` | 7:4と11:8がともに6。30を足してアドレスの幅とする解釈では、仮想アドレス、物理アドレスとも36bit(解釈は未確認) |

最初のドライバはハブの`IDENT1`の19:16をコア数として読み、8と表示していた。上の値に合わせて11:8に直し、ハブの`IDENT0`が「VHUB」でなければ終わるようにした。

続けて`V3D=2`のイメージで、MMUの設定と自己試験まで止まらずに進んだ。

| 表示 | 分かったこと |
| --- | --- |
| `page table at a000000, invalid accesses to 9d56000` | 4MBの連続したページテーブルを4GBより下に確保できた。`PT_PA_BASE`、`ILLEGAL_ADDR`、`MMU_CTL`、MMUのキャッシュの制御レジスタへの書込みでバスが止まらない。TLBの消去とMMUのキャッシュのフラッシュは、待つビットが時間内に0に戻った |
| `self test: BO at GPU 00090000, entry 30100879 for page 100879000` | BOのページが4GBより上(`0x1_0087_9000`)から取られ、有効と書込み可のビットと物理ページ番号を持つエントリになった |
| `self test: cache clean job ended (0)` | L2Tのキャッシュのクリーンで、待つビット(`TMUWCF`、`L2TFLS`)が0に戻った |

待つビットが0に戻ったことは、そのビットが一度も立たなかった場合と区別できないので、ビットの位置の確認としては弱い。GPUがMMUを通して実際にメモリを読み書きすること、割込みがINTID 281と282に届くこと、MMUのエラーの報告は、まだ確かめていない。これらは次の描画のジョブ(13.8の3)で確かめる。

### 13.8.2 実機の試験(`V3D=2`)

SDカードに書き込む回数を減らすため、`V3D=2`のイメージは、確かめられることを1回の起動でまとめて試す(`device/gpu/v3d/v3d_test.c`)。試験は起動の3秒後に優先度30の専用のタスクで始まり、1件ごとに`v3d test:`で始まる行をコンソールに出力する。どのジョブにも時間の上限があり、終わらないジョブは共通層がGPUをリセットするので、試験が失敗しても次の試験に進み、システムの起動も止まらない。GPUを悪い状態にするおそれのある試験(オーバーフローとMMUの違反)は後に回し、その後にもう一度描画して、GPUが回復したかどうかを確かめる。最後に割込みの回数と、成功した件数と失敗した試験の名前を出力する。

ジョブは、ハードウェアが実行できる最小のフレームである。ビニングのリストは描画を1つも含まず、レンダリングのリストはタイルバッファを1色でクリアする(またはメモリから読み込む)だけで、すべてのタイルをメモリ上のラスタ形式のバッファに書き出す。描画の対象は1つ(RGBA8UI、1ピクセル32bit)で、タイルは64×64である。パケットの並び、タイルとスーパータイルの大きさ、タイルの割当てメモリの大きさは、Mesaのv3dvがバッファを1色で埋めるとき、およびバッファをコピーするときと同じにした。試験はBOを線形マッピング(キャッシュする)を通して読み書きし、キャッシュの操作を明示的に行う。

| 試験 | 内容 | 成功の条件 |
| --- | --- | --- |
| `fill` | 64×64を1色で埋める | ジョブが`E_OK`で終わり、全ピクセルがその色で、バッファの直後の1ページが0のまま |
| `fill uneven` | 100×37(タイルの大きさの倍数でない) | 同上。タイルの端の切り取りを確かめる |
| `fill large` | 1920×1080 | 同上。スーパータイルが複数になる構成を確かめ、所要時間と書込みの速さ(MB/s)を出す |
| `copy` | CPUが書いた256×256のラスタを読み込んで、別のバッファに書き出す | 全ピクセルが一致する |
| `queue of 4` | 64×64のジョブを4つ続けて投入し、最後のフェンスを待つ | 4つとも正しい色で、フェンスの番号が投入の順 |
| `coherence` | コピー元のメモリにはA、CPUのキャッシュにだけBを置き、コピー先のキャッシュラインを読み込んでからコピーする | ジョブが終わり、メモリ上の結果がすべてAかすべてB。GPUがCPUのキャッシュを読んだか(B)、CPUが無効化せずにGPUの書込みを見られたかを出力する |
| `overflow` | 1920×1080で、タイルの割当てメモリを実際より少なく伝える | ジョブが`E_OK`で終わり、全ピクセルが正しい。メモリ不足の割込みの回数を出す |
| `MMU fault` | MMUにないアドレス(`0x8000`)へ書き出す | ジョブが`E_IO`で終わり、違反が報告される。違反の状態、アドレス、クライアント、スクラッチページに届いた語数を出す |
| `after fault` | 違反の後にもう一度64×64を埋める | `fill`と同じ |
| `interrupts` | ここまでの割込みの回数 | フレーム完了とビニングのフラッシュ完了が1回以上あり、禁止した割込みがない |

出力の例を次に示す(数値は例である)。

```text
v3d test: start
v3d test: fill 64x64 ok: job E_OK, 0 of 4096 pixels wrong, 0 written past the end, 180 us, 91 MB/s, first page 100879000
...
v3d test: interrupts: core 22 (frames 11, flushes 11, out of memory 1), hub 1 (MMU faults 1), turned off 0
v3d test: summary 10/10 passed
```
