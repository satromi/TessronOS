# 第7章　ファイルシステム

## 7.1 2つのファイルシステム

TessronOSは2つのファイルシステムを持つ。システムの実身を格納するTSFSと、ブートパーティションと外部メディアに使うFATである。

| | TSFS | FAT |
| --- | --- | --- |
| 用途 | 実身の格納 | ブートパーティション、PCとデータをやり取りするメディア |
| 名前 | 実身はUUIDで開く。ディレクトリツリーはない | パスで開く |
| 形式 | TessronOS独自。ジャーナルとチェックサムを持つ | FAT12、FAT16、FAT32。長いファイル名に対応 |
| API | 実身の基本操作`ob_`(第8章) | T2EX互換の`fs_` |

## 7.2 fs_

`fs_`はT2EXのファイル管理の関数である。`fs_open`、`fs_read`、`fs_write`、`fs_close`、`fs_mkdir`、`fs_rename`、`fs_stat`などでFATのボリュームを扱う。マウントテーブルは全体で1つで、`/boot`にSDカードの第1パーティション(QEMUではテスト用ディスクのFATパーティション)がマウントされる。USBメモリは、デバイスの実身を通して要求すると`/media`の下にマウントされる(6.1)。マウントに使うfimpは、区画の先頭の中身から判別して選ぶ(7.6)。

ファイルディスクリプタはプロセスごとに持ち、プロセスが終了すると閉じる。プロセスの`fs_read`と`fs_write`は256KBずつに分割して実行する。

FATは、電源断の後にマウントしたとき、クラスタチェーンとディレクトリエントリのサイズの不一致など、書込み途中で残った不整合を検査して修復する。

FATのファイルの大きさはディレクトリエントリの32ビットで決まるので、4GB-1バイトを越える書込みと切り詰めは`EX_FBIG`で拒否する。越える位置をまたぐ書込みは、入る分だけ書いてその長さを返す。以前は検査がなく、越えて書くとサイズのフィールドがオーバーフローして、ファイルの中身とクラスタチェーンが食い違った。切り詰めでファイルを伸ばすときは、クラスタチェーンを伸ばし、足したクラスタと、元の終端から最後のクラスタの終わりまでを0にする(以前はサイズだけを変え、伸ばした所を読むと`EX_NOENT`になった)。終端より先に書くときも、元の終端から最後のクラスタの終わりまでを0にする。`fs_read`と`fs_write`は戻り値がINTなので、1回に転送するのは0x7FFFF000バイト(LinuxのMAX_RW_COUNTに当たる)までとし、それより大きな要求には短い長さを返す。

### 名前の長さ

パスの1つの名前は767バイトまでとする(`NAME_MAX`。`FS_NAME_MAX`の768から終端の0を除いた数)。FAT、exFAT、NTFSの長いファイル名の255単位をUTF-8にしたときの最大で、`struct dirent`の`d_name`(768バイト、`T_DIRENT.name`と同じ)と`pathconf`の`_PC_NAME_MAX`もこの値である。newlibの`NAME_MAX`(255)は`include/posix/limits.h`で置き換える。パス全体は1023バイトまで(`FS_PATH_MAX`)。

ファイルのレイヤ(`fs.c`)は、パスを受け取る関数(`fs_open`、`fs_stat`、`fs_mkdir`、`fs_rename`、`fs_link`、`fs_chmod`、`fs_utime`、`*at`の各関数など)の入口で、名前の1つが767バイトを超えるか、パス全体が長すぎると、どのファイルシステムにも渡さずに`EX_NAMETOOLONG`(POSIXの`ENAMETOOLONG`)を返す。名前を切り詰めて受け取ることはしない。

objfs(「/」から仮身をたどるツリー、`objfs.c`)は、取り込んだファイルの名前(`tessronos.file.name`)か実身の名前を、そのまま名前として見せる。実身の名前には長さの上限がない(第8章)ので、767バイトを超える名前は文字の境界で縮め、同じ名前が並んだときと同じ`~N`の番号を`~1`から付けて見せる。番号を付けた名前も767バイトに収め、ほかの名前と重なれば番号を進める。見せた名前で開くと元の実身に届く。実身の名前そのものは変えない。箱の中身は、箱の仮身の数だけ読む(以前は4096個で打ち切っていた)。読んだ中身は、キャッシュと読んでいる呼出しが共有し、最後に解放した側がメモリを解放する。名前を引くたびにコピーすることはしない。

キャッシュした箱の中身は、箱と、箱が並べる実身の変更の通番(`knl_ob_chg_serial`、8.8.2)と、ボリュームの通番(`knl_obfile_serial`)が読んだときのままの間だけ使い、どれかが変わっていれば読み直す。デスクトップや実身のレイヤの関数(`om_obj_link_add`など)で仮身を足したり外したりしたときも、並べる実身の名前を変えたときも、次の一覧と名前の検索に反映される(ディレクトリの変更で無効になるLinuxのdentryのキャッシュに当たる)。比べるのは通番だけで、そのために実身を読むことはない。以前は2秒間(`OBJ_KEEP_MS`)保持したままにしていたので、objfsを通さずに足した実身が最大2秒見えなかった。「/」に当てる実身の再検索は、今も2秒ごとである。

POSIXの`rename`で付けた名前は、`xf_rename`がメタデータの`tessronos.file.name`に全体を書き、拡張子を除いた部分を全体のまま実身の名前にする(`om_store_rename`)。以前は63バイトで、UTF-8の文字の途中で切っていた。`xf_find`も名前の全体で比べ、`xf_name`は呼出し元のバッファに入らない名前だけを、拡張子を残して文字の境界で切る。

### ディスクの実身のキーから開く

利用者が差したディスクの中のファイルは、ディスクのデバイスの実身を開いたキーから開く。パスのツリー(`/media`)にはつながず、パスはファイルのレイヤの中とディスクの中のパスだけになる(Linuxのfsopenとfsmount(マウントをパスのツリーにつながずにディスクリプタで扱う)と、openat2の`RESOLVE_BENEATH`(ディスクリプタのディレクトリの下から出ない)に当たる)。

| 関数 | 働き |
| --- | --- |
| `fs_opn_vol(devkey, fimpnm, flags)` | ディスクのファイルシステムのルートディレクトリをディスクリプタ(vd)として返す。`fimpnm`がNULLなら中身から判別する。`flags`は`FS_MNT_RDONLY`だけ |
| `fs_openat(vd, path, oflags)` | ディスクの中のファイルを開く。返すのは普通のディスクリプタで、`fs_read`などがそのまま使える |
| `fs_statat`、`fs_mkdirat`、`fs_rmdirat`、`fs_unlinkat`、`fs_utimeat`、`fs_renameat` | ディスクの中のパスの操作。名前を変えるのは同じディスクの中だけ |
| `fs_fstatvfs(vd, st)` | 空き容量など |

vd自身もディスクリプタなので、`fs_getdents`でルートの一覧を読め、`fs_close`で閉じる。プロセスが終わると閉じる。

権限は、マウントの権限とディスクリプタの権限を分ける。

- マウントの権限は、そのディスクを開いている者のうち、書く者が1人でもいれば書込み可能である。読取り専用のマウントに書込み可能の要求が来たとき、そのマウントで開いているファイルがなければ、マウントを書込み可能でつなぎ直す(FATの不整合の検査と修復は、書込み可能でつなぐときに行うため)。開いているファイルがあれば`EX_BUSY`で拒否する。
- ディスクリプタの権限は、`fs_opn_vol`のときの`flags`とキーの権限で決まり、マウントが書込み可能になっても変わらない。読取り専用のvdからは、書くための`fs_openat`と、ディスクの中を変える操作が`EX_ROFS`になる。vdから開いたディスクリプタは、vdの権限を越えない。書くには、キーに`OB_OP_WRITE`が要る(今の`fs_attach_dev`と同じ)。

パスは、vdのディスクのルートから下だけをたどる。先頭の`/`はディスクのルートを指す。`.`と`..`はファイルのレイヤがパスを渡す前に文字列として正規化し、ルートより上に出る`..`は`EX_ACCES`で拒否する。パスはvdのマウントのfimpだけに渡すので、パスのツリーのほかのマウントには届かない。シンボリックリンクを持つfimpは、そのボリュームの中だけで解決し、ルートより上や別のボリュームを指すリンクはたどらない。KTESTで、`..`、`../..`、`/../x`、ルートより上を指すリンクで、vdの外のファイルを開けないことを確認する。

ディスクが抜かれたときは、今のパスのマウントと同じく、マウントに`gone`のフラグが立ち(`knl_fs_revoke`)、vdとそこから開いたディスクリプタは、読み書きとパスの操作に`EX_IO`を返す。`fs_close`は成功し、最後のディスクリプタが閉じたときにマウントが片付く。KTESTで、USBのディスクをQEMUのモニタで抜き、vdとファイルのディスクリプタが落ちずに`EX_IO`を返し、閉じられることを確認する。

`/media`のパスのツリーから同じディスクを使う形(`fs_attach_dev`)は、バックアップとファイル変換の移行が終わるまで残す。その間、1つのディスクのマウントは1つだけにする。`fs_opn_vol`は、そのディスクのマウントがあれば(`/media`にあっても)それを共有する。`fs_attach_dev`は、`fs_opn_vol`がパスなしで作ったマウントがあれば、それに`/media`のパスを付ける。`fs_detach_dev`は、vdが残っていればパスだけを外し、マウントは最後のディスクリプタが閉じたときに片付く。移行が終わったら、`fs_attach_dev`と`/media`の名前をプロセスから見える所から外す。

## 7.3 TSFS

TSFSは、実身の構造をそのままディスク上の形式にしたファイルシステムである。GPTのパーティションに置き、パーティションタイプGUIDは`54465331-0000-4000-8000-5446532d5631`である。ネイティブの形式にはバージョン4とバージョン5があり、ビルドが作るシステムボリュームと新しく作るボリュームはバージョン5である(下の「形式のバージョン5」)。

実身は次の要素からなる。

- 管理用セグメント。名前、日時、保護情報、レコードの並びと型、アプリケーションが格納する設定(`applist`、`window`、`tessronos.*`など)を持つJSONである。
- アイコン。ICOかPNGで、64KBまで。
- レコードの列。レコードは型(0〜31)とサブタイプを持つバイト列で、任意の位置に挿入と削除ができる。型1はxmlTADで、その中の`<link>`が仮身である。1つの実身のレコードは、バージョン4のボリュームでは256まで(`TSFS_MAX_REC`)で、バージョン5のボリュームには上限がない。ネイティブの形式では、配置表(1レコード48バイト)は数を32ビットで持つ管理用の部分である。小さいうちは実身ブロックのインライン領域(3584バイト)に置き、入りきらなくなると共通のヘッダを持つブロックの連続(1ブロックに約84レコード分)に移して、ジャーナルを通して書く。仮身表やメタデータと同じ置き方で、インデックスの段は増えない。256レコードの配置表は12KBで、4ブロックの連続になる。したがってバージョン4の上限は形式ではなく、管理用セグメントが持つレコードの並び(`records`)の大きさで決めている。256レコードの並びは約10KBで、バージョン4のボリュームのメタデータの上限(約492KB)に十分収まる。上限を64から256に広げたときに実身ブロックの形は変えていないので、それ以前のボリュームはそのまま読める。ただし、65以上のレコードを持つ実身を作ったボリュームは、上限が64のカーネルと検査のツールでは形が壊れていると判断される。カーネルの検査(`tsfsck.c`)とホストのツール(`tools/tsfs_py`、`mktsfs`、`fsck.tsfs`)の上限も256にした。`tests/ktest/ktest_tsfsobj.c`の`test_many_records`は、バージョン4のボリュームに256のレコードを型とサブタイプを変えながら作り、257個目が拒否されること、マウントし直しても中身と型が保たれること、途中を消すと後が詰まること、ボリューム全体の検査が実身について何も見つけないことを確認する。
- レコードのバイトが置かれるブロックの連なり(エクステント、ラン)。1つのランなら配置そのものに(`F_RUN`)、165まで(`TSFSO_MAX_EXTENTS`)なら1つのリーフのブロックに(`F_TREE`)置く。それより多いとき、バージョン4のボリュームでは、リーフの番号を並べたインデックスのブロックと、165ずつのランを持つリーフに(`F_TREE2`、2段のツリー)置き、165×165=27225のランまで持てる。以前は1つのリーフまでで、空きが細切れのボリュームでは大きなレコードが`E_NOMEM`で書けなかった。2段のツリーは1つのリーフに収まらないレコードのときだけ使い、収まるまで短くなれば1つのリーフに戻す。書き足すときは、変わったランを持つリーフから後とインデックスだけを書き直すので、1回の変更で書くブロックは少ない。バージョン5のボリュームでは、段の数を決めないランのツリー(`F_TREEN`)に置く(下の「ランのツリー」)。
  - 2段のツリーを初めて書いたボリュームは、スーパーブロックの非互換の機能に`TSFSBLK_INCOMPAT_XT2`(0x0002)のフラグを立てる(R1.200から)。フラグは、2段のツリーがなくなっても外さない。R1.110までのカーネルは、知らない非互換の機能のフラグがあるボリュームを開かず(`ts_opn_vol_blk`が`E_NOSPT`)、スーパーブロックを読む以外は何も書かないので、ボリュームを壊さない。R1.110の`fsck.tsfs`は、検査では「incompatible features 0x2: the kernel will not open it」のエラーを出す。ただし`--fix`を付けると、フラグは残したままスーパーブロックと予備を書き直し、2段のツリーを知らずに修復しようとするので、R1.200のボリュームにR1.110の`fsck.tsfs --fix`を使ってはいけない。R1.200からの`fsck.tsfs`は、知らない非互換の機能のフラグがあるボリュームには`--fix`と`--relink`で何も書かず、終了コード2で戻る(R1.110の`fsck.tsfs`は0x2のフラグを立てたボリュームで、R1.200の`fsck.tsfs`は知らない0x100のフラグを立てたボリュームで確認した)。R1.200からのカーネルの検査(`tsfsck.c`)と`tools/tsfs_py`は2段のツリーを読み、フラグのないボリュームの2段のツリーはエラーとして報告する。`ktest_tsfsobj`の`test_many_runs`は、2つのレコードを1ブロックずつ交互に伸ばして400を越えるランにし、フラグが立つこと、開き直しても全部読めること、検査が何も見つけないこと、短くすると1つのリーフに戻ることを確認する。
- リソース。レコードに付随する画像、音声、動画である。
- 仮身表。この実身が含む仮身の一覧で、TSFSが型1のレコードから生成する。作り直すのは、書き込んだ実身を、レコードを読み書きする最後のキーが閉じたときである(`tsfs.c`の`ts_cls_obj`)。属性だけで開いたキー(`TFO_SHARE`、ウインドウが変更の通知を受けるために開いたままにするキー)は数えない。仮身一覧のプロセスは自分の実身をそのキーで監視したまま保存するので、これを数えると、プロセスが終わるまで仮身表と参照数が変わらない。

実身はUUIDのバージョン7で識別し、B+ツリーでUUIDから検索する。時計が設定される前(電池のないマシンで、SNTPで時刻を合わせる前)に作る実身は、時刻を含まない乱数だけのバージョン4のUUIDで識別する。キャビネットは仮身を並べた実身であり、ファイルシステム側にディレクトリはない。

TSFSは仮身表から、各実身を指している同じボリュームの仮身の数(参照数)を自動で数える。ほかのボリュームの実身を指す仮身は、指す側のボリュームでは数えず、指される側のボリュームが持つ「ほかのボリュームからの参照」の記録を通して、指される実身の参照数に数える(8.3)。アプリケーションは参照数を操作しない。参照数が0になった実身は屑実身になり、空き領域が減ったとき、または要求されたときに回収される。

### 格納方式

TSFSには2種類の格納方式がある。

| 格納方式 | 形式 |
| --- | --- |
| ネイティブ | GPTのパーティションをTSFSの形式で使う。システムボリュームはこの方式 |
| FAT上 | FATのディレクトリに、実身を1つずつTADjs Desktopと同じ形式の複数のファイルで格納する |

FAT上の格納方式のファイルは次の形式である。この形式で書き出せば、TADjs Desktopで開ける。

| ファイル | 内容 |
| --- | --- |
| `{UUID}.json` | 管理用セグメント |
| `{UUID}_0.xtad` | 位置0のレコード(xmlTAD) |
| `{UUID}_N.xtad`、`{UUID}_N.bin` | 位置Nのレコード(`.bin`は型1以外) |
| `{UUID}.ico` | アイコン |
| `{UUID}_N_M.png`など | 位置Nのレコードのリソース |

### 障害耐性

ネイティブのTSFSは、電源断が起きても管理構造が壊れないように設計してある。

- 管理ブロックはすべてチェックサム(CRC32C)を持つ。読み込んだブロックのチェックサムが合わなければ、ボリュームを読取り専用に切り替え、以後は書き込まない。最初のエラーは、その種類とブロックをコンソールに出す(`tsfs: デバイス名: ERROR kind ...`)。
- 変更はジャーナルに書いてから本来の位置に書く。マウント時にジャーナルを再生するので、途中で中断した変更は、すべて反映されるか、まったく反映されないかのどちらかになる。
- エラーが記録されたボリュームは、マウントのときにジャーナルを再生せず、読取り専用で開く(エラーの種類、ブロック、最初と最後の時刻をコンソールに出す)。ジャーナルは検査(7.5)のときに再生する。それまでは、変更のトランザクションを始めようとしても`E_RONLY`で拒否する(`ts_jrnl_begin`)。以前は拒否せずにトランザクションを受け付け、ジャーナルのリングの長さが0のままコミットして、ゼロ除算の例外で止まっていた(ThinkPad X1 Yoga 第3世代で、起動中の時計の帯の書込み)。
- ジャーナルは本来の位置に書き終えた後も、前に書いたブロックのコピーを、リングが一周して上書きされるまで残す。秘密を含んでいたレコードを書き直したプログラムは、`ob_wip_vol`で、その実身のあるボリュームのジャーナルを0で上書きできる(`ts_jrnl_wipe`)。実行中のトランザクションが終わるのを待ち、すべてを本来の位置に書いてから、リングの全体を0で書き、デバイスのキャッシュをフラッシュする。リングには再生するトランザクションが残っていないので、再生は何もしない。その実身のレコードを書ける者だけが呼べる。ブラウザが、平文で保存されていたパスワードを暗号化し直した後に使う(14.4.7.1)。
- スーパーブロックは2つを交互に書き、さらにバックアップを持つ。
- 区画とボリュームを広げる途中で電源が切れても、元のまま使えるか、次に開くときに拡張を終える(7.7)。
- 開いたまま削除された実身や、仮身表を再構築している途中の実身は孤児のツリーに登録し、マウント時とアンマウント時に後処理する。

`tools/fsck.tsfs`がボリュームを検査し、`tools/mktsfs`がボリュームを作成する。どちらもPythonで書かれ、ホストで動く。マシンの上での検査と修復は7.5で述べる。

### ジャーナルの確定とボリュームのロック

ジャーナルのトランザクションは、作る、閉じる、確定させる、の3つの段階を通る(`tsfsjrnl.c`)。

1. 作る。変更する操作がハンドルを取り(`ts_jrnl_begin`)、管理ブロックの新しい内容をメモリのトランザクションに入れる。データのブロックは本来の位置にそのまま書く(ordered)。
2. 閉じる。最後のハンドルを解放した呼出し元が、空きビットマップ、グループのヘッダ、スーパーブロックの変更をトランザクションに加え、トランザクションをキューに入れる(`ts_jrnl_close`)。そのコピーはこの時から、すべての読込みに見える。デバイスには何も書かない。リングにキューの後ろの空きが足りないときだけ、ここでキューを書き、チェックポイントをする。
3. 確定させる。`ts_jrnl_durable`を最初に呼んだ者が、その時のキューをすべてリングに書く。まずデバイスのキャッシュをフラッシュし(キューのトランザクションが指すデータを媒体に書き込むため)、キューのすべてのトランザクションをディスクリプタブロックからコミットブロックまで1つのバッファに並べて1回の要求で書き(リングの端で折り返すときは2回)、最後にもう一度キャッシュをフラッシュする。デバイスがFUAの書込み(`TDN_FUAWRITE`、6.8)を受け付けるときは、リングへの書込みをFUAで行い、最後のフラッシュの要求は省く。受け付けないデバイスは最初の1回で`E_PAR`を返し、そのボリュームはそれ以降ふつうに書いてフラッシュする(`knl_tsfsblk_raw_writes_fua`)。書込みキャッシュを持たないと報告するUSBの大容量記憶(多くのカードリーダとUSBメモリ)は、Linuxのsdと同じく、フラッシュの要求にコマンドを送らずに成功を返し、FUAも受け付けない(6.3.0)。そのため、USBでは確定は、デバイスが書込みの完了を報告したことだけに頼る。トランザクションが指すデータの書込みがすべて完了したと報告されてから、リングへの書込みを出す。リングへの1回の書込みの中の順序は、ほかのデバイスでFUAで書くときと同じく、デバイスに任せる。完了を報告した後も自分のキャッシュに保持している(それをキャッシュのページで報告しない)デバイスでは、電源を切る直前の確定が失われることがある。これはLinuxでも同じである。書いている間に来た者はそれを待ち、多くはそれで確定する(group commit)。

`tsfs.c`の操作は、ボリュームのロックを持ったまま操作を行ってトランザクションを閉じ、ロックを解放する。ロックを持つ間にデバイスへ書くのは、データのブロックと、トランザクションの外で本来の位置に書くブロックだけになる。確定をいつ待つかは、次の「確定の保証」のとおりである。`ts_end_trx`で終えるトランザクションは、戻る前に確定させる。

#### 確定の保証

開いている実身のレコードを書く、足す、切り詰める、取り除く、並べ替える、型を変える操作(`ob_wri_rec`、`ob_apd_rec`、`ob_trn_rec`、`ob_del_rec`、`ts_ins_rec`、`ts_mov_rec`、`ts_set_rtp`)は、トランザクションを閉じてキューに入れたところで戻る。媒体に書き込むのは、次のどれかが最初に起きたときである(`tsfs.c`の`vol_lazy`)。

- そのキーを閉じたとき(`ob_cls_obj`)。閉じる操作は、そのキーで変えたものが媒体に書き込まれるまで待ち、書き込めなければエラーを返す。
- 同期のAPIを呼んだとき(`ob_syn_obj`。POSIXのレイヤの`fsync`と`fdatasync`は`fs_fsync`を通してこれに当たる。`sync`は全部のボリューム)。
- チェックポイントのタスクが動いたとき(5秒ごと、`CNF_TSFS_FLUSH_MS`)と、ほかの者が確定させたとき。キューはまとめて1回でリングに書くので、いくつの操作があっても、フラッシュの要求は2回(FUAで書けるデバイスでは1回)である。

レコードを丸ごと置き換える操作(`ob_rpl_rec`)、メタデータ、アイコン、リソースの書込み、実身を作る、消す操作は、これまでどおり戻る前に媒体に書き込む。

同じ実身を、書くキーと読むキーが同時に開いていることがある(排他を指定しない書く者と、書込みの排他`OB_O_WEXCL`で開いた書く者は、読む者を締め出さない。開くときの排他の指定は8.3)。TSFSのレイヤは、実身の開き方を開いたキーごと(`TSFSOBJ`)に持ち、レコードの読み書きはボリュームのロックの中で行う。`ob_rpl_rec`は新しい場所に書いてから1つの変更で差し替えるので、読む者に見えるのは古いレコードか新しいレコードで、混ざったものは見えない。その場で上書きする`ob_wri_rec`は、操作の途中の中身も見えうる。設定の実身の書込みは`ob_rpl_rec`を使う。

電源が切れたときは、次のようになる。

- 確定していない操作は失われる。ボリュームは壊れない(再生はコミットブロックの検査に通った最も長い先頭の部分だけを戻す)。
- レコードに書き足した分と、`ob_rpl_rec`で置き換えたレコードは、確定した時点の中身か、それより前の中身のどちらかになる。書き足すブロックは新しく確保し、置き換えは新しい場所に書いてから1回の変更で差し替えるからである。
- すでにあるブロックを上書きした範囲は、確定していなければ新旧が混ざることがある。データのブロックは本来の位置にそのまま書く(Linuxのext4の`data=ordered`に当たる)。混ざるのを避けたいプログラムは、`ob_rpl_rec`で丸ごと置き換えるか、同期のAPIを呼ぶ。

アプリの保存は、デスクトップ(`om_obj_record_put`、`tad_write`)、表計算、カレンダー、手帳、単語登録、システム環境設定、ネットワーク設定、ユーザ環境設定、外観と機器の設定(`uconf.c`)、トレーが`ob_rpl_rec`を使い、保存が終わったと見せる前に媒体に書き込む。書庫管理、バックアップ、展開、ファイル変換の取込みのように新しい実身に書いていくものは、書き終えてキーを閉じたときに媒体に書き込む。

書込みの区切りは、確定が1回ごとでなくなった後も、システムのツールでは4MBにしてある(`arc_pack.c`、`bk_util.c`、`bk_rest.c`、`bk_vol.c`、`unp_obj.c`、`xfu_in.h`の`XFU_CHUNK`、`xf.c`の`XF_CHUNK`)。1回の書込みの手間(実身ブロックと配置表を読み直すこと)が少ないほど速い。

1つのトランザクションの書き方は、これまでの「コピーを書く、キャッシュをフラッシュする、コミットブロックを書く、キャッシュをフラッシュする」から、「キャッシュをフラッシュする、コピーとコミットブロックを書く、キャッシュをフラッシュする」に変えた。フラッシュの回数は同じ2回で、それがキューのトランザクションの数によらなくなる。コミットブロックがコピーより先に媒体に届いても、再生は各コピーをディスクリプタブロックが持つCRCと比べ、合わないところで止まるので、半端なトランザクションを戻すことはない。この変更ではリングの形式と再生を変えていないので、前のカーネルで作ったボリュームもそのまま使え、`tools/tsfs_py`と`fsck.tsfs`も変わらない。

閉じたが確定していないトランザクションが解放したブロックは、そのトランザクションが確定するまで割り当てない(`tsfsblk.c`の`busy_add`、`knl_tsfsblk_unbusy`)。媒体の上ではまだ前の持ち主のものなので、次の持ち主のデータが先に書かれてから電源が切れると、前の持ち主の中身が他人のデータになってしまう。ボリュームが満杯で、空きがこのブロックだけのときは、閉じたトランザクションを確定させてから探し直す。Linuxのext4もXFSも、確定前に解放したブロックを同じ理由で使わない。

チェックポイントは、コピーの一覧を取るときと後片付けのときだけジャーナルのロックを持ち、本来の位置への書込みはロックを解放して行う。以前は書き終えるまでロックを持っていたので、その間、管理ブロックを読む操作はすべて待っていた。チェックポイントの最中に置き換えられたコピーは次の回に回し、書いている最中のコピーのバッファは書き終えるまで解放しない。書いている最中のブロックを本来の位置に書こうとする者は、チェックポイントが終わるのを待つ(`knl_jrnl_forget_blk`)。チェックポイントのタスクは5秒ごとのほか、コピーが512ブロックを超えたとき、リングが半分埋まったときにウェイクアップされる。

#### この方式にした理由

ThinkPad X1 Yoga 第3世代で、USBメモリのシステムボリュームから起動すると、デスクトップが最初のウインドウを出したところで10〜14秒止まった。デスクトップはボリュームのロックを待ち、ロックはかな漢字変換のタスクが、ジャーナルのリングへの書込みとSYNCHRONIZE CACHEの途中で持っていた。その起動ではUSBメモリへの書込みが4766回(合わせて15.8秒)、フラッシュの要求が1807回(3.8秒)あった。原因は次の4つの重なりであった。

- 1つの操作が1つのトランザクションで、操作ごとに確定させ、そのたびにデバイスのキャッシュを2回フラッシュしていた。リングへは1ブロックずつ要求していたので、小さな書込み1回でデバイスへの要求が8回ほどになった。
- その間ずっとボリュームのロックを持っていた。デスクトップは仮身を描くたびに実身を開いて閉じ、閉じるとき(`ts_cls_obj`)にロックを排他で取るので、変換のタスクの1回ごとの確定を待った。
- チェックポイントがジャーナルのロックを持ったまま本来の位置に書いていたので、その間は管理ブロックの読込みも待った。
- かな漢字変換(mozc)は最初の起動で学習のファイル`segment.db`(320KB)と`boundary.db`(80KB)を作る。C++のストリームが1KBずつ`write`するので、`ob_wri_rec`が782回、トランザクションも782になった。QEMUで数えると、変換エンジンの起動の間にトランザクションが854、デバイスへの書込みが4002回、フラッシュの要求が1730回で、実機の数と合う。USBのディスクを1秒300要求に絞ったQEMUのx64でも、変換エンジンの起動に12.5秒かかった。

変換エンジンのプロファイルが毎回作り直されているわけではない。同じイメージで2回目に起動すると、学習のファイルは残っていて、変換エンジンの起動は0.13秒で終わる。KERNEL.TXTの`user_dictionary.db`が無いという行は、書き込んだばかりのイメージの最初の起動だから出る。`.history.db`と`config1.db`が無いという行は、変換の履歴と設定を変えるまでmozcがそれらを作らないためで、2回目以降も出る。エラーではない。

かな漢字変換は、エンジンが続けて書いたものを`kconv.c`で256KBまでためて1回の`ob_wri_rec`にする(`KC_WBUF`)。ファイルを読む前、サイズを問い合わせる前、名前で探す、名前を変える、消す前、閉じる前に書き出す。学習のファイルを作るときの`ob_wri_rec`は782回から3回になる。

ほかのOSのジャーナルと比べて、次のように決めた。

| OS | トランザクションのまとめ方 | 媒体に書き込むタイミング | 書いている間のロック |
| --- | --- | --- | --- |
| Linux ext4(jbd2) | 実行中のトランザクション1つに、その間のすべての操作が入る | 5秒ごと(`commit=`)か満杯のとき。`fsync`はそれを待つ | 確定は専用のスレッドが書き、その間に次のトランザクションが実行される |
| FreeBSD UFS+SU | ジャーナルを持たず、書く順序の依存を追う(SU+Jはfsckを省くための補助のジャーナル) | syncerが30秒ごと。`fsync`はそのファイルの依存を書く | バッファごとのロック |
| ZFS | 5秒ごとのトランザクショングループ(txg) | txgごと。`fsync`はZILに書く | txgの書き出しは別のスレッド |
| NetBSD WAPBL | すべての操作を1つのログに入れる | ログが満杯のときかsyncerのとき。`fsync`はログを書く | ログの書き出しはロック(`wl_rwlock`)を排他で取り、その間は操作が止まる |
| TessronOS | 1つの操作が1つのトランザクション | レコードの書込みなどは、キーを閉じたとき、同期のAPI、5秒ごと。置き換え、メタデータ、作ると消すは操作が戻る前。キューをまとめて書く | ボリュームのロックを解放してから書く |

- 以前は、すべての操作が戻るときに媒体にある、という保証だった。1回の`ob_wri_rec`ごとにフラッシュの要求が2回入り、64KBずつ書くと生の書込みの18分の1、1KBずつの追記は0.11MB/sだった(`docs/private/io-limits-audit.md`)。2026年10月にユーザが、上の「確定の保証」に変えると決めた。保存の操作は`ob_rpl_rec`で戻る前に確定するので、アプリが「保存した」と見せた後に電源が切れても、保存した中身は残る。
- 1つの操作を1つのトランザクションにするのも変えない。操作が途中で失敗したとき、そのトランザクションを捨てて元に戻している(`ts_jrnl_abort`)。jbd2のように複数の操作を1つにまとめると、失敗した操作だけを戻すことができない(jbd2では操作は失敗せず、失敗すればジャーナル全体を止める)。バージョン5のボリュームで予備の配置を使う大きな操作は、1つの操作を複数のトランザクションに分ける(下の「メタデータとジャーナル」)。
- 書いている間にロックを持たないのは、jbd2の、確定中のトランザクションと実行中のトランザクションを分ける作りに当たる。WAPBLのように書き出しの間に操作を止めると、今回と同じく、デスクトップがほかのタスクの書込みを待つことになる。
- 電源断に対する安全性は落ちない。再生は前と同じで、コミットブロックの検査に通った最も長い先頭の部分だけを戻す。トランザクションは閉じた順にリングに入るので、どこで電源が切れても、各操作はすべて反映されるか、まったく反映されないかのどちらかで、後の操作だけが残ることはない。`ktest_tsfsjrnl`、`ktest_tsfsobj`の電源断の掃引(`test_cut_sweep`)、`make KTEST=1 KTONLY=tsfscut powercut`で確認した。

テストは次のとおりである。

- `ktest_tsfsjrnl`の`test_queue`: 閉じた3つのトランザクションはリングに書かれないまま読込みに見え、1つを待つと3つともが1回でリングに入り(`batches`が1増える)、その後の電源断で3つとも戻る。
- `ktest_tsfsjrnl`の`test_busy`: 閉じて確定していないトランザクションが解放したブロックは`ts_alloc_ext_at`で確保できず、確定した後は確保できる。
- `ktest_tsfsobj`の`test_unlocked`: リングの書き手を止めた状態(`TSFSJ_FAULT_HOLD`)で別のタスクが`ts_wri_rec`をすると、その操作は確定を待って戻らないが、その間に同じボリュームのほかの実身を開いて読んで閉じることができ、書いた実身の新しいサイズも見える。書き手を再開すると操作は戻る。

### デバイスに1回に読み書きする量

ネイティブのTSFSは、レコードの中身のうちディスク上で続いている部分を、1回の要求にまとめてデバイスに読み書きする。その大きさはデバイスが属性`TDN_IOMAX`(`include/ts/blk.h`)で返すバイト数で決め(`tsfsblk.c`の`io_open`がボリュームを開くときに問い合わせ、`tsfsobj.c`の`run_io_max`が使う)、返さないデバイスは32ブロック(128KB、`RUN_IO_BLOCKS`)のままにする。上限は1024ブロック(4MB)である。要求に使うカーネルのバッファは64バイトの境界に置き(`run_io_buf`)、SDHCIのドライバがバウンスバッファ(64KB)を通さずにDMAで直接読み書きできるようにする。

SDカードの値は、Raspberry Pi 5で動くLinux(github.com/raspberrypi/linuxのrpi-6.12.y、Raspberry Pi OSの既定)が同じカードに使う値に合わせる。Linuxでは次のように決まる。

| 項目 | 値 | 出典 |
| --- | --- | --- |
| 1要求の最大(ホスト) | `max_req_size` 4MB(ADMAのとき。ADMAがなければ512KB) | `drivers/mmc/host/sdhci.c`の`sdhci_setup_host`(「4MiB is preferred for multi-descriptor DMA」のコメント。カードが順に書く速さを保証するのは4MB単位の書込みだから) |
| 1要求のブロック数の最大 | `max_blk_count` 65535 | 同じ関数 |
| セグメント | `max_segs` 128(`SDHCI_MAX_SEGS`)、`max_seg_size` 64KB | 同じ関数(ADMAのディスクリプタ1つが転送するのは長さの16ビットで表せる64KBまで、`max_adma` 65536) |
| ADMA2のディスクリプタ | 64ビットのアドレスで12バイト(v4のモードで16バイト) | `drivers/mmc/host/sdhci.h`の`SDHCI_ADMA2_64_DESC_SZ` |
| ブロックレイヤのハードウェアの上限 | `max_hw_sectors` = min(65535, 4MB÷512) = 8192セクタ(`max_hw_sectors_kb` 4096) | `drivers/mmc/core/queue.c`の`mmc_alloc_disk`(`lim.max_hw_sectors = min(host->max_blk_count, host->max_req_size / 512)`) |
| ブロックレイヤの1要求の上限 | `max_sectors_kb` = min(4096、`BLK_DEF_MAX_SECTORS_CAP` 2560セクタ) = 1280KB | `block/blk-settings.c`の`blk_validate_limits`、`include/linux/blkdev.h` |
| 先読み | `read_ahead_kb` 128KB(`VM_READAHEAD_PAGES`。mmcは`io_opt`を示さないので、その2倍との大きいほうでも128KB)。Raspberry Pi OSのudevのルール(raspberrypi-sys-mods)はこれを変えていない | `block/blk-settings.c`の`blk_apply_bdi_limits`、`include/linux/pagemap.h` |
| 書込み | ページキャッシュにためてから1要求1280KBまでまとめる。カードのSCRがCMD23に対応していれば(`SD_SCR_CMD23_SUPPORT`)ブロック数を先に指定する(SET_BLOCK_COUNT)。SDHCIの仕様3.00以上でADMAならコントローラが自動で出すAuto-CMD23を使い、対応しないときはCMD12で終了する | `drivers/mmc/core/block.c`の`mmc_blk_alloc_req`と`mmc_blk_rw_rq_prep`、`sdhci.c`の`SDHCI_AUTO_CMD23` |

TessronOSのSDHCIのドライバは、`TDN_IOMAX`に1280KB(`SD_IO_MAX`)を返す。1280KBの要求は、コマンド1つ(1コマンドの上限`SD_XFER_MAX`は8192セクタ)で、ADMAのディスクリプタ40個(1つ32KB、`ADMA_MAX_LEN`。テーブルは256個まで)になる。データポートのときは同じ大きさを1ブロックずつ転送し、SDMAのときは512KBの境界で分けて出す。バッファが64バイトに揃っていない、またはコントローラから届かないときは、これまでどおり64KBのバウンスバッファで分けて転送する。NVMeは2MB(MDTSがそれより小さければMDTS)、AHCIは4MBを返し、呼出し元のバッファがカーネルのメモリならバウンスバッファを通さない(6.8)。USBの大容量記憶とvirtio-blkは`TDN_IOMAX`を返さず、128KBのままである。

プログラムのローダは1280KBずつレコードを読む(`elf.c`の`ELF_PIECE`)。書込みは、デバイスへの要求を同じく1280KBまでにするが、ブラウザのストアは256KBずつ`ob_wri_rec`を呼ぶ(`br_store.cc`の`kChunk`)。TessronOSの書込みは、データのブロックがデバイスに届くまでボリュームのロックを持ったままで、その間はほかのスレッドの同じボリュームの読出し(エンジンのスレッドがページの実身やフォントを読むなど)が待つ。そのため`tsfs.c`の`ts_wri_rec`は、256KB(`WRI_PIECE`)を越える書込みを256KBずつに分け、その間にボリュームのロックを解放する。分けたそれぞれが1つの変更で、媒体への書込みは「確定の保証」のとおりまとめて行う。Linuxは書込みをページキャッシュから非同期に出し、読出しを間に入れられるが、TessronOSはそうでないので、1回の書込みを短くして待ちを短くする。実機のSDカードの書込みは約3MB/sで、256KBなら約85ミリ秒、1280KBなら約0.4秒になる。QEMUのSDカードの経路(実機よりずっと遅い)で12.6MBを書いたとき、エンジンのスレッドが止まったのは、1280KBずつでは7秒と14秒、256KBずつでは5.5秒の1回であった。TSFSにはページキャッシュがない。読込みは、レコードのエクステントを見つけるまでに、実身ブロック、配置表、エクステントのリーフを読み、メタデータの`records`の並びを解析するので、小さく区切って読むと1回ごとの手間の影響が大きかった(64KBずつで1MBずつの半分の速さ)。そこで、読んだレコードのエクステントを、ボリュームごとに16件まで保持する(`tsfsobj.c`の`rc_*`)。保持したものは、そのボリュームの世代(変更のトランザクションの始めと終わりで1つ進む)が同じ間だけ使うので、どの実身が変わっても古い場所を読むことはない。保持しているレコードを、前の読込みが終わった所から512KBより小さく読むときは、512KBを先に読んでおき(`RA_BYTES`)、続く読込みはそこから渡す(Linuxの先読みのウインドウに当たる)。`iob`のスイートの`test_kept`が、小さく順に読んでいる途中で、別のキーで上書き、切り詰め、伸長、置き換えをして、どの後も新しい中身が読めることを確認する。プログラムのローダは1280KBずつ読むので、先読みはしない。

複数ブロックの転送の終了方法は、Linuxと同じ条件で決める(`drivers/mmc/core/block.c`の`mmc_blk_alloc_req`と`mmc_blk_rw_rq_prep`、`drivers/mmc/host/sdhci.c`の`sdhci_setup_host`と`sdhci_auto_cmd_select`、`sdhci_set_transfer_mode`)。

1. カードのSCRのCMD_SUPPORTにCMD23(ビット1)があれば、CMD18とCMD25の前にブロック数をCMD23(SET_BLOCK_COUNT)で指定し、成功した転送の後にCMD12を送らない。CMD_SUPPORTは、SD_SPECが2でSD_SPEC3(ビット47)が立つカードにあり、SD_SPEC4(ビット42)が立てば4ビット(ビット35〜32)、そうでなければ2ビット(ビット33〜32)である(`sd.c`の`mmc_decode_scr`)。対応しないカードは、これまでどおりAuto-CMD12で終了する。
2. SDHCIの仕様のバージョンが3.00以上のコントローラでは、CMD23をコントローラが出すAuto-CMD23にする。転送モードのビット3を立て、ブロック数をARGUMENT2(0x00)に書く。ARGUMENT2はSDMAのアドレスのレジスタと同じなので、SDMAで動かすときと、3.00より古いコントローラでは、CMD23をコマンドとして先に送る。ADMAとデータポートではAuto-CMD23を使う。
3. 転送が失敗したときは、CMD23を使っていてもCMD12を送ってカードを転送の状態に戻す(`sd_recover`、Linuxの`sdhci_finish_data`)。
4. 起動時のDMAの検査(`sd_dma_check`)は、データポートとCMD12で読んだ32KBと、選んだ方式と終了方法で読んだものを比べる。違えば、選んだ方式をCMD12で読み直し、それが合えばCMD23を使わず、合わなければその方式を使わない。決まった終了方法は`TessronOS: sda ...`の行に`CMD12`、`CMD23`、`Auto-CMD23`と出す。

eMMCは、LinuxではCSDのSPEC_VERSが3以上ならCMD23を使うが、TessronOSではCMD12のままにする。QEMUのsdhci-pciはAuto-CMD23を持たず(`hw/sd/sdhci.c`が扱う自動のコマンドはAuto-CMD12だけ。9.2と2026年10月のバージョンで確認)、QEMUのeMMCで試せず、CM5のeMMCは実機で確認していないためである。QEMUのsd-cardはCMD23を受け付けるが、SCRのCMD_SUPPORTを0と返すので、ふだんはCMD12で終了する。`ktest_sd`の`test_cmd23`は、CMD12とCMD23(コマンドとして送る)を強制して書いて読み、Auto-CMD23は実機でだけ試す。

ほかのOSも同じ考え方で決めている。NetBSDは1回の転送を`MAXPHYS`(64KB)に限り、FreeBSDは13.0から既定1MBの`maxphys`、Windowsはストレージのドライバが示す最大転送長、macOSはIOKitのデバイスが示す最大の量を上限にし、どれも順に読まれると先読みのウインドウを広げる。実行ファイルはページキャッシュ(Windowsはイメージのセクション)で共有し、同じプログラムの2つ目のプロセスはデバイスから読まない。TessronOSの共有は5.1のとおりである。

QEMUのsdhci-pciは、コマンドごとの待ち時間や帯域を実機のように再現しないので、要求の大きさによる速さの違いはQEMUでは判断しない。QEMUでは、1280KBの要求で読み書きした中身が正しいことだけを確認する(`ktest_sd`の`test_read_size`と、システムボリュームをSDカードに置いたブラウザのテスト)。

### 形式のバージョン5(R1.500)

R1.500で、ネイティブのTSFSの形式をバージョン5にし、形式で決まっていた上限を外した。実装はカーネル(`peripheral_kernel/fs`の`tsfs*.c`、`include/ts/tsfs*.h`)、ホストのツール(`tools/tsfs_py`、`tools/mktsfs`、`tools/tsfs-convert`)、テスト(`tests/ktest/ktest_tsfs*.c`)に入っている。テストの状況は下の「テスト」に書く。前の形式(バージョン4)のボリュームは、R1.500のカーネルでも前の上限のまま読み書きできる。ビルドが作るシステムボリュームはバージョン5である(`tools/mktsfs`の`MAKE_FORMAT`が5)。バージョン5への変換は片道で、戻す方法は作らない。R1.410からR1.500に更新したシステムでは、R1.500の最初の起動で、利用者に確認せずにシステムボリュームを変換する(下の「更新とシステム登録の流れ」)。

| 上限 | バージョン4 | 何で決まっていたか | バージョン5 |
| --- | --- | --- | --- |
| 1つの実身のレコード | 256(`TSFS_MAX_REC`) | 検査(`tsfsck.c`、`tools/tsfs_py`)が配置表の数を256までとみなす | 無し |
| 1つの実身のリソース | 64(`TSFSO_MAX_RES`) | 同上 | 無し |
| 1つの実身のリンク | 1024(`TSFSO_MAX_LINK`。R1.410までは`obxref.c`の`XR_MAX`、`tsfsck.c`の`CK_TRASH_MAX`も) | 同上 | 無し |
| リソースの拡張子 | 15バイト(`TSFSO_EXT_LEN`) | リソースの表の項目の16バイトのフィールド | 形式には無し。APIは767バイト(下の「拡張子」) |
| 1つの実身のメタデータ | 約492KB(R1.410までの`TSFSO_META_MAX`) | 1つのトランザクションに入る量 | 無し(実身のレイヤの`OB_META_LIMIT` 64MBは、メモリを使い切らないための上限として残る、8.12) |
| 1つのトランザクション | 254ブロック、リボーク508(`TSFSJ_MAX_BLOCKS`、`TSFSJ_MAX_REVOKE`) | ディスクリプタブロックとリボークブロックが1つずつ | リングの4分の1(254を下限) |
| 1つのレコードのラン | 27225(R1.410までの`XT2_MAX`、165×165) | 2段のツリー | 段の数を決めないツリー |

形式に関係しないメモリ上の表(`tsfsblk.c`の空きビットマップのブロックを持つ表(初めの数が`TSFSBLK_HELD_MAP`)と差し替えたグループの表、`tsfsobj.c`の確定の後に解放するランの表、ほかのボリュームへのリンクのキュー、レコードの並べ替えの表、`tab_load`が読む表、`tsfsck.c`の検査の表、`tsfspart.c`の空き領域の表)は、数に合わせて伸ばす表にした(R1.410までは`PEND_MAX`、`XQ_MAX`、`ord[TSFSO_MAX_REC+1]`、`seen[256]`、`fr[32]`などの固定の大きさだった)。これはバージョン4のボリュームでも同じに働く。差し替えたグループの表は、ボリュームを閉じるまで解放しない(`ag_retire`)。検査(`tsfsck.c`)は、実身ブロックのレコード、リソース、リンクの数を、そのボリュームの上限(`ts_blk_lim`、0は上限なし)と比べる。修復が隠れ屑実身を集めるTRASH(7.5)は、1つに入れる仮身をボリュームのリンクの上限までとし、それを超えるときはTRASHを複数作る(`CK_TRASH_MAX`を外した。バージョン5では1つに全部入れる)。

残すものは次のとおりである。

| 残すもの | 値 | 理由 |
| --- | --- | --- |
| `TSFS_MAX_OD` | 1024 | 同時に開く実身。プロセスごとの上限を足すまでの全体の上限(B) |
| `TSFS_PATH_MAX` | 256 | マウントのパス(B) |
| rid | 2^31 | 配置表の項目のridは32ビットで、上位のビットは配置で指すリソースのフラグ(`RID_PLACE`)に使う。1つの実身でレコードを2^31回作ると`E_LIMIT`。1秒に1000回作り続けて約25日かかる |
| アイコン | 64KB(`TSFS_ICON_MAX`) | 今回の対象ではない |
| ブロックのサイズ、グループのサイズ | 4096バイト、2^18ブロック | 形式の単位で、ボリュームの大きさを決めない |

#### 互換性のフラグとバージョン

スーパーブロックに次の2つのフラグを足し、スーパーブロックの`version`を5にする(`TSFSBLK_VERSION5`)。

| フラグ | 値 | 意味 |
| --- | --- | --- |
| `TSFSBLK_INCOMPAT_FMT5` | 非互換の0x0004 | バージョン5のボリューム。下の「大きな表」「拡張子」「メタデータとジャーナル」「ランのツリー」をすべて使ってよい。`mktsfs`と変換が立て、外さない |
| `TSFSBLK_COMPAT_CONVREQ` | 互換の0x0002 | 利用者が変換を認め、次の起動で変換することになっている(下の「更新とシステム登録の流れ」)。互換のフラグなので、前のカーネルは気にせずに使う |

`TSFSBLK_INCOMPAT_XT2`と同じ方式である。R1.410までのカーネルは、知らない非互換のフラグのあるボリュームを開かず(`ts_opn_vol_blk`が`E_NOSPT`)、スーパーブロックを読むほかは何も書かない。R1.200からの`fsck.tsfs`は、`--fix`と`--relink`で何も書かず、終了コード2で戻る。R1.110の`fsck.tsfs --fix`はバージョン5のボリュームにも使ってはいけない(上のXT2と同じ理由)。

R1.500のカーネルは、`FMT5`の無いボリュームをバージョン4として開き、上の表の前の上限をそのボリュームの値として使う(ボリュームごとの上限`T_TSFSLIM`、`ts_blk_lim`)。バージョン4のボリュームには、バージョン5の形を1つも書かない。上限を超える操作は以前と同じ`E_LIMIT`、`E_PAR`で拒否する。フラグを1つにまとめ、機能ごとに分けないのは、変換が片道ですべてを一度に変えるので、テストする組み合わせを「バージョン4」と「バージョン5」の2つに保つためである。`XT2`はバージョン5では意味を持たない(2段のツリーは段の数を決めないツリーの1つの形として読む)。

ジャーナルのヘッダのブロックと、ディスクリプタ、リボーク、コミットのブロックのバージョン(`JH_VERSION`と`JB_VERSION`の位置に書く`TSFSJ_VERSION`。バージョン4のボリュームでは2)は、バージョン5のボリュームでは5(`TSFSJ_VERSION5`)にする。

ボリュームごとの上限は`T_TSFSLIM`(`max_rec`、`max_res`、`max_link`、`ext_max`、`meta_max`、`xt_form`、`txn_budget`。0は上限なし)で、`ts_blk_lim`が返す。テストのために、`ts_blk_lim_test`でボリュームを閉じるまで戻り値を差し替えられる(バージョン4のボリュームで、上のレイヤをバージョン5の上限で試す)。1つのトランザクションの予算は`ts_jrnl_budget`、実行中のトランザクションに残るコピーの数は`ts_jrnl_room`が返し、テスト用の障害注入`ts_jrnl_fault(vol, TSFSJ_FAULT_BUDGET | n)`で、ボリュームを閉じるまで予算をnにできる(nが0でボリュームの値に戻す)。

#### 大きな表

配置表、リソースの表、リンクの表は、今も項目の数を実身ブロックの32ビット(`OB_NPLACE`、`OB_NRES`、`OB_NLINK`)で持ち、項目の形(48、64、48バイト)も変わらない。変わるのは次の3つである。

- 管理の部分(メタデータ、アイコン、3つの表)の配置の形に、ランのツリー(`F_TREE`、下の`F_TREEN`)を足す。バージョン4の管理の部分はインライン領域か1つのランだけで、大きな表は連続した空きを必要とした。バージョン5では、ツリーのリーフが共通のヘッダ(`TFTB`)を持つブロックを並べ、空きが細切れでも置ける。
- 大きな管理の部分は、ジャーナルを通さずに新しい場所に書く(下の「メタデータとジャーナル」)。
- 検査(`tsfsck.c`、`tools/tsfs_py`)は、表の数の上限を見ず、表の配置の大きさと数が合うことだけを見る。

すでにあるバージョン4の実身の表は、そのまま正しいバージョン5の表である。表はこれまでどおり全体をメモリに読む(`tab_load`は数に合わせて確保する)。10万個のリンクの表は4.8MBで、仮身表を作り直すときに全体を読む。表の中をインデックスで引く形はR1.500では入れず、テストで時間を測っておく。

#### 拡張子

リソースの表の項目(64バイト)の拡張子のフィールド(`RS_EXT`、16バイト)は、バージョン5では2つの形を持つ。

| フィールドの最初のバイト | 形 |
| --- | --- |
| 0xFF以外 | バージョン4と同じ。15バイトまでの拡張子をNULで埋める |
| 0xFF(`RSX_MARK`) | +4(`RSX_OFF`)に32ビットの位置、+8(`RSX_LEN`)に32ビットの長さ。拡張子は、同じリソースの表の管理の部分で、項目の並び(数×64バイト)の後ろに置く文字列領域にある |

0xFFはUTF-8の文字の最初のバイトにならないので、2つの形は取り違えない。15バイトまでの拡張子はいつも前の形で書くので、短い拡張子だけの実身の表はバージョン4と同じバイト列になる。文字列領域は表を書くたびに項目の順に詰めて作り直す(表は丸ごと書くので、空きの管理は要らない)。表の管理の部分の大きさは、数×64と文字列領域の長さの和になり、検査はそれを確認する。文字列領域の位置は項目の並びの終わりから数えたバイトの位置で、拡張子は終端の0を持たない。16バイト以上の拡張子と0xFFで始まる拡張子だけが文字列領域に入り、長さ0の0xFFの形と、領域の外を指す形は壊れているとする。

APIは拡張子を767バイト(`TSFSO_EXT_MAX`。`FS_NAME_MAX`の768から終端の0を除いた数)まで受け付ける。リソースはFAT上の格納方式とobjfsでファイルの名前の一部になるからである(7.2)。`T_TSFSRES`には拡張子の長さ`extlen`があり、`ext`(16バイト)に入らない拡張子は文字の境界で切って入れ、全体は`ts_obj_res_ext`が`ob_ref_nam`と同じ形で返す。実身のレイヤの`OB_RES_NAME`(64)は普通の長さの名前のバッファの大きさとして残し、最も長い名前の大きさ`OB_RES_NAME_MAX`(800)を足した。`ob_lst_res`(と`knl_tsfs_res_lst`)は、bufをNULLにすると、数と、名前の全部が占めるバイト数(戻り値)を返す。FAT上の格納方式では、ファイル名が長いファイル名の255文字に入らない拡張子を`E_PAR`で拒否する。

#### メタデータとジャーナル

バージョン4では、管理の部分はすべてジャーナルを通して書き、1つの操作が1つのトランザクションで、1つのトランザクションはディスクリプタブロック1つが指せる254ブロックまでである。そのため、メタデータは約492KBまでで、多くのブロックを解放する削除は`E_LIMIT`になることがあった。ほかのOSの方式は次のとおりである。

| OS | 1つのトランザクションの大きさ | 大きな操作 |
| --- | --- | --- |
| Linux ext4(jbd2) | ディスクリプタブロックをいくつでも続けられ、上限はジャーナルの4分の1(`j_max_transaction_buffers`)。`journal_csum_v3`は各項目にコピーのチェックサム、ディスクリプタブロックの終わりとコミットブロックにもチェックサムを持つ。`64bit`は項目のブロックの番号を64ビットにする | 大きなファイルの切り詰めは、inodeを孤児のリストに入れ、トランザクションを区切り直しながら進める(`ext4_truncate_restart_trans`)。電源が切れても、マウントのときに孤児のリストから続きを行う。大きな拡張属性の値は、ジャーナルを通さず専用のinodeのデータブロックに置く(`ea_inode`)。`large_dir`はディレクトリのインデックスを3段にする |
| XFS | トランザクションごとにログの予約量を決め、上限はログの大きさで決まる | 長い操作はトランザクションをロールし(`xfs_trans_roll`)、その間の状態をインテント(領域の解放の`EFI`と`EFD`など)としてログに書く。復旧はインテントから続きを行う |

TessronOSは、次の3つを役割を分けて組み合わせる。

1. ディスクリプタブロックのチェーン(ジャーナルの形式)。1つのトランザクションはディスクリプタブロックをいくつでも持ち、リボークブロックもいくつでも持つ。形式の定数を外し、1つのトランザクションの大きさを、ジャーナルのリングの4分の1(254ブロックを下限)という、ボリュームが持つ値にする(jbd2に当たる)。ジャーナルの項目はすでに64ビットのブロックの番号とコピーごとのCRCを持ち、コミットブロックがそれまでのすべてのCRCをつないだCRCを持つので、`64bit`と`journal_csum_v3`に当たるものは揃っている。
2. 大きな管理の部分は場所を変えて書く。新しい内容が予算の8分の1を超える管理の部分は、新しく確保したブロックに、ジャーナルを通さず、共通のヘッダとCRCを付けて直接書く。その後の小さなトランザクションで、実身ブロックの配置を差し替え、古いブロックを解放する。`ob_rpl_rec`がレコードを置き換えるのと同じで、ext4の`ea_inode`に当たる。データをコミットブロックより先に媒体に書き込むことは、確定の前のフラッシュの要求がすでに保証している(上の「ジャーナルの確定とボリュームのロック」)。解放した古いブロックを確定まで使わないこと(`busy_add`)、古い持ち主のコピーを再生で戻さないこと(`knl_jrnl_revoke`)も今の仕組みのままである。メタデータの大きさはトランザクションの大きさに入らなくなり、ジャーナルに2回書くこともなくなる。
3. 1つの操作を複数のトランザクションに分ける(予備の配置)。実身ブロックの+320に、予備の配置(`OB_SPARE`、32バイト)を1つ足す。そこにあるのは、その実身が持つが、どのレコードと管理の部分にも属さないランである。予備の配置が空でない実身は、フラグ`TSFSO_F_SPARE`を持ち、孤児のツリーに入る。マウントのとき(と修復のとき)、孤児のツリーの後処理が予備の配置を空にする。仮身表を`RELINK_STEP`ずつ作り直し、作り直しのフラグと孤児のツリーで続きを行う今の仕組みを、領域の確保と解放に広げたものである。

予備の配置は、次のように使う。どの操作も、すべての段階を終えてから戻るので、APIの保証(7.3の「確定の保証」)は変わらない。

| 操作 | 段階 | 途中で電源が切れたとき |
| --- | --- | --- |
| レコードの置き換え(`ob_rpl_rec`)、大きな管理の部分の書込み | 予算に入る分ずつ領域を確保し、予備の配置に足していく(1段階が1トランザクション)。データを書く。最後のトランザクションで、レコード(管理の部分)の配置と予備の配置を入れ替える。古いランは予備の配置に移り、それを予算に入る分ずつ解放する | 入れ替えの前なら、マウントが作りかけの新しい領域を解放し、古い中身が残る。入れ替えの後なら、新しい中身になり、マウントが古い領域を解放する |
| レコードの切り詰め、レコードの削除 | 最初のトランザクションで、レコードの大きさを変える(削除なら配置表から外す)。外れたランは、予備の配置に形`F_TRIM`(`PL_A`にrid、`PL_BYTES`に残す大きさ)で「このレコードの、大きさより後ろのランを返す」と書き、後ろから予算に入る分ずつ解放する | 大きさは最初のトランザクションで変わっている。残りのランはマウントが解放する |
| 実身の削除 | 今と同じく孤児のツリーに入れ、レコードを1つずつ上の削除で解放する | 今と同じく、マウントが続きを行う |

各段階は`ts_jrnl_room`(実行中のトランザクションに残るブロックの数)を見て、ビットマップのブロック、ツリーのノード、リボークの項目の分を残して止まる。予算が小さいボリューム(リングが小さいもの、下の見積もり)でも、どの操作も終わる。

予備の配置の形は、`F_RUN`、`F_TREE`、`F_TREE2`、`F_TREEN`(その実身が持つランそのもの。`PL_BYTES`は見ない)か、`F_TRIM`である。置き換えと大きな管理の部分の書込みでは、確保したランを前の4つの形で持つ。レコードの削除では、配置表から外したレコードの配置をそのまま予備の配置に移し、そこから後ろのランを解放していく(配置表から外したレコードはridで引けないので、削除には`F_TRIM`を使わない)。`F_TRIM`は切り詰めだけに使い、`PL_BYTES`はそのレコードの配置表の大きさと同じである。そのレコードの論理ブロックのうち、`PL_BYTES`を4096で割り上げた数から後ろが返すランで、検査はそれを予備の配置のものとして数える。ツリーの形の予備の配置では、ツリーのノードも予備の配置のものである。バージョン4から変換したレコードの`F_TREE2`の配置もそのまま予備の配置に移るので、検査は`F_TREE2`の予備の配置もツリーのノードとランを数える。孤児のツリーの項目の値は、作り直しのフラグのときと同じく実身ブロックである。

実身のレイヤ(`tsfsobj.c`)は次のように動く。

- どの操作も、上限をボリュームの`ts_blk_lim`から取る(0は上限なし)。バージョン4のボリュームでは以前と同じに、257個目のレコードと65個目のリソースと1025個目のリンクを`E_LIMIT`、16バイト以上の拡張子と約492KBを超えるメタデータを`E_PAR`、27225を超えるランを`E_LIMIT`(以前は`E_NOMEM`)で拒否し、バージョン5の形を書かない。ridが2^31に届いた実身にレコードを足すと`E_LIMIT`。
- 配置表、リソースの表、リンクの表、レコードの並び、仮身表を作るときの項目、ほかのボリュームへのリンクのキュー、確定の後に解放するランの表は、数に合わせて伸ばす。確定の後の解放は、空きビットマップのコピーが予算に入る分ずつのトランザクションに分ける。
- 仮身表の作り直しは、レコードから作る表を最初に1回だけ作り(ボリュームのロックの間はレコードが変わらない)、1つの段階で参照数を動かす実身の数を`RELINK_STEP`(64)とトランザクションに残るコピーの4分の1の小さいほうまでにする。同じ実身へのリンクは1つにまとめて数え、ほかのボリュームへのリンクは段階の数に入れない。同じ仮身の識別子の重なりはハッシュで調べ、表はマージソートで並べる。
- 予備の配置を使うのは、バージョン5で、利用者が開いたトランザクション(`ts_obj_begin`)の中でないときである。レコードの置き換えは、新しい中身が予算の8分の1のブロックを超えるとき、上の表の段階に分ける。切り詰めとレコードの削除は、レコードの配置がツリー(`F_TREE`、`F_TREE2`、`F_TREEN`)か、空きビットマップを予算の8分の1を超えて変えるランのとき、予備の配置を使う。それより小さい変更は、以前と同じ1つのトランザクションで行う。
- 大きな管理の部分の書込みは、新しいブロックを1つの操作のトランザクションで確保し(空きビットマップのコピーと、すでにあるツリーの右端のノードだけがジャーナルに入る)、中身をジャーナルを通さずに書き、同じトランザクションで配置を移す。古い管理の部分がツリーか大きなランなら予備の配置に移し、操作のトランザクションが確定した後に段階に分けて解放する。新しく確保したノードと、まだどこからも指されない配置のツリーのノードは、ジャーナルを通さずに書く。
- 実身の削除では、大きな配置(上の条件のもの)を持つ実身を先に孤児のツリーに移し(インデックスから外し)、大きなレコード、リソース、メタデータ、アイコン、リンクの表を1つずつ予備の配置に移して解放してから、残りを1つのトランザクションで解放する。
- 予備の配置を持つ実身に次の変更が来たとき(電源断の後、マウントの前の後処理が終わっていないときなど)は、先に予備の配置を空にする。
- テスト用のフックとして、`ts_obj_fan(vol, n)`(ランのツリーのノードに詰める項目をnにする)と、`ts_obj_cut(vol, k)`(この後に閉じるk個目のトランザクションで`TSFSJ_FAULT_AFTER_COMMIT`にする)がある。どちらもボリュームを閉じるまで有効である。
- `ts_obj_lst_rec`、`ts_obj_lst_res`、`ts_obj_lst_lnk`、`ts_lst_rec`、`knl_tsfs_lst_lnk`は、bufをNULL、nを0にすると数だけを返す。
- サルベージ(`ts_obj_salvage`)の1つのレコードの上限`SALV_REC_MAX`(64MB)は、レコードを丸ごとメモリに読んでからコピーするためのメモリの上限として残す。

3つを組み合わせる理由は次のとおりである。ディスクリプタブロックのチェーンだけでは、上限がリングの4分の1に移るだけで、10MBのメタデータには40MBのリングが要り、2回書く手間も残る。分けるだけでは、254ブロックという形式の定数が残り、予算の小さいトランザクションを多く重ねることになる。予備の配置を実身ブロックに置くのは、TSFSで1回の変更で切り替わる単位が実身ブロック(実身の配置の差し替え)だからである。インテントを別のログとして持つXFSの形にすると、ジャーナルの外にもう1つの再生の仕組みが要る。実身ブロックの1つの配置なら、今の孤児のツリーの後処理がそのまま続きを行える。

ジャーナルの形式は次のように変える。

| ブロック | バージョン4 | バージョン5 |
| --- | --- | --- |
| ディスクリプタ(`TFJD`) | 1つのトランザクションに1つ。+16に項目の数(254まで) | いくつでも。+28にトランザクションの中の番号(0から)。各ディスクリプタブロックの後ろに、それが指すコピーが続く |
| リボーク(`TFJR`) | 0か1つ。508項目まで | いくつでも。+28に番号 |
| コミット(`TFJC`) | +44にコピーの数 | +48にディスクリプタブロックの数、+52にリボークブロックの数を足す |

再生は、ディスクリプタブロックの番号kとそのコピーを読み、次のブロックが番号k+1のディスクリプタブロック、リボークブロック、コミットブロックのどれでもなければ、そこで止まる。コミットブロックの検査に通った最も長い先頭の部分だけを戻すことは変わらない。再生のときのリボークの表は伸ばす表にした(以前は`REPLAY_MAX_REVOKE` 4096。今は512から伸ばす、`REPLAY_RVK_FIRST`)。バージョン4のボリュームでは、ディスクリプタブロックとリボークブロックを1つずつにした以前の書き方のまま書く。リングにバージョンの違うトランザクションが混ざらないよう、変換はリングを空にしてから行う。

リングの並びとコミットブロックの検査(`tsfsjrnl.c`)は次のとおりである。

- 1つのトランザクションは、ディスクリプタブロック(番号0から)とそれが指すコピーの組をコピーの数だけ続け、その後にリボークブロック(番号0から)、最後にコミットブロックを置く。ディスクリプタブロックは254まで、リボークブロックは508項目まで指す。コピーのない(リボークだけの)トランザクションもディスクリプタブロックを1つ持つ。
- コミットブロックの`JC_CHAIN`は、最初のディスクリプタブロックのCRCのCRCに、後ろの各ブロックの項を排他的論理和でつないだものである。項は、そのブロックのCRCのCRCに、コピーならトランザクションの中のコピーの通し番号、2つ目からのディスクリプタブロックなら0xA5A5A5A5とディスクリプタブロックの番号の和、リボークブロックなら0x5A5A5A5Aとリボークブロックの番号の和を足したもの。バージョン4のトランザクション(ディスクリプタブロックとリボークブロックが1つずつ)は以前と同じ値になる。`JC_BLOCKS`(+44)はコミットブロックより前のリングのブロックの数で、バージョン5では+48のディスクリプタブロックの数と+52のリボークブロックの数も再生が確認する。
- 1つのトランザクションのリボークは、リングの半分から最大のトランザクション(ディスクリプタブロック、コピー、コミットブロック)を除いた分のブロックまで持つ。それを超えると、バージョン4と同じく、閉じるときにそれまでのトランザクションをすべて本来の位置に書いてからリボークを省く(リボークする古いコピーがリングに残っていない)。
- 閉じる前の空きビットマップのブロックを持つ表(`TSFSBLK_HELD_MAP`)は伸ばす表にした。1つのトランザクションが変える空きビットマップのブロックの数は、ジャーナルの予算で決まる(それぞれがコピーになる)。表のメモリが確保できないときは`E_NOMEM`で拒否する。以前の16を超えたときの`E_LIMIT`はなくなり、バージョン4のボリュームでも予算(254)までの空きビットマップを変えられる。
- リングに書くとき、キューの全部をメモリに並べられなければトランザクションごとに、それもできなければ64ブロックずつ並べて書く(`LAY_PIECE`)。

1つのトランザクションの予算(コピーのブロックの数)は、リングのブロックの数の4分の1と254の大きいほうである。リングには確定を待つトランザクションのキューも入るので、2つの最大のトランザクションが入ることも確認する(`TSFSJ_AREA_BLOCKS`と同じ考え方)。ジャーナルはボリュームの256分の1(最小515ブロック、最大1GB)で、広げたボリュームは作ったときの大きさのままなので、768MBで作って8GBに広げたシステムボリュームのリングは767ブロック、予算は254ブロックになる。変換ではジャーナルを広げない。上の2と3により、どの操作も予算の大きさによらずに終わるからである。

#### ランのツリー

ランのツリーの形`F_TREEN`(5)を足す。配置の`PL_A`はルートのノードのブロック、`PL_B`はランの数である。ノードは共通のヘッダ(`TFTB`)を持つブロックで、+64に項目の数、+68(`XN_LEVEL`)に段(リーフが0)を持ち、+128から24バイトの項目を165まで並べる。

| ノード | 項目(24バイト) |
| --- | --- |
| リーフ | 論理ブロック、ブロック、ブロックの数(`F_TREE`のリーフと同じ) |
| インデックス | 子の最初の論理ブロック、子のノードのブロック、子の下のブロックの数 |

段の数はルートのノードが持ち、形式では決めない(ext4のエクステントツリーの`eh_depth`に当たる)。検査は、8段を超えるツリーを壊れているとみなす(165^8は2^58を超え、ブロックの数より多い)。読込みは論理ブロックでインデックスをたどり、全部のランをメモリに読まない。書き足しは右端のパスと新しいリーフだけを、短くするときは右から外したリーフとパスだけを書く。`F_RUN`、`F_TREE`(1つのリーフ)、`F_TREE2`(2段)はそのまま読む。バージョン5のボリュームで`F_TREE2`のレコードを書き直すときは、`F_TREEN`にする。同じツリーを、管理の部分の`TFTB`のブロックを並べるのにも使う。

ノードの共通のヘッダの持ち主は実身(UUIDの下位64ビット)で、`F_TREE`のリーフと同じである。段kのインデックスのノードの子は段k−1のノードで、同じ段のノードは左から論理ブロックの順に並ぶ。インデックスの項目の最初の論理ブロックは子の最初の項目のものと同じで、3つ目の数は子の下のリーフのランのブロックの数の和である。どのリーフも1つ以上の項目を持つ。管理の部分のツリー(`F_TREE`、`F_TREEN`)では、論理ブロックは管理の部分の何番目のブロックかを表し、リーフのランの各ブロックが共通のヘッダ(`TFTB`)と`MB_PAY`バイトの中身を持つ。ランが1つに収まる管理の部分は、今と同じ`F_RUN`で書く。

#### 変換

変換は、取り付ける前のボリュームに対して、カーネル(`ts_cnv_vol`、`knl_ob_conv_boot`)かホストのツール(`tools/tsfs-convert`)が行う。中身のブロックは動かさず、書くのは数ブロックだけである。

1. バージョン4であること(`FMT5`が無く、非互換のフラグが`XT2`だけ)を確認する。`GROWING`のフラグがあれば、普段の開き方で拡張を終えてから進む。エラーが記録されたボリュームは変換しない。
2. 変換のためだけに開き、ジャーナルを再生し、孤児のツリーの後処理を終える。ここまでは前のカーネルがマウントのときにすることと同じで、形式は変わらない。
3. ボリューム全体を「通常」の処理方式で検査する(7.5、`ts_chk_vol`、修復はしない)。障害が1つでもあれば、何も書かずに終える。孤児と作り直しの警告は2の後処理で消えているはずで、残っていれば障害として扱う。
4. チェックポイントをしてリングを空にし、デバイスのキャッシュをフラッシュする。
5. スーパーブロックの片方に、`FMT5`を立て、`CONVREQ`を外し、`version`を5にした新しい世代を書き、キャッシュをフラッシュする。ここが変換の確定である。続けてもう片方とバックアップを書く。
6. ジャーナルのヘッダのブロックをバージョン5で書き(リングは空、次の番号は続きのまま)、キャッシュをフラッシュする。

カーネルでは、1と2は変換のためにボリュームを開くこと(`ts_obj_mount`。拡張の途中からの続き、ジャーナルの再生、孤児のツリーの後処理)で済み、`ts_cnv_vol`がその開いたブロックレイヤのボリュームに1の確認と3の検査を行い、4〜6をブロックレイヤの`ts_blk_convert`に任せる。`ts_blk_convert`は、4で`knl_jrnl_freeze`(実行中のトランザクションを待ち、確定したものをすべて本来の位置に書く)とデバイスのキャッシュのフラッシュを行い、5でスーパーブロックの片方を書いてキャッシュをフラッシュし(変換の確定)、もう片方、すべての予備のスーパーブロックの順に書き、6で`knl_jrnl_fmt5`がヘッダをバージョン5で書いてキャッシュをフラッシュする。

途中で電源が切れたときは次のようになる。5より前なら、ボリュームはバージョン4のままで、`CONVREQ`も残るので、次の起動でもう一度変換する。5の最初の書込みが途中で切れたときは、そのスーパーブロックのCRCが合わず、もう片方(バージョン4、世代が1つ前)から開く。5の後で6の前なら、スーパーブロックはバージョン5、ジャーナルのヘッダはバージョン4でリングが空である。R1.500のカーネルは、この組み合わせ(`FMT5`があり、ヘッダがバージョン4でリングが空)を変換の最後の段階が残ったものとして、ヘッダをバージョン5で書いて開く。リングが空でないバージョン4のヘッダと`FMT5`の組み合わせは壊れているとする。開くとき(`ts_jrnl_replay`)の扱いは次のとおり。

| スーパーブロック | ジャーナルのヘッダ | 開き方 |
| --- | --- | --- |
| バージョン4 | バージョン4 | 以前のまま |
| バージョン5 | バージョン5 | バージョン5のリングとして再生する |
| バージョン5 | バージョン4で、バージョン4として読むとトランザクションが1つもない | 変換の6が残ったもの。ヘッダをバージョン5で書き、もう片方のスーパーブロックと予備のスーパーブロックをバージョン5で書いて開く(`knl_jrnl_conv_left`、コンソールに`tsfs: デバイス名: convert: finished at opening`) |
| バージョン5 | バージョン4で、確定したトランザクションがある | 壊れている。リングを再生せず、エラー(`TSFSBLK_ERR_CSUM`、ジャーナルのヘッダのブロック)を記録して読取り専用で開く |
| バージョン4 | バージョン5 | 同上 |

スーパーブロックの`version`と`FMT5`が食い違う(バージョン5で`FMT5`がない、バージョン4で`FMT5`がある)コピーは、壊れたコピーとして読まない。`CONVREQ`は`ts_blk_convreq`が立てたり外したりし、トランザクションの外ならすぐ、中ならそのトランザクションと一緒にスーパーブロックを書く。バージョン5のボリュームに立てようとすると`E_OBJ`である。`ts_blk_convert`は、バージョン5のボリュームには何もせずに`E_OK`、読取り専用のものには`E_RONLY`、エラーが記録されたものと`XT2`のほかの非互換のフラグがあるものには`E_OBJ`を返す。

必要な空き容量は0である。変換は中身を動かさず、スーパーブロック2つ、バックアップ、ジャーナルのヘッダを置いた場所に書き直すだけである。新しい形は、後で大きな表やメタデータを書くときに、そのとき空きを使う。検査のメモリは、ボリューム全体のビットの表(8GBで256KB、1TBで32MB)と実身ごとの表である。

所要時間は検査でほぼ決まる。通常の検査は、ツリーのノード、各実身の実身ブロック、インライン領域の外にある管理の部分、ランのツリーのリーフと、グループのヘッダとビットマップを読む。R1.420のx64のシステムボリューム(768MB、397実身、510レコード)では、これがおよそ1000〜2000回の4KBの読込みになる。SDカードのランダムリードはA1の規格で1秒1500回以上(A2で4000回)なので、作ったばかりのシステムボリュームなら数秒で終わる。利用者が5万の実身を作ったボリュームでは10万回ほどで、SDカードやUSBメモリで1〜3分、NVMeで10〜20秒の見込みである。4〜6の書込みとフラッシュの要求は1秒に満たない。この数は読込みの回数からの見込みで、実機のテストで測った値に置き換える。

#### 更新とシステム登録の流れ

変換は、システムのボリュームと、利用者が認めたボリュームに行う。システムのボリュームは、バージョン4ならR1.500の最初の起動で必ず変換する(下の表)。ほかのボリュームは、利用者がディスク操作の〈形式を新しくする〉で選んだものを、その場で変換する(下の表)。次の起動で変換することを認めたフラグはボリュームのスーパーブロックの`CONVREQ`で、更新とシステム登録の上書きが立てる。起動のときは、システムのボリュームと、`CONVREQ`を立てたまだ取り付けていないボリュームを、システムのボリュームを取り付ける前に変換する(`obname.c`の`knl_ob_chk_boot`の後、`knl_sysvol_grow`の前に`knl_ob_conv_boot`)。変換しなかったボリュームからは`CONVREQ`を外す。起動時のファイル(`DISKFIX.REQ`)を使わないのは、システム登録したマシンでは`/boot`がWindowsと共用のESPで、そのルートに何も足さないため(3.10.10)と、登録先のボリュームにフラグを立てれば、登録した後の最初の起動でそのまま変換できるためである。

画面は、どれもBTRON標準のパネル(テキストとボタン)で、新しい部品は作らない。

| 場面 | 尋ね方 | 認めたとき |
| --- | --- | --- |
| R1.500からの更新で、パッケージの形式が新しい(`package.json`の`"tsfs_format"`がシステムボリュームのバージョンより大きい) | 更新の確認(`DT_SYSUP_CHECK`)のパネル(システム環境設定のパネル25)に、「システムをR1.500からR1.600に更新します。」に続けて「更新のあとの最初の起動で、システムのディスクを検査し、新しい形式に変えます。」「変えたあとは、前のバージョンでは起動できません。」「更新が終わったら、システムを再起動します。」を出し、[更新][取り消し] | 更新の最後の手順で`CONVREQ`を立てる |
| R1.410以前からR1.500への更新 | 尋ねない(ユーザの決定)。R1.410の更新の画面は変換を知らないので、更新はバージョン4のまま終わる。R1.500のカーネルは、起動のときにシステムのボリュームがバージョン4なら、`CONVREQ`がなくても変換する(システムのボリュームだけ。ほかのボリュームは`CONVREQ`を立てたものだけ) | 最初の起動で、取り付ける前に検査と変換を行い、結果を通知で示す |
| システム登録の上書き(`SI_KEEP`)で、登録先がバージョン4 | 〈登録〉の確認のパネルの「実身は残ります。」の後に「登録先のディスクは、登録のあとの最初の起動で検査し、新しい形式に変えます。」 | 上書きの最後に登録先のボリュームに`CONVREQ`を立てる。登録先から最初に起動したときに変換する |
| システム登録の初期化 | 尋ねない | 動いているシステムボリュームのコピーなので、その形式のままである |
| USBメモリなどシステムのものでないTSFSのボリューム | ディスク操作の〈形式を新しくする〉のパネル5に「ディスク「名前」(デバイス)を新しい形式に変えます。」「変える前にディスク全体を検査し、障害があれば変えません。」「変えたあとは、R1.410までのシステムでは使えません。」を出し、[取消][変える]。管理者の権限を求める | その場で、取り付けてあれば外して検査と変換を行い、取り付け直す(`ob_cnv_run`、プログラムからは`ob_cnv_vol`、11.26)。実身が開いているボリュームは変換しない |

変換が終わると、デスクトップの通知で「システムのディスクを新しい形式に変えました。」と示す。検査で障害が見つかったときは、変換せずに`CONVREQ`を外し、バージョン4のまま取り付けて起動を続け、通知で「ディスクに障害が見つかったので、形式を変えませんでした。ディスク修復で修復してから、もう一度変えてください。」と示し、検査の結果をディスク修復のウインドウに出す(`ob_cnv_boot_result`。`ob_chk_boot_result`と同じ渡し方で、最初に問い合わせたプロセスにだけ渡す)。システムのボリュームは`CONVREQ`が無くてもバージョン4なら変換するので、修復した後の起動で、もう一度自動で検査と変換を行う(修復しないうちは、起動のたびに検査して同じ通知を出す)。デバイスの読み書きが失敗したときは、上の「途中で電源が切れたとき」と同じで、5より前なら元のまま、後なら変換を終えている。5より前で失敗したときは「ディスクの読み書きに失敗したので、形式を変えませんでした。」と示す。システムのものでないボリュームを起動のときに変換したときは「ディスク「名前」を新しい形式に変えました。」と示す。通知は「ディスクの形式」を題に、送信元を「システム」とするデスクトップ自身の通知(`dt_note_own`)である。検査と変換の進み具合は、コンソールに出す(`tsfs: デバイス名: convert ...`)。

変換した後は、ブートパーティションに残る前のカーネル(`tessronos.img.old`、`tessronos.elf.old`、11.8.1)ではシステムのボリュームを開けない。前のカーネルに戻す方法は、変換する前にだけ使える。

#### mktsfs、fsck.tsfs、tsfs_py

`tools/mktsfs`と`tools/tsfs-import`は、新しいボリュームをバージョン5で作る。テストのために`--format 4`でバージョン4のボリュームも作れる。`--format`が無ければ環境変数`TSFS_FORMAT`(4か5)、それも無く`make`から実行されたとき(`MAKELEVEL`がある)は`tools/mktsfs`の`MAKE_FORMAT`、どちらでもなければ5で作る。`MAKE_FORMAT`は5で、ビルドが作るシステムのボリュームはバージョン5になる(カーネルがバージョン5のボリュームを開けるようになるまでは4にしていた)。`makefile`の呼び方は変えない。カーネルの`ts_format_blk`と`knl_tsfs_format`もバージョン5で作る。ライブラリの`Volume.format`の既定はバージョン4のままで、`version=5`で作る。

システムのボリュームがバージョン4のテスト用ディスク(起動のときの変換のテスト)は、`tools/tests/mkv4disk.py`がビルドのテスト用ディスク(QEMU virtは`test_disk.img`、x64は`sd.img`)のコピーに作る。ビルドと同じ`mktsfs`のコマンド(`make -n`で得る)に`--format 4`とシステムの区画の大きさを付けて作り直し、コピーのその区画に書く。ビルドの生成物は変えない。`--volume`では、ディスクのコピーを作らず、バージョン4のシステムのボリュームだけを書く(大きさはシステムの区画の大きさか`--size`)。そのボリュームから`tools/tests/mkwindisk.py make-ts4`が、前のシステム(R1.410)をディスク全体に登録した形のディスクを作る。ESP(FAT32、200MB)に`\EFI\BOOT\BOOTX64.EFI`と`\EFI\TESSRON\`のローダ、カーネル、`cmdline.txt`、`INSTALL.TXT`(ビルドの`sd.img`のESPから取る)を置き、その後ろにボリュームと同じ大きさのTSFSの区画「TessronOS」を置く。

`tools/tsfs_py`(`layout.py`、`journal.py`、`obj.py`、`check.py`、`repair.py`、`transfer.py`、`meta.py`)は、2つのバージョンを読み、上限をボリュームのバージョンから決める。ホストのツールはジャーナルを通さずに書くので、大きな管理の部分も予備の配置も使わない。連続した空きが無いとき、バージョン5では管理の部分を`F_TREE`か`F_TREEN`に、166以上のランのレコードを`F_TREEN`にする。テストのために、環境変数`TSFS_PY_XN_FANOUT`でノードに詰める項目の数を減らせる(カーネルの`ts_obj_fan`と同じ考え方)。

`fsck.tsfs`は、ディスクリプタブロックのチェーンの再生、`F_TREEN`、拡張子の文字列領域、予備の配置(`TSFSO_F_SPARE`と孤児のツリーの一致、`F_TRIM`のレコードの大きさより後ろのラン)を検査し、`--fix`は孤児のツリーの後処理として予備の配置を空にする。知らない非互換のフラグのあるボリュームを`--fix`と`--relink`で書かないことは変えない。バージョン5の`FMT5`は知っているフラグになった。

`tools/tsfs-convert`はホストで上の変換を行い、カーネルと同じ順で書く。`GROWING`のフラグがあるボリュームは変換しない(拡張を終えるのはカーネルなので、一度開いてから変換する)。3の検査では、`fsck.tsfs`のエラーと、使われていないのに確保されたブロックと、孤児のツリーに残った処理を障害として扱う。`-n`は1と3だけを行い、何も書かない。5の後で6の前に止まったボリュームは、`tsfs-convert`をもう一度実行するか`fsck.tsfs --fix`で、ジャーナルのヘッダをバージョン5で書く。同じバージョン4のイメージからは、`tsfs-convert`とカーネルの起動のときの変換が、取り付けで変わるフィールド(`generation`、`mount_count`、`mount_time`)のほかは同じスーパーブロックとジャーナルのヘッダを作る。

## 7.4 システムボリューム

システムボリュームはTSFSのネイティブのパーティションで、起動時に実身の格納先としてマウントされる。フォント、壁紙、定義実身、小物のプログラム、かな漢字変換の辞書、サンプルの実身を格納する。イメージは`etc/`以下のファイルから`tools/mktsfs`でバージョン5の形式で作成する(7.3)。

利用者が作る実身もここに置くので、載せる中身の大きさぎりぎりで作ると、原紙から実身を作れなくなる(R1.100の実機では空きが114688ブロック中1ブロックで、「実身を作れませんでした」となった)。Raspberry Piのカードのイメージでは、システムボリュームを2GBで作る(`build_make/makefile`の`SYS_VOL_SIZE`、3.3)。最初の起動で、区画とボリュームを8GB(`CNF_SYSVOL_GROW_MB`)まで広げる。カードが8GBより小さければ、カードの終わりまで広げる(7.7)。

## 7.5 ディスクの検査と修復

ネイティブのTSFSのボリュームは、マシンの上で検査し、修復できる(`peripheral_kernel/fs/tsfsck.c`、`include/ts/tsfsck.h`)。小物「ディスク修復」(11.25)がこれを使う。ホストの`tools/fsck.tsfs`とは別の実装で、同じ形式をカーネルの中から読む。実身ブロックとB+ツリーのノードの配置は`peripheral_kernel/fs/tsfsfmt.h`にまとめてあり、書く側(`tsfsobj.c`、`tsfsbtree.c`)と検査する側が同じ定義を使う。バージョン4とバージョン5のどちらのボリュームも検査し、上限はボリュームのバージョンから決める(7.3)。

### 検査の項目

検査はボリュームの構造に沿って、次の順に進む。項目の名前は超漢字Vのディスク修復小物の検査項目に当たる。

| 項目 | 見るもの |
| --- | --- |
| ボリュームの管理情報 | スーパーブロックの2面とバックアップ、アロケーショングループのヘッダ、空きビットマップのチェックサム、グループの空きブロック数とビットマップの一致、スーパーブロックに記録された異常 |
| リンクインデックス | 実身インデックス、屑実身のツリー、孤児のツリーの全ノード。ヘッダとチェックサム、ツリーの番号、キーの順序と親が分けた範囲、段、リーフのつながり |
| ファイルヘッダー | インデックスが指す実身ブロック。ヘッダとチェックサム、UUIDがインデックスのキーと同じこと、表の項目数とフラグが範囲(項目数はボリュームの上限、`ts_blk_lim`)に収まること |
| 通常インデックスと接続インデックス | 管理用セグメント、アイコン、配置表、リソース表、仮身表。配置の形、インライン領域の重なり、ブロックの連なりのヘッダ、項目数、ridの順、種別、バイト数、仮身表の順。バージョン5では、管理の部分のランのツリーとリソース表の文字列領域も見る |
| フラグメント・区切り・レコードサイズ | レコードとリソースの配置。エクステントのツリーのリーフ、連なりの続き方、ブロック数とバイト数の一致 |
| ファイルヘッダー情報 | 管理用セグメントがJSONのオブジェクトであること、`records`と配置表の一致、参照数と仮身表・固定の数の一致、壊れたリンク、屑実身のツリーと実身のフラグ、孤児のツリーと実身のフラグ(バージョン5では予備の配置と`TSFSO_F_SPARE`も)、スーパーブロックが指す実身 |
| 領域の割当て | 空きビットマップと実際に使われているブロックの一致 |
| 空き領域 | 完全のときだけ。空きブロックをデバイスから読む |
| 隠れ屑実身 | 生きている実身から仮身でたどれない実身 |
| ほかのボリュームからの参照 | ボリュームが持つ参照の記録(8.3)と、取り付けてあるほかのボリュームの仮身表との一致。行き先の実身が無い記録、指す側の実身が無い記録、数の食い違い、記録の無い仮身、スーパーブロックが指す記録の実身が無いこと |

使われているブロックは、ボリューム全体のビットの表にマークを付けながら数える。同じブロックに2度目のマークを付けようとした所で、二重割当てとして報告する。管理ブロックの検査はブロックレイヤの`ts_blk_good`で行い、異常を記録しない。普段の読出しで使う`ts_blk_check`は、異常を記録してボリュームを読取り専用にするためである。壊れたリンクは、仮身表で数える対象になっている項目のうち、同じボリュームのインデックスに無い実身を指すものである。

隠れ屑実身は、参照数が0でないのに、生きている実身から仮身をたどっても届かない実身である。たどり始めるのは、スーパーブロックが指す実身(ルートの実身、実身「システム」、保護区画、ほかのボリュームからの参照の記録)、固定のある実身、参照数が0の実身(屑実身。回収されるまではその仮身も数えられる)、開いたまま削除された実身である。自分自身を指す実身や、互いに指し合う実身の組がこれに当たる。

処理方式の簡易は、フラグメント・区切り・レコードサイズと領域の割当てを調べない。レコードの配置をたどらないと使用中のブロックが分からないので、ビットマップとの突き合わせもしない。完全は、空き領域に加えて、レコードとリソースのブロックもデバイスから読み、読めないブロックを報告する。データはチェックサムを持たないので、読めることだけを確認する。

### 修復

修復は、到達できるものを失わない操作に限る。最初の検査で、デバイスから読めないブロックや、壊れた管理の部分、配置の食い違い、二重割当てなど、ボリュームの全体像が欠ける障害が見つかったときは、何も書かない。全体像が欠けたまま書くと、使用中のブロックが空きに見えたり、参照数が少なく数えられたりするためである。ツリーのノードと空きビットマップは、ほかの所から作り直せるので、全体像が取れていれば作り直す(下の2と4)。ツリーとビットマップが同時に壊れていても、すべてのブロックを読んで実身を集めて作り直す(下の4)。読めるがチェックサムの合わない実身ブロックは、読めるものをサルベージする(下の1)。修復できる障害だけのときは、次の順に行う。

1. 壊れた実身ブロック: デバイスから読めるがヘッダかチェックサムが合わない実身ブロックは、ブロックの中身をそのまま手がかりにして、読めるものを新しい実身に移す(`ts_obj_salvage`)。管理用セグメントと配置表の配置は、形、範囲、大きさを確認してからたどり、別のブロックにある管理の部分はそれ自身のチェックサムが合うものだけを使う。管理用セグメントが読めれば名前を引き継いで「救出: 名前」とし、レコードは配置表とレコードの並びに沿って、全体が読めたものだけを同じ型とサブタイプで書く。リソースと仮身表は引き継がない(仮身表はレコードから作り直される)。新しい実身は、隠れ屑実身と同じくTRASHを作ってそこに集める。元の実身はツリーから外し、そのUUIDは何も指さなくなる。元の実身を指していた仮身は壊れたリンクとして4で外部のフラグが立ち、元の実身のブロックは何にも使われないブロックとして6で解放する。ビットマップを作り直す前に行うのは、元の実身のブロックがまだ使用中のうちに読み出すためである。この段階の後に検査をやり直す。
2. 空きビットマップ: グループのヘッダが持つチェックサムに合わないビットマップのブロックを、検査で使用中と分かったブロック(グループが自分で使うブロック、グループの終わりより後のビット、何かが指すブロック)から作り直す(`ts_blk_map_put`)。ほかの段階がそのグループからブロックを確保する前に行う。グループの空きブロック数もそれに従う。
3. 割当て漏れ: 使用中なのに空きになっているブロックを、使用中にする。ほかの段階がブロックを確保する前に行う。後にすると、修復が新しく確保したブロックが使用中のレコードと重なる。
4. ツリー: たどれなかった実身インデックス、屑実身のツリー、孤児のツリーを、実身ブロックから作り直す。実身インデックスか孤児のツリーがたどれないときは、ビットマップが使用中とするブロックのうち、ヘッダとチェックサムの正しい実身ブロックを読み出して実身を知る(解放されたブロックは前の中身を残しているので、使用中のブロックだけを見る)。同じ実身が2つのブロックに見つかれば、後のトランザクションが書いた方を採り、同じトランザクションのものなら全体像が欠けるとする。ビットマップのブロックも壊れていれば、そのブロックが受け持つ範囲はすべてのブロックを読む。このとき、削除されて解放された実身の古い実身ブロックも見つかるので、検査の本番の前に、見つけた実身のブロックと管理の部分とレコードの配置にマークを付けることを報告せずに繰り返し(`sift`)、2つの実身が同じブロックを使えば、実身ブロックを書いたトランザクションの古い方を古いコピーとして外す。ボリュームが自分で使うブロック(ツリーのノード、ジャーナル)を使う実身も古いコピーである。古いコピーが無くなるまで8回まで繰り返し、収まらなければ全体像が欠けるとする。ほかの実身とブロックが重ならない古いコピーは区別できないので、屑実身として残る。何も失わない方を選んだ扱いである。外した古いコピーのブロックは、何にも使われないブロックとして6で解放する。レコードの配置をたどらないとビットマップを作り直せないので、ビットマップが壊れているときは、簡易の処理方式でもレコードの配置まで調べる。実身インデックスには孤児のフラグの無い実身を、孤児のツリーには孤児か作り直しのフラグのある実身を、屑実身のツリーには屑実身のフラグのある実身を入れる。古いルートを破棄して全部のキーを入れるまでを1つのトランザクションで行うので、途中で電源が切れても、古いツリーか新しいツリーのどちらかが残り、空のツリーは残らない。古いツリーのノードは何にも使われないブロックになり、6で解放する。
5. 仮身表、参照数、隠れ屑実身: 壊れたリンクを持つ実身と、作り直しのフラグが残る実身の仮身表を、xmlTADのレコードから作り直す(`ts_obj_mark_relink`、`ts_obj_relink`)。無い実身への仮身は外部のフラグが立ち、数えられなくなる。孤児のツリーと屑実身のツリーから、余分な項目を除く。予備の配置が残る実身は、フラグを立てて孤児のツリーに入れ、予備の配置を空にする(`ts_obj_tidy`、バージョン5)。誰も開いていないボリュームでは、開いたまま削除された実身をマウント時と同じく回収する。参照数は、仮身表と固定から数えた値にし、屑実身のツリーと実身のフラグをそれに合わせる(`ts_obj_set_ref`)。隠れ屑実身は、新しいキャビネット実身「TRASH」を作って、そこへの仮身を並べる(1つのTRASHに入れる仮身はボリュームのリンクの上限までで、超えるときはTRASHを複数作る、7.3)。TRASHは参照数が0の屑実身で、実身ブロックにTRASHのフラグ(`TSFSO_F_TRASH`)を持つ。屑実身操作で見られ、ウインドウに移すと普通の実身に戻る。
6. 使われていない領域: 何にも使われていないのに使用中になっているブロックを解放する。続けて、グループの空きブロック数をビットマップから数え直し、壊れたスーパーブロックのコピー、バックアップ、グループのヘッダを、メモリにある正しい内容で書き直す(`ts_blk_mend`)。

各段階はボリュームのトランザクションとして書き、段階ごとに検査をやり直して、次の段階はその結果から始める。途中で電源が切れても、次の検査がその続きから直す。最後にもう一度検査し、何も残らなければ、スーパーブロックの異常の記録を消して、ボリュームを書込み可能な状態に戻す(`ts_blk_checked`)。異常が記録されたボリュームは読取り専用でマウントされ、ジャーナルを再適用していない。誰も開いていないボリュームでは、検査の前にジャーナルを再適用する(`ts_blk_replay`)。取り付け済みでジャーナルを再適用していないボリュームは、修復しない。

TRASHのフラグを持つ実身を削除するか屑実身として回収すると、それが指していた実身のうち、生きている実身から届かなくなったものと、それらだけが届くものも回収する(`ts_obj_drop_cycles`)。互いに指し合う実身の組は参照数が0にならないので、普段の回収では残る。この組を見つけるのは修復と同じ隠れ屑実身の判定で、TRASHが無くなった後のボリュームで行う。見つけた実身は、まず参照数を0にして屑実身のツリーに入れ、それから1つずつ回収する。回収は仮身を手放すが、相手の参照数は0より下がらないので、組がまとめて消える。生きている実身から届く実身は残る。ボリュームの全体像が取れないときは何もしない。

検査と修復の間は、そのボリュームを変える呼出しを止める(`ts_chk_vol`がボリュームのロックを排他的に取る)。呼出し元が自分のトランザクションを開いたままにしていれば、それが終わるのを待つ。

ボリュームの検査の後に、ほかのボリュームからの参照の記録を、取り付けてあるネイティブのボリュームの仮身表と突き合わせる(`knl_obxref_check`、8.3)。行き先の実身がボリュームに無い記録、指す側のボリュームが取り付けてあるのにその実身が無い記録、仮身表の数と食い違う記録、記録の無い仮身を見つける。修復では、記録を見つけたとおりに書き直す。参照数は記録の実身の仮身表から数えられるので、記録に合わせて動く。取り付けていないボリュームからの記録は確認できないので、そのまま残す。ボリュームの検査が全体像の欠けで修復を拒否したときは、記録も書き換えない。

### ボリュームの選び方とシステムのボリューム

`ob_chk_list`は、デバイス管理にあるディスクの全区画のスーパーブロックを読み、TSFSのボリュームを一覧にする(`peripheral_kernel/obj/obfsck.c`)。取り付け済みのボリュームは、検査はそのまま行う。修復するときは、システムのボリュームでなければ一度取り外し(`knl_obfile_detach`)、検査のためだけに開いて修復し、終わったら取り付け直す。取り外しは、そのボリュームの実身を開いている者がいれば拒否される(`ts_cls_vol`が`E_OBJ`を返す)。そのときは取り付けたまま修復する。ただし、異常が記録されて取り付けられたボリュームはジャーナルを再適用していないので、取り付けたままでは修復できず、結果にそう示す(`T_TSFSCK`の`inuse`と`refused`)。取り付けていないボリュームは検査のためだけに開く。検査の間は、そのボリュームの取り付けと取り外し(`ob_att_vol`、`ob_det_vol`)と区画の拡張を`E_BUSY`で拒否する。逆に、ボリュームの取り付け、取り外し、拡張をしている間は、どのボリュームの検査も`E_BUSY`で拒否する(`knl_ob_chk_hold`)。検査が開いたボリュームや、取り付けたまま検査しているボリュームが、検査の途中で閉じられたり大きさを変えられたりしないためである。プロセスの小物は、検査をシステムコール`ob_chk_vol`で呼ぶ。カーネルは`ob_chk_run`の通知のたびに、イベントをプロセスのメモリの表に書き、その後で件数を書く。プロセスの別のタスクは件数を見て進み具合を示す。`ob_chk_vol`と`ob_chk_request`は管理者だけに許す(付録A)。

システムのボリュームは、起動から終了まで書体やプログラムの読出しに使われ続ける。そのため、動いている間は検査だけを行い、修復は拒否する。修復の依頼は、起動ボリュームのファイル`/boot/DISKFIX.REQ`に「デバイス名 処理方式」の1行で書き(`ob_chk_request`)、システムを再起動する。次の起動では、システムのボリュームを取り付ける前に依頼を読んで消し、ボリュームを修復のためだけに開いて修復する(`knl_ob_chk_boot`)。依頼を先に消すので、修復が終わらなくても起動のたびに繰り返すことはない。結果と報告はメモリに残し、デスクトップが起動したときにディスク修復のウインドウに出す(`ob_chk_boot_result`)。

### 報告

検査と修復は、進むにつれてイベントを呼出し元の関数に渡す(`FP_TSFSCK`)。項目の始まり、見つけたもの(種類、実身のUUID、ブロック、種類ごとの数値)、修復したものである。修復の後の検査は、残ったものを種類ごとに1つのイベントで渡す。結果(`T_TSFSCK`)は、種類ごとの見つかった数、修復した数、残った数と、実身、レコード、仮身、ブロックの数を持つ。

### テスト

カーネルのテスト(`tests/ktest/ktest_dfix.c`、スイート`dfix`)は、作業用の区画にボリュームを作って行う。

- `test_clean`: ルートの実身が固定するキャビネット、2つの文書(1つは3ブロックのレコードを持ち、もう1つを指す)からなるボリュームを、検査、簡易、完全のどれでも障害なしとし、修復しても何も書かないこと。
- `test_repair`: 互いに指し合う2つの文書と、屑実身のツリーから外した屑実身を足し、ストアの下から、参照数を3増やし、何にも使わない3ブロックを確保し、レコードのブロックを1つ空きにし、仮身表の項目を無い実身に向け、異常を記録して読取り専用にする。検査がそれぞれを見つけ(書き換えないこと)、修復がそれぞれを直し、修復後の検査で何も残らないこと。完全の検査でも障害なしとなり、もう一度修復しても何も書かないこと。レコードの中身が書いたときのままで、TRASHが2つの仮身を持つ参照数0の実身であること。ボリュームに再び書き込めること。
- `test_refused`: レコードの配置をボリュームの外に向けると、配置の障害として見つかり、修復は何も書かないこと。
- `test_system`: 一覧に作業用の区画とシステムのボリュームがあり、使用中のシステムのボリュームを検査して、すべての実身について障害がないこと。修復は`E_BUSY`で拒否すること。
- `test_boot`: 参照数を狂わせたボリュームに修復の依頼を書き、起動時の処理を呼ぶと、依頼のファイルが消え、参照数が直り、結果が残ること。

- `test_index`: 実身インデックスのルートのノードのチェックサムを壊すと、リンクインデックスの障害として見つかり、修復できない障害は無いとされ、実身ブロックから4つの実身が見つかること。修復でインデックスが作り直され、古いノードが解放され、修復後の検査で何も残らないこと。レコードの中身と参照数が保たれ、屑実身は屑実身のツリーに戻ること。
- `test_map`: 実身のブロックのビットを含む空きビットマップのブロックを壊すと、アロケーショングループの障害として見つかり、修復で作り直されること。修復後に作った実身が、使用中のレコードのブロックを確保しないこと。
- `test_both`: 長いレコードを持つ実身を削除した後に別の実身を作り、さらにAの実身ブロックをコピーしてUUIDを変えた古いコピーを空きブロックに置いて、Aを書き直す。そのうえで実身インデックスのルートのノードと空きビットマップのブロックを両方壊すと、修復できない障害は無いとされ、古いコピーが外されて5つの実身が見つかること。修復でインデックスとビットマップが作り直され、修復後の検査と完全の検査で何も残らず、古いコピーのUUIDの実身が無く、レコードの中身と参照数が保たれ、修復後に作った実身が使用中のブロックを確保しないこと。
- `test_salvage`: 2つのレコードを持つ実身の実身ブロックで、ヘッダが使っていないバイトを変えてチェックサムを合わなくすると、ファイルヘッダーの障害として見つかり、修復できない障害は無いとされること。修復でTRASHが作られ、元のUUIDの実身は無くなり、TRASHが指す新しい実身の2つのレコードが元と同じで、元の実身が指していた実身の参照数が新しい実身の仮身で数えられること。
- `test_cycles`: 互いに指し合う2つの実身(片方は生きている実身からも届く実身を指す)を修復でTRASHに集め、TRASHにTRASHのフラグがあること。TRASHを削除すると、2つの実身も消え、生きている実身から届く実身は残り、空きブロック数が2つの実身を作る前に戻ること。
- `test_trash_split`: 1つの実身がリンクできる数より多い隠れ屑実身を、上限に収まる数のTRASHに分けて集め、修復後の検査で何も残らないこと(テストのためにボリュームの上限を`ts_blk_lim_test`で小さくする)。
- `test_attached`: 異常を記録したデータのボリュームを取り付け、その実身を開いている間は、修復が取り外せず書き換えないこと(`inuse`)。実身を閉じると、取り外して修復し、取り付け直し、参照数と異常の記録が直り、実身を開けること。
- `test_label_long`: 100字の日本語のラベルでボリュームを作ると(`knl_tsfs_format`)、`SB_LABEL`に先頭の63バイト(21字)が文字の境界で入り、ルートの実身があること。取り付ける前の`ob_chk_label`、取り付けた後の`knl_obfile_vol_label`、取り外して取り付け直した後のどれでも全体が読め、小さなバッファには文字の境界で切って入り、全体の大きさが返ること。`ob_chk_list`の項目に`TSFSCK_F_LABELCUT`が立つこと。
- `test_label_old`: ルートの実身の無い古い形式のボリューム(`ts_format_blk`だけ)で、取り付ける前も後も`SB_LABEL`がラベルとして読めること。
- `test_label_differ`: 取り付けずにルートの実身の名前を長い名前に変え、コピーと食い違わせる。取り付けるとラベルがルートの実身の名前になり、`SB_LABEL`が書き直されること。取り付けたままルートの名前を変えて`knl_obfile_label_sync`を呼ぶと、コピーがそれに合わせて書き直されること。
- `test_label_prot`: `knl_tsfs_format`で作ったルートの実身に`knl_obfile_top_prot`で付けた保護が、利用者のために作るタスクが`om_cre_obj`で作った実身の保護と、所有者、グループ、モード、属性、ACLのどれも同じであること。保護のあるルートはそのまま残すこと。

## 7.6 多くのディスクとボリューム

USBのディスクを何本も挿し、それぞれが複数の区画を持つときにも、すべての区画を同時にマウントまたは取り付けられる。固定の小さな表(マウント8、fimp 4、実身のボリューム4、TSFSのブロックレイヤのボリューム4、同時に開けるデバイス32)はやめ、表の上限はディスクの数と区画の数で決まる大きさにした。

| 表 | 上限 | 持ち方 |
| --- | --- | --- |
| ディスク | 表の上限は無い。virtio-blk、NVMe、SATAのディスクも、見つけたときに表を伸ばす(6.1)。USBのディスクの名前は`uda`から`udz`の次が`udaa`、`udab`と続く(6.1)。名前はデバイス名の8バイトに収まる`ud`と英字3文字までで、約18000台。USBの機器の数に表の上限は無く、xHCIのスロットはコントローラごとに255まで | USBのディスクの記述は、挿されたときに作り、抜かれても捨てずに次に使う。表は8から倍にして伸ばす |
| 1台の区画 | 255(`BLK_MAX_PART`)。GPTは区画表の項目の数(4096まで)を読み、使われている項目を数える。MBRは基本区画と拡張区画の中の論理区画で、論理区画はEBRの連なりをたどる(256個まで、後ろへ進まない連なりは切る) | |
| マウント(`fs_`) | 4096(`FS_MAX_MOUNT`) | 要るときに1つずつ作り、外しても捨てずに次に使う |
| 実身のボリューム(`obfile.c`)、TSFSのレイヤ(`tsfs.c`)、ブロックレイヤ(`tsfsblk.c`) | `CNF_MAX_VOL`(4096) | 同じ。ジャーナルとトランザクションの保留の表はボリュームの番号の位置に、初めて要るときに作る |
| fimp | 16 | 固定 |
| 同時に開けるデバイス、デバイスへの要求、登録できるデバイス | 上限は無い(`CNF_MAX_OPNDEV`、`CNF_MAX_REQDEV`、`CNF_MAX_REGDEV`は初めの数) | μT-Kernelの表。足りなくなると倍にして伸ばし、制御ブロックは番号から表で引く |
| デバイスの実身 | 上限は無い | 項目は1つずつ確保して表を伸ばし、使ったことのある所まで(`obd_hi`)を見る。デバイス箱に書く名前とUUIDは、全部を書く |
| 開いている実身 | 1024(`TSFS_MAX_OD`) | 固定 |

表の項目を要るときに作って捨てないのは、ロックを取らずに番号から項目を引く所(TSFSのレイヤの`vol_of`など)と、マウントを指したまま残るディスクリプタがあるからである。項目の場所が変わらず、メモリも返さないので、取り外しと同時に番号で引いても、使い終えたメモリには触れない。同時に使った数だけメモリが要り、抜き差しを繰り返しても増えない。項目を作るのは、表のミューテックスを取ってからで、作った項目は`__atomic_store_n`(リリースの順序)で表に置き、ロックを取らずに読む所は`__atomic_load_n`(アクワイアの順序)で読む。DI/EIだけの排他は4コアでは効かないので使わない。

ブロックレイヤのキャッシュは、ボリュームごとに最大32MB(`CNF_TSFS_CACHE`)で、全ボリュームの合計が128MB(`CNF_TSFS_CACHE_ALL`)を超えると、256ブロック(1MB)より多く持つボリュームは新しいブロックを確保せずに自分の最も古いブロックを入れ替える。デバイスごとの読み書きの回数は、デバイスのディスクリプタの番号の位置に数える。

### ボリュームのラベル

ネイティブのボリュームのラベルは、ボリュームのルートの実身(スーパーブロックの`root_uuid`が指す実身)の名前である。BTRON2ではすべての資源を実身と仮身で表すので、ラベルも実身の名前として持ち、長さの上限はない(実身の名前と同じく、メタデータに書ける長さまで)。スーパーブロックの`SB_LABEL`(64バイト)は、古いシステム、起動のツール、スーパーブロックだけを読む所のためのコピーとして残し、ラベルの先頭を文字の境界で切って入れる(終端の0を含めて64バイト、`label_put`)。

- 作るとき: `knl_tsfs_format`(`tsfspart.c`)が、フォーマット(`ts_format_blk`)の後で、ルートの実身を`{"name": ラベルの全体}`の図形の実身として作り、ルートに定めて1回保持する。ディスク操作の〈区画作成〉(`knl_tsfs_part_make`)はこれでボリュームを作る。ルートの実身はオブジェクトのレイヤの下で作るので、保護を持たない。デスクトップは作ったボリュームを取り付けた直後に、`knl_obfile_top_prot`で利用者の既定の保護(所有者とグループは利用者、モード0644、ACLなし)を付ける。以前デスクトップが`om_cre_obj`でルートの実身を作っていたときと同じ保護である。GPTの区画名には、作るときだけラベルを入れる。区画名はUTF-16の36単位(UEFIの規格、(A))なので、4バイトのUTF-8はサロゲートペアにし、36単位に入る最後の文字で切る(`gpt.c`の`set_name`)。
- 読むとき: ルートの実身の名前があればそれ、ルートが無いか名前が空なら`SB_LABEL`のコピー(`knl_tsfs_vol_label`)。大きさを先に問い合わせて確保する形で、`ob_ref_nam`と同じく、入るだけを文字の境界で切って入れ、全体の大きさを返す。取り付けたボリュームは`knl_obfile_vol_label`、ディスク修復の一覧のボリュームはSVCの`ob_chk_label`で読む。`T_TSFSVINF.label`、`T_OBFVREF.label`、`T_TSFSCKDEV.label`は64バイトのフィールドのまま残し、ラベルの先頭を文字の境界で切って入れる。`T_TSFSCKDEV`は、切ったとき`flags`に`TSFSCK_F_LABELCUT`を立てる。
- 食い違ったとき: ルートの実身の名前を使い、`SB_LABEL`を書き直す。書き直すのは、ボリュームを取り付けるとき(`obfile.c`の`attach_vol`)と、ルートの実身の名前を変えた後(`knl_obfile_label_sync`、`om_store_rename`から呼ぶ)である。読取り専用のボリュームはコピーを書き直さないが、読むラベルはルートの実身の名前になる。取り付けたボリュームが保持する名前も確保した文字列で全体を持ち(`knl_obfile_vol_nam`で全体を読む。ボリュームのラベルも`knl_obfile_vol_label`で全体を読み、固定長の`T_OBFVREF.label`はない)、ルートの名前を変えるとそれに合わせる。
- 古いコピー: 以前のシステムは`SB_LABEL`を63バイトのバイトの位置で切っていたので、文字の途中で終わるコピーがある。スーパーブロックを読むときに、途中の文字を除いて読む(`ts_label_whole`)。

古いシステムとの関係は次のとおりである。

| 場合 | 扱い |
| --- | --- |
| 新しいシステムで作ったボリュームを古いシステムで開く | 古いシステムは`SB_LABEL`のコピー(64バイトに入る先頭)をラベルとして見せる。ルートの実身は普通の実身として見え、ボリュームは壊れない |
| 古いシステムでフォーマットし直す | ルートの実身は無く、ラベルは`SB_LABEL`だけになる。新しいシステムはコピーをラベルとして読む。デスクトップが取り付けるときにルートの実身を作り、コピーの名前を付ける(11.26) |
| 古いシステムがルートの実身の名前を変える | 古いシステムはコピーを書き直さないので、コピーとルートの名前が食い違う。新しいシステムはルートの実身の名前をラベルとし、次に取り付けたときにコピーを書き直す |
| 古いシステムで作ったボリューム(ルートが無い、またはルートの名前がコピーと同じ) | コピーをラベルとして読む。ルートの名前がコピーと違えば、上と同じくルートの名前を使ってコピーを書き直す |

取り付けていないボリュームのラベルを`ob_chk_label`で読むときは、ディスクの検査が取り付けていないボリュームを開くのと同じに、そのためだけにボリュームを開いて(`ts_opn_vol`)ルートの実身のメタデータの`"name"`を読み、閉じる。ボリュームは取り付けない。検査や、ボリュームの取り付け、取り外し、拡張をしている間(`knl_ob_chk_hold`)と、開けないとき(壊れている、古い形式)は、コピーを返す。`ob_chk_list`は一覧を作るたびにすべてのボリュームを開くことはせず、取り付けていないボリュームはコピーを入れ、コピーが64バイトに1文字分足りないところまで埋まっているときは`TSFSCK_F_LABELCUT`を立てる(切ったかどうかは開かないと分からないため)。

`tools/mktsfs`、`tools/fsck.tsfs`、`tools/tsfs_py`も同じに扱う。`mktsfs -L`はラベルを文字の境界で切ってコピーに入れ、`--root`の実身の名前と違うとき(ルートが無くて切ったときを含む)はそう通知する。`fsck.tsfs`はルートの実身の名前をラベルとして示し、コピーがルートの名前の先頭と違えば注記する。

### 区画の中身の判別

区画を何の形式でマウントするかは、プログラムが指定する形式ではなく、区画の先頭の中身から決める(`peripheral_kernel/fs/fsprobe.c`、`knl_fs_probe`)。先頭の64KBを読み、次の順に見る。

| 形式 | 判別方法 | 扱い |
| --- | --- | --- |
| TSFS | ブロック0か1に`TFSVOL02`。チェックサムの合う、世代の新しい方からラベル、ボリュームのUUID、最上位の実身を読む | 実身のボリュームとして取り付ける(`ob_att_vol`、11.26) |
| exFAT | 起動セクタのOEM名。ラベルはルートディレクトリの先頭のセクタから読む | `exfatfs`でマウントする |
| NTFS | 起動セクタのOEM名 | `ntfsfs`でマウントする |
| FAT12、FAT16、FAT32 | FATのfimpと同じ条件の起動セクタ。種類はクラスタ数で決める | `fatfs`でマウントする |
| ext2、ext3、ext4 | バイト1024からのスーパーブロックのマジックナンバー0xEF53 | 扱えない |
| BTRONのCD-ROM、ISO 9660 | セクタ16からのボリューム記述子。システムIDが`BTRON SPECIFIED FILE SYSTEM`の区画記述子があればBTRON | BTRONはファイル変換がマウントせずに読む(11.9)。ISO 9660は扱えない |
| BTRONのファイルシステム | 先頭64KBの512バイトごとに、TRONディスクIDとディスク形式ID | ファイル変換が読む |
| 区画表 | 区画をサブユニットに持つディスク全体の、0xAA55で終わるセクタ0 | ボリュームは区画にある |
| 空 | 読んだ範囲がすべて0 | 扱えない |

`fs_attach_dev`にfimpの名前を渡さない(`NULL`)と、判別した形式のfimpでマウントし、マウントするfimpの無い形式には`EX_NOTSUP`を返す。ディスクの実身の属性には`tessronos.format`(`kind`、`label`、`fs`)として現れる。ファイル変換とバックアップは名前を渡さずにマウントし、ファイル変換はメディアの一覧に形式を示して、扱えない形式は「この形式は扱えません」と通知する。

### exFAT

`peripheral_kernel/fs/exfatfs.c`。読み書きとも、ファイルと名前について`fatfs`と同じ呼び方ができる。マウントはデバイスの実身(`fs_attach_dev`、`fs_opn_vol`)を通すので、ファイル変換、バックアップ、`/media`からそのまま使える。

ファイルのクラスタは、連続したクラスタの列(NoFatChain)で持ち、次のクラスタが使用中のときに初めてクラスタの表にチェーンを書く。ValidDataLengthより後ろは0として読み、ファイルを長くするだけでは書かない。名前の比較とNameHashはボリュームのアップケース表を使う。知らない副エントリを持つファイルは、そのエントリがクラスタを持つかもしれないので、削除と改名を`EX_NOTSUP`で拒否する。

媒体への書き順は、データ、ビットマップ、クラスタの表、ディレクトリのエントリとする。解放するときはエントリを先に書く。最初の変更の前に起動セクタのVolumeDirtyを立て、変更がすべて媒体に届き、書込みで開いたファイルが無くなって5秒たつと消す。このとき使用率も書く。この2つは起動領域のチェックサムの対象外である。バックアップの起動領域は変えない。

次のボリュームは読むだけで、書込みは`EX_ROFS`にする。VolumeDirtyかMediaFailureが立っている、クラスタの表が2つある(TexFAT)、主版数が1でない、アップケース表のチェックサムが合わない。ここで修復はしない(Windowsか`fsck.exfat`に任せる)。起動領域のチェックサムが合わないときはマウントしない。セクタは512バイトだけを扱う。

### NTFS

`peripheral_kernel/fs/ntfsfs.c`。読むのは名前、ディレクトリのインデックス(レコードの中とブロック)、属性リストで別レコードへ続く属性、レコードの中のデータ、クラスタの列、スパース、圧縮(LZNT1)である。暗号化されたファイルは一覧に出るが、データは読めない(`EX_NOTSUP`)。`$`で始まるボリュームのファイルは一覧に出さない。媒体の長さとオフセットはすべて確認してからたどる。

書くのは、すでに場所のあるファイルのバイトを同じ場所で置き換えることと、そのファイルの時刻だけである。NTFSはファイルのデータをジャーナルに入れないので、この書込みはジャーナルと構造に触れない。ファイルの作成、削除、改名、大きさの変更、圧縮・スパース・暗号化されたファイルと未初期化の部分への書込みは、`EX_NOTSUP`で拒否する。これらはレコードとインデックスとビットマップを、ジャーナルを通さずに一度に変えることになり、途中で電源が切れるとWindowsの`chkdsk`に頼ることになるからである。

次のボリュームは読むだけにする。NTFS 3.xでない、`$Volume`にdirtyのフラグがある、`$LogFile`の再開領域に再生すべき内容が残っている、`hiberfil.sys`に中身がある(休止状態、高速スタートアップ)。Windowsが中身を消した`hiberfil.sys`は問題にしない。

### テスト(exFAT、NTFS)

カーネルの外で実行するテストを`tools/tests/hostfs/`に置く。fimpのソースをそのままホストのコンパイラ(AddressSanitizerとUBSan付き)でビルドし、イメージファイルをデバイスとして動かす。`hostfs.sh exfat`は`mkfs.exfat`のイメージ(クラスタ512バイト、4KB、128KB)に、作成、1MBごとの書込み、部分セクタ、飛び越えた書込み、切り詰めと伸長、2つのファイルを交互に伸ばす断片化、2階層の移動を含む改名、1つのクラスタに収まらないディレクトリ、満杯になるまでの書込み、VolumeDirtyのボリュームの読取り専用を行い、終わったイメージを`fsck.exfat -n`で確認する。`hostfs.sh ntfs`(rootで`ntfs-3g`のループマウントを使う)は、`ntfs-3g`が作ったファイルを全部読んでハッシュを比べ、同じ場所での書込みの結果を`ntfs-3g`で読み返し、`ntfsfix -n`を通し、dirtyのフラグ、再生の残ったジャーナル、休止状態の各ボリュームが読取り専用になることを確認し、MFTの先頭をランダムに壊したイメージ200個で落ちないことを確認する。exFATのカーネル内のテストは`vols`のスイートの`test_all_on`で、`tools/tests/mkvoldisk.py`が作る本物のexFATの区画に書いて読み返し、読取り専用でマウントし直して読む。

### 取り外しと抜き取り

ボリュームの取り外し(`ob_det_vol`)は、そのボリュームの実身を開いているキーがあれば`E_BUSY`で拒否し、何も変えない。ただし、属性だけのキー(`OB_OP_ATRRD`だけで開いた、変更の通知を受けるためのキー)は取り外しを妨げない。そういうキーしか残っていなければ、それらを閉じて(通知の依頼も一緒に消える)取り外し直す(`obname.c`の`watch_keys_drop`。Linuxのinotifyの監視がアンマウントを妨げないのに当たる)。仮身一覧のウインドウは、仮身の指す実身をこのキーで監視しているので(`tv_app.c`の`ta_watch`)、最初のウインドウにディスクの仮身があっても切り離せる。閉じられたキーを後で使うと`E_ID`になる。同じボリュームのUUIDを持つボリュームがすでに取り付けてあるときの取り付けは`E_OBJ`で拒否する(1つのボリュームをコピーした区画を並べると、同じ実身が2か所に見えるため)。

媒体やディスクが抜かれると、デバイスの実身のレイヤ(`obdev.c`)が、そのデバイスと区画のマウントと実身のボリュームを、gone(取り去られた状態)にする(`knl_fs_revoke`、`knl_obfile_revoke`)。goneのボリュームの実身はもう見つからず、開いていたキーとディスクリプタはエラーを返し、最後のキーが閉じたときにボリュームを閉じて表の項目を空ける。同じ媒体を挿し直すと、空いた項目に取り付け直せる。

goneになったときにまだ開いている実身があれば、`knl_obfile_revoke`は、ボリュームのロックを持っている間にその実身のUUIDを集め(`knl_tsfs_vol_opened`)、ロックを解放してから、それぞれの実身の通知の依頼に`OB_E_DETACH`(媒体が取り去られた)を送る。続けて、属性だけのキーを閉じる(`obname.c`の`knl_ob_watch_keys_drop_of`)。取り外しのときの`watch_keys_drop`と同じ扱いで、通知を受けるためだけのキーがボリュームを押さえないようにするためである。キーを閉じると、通知の依頼も一緒に消える。閉じられたキーを後で使うと`E_ID`になる。属性のほかにも読むキーで通知を受けているプログラム(スライドショーなど)は、`OB_E_DETACH`を受けたらすぐ自分でキーを閉じる。最後のキーが閉じるとボリュームが閉じ、デバイス(USBのディスクの`uda`など)も閉じられて、名前が空く(`msc_unregister`)。そのため、同じディスクを挿し直すと同じ名前になる。

通知を受けるために実身を開いたままにしている所と、`OB_E_DETACH`を受けたときの扱いは次のとおりである。

| 所 | キー | 受けたときの扱い |
| --- | --- | --- |
| 基本文章編集、基本図形編集(仮身一覧)のプロセス(`lib/libtv/tv_app.c`の`ta_watch`) | 属性だけ | キーはカーネルが閉じる。監視の表から外し、仮身を描き直す。デバイスの一覧の実身(`OB_UUID_DEVLIST_INIT`)を監視し、ディスクが来たり取り付けられたりするたびに、開いた実身、親、仮身の指す実身を監視し直す。全部を監視し直せたら一覧の監視をやめる |
| スライドショー(`application/slide/sl_main.c`の`watch`) | 読込と属性 | 自分でキーを閉じる。画面に出ている絵はそのまま残す |
| 設定の監視タスク(`outer_kernel/wm/uconf.c`) | 属性だけ | キーはカーネルが閉じる。2秒ごとに探し直し、見つかったら監視し直す |
| かな漢字変換のユーザ辞書の監視タスク(`application/kconv/kconv.c`) | 属性だけ | 同じく、2秒ごとに探し直し、見つかったら単語を読み直す |

編集中の文章など、書込みのために開いているキーは閉じない。これまでどおり、そのキーが閉じるまでボリュームは残り、ディスクの名前も残る。その間に同じディスクを挿し直すと、別の名前(`uda`が使われていれば`udb`)になる。通知を受けても閉じないプログラムが読込のキーを持ち続けた場合も同じで、そのプログラムが終わる(キーが閉じる)まで名前が残る。これは仕様として残す。挿し直したボリュームは、名前が違っていても、ボリュームのUUIDで同じものと判別して取り付け直す(11.26)。デスクトップはこの変化を見て、そのボリュームの実身のウインドウを閉じ、仮身を虚身として描き直す(11.26)。システムのボリュームも同じにgoneになり、カーネルは止まらない。デスクトップは初期ウィンドウだけを、持っている記録で残し、同じボリュームが挿されると取り付け直す(11.26)。起動のときから一度取り付けたことのあるボリュームを取り付け直したときは、起動のたびに空にする実身を空にしない(`knl_obfile_again`)。

### 別のマシンのシステムのディスク

別のマシンのTessronOSのシステムのディスク(USBのディスクなど)をつなぐと、そのボリュームには、`etc/def`の固定のUUIDを持つシステムの実身(システム箱、初期ウインドウなど)が、いま動いているシステムのボリュームと同じUUIDで入っている。8.3の「実身のUUIDは取り付けたボリュームの間で重ならない」が崩れるので、次の2段階で扱う。

段階1では、そのボリュームにフラグを立て、探す順と判定を変える。

- フラグ: 取り付けるボリュームがネイティブのTSFSで、系の箱(`SYSDEF_SYSTEM_BOX`)の実身を持ち、ボリュームのUUIDが最初に取り付けたシステムのボリュームと違えば、そのボリュームは別のマシンのシステムのボリュームで、`OBFVOL.foreign`が立つ。最初に取り付けたボリュームは常にこのマシンのもので、FAT上の格納方式のシステム(ボリュームのUUIDが0)のときは、系の箱を持つほかのボリュームはすべて別のマシンのものになる。取り付けたときにコンソールへ`ob: パス is another machine's system volume, N aliases`と出す。フラグは`T_OBFVREF.foreign`と`knl_obfile_foreign`で読める。
- 探す順: UUIDでボリュームを探す`knl_obfile_vol_of`は、フラグのないボリュームを取り付けた順に探し、見つからなければフラグのあるボリュームを探す。システムのUUIDは、いま動いているシステムの実身を指す。`knl_obfile_first_vol`と`knl_obfile_machine`(このマシンのUUID)は、フラグのあるボリュームを返さない。
- 「そのボリュームの実身か」の判定: `knl_obfile_on(uuid, path)`は、パスのボリュームにUUIDの実身があるかではなく、UUIDで探した結果がそのボリュームかどうかを返す。切り離しのときの属性だけのキーの閉じ方(`watch_keys_drop`)、デスクトップの切り離しの判定(開いているウインドウ)、起動のたびに空にする処理は、これを使う。以前は、別のマシンのディスクに今のシステムの初期ウインドウと同じUUIDの実身があるので、初期ウインドウを「そのディスクの実身を開いているウインドウ」と数えて切り離しを拒否していた。
- 起動のたびに空にする処理: ボリュームを取り付けたあとの`knl_sys_clear_start`は、別のマシンのシステムのボリュームには行わない。以前は、そのボリュームの一時の箱の実身を、同じUUIDの今のシステムの一時の箱として空にしていた。
- 最上位の実身(11.26): デスクトップは、ルートの実身の無い別のマシンのディスクにルートの図形の実身を作るとき、その中に、そのマシンの初期ウインドウ(`SYSDEF_CABINET`の別名、下)を指す仮身を1つ置く。
- 権限: 11.26のとおり、システムが何も使っていないUSBの媒体の接続と切り離しは、デスクトップが管理者のパスワードを求めずに行う。取り付けと取り外しはデスクトップ(システムの資格)が`ob_att_vol`と`ob_det_vol`で行うので、カーネルの検査(プロセスが直接呼ぶときは管理者だけ)は変えない(LinuxのudisksがpolkitでUSBの媒体のマウントを利用者に許し、マウントそのものはrootのデーモンが行う分け方に当たる)。

段階2では、今のシステムのUUIDと重なる別のマシンの実身に、別名のUUIDを割り当てる(`peripheral_kernel/obj/obfile.c`)。取り付けのときにUUIDをマッピングするので(LinuxのidmappedマウントがユーザIDをマッピングするのに当たる)、プロセスとデスクトップは、別のマシンの実身を「別のUUIDの実身」として扱える。ウインドウの「1つの実身に1つのウインドウ」、切り離しの判定、仮身一覧の監視(`ta_watch`)は、変えずに働く。プログラムのリソース(データボックスなど)は、今のシステムのものを読む。

- 別名の表: 別のマシンのシステムのボリュームを取り付けるとき、そのボリュームの実身を全部たどり(`ts_lst_obj`)、このマシンのボリュームに同じUUIDの実身があるものごとに別名を作り、元のUUIDの順と別名の順の2組の表に持つ(`al_build`)。表はボリュームを取り外すと(媒体が抜かれて閉じると)捨てる。
- 別名の形: UUIDのバージョン8(RFC 9562)。先頭の6バイトは別名のマーク`7e 55 0a 11 a5 00`、バイト6の上位4ビットはバージョンの8、バイト8の上位2ビットはバリアントの`10`。残りの74ビットは、SHA-256(`tessronos.foreign-alias`の23バイト || 別のマシンのボリュームのUUIDの16バイト || 元のUUIDの16バイト)の先頭から取る(バイト6の下位4ビットに結果のバイト0の下位4ビット、バイト7に結果のバイト1、バイト8の下位6ビットに結果のバイト2の下位6ビット、バイト9〜15に結果のバイト3〜9)。同じディスクを挿し直せば同じ別名になるので、保存した仮身が次の取り付けでも有効である。
- 今のシステムと重ならない理由: TessronOSが作る実身のUUIDはバージョン7(時計が合っていないときはバージョン4、`ts_gen_uuid`)で、`etc/def`の固定のUUIDもバージョン7なので、バージョン8の別名とは重ならない。別名のマークを持つUUIDを指定して実身を作ること(`T_OBCRE.uuid`)は拒否する(別名が引ける間は`E_OBJ`、引けないときは`E_PAR`)。
- 引く所: `obfile.c`の中で、UUIDから実身を探す所(参照、名前、保護、削除、開く、参照数の増減)は、すべて`obf_real`で別名を解決し、別のマシンのボリュームと元のUUIDに替えてからTSFSへ渡す。ほかのファイルが、探したボリュームにUUIDをそのままTSFSへ渡す所も、`knl_obfile_real`(入れたUUIDから、ボリュームと元のUUIDを返す)で解決してから渡す(プロセスのプログラムを読む`sysman/proc.c`、ほかのボリュームからの参照の記録`obxref.c`)。元のUUIDの実身は、別名を持つかぎり、別のマシンのボリュームでは元のUUIDで探されない。`knl_obfile_alias`は、ボリュームと元のUUIDから別名を返す。
- レコードとメタデータ: 別のマシンのボリュームの実身のレコードとメタデータを読むときは、中に書かれたUUID(36文字の`8-4-4-4-12`で、前後が英数字や`-`に続かないもの)のうち、そのボリュームで別名を持つものを別名に替え、書くときは別名を元のUUIDに戻す。UUIDの文字列と別名の文字列は同じ36文字なので、レコードの大きさ(`ob_lst_rec`の戻り値)とオフセットは変わらない。オフセット付きの読込みは、前後に36文字ずつ多く読んで入れ替えてから求められた所を返すので、読む範囲がUUIDの途中で始まっても終わっても、別名の文字列が返る。戻すのは別名のマークを持つものだけで、今のシステムと重ならない元のUUIDはそのまま書く。オフセット付きの書込みがUUIDの文字列の途中で切れているときは戻せないので、プログラムはレコードを丸ごと書く(`ob_rpl_rec`、またはオフセット0から全部)。16バイトのUUIDをバイナリで持つ記録の形は、今は無い。
- 取り外したあと: ボリュームを取り外す(または媒体が抜かれる)と、別名の表は無くなり、別名で引くことはできなくなる。別名は元のUUIDに戻して今のシステムを探すことはしないので、別名の仮身は、今のシステムの実身には届かず、虚身になる。媒体が抜かれたときの`OB_E_DETACH`と属性だけのキーを閉じる処理(`knl_obfile_revoke`)も、別名で行う。以前は元のUUIDで送っていたので、同じUUIDの今のシステムの実身を監視するキーまで閉じていた。
- 一覧: 全部の実身の一覧(`ob_lst_obj`)は、別のマシンのボリュームの、別名を持つ実身を出さない。一覧はこのマシンの実身の整理(屑実身、名前で探すことなど)に使うためである。
- 移動、複製: 別名の仮身を今のシステムの記録へ移すとき(仮身の移動、複製でコピーする記録)は、保存のときに`om_link_fix`が、行き先が別のボリュームの実身なので「別のマシンのボリュームのUUID/別名」のプレフィックス付きに直す。別名は、元のUUIDのように今のシステムの実身を指すことがないので、別名のまま書く。そのボリュームが取り付けられていれば別のマシンの実身を開き、無ければ虚身になる。実身を複製(`om_copy`)して今のシステムのボリュームに作るときは、新しい実身は新しいUUIDになる(今と同じ)。

テストは`tests/ktest/ktest_vols.c`の`test_foreign`と`test_alias`で、VOLC1に今のシステムの系の箱、一時の箱、初期ウインドウ、機器の設定と同じUUIDの実身を作って別のマシンのシステムのボリュームにし、フラグ、探す順、`knl_obfile_on`、一時の箱を空にしないこと、切り離せること、別名の文字列が同じ長さで入れ替わること(途中で切れた読込み、レコードの大きさ、書込みで元のUUIDに戻ること)、別名で実身を作れないこと、取り外したあとに別名が引けないことを確認する。

## 7.7 区画の作成と拡張

TSFSの区画とボリュームは、後ろに空き領域があれば、作った後で広げられる。カードに書いたイメージの区画はイメージの大きさしかないので、システムボリュームは起動時に広げる。ディスク操作の〈区画作成〉と〈拡張〉(11.26)も同じ処理を使う。区画表(GPT)を書くのは`peripheral_kernel/sysman/gpt.c`、TSFSの区画とボリュームをまとめて扱うのは`peripheral_kernel/fs/tsfspart.c`、ボリュームを広げるのは`peripheral_kernel/fs/tsfsblk.c`である(`include/ts/gpt.h`)。

### 区画表の読み書き

区画表はディスク全体のデバイス(`sda`、`uda`など)から読む。プライマリのヘッダ(セクタ1)とその区画表の項目をCRCで確認し、合わなければディスクの最後のセクタにあるバックアップのヘッダと項目を使う。どちらも合わないディスクには書かない。先頭の2セクタが0のディスクは区画表の無いディスクとし、区画を作るときに保護MBRと128項目の区画表を新しく作る。MBRのディスクは扱わない。

空き領域は、どの区画にも使われていない範囲を1MB単位に切りそろえて数える。ディスクの終わりは、バックアップの区画表をディスクの最後の33セクタに置いたときの位置とする。イメージを書いたカードではバックアップの区画表がイメージの終わり、つまりカードの途中にあるが、そこも空き領域に含め、最初に区画表を書くときにカードの終わりへ移す。元のバックアップはそのまま残り、後で区画を広げたり作ったりしたときに上書きされる。

区画表を書くときは、毎回、プライマリとバックアップの両方を書き、CRCを計算し直す。順番は次のとおりで、それぞれを書いた後でデバイスのキャッシュをフラッシュする(`TDN_FLUSH`)。

1. バックアップの区画表の項目をディスクの終わりに書き、続けてバックアップのヘッダを最後のセクタに書く。
2. プライマリの区画表の項目を書き、続けてプライマリのヘッダをセクタ1に書く。
3. 保護MBRの大きさがディスクより小さければ直す。

電源が切れたときの扱いは次のとおりである。1の途中で切れたなら、プライマリのヘッダとその項目は元のままで、元のバックアップも元の場所に残るので、元の区画表として読める。2で項目を書き終えてヘッダを書く前に切れると、プライマリのヘッダのCRCが項目と合わなくなる。CRCを確認する読み手(`gpt.c`、ほかのOS)は、1で書いたバックアップ、つまり新しい区画表を使う。ドライバが区画を数える処理(`part.c`)はCRCを見ずにプライマリのヘッダが指す項目を読むので、やはり新しい区画表になる。どの場合も、読めるのは元の区画表か新しい区画表のどちらかで、両者が混ざることはない。

新しい区画は、使われている最後の項目の次の項目に置く。区画の番号(サブユニット、`sda1`の1)は使われている項目の順で決まるので、すでにある区画の番号は変わらない。

書いた後は、ディスク全体のデバイスに属性`TDN_PARTSCAN`を書き込む。SD、virtio-blk、USBのディスクのドライバは区画表を読み直し(`knl_part_rescan`)、すでにある区画の開始位置が変わっていないことを確認してから大きさを更新し、新しい区画を後ろに足し、サブユニットの数を変えてデバイスを登録し直す(`tk_def_dev`)。開いている区画はそのまま使い続けられる。開始位置の変わった区画や無くなった区画があれば、読み直しは何も変えずに`E_OBJ`を返す。最後に`knl_obdev_changed`でデバイスの一覧に変化を通知する。

### ボリュームの拡張

ボリュームを広げても、ジャーナルの大きさとアロケーショングループの大きさは作ったときのままにする。最後のグループをグループの大きさまで(新しい終わりがそれより手前ならそこまで)伸ばし、その後ろにグループを足す。最後のグループが64ブロック(`AG_MIN_TAIL`)より短くなるときにグループにしない規則は変えない。スーパーブロックの総ブロック数、グループの数、空きブロック数を新しい値にする。

こうして広げたボリュームのグループの配置は、総ブロック数から決まる配置(`layout()`)とは異なる。そこでスーパーブロックの互換の機能に`GROWN`(compatのビット0)を立てる。カーネルはもともとグループの配置をスーパーブロックの値から求めるので、カーネルの側に変える所はない。ホストの検査(`tools/tsfs_py/check.py`)は、`GROWN`のあるボリュームについては、グループの大きさが2の累乗で範囲内であることと、ジャーナルとグループの大きさから求めたグループの数が一致することを確認し、`layout()`との違いを警告しない。

グループの大きさが32768ブロックを超えると、最後のグループを伸ばしたときに空きブロックのビットマップのブロックが増えることがある。増えるブロックは最後のグループのデータ領域なので、そこが使われていれば広げずに`E_LIMIT`を返す。

ボリュームは使用中のまま広げられる(`ts_grow_vol_blk`)。まずジャーナルを止める(`knl_jrnl_freeze`)。実行中のトランザクションが終わるのを5秒まで待ち、確定したものをすべて本来の位置に書き、それ以降は新しいトランザクションを始めさせない。ジャーナルに残ったグループのヘッダやスーパーブロックの古いコピーが拡張の後に再生され、広げた内容が元に戻るのを防ぐためである。その後、ボリュームのロックを持ったまま、次の順に書く。

1. スーパーブロック。非互換の機能`GROWING`(incompatのビット0)を立て、広げる先の総ブロック数を416バイト目(`grow_to`)に書く。
2. 足すグループのそれぞれについて、空きブロックのビットマップ、続けてグループのヘッダ。すべて元のボリュームの終わりより後ろにある。
3. 最後のグループのビットマップ、続けてヘッダ。
4. すべてのバックアップのスーパーブロック。新しい大きさで書く。
5. 新しい大きさと`GROWN`を持ち、`GROWING`を外したスーパーブロック。続けてもう一方のコピーにも書く。

5が媒体に届くまでは、開いたときに読むスーパーブロックは1のものである。`GROWING`のあるボリュームを開くと(`ts_opn_vol_blk`)、カーネルは2から5をやり直して拡張を終える(コンソールに`tsfs: デバイス名: a grow cut short finished, ブロック数 blocks`)。最後のグループのヘッダは新旧どちらが書かれているかわからないので、開くときには確認しない。最後のグループのビットマップはCRCを確認せずに読み、元のグループの範囲のビットだけを使って作り直す。元の範囲のビットは、増えるビットマップのブロックに当たるビット(拡張の前は空き、後は使用中)を除いて新旧で同じなので、どちらが読めても同じものができる。1が媒体に届く前に切れたときは、元のボリュームのままである。`GROWING`を知らないカーネルはこのボリュームを開かない。ホストの検査は、`GROWING`のあるボリュームについて、拡張が途中で切れたことを警告する。

広げた後は、グループの表を新しく作り直す。データの読み書きの一部はロックを取らずにグループの表を読むので、古い表はボリュームを閉じるまで残す。

2の書込みをデバイスが拒否したときは、拡張をやめる。2が書くのは元の終わりより後ろのブロックだけで、ボリュームのどこからも指されていないので、ボリュームは元の大きさのまま書ける。スーパーブロックから`GROWING`と`grow_to`を外して書き、次に開くときにやり直さない。次の起動(システムボリューム)か次の〈拡張〉で、区画の大きさまで広げ直す。3から5の書込みが拒否されたときは、ボリュームの中のグループとスーパーブロックに触れているので、これまでどおりエラーを記録し、検査まで読取り専用にする。どちらのときも、拒否されたブロックとデバイスの応答をコンソールに出す(`tsfs: デバイス名: the grow could not write block ブロック (エラー)`)。記録するエラーのブロックも、拒否されたブロックである(以前は最初のグループの位置を記録していた)。

以前は2の失敗もエラーとして記録していたので、拡張のための1回の書込みの失敗で、システムボリュームが読取り専用になり、設定がすべて保存できなくなった(2026年10月、ThinkPad X1 Yoga 第3世代、USBのカードリーダのSDカードから起動したとき。エラーのブロック770は最初のグループの位置で、失敗したブロックではなかった)。QEMUでは、USBのディスクの、新しいグループのビットマップに当たるセクタへの書込みが失敗するようにし(`blkdebug`)、以前はエラーの記録と読取り専用になること、今は拡張をやめて元の大きさで使い続け、次の起動で広げ直せることを確認した。

USBの大容量記憶のドライバは、失敗した読み書きを、ディスクごとに最初の16回まで、コマンドの状態とセンスデータ(キー、ASC、ASCQ)とともにコンソールに出す(`usb: uda: write of 8 blocks at 1513528 failed: status 1, sense 0b/00/06, 4096 bytes moved`)。失敗の数は`USB.TXT`にも出る。SYNCHRONIZE CACHEを拒否するデバイスは、そのことを1回だけ出す。起動のときの`sysvol:`の行は、区画表の区画の範囲、区画のデバイスのブロック数を出し、ボリュームを広げる前にはその大きさと状態を出す。

### 区画とボリュームの順

区画とボリュームをまとめて広げるときは(`knl_tsfs_part_grow`)、区画表を先に、ボリュームを後に広げる。区画がボリュームより大きくても使っていない領域ができるだけだが、ボリュームが区画より大きいと開けないためである。区画を広げた後、ボリュームを広げる前に電源が切れると、区画だけが大きいボリュームが残る。区画がボリュームより1MB以上大きいときは、次の起動(システムボリューム)か次の〈拡張〉で、ボリュームを区画の大きさまで広げる。

区画を作るときは(`knl_tsfs_part_make`)、区画表に区画を足してから、その区画にボリュームを作る(`ts_format_blk`)。区画の大きさは1MB単位で、4MB以上(TSFSの最小のボリューム)でなければならない。

### システムボリュームの自動拡張

起動時、システムボリュームを取り付ける前に(`knl_sysvol_grow`、`peripheral_kernel/obj/obname.c`)、次の条件をすべて満たせば区画とボリュームを広げる。

- 区画がTSFSの型である。
- ディスクの最後の区画で、後ろに空き領域がある。
- 区画が`CNF_SYSVOL_GROW_MB`(8192MB、`config/config.h`)より小さい。

広げる先は8GBと、ディスクの終わり(バックアップの区画表の分を残し、1MB単位に切り下げた位置)の小さいほうである。広げたかどうかをコンソールに1行で出す。広げたときは`sysvol: grown 2048 MB -> 8192 MB`、広げなかったときは`sysvol: 2048 MB, not grown (理由)`で、理由は`at its limit`(すでに上限)、`not the last partition`(後ろに区画がある)、`no room after it`(後ろに空きがない)、`not a TSFS partition`である。条件を満たさなくても、区画がボリュームより大きければボリュームだけを広げる。

Raspberry Pi 5と4のカードのイメージ(`tools/mksd.py`)は、区画2がシステムボリュームで、最後の区画である。カーネル内のテストのイメージ(`KTEST=1`)は後ろに作業用の区画3があるので、広げない。2GBから8GBに広げるときに書くブロックは、足す24個のグループのヘッダとビットマップ、バックアップのスーパーブロックなど百ほどのブロックで、時間はかからない。

### テスト

`tests/ktest/ktest_grow.c`(スイート`grow`)は、`tools/tests/mkvoldisk.py`が作る96MBの空のUSBのディスク(`volg.img`)をQMPを通してハブに挿す。前の実行が残したものを消すため、先頭と末尾のセクタを0にしてから挿し直す。

- `test_fresh`: 区画表の無いディスクの空き領域が1つであること。そこに16MBのTSFSの区画を作ると、プライマリとバックアップの区画表がどちらもCRCを満たし、バックアップがディスクの終わりにあり、区画にラベルの付いたボリュームがあること。
- `test_image`: 36MBのイメージを書いたカードと同じくバックアップをディスクの途中に置いた区画表を書き、区画に実身を書いてから、区画とボリュームを48MBに広げる。バックアップがディスクの終わりに移ること、デバイスとボリュームが48MBになること、検査(`ob_chk_run`)で障害が無いこと、実身を読み返せること、元のボリュームより大きい20MBの実身を書けること。
- `test_live`: ボリュームを開いたまま64MBに広げ、開いているボリュームの大きさが変わり、続けて書けること。空きの無い所でもう一度広げると`E_LIMIT`になること。
- `test_cut_volume`: 8MBのボリュームを24MBに広げる書込みの数を数え、1つ目から最後までの各書込みの後で、電源が切れたことにする(`ts_cut_blk`)。開き直したボリュームが元の大きさか新しい大きさで、異常の記録も`GROWING`も無く、実身を読み返せ、4MBの実身を書け、検査で障害が無いこと。
- `test_cut_table`: バックアップがディスクの途中にある区画表で区画を広げる書込みの数を数え(5回)、そのそれぞれの後で電源が切れたことにする(`knl_gpt_cut`)。CRCを満たす区画表が必ずあり、区画の終わりが元か新しいかのどちらかであること。元のままの場合と広がった場合の両方が現れること。
- `test_sysvol`: 起動時のシステムボリュームの拡張の結果が、区画の大きさと合っていること。
- `test_out`: ディスクを抜く。

`make TARGET=_QEMU_VIRT_ KTEST=1 KTONLY=grow BUILD_ID=<名前> test`で実行する。起動時の自動拡張は、`TEST_DISK_MB=384 TEST_DISK_ROOM=96`を付けてテスト用ディスクを作り直すと確認できる。`tools/mkdisk.py --sys-room N`が、区画表をディスクの終わりのN MB手前で終わらせ(イメージを書いたカードと同じくバックアップがディスクの途中に来る)、システムボリュームの区画3を最後に置くので、起動時に`sysvol: grown 144 MB -> 240 MB`となる。その後`python3 tools/fsck.tsfs --partition 3 <テスト用ディスク>`で、広げたボリュームに障害が無いことを確認する。

ホストのツールでは、`tools/tests/test_tsfs_py.py`の`TestGrow`が、`Volume.grow`(カーネルと同じ手順で広げる)で広げたボリュームを検査して障害も警告も無いこと、`GROWN`を外すと配置の警告が出ること、`GROWING`を立てると途中で切れた警告が出ることを確認する。

## 7.8 システムボリュームの暗号化(未実装、将来の検討)

システムボリュームの暗号化は実装していない。実装するかどうかも決めていない。この節は将来検討するときのための設計の案で、ここに書いたものはどれもTessronOSにはまだ無い。実装するときは、まず末尾の表の方針を決める。

### 守るものと守らないもの

電源の切れたディスクやカードを持ち去られたときに、利用者の実身と設定を読まれないようにする。起動中のマシンへの攻撃、メモリの読取り、ブートパーティションの改ざん(カーネルをすり替えてパスワードを盗む)は守らない。ESPとRaspberry Piの第1パーティションは暗号化できず(ファームウェアが読む)、カーネルはここに平文で置くので、改ざんを防ぐにはセキュアブートが要る。今のローダはセキュアブートに対応していない。

### レイヤ構成

TSFSとディスクの間に、暗号化デバイス(`crypt`のレイヤ)を置く。ディスクの区画`nvmeaN`に対して、復号した内容を見せるブロックデバイスを登録し、TSFSはこちらをマウントする(`ob_att_vol`)。TSFSとジャーナル(7.3)は暗号化を意識しない。カーネルの中で行い、復号の前後を別のページに持つ。読むときはDMAのあと同じバッファの上で復号でき、書くときは平文のバッファを壊さないよう別のページに暗号化してから渡す。TSFSのブロック(4KB)ごとに、ブロック番号をIVにする。ブロックより小さいセクタの部分書込みの扱いが要らないので、電源断の性質はTSFSの今の前提(ブロックの書込みが途中で切れてもCRCで分かる)から変わらない。

暗号はAES-256-XTSを既定にする(x64のAES-NI、Pi 5のCortex-A76の暗号拡張)。Pi 4、Pi 400のCortex-A72(BCM2711)には暗号拡張が無いので、AESはソフトウェアで遅い。暗号拡張の無いCPU向けの選択肢としてAdiantumがある(下の表の2)。乱数はx64のRDRANDとUEFIの種、PiのRNGブロックを既存の`knl_rng`から取る。

カーネルは今、Mbed TLSの全体を`WIFI=1`(`WPA_MODE=kernel`、既定)のときだけリンクし、それ以外ではBluetoothのペアリング(6.8)のためのAES、bignum、ECPの部分(`build_make/sources.mk`の`SRCS_BT`)だけをリンクしている。暗号化では、AESの部分(AES-NIと暗号拡張の命令を含む)とSHA-512、Argon2idを小さく取り込むか、Mbed TLSの該当のファイルをカーネルのビルドに常に入れる。

### 鍵の持ち方

区画の先頭にヘッダを置き、そのブロック(と末尾の予備)にマスター鍵を暗号化して持つ。マスター鍵は乱数で作り、パスワードはArgon2idで作った鍵でこれを包む。パスワードの変更は包み直すだけで、全体を暗号化し直さない。ヘッダには複数のスロットを持ち、回復用の鍵(登録のときに表示して控えてもらう)を別のスロットに入れる。マスター鍵はカーネルのメモリにだけ置き、スリープ(3.10.11)の間も持つ。電源を切るときと再起動で消す。プロセスからは読めない。

### 起動時のパスワード入力

カーネルの`devinit`の、起動ディスクを見つけた直後に尋ねるのが、x64とPiで同じコードになる。画面はカーネルのコンソール(fbcon)で、キーはUSBのHIDとI2CのHIDとシリアルのドライバが上がった後なので、この段階では`ts_hid_read`がまだ使えない機種がある(BluetoothキーボードやSurfaceのキーボードカバーの準備は遅い)。この段階でのキー入力の経路を作る必要がある。日本語の配列を考えて、英数字だけを受け付ける。かな漢字変換は無い。

x64ではUEFIのローダがブートサービスの間にConInで尋ねる方法もある。ファームウェアのキーボードのドライバが使えるので確実で、外付けのキーボードも内蔵も動く。ただしPiでは使えず、コードが2つになる。

### 起動とシステム登録との関係

- 起動の流れ: x64はローダがカーネルをESPから読み、カーネルが尋ねて、システムボリュームを開く(3.10.1)。Piはファームウェアが第1パーティションからカーネルを読み、カーネルが尋ねる(3.2)。
- システム登録(`application/sysinst`、11.32、3.10.10): 〈暗号化する〉の選択を足し、パスワードを部品の入力欄で受ける。コピーのときに区画にヘッダを作り、ボリュームを暗号化しながらコピーする。今の登録は「読み返し」と「ボリュームの拡張」を行うので、どちらも復号した側のデバイスに対して行う。回復用の鍵はパネルに表示する。
- 区画の拡張(7.7)は復号した側のデバイスの大きさが広がる形にする。ヘッダの予備を末尾に置くと、拡張で移す必要がある。
- ディスク修復(11.25、7.5)はパスワードが通ってからでなければ動かない。
- システムのバージョンアップ(.tpk)はカーネルとローダとシステムの実身を替えるので、ヘッダの形式はこのバージョンをまたいで読める必要がある。
- 記録の区画`TSLOG`(FAT)とESPの`bootlog`には起動の記録が平文で残る。実身の名前が記録に出ないことを確認する。
