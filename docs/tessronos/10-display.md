# 第10章　表示とウインドウ

## 10.1 構成

画面まわりは外核の3つの管理機能からなる。描画管理`dp_`、フォント管理`fn_`、ウインドウマネージャ`wm_`である。いずれもEL1で、呼び出したプログラムのコンテキストで実行される。ただし画面の組み立てだけは、ウインドウマネージャの合成タスクが行う(10.4.4)。プロセスからはSVCクラス8と9、それにウインドウの実身の操作(クラス7)で使う。

```text
 プロセス             ウインドウの実身(ob_) / dp_ / wm_・mn_・kc_ のSVC
 ───────────────────────────────────────────
 ウインドウマネージャ  ウインドウ、枠、合成、部品、パネル、メニュー、データボックス、
                      外観設定テーブル、ポインタ、メッセージ行、トレー
 描画管理 dp_        描画環境、塗りつぶし、線、図形、領域、ピクセル転送
 フォント管理 fn_     FreeType。グリフを生成し、描画環境に描く
 画面ドライバ         オフスクリーンバッファとディスプレイへの転送
```

## 10.2 描画

描画はすべて描画環境(番号`gid`)に対して行う。描画環境は、描画先のピクセル、座標の原点、描画可能な範囲(フレームとクリッピング領域)、色、描画モード(上書き、排他的論理和、論理積)を持つ。ウインドウはそれぞれ専用の描画環境とピクセルバッファを持つので、ほかのウインドウに覆われても内容は失われない。

| 分類 | 主な関数 |
| --- | --- |
| 塗りつぶしと線 | `dp_fill_rect`、`dp_frame_rect`、`dp_line`、`dp_line_wide` |
| 図形 | `dp_fill_poly`、`dp_draw_poly`、`dp_fill_round`、`dp_frame_round`、楕円、扇形、弓形、円弧、シード塗りつぶし |
| 領域 | `dp_rgn_*`。行ごとの区間で表した領域 |
| ピクセル | `dp_put_argb`、`dp_get_argb`、`dp_put_mono`、`dp_put_gray` |
| パターン | 2色の網掛け(8段階)か、タイルと透過マスク。図形の`<pattern>`が`masks`で名指すマスクは、その図形の`<mask>`の定義を使い、なければTADの標準のマスク(0〜13番。4×4の模様で、1〜7番は0%から100%までの網、8〜13番は縦線、横線、2方向の斜線、2種の格子)を使う(`outer_kernel/tad/tad_view.c`) |

画像はPNG、JPEG、BMP、GIF、ICOをデコードでき、PNGへのエンコードもできる(`img_`)。

画面そのものは実身「画面」である(8.4)。解像度、色深度、選択できる解像度はそのレコード1で読み、解像度の変更はそこに書く。デスクトップが起動時に機器の設定の解像度にするときも、システム環境設定から再起動せずに解像度を変えるときも、システム環境設定が解像度を表示するときも、この実身を通す(10.2.2)。描画管理とウインドウマネージャは画面ドライバの関数を直接使う。

描画環境は、描いた範囲を通知できる(`dp_set_watch`)。通知する設定にした描画環境が後で画面に重ねるピクセル(ウインドウのピクセル)に描くと、描画管理は描いた矩形を、描画可能な範囲で切った画面座標で、`dp_watch`で登録された1つの関数に渡す。ウインドウマネージャは、すべてのウインドウの描画環境と枠を描く描画環境をこの設定にし、渡された矩形を次の組み立てに加える(10.4.4)。プログラムは`wm_damage`で損傷を通知しなくても、描いた部分が次の`wm_update`で画面に出る。関数は描画管理のロックを持たずに呼ぶ。

画面ドライバ(`device/disp/disp.c`)は、バックバッファのうち変化した部分を`ts_disp_damage`で受け取り、最大16個の別々の矩形として覚えておき、保留(`ts_disp_hold`)が解けたときに矩形ごとにフレームバッファへ送る。重なるか近い2つの矩形は、両方を囲む矩形が2つの面積の和より4096画素以上大きくならなければ1つにまとめる。それより離れていれば、間の画素を送るより別々に送るほうが安い。左上で点滅するキャレットと右下の時計は、画面全体ではなく2つの小さな矩形として送られる。16個を超えたときは、新しい矩形を、まとめたときに増える面積が最も小さい矩形にまとめる。`ts_disp_stat`は、送った回数、矩形の数、行数、画素数、送りにかかった時間の合計、面を切り替えた回数、切り替えが効くのを待った回数とその時間の合計を返す。フレームバッファが2面を持てる画面では、送りは表示していない面に書き、書き終えてからその面を表示させる(10.2.1)。

プロセスは、自分が作成したウインドウの描画環境(`wm_obj_gid`で取得する)にだけ、次の関数で描画できる。

`wm_obj_gid`は、描画環境の番号を渡したことを許可の表(`svc_gate.c`の`grants`)に記録し、描画の関数は呼ばれるたびにこの表で確かめる。表は、プロセスが開いたメモリの描画環境の表と同じミューテックス(`draw_mtx`)の中で読み書きする。起動のときにデスクトップが開く原紙箱と「TADjsについて」のように、別々のコアのプロセスが同時にウインドウを開くことがあるためである。以前は表に排他がなく、二つのプロセスが同じ空きの行に書くと、片方の記録が消えた。そのプロセスの描画はすべて`E_ID`で断られ、`wm_obj_flush`は通るので、ウインドウは「描いた」ことになったまま作業領域が白いままだった。閉じて開き直すと記録し直すので描かれる。

| 関数 | 機能 |
| --- | --- |
| `dp_fill_rect`、`dp_frame_rect`、`dp_line` | 塗りつぶし、枠、線 |
| `dp_put_argb` | ピクセルを書き込む |
| `dp_text`、`dp_text_width` | システムフォントで文字列を描く、幅を求める |
| `dp_draw_tad` | xmlTADを描く |
| `dp_img_decode` | 画像をデコードする |
| `wm_obj_flush` | 描画した内容を画面に反映する |
| `wm_obj_surf`、`wm_obj_put` | 作業領域の面をプロセスの空間にマッピングして得る、面に描いた矩形をウインドウに置いて画面に反映する |

自分で画素を作るプログラム(ブラウザなど)は、描画環境を通さずに作業領域の面(`wm_obj_surf`)に直接描く。面はウインドウごとにカーネルが持つページで、作業領域と同じ幅と高さの画素(1行は幅×4バイト)を持ち、呼んだプロセスの共有メモリ領域(5.3)の新しいアドレスに、読み書きできるようにマッピングする。ページは仮想アドレスだけが連続した領域(`knl_vmap`)なので、1ページずつ物理アドレスを引いてマッピングする(`knl_prc_map_kernel`)。ページはマッピングする前に0で埋める。プロセスは面に描いたあと、変わった矩形(作業領域の座標で最大16個)を`wm_obj_put`で渡す。カーネルは、ウインドウマネージャのロックを持ったままそれらの矩形を面からウインドウのピクセルへ行ごとにコピーし、描画環境で描いた矩形と同じくそのタスクが描いた矩形として記録して、`wm_update`と同じように組み立てを依頼し、終わるまで待つ。

ウインドウのピクセルそのものをプロセスにマッピングしないのは、二つの理由による。合成タスクは組み立てのたびにウインドウのピクセルを読むので、プロセスが直接描くと、ページを塗りつぶして文字をまだ描いていない状態が、ほかの理由で起きた組み立てによって画面に出る。また、ウインドウのピクセルには枠とタイトルバーも含まれるので、プロセスがそれを書き換えられてしまう。面はダブルバッファの裏側に当たり、表側であるウインドウのピクセルへは変わった矩形だけをコピーする。コピーするのはウインドウマネージャのロックの中で、合成タスクは組み立ての間このロックを持っているので、組み立てがコピーしかけのピクセルを読むことはない。コピーする量は変わった矩形の分だけで、`dp_put_argb`のように画素ごとに描画モードと透過色を調べることもない。面の画素の上位バイトは、透過色を使うウインドウ(ポップアップ)では0xFFが透過を表し、ほかのウインドウでは使わない。

ウインドウが持つ面は1つで、最後に求めたプロセスのものである。同じプロセスが同じ大きさのうちに求めると同じ面を返す。ウインドウの大きさが変わっても面はそのまま残り、`wm_obj_put`は面と作業領域の両方に収まる範囲だけをコピーする。プロセスが改めて`wm_obj_surf`を呼ぶと、新しい大きさの面を新しいアドレスに作り、古い面を手放す。手放すときは、先にプロセスの古いアドレスの各ページを何もないページ(書き込みが捨てられるページ。`knl_prc_sink_shared`)に置き換えてTLBを無効にし、そのあとでページを解放する。ウインドウが閉じたとき(`wm_close`)と、プロセスが終了したとき(`knl_wmobj_prc_end`が呼ぶ`knl_wm_surf_prc_end`。自分が作ったのではないウインドウの面も含む)も、同じ順で手放す。プロセスがまだ古いアドレスに描いていても例外にはならず、書き込みは捨てられ、次の`wm_obj_put`は`E_OBJ`か`E_ID`を返す。面のアドレスは共有メモリ領域に返さない(メモリの実身のアドレスだけを返して使い直す、8.3)ので、終了したプロセスの番号を受け継いだプロセスに古いアドレスのページが見えることはない。

プロセスが終わると(`knl_wmobj_prc_end`)、そのプロセスが作ったウインドウを閉じる。そのウインドウに置いたパネルとメニューも一緒に閉じ(`knl_pn_wins_gone`)、プロセスが単独で作ったパネル、メニュー、部品(`ui_open`のパネルなど。作ったプロセスを`WOFREE`の`maker`に持つ)も消す。プログラムは終わる前に自分で閉じて消すのが普通だが、障害や`ts_ter_prc`で止められたとき、ウインドウを出したままのスレッドが残っている間にプロセスが終わったときは、それができない。消さないと、パネルと部品が画面とウインドウの一覧(`ob_lst_obj`)に残り、単独のパネルの席(`WO_FREE_MAX`の64)も減ったままになる。テスト:ktest_v8の`test_blink_settings`の最後(設定のウインドウを出したままブラウザを終わらせ、ウインドウの数が戻ることを確かめる)。

カーネル試験の`prcobj`の組の`test_surf`は、`tests/uprog/svcprog.c`の`SP_SURF`を使って、プロセスが面に描いて置いた色が画面に出ること、同じ大きさのうちは同じ面が返ること、誤った引数(矩形の数、カーネルのアドレス、読出し専用のアドレス)を拒むこと、ウインドウを大きくして求め直すと新しい面が別のアドレスに大きく作られ、古いアドレスがもうそのページを指さないこと、ウインドウを閉じると面のページが解放され、プロセスがなお面に書いても例外にならず`wm_obj_put`を拒まれること、描き続けるプロセスを終了させると面が残らないことを確かめる。ブラウザでの効果は14.7.1で述べる。

### 10.2.1 画面の2面の切り替え

フレームバッファが画面2枚分の行を持ち、どちらを表示するかを画面に指示できるときは、画面ドライバは2面を切り替えて使う(ページフリップ)。送る矩形は表示していない面(裏の面)に書き、すべて書き終えてから裏の面を表示させる。送りかけの面が画面に出ることはない。裏の面は1回前の送りの時点の内容なので、送りのたびに、今回の矩形に前回の矩形を加えて(4096画素の規則で近いものを1つにまとめながら)バックバッファからコピーする。前回の矩形は前回表示させた面にだけ書いてあり、もう一方の面にはないからである。バックバッファには両方の最新の内容がある。

面の切り替えは画面の次の更新から効き、それまでは前に表示していた面が読み出され続ける。そのため、次の送りでその面に書く前に、前回の切り替えが確実に効いたことを確かめる。切り替えから更新1回分の時間が過ぎていれば待たない。過ぎていなければ、垂直帰線を待てる画面では切り替えの後に始まった帰線が終わるまで、待てない画面では切り替えから更新1回分の時間が過ぎるまで待つ。待つのは画面ドライバのロックを持った送りの中で、ウインドウマネージャのロックはすでに放している。どちらかの待ちがある画面では送りが1更新に1回に揃うので、合成タスクは自分では間隔を取らない(10.4.4)。

画面が更新の周期と、最後に帰線の終わりを見た時刻を返せるハードウェア(`T_DISPHW`の`frame_ns`、`blank_ns`、`blank_seen`)では、帰線を時計として使う。最後に見た帰線の終わりから周期ずつ数えて、前の切り替えの後に始まる最初の帰線の終わりを求める。切り替えが帰線の始まりの200マイクロ秒前(`DISP_GUARD_US`)より後なら、その帰線では効かないとみなして次の帰線にする。送りがその時刻を300マイクロ秒(`DISP_BLANK_SLOP_US`)過ぎてから来たときは、切り替えはもう効いているので待たない。画面だけを見て待つと、切り替えのときの値から数えるので、すでに過ぎた帰線は数えられず、次の帰線まで更新1回分余計に待つことになる。時刻より前に来たときは、帰線の始まりの1ミリ秒前(`DISP_WAKE_US`)まで眠り(`tk_dly_tsk_u`)、そこから画面を見て帰線を待つ。帰線を待つたびに見た帰線の終わりで時計を合わせ直すので、時計はずれない。最後に帰線を見てから1秒を過ぎたときは時計を使わず、画面だけを見て待つ。送りが時計で求めた時刻と300マイクロ秒より離れた帰線で終わったときは、時計が外れたものとして数える(10.4.5の`off`)。QEMUの画面には帰線がないので、試験は`knl_disp_sim_blank`で疑似的な更新(周期の1/20の帰線が周期ごとに終わる)を与え、同じ処理を確かめる。

`ts_disp_flip`で切り替えを使うかどうかを変えられる。使い始めるときは、裏の面に画面全体が欠けているものとして、次の送りで画面全体をコピーする。やめるときは、最後に表示させた面に以後の送りを書く。`ts_disp_ref`は、面の数(`fb_pages`)、表示している面(`fb_shown`)、切り替えを使っているか(`flipping`)を返す。解像度を変えると新しい大きさの最初の面を表示し、2面を使い続けられるときは次の送りで裏の面に画面全体をコピーする。機種に依存する層(`T_DISPHW`)は、面の数、面を切り替える関数、垂直帰線を待つ関数(なければ`NULL`)、垂直帰線を待たないときに切り替えが効いたとみなすまでの時間(`latch_us`)、起動時から切り替えを使うかを渡す。

| 機種 | 2面の取り方と切り替え | 起動時 |
| --- | --- | --- |
| Raspberry Pi 5 | メールボックスで仮想の大きさを高さの2倍にしたフレームバッファを求め(`SET_VIRTUAL_WH` 0x00048004)、仮想のオフセット(`SET_VIRTUAL_OFFSET` 0x00048009)の行で表示する面を指示する | 起動時の確認に通れば使う |
| Raspberry Pi 4系 | 1面のまま | 使わない |
| QEMU | `bochs-display`のモードは仮想の高さを2倍にしてあり、Yのオフセットのレジスタで表示する面を指示する。切り替えはすぐに効く | 使わない。試験(`ktest_disp`の`test_flip`と`test_blank`、`ktest_wm`の`test_pace`)だけが使う |

Raspberry Pi 5では、ファームウェアが起動前に用意して`simple-framebuffer`のノードで通知するフレームバッファは1面なので、そのノードの大きさで2面のフレームバッファをメールボックスで求め直し、ノードのバッファは使わなくなる(ノードがないときも2面で求める)。求める前に、バッファを確保しない問い合わせ(`TEST_VIRTUAL_WH` 0x00044004)で2面をくれるかを尋ねるが、その答えは記録に出すだけで、答えが2面に足りなくてもバッファを求める。Raspberry Pi 5のファームウェアは、`config.txt`で上限(`max_framebuffer_width`、`max_framebuffer_height`)を広げても、この問い合わせに今の画面の大きさを答えた。何面をくれるかは、実際に求めたバッファの仮想の大きさで判断する。Raspberry Pi 5のファームウェアは、2面を求めると仮想の高さを2倍と答えるが、新しいバッファは確保せず、起動時からの1面のバッファ(ノードと同じアドレス)をそのまま返し、確保した大きさも1面分と答える。2面目はそのバッファの直後の行から表示されるので、`CNF_DISP_FLIP`のときはページの割当て(`pfalloc.c`)が起動の初めに、ノードのバッファの直後の1面分も予約しておく。この範囲はファームウェアの領域ではなく、カーネルに渡された普通のメモリである。ただし実機(2026年10月3日)では、ファームウェアは表示の位置(`SET_VIRTUAL_OFFSET`)を2面目に変えたと答え、読み返しても2面目と答えたが、画面は1面目を表示したままで、起動時の照合が失敗した。メールボックスで答えた画素の並びも実際の表示には効いておらず、その並びで描くと赤と青が入れ替わった。そのため、Raspberry Pi 5の既定は`DISP_FLIP=0`(ノードの1面)とし、`make DISP_FLIP=1`で試せるだけにしている。試すときも、ファームウェアがノードと同じアドレスを返したら、画素の並びと不透明度の扱いはノードのものを使う。表示の位置を本当に切り替えるには、ファームウェアに任せず、表示のハードウェア(HVS)の表示リストを直接書き換える必要がある。`etc/boot/config.txt`は、4Kの画面の2面まで取れるように上限を3840×4320にしている。メールボックスで求めたバッファは、画素の並びが青を下位にし、最上位のバイトを不透明度として読まない設定(`SET_ALPHA_MODE`で無視)にする。ノードの形式`a8r8g8b8`では最上位のバイトを0xFFにするために1画素ずつ変換して送っていたが、この設定が通れば送りは行ごとのコピーになる。ファームウェアがくれたバッファがカーネルの使っているメモリにかかるなどして使えないときはノードに戻すが、そのときファームウェアはもうノードのバッファを表示していないかもしれない。そのような画面や、2面にすると表示が乱れる画面では、`make DISP_FLIP=0`(`CNF_DISP_FLIP`)でビルドすると、今までどおりノードの1面を使う。

Raspberry Pi 5の今の既定(`rpi5.mk`の`DISP_FLIP=1`)では、面の切り替えをファームウェアに頼まず、表示のハードウェア(HVS)の表示リストを直接書き換えて行う(`disp_rpi5.c`)。起動時にHVSのレジスタのアドレスウインドウから表示リストを探し、ノードのフレームバッファのアドレスを持つワード(実機では2つ)を見つける。2面目は、ページの割当て(`pfalloc.c`)が起動の初めに予約した1面分(`knl_fb_page2`)で、切り替えはそれらのワードに表示する面のアドレスを書くだけである。切り替えが効いたことは、フレームごとに変わるHVSのレジスタで確かめる。起動時に先頭の128ワードを120ミリ秒のあいだ休まずに読み続け、1フレームに1回(120ミリ秒で5〜9回)か2回(11〜17回)変わるワードを選ぶ。実機ではオフセット0x24のワードが1フレームに2回変わった。2回変わるワードは垂直帰線の間だけ別の値を持ち、その間は1080pで1ミリ秒に満たない。そのため垂直帰線を待つ処理も、起動時と同じく休まずに読み続ける。1ミリ秒眠りながら読むと帰線を読み飛ばし、2026年10月5日の実機では最初の待ちで40ミリ秒の上限を超えた。

ワードを選んだ後、さらに150ミリ秒までそのワードを読み続けて、変わった時刻を32回まで記録し、帰線の時計を作る(`hvs_clock_find`)。2回変わるワードでは、長く保つ方の値が帰線の外の値で、その値に変わった時刻が帰線の終わり、もう一方の値の続いた時間が帰線の長さである。1回変わるワードでは、変わった時刻をそのまま帰線の終わりとする。周期は最初と最後の帰線の終わりの間隔を回数で割った値で、どの終わりも最初の終わりから周期の整数倍の1/50以内に並び、周期が5〜50ミリ秒のときだけ時計を使う。ワードが2つより多くの値を取るとき、帰線の終わりが3回に満たないときも使わない。使えれば`hvs: clock: a frame every 〜 us (〜 ends of a blank timed), its blank 〜 us`を出し、切り替えが効いたとみなす時間を周期に1ミリ秒を足した値にする。帰線を待つ処理は、切り替えの後に始まった帰線の終わりを待つ。切り替えが帰線の中で行われたときは、その帰線の終わりは数えず、次の帰線の終わりまで待つ。見た帰線の終わりは時計に渡す。時計がある間は`disp.c`が帰線の1ミリ秒前まで眠らせるので、CPUを占めるのは帰線の前後の1ミリ秒余りだけである。時計が作れなかったときは、今までどおり切り替えのときの値から決まった回数変わるのを待ち、待つのは前の切り替えから更新1回分(17667マイクロ秒)以内に次の送りが来たときだけである。上限を超えたときは、その回は切り替えから17667マイクロ秒が過ぎるまで待つ。3回続けて上限を超えたときだけ、以後は垂直帰線を待たずに時間で待つ(`disp: flip: the wait for the vertical blank failed 3 times in a row`)。

面の切り替えと垂直帰線の待ちは1フレームごとにメールボックスを呼ぶので、`knl_mbox_property_wait`を使う。答えを500マイクロ秒まではそのまま待ち、過ぎると1ミリ秒ごとにタスクを眠らせて見る(上限100ミリ秒)。垂直帰線を待つ間、CPUを更新1回分占めないためである。

起動時の確認は2段からなる。まず`disp_rpi5.c`が、2つ目の面を表示させて表示の先頭の行をファームウェアから読み返し(`GET_VIRTUAL_OFFSET` 0x00040009)、1つ目の面に戻して同じく読み返す。読み返した行が違えば1面に戻す。続けて、垂直帰線まで答えを返さないタグ(0x0004800E)を7回続けて呼び、戻った時刻の間隔を測る。このタグはファームウェアのタグの一覧の文書には見当たらず、Pi 5のファームウェアで働くかは分かっていないので、起動時に測って決める。垂直帰線の割込みは使わない。表示のパイプライン(HVSと画素の出力)はファームウェアが動かしていて、その割込みもファームウェアが受けるからである。カーネルが受けるには、表示の経路を自分で動かすことになる。間隔の中央値が5〜50ミリ秒で、6つの間隔がどれも中央値の±25%に収まるときだけ垂直帰線を待てるものとし、切り替えが効いたとみなす時間を中央値の9/8にする。タグに答えがない、すぐに答える、間隔がそろわないときは使わず、60Hzの更新1回分に1ミリ秒を足した17667マイクロ秒を待つ。面を指示するタグそのものが2回とも4ミリ秒以上かかったときは、ファームウェアが垂直帰線まで待ってから答えているものとし、答えが返った時点で切り替えが効いたとする。

次に`disp.c`が、2面で送った結果を読み返して照合する(`flip_check`)。黒に見える暗い模様をバックバッファに描き、1面で画面全体を送って、表示している面が送ったとおりかを確かめる。次に2面に切り替え、1〜3個の矩形に新しい色を描いて送ることを8回繰り返し、各回で、その回と前の回の矩形の全画素と、無作為に選んだ4行の全画素を表示している面から読んで、送りが変換したバックバッファの値と比べる。最後に表示している面の全体を比べる。面はドライバのキャッシュしないマッピングから読むので、読む値は画面が読む値である。違う画素があれば1面に戻す。この照合で確かめられるのは、2面の大きさ、ピッチ、面の位置と、前回の矩形を加える処理である。画面が指示した面を本当に表示しているかは、ファームウェアが読み返す値でしか確かめられないので、最後は画面を見て確かめる。続けて、画面全体を1面で送る時間と2面で送る時間(コピーの時間、面を指示する時間、前の切り替えが効くのを待った時間)を、それぞれ3回のうち最短で測る。2面の送りは続けて行うので、待つ時間は送りが待ちうる最大の時間に近い。最後に両方の面を黒に戻す。

カーネル試験の`disp`の組の`test_flip`は、QEMUで2面を使い、画面全体を送ると表示する面が替わること、離れた2つの矩形を1つずつ送ると、2つ目の送りで表示した面に1つ目の矩形も入っていること、1〜3個の矩形を保留の中で描いて送ることを20回繰り返し、毎回、表示する面が替わり、その回と前の回の矩形と1行が表示している面でバックバッファと一致すること、切り替えの回数と送りの回数が20ずつ増え、待つことがないこと、使うのをやめると最後に表示した面に送ることを確かめる。同じ組のほかの試験は1面で送った結果を読むので、組の初めに2面をやめ、終わりに元に戻す。

実機の起動では、次の行が出る(数値は例である)。

```text
disp: asking the firmware for a framebuffer of 1920 x 1080, 32 bpp, 2 pages
disp: flip: two pages of 1920 x 1080 at 3e000000; the firmware showed the second from row 1080 in 180 us and the first again in 150 us
disp: vsync: the waits for the blank came every 16667 us (16500 to 16800, 60 Hz); a send within 18750 us of a flip waits for the next blank
TessronOS: display 1920 x 1080, 32 bpp, pitch 7680, at 3e000000, via mailbox, room for two pages
disp: flip: check passed: 8 sends, 2900 Kpx read back from the page shown, all as the back buffer holds them
disp: flip: whole screen 1920 x 1080: one page 2600 us; two pages 2700 us (copy 2550, flip 150, waiting 14000 for the flip before to be taken); waits for the next vertical blank
disp: flip: on: each send goes to the page not shown, which is then shown
```

| 行 | 分かること |
| --- | --- |
| `disp: flip: the firmware would not give two pages` | 問い合わせで断られ、ノードの1面のまま使う(今までと同じ) |
| `disp: the firmware gave one page` | 仮想の大きさが通らなかった。メールボックスの1面で使う |
| `disp: flip: the firmware's new buffer at 〜 cannot be used` | くれたバッファが使えずノードに戻した。画面が出なければ`DISP_FLIP=0` |
| `disp: flip: two pages of 〜` | 2つ目の面への切り替えと戻しが読み返せた。その時間が4ミリ秒以上ならファームウェアが垂直帰線を待って答えている |
| `disp: flip: the firmware does not show the second page` | 読み返しが合わず、1面で使う |
| `disp: vsync: the waits for the blank came every 〜` | 垂直帰線を待てる。周期とその幅 |
| `disp: vsync: no wait for the vertical blank`、`not a refresh apart` | 垂直帰線は待てない。切り替えから17667マイクロ秒を待つ |
| `disp: flip: check passed`、`check FAILED` | 2面の照合の結果。失敗なら最初の違う画素の位置と値が出て1面になる |
| `disp: flip: whole screen 〜` | 画面全体の送りの時間の、1面と2面の比較 |
| `disp: flip: on`、`off` | 以後の送りが2面か1面か |

使用中は、ウインドウマネージャの60秒ごとの統計の行(10.4.2)の末尾に、送りの回数と1回あたりの時間、面の切り替えの回数、切り替えが効くのを待った回数と1回あたりの時間が出る。照合に通っても、画面がちらつく、古い内容と新しい内容が交互に見えるときは、画面が指示した面を表示していない。そのときは`DISP_FLIP=0`でビルドする。

GPUで組み立てた範囲をフレームバッファへ直接書くことはしない。理由は13.10.8で述べる。

メモリの絵に描く描画環境もある(`dp_open_mem`)。`T_DPBMP`で渡した絵(画素の場所、行の間のバイト数、幅、高さ)の左上が0, 0で、原点と枠と見える所は絵の全体である。描いたものは画面に出ない。カーネルのプログラムは絵の画素にそのまま描く。プロセスが開くとき(A章のクラス8の22)は、カーネルが絵を写し取って描き、`dp_close`(同23)でプロセスの絵に書き戻す。描けるのは開いたプロセスだけで、プロセスが終わるとカーネルの写しを捨てて閉じる(`knl_dp_prc_end`)。基本図形編集の焼き付けが使う。

描画環境には、画素を持たずに描画を記録する環境もある(`dp_open_rec`)。この環境に描くと、塗りつぶし、枠、線、多角形、太さと線種のある折れ線、角の丸い矩形、画素の転送の各関数は、画素を書かずに、呼び出しを受け手の関数(`T_DPREC`)にそのまま渡す。原点、フレーム、クリッピングは普通の環境と同じに働き、渡すときに切り取りの矩形を1つ添える。上書き以外の描画モードの描画は渡さない。印刷はこの環境でページをPDFの描画命令に変換する(11.22)。

### 10.2.2 解像度の変更

解像度は、再起動せずに変えられる。システム環境設定の〈機器情報〉の「画面サイズ／色数」で大きさを一覧から選ぶか幅と高さを入れて〈設定〉を押すと、システム環境設定はデスクトップに`DT_RQ_SCREEN`(`include/ts/dtreq.h`)を送る。要求の文字列は「幅x高さ」と、パネルと縦横の比が違う大きさの置き方(`aspect`は比を保って左右か上下に黒い帯、`stretch`はパネル全体に広げる)である。置き方は、それを選べる画面(x64のIntelの内蔵グラフィックスのパネル)のときだけ選べる。

デスクトップは画面の実身のレコード1に「幅x高さ 置き方」を書き、自分のウインドウをすべて描き直し、壁紙を新しい大きさに敷き直してから、確認のパネル(`dt_confirm_timed`)を出す。30秒以内に［Ｅｎｔｅｒ］か〈確認〉を押すとその大きさを残し、機器の設定の`VIDEOMODE`(幅x高さ)と`VIDEOFIT`(置き方)に書いて次の起動でも使う。ほかのキーを押すか30秒たつと、前の大きさと置き方に戻す。答えは残したとき`E_OK`、戻したとき`E_ABORT`、画面がその大きさにできないとき`E_NOSPT`である。

画面の実身に書かれた大きさは`ts_disp_setmode`(`device/disp/disp.c`)が次の順で行う。

1. ウインドウマネージャのロックを取る(`knl_wm_screen_changing`)。合成タスクは組み立ての間このロックを持つので、これで古いバックバッファに組み立てることがなくなる。合成はバックバッファの場所もロックの中で読む。
2. 画面ドライバに新しい大きさを設定させ(`knl_disp_hw_setmode`)、新しい大きさのバックバッファを作って古いものを解放する。ドライバが断ったときは、ロックを放して(`knl_wm_screen_kept`)元の大きさのまま`E_NOSPT`を返す。
3. ウインドウマネージャが新しい画面に合わせる(`knl_wm_screen_changed`)。ウインドウのピクセルは画面の行の長さ(ピッチ)で並んでいるので、すべてのウインドウに新しいピッチのピクセルを作り、持っていた内容を収まるだけ写す。そのとき、元の画面のメッセージ行より上いっぱいの大きさだったウインドウ(全画面表示)は新しい画面のいっぱいにする。ほかのウインドウは、今の位置と大きさではなく、ウインドウが覚えている求められた位置と大きさ(下記)から置き直す。求められた矩形が元の画面に収まっていたウインドウと、前の画面で小さくされたか動かされたウインドウは、新しい画面に収まるように左上へ動かす(画面より大きければ画面の大きさまで小さくする)。元の画面からはみ出していたウインドウは、左上の角が画面に残るようにする。メッセージ行を新しい下端と幅で作り直し(`knl_msg_screen_changed`)、描画管理が持つ画面の大きさを取り直し(`knl_dp_screen_changed`)、開閉の動きの残像とポインタの下の画素を捨ててロックを放す。そのあと、各ウインドウの描画環境を新しいピクセルに付け替え、枠を描き、動いたウインドウのプログラムに動いたことを知らせ(`knl_wmobj_moved`)、画面全体を組み立てる。
4. 入力の座標の範囲を新しい大きさにする(`knl_hid_screen_changed`)。

ウインドウマネージャは、ウインドウごとに、求められた位置と大きさ(`wm.c`の`WMWIN`の`want`)を覚える。開いたときの矩形(`wm_open`)、プログラムが配置のレコード`OB_WR_PLACE`に書いた矩形(`wm_place`)、利用者やデスクトップが動かしたり大きさを変えたりした矩形(`wm_move`)がそれになる。画面の変更は今の位置と大きさだけを変え、求められた位置と大きさは変えない。そのため、640×480にして小さくなったウインドウも、大きな画面に戻すと、開いたときや利用者が最後に決めた大きさと位置に戻る。WindowsやGNOMEが、画面が狭くなって縮めたウインドウを画面が広がったときに元に戻すのと同じ形である。覚えるのは画面の大きさによらず1つで、画面の大きさごとには分けない。

利用者が小さい画面で自分でウインドウを動かしたり大きさを変えたりしたときは、次のように扱う。

- 大きさを変えたとき(枠を引いて広げる、縮める、全画面表示にする)は、その矩形が新しい求められた位置と大きさになる。利用者が決めた大きさは、あとで画面が広がっても勝手に戻さない。
- 大きさを変えずに動かしただけのときは、位置だけを新しくし、求められた大きさは残す。画面が広がると、動かした先を左上にして元の大きさに戻る(はみ出す分は左上へ寄せる)。

画面が小さくて縮められたウインドウは、ちょうど画面いっぱいの大きさになっていても全画面表示とはみなさず、求められた大きさに戻す。

プログラムが配置のレコードに書いた矩形は、メッセージ行より上の画面に収める(`wm_place`)。画面より大きければ画面の大きさまで小さくし、はみ出す分だけ左上へ動かす。開いたとき(`wm_open`)に画面より大きいウインドウは、これまでどおり画面の大きさにする。どちらも、求められた位置と大きさには頼まれたままの矩形を覚える。設定の小物の`ui_open`は、作業領域をパネルの大きさにする矩形を、頼まれた位置から書き直す。640×480の画面でもウインドウの下端は画面の中に入り、パネルのほうがタブの中身をスクロールさせる(10.7)。

全画面(ページの全画面、動画の全画面)は、ウインドウマネージャが持つウインドウの状態である(`wm_full`、`wm_full_is`)。LinuxのEWMHの`_NET_WM_STATE_FULLSCREEN`と同じく、プログラムは配置のレコードに旗`OB_WP_FULL`を立てて書くだけで、外枠の座標をはみ出させて書くことはしない。旗が立っているとき、矩形は見ない。

- 全画面にすると、ウインドウマネージャは今の外枠、求められた位置と大きさ、属性を覚え、枠、タイトル、スクロールバーの属性を外して、作業領域をウインドウのある画面の全体にする。メッセージ行の上にも重なる。
- 全画面のウインドウが一番前にあるとき(その前にあるのが、`wm_set_parent`でそのウインドウに属するパネルだけのときを含む)、合成はメッセージ行をそのウインドウの下に敷き、画面の下端の押下もそのウインドウのものにする。属するパネルはその前に見える。ほかのウインドウが前に来ると、メッセージ行はいつもどおりすべてのウインドウの上に出る。
- 全画面をやめる(旗を下ろして書く)と、覚えた外枠、位置と大きさ、属性に戻す。
- 全画面の間もウインドウの重なりの順と入力の行き先は変えない。読んだ配置のレコードには`OB_WP_FULL`が立っている。解像度を変えたときは、新しい画面の全体にする。
- デスクトップの全画面表示(`dt_fullscreen`、メッセージ行より上いっぱいで枠は残る)は、これとは別のもので、変えない。

試験は`wm`の組の`test_full`で、作業領域が画面と同じで枠がないこと、メッセージ行の場所がウインドウの色でその押下がウインドウに行くこと、属するパネルが前に見えてメッセージ行は下のままのこと、別のウインドウを前に出すとメッセージ行が戻ること、入力の行き先が変わらないこと、やめると元の外枠と枠に戻ることを見る。

画面ドライバは次のとおりである。

| 機械 | ドライバ | 変え方 |
| --- | --- | --- |
| QEMU(Arm) | `disp_bochs.c` | `bochs-display`のモードのレジスタ |
| Raspberry Pi 5、Pi 4系 | `disp_rpi5.c` | ファームウェアにその大きさのフレームバッファを求める(幅は8の倍数になる) |
| QEMU(x64) | `disp_gop.c` | 標準VGA(1234:1111)の、bochsと同じモードのレジスタ(3つ目のBARの0x500から) |
| x64のIntelの内蔵グラフィックス(第9世代) | `x86_64/disp_igfx.c` | パネルは本来の大きさのまま、プレーン、パイプの大きさ、パイプのスケーラだけを垂直帰線に合わせて変える(6.9) |

試験は、カーネル試験の`wm`の組の`test_screen_size`(ウインドウを開いたまま800×600にして戻し、ウインドウの内容が残ること、描画環境で描けること、全画面のウインドウが画面に合わせて大きさを変えること、端のウインドウが画面の中に入ること、ウインドウのピクセルが足りていることを見る。800×600より大きいウインドウを開いたもの、`wm_place`で置いたもの、小さい画面で大きさを変えたもの、動かしただけのものを作り、小さい画面では画面に収まること、戻したときに開いたときと置いたときの矩形に戻ること、大きさを変えたものはその大きさのまま、動かしただけのものは元の大きさに戻ることも見る)、`devob`の組の`test_display`(画面の実身への書込み)、`tools/tests/ui_screen_size.steps`(システム環境設定で一覧から選んで残す、幅を入れて残す、確認のパネルで戻す)、`tools/tests/ui_sysenv_small.steps`(640×480にして、システム環境設定の各タブでボタンの行が見え、スクロールで下の部品に届くこと、元の大きさに戻すとウインドウが開いたときの大きさに戻ることを見る)で行う。

### 10.2.3 表示の倍率

約210〜220ppiの画面(ThinkPad X1 Yoga 第3世代の2560×1440、Surface Go 2の1920×1280)では、1ドットを1画素に描くと文字と部品が半分以下の大きさに見える。そこで画面全体を倍率(100、125、150、175、200、250、300%)を掛けて描けるようにしている。

座標の単位は論理ピクセルである。今までのドットをそのまま論理ピクセル1つとし、ウインドウの位置と大きさ、作業領域、イベントの座標、損傷、パネルの定義、TAD、外観設定テーブルの長さ(タイトルの文字の大きさ、スクロールバーの幅など)はすべて論理ピクセルで、倍率によって変わらない。画面の物理ピクセルを扱うのは、画面ドライバ、描画管理の画素を書く所、フォント管理の字形を作る所、ウインドウマネージャのウインドウの画素と合成、ポインタ、メッセージ行だけである。アプリは手を入れずに大きく描かれ、描画環境で描く文字と線は物理ピクセルでくっきり描かれる。ほかのOSとの比べ方と、この形に決めた理由は検討書(`docs/private/x64_surface_go2_study.md`の5.18)にある。

画面ドライバ(`disp.c`)が倍率を持つ。`T_DISPSPEC`の`scale`が使っている倍率、`view_w`と`view_h`が論理の画面の大きさ(論理ビュー)、`scale_want`が求められた倍率である。論理ビューは物理ピクセルの幅と高さに100÷倍率を掛けて切り上げた大きさで(1280×800の150%は854×534)、切り上げるので右端と下端に壁紙が覗く帯は残らず、最後の論理ピクセルが1画素未満欠けるだけである。論理ビューが640×480(`DISP_VIEW_MIN_W`、`DISP_VIEW_MIN_H`)を下回る倍率は使わない。`ts_disp_setscale`はそのような倍率を`E_NOSPT`で断り、一覧にない倍率は`E_PAR`で断る。解像度を下げて求められた倍率が使えなくなったときは、その解像度で使える最大の段で描き、求められた倍率は覚えておいて、解像度を戻すとまた使う。換算は`disp_dev_of`(論理ピクセルvが始まる物理ピクセル⌊v×倍率÷100⌋)、`disp_view_of`(物理ピクセルuが属する論理ピクセル)、`disp_view_len`(論理ビューの長さ)で行う。

倍率の変更は解像度の変更(10.2.2)と同じ順で行う。画面ドライバはハードウェアとバックバッファを変えず、ウインドウマネージャのロックを取ってから論理ビューを変え、ウインドウマネージャ(`knl_wm_screen_changed`)と入力の層(`knl_hid_screen_changed`)に知らせる。ウインドウマネージャは、すべてのウインドウの画素を新しい倍率の大きさで作り直し、古い画素を最近傍で写して描き直しまでのつなぎにし、論理ビューに収まるようにウインドウを動かし、描画環境の倍率を変え、枠を描き直し、プログラムに描き直しを求める(`knl_wmobj_moved`。プロセスのウインドウには`OB_E_REDRAW`とパネルの描き直し)。メッセージ行は論理ビューの下端に作り直す。入力の層のポインタの範囲は論理ビューになる。コンソールには`TessronOS: display drawn at 150%, a view of 854 x 534`と`wm: drawn at 150% (was 100%), a view of 854 x 534`が出る。

| 層 | 倍率の扱い |
| --- | --- |
| 描画管理(`dp_`) | 描画環境ごとの倍率(`dp_set_scale`、`dp_scale`)。倍率を持つのは画素の置き場(ターゲット)を持つ環境だけで、ウインドウマネージャがウインドウの描画環境、枠を描く環境、メッセージ行の環境に設定する。論理ピクセル(x, y)は、ターゲットの角からの距離に倍率を掛けた物理ピクセル⌊(x−角)×倍率÷100⌋から次の論理ピクセルの位置までの矩形に描く。塗り、線、図形、パターン、`dp_put_argb`と`dp_put_mono`の画素は、すべて画素を書く所(`run`、`run_px`、`gray_run`など)でこの矩形に広げるので、100%の絵をそのまま大きくした形になり、線の位置と当たり判定は論理ピクセルと一致する。パターンは論理ピクセルの位置で色を決めるので、網掛けは100%と同じ模様に見える。`dp_get_pixel`と`dp_get_argb`は論理ピクセルの矩形の左上の画素を読み、`dp_copy_rect`は物理ピクセルのまま動かす |
| フォント管理(`fn_`) | 文字の大きさは論理ピクセルで指定する。倍率を持つ描画環境に描くと(`walk_scaled`、縦書きは`vwalk`)、字形を大きさ×倍率の物理ピクセルの大きさで作り(`letter_scaled`。ヒンティングをしないので送り幅は大きさに比例する)、論理ピクセルの組みのペン(1/64論理ピクセル)に倍率を掛けた位置に1/4物理ピクセルで置く(`dp_put_gray_dev`)。測る関数(`fn_width`、`fn_fit`、`fn_draw`の戻り値)は論理ピクセルで答えるので、行の組み、カーソル、選択の範囲は倍率で変わらない。大きな字形はキャッシュに物理ピクセルの大きさで別に持つ |
| ウインドウマネージャ | ウインドウの位置、作業領域、損傷、当たり判定は論理ピクセル。ウインドウの画素は物理ピクセルの大きさ(行は`wm_wpitch`バイト。論理ビューの幅のウインドウが画面より1画素広くなることがあるので、画面の行より長いことがある)で持ち、ウインドウの論理ピクセルxはウインドウの画素の⌊(x−外形の左)×倍率÷100⌋にあり、ウインドウの画素は画面の⌊外形の左×倍率÷100⌋から置く。合成には物理ピクセルに直した記述(`T_CPWIN`)を渡すので、合成(`compose.c`)とGPUの合成は変わらない。組み立てる部分は論理ピクセルで集め、組み立てる時に物理ピクセルに直す(周りに1画素ずつ広げる)。角の丸み、影、ぼかしの長さ、ドラッグ中の枠線の太さにも倍率を掛ける。壁紙は、「並べて表示」と「中央」は論理ピクセルで敷いて物理ピクセルでは最近傍で拡大し、「拡大」は画面の物理ピクセルで取る。`wm_screen`、`wm_copy_screen`、`wm_grab_screen`は論理ピクセルで答え、物理ピクセルの画面からは論理ピクセルごとに左上の画素を取る |
| 部品とパネル | 定義の矩形は論理ピクセルのまま、描画管理を通して描くので、何もしなくても大きく描かれる。パネルが開くときに下の画素を取っておく所は、倍率を持つ描画環境では物理ピクセルのまま取って戻す(`dp_get_dev`、`dp_put_dev`)。論理ピクセルで取ると、閉じたときに下の文字が粗くなるためである。メニューと一覧を画面の中に寄せるときは論理ビューの大きさを使う |
| アイコン | 仮身のアイコン(`om.c`)、タイトルバーのアイコン、アイコンの部品は、32×32のICOの絵から、描く枠の物理ピクセルの大きさで最近傍で取り直す(`dp_put_image`)。200%では元の絵の画素がそのまま出る。100%は今までと同じ取り方である。部品の絵(ピクトグラム)は最近傍で拡大する |
| ポインタ | 論理ピクセルで動き、物理ピクセルに置く。形はユーザ環境設定の大きさ(小、中、大)にさらに倍率を掛け、最近傍で拡大する(最大で108画素四方) |
| プロセスの面 | `wm_obj_surf`の面は論理ピクセルの大きさのままで、`wm_obj_put`がウインドウの画素に写すときに最近傍で拡大する |
| 倍率を知るアプリ | 外観設定テーブルの`LK_SCALE`(9143、百分率)で倍率を読める。ウインドウマネージャが書き、プログラムが書いても倍率は変わらない |

設定はシステム環境設定の〈機器情報〉の「画面サイズ／色数」のポップアップ「表示の倍率」で選ぶ(11.6)。画面の実身のレコード1は、`SCALE`(使っている倍率)、`VIEW`(論理ビュー)、`SCALES`(その解像度で使える段)の行を持ち、「150%」と書くと倍率を変える。「幅x高さ 置き方 150%」のように大きさと一緒にも書ける。デスクトップは起動時に、機器の設定の`VIDEOMODE`の次に`VIDEOSCALE`(百分率)を読んでその倍率にする。デスクトップの`dt_screen_size`は論理ビューを答え、ウインドウを画面いっぱいに広げる、中央に置くなどの計算に使う。解像度を変える処理だけが物理ピクセルの大きさ(`SIZE`)を読む。実身に保存した位置と大きさが論理ビューより大きいウインドウ(100%で作った900×700のウインドウを150%の1280×800で開くなど)は、`wm_open`が論理ビューの大きさに縮め、画面の中に寄せて開く。既定は100%で、画面の物理的な大きさ(EDID)を読んで決めることはまだしていない。

ブラウザは後で、`LK_SCALE`を`device_scale_factor`としてBlinkに渡し、物理ピクセルの大きさの面に描くようにする(検討書5.18.6)。それまでは論理ピクセルの面に描き、合成の前に最近傍で拡大される。

100%のときは、倍率の処理をすべて分岐の外に置いているので、今までと画素単位で同じである。カーネル試験の`wm`の組の`test_scale`は、一覧にない倍率と論理ビューが小さすぎる倍率を断ること、150%で論理ビューの大きさ、`wm_screen`と`LK_SCALE`の値、ウインドウの位置が変わらないこと、作業領域に描いた矩形が物理ピクセルで⌊倍率⌋の位置と大きさになること、文字列の幅が100%と同じで描いた戻り値も同じこと、開いたウインドウにも倍率が付くことを確かめる。画面を1600×1200にできるときは200%で、1論理ピクセルの線が2画素になること、文字の2×2の画素がそろっていない(16ドットの字形を拡大したのではなく32画素の字形を作った)こと、16ドットの枠に描いた32×32の絵の全画素が元の絵と同じこと、物理ピクセルで取って戻した画素が元どおりなことを確かめ、100%に戻すと今までどおり描けることを確かめる。画面の試験は`tools/tests/ui_scale.steps`(ポップアップで150%を選び、確認で戻す、残す)で行う。

### 10.2.4 GPUの面

GPUで画素を作るプログラム(GPUのプロセスでページを描くブラウザ、14.13.10)は、作業領域の面(`wm_obj_surf`)へ読み戻して写す代わりに、GPUのBOを2枚ウインドウに付け、その一方を作業領域に出させる。ウインドウマネージャは、出しているBOのページを作業領域の画素として直に読むので、GPUの描いた絵はプロセッサで1回も写されない。口は普通のウインドウのレコード`OB_WR_GSURF`(8。`include/ts/ob.h`の`T_OBWGSURF`、読むと`T_OBWGSTAT`)で、ウインドウの書込みの権利のあるキーで書く。

| 書くもの | 内容 |
| --- | --- |
| `OB_GS_SET` | BOの実身(`OB_S_GPUBO`、8.5.1)のキーを2つ、画素の大きさ、1行のバイト数(256の倍数で幅×4以上、どちらのBOも行×高さ以上)、形式(`OB_GS_XRGB8888`だけ)。キーは書いたプロセスのもので、読出しの権利が要る(`knl_gpu_bo_of_key`。ないと`E_OACV`、BOの実身でなければ`E_OBJ`)。ウインドウマネージャはBOの参照を自分で持ち、BOのページをカーネルの空間に写す(`knl_gpu_bo_kmap`、13.4.1)ので、書いた後はキーを閉じてよい。前に付けた2枚は、出していたBOの絵をウインドウの画素へ写してから手放す |
| `OB_GS_SHOW` | 出すBOの番号(0か1)、呼んだ側の番号(`serial`)、変わった矩形(16まで、0なら全体)。書込みはすぐ戻る。BOを使うGPUのジョブがすべて終わった後の最初の組み立てでそのBOを出し、ウインドウに`OB_E_CHANGE`(`code`がBOの番号、`x`が`serial`)を知らせる。前に出していたBOは、それより後のどの組み立ても読まない |
| `OB_GS_DROP` | 2枚を手放す。出していたBOの絵はウインドウの画素に写して残す |

SHOWとDROPは、SETをしたプロセスだけができる(ほかは`E_OBJ`)。出すのを待っている間に次のSHOWが来ると、矩形を足して(16を超えれば全体)それに替える。

描き終わりは、そのBOを使うジョブの数(`knl_gpu_bo_ref`の`busy`、13.4.2)が0になったことで知る。プロセスはジョブのフェンスの番号を知る口を持たないが、カーネルはジョブにBOの参照を持たせるときにBOごとに数えているからである。DRMシムはV3Dの`SUBMIT_CL`と`SUBMIT_CSD`、i915の`EXECBUFFER2`のBOの一覧をすべて`gp_sub_job`に渡す(`lib/libgl/gl_drm.c`、`gl_drm_i915.c`)。合成タスクは組み立ての始め(`take_asks`)に、待っているBOの数を見て、0なら表を替え、変わった矩形を組み立てる所に加える。ジョブの終わりは、GPUの共通層が1つの関数(`knl_gpu_end_hook`、ジョブの参照を返しフェンスを終わりにした後、ロックを持たずに呼ぶ)でウインドウマネージャに知らせ、待っているBOがあれば合成タスクを起こす。GPUのタスクが合成のロックを待つと、GPUで合成している合成タスク(ロックを持ってGPUを待つ)と互いに待つので、この関数は印を立てて合成タスクを起こすだけにしてある。見回りはしない。

組み立てでは、出しているBOを、持ち主のウインドウのすぐ手前に置く枠のない不透明なウインドウ(`T_CPWIN`。外形と作業領域はウインドウの作業領域の左上からBOの大きさまで、ピクセルはBOをカーネルに写したアドレス、行の長さはBOのもの)として、CPUの並び(`cp_lay`)にもGPUの並び(`lay`)にも同じ順で入れる(`gs_lay_test`)。合成の実装から見ると不透明なウインドウが1つ増えただけで、下のウインドウの作業領域は隠れた所として省かれ、V3DとIntelの合成は、ほかのウインドウのピクセルと同じくBOのページの物理アドレスをGPUの空間に写して読む(`wrap_of`、`igt_cp_wrap`)。写しを外すのは`knl_vunmap_pa`が呼ぶ`knl_vunmap_hook`なので、BOを手放すと合成の実装の表からも外れる。

次のときは手前に置かず、BOの変わった矩形をCPUでウインドウの画素へ写して、ウインドウを今までどおり重ねる(`gs_ready`、`gs_put`)。作業領域が不透明でない(`LK_OPA_WHOLE`とウインドウの不透明度、`LK_OPACITY`)、開閉の動きの途中、独自の外形を持つ、ポップアップ、角の丸みが作業領域にかかる、倍率が100でない(このときは`wm_obj_put`と同じ最近傍の拡大で写す)。手前に置いている間はウインドウの画素の作業領域は古いままなので、手前に置けなくなったとき、ウインドウを閉じるとき(閉じる動きのゴーストのため)、BOを手放すときに、出していたBOの全体を一度写す。大きさを変えたときと画面が変わったときは、写した絵を古いものとして扱う。

BOの寿命は次のとおりである。ウインドウが閉じたとき(`wm_close`)、SETをしたプロセスが終わったとき(`knl_wmobj_prc_end`が呼ぶ`knl_wm_gsurf_prc_end`。自分が作ったのではないウインドウでも)、DROPと付け替えのときに、写しを外して参照を返す。GPUのプロセスが落ちても、BOはウインドウマネージャの参照で残り、ウインドウは最後の絵を出し続ける。

サンドボックスの上では次のとおりである。付けられるのはウインドウの書込みの権利のキーを持つプロセスだけで、渡すBOも自分が読める実身のキーに限る。キーは呼んだプロセスのものだけを受け付けるので(`knl_ob_key_hold`)、ほかのプロセスのキーの番号を書いても`E_OACV`になる。GPUのプロセスのコンテキストの表には自分のBOしか入らず(13.5.1)、ウインドウのピクセルとカーネルの写しはその表に入らないので、BOを描くプロセスがほかのウインドウの絵を読むことはない。ブラウザの側では、レンダラはBOのキーを持たない(14.13.10)。

使っているのはブラウザである(14.13.10の「ウインドウのGPUの面」)。GPUのプロセスがBOを2枚作ってPRIMEの記述子(BOの実身のキー)をブラウザに渡し、ブラウザがSETとSHOWを書く。レンダラはBOの共有イメージに描くだけで、キーを持たない。GLがプロセッサの上にある機械(softpipe)では、GPUのプロセスがラスタの終わりごとに描いた絵をBOへ写すので、QEMUでもこの口の上でページが見せられる。

GPUのない機械(QEMU)ではBOをプロセッサで描いて確かめる。カーネル試験の`gl`の組の`gl_gsurf`は、試験用のプロセス(`tests/uprog/gpprog.c`の`gsurf`)がウインドウを作り、BOを2枚作って色を塗り、`OB_WR_GSURF`に付けて出させ、試験用のバックエンド(ジョブを試験が終わらせるまで止めておく)で次を確かめる。BOの色が画面に出て、ウインドウの画素には写されていないこと。BOの番号の誤り、ウインドウのキー、読めないキー、同じBOを2つ、行の長さの誤り、大きすぎる高さ、形式の誤りを断ること。2枚目を使うジョブが止まっている間は出ず、ジョブを終わらせただけで(フックで)矩形が出て、プロセスに知らせが届くこと。ウインドウを動かすと絵も動くこと、手前のウインドウに覆われた所はそのウインドウの色であること、作業領域を半透明にするとCPUで写す形に替わってウインドウの画素がBOと同じになり、不透明に戻すと手前に置く形に戻ること、DROPの後も最後の絵が残ること、ウインドウを閉じたときとプロセスを止めたときに何も残らず空きページが戻ること。V3DとIntelの合成がBOを手前に置いた並びで同じ画素を作ることは、実機で確かめる(未確認)。

## 10.3 フォント

フォントはFreeTypeで扱う。TrueTypeとOpenType(CFFを含む)を読み込め、グリフはヒンティングをせずに256階調で生成し、線を大きさに応じて少し太らせ、1/4画素の位置で作り分け、背景のピクセルとリニア空間で混ぜて描く(10.3.1)。フォントはシステムボリュームのフォントの実身から読み込む。一度生成したグリフはキャッシュする。縦書きでは、書体のGSUB表の`vert`の機能が示す縦書き用の字形を使い、字を上から下へ字の大きさの枠に1字ずつ置く(`fn_vdraw`、11.21)。

フォントの実身は実身「書体」からリンクしてあり、実身名かメタデータの`tessronos.file.name`で名前が付いている。実身「書体」にあるのは、ゴシック体の`NotoSansJP-Regular.otf`、明朝体の`NotoSerifJP-Regular.otf`、等幅の`NotoSansMonoCJKjp-Regular.otf`(Noto Sans Mono CJK JPを、Noto Sans JPと同じ文字の範囲に絞ったもの)の3つである。どれも`etc/font`のファイルから`tools/mkobj.py def`で`etc/def`に実身を作り、ビルドのときに`tools/mkobj.py rec`でファイルをレコード1にする。デスクトップは起動時に実身「書体」のリンク先をすべて開く。システムのフォントは、機器の設定の実身のレコード0にある仮身のうち、続柄が`tessronos.systemface`のものが指すフォントの実身である(仮身なので、フォントの実身の名前を変えても、どこに移しても追える)。その仮身がまだなければ、`ob_fnd_lnk`で名前(`NotoSansJP-Regular.otf`、`NOTOSANS.OTF`の順)から選び、選んだ実身への仮身を機器の設定に置く。どちらもなければ、最初に開けたフォントを使う。実身「書体」そのものは、根「システム」の仮身のうち続柄`system.fonts`のものから引く(`knl_sys_find`、8.13)。`etc/font/koganei.ttf`は出どころとライセンスが分からないので実身「書体」に入れず、試験用ディスクの`/boot`にファイルのまま載せて、TrueTypeの字形を読む試験(`ktest_fn`)だけが使う。壁紙は、機器の設定の実身のレコード0にある続柄`tessronos.wallpaper`の仮身が指す絵の実身で、システム環境設定で選ぶとその仮身を置き直す。敷き方は同じ設定の`WALLPAPER`の行の2語目に持つ。R1.110までは絵の実身のUUIDも`WALLPAPER`の行の文字で持っていたので、仮身がなくて行があるときは行から読み、仮身を作る。行は、R1.110で起動しても壁紙が出るように書き続ける。何も選んでいなければ、実身「壁紙」から`TESSRON.PIC`を探し、なければ最初のリンク先を使う。自分で文字を描くプロセスは`ts_face_find`、`ts_face_list`(`include/ts/face.h`)で実身「書体」からフォントの実身を得る。どちらも箱のリンクを名前で探す`ob_fnd_lnk`、`ob_lst_lnk`(8.3)を使う。

FreeTypeは複数のタスクから同時に呼んではならないので、フォント管理全体を1つのロックで保護する。サイズを設定して文字を描くような一連の操作は、ロックを保持したまま行う。

書体の大きさは、書体ごとに8つまで、FreeTypeの大きさのオブジェクト(`FT_New_Size`)として作っておき、同じ大きさに戻すときは選び直すだけにする(`FT_Activate_Size`)。8つを超えたら、いちばん長く選ばれていないものを作り直す。プロセスの字(`fn_dra_txt`、11.11)は、呼ぶたびにプロセスの大きさに設定して元に戻すので、毎回大きさを作り直していたときは、OpenTypeの書体で字を測る時間より大きさの設定のほうが長かった(1回あたりの設定と戻しで約30マイクロ秒、QEMU)。作っておく形にして、約2マイクロ秒になった。

### 10.3.1 字の描き方

字の描き方は、今のmacOS(10.14以降)と同じ考え方に揃えている。グレースケールのアンチエイリアス、ヒンティングなし、1画素未満の文字送り、線の太らせ、色ごとに分けた描画(RGBのサブピクセルレンダリング)をしないこと、の5点である。

| 項目 | TessronOS | macOS | 以前のTessronOS |
| --- | --- | --- | --- |
| 階調 | 256階調のグレースケール | グレースケール(10.14でRGBのサブピクセルレンダリングをやめた) | 256階調 |
| ヒンティング | しない | しない | しない |
| 混ぜ方 | リニア空間。字の色で曲線を選ぶ | 字の色で決まるガンマで混ぜる | 色の値をそのまま比例で混ぜる |
| 線の太らせ | 大きさの0.0121倍(横)、その1.25倍(縦)、片側0.3画素まで | フォントスムージング(同じ程度の太らせ) | しない |
| 字の位置 | 1/4画素 | 1画素未満 | 1画素 |

#### リニア空間で混ぜる

画面の色の値(sRGB)は光の強さに比例しない。光の強さを表すリニア値は、およそ色の値の2.2乗である。字が画素を半分覆うとき、色の値をそのまま半分ずつ混ぜると、白地の黒い字の縁はリニア値では4分の1ほどの暗さになり、黒地の白い字の縁は4分の1ほどの明るさにしかならない。同じ形の字が、黒字では太く重く、白字では細く見える。

そこで描画管理(`dp.c`の`gray_run`)は、背景と字の色のRGBの値をそれぞれ表(`dp_lin`、16ビットのリニア値)でリニア値にし、覆う割合で混ぜ、表(`dp_inv`と`dp_mid`)で一番近い色の値に戻す。戻す表はリニア値の16分の1ごとの値と、隣り合う値のリニア値の中間を持ち、中間と比べて最も近い値を選ぶ。どちらの表も、その曲線を初めて使うときに作る(1曲線あたり5KB)。表は`outer_kernel/dp/dp_gamma.h`にあり、曲線は7本である。字の色の明るさ(Rec.709の重み)が0の黒ではsRGBの変換式そのもの、明るくなるにつれて2.0、1.8…1.2乗とまっすぐに近づき、白では1乗(色の値をそのまま混ぜる)になる。

字の色で曲線を変えるのは、同じ形でも明るい字は暗い背景の上で線がにじんで太く見えるからである。macOSのCore Graphicsも、黒い字はガンマ2.0、白い字は1.0で混ぜている。Skiaはこれを、字の色の明るさを半分に見なしてマスクのガンマを選ぶことで真似ている。TessronOSは背景の画素を実際に読んで混ぜるので、Skiaのように背景を推定する必要はない。

コントラストの補正(覆う割合そのものを濃くする補正)はしない。SkiaはWindowsとLinuxではコントラストを足すが、macOSではCore Graphicsが字を太らせるのでコントラストを0にしている。TessronOSも太らせ(下記)で重さを戻すので、補正はせず、縁のなめらかさを覆う割合のまま保つ。

混ぜるのは覆う割合が1〜254の画素だけで、0は触らず、255は字の色にする。背景が字の色と同じ値なら変えない。続く画素が同じ背景と同じ割合なら、前の画素の結果を使う。

#### 線の太らせ

リニア空間で混ぜると、縁の画素が明るくなり、メニューや本文の大きさ(線が1〜2画素)では字が細く薄く見える。macOSはフォントスムージングとして、字の輪郭を大きさに応じて外へ広げてこれを補う。TessronOSも同じように、画素にする前の輪郭を`FT_Outline_EmboldenXY`で広げる(`fn.c`の`darken`)。広げる量は片側で、横が大きさ(画素)の0.0121倍、縦がその1.25倍、上限は0.3画素で、72画素を超える大きさでは広げない。16画素では片側0.19画素、全体で約0.39画素太くなる。送り幅は変えないので、字の位置と行の組みは変わらない。

FreeTypeにも線の太らせ(stem darkening)はあるが、使わない。CFFの太らせはAdobeのエンジンの中で行い、線の幅が細いほど多く太らせる(0.5画素以下で0.4画素、1画素で0.275画素、2.333画素以上で0)。ヒンティングをしないときは単位の大きさで輪郭を作るので、太らせる量が大きさに合わない。TrueTypeのドライバには太らせがなく、自動ヒンターの太らせは試験的で、ヒンティングを前提にしている。輪郭を広げる方法なら、CFFとTrueTypeの書体を同じに扱え、ヒンティングもいらない。

太字(`FN_ST_BOLD`)、斜体、回転した字も同じ処理で256階調にする。以前はこれらを白黒の2値で描いていた。書体が持つ埋め込みのビットマップを使う字(太字、斜体、回転でないとき)は、そのまま描き、太らせも1/4画素の作り分けもしない。

#### ヒンティングはしない

ヒンティングは、PostScriptの輪郭の書体では字を作る仕事の大半を占め、線を最大で半画素動かす。1/4画素の位置で字を作り分けても、ヒンティングで線が画素の格子に寄せられると、その効果が消える。ヒンティングをしなければ、字はどの位置でも同じ形になる。

#### 1画素未満の文字送り

文字列を描くとき(`fn.c`の`walk`)、ペンの位置を1/64画素の単位で持ち、字ごとに書体の送り幅(`FT_Get_Advance`、丸めない値)だけ進める。字は、ペンの位置に最も近い1/4画素の位置に置く。1/4画素ずつずれた字は、輪郭をその分ずらしてから画素にしたもので、同じ画素を1画素ずらして置いたものではない。

キャッシュは字ごとの項目(送り幅、上下の高さ)に、4つの位置ごとの画素(`GPIX`)を持つ。測るだけのときは画素を作らない。和文は1字ずつ整数の位置に置くことが多いので、位置0の画素だけで済むことが多い。

字の幅を測る関数(`fn_width`、`fn_fit`、`fn_draw`の戻り値)は、1/64画素のペンの位置を最も近い画素に丸めて返す。文字列の先頭k字の幅は、k字目が置かれる位置と半画素以内で一致するので、文章の組み(`docview.c`)が先頭からの幅で求めるカーソルの位置と選択の範囲は、描いた字とずれない。`fn_fit`は、丸めた幅が与えた幅に収まる最も長い先頭を返すので、`fn_width`の値をそのまま渡せば全体が収まる。丸めは文字列ごとなので、1字ずつ測った幅の和と、まとめて測った幅は1画素以上違うことがある。字間を空けて組む文字列(`run_space`が0でない)は、`docview.c`が1字ずつ整数の位置に描くので、測るときも1字ずつ測って足す。カーニングは以前から使っていない。

縦書き(`fn_vdraw`)では、字を字の枠の中央に置く横の位置を1/4画素で決め、縦は字の大きさの枠ごとに進める。印刷(記録の描画環境)には、ペンの位置を1/65536画素の行列で渡す。

ブラウザはSkiaで自分で字を描き、実身「書体」から書体の実身を得る(`ts_face_find`)だけなので、ここで述べた描き方の影響は受けない。

#### 速さとキャッシュの大きさ

`fn_report`は、求めた字の数、キャッシュにあった数、画素を作った数、描いた数、FreeTypeと描画にかかった時間に加えて、キャッシュにある字の数、位置ごとの画素の数、画素が使っているメモリと上限(4MB)を出す。カーネル試験`tv`の`test_doc`(見本の文章1ページ、Noto Sans JP)で、変える前と後を測った値は次のとおりである(QEMU、2026年10月15日)。

| 項目 | 変える前 | 変えた後 |
| --- | --- | --- |
| 測る(`tv_doc_height`) | 19ms | 17ms |
| 描く(1回目) | 148ms | 144ms |
| 描く(2回目) | 50ms | 46ms |
| 画素を混ぜる時間の合計 | 27ms | 27ms |
| キャッシュ | (数えていなかった) | 473字、画素は300組で57KB |
| 字の表(4096字分の項目) | 約384KB | 約320KB |

リニア空間で混ぜる処理は表を引くだけで、混ぜるのは縁の画素だけなので、描く時間は変わらない。和文は1字ずつ整数の位置に置くので、画素の組は字の数より少ない。

カーネル試験`fn`の`test_blend`は、白地に黒で半分覆った画素が187前後(リニア値で半分)、黒地に白で半分覆った画素が128、覆わない画素と背景と同じ色の字は元の値、全部覆う画素は字の色になることを確かめる。`test_subpixel`は、13画素の英文で、先頭からの幅が減らないこと、先頭の幅を`fn_fit`に渡すとその先頭が収まること、全体の幅が最後の先頭の幅と同じで、描いた戻り値とも同じことを確かめる。試験用のTrueTypeの書体では、41字の幅は全体で286画素、1字ずつ丸めて足すと303画素で、字ごとに丸めていた以前は文が6%広がっていた。

### 書体の登録と使用

実身「書体」のフォントの実身1つには、フォントのファイルが1つ入る。TrueTypeのコレクション(`ttcf`)なら1つのファイルに複数の書体があり、0から数える番号で区別する。各書体をどう登録したかは、その実身のリソース`_0_font.json`(`DT_FONT_RES`)にJSONで持つ。リソースの名前は、TSFSの実身がリソースを「_レコード番号_名前.拡張子」の形で持つことに合わせた。

```json
{"faces":[{"index":0,"name":"詳細名","use":true,"family":"Noto Sans JP",
           "class":"0050","attr":"0010","base":""}]}
```

| 項目 | 意味 |
| --- | --- |
| `index` | ファイルの中の書体の番号 |
| `name` | 詳細名。システム環境設定の一覧に出す名前 |
| `use` | 使用するかどうか |
| `family` | 文章が書体を名指すときのファミリ名。空ならファイルの名前表のファミリ名 |
| `class` | フォントクラス(16ビット、4桁の16進数)。各ビットは字の見た目を表す。0x8000見出し用、0x4000と0x2000線の端に飾り、0x1000線の太さに抑揚、0x0800線の端が丸い、0x0400角が丸い、0x0200線が途切れる、0x0100手書き風、0x0080上品、0x0040簡素、0x0020現代的、0x0010和風、下位4ビットは大きさと太さによる読みやすさ |
| `attr` | 属性(4桁の16進数)。0x0001太字、0x0002斜体、0x0004袋文字、0x0008影付文字、0x0010比例(字の幅が字ごとに違う)、0x0020縦書き(縦書き用の字形を持つ) |
| `base` | ベースのファミリ名。この書体にない字を描くファミリ |

リソースに書かれていない書体は、ファイルの最初の書体(番号0)を、ファイルに書かれたとおりのファミリで使う。システムの3つの書体はリソースを持たない。

デスクトップは起動時と書体の登録や変更のたびに`dt_res_faces`で実身「書体」を読み直す。まだ開いていない書体を`fn_open_obj`で開き、登録の内容を`fn_set_reg`でフォント管理に渡す。開いた書体は、ウインドウやメニューが描くのに使っているかもしれないので、閉じない。使用しないにした書体と、実身「書体」から外した書体は、開いたまま`FN_USE_OFF`にする。この書体は名前でも種類でも見つからなくなり、`fn_nface`の数にも入らない。メモリは次の起動まで残る。フォント管理が同時に開ける書体は16である。

フォント管理は書体を次のように選ぶ(`fn_find_style`)。

- 文章の書体名(`<font face>`)と同じファミリの、使用する書体を探す。ファミリ名は、登録したファミリがあればそれ、なければファイルのファミリ名で比べる。
- 同じファミリに複数あれば、求める字の見た目(太字、斜体、袋文字、影付文字)に最も近い属性の書体を選ぶ。求めた見た目を持つ属性は加点し、求めていない見た目を持つ属性はそれより大きく減点する。
- 選んだ書体が属性として持つ見た目は、文章の組版(`docview.c`の`run_font`、`draw_text_item`)で重ねて加えない。太字の書体を太字で求めたとき、さらに太らせることはない。
- 一般名(`serif`、`明朝`、`sans-serif`、`ゴシック`)は、クラスを登録した書体ではクラスの0x6000(線の端の飾り)の有無で、登録していない書体ではファミリ名の語(`Serif`、`Mincho`、`Sans`、`Gothic`)で選ぶ。`monospace`はファミリ名の`Mono`で選ぶ。
- 何も見つからなければシステムの書体を使う。

ベースのファミリを登録した書体にない字は、その字を持つベースの書体で描く(`fn.c`の`letter_face`)。ベースの書体には、元の書体と同じ大きさ、見た目、回転を1回の文字列の描画の間だけ設定し、終わったら戻す。ベースの書体はシステムの書体であることが多く、その設定を変えたままにしないためである。ベースは1段だけで、ベースのベースはたどらない。

見本を表示するときだけ、使用しない書体や登録していない書体を、別の書体として開く(`FN_USE_TRIAL`)。ファミリ名は`見本:実身のUUID:番号`で、この名前を名指したときだけ見つかる。見本のウインドウを閉じると閉じる。

カーネルの試験`ktest_fn`の`test_reg`は、同じファミリの普通の書体と太字の書体から求める見た目に合う方が選ばれ、持っている見た目が答えられること、使用しない書体が名前でも数でも見つからないこと、見本の書体がその名前でだけ見つかること、ASCIIの40字ほどしか持たない試験用のTrueTypeの書体にベースとしてシステムの書体を登録すると、漢字がシステムの書体と同じ幅で描かれ、書体が持つ字はその書体のままで、システムの書体の大きさが元に戻ることを確かめる。

描く先が記録の描画環境のときは、文字をグリフの画素にせず、グリフの番号、元の文字、サイズと、グリフの座標から描く先の座標への行列(長体、平体、斜体、文字の回転を含む)を渡す(`dp_rec_glyph`)。印刷が書体の部分集合を作るために、フォントの表をそのまま読む関数(`fn_sfnt_table`)もある(11.22)。

## 10.4 ウインドウ

ウインドウは、外形、ワークエリア、タイトルバー、スクロールバー、重なり順を持つ。ウインドウの枠とタイトルバーはウインドウマネージャが描き、ワークエリアの中はそのウインドウのプログラムが描く。タイトルバーの左端には、ウインドウが表示している実身のアイコンを表示する。プロセスの小物のウインドウには、そのプログラムの実身のアイコンが表示される。どちらのアイコンも持たないウインドウ(デスクトップのパネルや、アイコンの無いプログラムのウインドウ)には、既定のアイコンとしてシステム環境設定のプログラムの歯車のアイコンを色付きで表示する(`wm_set_icon_default`)。既定のアイコンはデスクトップが起動時に実身から読んで渡す。ウインドウマネージャが枠を描く最中に実身を読まないのは、ウインドウマネージャのロックを持ったまま実身の管理を待たないためである。デスクトップが起動するまでの短い間だけは、タイトルの文字の色で描く図形のマークが出る。

ウインドウの外観は超漢字Vに合わせてある。枠とタイトルバーの図柄は外観設定テーブルの配色で決まり、その上に重ねる見た目(枠やウインドウ全体の半透明、枠とタイトルバーに重ねる色、角の丸み、影、透けて見える背後のぼかし、開閉の動き)はシステム環境設定の〈ウィンドウ〉で設定する(10.4.1)。壁紙は並べて表示、中央、拡大を選べる。

操作の規則は次のとおりである。

- タイトルバーをドラッグするとウインドウが移動する。右下の角をドラッグするとサイズが変わる。移動中の表示を枠線だけにしたとき(`LK_LIVE`が0)は、ドラッグの間は枠線だけがポインタに従い、ボタンを離した位置へウインドウが移動する。
- 仮身や図形をドラッグするときも同じ設定に従う。`LK_LIVE`が1なら、デスクトップはドラッグを始めるときに運ぶものの画面上の位置を`wm_set_drag_from`で渡し、ウインドウマネージャはその部分の画素をコピーして、ドラッグの間は枠線の代わりにその絵をポインタに合わせて動かす。プロセスの仮身(`DT_RQ_CARRY`)では、依頼が届くまでにポインタが動いていることがあるので、運ぶものの位置はボタンを押した位置(`ts_hid_press_at`)と`grab_x`、`grab_y`から求める。絵は枠線と同じく、どのウインドウよりも上に重ね、どのウインドウの画素にも書かない。大きさを変える操作、範囲の選択、文字列のドラッグ、画面印刷の範囲の指定は、設定によらず枠線で示す。コピーする画素は合計で4M画素(`WM_DRAG_PX_MAX`)までで、それを超える分と画面からはみ出すものは枠線で示す。
- タイトルバー左端のピクトグラムをダブルクリックすると、ウインドウを閉じる。
- ウインドウを閉じると、残ったウインドウのうち最前面のものに入力フォーカスが移る。
- ホイールの縦と横の回転は、ポインタの下にあるウインドウのプログラムにイベントとして通知される。
- 右ボタンで、入力フォーカスを持つウインドウのメニューが開く。ウインドウのない場所で押したときは、最前面のウインドウのメニューが開く。メニューの項目は左ボタンでだけ選び、右ボタンを押しても離しても項目は選ばれない。メニューを開いた右ボタンを押している間は、ほかのボタンの押しと離しをメニューに渡さない。メニューの外を押すか、Escで閉じる。開いた押下の離し方の規則は下の「メニューと一覧を開いた押下の離し」に書く。メニューが開いている間、ポインタとキーの入力はメニューだけに渡し、下のウインドウやパネルには通知しない。パネルの部品は左ボタンだけで操作し、右ボタンの押下では選択を変えない。どのウインドウのメニューも、先頭はウインドウの共通メニュー(閉じる)、末尾はウインドウ、小物、実行である。デスクトップのウインドウは実身の共通メニューで、プロセスとして動くプログラムと管理情報のウインドウはウインドウの末尾の共通メニュー(`SYSDEF_MENU_TAIL`)を取り込む。プロセスのメニューの小物の一覧はカーネルがデスクトップから受け取って埋め、選ばれた小物はデスクトップが起動する。プロセスのウインドウには仮身がないので、実行は灰色で表示する。
- Shift+PauseとCtrl+Shift+Pauseはどのウインドウにも渡さない。入力の層がリングに入れる前に強制終了のタスクへ渡し(`knl_fq_input`)、`wm_read_event`には来ない(5.5.1)。強制終了のウインドウが開いている間は、ほかのイベントもすべてそこへ渡す(5.5.3)。`wm_read_event`は、デスクトップの主ループの監視に入力を待っている間であることを通知する(`knl_wdog_idle`、4.7.2)。

ウインドウの大きさが変わると(`wm_move`、`wm_place`、解像度や倍率の変更)、ウインドウマネージャは次のように扱う。

- ウインドウのピクセルが足りなくなって作り直すときは、前のピクセルを両方に収まるだけ写す。行の長さ(`wm_wpitch`)はどちらも同じなので、ページのまま写せる。プログラムが新しい大きさで描き直すまで、前の内容を見せておくためである。
- 新しいワークエリアのうち前のワークエリアになかった所(広げた右と下の帯で、前の枠とスクロールバーがあった所も含む)は、ウインドウのロックを持ったまま、開いたときと同じワークエリアの色(`WM_LOOK_WORK`、ポップアップは`WM_CLEAR`)で埋める(`uncovered_clear`)。プログラムが描き直すまで、そこが黒や前の画素のまま見えることはない。縮めたときは埋める所がない。
- 描画環境は1回の呼出し(`dp_set_place`)で新しいピクセル、角、原点、枠に付け替え、プログラムに描き直しを求める(`knl_wmobj_moved`。プロセスのウインドウには`OB_E_REDRAW`)。
- ウインドウの描画環境の見える範囲(`visible`)は、プログラムが狭めていないときは、ワークエリアの大きさではなく十分に大きな矩形(`DP_VIS_WHOLE`、2の20乗)にする。描く所は枠(ワークエリア)で切るので、ワークエリア全体に描けることは同じである。プログラムは図形や仮身の中身を描く間だけ見える範囲を狭め、`dp_ref`で読んだ前の範囲に戻す。見える範囲をその時のワークエリアの大きさにしていたときは、狭めてから戻すまでの間に大きさが変わると、古い大きさの矩形を戻してしまい、以後の描画がすべて古い大きさで切られていた。プロセスで動く仮身一覧(原紙箱、原紙集め)のウインドウを右下の角で広げると、広げた所が黒いまま残ったのはこのためである。描画環境の見える範囲は、Xのクリップのない状態と同じく、ウインドウの大きさによらない値で表す。

試験は`tools/tests/ui_proc_grow.steps`で行う。原紙集めのウインドウを角で何段階かに分けて広げ、ワークエリアの右端と下端が白いことを見る。縮めたとき、1回で広げたとき、角のダブルクリックで全画面表示にして戻したとき、基本文章編集のプロセスのウインドウを広げたときも見る。

ウインドウは実身としても扱える(ウインドウの実身、8.1)。プロセスは`ob_cre_obj`でウインドウを作成し、キーを開き、イベント通知を要求して入力を受け取る。ウインドウの実身のレコードは次のとおりである。

| レコード | 内容 |
| --- | --- |
| 0　描画 | xmlTAD。書き込むとウインドウの内容がそのTADになる |
| 1　形状 | ウインドウの形を表すxmlTADの図形 |
| 2　配置 | 外形、ワークエリア、重なり順、表示の有無。書き込むとウインドウが移動する |
| 3　状態 | 部品の値 |
| 4以降 | ウインドウの種類ごとのデータ。ウインドウではレコード4がドロップされた仮身、レコード5がスクロールバー、レコード8がGPUの面(10.2.4)、パネルではその部品へのリンク、メニューでは項目 |

ウインドウの作成時のメタデータに、`"rect":[左,上,右,下]`、`"attr":枠の種類`、`"shows":"UUID"`(表示している実身)、`"icon":"UUID"`(アイコンを借りる実身)、`"sub":"UUID"`(親のウインドウ)を指定できる。

`"attr"`に`WM_ATTR_NOFOCUS`を含めたウインドウは入力の対象にならない。`wm_focus`はこのウインドウに入力の対象を与えず、押されて前に出ても、キーはそれまで入力の対象だったウインドウに届く。画面キーボード(キー配列、11.15。ソフトウェアキーボード、11.31)はこの属性で作り、絵のキーを`wm_key_put`で入力の対象のウインドウに入れ、キーボードで押されているキーを`OB_N_KEYSEEN`の通知で知る。ただし、このウインドウを持ち主にしてパネルを出している間(`wm_panel_open_at`、プロセスの基本図形編集のパレットの色の部品から出すシステムの色のパネル)は、そのウインドウの帯を入力の対象のウインドウの帯の色で、入力の対象のウインドウの帯をそうでない色で描く(`wm_lit`)。キーはそれまでの所に届いたままで、見え方だけを、入力を受け取れるウインドウがパネルを出して入力の対象になったときと同じにする。パネルを閉じるか、そのウインドウを閉じると元に戻る。同じく、ポップアップ(`WM_ATTR_POPUP`、帯を持たないパネルのウインドウ)が入力フォーカスを受け取っている間は、入力フォーカスをそのポップアップに渡したウインドウの帯を入力フォーカスの色で描く(プロセスの`ui_dlg_open`のパネル)。データボックスのパネルが開いたときに入力フォーカスを持つ最初のテキストボックスは、カーネル内のパネルと同じく文字をすべて選んだ状態で始まり、プログラムがそこに入れた文字もすべて選んだままにする(`knl_pn_set_state`)。

入力フォーカスは、利用者の操作に結びつくときだけ移す。背景で開くウインドウが、打っている文字を横取りしないためである。規則は次のとおりである。

- 開いたウインドウ。デスクトップが利用者の操作(仮身のダブルクリック、メニューの「小物」「実行」)でプログラムを起動するときは、その時点の押下の番号(チケット、`wm_act_ticket`)を起動するプロセスに付ける。`knl_ob_prc_start`がプロセスの最初の命令より前に付けるので、ウインドウがどれほど早く開いても間に合う。そのプロセスが最初に開く普通のウインドウ(タイトルバーがあり、従属、ポップアップ、`WM_ATTR_NOFOCUS`、`WM_ATTR_FLOAT`のどれでもないもの)が入力フォーカスを受け取る。チケットは1回限りで、プロセスの2つ目以降のウインドウには効かない。
- チケットの期限。ボタンまたはキー(修飾キーを除く)が次に押されると無効になる。起動を待つ間に別の作業に移った利用者の打鍵を奪わないためである。押下がなくても、最後の押下から60秒(`WM_ACT_MS`)で無効になる。
- 入力フォーカスを持つプロセスが開くウインドウ。最後の押下から2秒以内なら入力フォーカスを受け取る。メニューの操作で開く別のウインドウがこれにあたる。ブラウザのスクリプトが操作なしで開く別のウインドウは、2秒を過ぎていれば受け取らない。
- 問い合わせのパネル(ポップアップ、`ui_dlg_open`のパネル)。開くと入力フォーカスを受け取り、閉じると開いたときに入力フォーカスを持っていたウインドウ(`back`)に返す。問い合わせが出ている間に、そのプログラムのウインドウが入力フォーカスを受け取ったとき(押されたとき、`wm_focus`)は、入力フォーカスを問い合わせに渡し、戻り先をそのウインドウにする(`knl_wmobj_focused`)。利用者が次に答えるのはその問い合わせだからである。
- デスクトップのパネル(OSの終了の確認、名前の入力など、`dt_pn_run`と`dt_confirm_timed`)は、そのパネルの下のウインドウが入力フォーカスを持つときに打たれたキーだけで答える。デスクトップは入力をすべて読むが、ほかのウインドウ(プログラムの問い合わせなど)に打たれたEnterをパネルの了解とはしない。プログラムのパネルに答えたEnterで、背後で待っていた「OSを終了しますか？」に「はい」と答えてしまわないためである。
- それ以外のウインドウは入力フォーカスを受け取らない。通知(`WM_ATTR_NOFOCUS`)、常駐の小物、チケットのないプロセスのウインドウがこれにあたる。前面には出るが、キーの行き先は変わらない。
- プロセスの頼み(`DT_RQ_OPEN`、`DT_RQ_TOOL`)は、頼んだプロセスが入力フォーカスを持つウインドウの持ち主のときだけ操作として扱う。カーネルの中からの頼みも操作として扱う。持ち主でないプロセスの頼みで開いたものは、デスクトップのウインドウであっても、入力フォーカスを元のウインドウに残す。
- 自動起動(仮身の属性)で開くウインドウは、起動時の復元も含めて入力フォーカスを受け取らない。一緒に開いた元のウインドウ、またはそれまで入力フォーカスを持っていたウインドウが持ち続ける。自動起動で開いたウインドウは元のウインドウより前に重なる(11章「自動起動で開くウインドウの重なり」)。
- ドロップ。受け取るプログラムがいるウインドウにドロップすると(`wm_obj_drop`、`wm_obj_drop_text`、`OB_E_DROP`の通知の前)、そのウインドウが前面に出て入力フォーカスを受け取る。デスクトップのウインドウへのドロップも同じである(`dt_drop_keys`)。プログラムの答えを待たないのは、読み込みに時間のかかるプログラムで、その間の打鍵が元のウインドウに入らないようにするためである。
- 拒否されたドロップ。`OB_DR_REFUSE`の答えが来たら、入力フォーカスと前面を、ドロップ前のウインドウに戻す。何も入らなかったので、利用者はドロップ前の作業を続けるからである。答えの前に利用者が入力フォーカスを移していたら戻さない。ドロップを受け取るプログラムがいないウインドウ、デスクトップが「ここには置けません」と断るウインドウでは、最初から移さない。プロセスのウインドウからほかのプロセスのウインドウへのドロップ(11.4)も同じ規則で、権利がなくて渡せないときは最初から移さない。
- 変わらないもの。`WM_ATTR_NOFOCUS`のウインドウはドロップでも開いても受け取らず、その打鍵先は変わらない。入力フォーカスをポップアップ(問い合わせのパネル)が持つ間は、開いたウインドウもドロップも入力フォーカスを取らない。閉じたときの戻り先(`back`)は従来どおりである。

試験は`tools/tests/ui_focus_open.steps`と`ui_focus_drop.steps`で行い(仮身を置いた元はデスクトップのウインドウの図形のページ)、移した後に打ったキーがそのウインドウに届くことを確かめる。

`"attr"`に`WM_ATTR_SCREEN`(0x0800)を含めたウインドウは、メッセージ行を含めた画面全体を覆う。この属性のウインドウが1つでも開いている間、ウインドウマネージャはメッセージ行を隠し、最後の1つが閉じると元に戻す(最初の1つが開く前から隠れていれば隠れたまま)。プログラムが閉じても、プロセスが終わってウインドウが閉じても戻る。タイトルバーがなくても普通のウインドウとして扱い(`WM_ATTR_OWN`)、利用者の操作で開いたときと押されたときに入力フォーカスを受け取り、手前のウインドウが閉じたときの次の入力の対象にもなる。スライド(11.11)はこの属性で`"full":1`のウインドウを作る。

`"attr"`に`WM_ATTR_FLOAT`(0x0400)を含めたウインドウは浮かぶ。枠と入力は普通のウインドウと同じであるが、浮かばないウインドウのすべてより前にあり、ポップアップよりは後ろにある。新しく開いたウインドウや前に出したウインドウは、浮かぶウインドウの後ろに来る。浮かぶウインドウどうしの順は、前に出した順である。ブラウザのピクチャインピクチャのウインドウ(14.7.8)はこの属性で作る。ソフトウェアキーボード(11.31)は`WM_ATTR_NOFOCUS`と一緒にこの属性で作る。押されて前に出ても入力の対象は移らず、ほかのウインドウを開いたり前に出したりしてもその後ろに来るので、キーボードはいつも作業中のウインドウより前にある。最前面の組の数え方(`active_root`)では、`WM_ATTR_NOFOCUS`のウインドウは浮かぶかどうかによらず数えないので、キーボードを押して前に出しても作業中のウインドウの従属ウインドウは隠れない。

`WM_ATTR_NOFOCUS`と`WM_ATTR_FLOAT`の両方を持つウインドウは入力補助(`WM_ATTR_AID`)で、メニューを除くほかのすべてのウインドウより前にある。パネル、カラーピッカーなどのポップアップ、全画面のウインドウ(`WM_ATTR_SCREEN`、`wm_full`)、メッセージ行より前に出る。パネルを開いても、ウインドウを前に出しても後ろに下げても、入力補助の後ろに来る(`aids_front`)。メッセージ行は入力補助の上に描かず(合成では、最初のポップアップか全画面のウインドウと同じく、入力補助の手前でメッセージ行を置く)、入力補助の上の押下はメッセージ行に渡さない。全画面のウインドウがメッセージ行を下に敷くかどうか(`full_front`)の判定でも、入力補助は数えない。キーを持たないだけのウインドウ(図形編集の道具パネル、通知)や、浮かぶだけのウインドウ(ピクチャインピクチャ)は入力補助ではなく、今までどおりポップアップの後ろにある。属性を新しく足さずに組で分けたのは、ソフトウェアキーボードがもともとこの組で作っていて、ほかにこの組のウインドウがないからである。ダイアログに打つためのキーボードがダイアログに隠れないようにする。ピクチャインピクチャのウインドウはソフトウェアキーボードの後ろになる。

`WM_ATTR_POPUP`に`WM_ATTR_MENU`(0x1000)を加えたウインドウはメニューで、入力補助も含めたすべてのウインドウより前にある。メニューの一覧(`mn_open_body`。下位の一覧も)、部品のリスト(`WM_PT_POPUP`の`pop_open`)、かな漢字変換の候補(`cand_put`)がこの属性で開く。どれも選べばすぐ消えるもので、選ぶ途中で何かに隠れると操作できない。ソフトウェアキーボードを出したまま、その小物やほかのウインドウの右ボタンのメニューを開いても、メニューはキーボードより前に出る。メニューの上に描くのはポインタだけである。問い合わせのパネルやダイアログは`WM_ATTR_MENU`を持たず、入力補助の後ろにある。パネルの文字の欄にソフトウェアキーボードで打てるようにするためで、X Window Systemの多くの環境でスクリーンキーボードがダイアログより前に、ポップアップメニューがそのさらに前に出るのと同じ形である。

重なりの層は、後ろから次の順である。同じ層の中では後から開いたもの(または後から前に出したもの)が上にある。メニューの下位の一覧は親の一覧より後に開くので、親の上に重なる。ウインドウを開いたり前に出したり後ろに下げたりすると、ウインドウマネージャは`attr_front`で、そのウインドウの層より上の層を順に前へ戻す(`floats_front`、`popups_front`、`aids_front`、`menus_front`)。`attr_front`は層のウインドウを後ろのものから順に1つずつ最前面へ移し、全部を移し終えるまで止めない。最後に移すのがいちばん手前にあったものなので、層の中の順は前に戻す前と変わらない。途中で「すでに位置にある」と見て止めると、先に移したものがその後ろに残って順が逆になる。どの層もこの1つの関数で前に戻すので、メニュー、入力補助(左右のソフトウェアキーボード)、ポップアップ、浮かぶウインドウのどれでも同じ性質を持つ。前に出したウインドウは自分の層の先頭に来て、上の層を越えない。メニューを`wm_lower`で後ろに下げても、メニューの層の先頭に戻る。

| 層 | ウインドウ |
| --- | --- |
| 1 普通のウインドウ | タイトルバーのあるウインドウ、全画面のウインドウ、従属ウインドウ、枠だけのウインドウ |
| 2 浮かぶウインドウ | `WM_ATTR_FLOAT`だけのもの(ピクチャインピクチャ) |
| 3 ポップアップ | `WM_ATTR_POPUP`(問い合わせのパネル、ダイアログ、カラーピッカー、プログラムが開く問い合わせのウインドウ) |
| 4 入力補助 | `WM_ATTR_AID`(ソフトウェアキーボード) |
| 5 メニュー | `WM_ATTR_POPUP`と`WM_ATTR_MENU`(メニューの一覧、部品のリスト、変換の候補) |
| (最上) ポインタ | 合成の最後に描く |

メッセージ行は、後ろから数えて最初のポップアップ、入力補助、メニュー、全画面のウインドウのすぐ後ろに置く。試験は`tests/ktest/ktest_wm.c`の`test_layers`で行い、入力補助をパネルの上に、メニュー(`WM_ATTR_MENU`のウインドウと`wm_menu_open`で開いたもの)を入力補助の上に重ね、入力補助を前に出した後も、メニューの領域の画素とその位置のウインドウ(`wm_at`)がメニューのものであることを確かめる。続けて`ly_lists`で、メニューの一覧から下位の一覧を2段開き、子が親より前にあること(重なりの順、重なる所の画素と`wm_at`)を、ソフトウェアキーボードがある場合とない場合の両方で確かめる。メニューを開いたまま、パネル、キーボード、普通のウインドウを前に出したり、別のウインドウを開いたり、親の一覧を後ろに下げたりしても、一覧の間の順が変わらないことも確かめる。

`"attr"`に右(`WM_ATTR_RBAR`)、下(`WM_ATTR_BBAR`)、左(`WM_ATTR_LBAR`)のスクロールバーを含めると、そのウインドウはスクロールバーを持つ。スクロールバーのレコード(`OB_WR_BARS`)は、右、下、左の順に並んだ`T_OBWBAR`で、それぞれ全体の範囲(`lo`〜`hi`)と、そのうちワークエリアが表示している範囲(`clo`〜`chi`)を持つ。単位はプログラムが決める。プログラムはスクロールするたびにこのレコードを書き、つまみの位置と長さを合わせる。書かれたスクロールバーは、ウインドウマネージャがその場で枠に描き直し、ワークエリアが描き直されていなくても次の画面の更新で画面に出す。タイトルとアイコンを変えたときも同じである。スクロールバーの操作はデスクトップが受け取る。つまみの前後の領域を押すと1画面分、つまみをドラッグするとその位置へのスクロールを、`OB_E_SCROLL`でプログラムに通知する。通知の`code`はどのスクロールバーか(`OB_BAR_*`)、`x`は表示範囲の先頭の移動先(範囲内に収めた値)、`y`は操作の種類(`OB_SCR_PAGE`、ドラッグ中の`OB_SCR_KNOB`、離したときの`OB_SCR_DONE`)である。ドラッグ中の通知は外観設定テーブルの`LK_SCR_LIVE`(ドラッグ中にページを追従させる)が1のときだけ送り、つまみそのものはデスクトップが動かす。スクロールバーの上でのボタンの押下はプログラムにも`OB_E_PRESS`として届くが、位置がワークエリアの外になるので区別できる。

`"sub"`を指定したウインドウは従属ウインドウになる。ウインドウマネージャは、どのウインドウを前面に出したり背面に回したりしても、従属ウインドウを常に親のウインドウのすぐ前に置く(`wm_set_parent`)。親のウインドウを移動すると、従属ウインドウも同じだけ移動する(大きさだけを変えたときは動かさない)。移動先が画面の上端より上になる従属ウインドウは上端で止める。従属ウインドウを前面に出すと、親のウインドウも一緒に前面に出て、従属ウインドウはそのすぐ前に来る。親が閉じると、従属ウインドウは独立したウインドウに戻る。タイトルバーのない従属ウインドウも、クリックすると前面に出て入力フォーカスを受け取り、枠をドラッグして移動できる。ブラウザのツールパネル(14.7)、基本表計算の操作パネル(11.13)、基本図形編集の道具パネルと実寸パネル(11.3。プロセスの基本図形編集の道具パネルとパレットも)がこれを使う。`lib/libui`のウインドウは、開く前に`ui_sub`で親のウインドウを指定すると、従属ウインドウとして開く。`ui_attr`に`UI_ATTR_UNTITLED`を付けると、題名のない枠だけのウインドウとして開く(基本図形編集のパレット)。

従属ウインドウは、親のウインドウとそれに従属するウインドウの組(親をさかのぼった先の、どれにも従属しないウインドウを根とする組)が使われている間だけ表示する。

- 使われている組は、最前面(アクティブ)のウインドウの組である。最前面のウインドウは、表示しているウインドウのうち、タイトルバーを持つか従属ウインドウであるもので、いちばん手前のもの(`active_root`)とする。ポップアップ(メニュー、問い合わせのパネル)は開いたウインドウの上に出るものなので数えず、問い合わせに答えている間もその下の組の従属ウインドウは消えない。入力の対象にならないウインドウ(`WM_ATTR_NOFOCUS`、画面キーボード)も数えない。浮かぶウインドウ(`WM_ATTR_FLOAT`、ピクチャインピクチャ)は、どのウインドウで作業していても前にあるので、入力フォーカスを持つときだけ数える。タイトルバーも親もない枠だけのウインドウ(基本図形編集のパレット)も数えない。
- ほかのアプリのウインドウを押して前に出したり、プログラムが新しいウインドウを開いたり(開いたウインドウは最前面に出る)して最前面の組が変わると、ウインドウマネージャはそれまでの組の従属ウインドウを隠す(`subs_away`)。隠しても重なり順の中の位置はそのままで、親のすぐ前にある。
- 親のウインドウ(またはその従属ウインドウ)を押すと、隠していた従属ウインドウを表示する。押したウインドウは前面に出るので(`wm_raise`は従属ウインドウなら親を出す)、親とその従属ウインドウの組がそろって最前面になり、従属ウインドウは親のすぐ前に来る。前に出たウインドウを閉じて親の組が最前面に戻ったときも同じである。1つの親に従属ウインドウが複数あるときは、その間の順は変えない。
- 判定は、重なり順と表示を変えるすべての呼び出し(`wm_open`、`wm_raise`、`wm_lower`、`wm_focus`、`wm_set_parent`、`wm_show`、`wm_close`)の最後に、ウインドウマネージャのロックの中で行う。デスクトップのウインドウにもプロセスのウインドウ(`"sub"`で作った従属ウインドウ)にも同じ決まりが働く。

どのウインドウを隠すかは次のとおりである。

| ウインドウ | 他の組が使われている間 |
| --- | --- |
| 従属ウインドウ(道具パネル、操作パネル、実寸パネル、ブラウザのツールパネル) | 隠す |
| モードレスのダイアログを従属ウインドウにしたもの | 隠す(親の組に戻れば同じ場所に出る) |
| ポップアップ(`WM_ATTR_POPUP`。メニュー、問い合わせのパネル、部品のリスト) | 隠さない。答えるまでの短い間だけ出ていて、ほかのウインドウより前にある |
| 画面の中央に出るパネル(`wm_panel_open_centre`、モーダル) | 隠さない。従属ウインドウではない |
| 基本図形編集のパレット | 隠さない。枠だけのウインドウで、開いている間はそのウインドウだけでイベントを読む(モーダル)ので、ほかの組に移ることがない |
| 基本図形編集のパターン編集 | 図形のウインドウの従属ウインドウにする。デスクトップの普通のウインドウ(DTOWN)で、開いている間も図形のウインドウの組が最前面のままなので、道具パネルも消えない |
| 独立のウインドウ、浮かぶウインドウ(`WM_ATTR_FLOAT`) | 隠さない |

隠している間の扱いは次のように決めた。

- プログラムから見た表示の有無は変えない。`wm_ref`の`visible`は表示していることを返し、隠していることは`away`で分かる。ウインドウの実身の配置のレコード(`OB_WR_PLACE`)の表示の有無も同じで、プログラムが配置を読んで書き戻しても、隠したままの状態にならない。プログラムが`wm_show`で隠したウインドウは、組が使われるようになっても隠したままである。他の組が使われている間にプログラムが表示を求めたときは、組が使われるようになるまで隠しておく。
- 隠している間は、押しても当たらず(`wm_at`)、画面の合成にも入らない。
- 親のウインドウが閉じられたら、従属ウインドウは独立したウインドウに戻り(親の番号を消す。後で同じ番号で開いたウインドウの従属ウインドウにならない)、隠していたなら表示する。プログラムが閉じ忘れたウインドウが、見えないまま残らないためである。デスクトップの道具パネルは、残っている図形のウインドウにすぐ付け替える(11.3)。
- 隠れている従属ウインドウをアプリが閉じたときは、普通に閉じる。画面に出ていないので描き直しも起きない。
- ウインドウの一覧(右ボタンのメニューの「ウインドウ」、`wm_list`)には、表示している従属ウインドウだけが出る。隠している間は出ない。親のウインドウを選べば組が戻る。ウインドウ一覧の小物はデスクトップの実身のウインドウだけを並べるので、従属ウインドウはもともと出ない。強制終了の小物は、入力フォーカスを持つウインドウとその前のポップアップを見るので、隠れている従属ウインドウは出ない。プロセスを選んで終わらせると、隠れているウインドウも一緒に閉じる(5.5)。
- 画面印刷の「最前面のウインドウ」(`wm_front_group`)は表示しているウインドウだけを組に入れる。組が使われていれば従属ウインドウは表示しているので、親と一緒に取り込む。

ほかのシステムとの比較は次のとおりである。

- Windowsの所有されたウインドウ(owned window)は、所有者より常に前にあり、所有者を前に出すと一緒に前に出て、所有者を最小化すると隠れる。所有者のアプリが非アクティブになっても隠れず、ほかのアプリのウインドウの下に見えたまま残る。前後の関係(親のすぐ前、親を前に出すと一緒に出る)はこれと同じにした。
- macOSのパネル(NSPanel)は、`hidesOnDeactivate`が真(ユーティリティのフローティングパネルの既定)だと、アプリが非アクティブになると隠れ、アクティブに戻ると現れる。隠す決まりはこれに近い。違いは単位で、macOSはアプリ単位であるが、TessronOSは親のウインドウの組の単位である。TessronOSのデスクトップは1つのタスクの中で多くのアプリ(キャビネット、基本文章編集、基本図形編集など)のウインドウを開くので、プロセスやタスクではアプリを区別できない。基本図形編集の別の図形のウインドウに移ったときは、道具パネルをそのウインドウに付け替えるので消えない(11.3)。
- 超漢字の取扱説明書は、基本図形編集の道具パネルを表示メニューの「道具パネル表示」で出したり消したりするもので、表示の状態と位置は実身に保存されると説明している。実寸パネルも同じである。パネルはその実身のウインドウのためのもので、ほかのアプリが前に出たときにどう見えるかは書かれていない。ほかのアプリが使われている間に隠すことは、利用者の指示による決まりで、説明書の記述とは食い違わない(表示メニューで消した道具パネルは、組が戻っても出ない)。

ウインドウはそれを作ったプロセスを記録していて、プロセスが終了するとシステムが閉じる(5.5)。

ウインドウの枠は、ウインドウマネージャが持つ1つの描画環境を、描くたびにそのウインドウのピクセルに向けて描く。枠を描くのはウインドウを開いたり動かしたりしたタスク(プロセスのタスクのこともある)である。この描画環境は専用のロックで守り、向け先の設定から描き終わるまでを1つの操作にする。守らないと、2つのタスクが同時に枠を描いたとき、一方の向け先に他方の範囲で描き、ウインドウのピクセルの末尾を越えて書き込む。ロックの順序はウインドウマネージャのロック(`wm_mtxid`)が先である。ポインタはこの描画環境を使わず、ウインドウマネージャのロックの中でバックバッファに直接置く(10.4.3)。

試験が画面をコピーするときは`wm_copy_screen`を使う。ウインドウマネージャの排他の中で画面全体をコピーするので、画面を組み立て直している途中の状態はコピーされない。画面の一部をコピーするときは`wm_grab_screen`を使う。同じ排他の中で矩形をコピーし、ポインタを除くときは、ポインタを置いたときに取っておいたその下の画素でポインタの部分を置き換える。画面印刷(11.24)がこれを使う。プロセスからはSVC`wm_grab_screen`(クラス9の38)で呼ぶ。カーネルは矩形を64K画素までの帯に分けて、帯ごとに同じ排他の中でカーネルのメモリに写し、それをプロセスのメモリに写す。帯の間に画面が組み立て直されることはあり得るが、動画として流す画面の共有では問題にならない。ブラウザは、利用者が許可のパネルで画面の共有を許したときだけこれを呼ぶ(14.4.8)。

### 10.4.1 ウインドウの見た目と合成

画面はオフスクリーンバッファの中で、背景から奥のウインドウの順に組み立てる。ウインドウはそれぞれ自分のピクセルバッファを持つので、手前のウインドウを透かして奥を見せるときも、奥のウインドウのプログラムに描き直しを求めない。組み立ては変化した部分だけで行う。変化した部分は1つの外接矩形にはまとめず、最大16個の別々の矩形(部分)として集め、部分ごとに組み立ててそれぞれ画面に送る。重なるか近い2つの部分は、両方を囲む矩形が2つの面積の和より8192画素以上大きくならなければ1つにまとめる。部分を1つ組み立てるたびにウインドウの並びをたどる手間がかかるので、小さな隙間はまとめて組み立てたほうが安い。16個を超えたときは、新しい部分を、まとめたときに増える面積が最も小さい部分にまとめる。部分どうしは重なってもよい。どの部分も背景から組み立て直すので、2つの部分に含まれる画素は2度組み立てても同じ値になる。`wm_update`は、ウインドウごとの損傷(`wm_damage`)と、ウインドウの開閉、移動、前後の入れ替え、不透明度と色の変更、枠の描き直しで変わった場所(影の届く範囲を含む)と、ウインドウの描画環境で描いた矩形(10.2)をこうして集め、ポインタはそのあとで動かす(10.4.3)。外観の設定、配色、壁紙を変えたときは画面全体を変わった場所に加えるので、そのあとの`wm_update`は画面全体を組み立てる。ドラッグ中の枠線(`wm_set_drag`)を動かしたときは、前後の枠線の4辺だけを部分にするので、枠線の内側は組み立て直さない。

見た目の設定は外観設定テーブルの9100〜9116で、枠かタイトルバーを持つウインドウにだけ掛かる。メニューやポップアップの一覧は自分で影を描き、透過させないので対象外である。設定を変えると、開いているすべてのウインドウにすぐ反映される。

既定値では不透明で、角も影もない。プログラムが`wm_set_opacity`で自分のウインドウに設定した不透明度と`wm_set_tint`の色は、この設定とは別に掛かる。不透明度は両者の積になる。

1つのウインドウは次の段階で重ねる(`outer_kernel/wm/compose.c`)。各段階は、ウインドウの外形、ワークエリア、ピクセル、部分ごとの不透明度、角の半径、重ねる色、影、ぼかしをまとめた記述(`T_CPWIN`)だけを入力とし、ウインドウマネージャの内部の表は参照しない。GPUで合成するとき(10.4.2)は、同じ記述を受け取って同じ段階をGPUで行う。

1. 影。外形を影のずれだけ動かした角丸の矩形の内側を最も濃くし、外側では影の幅にかけて直線的に薄くする。ウインドウ自身の下には影を落とさない。半透明の枠から自分の影が透けて見えないようにするためで、覆われる部分は計算もしないので、手間は影の帯の分だけである。濃さは、角丸の矩形の直線部分からの横と縦の距離だけで決まり、どちらかが角の半径と影の幅の和に達すれば0になる。そこで影を落とすたびに、その範囲の距離の組ごとの濃さの表(最大65×65)を先に作り、画素ごとには表を引く。画素ごとに平方根を求めていたときと結果は画素ごとに一致する(`ktest_wm`の`test_shadow_same`が300個のウインドウの外側の全画素で確かめる)。
2. ぼかし。不透明度が255未満の部分について、その下に見える画面(それまでに重ねた背景と奥のウインドウ)をぼかす。ぼかすのは透ける部分だけで、不透明なら何もしない。枠だけを透かす設定なら、手間は枠の帯の分だけである。求め方は次の段落で述べる。
3. 合成。ウインドウをワークエリアと、上、下、左、右の枠の帯の5つに分け、それぞれの不透明度で背後と混ぜる。枠だけを透かす設定のワークエリアは行単位のコピーである。角は1ドットを64点でサンプリングした被覆率で背後と混ぜるので、輪郭が階段状にならない。ポインタの位置からウインドウを探すときは、被覆率が半分以上のドットからなる形を使う。辺に沿って走る線は、角を切る円と同じ中心で1ドットずつ内側の円に沿って描き直すので、枠は角で切り取られたようには見えず、角に沿って曲がる。描き直す深さは角の辺ごとに決める。スクロールバーのない辺では、枠の帯だけでなく、その内側に沿って描かれたもの(パネルがワークエリアの周りに描く太い枠など)も含めて角の範囲すべてを曲げる。スクロールバーのある辺と、タイトルバーのある上の辺では、外側の輪郭線とその内側の線の2本だけを曲げる(バーとタイトルの帯は線ではなく、帯にはピクトグラムがある)。それぞれの線の色は、角のすぐ外の2つの辺(縦の辺と横の辺)の画素から読み、角の中の各サンプルはより近い方の辺の線を取る。この描き直しはウインドウ自身の画素に対して組み立てのたびに行い、描き直しても結果が変わらないので、プログラムが角の中に描いたものも直り、GPUとCPUのどちらの合成も同じ画素を読む。
4. 色。枠の帯とタイトルバーに重ねる色は、合成の直前に掛ける。ウインドウのピクセルには描き込まないので、色を変えても枠を描き直す必要はなく、ウインドウを動かした跡にも色が残らない。

ぼかしは、縦横を半分ずつにした画像の段(レベル)を通して求める。レベル0は画面そのもので、レベルkの画素(x, y)は画面の(x×2^k, y×2^k)から2^k×2^kドットの範囲に当たる。この対応は組み立てる範囲によらず画面の位置で決まるので、ある画素の値は画面をどう分けて組み立てても同じになる。透ける部分ごとに、次の縮小を深さdの回数だけ行ってレベルdまで下り、レベルdで平滑化し、拡大をd回行ってレベル0に戻る。

| 処理 | 内容 |
| --- | --- |
| 縮小 | レベルkの画素を、レベルk−1の対応する位置の周りの4×4画素から、縦横それぞれ1、3、3、1の重み(合計64)で求める |
| 平滑化 | レベルdの画素を、同じレベルの周りの5×5画素から、縦横それぞれa、b、m、b、aの重み(各合計64)で求める。aが0なら3×3画素である |
| 拡大 | レベルk−1の画素を、レベルkのうち自分の中心に近い2×2画素から、近い方を3、遠い方を1の重み(縦横それぞれ合計4)で求める |

各処理はチャネルごとの重み付きの和を一度だけ丸めて8ビットに戻す。どの画素も1つ前のレベルの数画素だけから決まるので、GPUでは1画素を1つのフラグメントで求めて並列に処理でき、CPUと同じ値になる(13.10)。読む画素は、そのレベルのうち組み立てる範囲に掛かる画素に限り、その外は端の画素を繰り返す。CPUでは各処理を行方向と列方向に分けて行い、3つのチャネルを64ビットのワードの21ビットずつの区画に入れて同時に足す。最も大きい和(4096×255)でも区画からあふれない。

設定値rは、半径rの箱型の平均(2r+1画素の平均)と同じ広がり、すなわち方向ごとの分散r(r+1)/3(画素の2乗)になるように、深さと平滑化の重みに対応させる。縮小と拡大をd回ずつ行うと分散は(4^d−1)/2になり、レベルdの平滑化は自身の重みの分散の4^d倍を加える。深さは、縮小と拡大だけの分散がr(r+1)/3を超えない最も深いものとし、残りを平滑化で補う。平滑化の重みは64分の1単位で、中央が隣より小さくならないように選ぶ。どのrでも、求めた分散は目標と0.9以内で一致する。重みは中心が重く裾が滑らかに減るので、同じ分散の箱型の平均よりも輪郭がやや締まって見えるが、縞やブロック状の跡は出ない。

届く距離は、ある画素のぼかしが読む画面の画素までの最大の距離で、縮小と拡大の3(2^d−1)ドットに、平滑化の片側の画素数(aが0でなければ2、そうでなければ1)の2^d倍を加えたものである(`cp_spread_reach`)。CPUの手間は、ホストでの計測で、600×400のウインドウの枠だけをぼかすときr=2〜6で箱型の平均の0.7〜1倍、420×300のウインドウ全体をぼかすときr=2〜16で0.6倍前後である。枠の細い帯は周りのレベルの画素を余分に求めるので、r=16の枠だけのぼかしは箱型の平均の約1.5倍になる。

ぼかしは、組み立てる矩形の外側の画素も使う。一部の矩形だけを組み立てるときに透けてぼかすウインドウがその近くにあれば、届く距離にそうしたウインドウの数を掛けた幅だけ広い範囲を背景から組み立て、広げた縁の部分は組み立てる前の内容に戻す。数を掛けるのは、手前のウインドウがぼかすのは奥のウインドウがぼかした結果で、その分だけ遠くの画素に依存するからである。数えるのは広げた範囲の近くにあるウインドウで、広げると数が増えることがあるので、数が変わらなくなるまで繰り返す。逆に、ある部分の内容が変わると、その上で透けてぼかすウインドウでは、変わった部分から同じ幅だけ離れた画素まで見え方が変わる。そこで`wm_update`は、ウインドウの損傷と変わった場所を、同じ求め方の幅だけ広げてから部分として集める。こうすると、一部を組み立てた結果と画面全体を組み立てた結果が一致する。ぼかしを使わないとき(`LK_BLUR`が0、既定)は広げない。

手前のウインドウが奥のウインドウを影ごと覆うときは、奥のウインドウを重ねない。覆っているとみなすのは手前のウインドウの不透明な部分だけで、枠を透かすならワークエリア、角を丸めるなら角の行を除いた範囲である。ウインドウを開閉、移動、前面と背面の入れ替え、表示と非表示の切り替えをしたときは、影の届く範囲まで組み立て直す。

一部だけが覆われているウインドウも、見えている所だけを処理する(`cp_lay`)。手前のウインドウが不透明に描く画素は、そのウインドウの画素(重ねる色を掛けたもの)だけで決まり、背後の値によらない。そこへ奥のウインドウが落とした影や混ぜた画素は、手前のウインドウを重ねたときに消えるので、初めから処理しなくてよい。ほかの画素を読むのはぼかしだけで、ぼかしはそれまでに重ねた背景と奥のウインドウを読む。そこで、ぼかしが読む画素だけは、手前に不透明なウインドウがあっても奥のウインドウを重ねておく。

部分を組み立てるとき、最初のポップアップより奥のウインドウの並び(最大64個、超えた分は最も奥から従来どおりに重ねる)を手前から順に調べ、不透明に描かれる範囲を矩形の集まりとして集めていく。

1. ウインドウが届く範囲(外形、影、5つの部分)からこの集まりを切り取った残りが、そのウインドウの見えている所である。残りは最大16個の矩形で、それを超える切り取りは行わない。
2. 見えている所のうち透ける部分をぼかすなら、その部分を届く距離だけ広げた範囲を集まりから取り除く。そのウインドウの影は、見えている所に加えてこの範囲にも落とす。ぼかしが自分の影を落とした画素を読むためである。
3. そのウインドウが不透明に描く範囲を集まりに加え、2.の範囲をもう一度取り除いてから、奥のウインドウへ進む。不透明に描く範囲は、不透明度が255で透過色を使わない部分(全体が不透明なら外形)から、角を丸めるときの四隅の正方形を除いたものである。角の行のうち両端の角の間は不透明である。開閉の動きの途中のウインドウと独自の外形を持つウインドウは、不透明に描く範囲を持たない。

集まりは最大64個の矩形で、あふれたときは小さい矩形から捨てる。矩形を捨てたり切り取りを省いたりしても、処理する範囲が広がるだけで結果は変わらない。そのあと奥から順に、各ウインドウの影、ぼかし、合成を見えている所の矩形の中だけで行う。1つのウインドウでは、すべての矩形に影を落としてからぼかしをすべて求め、そのあとで合成する。ぼかしの各段は、矩形の中でも部分全体を読める範囲として求めるので、ある画素の値は矩形の分け方によらない。こうすると、ぼかしが読む画素は奥から順にすべてを重ねたとき(`cp_window`を並びの順に呼ぶ)と同じ値を持ち、組み立てた画面は画素ごとに一致する。GPUの起動時の確認(13.10.6)は`cp_window`を順に呼んだCPUの結果と比べるので、確認の基準も変わらない。GPUの実装は、1つのジョブの中で後のコピーが書き直す所を描かない(13.10.5)。CPUの実装も同じ考え方であるが、ぼかしが読む範囲だけを除くので、ぼかしのところで区切らずにウインドウの並び全体で隠れた所を省く。

QEMU(TCG、4コア、1280×800)で、ずらして重ねたウインドウを組み立てた時間は次のとおりである(カーネル試験の`test_hide_same`と`test_hide_time`、NEONの処理、ミリ秒)。

| 場面 | 従来 | 見えている所だけ |
| --- | --- | --- |
| 段階だけ、640×420の8個、不透明で角なし | 6.4 | 4.3 |
| 段階だけ、同じ8個、枠を透かし角を丸め影とぼかし | 27.5 | 19.2 |
| 段階だけ、同じ8個、全体を透かし角を丸め影とぼかし | 104 | 104〜109 |
| 合成タスクの画面全体、6個、不透明で角なし | 6.7 | 5.1 |
| 合成タスクの画面全体、6個、枠を透かし角を丸め影とぼかし | 23.6 | 16.8 |
| 合成タスクの画面全体、6個、全体を透かし角を丸め影とぼかし | 76.2 | 74.7 |

全体を透かすときは不透明な所がないので省けるものがなく、手間は従来と同じである。段階だけを測ると0〜5%遅く、合成タスクで測ると速いことも遅いこともある。従来の処理で枠を透かす8個の場面を段階ごとに測ると、背景のコピー1.1、影7.0、ぼかし11.7、合成8.1ミリ秒で、省いたのは隠れたウインドウの影とぼかしと合成である。`cp_hide_use`で省くのを止めると従来の処理になり、`cp_hidden`は省いた画素数を数える。

開閉の動きでは、開くウインドウを外形の236/256の大きさと72/255の濃さから元の大きさと濃さへ、閉じるウインドウをその逆へ、指定の時間で変化させる。進み具合は時刻から求めるので、処理が遅れても動きの時間は延びず、途中の段階が省かれる。閉じたウインドウはピクセルだけを残して動きが終わるまで重ね、終わったら解放する。動きの間は、ウインドウマネージャのタスク(優先度21)が、動いているウインドウの範囲の組み立てを16ミリ秒ごとに合成タスクに頼む(10.4.4)。組み立てを待たないので、動きの途中の段階は合成タスクが組み立てるたびにまとめて進む。

設定はデバイス設定の実身(`SYSDEF_CONF_DEV`)のレコード1に、`WIN_LOOK`、`WIN_OPACITY`などの行(`cf_look_items`)として保存する。`LK_GPU`の行は`WIN_GPU`である。起動時と、その実身が書き換えられたときに監視タスクが読み直して反映する。プロセスが`wm_set_look`でこれらの番号を書くと、範囲を確かめてからすべてのウインドウに反映し、画面を組み立て直す。

### 10.4.2 合成の実装

合成の段階には2つの実装がある。どのマシンでも使えるのはCPUによる実装(`compose.c`)で、QEMUとRaspberry Pi 4は常にこれで合成する。CPUの実装は、合成タスクの中ではNEONの命令で内側のループを処理する(10.4.4)。Raspberry Pi 5では、`V3D=2`または`V3D=3`でビルドしたとき、V3DのドライバがGPUによる実装を`cp_gpu_set`で登録する(13.10)。登録のインタフェース(`T_CPGPU`)は次の4つである。

| 項目 | 内容 |
| --- | --- |
| `align` | GPUが組み立てる範囲の左端の単位(ピクセル)。V3Dでは16(64バイト) |
| `wants` | その大きさの範囲をGPUで組み立てる価値があるか。起動時の確認(13.10.6)に通っていなければ常に偽 |
| `lay` | 背景と、奥から数えたウインドウの並び(`T_CPWIN`、最大64個)を受け取り、背景と並びの先頭から何個のウインドウを重ねたかを返す。失敗したら負の値を返し、何も重ねていないものとして扱う |
| `note` | 1回の組み立てにかかった時間を通知する。GPUの側が、GPUの組立ての時間の内訳(13.10.7)とあわせて統計としてコンソールに出す |

組み立てる部分が複数あるときは、部分ごとに次の判断をする。大きな部分はGPUで、小さな部分はCPUで組み立てることがある。`LK_GPU`が1で、登録された実装があり、その部分について`wants`が真のとき、部分の左端を`align`の倍数に、右端を倍数か画面の右端に広げる。広げた範囲も画面全体を組み立てたときと同じ内容になるので、広げた分も画面に送ってよい。次に、奥から順にウインドウを調べ(覆われていて重ねないものは除く)、最初のポップアップ(メニューや一覧)の手前までを`lay`に渡す。GPUが背景とその先頭からn個を重ねたら、CPUはn+1個目から後(メッセージ行、ポップアップ、閉じつつあるウインドウ、ドラッグ中の枠線を含む)をこれまでどおりに重ねる。このとき最初のポップアップまでのウインドウは、GPUの結果の上で見えている所だけを処理する(10.4.1)。ポインタはすべての部分を組み立てたあとで置く(10.4.3)。`lay`が失敗したときは、背景からすべてをCPUで組み立てる。GPUが重ねないウインドウ(独自の外形を持つもの)があれば、そこから後はCPUが重ねる。`lay`に渡した範囲のバックバッファの内容は、それまでCPUのキャッシュにあって書き戻していない値も含めて捨てられる(GPUが範囲のすべてのピクセルを書き直すため、13.10.5)。V3Dの実装は、範囲のうちどのウインドウもかからない所の背景を、GPUが働く間に`lay`の中でCPUがコピーすることがある。`lay`が返ったときの範囲の内容は、どちらが組み立てても同じである。範囲のうち後で元に戻す部分(ぼかしのために広げた縁、`cp_margin_keep`)は、`lay`の前に読んで取っておく。

小さな範囲(キャレットの点滅など)はCPUのほうが速い。`wants`は、起動時の確認で測った、GPUがCPUより速くなる範囲の大きさ(画素数)を閾値にし、見た目の効果を使うかどうかで2つの閾値を使い分ける。`note`は部分ごとに呼ぶ。

`wm_stat`は、組み立てた回数、重ねたウインドウと省いたウインドウの数に加えて、組み立てた部分の数、組み立てた画素数(ぼかしのために広げた縁を含む)、ポインタを新しい場所に置いた回数と、そのうち何かを組み立てたときの回数を返す。ウインドウマネージャは、組み立てか移動があった間、60秒ごとに次の形の1行をコンソールに出す。組み立てた画素数と送った画素数は1秒あたりの値も出す。Hは、手前の不透明なウインドウに隠れていて処理を省いたウインドウの画素数(千画素単位、10.4.1の`cp_hidden`の増分)で、同じ画素を複数のウインドウの分だけ数えるので、組み立てた画素数を超えることがある。末尾は画面ドライバの送りで、送りの回数Dと1回あたりの時間(マイクロ秒)、面を切り替えた回数F、切り替えが効くのを待った回数Wと1回あたりの時間(10.2.1)である。1面の画面ではFとWは0になる。

```
wm: in T s: B builds (P parts), X kpx built, X/T kpx/s, H kpx of windows hidden and left out; R rects sent, S kpx, S/T kpx/s; pointer moved M times, N with something built; D sends of U us each, F flips, W waited for a flip, V us each
```

### 10.4.3 ポインタ

ポインタは、組み立てた画面の上にバックバッファへ直接置き、置く前にその正方形の下にあった画素を取っておく(`pointer.c`)。ポインタだけが動いたときは、取っておいた画素を元の場所に戻し、新しい場所の画素を取ってからポインタを置き、その2つの正方形だけを画面に送る。ウインドウは1つも組み立て直さない。どのウインドウマネージャの組み立ても、組み立てる部分(ぼかしのために広げた縁を含む)がポインタの正方形にかかるときは、先にポインタを取り除いて下の画素を戻し、部分を組み立て、最後に新しい下の画素を取ってからポインタを置き直す。こうすると、取っておく画素は常にその場所のウインドウの見え方(ドラッグ中の枠線を含む)と一致し、バックバッファを読む試験やスクリーンショットには、画面全体を組み立てたときと同じ画面が見える。ポインタの形(`wm_set_pointer`)や大きさ(`LK_PTR_SIZE`)が変わったとき、表示を消したとき(`wm_show_pointer`)も、次の`wm_update`か`wm_pointer_moved`で同じように取り除いて置き直す。ポインタを置く場所は、その時点で入力層が返す位置(`ts_hid_pointer`)である。入力層はポインタの移動を受け取るたびに合成タスクを起こし(`knl_wm_pointer_hint`)、合成タスクは次の組み立てでポインタをその時点の位置に置く。ポインタを動かすのはイベントを読むプログラムではないので、デスクトップが重い処理をしている間もポインタはマウスに従う。`wm_pointer_moved`も組み立てを頼むだけで、待たずに戻る。`wm_pointer_last`は最後に置いた正方形の左上と大きさを返し、まだ一度も置いていなければ偽を返す(このとき`wm_update`は画面全体を組み立てる)。画面の解像度が変わったときは、取っておいた画素を捨ててから画面全体を組み立てる。

ポインタの形は16種類(`WM_PT_SELECT`〜`WM_PT_MENU`、`include/ts/wm.h`)で、どれも24画素四方の手の絵である。白い手を黒い線で縁取り、多くの形は動作の向きを示す黒い印(縁は白)を添える。1つの形は2枚の面(どの画素を置くかのマスクと、置く画素のうちどれが黒かの本体)でできている。普通の形は指先で、ほかの形は印の中心で指す(ホットスポット)。大きさ(`LK_PTR_SIZE`)や画面の倍率が違うときは、描いた形から最近傍の点で作る。ウインドウの右下の角(大きさを変える部分)に乗ったときは、デスクトップがつかむ形(`WM_PT_GRIP`)にし、離れると普通の形に戻す(11.1「ウインドウの右下の角と全画面表示」)。角をドラッグする間は大きさを変える形(`WM_PT_PICK`)、タイトルバーでの移動の間は移動の形(`WM_PT_MOVE`)、スクロールバーのつまみを持つ間は向きのあるつかむ形(`WM_PT_VGRIP`、`WM_PT_HGRIP`)になる。

Raspberry Piのファームウェアには、メールボックスのプロパティでハードウェアカーソルを使うタグ(0x00008010で形とホットスポット、0x00008011で表示と位置)がある。文書にある条件は32ビットARGBの画像をVideoCoreのバスアドレスで渡すことで、どの機種とどの表示経路で働くかは書かれていない。Pi 5のファームウェアが用意するフレームバッファで働くかは確かめていないので、使っていない。

### 10.4.4 合成タスク

画面を組み立てるのは、ウインドウマネージャの合成タスク(優先度10)だけである。入力(USBの管理タスク、優先度8)とGPU(優先度9)より低く、デスクトップやプロセスのタスクより高い。`wm_composite`、`wm_composite_at`、`wm_update`、`wm_set_drag`を呼んだタスクは自分では組み立てず、何を組み立ててほしいか(画面全体、矩形、変化した所)を記録して合成タスクを起こし、その組み立てが終わるまで待つ。組み立ては1更新に1回までである。2面を切り替え、切り替えが効いたことが画面から分かる(帰線を待てるか、効くまでの時間が決まっている)ときは、組み立てた画面の送りが前の切り替えが効くのを待つので(10.2.1)、その待ちが画面の更新に合わせて1更新に1回に揃える。`ts_disp_paced`はそのときの更新の周期を返し、合成タスクは自分では待たずに、依頼が来ればすぐに組み立てる。合成タスクも間隔を取って待つと、自分の待ちの後に送りの待ちが重なり、その間に帰線を1回逃して、1フレームを2更新続けて表示することがある。それ以外の画面では、組み立てを始める時刻を`WM_FRAME_US`(16667マイクロ秒、60Hzの1フレーム)おきの位置に合わせる。次の位置は前回の組み立てを始めた時刻ではなく前回の位置から数え、マイクロ秒の単位で眠る(`tk_dly_tsk_u`)。前回の開始から数えて残りをミリ秒に切り上げて眠っていたときは、ウインドウに描いては`wm_update`することを続けても、QEMUで組み立ての間隔が17.6ミリ秒(毎秒56.8回)になり、疑似的な更新で2面を切り替えても同じだった(`test_pace`)。今は16.66ミリ秒である。位置に遅れて始めたときも次は次の位置で始めるが、前回の開始から半フレームは空ける。1フレームより長く依頼がなかったときは、依頼が来ればすぐに組み立て、そこから位置を数え直す。待つ間に届いた依頼は、次の1回の組み立てにまとめる。1フレームのうちに10回変化しても、組み立ては1回である。

変化した所は、依頼を受けた時ではなく組み立てを始める時に集める。ウインドウの損傷(`wm_damage`)、ウインドウの開閉や移動などで変わった場所(`wm_gone`)、ウインドウの描画環境で描いた矩形(10.2)である。描いた矩形はタスクごとに分けて持ち、そのタスクが組み立てを依頼したときに初めて組み立ての対象にする。ほかのタスクの依頼やポインタの移動による組み立てで、描いている途中のウインドウ(ページを塗りつぶして文字をまだ描いていない状態)が画面に出ないようにするためである。

| 関数 | 動作 |
| --- | --- |
| `wm_composite` | 画面全体の組み立てを依頼し、終わるまで待つ。外観、配色、壁紙、解像度のように画面全体が変わるときに使う |
| `wm_composite_at` | 矩形の組み立てを依頼し、終わるまで待つ |
| `wm_update` | 変化した所の組み立てを依頼し、終わるまで待つ |
| `wm_post` | `wm_update`と同じ依頼をして、待たずに戻る。すぐに描き直さない呼び出し元(開閉の動きのタスク)が使う |
| `wm_flush` | それまでにどのタスクが依頼した組み立ても終わるまで待つ |
| `wm_pointer_moved` | 組み立てを依頼して待たずに戻る。ポインタは組み立てのたびにその時点の位置に置く |

待つのは、続けて描き直す呼び出し元の描きかけを合成タスクが読まないようにするためと、試験が戻った直後のバックバッファを読めるようにするためである。待つ呼び出し元はそれぞれセマフォ(16個)で待ち、合成タスクは組み立てを終えると、その組み立てで済んだ依頼の待ち手だけを起こす。16個を超えたときは1ミリ秒ごとに確かめる。合成タスクがない間(起動の途中と、作れなかったとき)と、合成タスク自身が呼んだときは、呼び出し元がその場で組み立てる。ロックは、ウインドウマネージャのロック(`wm_mtxid`)、描いた矩形を守るロックの順に取る。描いた矩形のロックは最後に取るロックで、描画管理から呼ぶときは描画管理のロックを持っていない。組み立ての間は、これまでどおりウインドウマネージャのロックと画面の保留(`ts_disp_hold`)を持ち、GPUで組み立てるときはGPUの処理が終わるまで合成タスクが待つ。

デスクトップは、キャレットや選択枠の点滅、ウインドウのドラッグ中の移動、メニュー、パネル、ツールのウインドウ、ダイアログのような部分的な変化に`wm_update`を使い、`wm_composite`は起動と終了、解像度の変更、試験からの外観の変更だけで使う。キャレットの点滅では、ウインドウの描画環境の表示範囲をキャレットの矩形に絞ってページを描き直すので、画面に送るのもキャレットの矩形だけである。スクロールバーは、値が変わらなければ描き直さない(`wm_set_bar`)。

合成タスクは`TA_FPU`で生成するので、浮動小数点とSIMDのレジスタを持つ(4.2)。CPUの合成の内側のループは、合成タスクの中ではNEONの命令(`outer_kernel/wm/compose_simd.c`)で処理する。行のコピー(背景、不透明な行、ぼかしのために広げた縁の保存と復元)、不透明度による混合、枠とタイトルバーに重ねる色、プログラムの色、角の行のうち被覆率が255の中央、影の濃さ(濃さの計算は従来どおり1画素ずつ行い、暗くするところだけを4画素ずつ行う)、ぼかしの縮小、平滑化、拡大である。混合の255での割り算は、v+1+(v>>8)を8ビット右に送る計算で、v<65535で正確に一致する(混合の最大は255×255+127)。ぼかしの和は1チャネルを16ビットの区画に入れ、平滑化の列方向だけ32ビットで足す。どの処理も従来のCPUの処理と同じ画素を書く。`compose.c`は、そのタスクがNEONを使えると登録されているか(`cp_simd_allow`)を部分ごと、行ごとに確かめ、ほかのタスク(GPUの起動時の確認など)から呼ばれたときは従来の処理を使う。`compose_simd.c`だけは`-mgeneral-regs-only`と`-mstrict-align`を外してビルドする。`-mstrict-align`のままでは16バイトのロードとストアが4バイトずつに分けられる。扱うのはどれも通常のメモリで、整列の検査(`SCTLR_EL1.A`)はしていない。フレームバッファへの転送はデバイスのメモリへの書込みで整列が要るので、画面ドライバの従来のコピーのままにしてある。

カーネル試験の`wm`の組には、20回の依頼が1〜2回の組み立てにまとまること(`test_coalesce`)、描画環境で描いただけの部分が次の`wm_update`で画面に出ること、入力層だけでポインタが動くこと、乱数で作った100の場面(ウインドウ1〜4個、不透明度、角の丸み、影、ぼかし、色、透過色、組み立てる範囲を変える)でNEONと従来の処理の結果が1画素も違わないこと(`test_simd_same`)、画面全体を両方で組み立てて同じになること(`test_simd_time`)を確かめる試験がある。見えている所だけを処理すること(10.4.1)については、乱数で作った200の場面(ウインドウ2〜12個、多くは全体か枠が不透明、一部は開閉の途中、NEONと従来の処理を交互に、組み立てる範囲を変える)で、`cp_lay`の結果が`cp_window`を順に呼んだ結果と1画素も違わず、省いた画素があること(`test_hide_same`)、画面の大きさで8個のウインドウを3つの見た目で組み立てて両方が同じになること、合成タスクで6個のウインドウを画面全体について両方で組み立てて同じになること(`test_hide_time`)を確かめ、それぞれの時間を出す。

QEMU(TCG、4コア、1280×800)でデスクトップを操作して測った値は次のとおりである(`tools/ui_run.py`の`stat`と`lag`。組み立てた画素数は千画素単位)。

| 操作 | 変更前 | 変更後 |
| --- | --- | --- |
| 何もしない5秒 | 6回、6144 | 6回、1未満 |
| 文書を開いてキャレットが点滅する5秒 | 7回、6145 | 6〜7回、1未満 |
| キャレットの点滅中に4秒ポインタを動かしたときの最大の遅れ | 38ミリ秒 | 6ミリ秒 |
| 同じ間の組み立て | 5回、5120 | 4回、1未満 |
| 10文字の入力(落ち着くまで) | 30回、24725 | 20回、5607 |
| ウインドウのドラッグ(12段階) | 12回、12288 | 11〜12回、5778 |

TCGはNEONの命令を1命令ずつ補助関数で模擬するので、QEMUではNEONの処理は従来の処理と同じ程度の速さで(画面全体の組み立ての段階だけで、不透明で角のない3つのウインドウが1.4ミリ秒対1.1ミリ秒、見た目の効果を全部使うと37ミリ秒対43ミリ秒)、差は測れない。実機の速さは`test_simd_time`と`test_simd_same`が出す値で確かめる。

### 10.4.5 フレームの歩調の測定

アニメーションのように続けて描くプログラムが毎秒60フレームに届かないとき、どこで1フレームを越えたかを、合成タスク、画面ドライバ、プログラムの3か所で数える。

ウインドウマネージャは`wm_frames`(`T_WMFRAMES`)で、組み立ての回数、続けて始めた組み立て(前の開始から`WM_APART_MS`(100ミリ秒)以内)の間隔の合計と最大、そのうち更新1.5回分より間が空いた回数、ウインドウを重ねるのにかかった時間(合計と最大)、組み立てた画面の送りにかかった時間(前の切り替えが効くのを待つ時間を含む)、間隔を取るために眠った時間、組み立てを待った呼び出し元(`wm_update`など。プログラムがフレームを出す`wm_obj_put`もこれで待つ)の回数と時間を数える。画面ドライバは`ts_disp_frames`(`T_DISPFRAME`)で、更新の周期、切り替えの回数、切り替えの間が更新何回分だったか(四捨五入して、半分未満、1、2、3、4以上)、帰線の時計があるときに切り替えが帰線の終わりから更新のどの4分の1で行われたか、前の切り替えが効いたかを確かめた送りの数、そのうち時計で効いたと分かって待たなかった数、画面を見て帰線を待った数、見て待った時間と眠った時間、時計から外れた帰線の数を数える。

組み立てが毎秒20回以上続く間は、10秒ごとに次の2行をコンソールに出す(`WM_FRAMES_MS`、`WM_FRAMES_MIN`)。Raspberry Pi 5ではCOM3に出る。数値は例である。

```text
wm: frames: in 10000 ms 600 builds, 60.0 a second; 16666 us apart (most 17200), 0 over a refresh and a half; laying 900 us (most 2100), sending 13800 us (most 16500), asleep for the pace 0 us, a build each; 600 waits for a build, 14500 us (most 16900)
disp: frames: refresh 16667 us; 600 flips, refreshes apart 0:0 1:600 2:0 3:0 4+:0; quarter after the blank 598/2/0/0; 600 sends during a flip: 0 taken by the clock, 600 waited (watching 1100 us, asleep 11500 us each), 0 blanks off the clock
```

小物「歯車」は、5秒ごとの行に、1フレームを描く呼び出し(GPUの仕事を積むだけの部分)の時間と、`eglSwapBuffers`の時間(GPUの仕事の終わりを待ち、ウインドウの画素へコピーし、その画面が組み立てられて送られるまで待つ)の平均と最大を加える。

```text
glgears: 300 frames in 5.0 seconds = 60.0 fps (320x280); drawing 400 us (most 900), eglSwapBuffers 16000 us (most 17000) a frame
```

読み方は次のとおりである。

| 見る所 | 分かること |
| --- | --- |
| `disp: frames:`の`refreshes apart`が1以外に多い | 2なら切り替えが1回の帰線を逃した。0なら1更新に2回切り替えている(帰線を待てていない) |
| `taken by the clock`が多い | 送りが前の帰線の後に来た。時計がなければ、その分だけ更新1回分を余計に待っていた |
| `blanks off the clock`が0でない | 帰線の時計が外れている。`hvs: clock:`の行の周期と帰線の長さを見る |
| `quarter after the blank`が後ろの4分の1に寄る | 送りが帰線の直前に終わっている。重ねる時間かコピーする時間を減らす余地がある |
| `wm: frames:`の`apart`が更新より長く、`asleep for the pace`が0 | 組み立てが依頼を待っている。プログラムのフレームが遅い |
| `sending`が長く`watching`と`asleep`の和に近い | 送りの時間のほとんどは前の切り替えが効くのを待つ時間で、待つ相手は画面の更新である |
| `glgears:`の`eglSwapBuffers`から`wm: frames:`の`waits for a build`の時間を引いた残り | GPUの仕事の終わりを待つ時間とウインドウの画素へコピーする時間 |
| `glgears:`の`drawing`と`eglSwapBuffers`の和が更新より長い | プログラムのフレームが1更新に収まっていない。合成や送りではなくプログラムかGPUの側を見る |

カーネル試験の`disp`の組の`test_blank`は、疑似的な更新(16667マイクロ秒)で、切り替えの直後の送りがその切り替えを取る帰線の終わりまで待ってそれ以上は待たず、その切り替えが更新の最初の4分の1に入ること、切り替えから17.8ミリ秒後(帰線の後で、効いたとみなす時間の内)の送りが待たずに時計で効いたと分かること、30回続けた送りが更新1回分ずつ間を空け、帰線の前に眠ること、時計が外れないことを確かめる。`wm`の組の`test_pace`は、ウインドウに描いては`wm_update`することを60回繰り返し、1面で送る画面では合成タスクが16667マイクロ秒おきの位置で組み立て、60フレームが1秒(60×16667マイクロ秒)と30ミリ秒の内に収まること、疑似的な更新で2面を切り替える画面では合成タスクが眠らず、切り替えが1更新に1回(更新1回分の間)になることを確かめる。

### 10.4.6 指の押下とつまみの当たり

ウインドウの右下の角、仮身の右端と下端、選んだ図形のつまみ、線の端、変形のつまみは、マウスに合わせて数画素の広さしかない。指は触れるたびに数mmずれるので、タッチスクリーンではそれに当たらず、仮身の大きさを変えられなかった。そこで、押下が指のときだけ、つまみの当たりを広げる。見た目は変えず、マウスとペンの当たりも変えない。

#### 押下が指かどうかを知る所

押下が指かどうかは、どの機器から来たかを知っている入力の層だけが分かる。`T_HIDEV`の形は変えない(6.4.1)ので、イベントに印を足さず、入力の層が`ts_hid_read`で返したイベントについて答える口(`knl_hid_taken_touch`)を作った。ウインドウマネージャは押下を読むたびに(`wm_read_event`)それを尋ね、指の押下の時刻と、触れた画面の100mmあたりの画素の数を覚える(`knl_wm_touch_note`、最近の8つ)。プログラムは押下のイベントの時刻(`T_WMEV.when`、`T_OBNTM.when`)で`wm_hit_slop(when)`を呼び、つまみの当たりを何画素広げるかを得る。マウス、ペン、試験などが入れた押下、覚えていない押下には0を答える。プロセスからはSVC`wm_hit_slop`(クラス9の37)で呼ぶ。

押下の時刻で問い合わせるのは、Windowsの`GetMessageExtraInfo`と同じ考えである。Windowsはタッチとペンから作ったマウスのメッセージに印(`MI_WP_SIGNATURE`)を付け、プログラムはそのメッセージについてだけ印を読む。「最後の押下がタッチか」をそのまま尋ねる形にすると、プログラムが押下を処理する前に次の押下が来たとき、別の押下について答えてしまう。Linuxのlibinputも、タッチかどうかをイベントごとの道具の種類(`libinput_tablet_tool_get_type`、タッチの機器の種類)で渡し、機器の状態としては渡さない。どちらもイベントに結び付けて渡すので、TessronOSも押下の時刻に結び付けた。

#### 当たりの広さ

広げる幅は、ユーザ環境設定の〈ＰＤ属性〉の「つまみ範囲（タッチ）」(`LK_TCH_HIT`、0.1mm単位、0〜10mm、既定4mm)を、触れた画面の大きさで画素に直したものである(6.4.1の「画面の大きさとタッチ操作補正」)。「タッチ操作補正」(`LK_TCH_ON`)を切ると0になる。マウスの当たりと合わせて、指の当たりは5〜7mmの幅になる。Windowsは、タッチの対象の大きさを7.5mm角(最小でも5mm)とし、タッチのときだけウインドウの縁の大きさを変える当たりを広げる。X1 Yogaの14型を倍率200%で使うと、4mmは16画素である。数をアプリごとに持たず、どのつまみの判定も`wm_hit_slop`で得た幅を、次の`wm_hit_in`の決まりで使う。

#### 本体の押下を食いすぎないための決まり

- つまみの外側(物の外)は、マウスの当たりより`wm_hit_slop`の分だけ遠くまで当たりとする。
- つまみの内側(物の中)は、マウスの当たりより`wm_hit_slop`の分だけ深くまで当たりとするが、物の幅または高さの1/3を越えない(`wm_hit_in`)。マウスの当たりのほうが広ければ、マウスの当たりのままとする。中へ広げるのは、押す前から選んでいて、つまみが見えている物だけとする。選んでいない物を指で押したときは、選ぶための押下なので、マウスと同じ当たりで判定する。こうして、どんなに小さい仮身でも、左上の2/3は本体として移動や開くに使える。閉じた仮身(高さが名前の1行)の下端は、中にはほとんど広がらず、外に広がる。
- 指の下に物があれば、その物を押したことにする。物の外のつまみの当たりは、指の下に何もないときだけ使う。選んでいない仮身の外に当たりを置くと、何もない所を押して範囲を選ぶことができなくなるので、外の当たりは選んでいる1つの物(基本文章編集では選んでいる1つの仮身や画像)に限る。図形編集の選んだ図形のつまみ(右下の8画素の四角)は、マウスと同じく、ほかの物より先に判定する。
- ウインドウの右下の角は、指のときはウインドウの外へも`wm_hit_slop`の分だけ当たりを広げる。ウインドウマネージャは、指の押下の行き先を決めるとき(`at_reach`)、手前から順に、その場所を覆うウインドウか、右下の角の広げた当たりにその場所が入るウインドウを選ぶ。角の当たりはそのウインドウの枠と同じ重なりの順で、後ろのウインドウより先になり、手前のウインドウがその場所を覆っていればそちらが先である。Windowsが、縁の大きさを変える当たりをウインドウの外に持つのと同じである。枠の上では、角の当たりを下端と右端の枠に沿って広げる(作業領域は広げない)。
- 変形のつまみと線の端は、指のときは届く範囲を広げ、その中で最も近いものを取る。マウスのときは今までどおり最初に見つかったものを取る。

### 10.4.8 複数の画面

ビューは1枚の面で、画面はその中の矩形として並ぶ。先頭の画面が主画面で、ビューの左上にある。合成、バックバッファ、ポインタの座標はビュー全体のままで、画面ごとの違いは配置だけにある。

出力(画面を映す装置)が主画面の1つだけのときは、起動の設定`screens=N`で、その画面を同じ幅のN列に分けて試せる(今までと同じ)。主画面のほかに出力があるときは、出力ごとに1つの画面になり、大きさも出力ごとに違ってよい。バックバッファはすべての画面を囲む矩形の大きさにし(`T_DISPSPEC`の`width`と`height`。主画面の大きさは`main_w`と`main_h`)、画面ドライバ(`disp.c`)は損傷の矩形を出力ごとに切り、その出力の位置を引いてから、出力ごとのフレームバッファへ写す。主画面のほかの出力は1面で、面の切替えと帰線の待ちは主画面だけが行う。出力が1つのときの送りは今までと同じである。

| 口 | 内容 |
| --- | --- |
| `knl_disp_hw_more`(`disp_hw.h`) | 起動時、主画面を用意した後に、機種のドライバが見つけた出力を1つずつ答える。置く辺(`DISP_SIDE_RIGHT`、`DISP_SIDE_BELOW`)と辺に沿ったずれも答える。QEMU では、2台目の`bochs-display`(Arm)と`secondary-vga`(x64)を、幅1024、主画面と同じ高さの出力として答える |
| `knl_disp_out_attach`、`knl_disp_out_detach` | システムの動作中に出力を足す、外す。解像度の変更と同じ順(ウインドウマネージャのロック、新しいバックバッファ、`knl_wm_screen_changed`、`knl_hid_screen_changed`)で行う。外した画面にあったウインドウとポインタは主画面に移る(`knl_disp_follow`) |

出力ごとに更新の周期と帰線の時刻が違うので、主画面のほかの出力は、それぞれ自分のフレームの刻みで面を切り替える。Linuxの合成器(Westonやmutter)が出力ごとに再描画の周期を持ち、各出力の帰線(KMSのページフリップの完了の知らせ)を合図に、その出力の損傷だけを送って次のフリップを頼むのと同じ形である。合成タスクは1つのままで、主画面の帰線に歩調を合わせる(10.4.4)。ほかの出力は次のように送る(`disp.c`の`send_outs`、`out_step`、`out_task`)。

- 2面を持ち、表示する面を指示できる出力(`T_DISPHW`の`pages`が2で`flip`がある)は、損傷を出力ごとの保留の表(`pend`)にためる。前の切替えが効いた後なら、保留と、裏の面に欠けている前回の分(`old`)を裏の面に写して、その面を表示させる。送りかけの面は画面に出ないので、ティアリングは起きない。
- 前の切替えがまだ効いていないかもしれないとき(切替えから`latch_us`がたっていず、帰線もまだ見ていない)は、その出力のためには待たない。保留に残して、出力のタスク(優先度10)を起こす。このタスクは、帰線を待てる出力では帰線まで(ロックの外で)待ち、待てない出力では1ミリ秒ごとに`latch_us`がたったかを見て、保留を送る。合成タスクと主画面の送りは、ほかの出力の帰線を待たない。
- 1面の出力は、損傷をそのまま表示している面へ写す。
- 出力を足したときと外したとき(バックバッファを作り直したとき)は、どちらの面も古いので、出力の全体を`old`にして次の送りで両方の面をそろえる。
- QEMU の2台目の`bochs-display`と`secondary-vga`は、窓に2面分の空きがあれば2面で切り替える(Yのオフセットのレジスタ。切替えはすぐに効くので`latch_us`は0)。

出力は、それより前の画面すべてを囲む矩形の右の辺、下の辺、左の辺、上の辺のどれかの外に、足した順に置く(`DISP_SIDE_RIGHT`、`DISP_SIDE_BELOW`、`DISP_SIDE_LEFT`、`DISP_SIDE_ABOVE`)。辺に沿ったずれは主画面の角から測り、0以上だけを受け付ける(負は`E_NOSPT`)。置き方は`disp.c`の`outs_place`が決める。主画面の左上を(0, 0)として各出力の位置を求め、それから全体を囲む矩形の左上が(0, 0)になるように全部をずらす。バックバッファとビューはこの矩形で、左上は常に(0, 0)である。主画面はその中の`T_DISPSPEC`の`main_x`、`main_y`にあり、左か上に画面がなければ(0, 0)のままである。主画面の送り(`send_list`、`send_rows`)は、バックバッファのこの矩形を主画面のフレームバッファの(0, 0)から写し、フロントバッファの追跡に渡す矩形(`invalidate`、`flushed`)も主画面の自分の座標に直す(`on_main`)。画面の実身のレコード1の`SIZE`は主画面の大きさ、`WIDTH`、`HEIGHT`、`PITCH`はバックバッファのもので、画面が2つ以上のときは`SCREENS`(画面の数)と`SCREEN0`、`SCREEN1`…(ビューでの位置と大きさ)の行が加わる。

`ts_disp_screens`と`ts_disp_screen`が画面の数と矩形を答える。画面0が主画面で、その矩形は左か上に画面があると(0, 0)から離れる。ウインドウマネージャは`wm_screen_at`(ある点の画面)、`wm_screen_main`(主画面の大きさ)、`wm_screen_main_rect`(主画面のビューでの矩形)、`wm_screen_is_main`(ある画面の矩形が主画面のものか)を持つ。`wm_screen`はビュー全体のままである。主画面に何かを置くカーネルの部分(異常終了の確認、通知、`fquit`の中央に置くパネル、デスクトップの全画面表示)は、主画面の大きさだけでなく、この矩形の角から置く。

画面の大きさ、位置、倍率が変わるたびに、`disp.c`は変わる前の画面の矩形を出力の番号(`DISPOUT`の`id`。主画面は0)と組にして覚える(`was_take`)。`knl_disp_follow`は、変わる前のビューの点が今どこかを答える。主画面か、まだある画面の上の点は、その画面の角からの位置を保ってその画面と一緒に動き、外された画面の上の点は、主画面の角から同じ位置へ移って主画面の中に収まる。どの画面にもない点は一番近い画面と一緒に動く。ウインドウマネージャ(`knl_wm_screen_changed`)はウインドウの求めた位置の中央を、入力の層(`knl_hid_screen_changed`)はポインタを、この答えで動かす。左に画面を足すと、主画面のウインドウとポインタは主画面と一緒に右へ動き、主画面の上での見た目の位置は変わらない。出力の層(10.4.9)はほかの出力の辺やモードを変えるとき、いったん全部を外して入れ直すので、ほかの出力の上にあったウインドウとポインタは、置く辺を変えたときも外したときも主画面に戻る。全画面(`wm_full`)のウインドウは、移った先の画面の大きさになる。

| もの | 画面ごとの扱い |
| --- | --- |
| 壁紙 | 画面ごとに中央に置く、引き伸ばす、並べる |
| メッセージの行 | 主画面の下端だけ。幅は主画面の幅で、主画面の左端から置く(`msgline.c`の`ml_left`、`knl_msg_band`) |
| メニュー、候補の一覧 | 開く場所の画面の中に収める(上端もその画面の上端) |
| ウインドウを開くときの収め方、`full`と`wide`、全画面(`wm_full`)、デスクトップの全画面表示 | ウインドウの中央がある画面。メッセージ行の分を引くのは主画面だけ |
| どの画面か(`wm_screen_at`) | 点を含む画面。どれにも含まれなければ一番近い画面 |
| 画面にない部分(大きさの違う画面の間の隙間) | 地面の色で埋める |
| 通知、確認のパネル、プログラムが中央に置くもの | 主画面。プログラムの`wm_screen`のSVCは主画面の大きさを、`wm_screen_main_rect`のSVCは主画面の矩形を答える。中央に置くものは`wm_main_centre`で主画面の矩形から置く |
| 画面の写し | ビュー全体 |

実機の外付けの画面のモード設定はまだ無いので、実機の表示はまだ1画面である。

入力の層(`hid.c`)は、主画面のほかに出力があるとき、画面の矩形を覚えておく(`screens_take`、`knl_hid_screen_changed`で読み直す)。ポインタは画面のどれかの上だけを動き、大きさの違う画面の間の隙間に出ようとすると、一番近い画面の一番近い点に止まる(`ptr_keep_on`)。タッチスクリーンとペンの絶対座標は、ビュー全体ではなく主画面(ノートPCでは内蔵のパネル)の矩形に写し、指の長さ(100mmあたりの画素)もその画面の大きさで求める。出力が1つのときは、`screens=N`の列も含めて、今までどおりビュー全体を1つの矩形として扱う。外付けのタッチの機器を外部の画面に写す設定は、まだ無い。

試験は、カーネル試験の`disp`の組の`test_screens`(メモリのフレームバッファを出力として右と下に足し、バックバッファの大きさ、各画面の矩形、`wm_screen_at`、画面をまたぐ矩形が両方の出力に写ること、外すと元に戻ることを見る)と`test_second`(2台目の装置で起動したとき、それが主画面の右の画面であること)、`wm`の組の`test_screens_out`(足した画面での全画面、メッセージ行が主画面に残ること、`wm_place`がその画面に収めること、隙間に置いたポインタが一番近い画面に止まること、外したときにウインドウがビューに戻ること、下に置いた画面での判定)、`disp`の組の`test_screens_left`(左と上に足したときのバックバッファの大きさ、`main_x`、`main_y`、各画面の矩形、主画面が自分の矩形を、左と上の画面が自分の部分を受け取ること、`knl_disp_follow`が主画面の点を主画面と一緒に、左の画面の点をその画面と一緒に動かし、外した画面の点を主画面へ移すこと、外すと主画面が角に戻ること)、`wm`の組の`test_screens_left_wm`(左に足すと主画面のウインドウとポインタが一緒に動くこと、左の画面での全画面とメッセージ行のないこと、2つの画面をまたぐウインドウが両方に出ること、外すと左の画面のウインドウとポインタが主画面に移り、主画面のウインドウが元の位置に戻ること、上に足したときのメッセージ行の位置)、`disp`の組の`test_mirror`(複製の出力が画面に数えられず、ビューとバックバッファが変わらないこと、同じ大きさでは主画面の画素がそのまま、320×240では比を保って中央に縮めて写り、余白が黒いこと、`knl_disp_fit`の矩形)、`wm`の組の`test_mirror_wm`(左の画面を複製に替えると、左のウインドウとポインタが主画面に戻り、主画面のウインドウとメッセージ行が角に戻り、複製の出力に主画面の画素が写ること、拡張に戻すと主画面とウインドウがまた動くこと、2台目の装置があるときは画面の実身に`mirror`の行を書いて複製にし、読み直し、古い`right`の行で戻せること)である。QEMU で2台目の装置を付けて試すときは、Arm では`make ... QEMU_EXTRA="-device bochs-display,id=disp2,addr=0x1f" test`、`tools/ui_run.py`では環境変数`UI_SCREENS=2`にする。`test_second`は、2つの画面にまたがるウインドウを開き、QEMU にそれぞれの装置の表示を`obj/kt_screens_head0.ppm`と`obj/kt_screens_head1.ppm`へ書かせる。`test_out_flip`は、2面のメモリの出力で、送りが裏の面に行ってから切り替わること、切替えが効く前の送りが待たずに戻り、出力のタスクが後で両方の分を持った面に切り替えることを見る。

#### 主画面の左と上に置く画面の座標の持ち方

左と上の画面は、XのRandRと同じく、全体の左上を(0, 0)にして主画面の原点を動かす形にした。主画面の左上を(0, 0)のまま保って外部の画面に負の座標を持たせる形(Windowsの形)と、コードで見比べて決めた。

- 負の座標の形では、ビューの座標がそのままバックバッファの位置である前提を、全部の層で崩すことになる。数えたところ、`wm.c`だけで0で切る所や0からビューの幅までを回す所が約40、`disp.c`でバックバッファの大きさで切る所が約45、ほかに`dp.c`の画面の切り取り、`pointer.c`、`msgline.c`、`compose.c`、GPUの合成(`igt_compose.c`、`v3d_compose.c`)、`hid.c`の`ptr_keep_on`、壁紙の並べ方の剰余、倍率の切り捨てがある。1か所でも直し漏れると、負の行や列でバックバッファの外を読み書きする。
- 原点を動かす形では、ビューとバックバッファは今までどおり(0, 0)からの矩形のままで、0で切る所はどれも正しいままである。直すのは「主画面はビューの角にある」と決めていた所だけで、`ts_disp_screen(0)`、`wm_screen_main`、`main_screen`を使う所を探せば全部見つかる(`disp.c`の主画面の送り、`wm.c`の`main_screen`、`msgline.c`、`fquit.c`、デスクトップの`full_rect`、`dtnotify.c`、`dtfault.c`)。直し漏れても、物が別の画面に出るだけで、メモリは壊さない。
- 原点を動かす形の短所は、主画面が動くと、それまでのビューの座標が別の場所を指すことである。開いているウインドウとポインタは`knl_disp_follow`で主画面と一緒に動かす(上の段落)。覚えておくウインドウの位置は、ビューの座標ではなく画面からの相対の位置にした(次の項)。

#### 画面の複製

主画面のほかの出力は、自分の位置を持つ代わりに、主画面と同じ絵を出せる(`DISP_SIDE_MIRROR`)。LinuxのDRMでいう、2つのCRTCが同じフレームバッファの同じ領域を走査する形である。複製のための別の送りの道は作らず、出力ごとに「バックバッファのどの矩形を出すか」(`DISPOUT`の`x`、`y`、`sw`、`sh`)の指定を一般化して表す。拡張の出力はその出力の大きさの矩形を自分の位置に持ち、複製の出力は主画面の矩形(`main_x`、`main_y`と主画面の大きさ)を指す。

- 複製の出力は画面として数えない。`ts_disp_screens`と`ts_disp_screen`は複製の出力を飛ばすので、ウインドウマネージャ、入力の層、メッセージ行、〈識別〉、覚えるウインドウの位置(`wm_place_keep`、`wm_place_open`)から見ると画面は1つで、ビューは主画面だけである。出力の層の`T_DISPOUTINFO`の`screen`も-1になる。画面ドライバの上の出力の番号(`knl_disp_screen_hw`、`knl_disp_out_attach`の答え、`knl_disp_out_detach`の引数)は画面の番号とは別で、`knl_disp_out_screen`がその出力の画面の番号(複製は-1)を、`knl_disp_out_count`が主画面のほかの出力の数を答える。
- 拡張と複製の切替えは、出力の層が出力をいったん外して付け直す今までの道を通る。外したときの追従(`knl_disp_follow`)で、外部にあったウインドウとポインタは主画面に戻り、主画面のウインドウは主画面と一緒にビューの角へ戻る。拡張に戻すと、主画面とそのウインドウはまた主画面と一緒に動く。
- 解像度が違うときは、Linuxのデスクトップ環境と同じ順で決める(`ts_disp_mirror_mode`)。外部の出力のモードの一覧に主画面と同じ大きさがあれば、外部をそのモードにする。主画面のモードは変えない。なければ外部の推奨のモードにして、主画面の絵を拡大・縮小して合わせる。比は保って中央に置き、余白は黒にする(`knl_disp_fit`)。
- 拡大・縮小は、出力のドライバにスケーラがあればそれで行う(`T_DISPOUTHW`の`fit`。Intelのパイプのスケーラ、6.9.1)。このとき出力のフレームバッファは主画面と同じ大きさで、送りはそのまま写す。スケーラのない出力(QEMUの`bochs-display`と`secondary-vga`、ファームウェアの面)は、送りが拡大・縮小して写す(`out_send_scaled`)。出力の各画素に一番近い主画面の画素を取り、行ごとに`send_row`で出力の形式に直す。余白は付け直したときに黒で埋める(`out_black`)。複製のまま主画面の解像度を変えたときは、画面ドライバが出力の層に知らせ(`knl_disp_out_main_changed`)、出力の層が複製の出力のモードを新しい大きさで選び直して(`mirror_size`、`ts_disp_mirror_mode`と同じ決め方)、外して付け直す。出力の層自身が主画面の大きさを変えるとき(`ts_disp_commit`)も同じことを`apply_locked`の中で行う。スケーラの元の大きさ、送りの拡大・縮小の矩形、余白の黒は、こうして新しい大きさで作り直される。外部が新しい大きさのモードを持てばスケーラを使わない複製に、持たなければスケーラを使う複製に、同じ道で切り替わる。送りの量は出力の画素の数で、主画面1280×800を1920×1080に写すと、変わった矩形ごとに出力側の約2倍の画素を読む計算になる。QEMUでの測定はしていない。

#### 新しく開くウインドウの画面

覚えた位置のないウインドウ(初めて開く小物やアプリ、プログラムの既定の位置で開くもの、中央に置くもの)は、ポインタのある画面に開く。`wm_screen_new_rect`(プロセスからは同じ名前のSVC、A.9)が、その画面の矩形を返す。ポインタのある画面を決められないとき(ポインタがない、ポインタがどの画面の矩形にも入らない)は主画面を返す。一番近い画面にも、ビューの左上にある画面にも落とさない。点の画面を返す`wm_screen_of`も同じで、どの画面にも入らない点は主画面になる。複製のときは画面が1つなので、いつも主画面である。

プログラムの既定の位置は、`wm.h`の`wm_new_x`、`wm_new_y`で、この画面の左上からの位置としてビューに直す。中央に置くものは`wm_new_centre`を使う。主画面が常にビューの角にあったときの「ビューの角からの位置」と同じ意味になる。直したのは次のとおりである。

- ライブラリ:`lib/libtv/tv_app.c`の`place_of`(仮身一覧、基本文章編集、基本図形編集、屑実身操作などの道具の既定の位置)。
- `ui_open`に既定の位置を渡すアプリ:バックアップ、文字検索、ネットワーク環境設定、音量ミキサー、システム環境設定、ユーザ環境設定、単語登録、トレー表示、電卓。
- 自分でウインドウを作るアプリ:キー配列、ファイル変換、書庫、スライドの全画面表示、マイクロスクリプトの全画面と横いっぱい。
- 覚えた位置がないときだけ新しい画面に置くアプリ:基本表計算、カレンダー、かな入力練習、マイクロカード、マイクロスクリプト、電子手帳。
- 中央に置くアプリ:ディスク操作、ディスク修復、BeFC・BeSFC、システム登録、印刷の画面表示。
- カーネル:位置を指定せずに作ったウインドウの実身(`wmobj.c`)、デスクトップのコンソールの行のウインドウ。

覚えた位置のあるウインドウは、今までどおり覚えた画面のその位置に開く。その画面がつながっていなければ主画面に開く。システムのパネル(終了の確認、異常終了の確認、通知)とメッセージ行は主画面のままで、`wm_main_centre`と`wm_screen_main_rect`を使う。問合せのパネル(`lib/libui/ui.c`の`ask_place`)は、呼んだウインドウがあればその中央がある画面の中央に、なければ主画面の中央に置く。スクリーンキーボードは主画面だけに置く。

主画面の原点を動かしたとき、プログラムの既定の位置(ビューの角からの数値)は、ビューの左上にある画面、つまり左か上に置いた外部の画面を指すようになっていた。右や下に置いたときは、主画面がビューの角にあるので起きなかった。

#### 覚えておくウインドウの位置と主画面の矩形

実身のメタデータの`window`に覚える位置は、ウインドウの左上の点がある画面の左上からの相対の位置である。2つの画面をまたぐウインドウは、左上の点がある画面のものとして覚える。主画面以外の画面のときは、どの画面かを`window`の`screen`(8桁の16進)に書く。値は、その画面に映っているディスプレイのEDIDの識別で、出力の設定の保存(`DISPLAY.<識別>`、10.4.10)と同じものである。新しい識別の仕組みは作っていない。主画面の位置は`screen`を書かない(前に`screen`があれば空にする)。`screen`のない位置は主画面からの相対として読む。主画面が(0, 0)にあった構成で覚えた位置は同じ数値になるので、1画面や右・下の配置で覚えた位置はそのまま使える。`screen`を知らない古いバージョンは、この項目を読み飛ばす。EDIDの識別のないディスプレイ(ファームウェアの面だけの出力など)の上のウインドウは、主画面からの相対で覚える。

ビューの座標と覚える位置との変換は、ウインドウマネージャの2つの呼出しだけが行う(`include/ts/wm.h`の`T_WMPLACE`)。`wm_place_keep`は、ビューの矩形から、左上の点がある画面(どの画面にもなければ一番近い画面)とその画面からの相対の矩形を作る。`wm_place_open`は、覚えた位置をビューに戻す。名指す画面がつながっていれば1を返す。つながっていなければ0を返し、主画面の角から同じ相対の位置に置き、主画面の中(メッセージ行の上)に収まるように寄せる。プロセスは同じ名前のSVC(`wm_place_keep`、`wm_place_open`、A.9)で呼ぶ。自分で位置を覚えるプログラムが開く前に使う`wm_place_xywh`(位置、大きさ、`screen`の文字列からビューの位置)と、`screen`の文字列を数にする`wm_place_screen_of`も`wm.h`にある。メタデータの`screen`の書込みは、JSONのライブラリの`js_set_str`(ある項目に文字列を書く。なければオブジェクトの最後に足す)で行う。

| 覚える所 | 読む所 |
| --- | --- |
| 実身のメタデータの`window`(`lib/libtv/tv_app.c`の`ta_window_keep`。基本文章編集、基本図形編集、仮身一覧) | `tv_app.c`の`place_of` |
| 同じ(`outer_kernel/om/om_store.c`の`om_store_set_window`。原紙から作った実身の位置をずらすとき) | `om_store_window` |
| ― | 基本表計算(`calc_main.c`)、カレンダー(`cal_main.c`)、かな入力練習(`kp_main.c`)、マイクロカード(`mc_main.c`)の`window`の`pos` |
| マイクロスクリプトの`microscriptWindow`(`ms_main.c`の`ms_win_save`) | `ms_main.c`の`open_window`。`window`の`pos`も |
| 電子手帳の`tessronos`の`techo`の`windows`(`tc_main.c`の`places_keep`) | `tc_main.c`の`kept_places`と`places` |
| 図形の道具パネルの`window`の`panelpos`(`fg_tool.c`の`keep_place`) | `fg_tool.c`の`kept_place` |
| スクリーンキーボードの機器の設定の`SOFTKB_WIN_*`(6つ目の語が`screen`) | `sk_main.c`の`win_kept` |

書庫(`application/archive`)とバックアップ(`application/backup`)は`window`をそのまま写すか、`pos`と大きさだけを書き直す。`screen`が落ちた位置は主画面からの相対として開く。

プロセスは主画面の矩形を`wm_screen_main_rect`のSVC(A.9)で得る。今までの`wm_screen`のSVCは主画面の大きさを返すままで、呼ぶ側は変えずに動く。主画面の中央に置くプログラムは`wm.h`の`wm_main_centre`(主画面の矩形の中央、左と上は主画面の中に収める)を使う。直したのは、問合せのパネル(`lib/libui/ui.c`の`ask_place`)、ディスク操作(`dop_main.c`)、ディスク修復(`df_main.c`)、BeFC・BeSFC(`emu_main.c`)、印刷の画面表示(`bp_main.c`)、スクリーンキーボードの既定の位置と画面への収め方(`sk_main.c`)、デスクトップの異常終了の確認(`dtfault.c`)である。システムインストール(`application/sysinst/si_main.c`)も主画面の大きさだけで中央に置いているが、別の作業で編集中のため、まだ直していない。

### 10.4.9 出力の層

画面を映す装置(出力)の一覧と、そのモードの設定は、出力の層(`device/disp/dispout.c`、公開の型と呼出しは`include/ts/dispout.h`)が受け持つ。LinuxのDRM/KMSのコネクタとCRTCに当たる層で、ドライバは出力ごとに`T_DISPOUTHW`(`disp_hw.h`)でその出力を説明し、画面ドライバ(`disp.c`)は、入っている出力が見せる画面を持つ。

| `T_DISPOUTHW`の欄 | 内容 |
| --- | --- |
| `kind`、`name` | コネクタの種類(`DISP_CON_*`)と名前(Linuxのコネクタ名に合わせて`Virtual-1`、`eDP-1`、`HDMI-A-1`など) |
| `detect` | 何かが挿さっているか(`DISP_ST_*`) |
| `get_edid` | EDIDを読む。基本のブロックと拡張のブロック(`DISP_EDID_MAX`は512バイト、4ブロック) |
| `modes` | EDIDのない出力でのドライバ自身のモードの一覧 |
| `check` | そのモードを出せるか。何も書かない |
| `commit` | そのモードにする(NULLなら切る)。主画面のほかの出力だけで、主画面の大きさは今までどおり`knl_disp_hw_setmode`で変える |
| `power`、`brightness`、`invalidate`、`flushed`、`wm_again` | 実機のドライバ(Intel)が後で入れる欄。電源の入切(DPMSに当たる)、内蔵パネルの明るさ、表に見えている面への書込みの始まりと終わり(フロントバッファの追跡、PSR)、ウォーターマークとDDBの計算し直し。QEMUのドライバではNULL |
| `fit` | `ctx`の後の欄。主画面を別の大きさのモードで複製するとき、主画面の大きさのフレームバッファをスケーラでモードに合わせて出せるかを調べ、出せると決める(次の`commit`で反映)。スケーラの制約を越えると`E_NOSPT`。NULLの出力は送りが拡大・縮小する |

`T_DISPHW`の`out`が、そのフレームバッファを見せる出力を指す。主画面のドライバが`out`を渡さないとき(GOPのまま、Intelの内蔵グラフィックス)は、ファームウェアが用意したフレームバッファの出力(`Firmware-1`、モードは今の大きさの1つ)として扱う。

EDID(`device/disp/edid.c`)からは、製造者の3文字、製品番号、シリアル、名前(記述子0xFC)、物理の大きさ、HDMIかどうか(CTAの拡張のHDMIの識別子)、音を出せるか(CTAの基本の音声の印か音声のデータブロック)、モードの一覧を読む。一覧はLinuxの`drm_add_edid_modes`と同じ順で、詳細タイミング(基本のブロック、続いて拡張のブロック。最初のものが推奨)、標準タイミング(基本のブロックと記述子0xFA)、確立タイミング、CTAの拡張のVIC(映像のデータブロック)の順に並べ、大きさとリフレッシュとインタレースが同じものは重ねない。表(VESAのDMTの主なものとCTAのVICの主なもの)にない標準タイミングはCVTの短い帰線の式で時間を決める。

| 呼出し | 内容 |
| --- | --- |
| `ts_disp_outputs`、`ts_disp_output` | 出力の数と、1つの出力の情報(`T_DISPOUTINFO`:見せている画面の番号か-1、種類、状態、名前、EDIDから読んだもの、モードの数、今のモード、ビューでの位置) |
| `ts_disp_out_modes`、`ts_disp_out_edid` | モードの一覧(推奨が先頭)と、EDIDのバイト列 |
| `ts_disp_state` | 今の状態(`T_DISPSTATE`:出力ごとに入か切、モードの大きさ、置く辺とずれ) |
| `ts_disp_check` | その状態にできるかを、何も書かずに調べる。主画面を切る状態、出力の数が合わない状態、出力の一覧にない大きさ、置けない辺と位置を断る |
| `ts_disp_commit` | 調べた上でその状態にする。主画面の大きさ、続いてほかの出力をいったん外し、一覧の順に入れ直す。ほかの出力が変わらないときは外さない。どれかの出力が自分の分を受け付けないときは、前の状態に戻してその誤りを返す |
| `knl_disp_out_hotplug`、`knl_disp_out_watch` | ドライバが抜き差しを知らせる口と、それを受ける者(画面の実身、10.4.10)を登録する口 |

切った出力は画面を持たないが、一覧には残る(見せている画面の番号が-1)。QEMU の2台目の`bochs-display`と`secondary-vga`はEDID(レジスタの窓の先頭)とモードの設定(`commit`)を持ち、主画面の`bochs-display`と標準VGAはEDIDを持つ。

試験は`disp`の組の`test_outputs`で、出力ごとにEDIDとモードの一覧を読み、推奨が先頭であること、状態の検査が断るべきものを断ること、主画面を一覧の別のモードにして戻せること、モードを受け付けない出力(試験の`Test-1`)で`commit`が前の状態に戻すこと、切った出力が一覧に残ることを見る。

#### 実機のドライバを載せる口(案)

IntelとRaspberry Piのドライバは、まだこの層に載せていない(Intelは省電力の作業の範囲で、どちらも実機が要る)。載せるときの対応は次の案とする。

| 欄 | Intel(`disp_igfx.c`、`disp_ext.c`) | Raspberry Pi 5 |
| --- | --- | --- |
| `kind`、`name` | VBTの子デバイスの表から(`eDP-1`、`DP-1`、`HDMI-A-1`) | `HDMI-A-1`、`HDMI-A-2` |
| `detect` | PCHのHPD(`SDEISR`)、TCポートは`PORT_TX_DFLEXDPSP` | ファームウェアの`GET_NUM_DISPLAYS`、自前のときはHDMIのHPD |
| `get_edid` | DP AUXのI2C、GMBUS(今の`disp_ext.c`)、eDPはOpRegionかAUX | ファームウェアのEDIDのタグ |
| `check`、`commit` | パイプ、トランスコーダ、DDI、DPLL、CDCLK、DDBとウォーターマークを全パイプで計算してから書く | ファームウェアの面のモード(`SET_DISPLAY_NUM`の後の大きさ) |
| `invalidate`、`flushed` | 今の`T_DISPHW`の`dirty`(PSRを抜ける)をここへ移す。主画面の送りと面の切替え(`disp_hw.flip`)の後、起動時の2面の照合の後にも呼ぶ(今の`main_told`) | なし |
| `power`、`brightness`、`wm_again` | パネルの電源の順、PCHのPWM、`knl_igfx_wm_again` | なし |

Intelの外付けの画面(DDI B、C)を載せる手順の骨子と、パイプが2本のときのDDB、ウォーターマーク、SAGVの扱いは6.9.1に書いた。Raspberry Pi 5は、ファームウェアが数える画面と各画面の設定を記録に出すだけの`knl_disp_hw_more`を置き(出力は増やさない)、実機の記録を見てから2つ目の面を出力にする。

Intelで、パネルのほかのパイプを点ける前に`knl_igfx_psr_hold(TRUE, 理由)`を呼び、そのパイプを消した後に`knl_igfx_psr_hold(FALSE, 理由)`を呼ぶ(PSRは1本のパイプのときだけ入るため。外付けの画面の段階で使う)。

### 10.4.10 出力の実身と設定の保存

出力が2つ以上あるとき、出力ごとにデバイスの実身を作る(`peripheral_kernel/obj/obdisp.c`の`outs_start`)。名前はコネクタ名(`Virtual-2`、`HDMI-A-1`など)で、ほかのデバイスと同じくデバイス箱に置き、新しい箱は作らない。画面の実身のレコード0は各出力の実身へのリンク(仮身)を持つ。

| 実身 | レコード |
| --- | --- |
| 画面 | 1 今までの行に加えて、`OUTPUTS`(出力の数)、出力ごとに`OUTi`(名前、`on`か`off`、大きさ、置く辺`right`、`below`、`left`、`above`か、主画面の複製の`mirror`、ずれ、EDIDの識別の16進、製造者、名前)と`OUTMODESi`(出せる大きさの一覧)、主画面のほかの出力には`OUTMIRRORi`(複製するときのモードの大きさと、今それにできるかの`ok`か`no`)。`OUT1 on 1024x768 right 0`、`OUT1 off`のような行を書くと、出力をまとめてその状態にする(`ts_disp_commit`) |
| 出力(`Virtual-2`など) | 1 `NAME`、`KIND`、`STATUS`、`SCREEN`、`SIZE`、`REFRESH`、`MAKER`、`MODEL`、`PRODUCT`、`IDENT`、`MM_W`、`MM_H`、`HDMI`、`AUDIO`、`EDID`、`MODES`の行。2 EDIDのバイト列。どちらも読むだけ |

抜き差しがあると、出力の層の知らせ(`knl_disp_out_watch`)を受けて、出力の実身と画面の実身に`OB_E_CHANGE`を出す。

設定は、機器の設定の実身に、ディスプレイのEDIDの識別ごとに`DISPLAY.<識別>`の行(値は`on 1024x768 right 0`か`off`。辺は`right`、`below`、`left`、`above`、複製は`mirror`)で保存する。辺を左と上に広げる前の保存(`right`と`below`)も、複製を足す前の保存も、そのまま読める。複製で保存したディスプレイは、挿し直したときも起動時も複製で出る。保存した大きさが今は使えないとき(主画面の解像度を変えたときなど)は、その時の複製のモード(`ts_disp_mirror_mode`)で出す。同じディスプレイを挿し直すと、同じ配置とモードに戻る。デスクトップは起動時に、解像度と倍率(`VIDEOMODE`、`VIDEOSCALE`)の後で、主画面のほかの出力に保存された行を当てる(`desktop.c`の`outs_start`)。システム環境設定からの変更は`DT_RQ_SCREEN`に`OUTi`の行を載せて頼み、デスクトップが画面の実身に書いて確認のパネル(30秒)を出し、残すと保存し、残さなければ前の行を書き戻す(`outs_req`)。主画面の解像度と倍率は今までどおり`VIDEOMODE`、`VIDEOFIT`、`VIDEOSCALE`に保存する。

システム環境設定の〈機器情報〉の「画面サイズ／色数」のページは、出力が2つ以上のときだけ、上の段に3つの部品を出す(11.6)。出力の選択(ポップアップ。主画面が1番)、使うか使わないか(主画面のときは無効)、主画面の右、下、左、上のどれに置くか、主画面の複製にするか(同じ。ポップアップ)。複製を選ぶと、複製するときのモードの大きさ(`OUTMIRRORi`)を幅と高さの欄と一覧に入れる。複製にできない出力(スケーラの制約を越える)で選ぶと、理由を問合せのパネルで示し、選択を元に戻す。選んだ出力の大きさの一覧とその大きさは、今までの一覧と幅と高さの欄に出す。出力が1つのときは、部品を隠してページは今までと同じに使える。ずれ(辺に沿った位置)は0である。

試験は`tools/tests/ui_screens_out.steps`(`UI_SCREENS=2`で`tools/ui_run.py`)で、2台目を選んで切り、主画面の下に置き、右に戻し、そのたびにデスクトップが保存することを見る。左と上は`tools/tests/ui_screens_left.steps`で、左に置き、上に置き、右に戻す。複製は`tools/tests/ui_screens_mirror.steps`で、複製にして2台目の表示を見て、右に戻す。

| 番号 | 内容 |
| --- | --- |

| 400〜499 | パターン(背景、縁、タイトルバー、ランプ、スクロールバーのつまみ) |
| 550〜579 | 色 |
| 580〜599 | フォント |
| 9000〜9199 | 設定(ウインドウの見た目、キーとポインタの属性、音、入力方式) |

配色は外観設定テーブルの値の組で、システム環境設定で切り替える。ウインドウの見た目(10.4.1)とユーザ環境設定で変更する値も、このテーブルの設定項目である。タイトルの文字サイズとスクロールバーの幅を変えると、開いているすべてのウインドウの枠とワークエリアがその場で再計算され、再描画される。メニューの文字サイズは次に開くメニューから反映される。ポインタのサイズを変えたときは、変更前のサイズで覆っていた画素を戻し、新しいサイズで置き直す。プロセスは`wm_look`で値を読み出し、管理者は`wm_set_look`で書き換えられる。

## 10.6 部品

部品は、BTRONの部品と同じ種類と番号を持つ。

| 番号 | 部品 |
| --- | --- |
| 1 TB | テキストボックス |
| 2 XB | 秘匿テキストボックス(パスワード入力) |
| 3 NB | 数値ボックス |
| 4 SB | 連番ボックス(数値や名前の欄を並べたもの) |
| 5 AS | オン/オフスイッチ |
| 6 MS | 押しボタン |
| 9 WS | スイッチセレクタ |
| 10 SS | スクロールセレクタ |
| 11 VL | ボリューム |
| 13 | タブパネル |
| 0 | ラベル |
| 14 | 線 |
| 15 | アイコン |
| 16 | ポップアップ |

部品の描画と操作は次のとおりである。

- 名前の文字は16ドットで、明るい色の影を右下に1ドットずらして付ける。
- スイッチは角を丸めた立体的な箱で、Enterで押されるスイッチは内側に強調枠を持つ。
- オン/オフスイッチとセレクタの名前の前にはランプがあり、選択したものが点灯する。現在有効な値の名前には下線を引く。
- 押しボタンにランプはない。名前の文字間を広げてボタン全体に描き、押している間は枠を反転表示する。
- スイッチとセレクタは、ボタンを離したときに部品の上にあれば有効になる。押したまま部品の外へ出ればキャンセルできる。
- テキストボックスは、入力フォーカスを持つ間は白背景になり、カーソルが点滅する。Tabで次のボックスに移り、ボックスに入ると文字列全体が選択される。かな漢字変換で日本語を入力できるボックスもある。
- 秘匿テキストボックスは、文字ごとに網掛けの四角を1つ描く。プログラムは、ほかの所に保存してあって自分も知らない文字(保存したパスワード)の代わりに、決まった数の`XB_STANDIN`(0x7F)を書ける。この印も1文字として四角で描く。印が入っている間に文字のキーかBackSpaceを押すと、印はすべて消え、打った文字だけが残る。印のまま読み出せば印が返るだけなので、プログラムは「打ち直されていない」ことだけを知り、元の文字は画面にも部品の値にも現れない。キーボードで0x7Fは打てないので、打った文字と印が混ざることはない。
- 連番ボックスは欄ごとに数値か名前を持つ。入力中の欄の下の三角を押すか、上下の矢印キーで値が増減する。
- ボリュームはスクロールバーと同じ形で、つまみをドラッグして値を変える。
- ポップアップは、いくつかの名前から1つを選ぶ部品である。押すと名前の一覧が開き、選んだ名前が部品に出る(下記)。
- 名前は欄の幅に収まるように描き、収まらないときは末尾を「…」にして省く。欄の外や部品の外に文字がはみ出すことはない(10.6.1)。

タブパネルは、上下2段のタブを持つ部品である。各部品は自分が属するタブを持ち、そのタブが選択されているときだけ描画され、操作を受け付ける。タブはふつうシートの上に横に並ぶ。`P_DOWN`を指定すると、シートの左側に縦に並ぶ。縦に並べたタブは横のタブを横倒しにした形で、幅はいちばん長い名前に合わせてそろえ、下の段は持たない。選択できないタブは灰色の名前で描き、押しても選ばれない(`inact`)。トレー小物(11.27)が使う。

データボックスのパネル(18.15)では、`<tags>`に`down="true"`で縦に並べ、`view="true"`でシートをプログラムが描くことを示す。`view`のパネルが描かれるたびに、パネルの地がシートに描いたものを覆うので、ウインドウに`OB_E_REDRAW`を知らせ、プログラムに描き直させる(`knl_wmobj_view_drawn`)。プロセスはタブの部品の状態(`OB_WR_STATE`)に2つ目の`INT`を書くと、選べないタブ(`inact`、1つ目のタブがビット0)を決められる。部品の`OB_WR_PLACE`に書いた外形が今と違えば部品をそこへ動かし、タブの部品では作業領域の欄(`wleft`〜`wbottom`)をシートの位置にする(読むと今のシートが入っている)。読んだものに旗だけを変えて書き戻すと、位置は変わらない。置いたパネルの`OB_WR_PLACE`に書くと、位置はそのままでパネルの大きさが変わる(`knl_pn_set_size`)。ウインドウの大きさに合わせてパネルを置き直すプログラム(トレー小物)が使う。`<label num rect>`は、矩形の高さの中ほどに文字を置くラベルである(`<text>`は基準線に置く)。

ポップアップ(`WM_PT_POPUP`、16)は、セレクタと同じく名前の並びを持ち、値は選んでいる名前の番号(1から、0は選んでいない)である。名前の並びはセレクタと同じく部品が自分で持ち(10.6.2)、プロセスは部品のレコード4に書いて入れ替える。デスクトップのようにカーネルの中でパネルの定義(`T_WMPANEL`)を作るときは、部品の`type`を`WM_PT_POPUP`にし、`wm_part_name`で名前を部品に足して、名前の数を`count`に、選んでいる番号を`value`に書く。開いたあとの値は`wm_panel_get`と`wm_panel_set`で読み書きする。BTRONの部品の番号7と8は絵を持つスイッチと押しボタンなので、ポップアップにはTessronOSが足した部品の番号の続きを使う。

見た目は次のとおりである。

- 本体はスイッチと同じ角の丸い立体的な箱で、外観設定テーブルの部品の背景(`LK_INACTPARTS`)で塗る。`P_NOFRAME`なら枠を描かず背景だけ、`P_EMPHAS`ならスイッチと同じ強調枠を内側に描く。
- 選んでいる名前を、セレクタの名前と同じ位置(左端からマージン16ドット)に、ランプを付けずに描く。名前にタブがあれば、印の手前までをその名前の欄に分け、入らない欄は「…」で省く(10.6.1)。
- 右端のマージンと8ドットの幅の欄に、下向きの三角の印を描く。幅はマージンの3/4、高さは3/8で、ボリュームのつまみや連番ボックスの三角と同じパターン(`LK_PEMPHAS`)で塗る。
- 一覧が開いている間は、押しボタンを押している間と同じく枠を反転表示する。操作できない部品はスイッチと同じく白の網掛けで覆う。

一覧はメニューの一覧と同じもので、自分のポップアップウインドウとして、ほかのすべてのウインドウより前に開く。メニューの文字の大きさで名前を1行に1つ並べ、枠と網掛けの影を付け、ポインタの下の行を反転表示する。選んでいる名前の行には印を付ける。名前のタブの後ろは、メニューのキーの欄と同じく右端にそろえる。選べない名前(`inact`)は淡色で描き、選べない。一覧は、選んでいる名前の行が部品に重なり、名前の書き出しが部品の名前の書き出しとそろう位置に開く。幅は部品の幅以上である。画面からはみ出すときはメニューと同じく画面の中に寄せる。画面の高さに入りきらない数の名前があるときは、選んでいる名前を中心にした入るだけの行を出す。

操作は次のとおりである。

- 部品を左ボタンで押すと一覧が開く。押したまま行の上へ動かして離すと、その名前を選ぶ。
- 開いた押下をクリックとして離すと(ダブルクリックの間隔のうちに離すか、押した点からポインタがほとんど動いていない。下の「メニューと一覧を開いた押下の離し」)、一覧は開いたままになる。そのあと行を押して離すと選ぶ。
- 一覧の外で離したとき、一覧の外を押したとき、Escのときは、何も変えずに一覧を閉じる。右ボタンでは選ばない。
- 上下の矢印キーで反転表示する行を動かし(選べない行は飛ばす)、Enterで選ぶ。一覧は、開いた押下を扱ったのと同じデスクトップのタスクが、続く入力を読む前に開く(`pop_open`)。入力の層から読んだ順に一覧が受け取るので、開いた直後に打ったキーも、間を空けずに続けて打ったキーも取りこぼさず、一覧が開いている間のEnterが親のパネルの既定のボタンに届くこともない。
- 一覧が開いている間、ポインタとキーの入力は一覧だけに渡し、下のウインドウやパネル、プロセスには通知しない。入力を読む`wm_read_event`が、ほかへ渡す前に`knl_pn_list_event`に渡す。

名前を選ぶと部品の値が変わり、部品に離した通知(`OB_E_RELEASE`)と、値が変わったときは変化の通知(`OB_E_CHANGE`)が出る。`lib/libui`では`UI_EV_CHANGE`になり、`ui_value`で選んだ番号を読み、`ui_set_value`で選ぶ名前を変え、`ui_names`で名前の並びを入れ替える。パネルを閉じたとき、部品を無効か非表示にしたとき、名前の並びを入れ替えたときは、開いている一覧を閉じる。ただし、部品が今持っているのと同じ名前の並びを書いたときは何も変えず、一覧も閉じない(`knl_pn_set_names`)。状態を1秒ごとに読み直して部品に書き直す小物(ネットワーク設定の〈Ｗｉ－Ｆｉ〉、システム環境設定の〈ネットワークアダプタ〉など)で、開いた一覧がすぐ閉じて選べなくなっていたためである。一覧は画面に同時に1つだけである。

状態を読み直す小物は、名前の並びや中身が変わったときだけ部品の値を書き、毎回は書かない。人が一覧で選んで部品の値が変わったあと、その知らせ(`OB_E_CHANGE`)を小物が読む前に、前に読んだ古い値を小物が書くと、選んだ値が消える。ネットワーク設定は1秒ごとに〈保存した接続〉へ、読み直しの初めに読んだ値を書き直していたので、選んだ瞬間がその間に入ると(UIテストで20回に4回)選んだことが取り消された。キーの間隔(0.5秒と1.5秒)とは関係が無かった。ネットワーク設定は名前の並びが変わったときだけ書く。システム環境設定の〈ネットワークアダプタ〉のアダプタの一覧は、選んでいる行と今の設定の下線を、それが変わったときだけ書く。

#### メニューと一覧を開いた押下の離し

右ボタンのメニュー(デスクトップのウインドウのメニュー`dt_run_menu`、プロセスのメニュー`mn_pop_men`の`drive_menus`)とポップアップの一覧(`knl_pn_list_event`)は、開いた押下からその離しまでを同じ規則で扱う(`wm_click_begin`、`wm_click_take`)。

| | 開いた押下の離しの扱い | 確かめたもの |
| --- | --- | --- |
| Windows | 右クリックのメニューは、右ボタンを離したときに出す。`DefWindowProc`は`WM_RBUTTONUP`を処理するときに`WM_CONTEXTMENU`を作り、アプリケーションはそれを受けて`TrackPopupMenu`でメニューを出す。開いた押下の離しは、メニューが出る前に済んでいる | Microsoft Learnの`WM_CONTEXTMENU`の説明 |

| Qt | メニューを出した位置から、マンハッタン距離で`QApplication::startDragDistance()`を超えて動くか、6回より多く動くまでは「動いていない」とみなす(`QMenuPrivate::hasMouseMoved`)。メニューの中で押してから、動かさずに離すと、項目を選ばずにメニューを閉じる。開いた押下の離しそのものの扱いは、全部は確かめていない | `src/widgets/widgets/qmenu.cpp`(dev) |

規則は次のとおりである。

- 開いた押下の離しは、押してから離すまで動かしていなければ、クリックとみなす。動かしていないとは、ポインタが押した点から8ドット(GTK 3の設定`gtk-dnd-drag-threshold`の既定値と同じ値)より遠くへ行かず、ポップアップの一覧では、開いたときに部品の上に来た行(`ls_hot0`)から別の行へ移っていないことである。動かしていない離しが、ダブルクリックの間隔(外観設定テーブル`WM_LOOK_DBLTIME`、既定400ms)のうちに来たとき、または押した点が分かっていてそこから動いていないときは、メニューと一覧は開いたままで、何も選ばない。ゆっくり押して離す人でも、動かしていなければ開いたままになる。
- 押したまま8ドットより遠くへ動かすか、一覧の別の行へ移してから離したときは、間隔のうちでもクリックとはみなさず、その場所で離したものとして扱う。一覧は離した行を選び、メニューは外で離すと閉じる。Windows、macOS、GTKのポップアップで、押したまま別の項目へ動かして離すとその項目を選ぶのと同じである。
- 開いた押下のボタンは、その押下の通知が言うボタンを使う(`wm_click_begin`の`code`)。ポップアップの一覧は、部品を押した通知のボタンを渡す。ボタンを知らないところ(プロセスのメニュー`knl_wmobj_menu_run`、デスクトップのメニュー`dt_run_menu`)は`WM_CK_FIND`を渡し、ウインドウマネージャがその時刻の押下を、読んだ押下と、オブジェクトの層に渡された押下の記録(`knl_wm_press_seen`、最後の8回)から引く。記録に無い押下は、追う押下が無いものとして扱い、ボタンを推し量らない。テストが直接渡す押下も、実機で読んだ押下も、同じ道で記録する。
- 開いた押下のボタンを押している間に来たほかのボタンの押しと、その離しは、メニューにも一覧にも渡さない。
- プロセスのメニュー(`mn_pop_men`)は、プロセスが押下の通知を読んでから開くので、素早いクリックでは、メニューを始める時点で開いた押下の離しがもう済んでいることがある。その離しは、まだ開いていないメニューには届かない。そこでウインドウマネージャは、ボタンごとに最後に離した時刻を、入力が届いた順に、どのメニューより先に書き残す(`outer_kernel/wm/wmobj.c`の`wo_up_when`、`knl_wmobj_event`)。メニューを始めるとき(`knl_wmobj_menu_run`)、開いた押下のボタンの最後の離しが押下と同じ時刻か、それより後なら、クリックはもう終わったとみなし、メニューを開いたままにする。素早いクリックでは、PS/2やUSBのマウスの1回の報告に押下と離しが両方入り、二つは同じ時刻で届くので、同じ時刻も含める。前のクリックの離しは押下より前の時刻なので、終わったクリックとは数えない。同じ離しが後から入力の流れでメニューに届いたときは、時刻が同じものを一度だけ読み飛ばし、離しを二度数えない。これが無いと、メニューは開いた押下がまだ続いているとみなすので、一つ上の規則により左ボタンの押しと離しを渡さず、項目を選べなくなる。

最後の規則は、ThinkPad X1 Yoga 第3世代の実機(TrackPoint、PS/2)で、右ボタンを素早く押して離すと、メニューの先頭の「閉じる」が選ばれて前面のウインドウが閉じていたことへの対策である。メニューは右ボタンの押しと離しでは選ばないので、選ぶには左ボタンの押しと離しがメニューの上に届く必要がある。UIテストで、右ボタンを押している間に左ボタンを押して離すと、直す前はウインドウが閉じることを確かめた。実機では、マウスのパケットの区切りがずれると、動きのバイト(-1を表すFFなど)が先頭のバイトとして読まれ、押していない左ボタンのビットが立つ。その直しは06章のPS/2の行と`device/ps2/ps2.c`の注釈に書いた。この規則は、どの入力の機器(TrackPoint、タッチパッド、USBのマウス、タッチパネル)でも、入力の層の後で同じに働く。

### 10.6.1 一覧の欄

スクロールセレクタ、スイッチセレクタ、ポップアップの名前は、タブ(0x09)で区切ると欄(列)に分かれる。GTKの`GtkTreeView`の列と省略(ellipsize)、Windowsのリストビューの列と同じ考え方で、欄ごとに幅を持ち、その幅に入らない文字は末尾を「…」(U+2026)にして省く。1つの部品の中では、どの行も同じ欄の幅で並ぶので、縦にそろった表になる。タブの無い名前は1つの欄で、スイッチやセレクタの名前がこれまでどおり隣の名前の場所にかかってもよいように、部品の右端の4ドット手前まで使い、そこに入らなければ同じく「…」で省く。描くのは標準の部品の描画(`outer_kernel/wm/pdraw.c`の`name_in`)で、プログラムは名前をタブで区切って渡すだけである。

欄の幅は次のように決める。

1. データボックスのパネルの定義に`cols`があれば、それに従う(10.7)。`cols="0,64r,112"`は、左から順に欄の幅をドットで書いたもので、0の欄は、ほかの欄が取った残りを0の欄どうしで等分する。数のあとの`r`は、その欄の文字を右端にそろえる(数や大きさの欄)。書いていない欄は0と同じである。幅の合計が行に入らないときは、決まった幅の欄を同じ割合で縮める。
2. `cols`が無ければ、中身から決める。2つ目より後の欄は、その部品のすべての名前のうち、その欄でいちばん幅のある文字の幅にする。ただし、それらの合計は行の幅の半分までとし、超えるときはその割合で縮める。1つ目の欄(名前)が残りを取る。一覧をスクロールしても欄の幅は変わらない。

行の文字は、ランプとマージン(16ドット)の後から、行の右端の8ドット手前までに並べ、欄と欄の間は8ドット空ける。欄の幅は論理ピクセルなので、表示の倍率(10.2.3)を変えても欄の位置と幅は同じで、全体が大きく描かれる。倍率では字形を物理ピクセルで作るので、文字の幅がわずかに測った幅と違うことがある。それでも欄の外に出ないように、欄ごとに描く範囲をその欄の矩形に絞ってから描く。省いた文字の後ろの「…」は、測った幅で欄に入る位置に置く。

部品の`sb_n`、`sbw[]`、`sbf[]`(連番ボックスの欄に使うもの)を、一覧、セレクタ、ポップアップでは欄の幅の指定の置き場に使う(`SBF_RIGHT`が右寄せ)。部品の定義の構造(`T_WMPART`)の大きさは変えていない。

部品は、CtrlかAltをかけたキーを文字として扱わない。テキストボックスでかな漢字変換の途中でなければ、そのキーは部品の値にせず、パネルを置いたプログラムに渡す(`part.c`の`pn_key`)。CtrlとAltのキーはコマンドで、受け取ったプログラムは、それが何のコマンドかを、キーの位置ではなくキー配列を通した後の文字で決める(`wm_key_cmd`、11.15)。英字配列がDvorakのとき、Dの位置(0x07)のキーはeを打つので、Ctrlとそのキーは、物理キーボードでもソフトウェアキーボードでもCtrl+Eになる。

色の平面(`WM_PT_SVMAP`、17)と色相のバー(`WM_PT_HUEBAR`、18)は、色を選ぶための部品である。平面は、ある色相について、左から右へ彩度、下から上へ明度を変えた色を描く。値は色相、彩度、明度をまとめた整数(`WM_SVMAP_VALUE`)で、印は下の色に応じて黒か白の丸の輪である。バーは右から左へ色相を描く細い角丸の帯で、値は0から359の色相、印は丸である。どちらも押すかドラッグすると印と値が動き、ドラッグが部品の外へ出ても端で止まる。色の丸(`WM_PT_COLDOT`、19)は部品の色を丸く塗るだけで、押しても何も起きない。スポイト(`WM_PT_DROPPER`、20)はスポイトの絵で、押しボタンと同じく離したときに応答を返す。パネルの種類`WM_PNL_SHEET`は、灰色の地と太い枠の代わりに白い地と細い枠を描く。少しの部品を載せるポップアップに使う。

色の部品(`WM_PT_SWATCH`)に応答(`answer`)を持たせると、押しても印を付けず、押しボタンと同じく離したときに応答を返す。色を見せて、押すと何かをする欄に使う。プログラムは`wm_panel_set_colour`で色を書き換え、`wm_panel_colour`で読む。

`wm_panel_show`は部品を見せるか隠す。キーを持つ部品を隠すと、キーは見えているテキストボックスに移る。`wm_panel_part_screen`は部品の画面の上の矩形を答える。`wm_panel_open_at`は、`wm_panel_open_centre`と同じ自分のウインドウを持つパネルを、画面の指定の位置に開く。画面からはみ出すときは、画面の中に収める。

### 10.6.2 部品の名前の持ち方

スクロールセレクタ、スイッチセレクタ、ポップアップ、タブパネルの名前と、連番ボックスの名前の欄の名前は、部品ごとに、名前の大きさに合わせて確保した塊(`T_WMNAMES`)に持つ。塊は0で終わる名前を並べたもので、部品の`names`が指す。中身はウインドウマネージャだけが扱う(`outer_kernel/wm/pdraw.h`)。名前の数と長さの合計に上限はなく、確保できないときだけ`E_NOMEM`になる。

以前は、パネル1枚のすべての部品の名前を、定義(`T_WMPANEL`)の中の8192バイトの置き場(`pool`)に並べていた。ブラウザの〈設定〉の〈履歴〉は、実機では行にして8KBを大きく超え(履歴の記録で約29KB)、名前の書き換えが`E_LIMIT`で断られ、一覧が空のままになった。置き場を広げても、次に大きな一覧で同じことが起きる。また、書き換えは置き場を全部の部品の分だけ詰め直していたので、途中で一杯になると、それより前の部品の名前の位置がもう詰め直した位置に書き換わったまま残り、ほかの部品の名前がずれた。GTKの`GtkListStore`、WindowsのリストビューやQtの`QStringListModel`も、一覧の行を部品(モデル)ごとに、行の数に合わせて持つ。TessronOSもそれにならい、名前を部品ごとの塊にした。

- 定義を作るカーネルの中のプログラム(デスクトップ、データボックスのパネルの読込み`pndef.c`)は、`wm_part_name`で部品に名前を足す。塊は一杯になると2倍の大きさに作り直すので、名前をn個足しても写し直しは数回である。戻り値は、その名前が部品の名前の中の何バイト目か(連番ボックスの名前の欄の`sbpool`に書く)。名前を持たせた定義は`wm_panel_free`で返す。
- パネルを開くとき(`wm_panel_open`)は、定義の各部品の塊を写して、パネルの持ち物にする。定義は写すという決まり(16.2.3)はそのままで、呼んだ側はすぐに定義を返してよい。写せないときは開かずに`E_NOMEM`を返し、写した分も返す。開いたパネルに部品を足すとき(`knl_pn_add`)も同じく写す。部品を外に写して渡すとき(`knl_pn_part`)は、塊を指さない(`names`を空にする)。
- 名前の書き換え(`knl_pn_set_names`、部品のレコード4)は、新しい塊を確保して写してから、古い塊と取り替えて返す。ほかの部品の名前は動かない。確保できないときは、部品は前の名前のまま残り、`E_NOMEM`を返す。名前の読出し(`knl_pn_names`、レコード4の読出し)は、ロックの中で呼び手のための写しを作って渡すので、名前の長さに上限はない。
- パネルを閉じるとき(`wm_panel_close`)、部品を外すとき(`knl_pn_del`)に塊を返す。プロセスが終わったとき(`knl_wmobj_prc_end`)と、ウインドウがなくなったとき(`knl_pn_wins_gone`)も、パネルは`wm_panel_close`で閉じるので、同じ道で返る。
- データボックス(`db_put`)は定義をバイト列のまま持つので、部品の名前は入らない。`wm_panel_open_box`で開いたパネルの名前を持つ部品は、名前なし(数0)で開き、プログラムがあとで書く。
- プロセスは名前の全部を1回の`ob_wri_rec`で書く(`lib/libui`の`ui_names`)。カーネルは書き込みの大きさに上限を置かないので、分けて書く形は要らない。`ui_names`は、ウインドウマネージャの答え(`E_NOMEM`、部品がなければ`E_NOEXS`)を返す。

描くのは見えている行だけである。スクロールセレクタは、先頭に見えている行の名前を1度たどって見つけ、続く行は1つ前の名前の次として読む。欄の幅を中身から決める一覧(10.6.1)では、すべての名前の欄の幅を測る必要があるが、測った結果を塊に覚えておき(`ncol`、`nat`。測った書体`colfid`も)、名前が変わるまで測り直さない。そのため、名前を書いた後の最初の描画だけがすべての名前を読み、それ以後のスクロールや選択は見えている行の分だけかかる。スクロールバーのつまみの位置と大きさは、名前の数と見えている行の数から計算し、名前は読まない。

試験は、カーネル試験の`part`の組の`test_names_big`で行う。5000行、合計100KB以上の名前を書いて読み戻し、描画、ホイールでのスクロール、行の選択を行う。確保を失敗させる試験用の口(`knl_pn_test_nomem`、`USE_KTEST`のときだけ)で、書き換えの途中で失敗させても、その部品とほかの部品の名前が前のままであることを見る。パネルを3回開いて閉じ、カーネルのヒープの使用量が戻ることも見る。ブラウザでは、`v8`の組の`test_blink_hist_many`が、履歴を3000件にした〈設定〉の〈履歴〉の一覧に、3000行が入ることを見る(試験の手順`setstep=histfill:N`で履歴を足す)。

## 10.7 パネルとデータボックス

パネルは部品を並べたものである。パネルの定義は、データボックス実身のレコード0に、番号付きの`<panel>`要素としてxmlTADで書く。

```xml
<databox>
<panel num="1" rect="0,0,435,324" title="ネットワーク設定" kind="bare">
<tags num="100" rect="0,0,435,324" inner="4,28,431,320" value="1">
<tag>＠ネットワーク</tag><tag>アドレス</tag><tag>＋状態</tag>
</tags>
<text sheet="1" x="8" y="80">自ホスト：</text>
<box num="11" sheet="1" rect="136,58,264,88" max="79" ascii="true"/>
<button num="35" sheet="2" rect="320,272,408,296">表示更新</button>
</panel>
</databox>
```

部品の要素には、`text`(ラベル)、`tags`(タブパネル)、`box`(テキストボックス)、`secret`(秘匿テキストボックス)、`number`(数値ボックス)、`serial`(連番ボックス)、`switch`(オン/オフスイッチ)、`button`(押しボタン)、`select`(セレクタ)、`choice`(選択スイッチ)、`list`(スクロールセレクタ)、`popup`(ポップアップ)、`volume`(ボリューム)、`line`(線)、`icon`(アイコン)、`swatch`(色)がある。線の部品は、矩形の高さが1ならその上の行に水平の線を、幅が1ならその左の列に垂直の線を引き(矩形の右と下の辺は矩形の外)、それ以外は左上の角から右下の角へ線を引く。押しボタンは`pict="0_N.png"`で絵の押しボタンになる。絵はそのデータボックスの実身のレコード0の資源N(PNG)で、カーネルはパネルの定義を読むときにその時のタスクで絵を読んで覚え(`knl_pn_pict_load`)、描くときは押しボタンの枠の内側の中央に置く。システムの書体に字のない記号(マイクロカードの≒)や、罫線とグラフの絵(基本表計算の操作パネル)、図形編集の道具がこれを使う。色の部品(`WM_PT_SWATCH`)は、プログラムが状態のレコードに0xRRGGBBの整数を書くと、その色で塗る。2つ目の整数も書くと、それが0でないときに選んだ印を付け、0なら印を消す(`lib/libui`の`ui_set_swatch`。色の並びで選んでいる色を示す)。`off="true"`にして色を見せるだけに使う。アイコンの部品(`WM_PT_ICON`)は、実身のアイコンを仮身と同じ絵で見せる。プログラムが実身のUUIDを文字として書く(テキストボックスと同じく状態のレコードに書く)と、カーネルはその時に書いたプログラムのタスクでアイコンを読み、描くときは覚えた絵を部品の矩形の中央に置く(大きければ縮める)。空の文字なら何も描かない。押しても何も起きない。設定の小物のウインドウ(`lib/libui`、`ui_open`)は、開く前に`ui_attr`で大きさを変えられることと右の縦のスクロールバーを頼めば、それを持つ。スクロールバーはウインドウの持ち主のもので、`ui_bar`で全体と見えている所を書き、つまみや溝の操作(`UI_EV_SCROLL`)、ホイール(`UI_EV_WHEEL`)、大きさの変化(`UI_EV_SIZE`、`ui_work`で作業領域の大きさを読む)を受けて、パネルに見せるものを替える。パネル自身は動かない。ラベルの位置は(x、ベースライン)で指定する。部品はプログラムから`num`の番号で指定する。カーネルの中のプログラムは、`wm_panel_set_text`でテキストボックスの文字を書き換え、ラベルに使うとラベルの文字を書き換える(基本図形編集の道具パネルのポインタの座標)。

スクロールセレクタ、スイッチセレクタ、ポップアップは、`cols="0,64r,112"`で欄の幅を指定できる(10.6.1)。ネットワーク設定の走査の一覧(SSID、電波の強さ、暗号方式)、システム環境設定のネットワークアダプタの一覧(使用中と種類、名前、リンク、アドレス)とディスクの一覧(名前、大きさ、付け先)がこれを使う。指定の無い一覧も、欄の幅を中身から決めて「…」で省く。

タブパネルに`scroll="true"`を付けると、タブの中身がスクロールする。ウインドウの作業領域がパネルの定義より低いとき(小さい画面で開いた、あとで画面を小さくした)、パネルは作業領域の下端で終わり、タブの枠もそこまで縮む。表示しているタブの部品は、タブの中の残った所(下の段のタブがあればその下から)に、ずらして見せる(`part.c`の`pn_fit`、`pn_view`)。`foot="true"`を付けた部品(タブの下端のボタンの行と、その行に並ぶ部品)はスクロールせず、パネルの下端と一緒に上がって、いつもウインドウの中に見える。スクロールするのはそれより上の部品で、見えている所の外は描かず、押しても当たらない。どこまでスクロールできるかは、表示しているタブの、下端に置かない部品の一番下で決まる。

ウインドウに右のスクロールバーがあれば(`ui_attr(WM_ATTR_RBAR)`)、そのスクロールバーはパネルのものになる。ウインドウマネージャがタブの中身の高さと見えている所をドット単位で書き(`pn_bar`)、溝とつまみの操作はパネルが受ける(`knl_pn_scroll`。プログラムには`UI_EV_SCROLL`が来ない)。タブの中身が全部見えるときは、つまみがスクロールバーいっぱいになって動かない。大きさの変えられないウインドウのスクロールバーは細いので、画面が大きいときの見た目は、右の枠が8ドット太くなるだけである。ホイールは、一覧の上ならその一覧を、ほかの所ならタブの中身を、一覧の3行分ずつスクロールする。［Tab］で入力の対象を移したときは、その部品が見えるまでスクロールする。ほかのタブに替えると、先頭から見せる。パネルは、ウインドウの大きさが変わるたびに(画面の解像度の変更を含む)高さを取り直す(`knl_wmobj_moved`から`knl_pn_fit`)。部品が中に収まっているかの自己検査(`wm_panel_self_check`)は、定義の高さで見る。システム環境設定のパネル1がこれを使い、640×480でも〈設定〉〈確認〉などのボタンの行がウインドウの中に見える。

パネルを描くのと、パネルの中身を変えるのは、一度に一つのタスクだけが行う(`part.c`の`pn_lock`。同じタスクは重ねて取れる)。パネルは、部品を書き換えたプロセスのタスク(`ob_wri_rec`)、入力を読むタスク(押下、ホイール、キャレットの点滅)、ウインドウのスクロールバーを動かしたデスクトップのタスクから、どのプロセッサででも描かれる。二つが同時に描くと、互いの部品の上に地を塗る。さらに、どちらも描画環境の描ける範囲(スクロールするタブの中、テキストボックスの文字の枠)を狭めてから、見つけた範囲に戻すので、もう一方が狭めた範囲を戻してしまうことがある。そうなると、そのウインドウはそれ以後、細い帯の中にしか描けなくなる。名前の書き換え(`knl_pn_set_names`)は部品の名前の塊を取り替えて古い塊を返すので、描いている最中なら返した塊を読ませてしまう。そこで、描くこと(`wm_panel_draw`、部品1つの描き直し、点滅)、スクロールの位置と高さの変更、部品の値・名前・フラグの書き換え、部品の追加と削除、パネルとメニューを開くことと閉じること、入力の処理を、すべてこのロックの中で行う。このロックはウインドウマネージャのロックとオブジェクトの層のロックより先に取り、それらを持ったまま取らない。試験は、カーネル試験の`part`の組の`test_scroll_draw`で行う。スクロールするパネルを二つのタスクが同時に描き、一方はスクロールと部品の書換えも行う。そのあとで、描画環境の描ける範囲が元のままであることを見る。直す前は、x64で範囲が`11,50-379,62`(テキストボックスの文字の枠)のまま残った。

プログラムが自分で描くウインドウの上や下にパネルを置くとき(`ui_strip`)は、パネルがウインドウの作業領域の全体ではない。そのようなパネルのテキストボックスは、開いたときに入力の対象にならず、押したときに入力の対象になり、作業領域の自分で描く所を押すと外れる(`part.c`の`beside`)。この扱いになるのは、`ui_strip`が作ったパネル(パネルの実身のメタデータの`tessronos.part`に`"beside":1`、`knl_pn_set_beside`)だけである。作業領域より低いだけの普通のパネル(尋ねるパネル、カーネルの中で開くパネル)は、作業領域の全体を占めるパネルと同じく、開いたときに最初のテキストボックスが入力の対象になる。キーはそれまで、プログラムの描く内容のものである。作業領域の全体を占めるパネル(設定の小物、尋ねるパネル)は、今までどおり最初のテキストボックスが入力の対象になる。キー配列、マイクロカード、予定表のツールバーがこの形である。

選択スイッチは`<choice num="11" rect="164,18,244,40" group="10" value="1">左</choice>`のように書く。1つの部品が1つの選択肢で、同じ`group`の部品のうち1つだけが入る(`WM_PT_CHOICE`。デスクトップの部品のパネルの選択肢と同じ部品)。入っているかどうかは、それぞれの部品の値(0か1)で読む。

ポップアップは`<popup num="16" rect="120,282,440,308" value="1"><name>明朝</name><name>ゴシック</name></popup>`のように書く。`<name>`は省いてよく、そのときはプロセスが開いたあとで名前の並びを書く。`value`を省くと、名前があれば1、なければ0である。高さはテキストボックスと同じ26ドットほどにする。

プロセスは、パネルの実身を作成するときにメタデータの`tessronos.part`に`box`(データボックスのUUID)と`num`(パネルの番号)を指定し、`ob_map_rec`で自分のウインドウに配置する。パネルのリンクのレコードから部品のUUIDを取得し、部品を開く。部品の値は状態のレコード(3)で読み書きし、セレクタの名前の並びは部品のレコード4に書く。無効状態と非表示状態は配置のレコード(2)のフラグで切り替える。部品で起きたイベントはパネルのその部品のリンクのレコードにも通知されるので、パネルに一度だけ通知を要求すればよい。部品の値、名前、表示を書き換えると、ウインドウマネージャはパネルを描き直して画面の組み立てを求めるが、組み立て終わるのを待たずに戻る(`wm_post`)。値とフラグを前と同じに書いたとき(部品の中身と、キー入力を受ける部品が変わらないとき。`knl_pn_set_state`と`knl_pn_set_flags`が1を返さない)は、描き直さず組み立ても求めない。周期で読み直したページを毎回書き込んでも、変わらなければ画面は動かない。パネルは地から全体を描き直すので、描き直す前に、それまでに求めた組み立てが終わるのを待つ(`wm_flush`。待つものがなければすぐ戻る)。待たないと、部品を続けて書き換えるプログラムでは、組み立てが地だけを塗った途中のパネルを読んで画面に出し、ウインドウが点滅して見える(2026-11-06。システム環境設定を開くと、パネルを65回描き、その間の56回の組み立てが描画の途中を読んでいた)。部品を書き換えてからウインドウを描いて表示する(`wm_obj_flush`)プログラムは、両方が1回の組み立てで画面に出る。ウインドウの実身を作るメタデータに`"hidden":1`があると、ウインドウは隠した状態で作られ、配置のレコード(2)に`OB_WP_SHOWN`を書いたときに初めて出る。隠している間に書き換えた部品は描かず、出すときにそのウインドウのパネルを1回だけ描く。隠したウインドウに置いたパネルも、置いたときには描かない(メニューは除く)。`lib/libui`では`ui_attr`に`UI_ATTR_HIDDEN`を付けて開き、部品の状態を決めてから`ui_reveal`で出す。システム環境設定、ユーザ環境設定、ネットワーク設定もこの形で開き、開いたときのパネルの描画は1回になる(以前はそれぞれ65回、81回、64回描いていた)。開いたパネルの部品が1つずつ描き直されて見えることがない。

`lib/libui`は、この手順と、部品を番号で読み書きする関数をまとめたライブラリである。描画は一切しない。

### 10.7.1 パネルと通知の文の折り返し

ラベルの部品は1行で、長い文を折り返さない。長い文を何行かのラベルに分けて見せるもの(ブラウザの許可の確認などのパネルの`dlg_lines`、デスクトップの通知の`dtnotify.c`の`wrap`)は、行がいっぱいになった所で、禁則を守る位置まで戻って折る(`include/ts/kinsoku.h`の`kin_break`)。行頭に置かない字(、。，．：；？！・ー）」』】〕｝〉》と小書きのかな、半角の,.:;?!)]})と、行末に置かない字(（「『【〔｛〈《と半角の([{)の表は、文章の表示(`docview.c`)が文書に禁則の指定がないときに使うものと同じ1つである。英字の語(空白を含まない半角の字の並び)は、1行に収まる限り途中で折らない。折った後の空白は次の行の頭に置かない。

行頭に置かない字が次の行の頭に来るときは、その前の字と一緒に次の行へ送る(追い出し)。JIS X 4051では、行頭禁則の処理は追い込み、追い出し、ぶら下げのどれかである。パネルと通知の行は右端をそろえないので、追い込みで詰める字間がない。ぶら下げは字を行の右の外に置くので、ラベルの部品の矩形からはみ出して切れる。そのため追い出しにした。たとえば「`https://webrtc.github.io`がマイクの使用を求めています。」は、52桁で「…求めていま」「す。」と折れ、句点だけの行はできない。行のどこでも折れないとき(区切りのない長い英字の並び)は、いっぱいになった所で折る。

## 10.8 メニュー

メニューは定義実身から作成する。定義実身のレコード0の`<menu>`要素に項目を並べる。

```xml
<menu>
<include><link id="…_0.xtad"/></include>
<item code="update" key="S">設定を更新</item>
<line/>
<item code="clear">削除</item>
</menu>
```

`<include>`は別の定義の項目をその位置に取り込む。どのウインドウのメニューにも出る共通の項目(閉じる、仮身操作、実身操作、屑実身操作、ウインドウ、小物、実行)はシステムの定義実身にあり、プログラムはそれを取り込むだけでよい。項目にリンクを持たせると、そのリンク先の定義がその項目のサブメニューになる。プログラムのコードが扱うのは定義実身のUUIDと項目の`code`だけで、メニューの文言や並び順はコードに書かない。プロセスは`mn_cre_men`でメニューを作成し、`mn_pop_men`で表示して選択結果を受け取る。

サブメニューを持つ項目(小物、ウインドウ、実行、仮身操作、書式、文字サイズなど)は、それ自身を選ぶ項目ではない。ポインタをその項目の上に置くと、ユーザ環境設定のメニュー反応時間の後にサブメニューが開き、ポインタがほかの項目へ移ると閉じる。その項目をクリックする(左ボタンを項目の上で押して離す)と、サブメニューは待たずにすぐ開き、固定表示になる。メニューは閉じない。固定表示のサブメニューは、ポインタが親のメニューのほかの項目の上を通っても、メニューの外へ出ても閉じない。サブメニューの項目をクリックすると、そのときに選択が確定し、メニュー全体が閉じる。親のメニューで別の項目をクリックすると、固定表示のサブメニューは閉じ、その項目を選ぶか、その項目のサブメニューを固定表示する。サブメニューをたどって開いた途中の項目をクリックしたときは、その項目から親までのメニューがすべて固定表示になる。メニューの外を押すか、Escで、全体が閉じる。この扱いはウインドウマネージャのメニューの層(`outer_kernel/wm/part.c`の`menu_event`と`menu_sub_keep`)で行うので、デスクトップのウインドウのメニュー(`dt_run_menu`)にも、プロセスのメニュー(`mn_pop_men`)にも、強制終了のメニューにも同じに効く。アプリは、サブメニューを持つ項目の選択を受け取ることがない。テスト:ktest_partの`test_menu_sub`。

## 10.9 メッセージ行とトレー

画面下端のメッセージ行は、入力モード(英字、日本語、ローマ字、かな)と時刻を表示し、プログラムの短いメッセージを表示する(`wm_msg_put`)。トレーは、プログラム間で仮身や文字列を受け渡すための一時的な保管場所(クリップボード)である。プロセスは`tr_`のSVC(付録Aのクラス9の20〜29)でトレーを使う。トレーはシステムの実身で、そのキーはカーネルのものなので、プロセスの呼出しはカーネルのタスクが1件ずつ代わりに行い、入れるバイト列と取り出すバイト列はカーネルのメモリを通して受け渡す。

## 10.10 かな漢字変換

かな漢字変換は、Mozcを移植した変換エンジン(`MOZC=1`でリンクする)で行う。リンクしない構成では、ローマ字からかなへの変換だけを行う。入力モードは[ひらがな/カタカナ]キーで日本語、[英数]キーで英字に切り替わる。パネルのテキストボックスとプロセス(`kc_`のSVC)が、同じ変換エンジンを使う。小物「単語登録」でユーザ辞書に登録した単語は、どちらの構成でも変換の候補に出る(11.16)。

変換の候補の一覧は、システムが出す。プロセスのアプリ(コンソール、電子手帳、基本表計算、マイクロカード、マイクロスクリプト)は、変換中の文字列だけを自分のウインドウに描き、候補は普通のウインドウのレコード`OB_WR_CAND`(`T_OBWCAND`、`ob_cand_put`)に書く。書くのは、変換中の文字列の箱(作業領域の`x`、`top`、`bottom`)、1ページの候補(9つまで)、選んでいる候補、ページの先頭と全部の数である。ウインドウマネージャは、それを前面に出てキーを持たない小さなウインドウ(`WM_ATTR_POPUP`と`WM_ATTR_NOFOCUS`)に、パネルのテキストボックスの候補と同じ描き方(白地に暗い線の枠、番号付きの行、選んでいる行の反転)で描き、全部の数がページより多いときは「何番目/全部の数」を下に添える。置く所は箱の下で、画面の下端に収まらなければ箱の上にする。候補の数を0にして書くか、ウインドウを閉じると消える。候補の行を押すと、ウインドウマネージャはウインドウの持ち主に、レコード`OB_WR_CAND`の押下(`OB_E_PRESS`、`code`が行の番号)として知らせる。ウインドウそのものの押下はレコードを持たない(-1)ので、取り違えない。テスト:ktest_mnの`test_cand`。

入力モードはキーボードのもので、ウインドウマネージャが入力を読む流れの中で、キーが届いた順に切り替える(`wm_read_event`から`knl_msg_mode_key`、`outer_kernel/wm/msgline.c`)。モードを切り替えるキーも、それより後のキーも、宛先へ渡す前にモードを決めるので、キーの通知(`T_OBNTM`)には、そのキーを処理した時点のモード(`imode`)が載る。モードを切り替えるキーの通知には、切り替えた後のモードが載る。プロセスは、キーの意味(変換器に渡すか、英字のまま入れるか)を、今のモード(`kc_mode`)ではなく通知のモードで決め、`kc_hid_key`にそのモードを渡す。プロセスの処理が遅れて、確定のEnterを読む前に英数キーまでがウインドウマネージャを通っても、Enterは日本語のモードのキーとして変換器に渡り、確定は失われない。英語のモードのキー(英数キー自身を含む)が変換の途中に届いたときは、プロセスはまず変換中の文字列を、それを打ったモードでの確定(Shift+Enter)で入れてから、そのキーを英語のキーとして扱う。

LinuxのIBusとfcitx5は、モードの切替えを入力コンテキストのキーの処理の一部として、キーと同じ順に行い、切り替えるときに変換中の文字列を確定する。macOSの入力メソッドも、入力ソースを切り替えるときに変換中の文字列を確定してから、後のキーを新しい入力ソースに渡す。どれも、キーを解釈する時点のモードを後から読み直すことはしない。TessronOSでは、モードはシステムに1つで、変換のセッションはプロセスごとにあるので、モードをキーと一緒に通知に載せて、同じ順序を保つ。
