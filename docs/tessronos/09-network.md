# 第9章　ネットワークとカレンダ

## 9.1 TCP/IP

TCP/IPスタックはNetBSD 11.0のカーネルのものである。NetBSDのカーネルのコードを、ハイパーコールと呼ぶ小さなインタフェースの上で動く部品として切り出したrumpカーネルの仕組みを使い、TessronOSのカーネルの中で動かす。ソースコードはNetBSDの配布物をそのまま使い、変更しない。`tools/netbsd/build.sh`がソースを取得してTessronOSのツールチェーンでコンパイルし、1つのオブジェクト(`~/tessronos-netbsd/rumpnet.o`)にまとめ、カーネルにリンクする(12.2)。

対応しているのは、IPv4、IPv6、TCP、UDP、ICMP、ICMPv6、ARP、近隣探索、IGMPとMLDによるマルチキャスト、Ethernetとループバックである。TCPはウインドウスケール、SACK、タイムスタンプを持ち、輻輳制御はNewRenoである。IPv6のアドレスは、スタックが付けるリンクローカルアドレスと、ルータ広告から作るアドレス(SLAAC)である。DHCP、ルータ広告の処理、DNSによる名前解決、SNTPは、NetBSDでもカーネルの外のプログラムが行うものなので、スタックの外にあるTessronOSのコードで行う(9.3、9.4)。

以前のスタックであるlwIP 2.2.0も残してあり、`make NETSTACK=lwip`でビルドすると、NetBSDのスタックの代わりに組み込まれる。どちらのスタックでも、`so_`の関数の名前、引数、定数、構造体、エラーコード、SVCクラス5の番号は同じである。

### 9.1.1 構成

| 部分 | 場所 | 内容 |

### 9.1.2 ハイパーコール

rumpカーネルは、ホストに対してハイパーコール(`rumpuser_`で始まる関数、インタフェースのバージョンは17)を呼ぶ。TessronOSでは、ホストはカーネル自身である。

| 資源 | 実現 |
| --- | --- |
| メモリ | 2のべき乗のページ数の要求はページアロケータから、それ以外は`Kmalloc`から確保する。1ページの要求は、一度確保したページをrumpカーネル専用のリストで使い回し、ページアロケータには返さない。起動時に4MB分を確保しておく。rumpカーネルが使うメモリの上限は128MBで、それを超えるとrumpカーネル自身がプールを縮める |
| スレッド | T-Kernelのタスク。優先度10、スタック64KB |
| 仮想プロセッサ | 1つだけ持つ。rumpカーネルのスレッドは仮想プロセッサを持っている間だけrumpカーネルのコードを実行する。プロセッサの数と同じだけ持たせると、Raspberry Pi 5の4つのコアでページの多数の取得が重なったときに、スレッドのロックと載っている仮想プロセッサの対応が食い違い、rumpカーネルのスケジューラの検査で止まったため、1つにした。呼び出す側のタスクはrumpカーネルの外では並行に動く |
| ミューテックス、読み書きロック、条件変数 | スピンロックで守る待ちの列と、待つ間だけ借りるセマフォで作る。rumpカーネルは数千のロックを作るので、T-Kernelのオブジェクトは使わない。ロックを解放すると待っているタスクを起こし、起きたタスクがあらためてロックを取る。優先度の低いタスクがロックを渡されたまま実行されない、ということが起きない。スピンミューテックスは、仮想プロセッサを持ったまま取りに行くロックである。そのため、スピンミューテックスで条件変数を待っていたスレッドは、起きたら先に仮想プロセッサを取り戻し、それからミューテックスを取る。逆の順では、ミューテックスを持って仮想プロセッサを待つスレッドと、仮想プロセッサを持ってミューテックスを待つスレッドが互いを待ち、仮想プロセッサが1つなのでrumpカーネル全体が止まる(`select`と`poll`の待ちで起きた) |
| 時計 | システム時刻と単調時刻(`ts_get_mono`)。rumpカーネルのタイマは1秒に100回の刻みで進むので、その時計のスレッドは10ミリ秒ごとに起きる(4.4) |
| 乱数 | カーネルの乱数(`ts_get_random`) |
| コンソール | T-Monitorのコンソールに1行ずつ出力する |

rumpカーネルの外で待つとき(カードの読み書き、ロックの待ち、時計による待ち)は、仮想プロセッサとビッグロックを手放してから待ち、終わると取り直す。こうしないと、待っている間、rumpカーネルのほかのスレッドが動けない。

rumpカーネルは、どのスレッドとして動いているかを、タスクIDで引く表で知る。`so_`を呼んだタスクには、ソケットを持つrumpカーネルのプロセスのスレッドを1つ貸し、呼出しが終わると返してもらう。スレッドは必要な数だけ作り、以後は使い回す。

`make RUTRACE=1`でビルドすると、ロックを5秒以上待っているタスクを、待たせた場所のアドレスとともにコンソールに出力する。ロックの取り合いで止まったときの調査に使う。あわせて、表を引くタスクIDを割込みを止めて読み直し、`tk_get_tid`の答えと食い違えば`rumpuser: CHECK tk_get_tid gave …`と出す。表の欄が別のタスクのものと食い違ったとき(先にほかの値が入っている欄への設定、別のスレッドの欄の解除、スレッドの無いまま仮想プロセッサを手放す・取り直す)は、その前後のスレッドの設定・解除・開始・終了・待ちの出入りの記録を出す。負荷試験で、curlwpが別のスレッドになる(`rump_lwproc_curlwp_clear`の`l == curlwp`)、curlwpが無いまま仮想プロセッサを取り直す・手放す、ソケットのロックを持っていないと判断される(`solocked`)の止まり方は、`tk_get_tid`がタスクの移動の間に別のタスクのIDを返していたためだった(4.3)。

ロックと条件変数の待ちは、セマフォの時間の指定のない待ちが合図でだけ終わることを前提にしている。カーネルが別のCPUの合図と食い違って`E_TMOUT`を返すと(4.3)、ロックの待ちは合図が来たものとして進むが、条件変数の時間切れの扱いでは、もう取られた合図を待ち続けてそのスレッドが止まり、カーネルが後から書くエラーコードがスレッドのスタックを壊す。ブラウザの試験の切り替わりで、ワークキューのスレッドが仮想プロセッサを待つ`rump_schedule_cpu_interlock`の中で、上位が欠けた戻りアドレスへ戻って止まったのはこのためで、4.3の直しで起きなくなった。

試験グループ`rump`(`tests/ktest/ktest_rump.c`)は、4つのCPUからrumpカーネルに同時に負荷を掛ける。優先度の違う多くのタスクが、ループバックで接続を作っては使って閉じ(1つの待ち受けのソケットを3つのサーバが受け付けて返す)、データグラムを1〜2ミリ秒の待ちでやりとりし、何も来ないソケットを1ミリ秒ずつ待ち、ソケットを作ってはすぐ閉じる。あわせて、プロセスが接続して1バイト送り、返事を受けて自分で終わるか、返事のないまま待っているところを終了させられる。合図で終わる待ちと時間切れになる待ちが、rumpカーネルのロックと条件変数の中で交差する。すべてが進み、止めればすべてが終わり、その後も接続が通ることを確かめる。時間は`make KT_RUMP_S=<秒>`で変える(既定は20秒)。`STKWATCH=1`(4.7.6)と合わせると、スタックの書き換えを起きたところで検出する。

### 9.1.3 インタフェース

ネットワークデバイスはデバイス`neta`で、スタックはドライバを直接呼ばずにこのインタフェースを使う。Raspberry Pi 5ではRP1のEthernet、QEMUではvirtio-netがその下にある。x64のPCでは、virtio-net、IntelのLAN、USBのLAN、Wi-Fiの中から選んだものがその下にある(9.6)。

RP1のEthernet(Cadence GEM、`device/net/eth_rp1.c`)は割込みを使わず、読み手が受信のリングを見る。受信の記述子は128個で、1つが16バイトなので、データキャッシュの1ライン(64バイト)に4つが入る。1つの記述子をキャッシュから書き戻すと、同じラインのほかの3つもキャッシュにあった古い値で書き戻される。その間にコントローラが埋めた記述子は空きに戻ってフレームが失われ、ドライバはコントローラが追い越した記述子を待ち続けることになる。そこで、受信の記述子は同じラインの4つを読み終えてからまとめてコントローラに返し、コントローラが書く可能性のあるラインには書き込まない。リングが満ちて受信できなかったフレーム(`RSR`のBNA)は捨てられ、コントローラは記述子が返されると受信を続ける。返した後も200ミリ秒フレームが入らないときだけ、受信を止め、1ミリ秒置いてからリング全体を先頭から返し直して再開する(`eth: receiving started again`)。

rumpカーネルの中では、カードは`neta0`、ループバックは`lo0`(127.0.0.1)というインタフェースになる。`neta0`が送るフレームは、リングに入れて専用のタスクがデバイスに書き込む。デバイスはフレームを受け取るまで書いたタスクを待たせるので、rumpカーネルのスレッドが自分で書くと、フレームごとにスタック全体が止まるからである。受信は`neta0`のスレッドがデバイスを読んで待ち、フレームが届くと、そのときまでに届いていたものと合わせて最大16個をまとめてスタックに渡す。リンクの状態は「不明」とし、スタックはこれを接続されているものとして扱う。

### 9.1.4 性能

QEMU(Windows版、4コア)での測定値を示す。`ktest_so`と`ktest_svcio`(`NET=user`)が16MBを送って測る。

| 項目 | NetBSD | lwIP |
| --- | --- | --- |
| ループバックのTCP | 48〜66MB/秒 | 31〜33MB/秒 |
| ホストからのTCP | 10〜16MB/秒 | 13.5〜14MB/秒 |
| ホストへのTCP | 3〜5MB/秒 | 10〜11MB/秒 |
| 何もしない呼出し(`so_fcntl`)1回 | 1.5〜6マイクロ秒 | 0.05マイクロ秒 |

ホストへの送信が遅いのは、QEMUのユーザモードネットワークが受け取ったセグメントごとにACKを返し、ACKのたびに受信、プロトコル処理、送信のタスクが順に動くためである。1回の呼出しは、rumpカーネルのスレッドとして仮想プロセッサを取り、NetBSDのシステムコールとしてディスクリプタを引くので、関数を直接呼ぶlwIPより時間がかかる。

## 9.2 ソケット

T2EXのBSDソケット互換の関数`so_`を提供する。カーネル内からは下表のすべてを関数として呼べる。プロセスからはSVCクラス5で、「ソケット」の行のすべて、`so_send`、`so_recv`、`so_sendto`、`so_recvfrom`、`so_recvtos`、`so_poll`、`so_getsockopt`、`so_setsockopt`、`so_fcntl`、`so_resolve`、`so_resolveall`、「インタフェース」の行の`so_getifaddr`、`so_getdns`、`so_setifaddr`、`so_dhcp_start`、`so_getobj`を呼べる。名前と引数はどちらも同じである。

| 分類 | 関数 |
| --- | --- |
| ソケット | `so_socket`、`so_close`、`so_bind`、`so_connect`、`so_listen`、`so_accept`、`so_shutdown`、`so_getsockname`、`so_getpeername` |
| 送受信 | `so_send`、`so_recv`、`so_sendto`、`so_recvfrom`、`so_recvtos`、`so_read`、`so_write`、`so_sendmsg`、`so_recvmsg` |
| 待ち合わせ | `so_select`(カーネル)、`so_poll`(プロセス) |
| オプション | `so_getsockopt`、`so_setsockopt`、`so_ioctl`、`so_fcntl` |
| 名前解決 | `so_getaddrinfo`、`so_resolve`、`so_resolveall`、`so_getnameinfo`、`so_gethostname`、`so_sethostname` |
| インタフェース | `so_getifaddr`、`so_getdns`、`so_setifaddr`、`so_dhcp_start`、`so_getifaddr6`、`so_getdns6`、`so_setip6`、`so_getip6`、`so_setdns6` |
| 実身 | `so_getobj` |

IPv6のアドレスの状態を読む関数(`so_getifaddr6`、`so_getdns6`、`so_getip6`)と、IPv6の設定を変える関数(`so_setip6`、`so_setdns6`)はSVCにしていない。プロセスはIPv6の状態をシステムの実身のレコード7で読み(9.3.4、8.4)、設定はネットワーク設定の実身を書き換えて変える(9.3)。デバイスやソケットと同じく、資源の状態は実身のレコードとして見せ、APIを増やさない方針による。

ソケットは作成したプロセスが所有し、プロセスが終了すると閉じられる。他のプロセスのソケット番号は使えない。インタフェースのアドレスを変更する関数と`so_dhcp_start`は管理者だけが呼べる。

構造体と定数は`include/ts/sodef.h`(プロセスには`include/ts/soapp.h`)にある。アドレスの構造体はファミリの前に長さのバイトを持つ。値はlwIPのときと同じで、`so_`の層がNetBSDの値との間で変換する。ソケット番号はシステム全体で0から63(`SO_MAX`)で、1つの番号はrumpカーネルの1つのディスクリプタに対応する。すべてのソケットは、rumpカーネルの1つのプロセスのディスクリプタである。

ソケットはIPv4(`AF_INET`、`struct sockaddr_in`)でもIPv6(`AF_INET6`、`struct sockaddr_in6`)でも作れ、`so_bind`、`so_connect`、`so_accept`、`so_getsockname`、`so_getpeername`、`so_sendto`、`so_recvfrom`はどちらのアドレスも受け渡す。リンクローカルアドレスは、`sin6_scope_id`にインタフェースの番号(`so_ifnametoindex`)を入れて指す。`IPV6_V6ONLY`の既定はNetBSDと同じく1で、IPv6のソケットはIPv6だけを扱う。0にしてから`::`にバインドしたソケットはIPv4の接続も受け、相手のアドレスは`::ffff:a.b.c.d`になる。`IPV6_V6ONLY`はバインドする前にだけ変えられる。ほかに`IPV6_UNICAST_HOPS`、`IPV6_MULTICAST_IF`、`IPV6_MULTICAST_HOPS`、`IPV6_MULTICAST_LOOP`、`IPV6_JOIN_GROUP`、`IPV6_LEAVE_GROUP`を扱う。

送るデータグラムのTOS(IPv4、`IP_TOS`)とトラフィッククラス(IPv6、`IPV6_TCLASS`)は設定でき、読み出せる。下位の2ビットはECNのビットである。受け取ったデータグラムのTOSとトラフィッククラスは、ソケットが`IP_RECVTOS`か`IPV6_RECVTCLASS`を1にしておくと、`so_recvtos`(`so_recvfrom`と同じ引数に、値を受け取る`INT *p_tos`を加えたもの)が返す。求めていないソケットと、値が来なかったデータグラムでは-1になる。IPv6の値はNetBSDの付随データ(`IPV6_TCLASS`)がそのまま運ぶ。IPv4には、NetBSDに受け取ったTOSを渡すオプションがない。そこで`IP_RECVTOS`はNetBSDの`IP_RECVTTL`として設定し、TessronOSの部品(`tsnet_conf.c`)が、受信の付随データを作るNetBSDの関数`ip_savecontrol`の後で、TTLの横にTOSの1バイトを足す。NetBSDのソースは変えず、リンクのときにその関数の呼出しを部品の関数に向ける(`ld --wrap`、12.7)。TTLの付随データは渡さない。lwIPのときは、`so_recvtos`はいつも-1を返す。

プロセスのPOSIXのソケット(`lib/libcxxrt/ts_socket.c`)も、Linuxの形の`AF_INET6`のソケットとアドレスを`so_`の形に変えて扱う。`IPV6_V6ONLY`、`SO_LINGER`、`IP_TOS`、`IPV6_TCLASS`、`IP_RECVTOS`、`IPV6_RECVTCLASS`を渡す。`recvmsg`は、付随データの場所があれば`so_recvtos`で受け取り、TOSを`IP_TOS`の1バイトの、トラフィッククラスを`IPV6_TCLASS`の`int`の付随データとして返す。`inet_pton`、`inet_ntop`、`getaddrinfo`、`getnameinfo`はIPv6のアドレスも扱う(9.3.2)。`poll`は1回に64まで(システムのソケットの数と同じ)のソケットを待てる。

エラーは、NetBSDのerrnoの値を次の表のエラーコードにして返す。表にないものは`E_SYS`である。`SO_ERROR`で読むerrnoの値も`sodef.h`の値にする。

| errno | エラーコード |
| --- | --- |
| `EINVAL`、`EFAULT` | `E_PAR` |
| `EBADF`、`ENOTSOCK` | `E_ID` |
| `EACCES` | `E_OACV` |
| `ENOMEM`、`ENOBUFS` | `E_NOMEM` |
| `EMFILE` | `E_LIMIT` |
| `EAGAIN`、`ETIMEDOUT` | `E_TMOUT`(ブロックしないソケットで待つことになった場合と、`SO_RCVTIMEO`などの時間切れ) |
| `EINPROGRESS`、`EALREADY`、`EADDRINUSE` | `E_BUSY` |
| `EISCONN`、`ENOTCONN` | `E_OBJ` |
| `ECONNRESET`、`ECONNABORTED`、`ECONNREFUSED`、`EHOSTUNREACH`、`ENETUNREACH`、`ENETDOWN`、`EHOSTDOWN`、`EPIPE` | `E_IO` |
| `EOPNOTSUPP`、`EAFNOSUPPORT`、`EPROTONOSUPPORT` | `E_NOSPT` |

NetBSDのソケットの動作のうち、以前と異なるものは`so_`の層で次のように合わせている。

- 接続が切れたソケットに書いてもシグナルは生じず、`E_IO`になる。
- `so_listen`のbacklogは指定にかかわらず最大値にする。受け付け待ちの接続の数は、以前から制限していない。
- データグラムのソケットの`SO_REUSEADDR`は、両方が指定していれば同じポートを共有できる。NetBSDではそのために`SO_REUSEPORT`も設定する。
- `FIONREAD`はデータのバイト数だけを返す。データグラムの送信元のアドレスは数えない。
- `so_fcntl`の`F_GETFL`は`O_NONBLOCK`と`O_RDWR`を返し、`F_SETFL`は`O_NONBLOCK`だけを受け付ける。
- `so_recvmsg`と`so_sendmsg`は補助データを扱わない。
- 64のソケット番号がすべて使われているときの`so_socket`と`so_accept`は、`E_LIMIT`を返す(lwIPでは`E_SYS`だった)。
- NetBSDでは受け付けたソケットが待ち受けのソケットの`O_NONBLOCK`を引き継ぐ。プロセスの`so_accept`は受け付ける間だけ待ち受けのソケットを`O_NONBLOCK`にするので、受け付けたソケットのフラグを待ち受けのソケットの元のフラグに戻す。

下位のスタックが持たない機能、たとえば帯域外データ(`so_sockatmark`)は、無期限に待つことがないよう`E_NOSPT`を返す。`so_resctl`と`so_break`も`E_NOSPT`である。

### 9.2.1 ソケットの実身

ソケットは通信の実身(`OB_T_CHANNEL`、サブタイプ`OB_S_SOCKET`)でもある(8.5)。`so_socket`と`so_accept`がソケット番号を割り当てたところで実身を作り、`so_close`が番号を返す前に消す。プロセスの終了による後始末(`knl_so_prc_end`)も`so_close`を通るので、同じように消える。スタックが実身の層を呼ぶのはこの2か所だけで、送受信やオプションの呼出しはこれまでどおり番号でソケットを指し、実身を探さない。番号のAPI(`so_`)もPOSIXのAPI(`lib/libcxxrt/ts_socket.c`)も変わらない。どちらのスタックでも同じ作りで、実身を扱うのはスタックの外の`obsock.c`である。

プロセスは`so_getobj`で自分のソケットの実身のUUIDを得て、`ob_opn_obj`で開ける。他のプロセスのソケット番号には`E_ID`を返す。実身は`ob_lst_obj(OB_T_CHANNEL, OB_S_SOCKET, ...)`でも列挙でき、プロセスの実身のレコード0からも仮身で辿れる。

| 項目 | 内容 |
| --- | --- |
| 名前 | `socket 3 (process 12)`。カーネルのソケットは`socket 3 (kernel)` |
| 保護 | 所有者は作ったプロセスが代理するユーザ、グループはその最初のグループ、モードは`rw-------`。変更はできない。カーネルのソケットの所有者はシステムである |
| レコード0 | 説明のxmlTAD。プロトコル、種類、両端のアドレスとポート、状態と、所有するプロセスの実身への仮身 |
| レコード1 | データ。読むと受信し、書くと送信する。大きさは受信して読んでいないバイト数 |
| メタデータ | `socket`の下に`number`、`process`(カーネルは0)、`family`(`inet`、`inet6`)、`type`(`stream`、`datagram`、`raw`)、`protocol`(`tcp`、`udp`など)、`local`と`remote`(`address`と`port`、ないときは`null`)、`state`(`listening`、`connected`、`bound`、`open`)、`waiting` |
| 削除 | `ob_del_obj`はソケットを閉じる |
| イベント | 閉じると`OB_E_DELETE`を1回通知する |

データをどのレコードに置くかは、通信の実身であるメッセージキューに合わせて決めた。キューではレコード0の書込みが送信、読出しが受信で、キーを`OB_O_NOWAIT`で開いていなければ、空のときと満杯のときに待つ。ソケットの実身はデバイスの実身と同じくレコード0を説明に使うので、データをレコード1に置き、送受信と待ち方をキューと同じにした。プロセスの呼出しは200ミリ秒ごとに区切って待ち、その間にプロセスが終了させられれば`E_DISWAI`で戻る(`so_recv`、`so_send`と同じ)。`OB_O_NOWAIT`のキーでは待たずに`E_TMOUT`を返す。ソケットに設定した`SO_RCVTIMEO`、`SO_SNDTIMEO`、`O_NONBLOCK`はそのまま効く。オフセットは0だけを受け付け、レコード0への書込みは`E_RONLY`である。

実身を作るにはUUIDが要る。実身の層が動き出す前(起動中の`so_main`)に作られたソケットは、実身の層が動き出したときに実身を与える。時計が設定される前に作られたソケットの実身は、version 4のUUIDで識別する(7.3)。

## 9.3 設定

ネットワーク設定は、ネットワーク設定の実身のレコード1にある次の形式の行である。キーと値の間はタブで区切る。

```text
$$HOST <ホスト名> cnet <サブネットマスク> <IPアドレス> NETDRV DEVICE=neta
$$DNS <名前> cnet <サブネットマスク> <IPアドレス> DOMAIN=<ドメイン>
$$DNS <名前> cnet <サブネットマスク> <IPアドレス>
$$GW gateway cnet <サブネットマスク> <IPアドレス>
$$NTP <NTPサーバ>
$$IPV6 <on|off> <auto|fixed|none> [temp]
$$IPV6ADDR <IPv6アドレス>/<プレフィックス長>
$$IPV6GW <IPv6アドレス>
$$IPV6DNS <IPv6アドレス>
$$IPV6DNS <IPv6アドレス>
```

自ホストのIPアドレスが0.0.0.0ならDHCPでアドレスを取得する。DNSサーバのアドレスが0.0.0.0ならDHCPで取得したものを使う。`$$GW`と`$$NTP`がキーだけの行なら、ゲートウェイを使わず、時刻合わせもしない。

`$$IPV6`はIPv6を使うかどうか(`on`、`off`)と、アドレスの決め方である。`auto`はルータ広告からアドレスを作り(9.3.3)、`temp`を付けると一時アドレスも作る。`fixed`は`$$IPV6ADDR`のアドレスとプレフィックス長をインタフェースに付け、`$$IPV6GW`をデフォルトルータにする。`none`はリンクローカルアドレスだけを使い、ほかのアドレスを付けない。`$$IPV6DNS`は2つまでのIPv6のDNSサーバで、ルータが示したものより先に尋ねる。アドレスの行がキーだけなら、そのアドレスはない。`$$IPV6`の行がない設定は`on auto`として扱う。アドレスはRFC 5952の最も短い形で書く(`lib/libconf`の`cf_ip6str`)。

デスクトップ構成では、起動時にこのレコードを読み込んで設定を反映する。以後は監視タスクがレコードの変更をイベントで受け取り、書き換えられるたびに、ホスト名とドメイン、インタフェースのアドレスとDNS、NTPサーバを順に設定し直す(`so_conf`)。ネットワーク設定の小物(第11章)はこのレコードを書き換えるだけである。

起動直後にDHCPでアドレスを取得するかどうかと、SNTPで時刻を合わせるかどうかは、`config.h`の`CNF_NET_DHCP`と`CNF_NET_SNTP`で決まる。Raspberry Pi 5の構成ではどちらも1で、起動するとアドレスを取得し、アドレスが決まったら時刻を合わせる。ルータ広告からIPv6のアドレスを作るかどうかは`CNF_NET_SLAAC`で決まり、どの構成でも1である(9.3.3)。起動後にネットワーク設定の実身を読むと、`$$IPV6`の行に従ってIPv6の設定を変える(9.3.4)。

固定のアドレスを設定すると(`so_setifaddr`)、アドレスとサブネットマスクから決まるブロードキャストアドレスとともに`neta0`に設定し、ゲートウェイをデフォルトの経路にする。

### 9.3.1 DHCP

DHCPのクライアント(`so_dhcp.c`)は専用のタスクで動き、スタックのUDPのソケットで問い合わせる。アドレスがまだないときは、インタフェースのアドレスを0.0.0.0、ブロードキャストアドレスを255.255.255.255にしておく。こうするとスタックは68番のポートからブロードキャストを送り、応答を受け取れる。サーバには応答をブロードキャストで返すよう求める。

DISCOVER、OFFER、REQUEST、ACKの順に進み、アドレス、サブネットマスク、ルータ、2つまでのDNSサーバを設定する。リース期間の半分で同じサーバに更新を求め、8分の7を過ぎたらどのサーバにでも求める。リースが切れるとアドレスを外して最初からやり直し、NAKを受け取ったときもやり直す。`so_dhcp_start`は最初から問い合わせ直すが、インタフェースにアドレスがあれば、新しいリースを得るまでそのアドレスを使い続ける。固定のアドレスを設定すると問い合わせをやめる。応答がなくてもエラーにはせず、間隔を4秒から64秒まで延ばしながら問い合わせを続ける。

REQUESTに答えが無いときは、同じトランザクションIDのREQUESTを4秒、8秒、16秒の後に送り直す。待ちはそれぞれ1秒の範囲で乱数で長くも短くもする(RFC 2131の4.1)。4回目にも答えが無ければ、DISCOVERからやり直す。LinuxのsystemdのDHCPのクライアント(`sd-dhcp-client.c`)も、REQUESTを4秒から倍々で最大5回送り直してから最初に戻る。前は、REQUESTの答えを4秒待つと、新しいトランザクションIDでDISCOVERからやり直していた。そのため、OFFERの直後に来たREQUESTに答えないサーバや中継(提供したアドレスをまだ確かめている、1つの局のDHCPのメッセージを一定の時間に1つしか通さない、など)のネットワークでは、どのREQUESTもOFFERの0.1〜0.2秒後に届き、ACKがいつまでも来なかった(ThinkPad X1 Yogaとメッシュのルータの組み合わせで、ACKまで42秒かかった。原因がこれかどうかは次の実機で確かめる)。

`so_dhcp_start`で問い合わせ直すとき、インタフェースにこの起動の中で得たリースのアドレスがあり(同じカードで、期限が切れていない)、まずそのアドレスをREQUESTで求める(INIT-REBOOT、RFC 2131の3.2と4.3.2)。Wi-Fiでつなぎ直したときや、同じネットワークに戻ったときは、DISCOVERとOFFERを経ずに1往復でアドレスが確かめられる。WindowsとLinux(NetworkManager、systemd-networkd)も、前のリースがあればINIT-REBOOTから始める。NAKが来たらアドレスを外し、4秒ほど答えが無ければ、アドレスを持ったままDISCOVERから問い合わせる。リースは記憶の中にだけ持ち、再起動をまたいでは持たない(WindowsとLinuxはリースをファイルに残し、起動の直後にもINIT-REBOOTを使う)。

どのメッセージにも、問い合わせを始めてからの秒数(`secs`、RFC 2131の2章)を入れる。前は常に0だった。

トランザクションIDは1回りの問い合わせに1つで、DISCOVERを送り直すときも同じIDのまま`secs`だけを増やす(systemd-networkdの`sd-dhcp-client.c`はIDを始めのときだけ選び、ISCのdhclientも同じ)。新しいIDにするのは、NAK、4回のREQUESTに答えが無いとき、DECLINE、リースを失ったとき、INIT-REBOOTが通らなかったときで、そのとき`secs`も0から数え直す。前はDISCOVERのたびにIDを変えていた。NAKにサーバの言い分(option 56)があれば、`net: DHCP: the offer of ... was refused (NAK) after N REQUESTs (the server says "...")`の行に出す。

問い合わせを始めるとき、インタフェースにあるアドレスが、この起動の中でほかのカードで得たリースのものなら、外してから0.0.0.0で問い合わせる(`net: DHCP: the address ... was leased to another card: taken away`)。Linuxではアドレスはそれを付けたインタフェースに残り、新しいカードのインタフェースは何も持たずに始まる。前は、有線で得たアドレスを持ったままWi-FiでDISCOVERを送り、送り元のアドレスがRFC 2131の4.1(アドレスを得る前の同報は送り元を0にする)と違っていた。

DHCPの進み方はコンソールに出す。REQUESTを送り直すたびに`net: DHCP: no answer in about N s to the REQUEST for address ... (xid ...); sent again, K of 4`、ACKが来たら`net: DHCP: acknowledged N ms after the first DISCOVER, the REQUEST sent K times`、INIT-REBOOTでは`net: DHCP: the lease held asked for first (INIT-REBOOT)`とその結果の行を出す。

アドレスが決まった後、NetBSDのスタックはRFC 5227のとおりにそのアドレスがほかの機械に使われていないかをARPで確かめ、終わるまでそのアドレスから送らない。RFC 5227の時間(最初の待ちPROBE_WAITが0〜1秒、3回の探査をPROBE_MIN〜PROBE_MAXの1〜2秒おき、最後の探査の後にANNOUNCE_WAITの2秒)のままでは、ACKから最初のデータまで4〜8秒かかっていた(ThinkPad X1 Yogaの実機で、ACKの8秒後にようやくゲートウェイを引き、APのADDBAと最初の局宛てのデータが来た)。LinuxのNetworkManagerは、この確かめをn-acdで行い、既定の`ipv4.dad-timeout`の200ミリ秒に収める。手順はRFCと同じ3回の探査のまま、RFCの各時間を「200ミリ秒/7000ミリ秒」倍に縮め(PROBE_WAITとPROBE_MINが28.6ミリ秒、PROBE_MAXとANNOUNCE_WAITが57.1ミリ秒、全体で114〜200ミリ秒)、確かめの後の告知(2回、2秒おき)と守り(DEFEND_INTERVALの10秒)はRFCの時間のままにする(`n_acd_probe_config_set_timeout`、`n-acd-probe.c`)。TessronOSも同じ形にする。NetBSDの`if_arp.c`に`tools/netbsd/patches/if_arp-dad-timeout.patch`を当て(`tools/netbsd/build.sh`と`tools/x64/netbsd/build.sh`が写しに当てて翻訳する)、探査の待ちを`ip_dad_timeout_ms`(200)で縮める。探査の回数(`ip_dad_count`の3)、告知、守りは変えない。rumpカーネルの時計は10ミリ秒刻みなので、待ちは切り上げて0〜30ミリ秒、30〜60ミリ秒おきに3回、最後に60ミリ秒で、全体は約90〜210ミリ秒である。

DHCPのクライアントは、ACKで新しいアドレスを設定した後、その確かめの結果を20ミリ秒ごとに見る(`rump_tsnet_addrstate4`、`SIOCGIFAFLAG_IN`の`IN_IFF_TENTATIVE`と`IN_IFF_DUPLICATED`。3秒まで)。ほかの機械が探査に答えて重複が見つかったら、アドレスを外し、0.0.0.0からDHCPDECLINE(求めたアドレスとサーバの識別子とクライアントの識別子だけ、RFC 2131の表5)を全員宛てに送り、10秒待ってからDISCOVERでやり直す(RFC 2131の3.1の5)。NetworkManagerも、DHCPのアドレスの重複でDECLINEを送ってやり直す。結果は`net: DHCP: the address ... checked against the other machines in N ms: not in use`(重複のときは`another machine's`と`DECLINE sent`)の行に出る。前は重複を見ていなかったので、重複したアドレスは使えないまま残っていた。

### 9.3.2 名前解決

名前解決(`so_dns.c`)は、名前のIPv4アドレス(Aレコード)、IPv6アドレス(AAAAレコード)、またはその両方をDNSサーバに尋ねる。両方を尋ねるときは2つの問い合わせを同じサーバに続けて送り、2つの応答をまとめて待つ。一方の応答が来たら、もう一方は0.5秒だけ待つ。AAAAに答えないサーバのために名前解決のたびに待たされないよう、どちらかの種類のアドレスが得られたら、それ以上は尋ねない。CNAMEで別名が返っても、同じ応答に含まれるアドレスを使う。問い合わせるサーバは、IPv4のサーバとして設定で指定したもの、なければDHCPで得たもの(固定のアドレスなら`so_setifaddr`で指定したもの)、その後にルータ広告が示したIPv6のサーバ(9.3.3)で、それぞれのアドレスのファミリのUDPで尋ねる。サーバごとに、1秒、2秒、4秒、8秒と待ち時間を延ばしながら4回まで尋ねる。

答えは名前と種類(AとAAAA)ごとに、そのレコードが示す有効期間(最長5分)の間、64件まで保持する。存在しない名前と、その種類のアドレスを持たない名前は30秒保持する。ページが同じホストの名前を何度も解決しても、問い合わせは1回で済む。`localhost`は常に127.0.0.1と::1である。ドットを含まない名前が見つからなければ、設定のドメインを付けてもう一度尋ねる。

`so_resolveall`は名前のアドレスを、ファミリ(`AF_INET`、`AF_INET6`、両方なら`AF_UNSPEC`)を指定して最大16個返す(アドレスの構造体`T_SOADDR`はファミリ、リンクローカルアドレスのインタフェースの番号、16バイトのアドレス)。数字のアドレス(`2001:db8::1`、`fe80::1%neta0`、`10.0.2.2`)はそれ自体を返す。返す順は試すべき順で、RFC 6724の宛先アドレスの選択を簡略にしたものである。このホストが送信元に使えるアドレスを持たない宛先を後ろに回し、送信元と宛先のスコープが同じもの、方針表のラベルが同じものを先にし、残りを方針表の優先度の高い順にする。このため、IPv6のアドレスがリンクローカルかサイトローカル(QEMUのユーザモードネットワークが配るfec0::/64)だけのホストでは、IPv4のアドレスを先に試す。`SO_RA_ADDRCONFIG`を指定すると、外へ届くアドレス(IPv4のアドレス、またはリンクローカルでもサイトローカルでもないIPv6のアドレス)を持たないファミリは尋ねない。どちらのファミリのアドレスもまだないときは、この指定を無視する。ループバックのアドレスは外さない。

`so_getaddrinfo`は`so_resolveall`の答えを`struct addrinfo`の連結リストにして返す。`hints`の`AI_ADDRCONFIG`は`SO_RA_ADDRCONFIG`になり、`AI_NUMERICHOST`は数字のアドレスだけを受け付ける。名前を指定しないときは、ループバック(`AI_PASSIVE`なら任意)のIPv4とIPv6のアドレスを、IPv4を先にして返す。サービスは数字で指定する。`so_resolve`は従来どおり最初のIPv4アドレスを1つ返す。`so_getnameinfo`は数字だけを返し、IPv6のアドレスは最も短い形(RFC 5952)にし、リンクローカルアドレスには`%`とインタフェースの名前を付ける。

プロセスの`getaddrinfo`(`lib/libcxxrt/ts_socket.c`)は、数字のアドレスを自分で読み、名前はSVCの`so_resolveall`で尋ねて、その順のまま`struct addrinfo`のリストにする。`AI_ADDRCONFIG`、`AI_NUMERICHOST`、`AI_PASSIVE`、`AI_CANONNAME`を扱う。名前を指定しないときの答えはカーネルの`so_getaddrinfo`と同じである。`gethostbyname`は従来どおり最初のIPv4アドレスを返す。

### 9.3.3 IPv6のアドレスの自動設定

NetBSDのカーネルは、インタフェースを上げるとMACアドレスから作ったリンクローカルアドレスを付けるが、ルータ広告の処理はカーネルの外のプログラムに任せている。TessronOSでは`so_slaac.c`のタスクがこれを行う(RFC 4861、RFC 4862、RFC 8106、RFC 8981)。

タスクはリンクローカルアドレスの重複の確認が済むのを待ち、そのインタフェース識別子(アドレスの下位64ビット)を取る。次に、ICMPv6のルータ広告だけを受けるrawソケットを開き、全ルータのマルチキャストアドレス(ff02::2)にルータ要請を4秒おきに3回送る。以後は、設定がルータ広告を使わなくなるか(9.3.4)スタックが止まるまで広告を待ち、ケーブルが抜けて挿し直されたときにも要請をやり直す。アダプタの管理(`netadp.c`)が、使っているカードのリンクが上がり直した(Wi-Fiがネットワークにつながった、ケーブルが戻った)ときと、使うカードが替わったときに、DHCPの問い合わせ直し(9.6)と同じ所で`knl_so_slaac_relink`を呼ぶ。タスクは次の見回り(1秒以内)で、要請を4秒おきに3回送り直す。リンクの状態の見回りだけでは、Wi-Fiが切れてすぐ別のネットワークにつながったときを見逃し、新しいネットワークの接頭辞は次のルータ広告(数分ごと)まで待つことになっていた。LinuxもリンクがUPになるとルータ要請をやり直す。要請はDHCPの設定に関わらず送り、作ったアドレスはそのまま残す。

広告は、送信元がリンクローカルアドレスで、ホップ制限が255のもの(リンクの外からは送れない)だけを受け付ける。ホップ制限は受信の付随データ(`IPV6_RECVHOPLIMIT`)で知る。

- プレフィックス情報のうち、自動設定のフラグが立った64ビットのプレフィックスから、プレフィックスとインタフェース識別子を合わせたアドレスを作り、有効期間と推奨期間を付けて`neta0`に設定する(`rump_tsnet_setaddr6`)。オンリンクのフラグが立っていればプレフィックス長は64で、プレフィックスの経路も付く。新しいアドレスはカーネルが重複を確かめ、その間は送信元に使わない。推奨期間を過ぎたアドレスはカーネルが新しい接続の送信元に選ばなくなり、有効期間を過ぎたアドレスはカーネルが外す。
- 同じプレフィックスがまた広告されると有効期間を更新するが、残りが2時間を超えるアドレスを2時間より短くはしない(RFC 4862 5.5.3)。偽の広告でアドレスを消されないためである。
- ルータの寿命が0でなければ、送信元をデフォルトルータとして寿命の間覚え、覚えている最初のルータを経由するIPv6のデフォルトの経路を設定する(`rump_tsnet_defroute6`)。寿命が切れるか0の広告が来れば、次のルータに替えるか経路を外す。ルータは3つまで覚える。
- RDNSSのオプションが示すDNSサーバを、その寿命の間3つまで覚え、名前解決に使う(9.3.2)。

設定で一時アドレス(プライバシー拡張、RFC 8981)を使うときは、プレフィックスごとに、インタフェース識別子を乱数にしたアドレスも作る。一時アドレスの有効期間は2日、推奨期間は1日から乱数の値(最大でその10分の4)を引いたもので、どちらもプレフィックスの期間より長くはしない。推奨期間が切れる5秒前に次の一時アドレスを作り、古い一時アドレスは有効期間が切れるまで残すので、その上の接続は続けられる。乱数で作る識別子は、すべて0のものと、RFC 5453で予約された範囲を避ける。重複の確認で他のホストが使っていると分かったときは作り直し、3回まで試す。一時アドレスにはカーネルの`IN6_IFF_TEMPORARY`のフラグを立て、カーネルの送信元アドレスの選択(RFC 6724の規則7)が同じプレフィックスの安定したアドレスより一時アドレスを先に選ぶようにする(`ip6_prefer_tempaddr`)。安定したアドレスはそのまま残り、外からの接続を受けられる。コンソールには`net: IPv6 temporary address fec0::8c1d:2f0a:61e4:93b7 (86400 s)`のように表示する。DHCPv6は扱わない。

アドレスの表とルータ、DNSサーバはタスクだけが書き換える。タスクを止める`knl_so_slaac_stop`は、タスクがルータ広告の待ちから抜けるのを待ってから戻るので、止めた側がそのあとでアドレスを外せる。設定がルータ広告を使わなくなったときは、作ったアドレス(一時アドレスを含む)をインタフェースから外し、デフォルトの経路を消し、ルータが示したDNSサーバを忘れる。

作ったアドレスとデフォルトルータは`so_getifaddr6`で、DNSサーバは`so_getdns6`で読める(`T_SOIF6`にはアドレス、プレフィックス長、状態のフラグ`SO_IF6_`、有効期間と推奨期間の残りが入る)。起動時にはコンソールに`net: IPv6 address fec0::5054:ff:fe12:3456 (86400 s)`、`net: IPv6 default router fe80::2`のように表示する。

### 9.3.4 IPv6の設定と状態

ネットワーク設定の実身の`$$IPV6`の行(9.3)は、設定を読み込む`so_conf`が`so_setip6`と`so_setdns6`を呼んで`neta0`に反映する。設定が前と同じなら何もしないので、IPv4の設定や時刻サーバだけを変えたときに、IPv6のアドレスやその上の接続は影響を受けない。変わったときは、まず前の設定が付けたものを外し、それから新しい設定を付ける。

| 設定 | `so_setip6` | `neta0`のIPv6 |
| --- | --- | --- |
| `on auto` | `SO_IP6_AUTO` | リンクローカルアドレスと、ルータ広告から作るアドレス。デフォルトルータとDNSサーバもルータ広告から得る(9.3.3) |
| `on auto temp` | `SO_IP6_AUTO`と`SO_IP6_TEMP` | 上に加えて一時アドレス。新しい接続の送信元には一時アドレスを選ぶ |
| `on fixed` | `SO_IP6_FIXED` | リンクローカルアドレスと固定のアドレス(期間は無期限)。`$$IPV6GW`があればそれを経由するデフォルトの経路。ルータ広告は聞かない |
| `on none` | `SO_IP6_LINK` | リンクローカルアドレスだけ。デフォルトの経路はない |
| `off` | `SO_IP6_OFF` | IPv6を使わない。NetBSDのインタフェースの`ND6_IFF_IFDISABLED`を立て、カーネルは`neta0`でIPv6を送りも受けもしない。リンクローカルアドレスは確認中のフラグのまま残り、使われない。ループバックの::1は使える |

`off`から戻すと、カーネルはリンクローカルアドレスの重複をもう一度確かめる。`auto`に戻すと、ルータ要請からやり直し、以前と同じインタフェース識別子から同じ安定したアドレスを作る。固定のアドレスには、未指定、ループバック、リンクローカル、マルチキャストのアドレスは使えない(`E_PAR`)。`$$IPV6DNS`のサーバは`off`のとき以外、ルータが示したサーバより先に尋ねる(9.3.2)。

今のIPv6の状態は、システムの実身のレコード7(8.4)にIPv4の状態と並べて次の行で出す。ネットワーク設定の小物の〈ＩＰｖ６〉〈状態〉はこれを読んで表示する。

```text
IPV6 <off|none|fixed|auto|auto temp>
ADDRESS6 <アドレス>/<プレフィックス長> <link|auto|temp|fixed> <有効期間の残り> <推奨期間の残り> [tentative] [duplicated] [deprecated]
GATEWAY6 <デフォルトルータ>
DNS6 <DNSサーバ>
```

`ADDRESS6`はインタフェースのアドレスごとの行で、種類はリンクローカルアドレス、ルータ広告から作ったアドレス、一時アドレス、固定のアドレスである。期間の残りは秒で、期限がなければ`infinite`である。そのあとに、重複の確認中、他のホストが使っている、推奨期間を過ぎた、のフラグが付く。`DNS6`は尋ねる順に並ぶ。

lwIPのスタック(`NETSTACK=lwip`)はIPv6を持たないので、`so_setip6`は`SO_IP6_OFF`以外に`E_NOSPT`を返し、`so_getip6`は常に`SO_IP6_OFF`である。

## 9.4 時刻合わせ

SNTPクライアントは、インタフェースにIPアドレスが設定されるとNTPサーバに問い合わせ、システム時刻を合わせる。NTPサーバは設定の`$$NTP`の行で指定する。電池のないRaspberry Pi 5は起動のたびに1985年から計時を始めるので、ネットワークに接続していれば、ここで正しい時刻になる。

## 9.5 カレンダ

T2EXのカレンダ関数`dt_`を提供する。`dt_strftime`以外はプロセスからもSVCクラス3で呼べる。

| 関数 | 機能 |
| --- | --- |
| `dt_gettime`、`dt_settime` | システム時刻を秒単位で取得する、設定する |
| `dt_gmtime`、`dt_localtime` | 秒を年月日時分秒に変換する |
| `dt_mktime` | 年月日時分秒を秒に変換する |
| `dt_strftime` | 日時を文字列に整形する |
| `dt_getsystz`、`dt_setsystz` | システムのタイムゾーンの標準時の差を取得する、差だけで設定する |
| `dt_getsyszone`、`dt_setsyszone` | タイムゾーンのIANAの名前を取得する、名前と標準時の差で設定する |
| `dt_getrtc`、`dt_setrtc` | PCのRTCをローカル時刻とUTCのどちらとして扱うかを取得する、設定する(x64だけ、9.5.1) |

時刻を設定できるのは時計の実身への書込み権限を持つユーザで、デフォルトでは管理者だけである。タイムゾーンは実身「暦」のメタデータに、UTCからの東向きの標準時の差を分単位で`tessronos.calendar.tz`に、IANAのタイムゾーンの名前(`Asia/Tokyo`など、48バイト未満の英数字と`/_+-`)を`tessronos.calendar.zone`に格納する。デフォルトは540分と`Asia/Tokyo`で、再起動しても保持される。名前のない古い暦は、差が540分なら`Asia/Tokyo`とみなす。`dt_setsystz`で差だけを変えると名前は空になる(同じ差を設定したときは名前を残す)。

`dt_localtime`と`dt_mktime_local`は、名前が次の地域のものなら夏時間に従い、夏時間の間は差に60分を足し、`tm_isdst`を1にする。カーネルはタイムゾーンのデータベースを持たず、規則を表で持つ。

| 規則 | 名前 | 夏時間の期間 |
| --- | --- | --- |
| 米国とカナダ | `America/Anchorage`、`Los_Angeles`、`Denver`、`Chicago`、`New_York`、`Halifax` | 3月の第2日曜2時から11月の第1日曜2時(現地) |
| 欧州連合 | `Atlantic/Azores`、`Europe/London`、`Paris`、`Berlin`、`Athens` | 3月の最終日曜から10月の最終日曜、1時(UTC) |
| 豪州の南東部 | `Australia/Adelaide`、`Sydney`、`Melbourne` | 10月の第1日曜2時から4月の第1日曜3時(現地) |
| ニュージーランド | `Pacific/Auckland` | 9月の最終日曜2時から4月の第1日曜3時(現地) |

夏時間の終わりに2度来る1時間の現地時刻を`dt_mktime_local`でUTCにすると、夏時間の方になる。タイムゾーンのデータベースを持つプログラム(ブラウザのICU、14.4)は名前を使い、その地域の過去の規則も含めて扱う。名前は、ユーザ環境設定の〈個人属性〉で地域を選ぶと設定される(11.3)。カーネルの試験`time`の群の`test_zone_name`が、名前の保存と読み戻し、差だけの設定で名前が消えること、米国と欧州連合の夏時間の始まりと終わりの前後、豪州とニュージーランドの夏と冬、日本の通年の時刻と、その逆の変換、誤った名前の拒否を確かめる。

### 9.5.1 PCのRTC

Windowsの入ったPCのRTC(CMOSの時計、`kernel/sysdepend/x64/rtc.c`)は、Windowsの決まりでローカル時刻(日本ならJST)を持っている。x64のTessronOSは、RTCをローカル時刻として扱うかUTCとして扱うかを設定で選べ、既定はローカル時刻である(`config.h`の`CNF_RTC_LOCAL`)。WindowsやLinuxの`timedatectl set-local-rtc 1`(`/etc/adjtime`の`LOCAL`)と同じ扱いになる。Raspberry PiのRTCはこれまでどおりUTCで、この設定はない。

設定は実身「暦」のメタデータの`tessronos.calendar.rtc`(`"local"`か`"utc"`)に置き、RTCに最後に書いたときのUTCからの東向きの差(分)を`tessronos.calendar.rtcofs`に記録する。ユーザ環境設定の〈個人属性〉の「内蔵時計」で選び(11.3)、プログラムからは`dt_getrtc`、`dt_setrtc`で読み書きする(x64だけ)。設定に要る権限はタイムゾーンと同じ`TSN_RIGHT_ZONE`である。

| 場面 | 扱い |
| --- | --- |
| ファームウェアの差 | ローダがUEFIの`GetTime`を呼び、`EFI_TIME`の`TimeZone`が-1440〜1440なら`T_BOOTINFO`の`rtc_tz`で渡す。UEFIの仕様の「Localtime = UTC - TimeZone」のとおり、UTCはRTCの時刻に`TimeZone`分を足したものとし、設定より優先する。`Daylight`は使わない。多くのPCは`EFI_UNSPECIFIED_TIMEZONE`(0x07FF)を返し、そのときは設定に従う。ローダは`LOADER.TXT`に`GetTime`の答えを1行出す |
| 起動 | タイマの初期化でRTCを読む。まだ暦を読んでいないので、ビルドの既定(ローカル時刻、`CNF_TIMEZONE`の地域の規則)で解釈する。暦を読んだとき(`knl_dt_zone_load`)、それまでにだれも時刻を設定していなければ、暦の設定と`rtcofs`で読み直し、システム時刻を差の分だけ動かす。RTCには書かない |
| ローカル時刻のRTCを読む | `rtcofs`があればその差で読む。なければタイムゾーンの規則で読む |
| 書く | `tk_set_tim`などで時刻を設定したとき(NTP、ユーザ環境設定)、その時点のタイムゾーンと夏時間の差を足したローカル時刻を書く。UTCとして扱うときはUTCを書く |
| 夏時間の切替わり | カーネルのタスクが1分ごとにRTCが持つべき差を調べ、変わっていればシステム時刻から書き直し、`rtcofs`を更新する。電源を切っている間に切り替わったときも、起動して暦を読んだ後に書き直す |
| タイムゾーンの変更 | システム時刻(UTC)はそのままにし、RTCを新しいタイムゾーンのローカル時刻で書き直す |
| 設定の変更 | システム時刻はそのままにし、RTCを新しい設定で書き直す |

夏時間の終わりに2度来る1時間は、RTCの時刻だけでは夏時間のものか標準時のものか分からない。TessronOSはRTCに書いたときの差を`rtcofs`に記録し、起動時にはその差で読むので区別できる。Windowsも同じく、RTCに書いたときの差をレジストリ(`TimeZoneInformation`の`ActiveTimeBias`)に記録して読む。Linuxは差を記録せず(`hwclock`はCライブラリの`mktime`に任せる)、`timedatectl`はRTCをローカル時刻にすると夏時間の扱いを保証できないと警告する。記録がないとき(最初の起動、古い暦)は規則で読み、2度来る1時間は夏時間の方とする(`dt_mktime_local`と同じ)。電源を切ったまま夏時間が終わった直後に起動したとき、RTCはまだ夏時間の時刻を持っているので、この選び方が合う。

タイムゾーンを変えてもシステム時刻(UTC)は変えず、RTCを書き直す。Linuxの`timedatectl set-timezone`は、RTCがローカル時刻のとき新しい差でRTCをシステム時刻から合わせ直し、Windowsもタイムゾーンを変えるとシステム時刻(UTC)を保ち、表示する時刻が新しいタイムゾーンのものに変わる。設定を変えたときの扱い(システム時刻を保ってRTCを書き直す)は、`timedatectl set-local-rtc`の既定(`--adjust-system-clock`を付けないとき)と同じである。

同じPCでWindowsも使い、夏時間のある地域にいるとき、一方のOSが夏時間の切替わりでRTCを書き直したことは他方の記録に表れないので、他方の起動直後に1時間ずれることがある。NTPで合わせれば直る。日本のように夏時間のない地域では起こらない。

起動のログ(x64の実機では`KERNEL.TXT`)には、暦を読んだ後に次の行が出る。

```
rtc: read 2026-10-19 21:00:05 at the start, kept as the local time (Asia/Tokyo, 540 min east, as last written): UTC 2026-10-19 12:00:05
```

カーネルの試験`time`の群の`test_rtc_kept`(x64だけ)が、時刻の設定後のRTCの値(ローカル時刻とUTC)、設定とタイムゾーンを変えたときにシステム時刻が保たれRTCが書き直されること、走っている間と電源を切っている間の夏時間の終わり、記録の差による読み直しと規則による読み方(2度来る1時間、存在しない1時間)、暦がUTCと言う起動、ファームウェアの差を確かめる。`so`の群の`test_sntp`は、x64ではNTPで合わせた後のRTCの値が設定どおりであることも確かめる。

## 9.6 ネットワークアダプタとWi-Fi(x64のPC、Raspberry Pi 5)

x64のPCは複数のネットワークアダプタを持てる。QEMUのvirtio-net、チップセットのIntelのLAN(I219、`e1k.c`)、USBのLANアダプタ(`cdcnet.c`)、Wi-Fiである。プロトコルスタックはどの場合もデバイス`neta`のインタフェース`neta0`だけを使い、その下のカードを`device/net/netsel.c`が選ぶ(9.1.3)。Wi-Fiはx64のビルドに既定で入り、`make TARGET=_X64_ WIFI=0`で除ける(12章)。

### 9.6.1 アダプタの選択

どのアダプタを使うかは利用者が選ぶ。システム環境設定の〈機器〉〈機器情報〉〈ネットワークアダプタ〉(11.6)がアダプタの一覧とそれぞれのリンクの状態を示し、その一覧で「自動」の行かアダプタの行を選んで〈設定〉を押す。選んだものは機器の設定の`NET_ADAPTER`(`auto`、`vnet`、`e1k`、`cdcnet`、`wifi`)に書く。

アダプタの管理(`device/net/netadp.c`)は、起動時に最初にカードのアドレスが尋ねられたときに(`knl_netdev_init`)タスクを作り、実身の層ができるのを待ってから動く。機器の設定は2秒ごとに、読む間だけ開いて読む(Wi-Fiの設定と同じく、ボリュームを固定しないため。書込みの知らせを受けるには実身を開いたままにする必要があり、そうするとシステムボリュームを外せなくなる)。機器の設定を書く者は書込みの排他(`OB_O_WEXCL`、8.3)で開くので、書いている最中でも読める。読めなかったとき(完全な排他`OB_O_EXCL`の者が開いているとき、媒体の誤り)は選択を変えず、次の2秒後に読み直す(`net: the machine's settings not read now (誤り): the adapter chosen stays`の行を、誤りが変わったときに1回出す)。起動のときの最初の読込みは、読めるまで0.1秒ごとに5秒まで繰り返す。前は、書く者はほかのキーをすべて締め出し、読めなかったときを「自動」の選択として扱っていたので、システム環境設定やウインドウシステムが書いている瞬間に読むと有線のカードに移っていた。Wi-Fiの管理(`wifi.c`の`conf_text_`)も、Ｗｉ－Ｆｉの設定を読めなかったときは前の設定のままにする(前は空の設定として扱い、つないでいるネットワークを離れることがあった)。

KTESTの`iob`の`test_conf_busy`は、次を確かめる。`OB_O_WEXCL`で開いたキーで`NET_ADAPTER`を書き換えると、そのキーを開いたままのうちにアダプタの管理が新しい選択を読む。その間、読むキーは開け、ほかの書くキーは`E_BUSY`になる。300ミリ秒開いたままにする書く者がいても、次の書く者は待ってから書ける。完全な排他(`OB_O_EXCL`)の書くキーで5秒開いたままにすると、読む側は開けないが、選択は変わらない(直す前は2秒後に`auto`に変わった)。カードを見直すのは、ドライバがリンクの上下やカードの出入りを知らせたとき(`knl_netadp_link`、`include/ts/net.h`)と、設定を読み直したときである。IntelのLANはリンクの変化の割込み(`ICR`の`LSC`)で、USBのLANは抜き差しで、Wi-Fiは管理のタスクが接続や切断で状態が変わったときに知らせる。リンクの変化を知らせられないカード(PHYに割込みの無いボードのEthernetと、割込みの無いIntelのLAN)があるときだけ、LinuxのPHYの層と同じく1秒ごとにそのリンクを見る。前は0.5秒ごとにすべてのカードを見ていた。見直すときは、次の順で使うカードを決める。

1. `NET_ADAPTER`がアダプタを名指していて、そのアダプタがあれば、それを使う。
2. 「自動」のとき、リンクが上がっている有線のカード(virtio-net、IntelのLAN、USBのLANの順)。
3. 接続しているWi-Fi。
4. どちらも無ければ、今のカードのまま(ケーブルを一瞬抜いただけでスタックを動かさない)。

Wi-Fiのカードは、カードが起動して本当のMACアドレスを読めるまで(`knl_wifi_mac_known`)、選ばない。それまでWi-Fiが返すアドレスは仮のもの(02:00:00:54:57:46)である。前は、利用者がWi-Fiを選んでいると、カードの準備の前に`neta0`を仮のアドレスに替え、0.6秒ほど後に本当のアドレスに替え直していた(hw10oの実機)。Linuxでは、ドライバがカードのNVMからアドレスを読むまでインタフェースが無く、NetworkManagerも使わない。利用者の選んだWi-Fiは捨てずに覚えておき(機器の設定の`NET_ADAPTER`も変えない)、その間は「自動」と同じ選び方でカードを決め、カードが起動したら(状態の変化の知らせで)Wi-Fiに移る。待っていることは`net: the Wi-Fi chosen, its card not started yet: e1k stays in use until it has`の行に1回出す。カードの準備の間と起動に失敗したときは、システム環境設定の〈ネットワークアダプタ〉のWi-Fiの行に「準備中」か「起動の失敗」を出し、アドレスの欄は「－」にする。ネットワーク設定の状態にも「準備中」か「起動の失敗(ファームウェアを読めないか、カードが応答しません)」を出す。Wi-Fiがつながったのにスタックがほかのカードに残るときは、`net: the Wi-Fi joined a network, the stack stays on ... (chosen ..., the card's address ...)`の行に理由を出す。

カードが替わって`neta0`のMACアドレスが変わったとき(`rump_tswifi_setmac`)は、IPv6のリンクローカルアドレスを作り直すのに加えて、IPv4のARPの表を空にし(NetBSDの`in_if_down`と同じ`lltable_purge_entries`)、IPv4のアドレスを確かめ直して新しいアドレスで告知する(`in_if_link_down`と`in_if_link_up`。リンクが戻ったときと同じ手順)。Linuxも、アドレスが変わると(`NETDEV_CHANGEADDR`)近隣の表を消し、gratuitous ARPを送る。前のカードの表は別のネットワークのものかもしれず、まわりの機械は前のカードのアドレスで覚えているからである。

カードを替えるときは、先に`neta0`のリンク層のアドレスを新しいカードのものにし(rumpカーネルの`if_set_sadl`、`rump_tswifi_setmac`)、それから`netsel.c`の選択を替え、ネットワーク設定を読み直す(`so_conf`)。アクセスポイントは関連付けたアドレスからのフレームしか受け付けず、ARPと近隣探索もインタフェースのアドレスで答えるからである。設定がDHCPなら、新しいカードのアドレスで問い合わせ直す。`so_conf`はDHCPがすでに動いていれば何もしないので、続けて`so_dhcp_start`で問い合わせを初めからやり直させる(DHCPのタスクは問い合わせを始めるたびにカードのアドレスを読む)。使っているカードのリンクが上がり直したとき(ケーブルを挿し直した、Wi-Fiが切れた後につなぎ直した、別のネットワークにつないだ)も、同じく問い合わせ直す。IPv6のルータの要請も、同じ所で送り直させる(9.3.3)。Wi-Fiのつなぎ直しは、管理のタスクが接続のたびに1つ増やす数(`knl_wifi_link_gen`)で見るので、知らせを受けて見直すまでの間に切れてつながっても見逃さない。問い合わせ直す間も、持っているアドレスはそのまま使う(`so_dhcp.c`)。同じネットワークにつなぎ直してサーバが同じアドレスを返せば、コネクションは切れない。前は`so_conf`だけを呼んでいたので、DHCPが動いていると問い合わせ直さず、別のカードや別のネットワークに移っても、前のアドレスが貸出しの期限まで残っていた。また、起動のときWi-Fiがつながる前に始まったDHCPは、答えが無いので待ちを64秒まで延ばしていく。つないだ直後に問い合わせ直さないと、アドレスが取れるまで最大で1分ほどかかっていた。LinuxのNetworkManagerとsystemd-networkdも、リンクが上がるたびにDHCPを始め直す。IPv6のリンクローカルアドレスはリンク層のアドレスから作るもの(EUI-64)なので、`rump_tswifi_setmac`はアドレスを替えたとき、前のアドレスから作ったリンクローカルアドレスを消し、インタフェースの起動のときと同じく新しいアドレスから作り直す(`in6_ifattach`、重複の確かめも行う)。前は作り直さず、有線のカードで起動してWi-Fiに移った後も有線のMACから作ったアドレスが残り、近隣探索もそのアドレスの要請のマルチキャストに入っていた(ThinkPad X1 Yoga 第3世代)。ルータの広告から作るアドレス(`so_slaac.c`)のインタフェース識別子も、つなぎ直しを知らされるたびにリンクローカルアドレスから取り直し、変わっていればルータから受けたものを捨てて作り直す。前は識別子を始めに一度だけ取っていたので、グローバルアドレスも有線のMACのままだった。コンソールに`net: adapter e1k -> wifi, address ...`と出る。アドレスを替えられるのはWi-Fiを含むビルドだけで、`WIFI=0`のビルドでは選択を示すだけになる。

`netsel.c`は、時間の指定のない読出しを0.2秒ずつに区切って待つ。カードが替わったとき、前のカードで待っている`neta0`の読み手が新しいカードに移れるようにするためである。

アダプタはデバイスの実身「netadp」(`OB_S_NET`)でもある。レコード1は次の行で、変わると`OB_E_CHANGE`を通知する。ただし`WIFI`の行の電波の強さと`ADAPTER wifi`の速さは変わり続ける測った値なので、それだけが変わったときは知らせない(レコードはその値で書き換える)。知らせはレコードを書き換えてから出すので、知らせを受けて読んだ者は、知らせのもとになった内容を読む。

```text
SELECT auto
USING e1k
ADAPTER e1k wired up 1000 48:2a:e3:0a:7a:75 Intel Ethernet 8086:15d7
ADAPTER wifi wifi up 54 00:28:f8:xx:xx:xx Intel Wi-Fi 8086:24fd
WIFI connected -52 <SSIDの16進>
```

`ADAPTER`の行はアダプタの名前、有線か無線か、リンク、速さ(Mb/s)、MACアドレス、アダプタの説明である。

### 9.6.2 Wi-Fiの構成

最初に対応したのは、ThinkPad X1 Yoga 第3世代のIntel Dual Band Wireless-AC 8265(PCI 8086:24FD)である。OpenBSDのiwm(4)が扱うIntelのカード(7260、3160、7265、3165、3168、8260、8265、9260、9560)は同じ経路で動く見込みである。Surface Go 2のWi-Fi 6 AX200(PCI 8086:2723)は世代が違うので、OpenBSDのiwx(4)を同じ層に足した(2026-10-26、9.6.9の「iwx」)。層はカードのPCIのIDでiwmかiwxを選ぶ。iwxの扱うほかのカード(AX201、AX210、AX211)は、ファームウェアを載せていないので、今は起動の途中で止まる。

x64のPCのWi-Fiは、OpenBSDの802.11の層とiwmを、rumpカーネルの外のTessronOSの層で動かす(`device/net/wifi/obsd`、9.6.9)。Raspberry Pi 5のWi-Fiは、NetBSDの802.11の層とbwfmを、TCP/IPスタックと同じrumpカーネルの中で動かす(9.6.8)。管理のタスク、WPA2とWPA3の鍵の交換、カードの選択、ネットワーク設定はどちらも同じものを使う。前はx64のPCでもNetBSDのiwmと802.11の層をrumpカーネルの中で動かしていた(`WIFI_NET80211=nbsd`)が、OpenBSDの層が802.11n、PMF、WPA3、背景の走査を持ち、実機でつながったので、その形は除いた(2026-10-23)。NetBSDのiwmでつないでいたときに見つけたこと(9.6.3、9.6.4)は、同じNetBSDの802.11の層を使うbwfmにも当てはまるので、その節に残す。

誤りを直す当てのほかに、規格どおりの機能に要るもので、ドライバにその手段が無いときに限って、機能のための当てを置く。変更は最小にし、NetBSDのコードの動きは変えず、TessronOSの関数を呼ぶ口を足すだけにする。その関数が何もしなければ、元と同じ動きになる形にする。先頭には、何の規格の機能に要るか、なぜドライバの外ではできないか、ほかのOSではどうしているかを書く。Raspberry Pi 5のWi-Fi(bwfm)の`tools/netbsd/patches/bwfm-join-hooks.patch`がこれにあたる。bwfmは参加の直前にチップの`mfp`を0と書き、チップのsupplicantに何も渡さない。そのため、PMF(802.11w)もWPA3(SAE)も使えない。当ては、`bwfm_connect`が`mfp`を書いた直後と、チップのイベントの受け口の頭で、`tswifi_sdio.c`の関数を1つずつ呼ぶ2行である(9.6.8)。OpenBSDのbwfmも`mfp`を0と書き、SAEを持たない。Linuxのbrcmfmacは同じ設定を参加の前に書く。`bwfm.c`は当てた写しから翻訳する。当てを変えたときは、`build_make/wifi_arm.mk`の依存でrumpカーネルが作り直される。

### 9.6.3 bwfm0とneta0

この節と9.6.4は、rumpカーネルの中のNetBSDの802.11の層(Raspberry Pi 5のbwfm、ARMのWi-Fiのシミュレータ)のものである。前のx64の形(NetBSDのiwm、`iwm0`)で見つけたことも、同じ層のこととしてそのまま残す。x64のPCのOpenBSDの層のことは9.6.9に書く。

`bwfm0`(前のx64では`iwm0`)はnet80211のインタフェースで、IPのアドレスを持たない(IPv6も止めておく)。net80211が受信したフレームから取り出したEthernetのフレームは、`iwm0`のスタックには渡さず、`tswifi_if.c`がTessronOSに渡す(`rumpcomp_tswifi_input`)。管理のタスクは、EAPOL(Ethernetの種類0x888E)をハンドシェイクに回し、それ以外を受信のリング(128個)に入れる。Wi-Fiが`netsel.c`の選ぶカードのとき、`neta0`の読み手はそこから読む。`neta0`が送るフレームは、`netsel.c`から`rump_tswifi_send`で`iwm0`の送信の列に入り、net80211が802.11のフレームにして暗号化する。`rump_tswifi_send`はフレームをmbufに写し(`m_devget`)、受けたインタフェースの印を消して(`m_reset_rcvif`)、`if_transmit_lock`で送る。前は`m_set_rcvif(m, NULL)`で消していたが、NetBSDの`m_set_rcvif`はインタフェースの番号を読むためにポインタをたどるので、NULLを渡すと0番地の近くを読む。x64では0番地の近くは写していないのでページフォールトになり、最初に送るフレーム(4ウェイハンドシェイクのメッセージ2)で止まっていた(hw2、ThinkPad X1 Yoga 第3世代)。接続していない間に来たフレームは捨てる。ただし、関連付けを頼んだ後、net80211がまだRUNになっていない間に参加先のAPから来たEAPOLのフレームは、1つ取っておき、関連付けを見た時点でハンドシェイクに渡す。iwmはRUNへの切替えをファームウェアへの命令を出す別の仕事で行うので、APが関連付けの応答の直後に送るメッセージ1がRUNより先に届くことがあるためで、wpa_supplicantが関連付けの知らせより先に来たEAPOLを取っておくのと同じ扱いである。EAPOLの鍵のフレームは、送受のたびに、4ウェイハンドシェイクの何番目か(鍵の情報のビットから)、再送の番号、送ったときにカードが受け取ったかを`wifi: EAPOL-Key in`と`out`の行に出す。接続をあきらめたときはその理由を出し、記録のファイルをすぐ書かせる。

セキュリティの設定では、802.11の認証の方式(`IEEE80211_IOC_AUTHMODE`)はWPA2でも常に開いた認証(`IEEE80211_AUTH_OPEN`)にし、WPA2は`IEEE80211_IOC_WPA`とプライバシーの印で別に設定する。wpa_supplicantのBSD用の層(`driver_bsd.c`の`wpa_driver_bsd_associate`)がSTAを設定するのと同じ形である。`IEEE80211_AUTH_WPA`はAPの側の方式(hostapdの`bsd_set_ieee8021x`)で、net80211はこれを`IEEE80211_AUTH_8021X`として持ち、その方式で参加したSTAは、RUNになってもAPのノードのポートが開かれない(`ieee80211_newstate`)。STAでポートを開く口(`IEEE80211_MLME_AUTHORIZE`)はAPにしか無い。前は`IEEE80211_AUTH_WPA`を書いていたので、APからのデータのフレームはEAPOLのほかすべて「ポートが開いていない」として捨てられ(`is_rx_unauth`)、4ウェイハンドシェイクは終わるのにDHCPの答えが届かなかった(ThinkPad X1 Yoga 第3世代、iwm。シミュレータ(9.6.12)で同じ形を再現して確かめた)。認証の方式を替えるとnet80211はWPAとプライバシーの印を消すので、その後で印を読み直してから設定する。`wifi: link:`の行の終わりに、ポートが開いていないために捨てた数と、ポートが開いているかどうかを出す。

参加は、セキュリティの設定(`rump_tswifi_param`)、関連付けの要求に付ける情報要素(`IEEE80211_IOC_OPTIE`)、関連付けの要求(`IEEE80211_IOC_MLME`のASSOC。BSSIDとSSID)の順である。net80211は認証の方式とWPAの設定の変更にENETRESETを返し、iwmはカードを止めて始め直す。止めるときに走査の表は消えるので、始め直した後は、カード自身の走査が始まるのを見てから(3秒見えなければこちらから走査を始めて)その結果で参加する。設定が変わらなければ始め直しは起きない。関連付けは、NetBSDのwpa_supplicantのBSD用の層(`driver_bsd.c`の`bsd_associate`)と同じく、MLMEの要求にSSIDとBSSIDを入れて頼むだけで、`SIOCS80211NWID`(望むSSID)は書かない。net80211は渡されたBSSIDとSSIDで走査の表からノードを探して参加する(`ieee80211_find_node_with_ssid`は引数のSSIDで比べる)。望むSSIDを使うのは、net80211が走査の結果から自分で選ぶとき(`ieee80211_match_bss`)とIBSSだけで、ローミングを管理のタスクに任せる設定(`IEEE80211_ROAMING_MANUAL`)では使わない。bwfmも、参加するノードのSSID(`ni_essid`)で参加する(`bwfm_connect`)。以前は関連付けの要求の前に`SIOCS80211NWID`を書いていたが、これはENETRESETを返すので、iwmでは参加のたびにカードが始め直して走査の表が消え、続く関連付けの要求が対象のノードを見つけられずEINVAL(22)で断られていた(ThinkPad X1 Yoga 第3世代で「refused (22)」)。iwmとbwfmは同じ手順である。net80211かiwmが断った設定の要求は、`tswifi: SIOCS80211 type ... error`の行に、種類、値、長さ、誤りの番号を出す。

走査の結果の電波の強さは、ドライバがnet80211に渡す値から求める。iwmは強さの大きさを符号なしで渡す(83は-83 dBm)ので、x64ではその符号を戻す。bwfm(Raspberry Pi 5)は符号付きのdBmを渡す。BSSIDが全部0の項目は、net80211自身のノードでAPではないので、結果から除く。

### 9.6.4 接続の流れ

管理のタスク(`wifi.c`)は、net80211を`SIOCS80211`と`SIOCG80211`の`IEEE80211_IOC_ROAMING`、`AUTHMODE`、`PRIVACY`、`WPA`、`DROPUNENCRYPTED`、`OPTIE`、`MLME`、`WPAKEY`、`DELKEY`で操作する。wpa_supplicantのBSD用の層(`drivers/driver_bsd.c`)が使うのと同じ口で、rumpカーネルの入口(`tswifi_if.c`の`rump_tswifi_*`)から呼ぶ。走査の結果だけは、ioctlを使わずにnet80211の走査の表を直接たどる(9.6.6)。ローミングは管理のタスクに任せる設定(`IEEE80211_ROAMING_MANUAL`)にするので、net80211は自分からは走査も参加もせず、どの段階に進むかはすべて管理のタスクが決める。iwmとbwfmは同じ手順で動かし、ドライバによる分岐は持たない(信号の強さの符号だけは、ドライバの渡し方が違うので直す。9.6.3)。

管理のタスクは50ミリ秒ごと(関連付けとハンドシェイクの間は20ミリ秒ごと)にnet80211の状態(`ic_state`、走査中の印、インタフェースの`IFF_UP`と`IFF_RUNNING`)を読み、次の段階に進む。

#### 走査

走査は`rump_tswifi_scan`で頼み、`ieee80211_begin_scan`で前の結果を捨てて始める。net80211が走査中の印(`IEEE80211_F_SCAN`)を落としたら終わりとする。走査はINITの状態からだけ始める。ローミングを管理に任せると、net80211は走査が終わってもSCANの状態に留まり、アクセスポイントに離脱させられた(認証の解除か関連付けの解除を受けた)後はAUTHかASSOCに留まる。SCANのまま走査を頼むとSCANからSCANへの移りになり、bwfmはそれを新しい走査としない(`bwfm_newstate_cb`は前の状態がSCANでないときだけ走査する)。AUTHとASSOCからは走査を始められない。そこで`rump_tswifi_scan`は、INITでなければ先にINITへ移し(ドライバは自分のタスクで移る)、EAGAINを返す。管理のタスクは0.2秒後に頼み直す。走査がすでに進んでいれば(iwmは起動のときと始め直したときに自分で走査を始める)、それを頼んだ走査とみなして0を返す。前はSCANのまま頼んでいたので、Raspberry Pi 5では最初の走査より後の走査が始まらず、15秒で「走査が終わらない」として空の結果を取っていた。そのため、起動のときに見つからなかったアクセスポイントや、切れたネットワークを、参加の失敗でINITに戻るまで見つけられなかった。iwmはSCANからSCANでも走査するので、この誤りはx64では出ていなかった。

1. カードを起動し、`iwm0`か`bwfm0`を上げ、最初の走査を頼む(iwmは上げたときに自分で始めた走査をそれとみなす)。
2. 走査の結果を、電波の強い順に実身「wlan0」のレコード2にし、最初の4回はコンソールにも出す。
3. 保存したネットワーク(9.6.6)のうち、利用者が〈接続〉で名指したもの、なければ「自動で接続」の印のある最も強いものを選ぶ。同じSSIDのアクセスポイントが何台かあれば、最も強いBSSIDを選ぶ。保存したネットワークは保存した利用者のもので、名指しできるのは書いた利用者のものだけ、自分から接続するのはデスクトップにログインしている利用者(だれもログインしていなければ利用者、8.7)のものだけである。保存したネットワークが無い、`$$WIFI off`、〈切断〉の後は、自分からは接続しない。接続していない間は30秒ごとに走査し直す。

#### 参加

4. WPA2-Personalなら、保存してある鍵(PMK、9.6.6)をそのまま使い、アクセスポイントのRSNの要素から暗号を決め(ペアの鍵はCCMP、無ければTKIP。グループの鍵はアクセスポイントのもの)、自分のRSNの要素を関連付けの要求に入れる。暗号の無いネットワークはそのまま求める。セキュリティの設定と関連付けの要求の手順は9.6.3に書いた。
5. 管理フレームの保護(PMF、802.11w)は使わない。NetBSD 11.0のnet80211はPMFを持たない。アクセスポイントがPMFを「使える」とするだけなら、PMFなしで参加する。「必須」とする(RSNの能力のMFPRが立つ)アクセスポイントは、関連付けを断るので、参加を始める前に`wpa_glue.c`が断り、`REASON unsupported`とする(前は8秒待って`timeout`になっていた)。Linuxのmac80211とiwlwifiはPMFを持ち、wpa_supplicantは既定でPMFを「使えれば使う」とする。
6. 8秒で関連付けが済まないときは離脱して失敗とし、そのネットワークを20秒(4回以上続けて失敗したら2分)休ませる。

#### 鍵の交換

7. 関連付けが済むと(net80211の状態がRUN)、wpa_supplicantの状態機械が4ウェイハンドシェイクとグループ鍵のハンドシェイクを行う。関連付けを見る前に届いたメッセージ1は取っておいて渡す(9.6.3)。ペアの鍵は`IEEE80211_KEYIX_NONE`でnet80211のペアの鍵に、グループの鍵はアクセスポイントの決めた番号(1か2)で`IEEE80211_KEY_GROUP`として、受信の続き番号(RSC)と一緒に設定する。終わると接続済みになる。
8. 暗号化と復号は、iwmではnet80211がソフトウェアで行う(`iwm_tx`が`ieee80211_crypto_encap`を呼ぶ。NetBSDのiwmはカードの暗号の機能を使わない)。bwfmではチップのファームウェアが行い、鍵は`bwfm_key_set`でチップに渡る。net80211は、ペアの鍵を設定するまでEAPOLを暗号化せずに送る。`DROPUNENCRYPTED`の間も、暗号化されていないEAPOLは受け取る。
9. 再送はアクセスポイントが行う。メッセージ1が届かなければアクセスポイントが送り直す。こちらのメッセージ4が届かなければ、メッセージ3がもう一度来る。状態機械はそれに答え直し、ペアの鍵を二度は設定しない(鍵の再設定の攻撃への備え)。どちらもホストの試験(9.6.7)で確かめる。2回目のメッセージ4はペアの鍵で暗号化して出る。これはLinuxでも同じである。
10. 10秒でハンドシェイクが終わらない、または途中で関連付けが切れたときは、パスフレーズの誤りの見込みとして`REASON password`を示し、6.と同じく休ませる。
11. TKIPのMICの誤りの対策(60秒に2回の誤りで止める)は持たない。net80211はMichaelの誤りを経路のソケットで知らせるが、それを聞いていない。TKIPをペアの鍵に使うのはCCMPを持たないアクセスポイントだけである。

#### 伝送

12. `neta0`の送るフレームは、`netsel.c`、`knl_wifi_send`、`rump_tswifi_send`を通って`if_transmit_lock`でインタフェースの送信の列に入り、そのままドライバの送信が呼ばれる。接続していない間と、列があふれたとき(ENOBUFS)は捨ててE_IOを返し、TCPの再送に任せる。フレームは1514バイトまで(MTU 1500)である。
13. 受けたフレームは受信のリング(128個)に入る。あふれた分と接続していない間に来た分は捨て、数える(`dropped`)。
14. 接続すると、アダプタの管理がDHCPの問い合わせをやり直させる(9.6.1)。ARPの要求などの同報はグループの鍵で受ける。
15. 電源の節約。iwmは使わない(`iwm_power_update_device`がCAMの印を立て、MACの電源の命令に節約の印を入れない)ので、受信が止まることは無い。Linuxのiwlwifiは既定で節約を使う。bwfmはチップの`PM_FAST_PS`(`bwfm_init`)で、Linuxのbrcmfmacの既定と同じく、送受の後しばらく起きている形の節約になる。
16. 速さの選び方。iwmはnet80211のAMRRを0.5秒ごとに走らせ(`iwm_calib_timeout`)、802.11a/b/gの速さから選ぶ(802.11nは無い、9.6.2)。始めは最も遅い速さで、成功が続くと上げる。bwfmはチップのファームウェアが選ぶ。wlan0の`RATE`は今の送信の速さである。Linuxのiwlwifiはファームウェアの速さの選び方で802.11nとacの速さを使う。
17. 接続している間は1分ごとに、`wifi: link:`の行に電波の強さ、速さ、周波数、送った数、受けた数、捨てた数を出す。

#### 保ち続けること

18. グループの鍵とペアの鍵の更新は、接続している間に来たEAPOLも状態機械に渡すので、そのまま受ける。ホストの試験で、両側の新しい鍵が一致し、前の鍵と違うことを確かめる。
19. ビーコンを見失うと、iwmではカードのファームウェアが続けて8回を超えて見失ったことを知らせ(`IWM_MISSED_BEACONS_NOTIFICATION`)、net80211がアクセスポイントに探索の要求を送り、それでも答えが無ければSCANに移る。iwmはRUNから下の状態に移るときカードを始め直す。bwfmではチップがリンクの切れを知らせ(`BWFM_E_LINK`)、SCANに移る。どちらも管理のタスクから見ればRUNでなくなったことで、次の「切断」の扱いになる。
20. 接続している間は走査しない。NetBSDのnet80211とiwmは、RUNのまま走査する手段を持たない。そのため、接続している間に、より強いアクセスポイントへ移ることはしない(OpenBSDのnet80211はiwmで背景の走査とローミングを持つ。Linuxではwpa_supplicantの`bgscan`とmac80211の走査で行う)。〈走査〉の指示も、接続している間は断る。

#### 切断と始め直し

21. アクセスポイントからの認証の解除と関連付けの解除、ビーコンの見失いで、net80211はRUNから外れる。管理のタスクはそれを見て、ハンドシェイクの状態を捨て、`REASON lost`とし、すぐに走査からやり直す(上の走査の始め方でINITに戻してから)。見つかれば休ませずに参加する。アクセスポイントが言った理由は、接続している間もnet80211の認証と関連付けの出力を止めないので、`recv deauthenticate (reason N)`などの行に出る。記録のファイルもすぐ書かせる。
22. こちらからの切断(〈切断〉、別のネットワークへの〈接続〉、利用者の替わり、`$$WIFI off`への書換え)は、`rump_tswifi_deauth`で行う。`IEEE80211_MLME_DEAUTH`は使わない。これはnet80211をRUNから直接INITに移し、iwmはINITへ下りるとき先にカードを初期化し直してから(`iwm_stop_device`、`iwm_init_hw`)net80211に移らせる。net80211はその移りでアクセスポイントに関連付けの解除を送るが、初期化し直したカードにはもうその局が無く、ファームウェアの誤り(SW_ERR)になってiwmがインタフェースを下げていた(ThinkPad X1 Yoga 第3世代で〈切断〉のたびに`wifi: the card stopped`)。そこでiwmではSCANへ移らせる。iwmは先にnet80211をINITに移し(関連付けの解除はカードが局を持っている間に出る)、それからカードを始め直して走査する。インタフェースは下がらない。bwfmのチップはnet80211の状態にかかわらず関連付けを保つので、`BWFM_C_DISASSOC`でチップに離れさせてからINITに移す。前はnet80211だけをINITにしていたので、Pi 5では〈切断〉してもチップがつながったままだった。〈切断〉の後は、〈接続〉か設定の書換えまで自分からはつながない。接続しているネットワークへの〈接続〉は何もしない。
23. カードが止まったとき。iwmは、ファームウェアの誤り(`IWM_CSR_INT_BIT_SW_ERR`)、ハードウェアの誤り(`HW_ERR`)、送ったフレームが出て行かない(`iwm_watchdog`の`device timeout`)と、インタフェースの`IFF_UP`を落としてカードを止める。カードの起動の失敗(`iwm_init`)でも`IFF_UP`を落とす。前は、それを始め直すものが無く、以後の走査はすべてENETDOWNで、再起動するまでWi-Fiが使えなかった。今は、`IFF_UP`が1秒落ちたまま、または上がっているのに`IFF_RUNNING`が10秒落ちたままなら、管理のタスクがインタフェースを下げて上げ直し(起動と同じ`iwm_init`、ファームウェアの読込みから)、すぐ走査する。2回目からは10秒、30秒、60秒、その後は2分おきで、接続できたら数え直す。コンソールに`wifi: the card stopped`の行と回数を出し、x64では最初の1回に`wifi: irq`の行も出す。iwmの`IWM_DEBUG`は有効なので、ファームウェアの誤りの記録(`iwm_nic_error`)も出る。Linuxのiwlwifiはファームウェアを読み直してmac80211が設定をやり直し(`ieee80211_restart_hw`)、つなぎ直す。OpenBSDのiwmは、同じ誤りで止めて初期化をやり直す仕事を起こす。
24. つなぎ直し。切れたときはすぐ、参加に失敗したときは6.のとおり休ませてから、何回でも試す。wpa_supplicantも、認証の失敗が続くとそのネットワークをしばらく(10秒から次第に長く)使わないが、あきらめはしない。

#### ローミング

25. 同じSSIDのアクセスポイントが何台かあるときは、参加するたびに走査の結果から最も強いBSSIDを選ぶ。接続している間は移らない(20.)。電波の弱い所へ動いて、アクセスポイントに離脱させられるかビーコンを見失うと、21.で走査し直し、そのとき最も強いもの(別のアクセスポイントのことがある)に参加する。参加し直すと、アダプタの管理がDHCPを問い合わせ直す。

#### 利用者、設定、システムの眠り

26. 利用者が替わると(ログアウトとログイン)、接続中のネットワークが新しい利用者のものでなければ切断し、新しい利用者のネットワークを探す(LinuxのNetworkManagerの利用者ごとの接続、`permissions=user:…`と同じ考え方)。
27. 設定の`$$WIFI off`は、自分からつながないことに加えて、そう書き換えた時点でつながっていたネットワークから離れる。カードの電源は切らない。
28. 電源を切るときと再起動のとき(デスクトップの終了、電源ボタン、再起動。どれも`usermain`から戻って`knl_finish_device`を通る)は、接続しているネットワークから、理由3(離れる)の認証の解除を送って離れてから止める(`knl_wifi_shutdown`。管理のタスクが〈切断〉と同じに行い、1秒まで待ち、フレームが出る0.1秒を足す。`REASON off`)。Linuxはインタフェースを下げるとき(`cfg80211_leave`、`WLAN_REASON_DEAUTH_LEAVING`)と、NetworkManagerとwpa_supplicantが止まるときに切断を送り、Windowsも同じである。前は送らずに電源を切っていたので、アクセスポイントとメッシュは、その局が前の起動でつないでいたアクセスポイントにまだいると覚えていた。次の起動で別のアクセスポイント(同じメッシュの別の機械)につなぐと、局宛てのユニキャストが前のアクセスポイントへ流れ、届かなかった見込みが高い(hw6oとhw10oの実機。f4:d5:80:31:fc:d0につないだ間、局宛ての保護されたユニキャストが50秒から90秒以上1つも来ず、DHCPのREQUESTに答えが無かった。〈切断〉と〈接続〉の後は、すぐ届いた)。行は`wifi: the machine goes off: the network is left`と`wifi: the network left`である。
29. TessronOSには今、システムの眠り(サスペンド)が無い。入れるときは、起きた後にカードを始め直す(iwmはファームウェアを読み直す必要がある)。23.の始め直しがそのまま使える。

WPA3(SAE)、WPA(RSNの無いもの)、WEP、802.1X(企業向け)のネットワークには接続しない(走査の一覧には暗号の種類を付けて出す)。WPA2とWPA3を両方受け付けるアクセスポイントには、WPA2で接続する。

流れ全体をほかのOSと比べて調べた結果の一覧は、`docs/private/wifi_flow_review.md`にある。

実機で1回起動すれば各段階が分かるように、次のことをコンソール(とTSLOGの`KERNEL.TXT`)に出す。カードの検出(`wifi: card 8086:24fd at 2:0.0`)、MSIの番号、ファームウェアの実身の読込み(`wifi: firmware iwm-8265-36: 2436632 bytes`)、命令のキューの様子(`wifi: cmdq`の行。カードを起こして読んだSCDのレジスタ(SRAMとDRAMの基底、TXFACT、EN_CTRL、命令のキュー9の書込みと読出しの位置と状態)、FHのTXの各チャネルとRXのレジスタ、命令のキューのTFDの中身とそれが指す命令の頭(番号、フラグ、位置、キュー)、カードが最後に書いたRXの状態(閉じたRBの番号)、割込みの原因の表(ICT)の0でない項目。割込みのたびにも、ICTの0でない項目の数と最初の1つを残す)、カードのPCIeの装置の制御、リンクの制御と状態(ASPM)、装置の制御2(LTR)、割込みの様子(`wifi: irq`の行。ファームウェアを読んだ3秒後と8秒後と、カードが起動しなかったときに出す。来た割込みの数、ハンドラのスレッドが起きた数、割込みの宛先のプロセッサ、PCIのコマンドとステータス、カードが持つMSIのアドレスとデータとマスク、カードのCSR_INT、CSR_INT_MASK、FH_INT、GP_CNTRL、ICT、ファームウェアを送るチャネルの値、最後の8回の割込みのそれぞれでハンドラが読んだCSR_INTなど)、iwmの各段階(iwmの`IWM_DEBUG`の出力と`iwm0: hw rev ..., fw ver ..., address ...`)、`iwm0`の起動、走査の結果、接続先、net80211の状態の移り変わり(認証、関連付け、RUN。net80211の`IEEE80211_DEBUG`の状態、認証、関連付け、WPAの出力)、EAPOLの鍵のフレームの送受、wpa_supplicantの言うこと(`WPA: RX message 1 of 4-Way Handshake`など。鍵の値は出さない)、鍵の設定、接続と切断、アクセスポイントが離脱させたときの理由(`recv deauthenticate (reason N)`など)、接続している間の1分ごとのリンクの様子(`wifi: link:`)、カードの始め直し(`wifi: the card stopped`)、アダプタの切替えとDHCPの問い合わせ直し(`net: ... the address is asked for again`)、DHCPの結果(9.3.1)。iwmの細かい出力とnet80211のWPAの出力は、接続している間は止める。

### 9.6.5 ファームウェア

8265のファームウェアは、OpenBSDのiwm(9.6.9)が`iwm-8265-36`の名前で求めるAPIの版36の`iwlwifi-8265-36.ucode`である。`tools/x64/wifi/fw.sh`が、linux-firmwareのタグ20230117から、git.kernel.org(だめならgitlab.comの写し)で取り、新しい空のディレクトリに置いてSHA-256と大きさを確かめてから`~/tessronos-wifi-fw`に移す。Intelの許諾(`LICENCE.iwlwifi_firmware`)も同じく取る。このバイト列は、OpenBSD 8.0が配るiwmのファームウェア(`firmware.openbsd.org`の`iwm-firmware-20240410.tgz`、その`iwm-8265-36`)と同じで、OpenBSDのiwmで使われているものである(git.kernel.org、gitlab.com、OpenBSDのパッケージの3つで同じSHA-256だった。許諾の`iwm-license`も`LICENCE.iwlwifi_firmware`と同じ)。後のタグ(例えば20260810の`intel/iwlwifi/iwlwifi-8265-36.ucode`)は同じ名前の新しいファイルで、TLVの種類66と67(Linuxの`IWL_UCODE_TLV_SEC_TABLE_ADDR`と`D3_KEK_KCK_ADDR`)を持つ。OpenBSDのiwmの`iwm_read_firmware`は知らない種類を誤り(EINVAL)として読込みをやめるので、ThinkPad X1 Yoga 第3世代で`iwm0: firmware parse error 22, section type 66`になった。OpenBSDのソースは変えず、OpenBSDのiwmが読むファームウェアを使うことで直した。

`WIFI=1`のx64のビルドは、`tools/x64/wifi/mkobj.py`でこれを固定のUUIDのただの実身(`SYSDEF_FW_IWM8265_36`、名前`iwlwifi-8265-36.ucode`)にする。レコード1がファイルそのもの、レコード0が説明とIntelの許諾の文、所有者はシステムで誰でも読める。実身「システム」から仮身で結び、ARMのイメージには入れない(`mktsfs`の`--over`で、x64の`WIFI=1`のビルドだけ実身「システム」を差し替える)。前のNetBSDのiwm(除いた形、9.6.2)が求めたAPIの版22の`iwlwifi-8265-22.ucode`の実身(`SYSDEF_FW_IWM8265`)は、その形と一緒に除いた。

Surface Go 2のWi-Fi 6 AX200のファームウェアは、OpenBSDのiwx(9.6.9)が`iwx-cc-a0-77`の名前で求めるAPIのバージョン77の`iwlwifi-cc-a0-77.ucode`(1,368,096バイト)である。`fw.sh`が、linux-firmwareのタグ20251021の`intel/iwlwifi/`から、8265と同じ手順で取る(ファイルごとにタグと木の中の場所を持つ)。このバイト列は、OpenBSD 8.0が配るiwxのファームウェア(`firmware.openbsd.org`の`iwx-firmware-20251021p0.tgz`、その`iwx-cc-a0-77`)と同じである(git.kernel.org、gitlab.com、OpenBSDのパッケージの3つで同じSHA-256。許諾の`iwx-license`も`LICENCE.iwlwifi_firmware`と同じ)。1つ前のタグ20250917の同じ名前のファイルは、大きさが同じで中身が違う。`mkobj.py`がこれを実身`SYSDEF_FW_IWXCC_77`(名前`iwlwifi-cc-a0-77.ucode`)にし、8265のものと同じ形で実身「システム」から結ぶ。AX200はPNVMのファイルを読まない。

### 9.6.6 設定と状態

接続するネットワークは、設定の実身「Ｗｉ－Ｆｉの設定」(`SYSDEF_CONF_WIFI`、`WIFI=1`のビルドだけ、実身「システム」から仮身で結ぶ)のレコード1の次の行である。

```text
$$WIFI	on
$$WIFINET	<SSIDの16進> <open|wpa2|wpa3|wpa2wpa3> <auto|manual> <ユーザのUUID>
$$WIFIPSK	<番号> <64桁の16進>
$$WIFISAE	<番号> <パスワードの16進>
```

`$$WIFINET`の4つ目の語は、そのネットワークを保存した利用者である。保存したネットワークはその利用者だけのもので、ほかの利用者からは見えず、使えず、消せない。同じSSIDを何人かの利用者がそれぞれの鍵で持てる。「すべての利用者に共通の接続」は持たない。`$$WIFIPSK`の番号は`$$WIFINET`の行の順(0から)で、値はそのネットワークの鍵、つまりWPA2のPMK(パスフレーズとSSIDからPBKDF2-SHA1の4096回で求めた32バイト)である。WPA2のパスフレーズそのものは保存しない。

`$$WIFINET`の2つ目の語はセキュリティで、`open`(なし)、`wpa2`(WPA2-Personal)、`wpa3`(WPA3-Personal、SAE)、`wpa2wpa3`(WPA2/WPA3-Personal)のどれかである。`wpa2wpa3`は、アクセスポイントがSAEを出していればWPA3で、出していなければWPA2でつなぐ(移行モードのアクセスポイントと、WPA2だけのアクセスポイントのどちらにもつながる)。`$$WIFIPSK`を持つのは`wpa2`と`wpa2wpa3`、`$$WIFISAE`を持つのは`wpa3`と`wpa2wpa3`である。`$$WIFISAE`の値はWPA3のパスワードそのもの(8〜63文字の印字できるASCII)を16進で書いたものである。16進にするのは、空白を含むパスワードを1語で書くためで、隠すためではない。

#### 鍵の保存の決め方

LinuxのNetworkManagerとwpa_supplicantの持ち方と比べて、次のように決めた。

| | NetworkManager | wpa_supplicant | TessronOS |
| --- | --- | --- | --- |
| 置き場 | `/etc/NetworkManager/system-connections`のファイル。rootだけが読み書きできる(600) | `wpa_supplicant.conf`。ふつうrootだけが読める | 設定の実身「Ｗｉ－Ｆｉの設定」。所有者はシステム、グループは管理者、モード`rw-------` |
| 鍵の形 | `psk=`にパスフレーズを平文で書く。WPA3も同じ`psk=` | `psk="..."`のパスフレーズか、`wpa_passphrase`が作る64桁の16進のPSK。WPA3は`sae_password="..."`か`psk="..."`の平文 | WPA2は64桁の16進のPMKだけ。WPA3はパスワード(16進で書く) |
| 利用者ごとの接続 | 接続の`permissions=user:…`で、その利用者だけが使える接続にする。秘密は利用者のキーリング(GNOMEのキーリング)に置くこともでき、NetworkManagerが接続のたびに秘密のエージェントに求める | 無い | すべての接続が保存した利用者のもの。同じ設定の実身に持ち主のUUIDを付けて置き、鍵もそこに置く |
| 読める者 | rootと、キーリングの持ち主の利用者のプロセス | root | カーネル(Wi-Fiの管理)と管理者だけ。ふつうの利用者のプロセスは鍵を読めない |
| 書ける者 | polkitの規則で決まる | root | カーネルのWi-Fiの管理だけ。プログラムはwlan0に依頼を書き、書いたプロセスの利用者の接続だけが変わる。管理者のパスワードは尋ねない |

理由は次のとおりである。

- パスフレーズではなくPMKを持つ。PMKはWPA2の4ウェイハンドシェイクに必要なもののすべてなので、接続には困らない。一方、パスフレーズは人が覚えやすい語で、ほかのネットワークやサービスにも使い回されていることがある。PMKは一方向の関数(PBKDF2)の結果なので、設定の実身が漏れてもパスフレーズは分からない。wpa_supplicantの`wpa_passphrase`が作る形と同じで、その分だけNetworkManagerの平文より安全である。PMKはSSIDに結び付くので、別のSSIDでは使えない。SSIDを変えるときはパスフレーズを入れ直す。
- WPA3のネットワークでは、パスワードそのものを持つ。SAEは接続のたびにパスワードから計算するもので、PMKのように前もって求めておける値が無い。hunting and peckingの方式では、パスワードの要素(PWE)が自分とアクセスポイントのMACアドレスに依るので、アクセスポイントごとに作り直す。H2Eの方式ではSSIDとパスワードから求めるPT(パスワードの要素)を持てば足りるが、H2Eを持たないアクセスポイントがまだ多く、PTだけではそれにつなげない。PTはパスワードから接続のたびに求め、保存しない。Raspberry Pi 5では、SAEをチップのファームウェアが行い(9.6.8)、ファームウェアには`sae_password`のiovarでパスワードそのものを渡す。外部認証(`sae_ext`)を持たないので、ホストで計算した値を渡す道も無い。NetworkManagerもwpa_supplicantも、WPA3のパスワードを平文で持つ。パスワードの守りはPMKと同じで、カーネルだけが読める設定の実身に置き、wlan0のレコード1にもネットワーク設定の小物にも出さない。WPA2/WPA3は両方を持つ。WPA2に変えるとパスワードを消し、WPA3に変えるとPMKを消して、使わない鍵は残さない
- 鍵を持つのはカーネルだけにする。ふつうの利用者のプロセスは、設定の実身を開けない(8.6、モードの「その他」に何も無く、利用者のグループも持たない)。ネットワーク設定の小物も設定の実身を開かない。保存も削除もwlan0に依頼を書き、wlan0のレコード1の`SAVED`の行には鍵を出さない。管理者は保護の判定で何でも許されるので読めるが、それはLinuxのrootと同じである。前の形の`rw-rw----`は、グループの管理者に読み書きを与えていたが、管理者はもともとすべてを許されるので、意味が無かった。
- 接続は利用者ごとにする(ユーザの指示)。どこにつなぐかは人ごとの好みと秘密で、ほかの人の家や職場のネットワークの名前は見せず、その鍵でつながせない。NetworkManagerの利用者ごとの接続と同じく、自分から接続するのはログインしている利用者の接続だけで、利用者が替われば前の人の接続を切る。
- 置き場は今の設定の実身1つにし、利用者ごとに実身を分けない。分ける案(利用者ごとに「Ｗｉ－Ｆｉの設定」の実身を持つ)は、利用者の資源をその利用者の実身にするという点ではBTRON2らしい。しかし、鍵をカーネルだけが読めるようにするには、その実身の所有者をシステムにしなければならず、利用者の実身ではなくなる。利用者が増えるたびにカーネルが実身を作り、どこかから仮身で結ぶ置き場も要るが、新しい「○○箱」は作らない方針である。カーネルは自分から接続するときに全員の実身を開いて回ることにもなる。持ち主のUUIDを付けた行を1つの実身に置けば、保護は1か所で済み(`rw-------`)、バックアップやボリュームの扱いも今のままで、利用者が別の利用者の行を見られないことはカーネルが保証する(wlan0のレコード1は、読んだプロセスの利用者の行だけを返す)。それで1つの実身にした。
- 保存、変更、削除、接続、切断は、自分の接続については何も尋ねない(ユーザの指示)。ほかの利用者の接続には、もとより何もできない。鍵がプロセスに渡らないことは、尋ねるかどうかと関係なく保つ。
- TessronOSのデスクトップには、今はログインの画面が無く、ふだんはだれもログインしていない(プログラムは利用者として動く)。そのため、カーネルから見た「ログインしている利用者」は、ログインが無ければ利用者である。ログインせずに保存した接続は利用者のもので、ログインせずに使っている間は自分から接続する。ログインの画面ができてその間を区別できるようになったら、その間は自分から接続しないようにする(`knl_ob_session`の呼出しで利用者が替わったことは、すでに受け取っている)。

#### 依頼

保存したネットワークを変えるのは、wlan0のレコード1に書く次の行である。カーネルのWi-Fiの管理が、書いたプロセスの利用者(8.7の資格情報)のネットワークについて、設定の実身を読み、変え、書いて、終わってから書込みに答える。ほかの利用者のネットワークは、同じSSIDでも変わらない。

```text
SAVE <SSIDの16進> <open|wpa2|wpa3|wpa2wpa3> <auto|manual> [<パスフレーズ>]
FORGET <SSIDの16進>
```

`SAVE`のパスフレーズは行の残りすべてで(空白を含めてよい)、8〜63文字の印字できるASCIIか、64桁の16進のPSKである。`wpa3`と`wpa2wpa3`では8〜63文字の印字できるASCIIだけで、64桁の16進は断る(SAEはPSKではなくパスワードから計算する)。それ以外は`E_PAR`で断り、鍵は変えない。パスフレーズを省くと、そのネットワークが持つ鍵をそのまま使う。セキュリティが要る鍵を持っていないとき(鍵の無いネットワーク、ほかの利用者だけが持っているもの、PMKしか持たないネットワークを`wpa3`や`wpa2wpa3`に変えるとき)にパスフレーズを省くと、`E_NOEXS`で断る。保存の行はコンソールに`wifi: saved a network, a new key: 0 (wpa3)`のように出る。書いた利用者の持たないネットワークの`FORGET`も`E_NOEXS`である。パスフレーズはカーネルの中で鍵にしたらすぐに消し、どこにも残さない。書込みの1行を受け取る場所も、使ったら0で埋める。依頼は一度に1つで、管理のタスクがしている間、次の依頼は待つ。カードが起動しなかったとき(`STATE nofirmware`)も、管理のタスクは依頼だけは受け付ける。

管理のタスクは起動時と、2秒ごとにこのレコードを読み、変わっていれば読み直す。実身を開くのは読み書きする間だけである。開いたまま変更の通知を待つと、システムボリュームを外せなくなる(電源断、ボリュームの検査と修復、バックアップ)。読み直したとき、接続中のネットワークと名指しされているネットワークは、行の位置ではなくSSIDと持ち主で探し直す。

鍵を持つ前の設定(`$$WIFIPASS	<番号> <パスフレーズ>`の行)は、読んだときにパスフレーズから鍵を作り、`$$WIFIPASS`の行を除いて書き直す。前の版の設定も読む。ユーザのUUIDのある`$$WIFINET`はその利用者のものである。持ち主の語の無い行と`all`の行は、読んだときにログインしている利用者(起動したときは、だれもログインしていないので利用者)のものにして書き直す。管理者のものにする案もあるが、管理者はふだんログインしないので、自分から接続されなくなる。今まで使っていた人(ログインの無い今は利用者)のものにすれば、今までどおりつながる。同じ利用者の同じSSIDが2度になれば、先の行に後の行の鍵を移して1つにまとめる。すでに配ったマシンの設定の実身は`rw-rw----`のままだが、上に書いたとおり保護の効き目は`rw-------`と同じである。

保存できるネットワークの数に上限は無い。管理のタスクは`$$WIFINET`の行の数だけ場所を用意して全部を読み、ネットワーク設定も全部を読んで書き直す。

Wi-Fiのカードはデバイスの実身「wlan0」(`OB_S_NET`)でもある。レコード1は状態で、だれでも読める。状態が変わると、管理のタスクがその場でレコード1の`OB_E_CHANGE`を、走査が終わるとレコード2の`OB_E_CHANGE`を知らせる。`SIGNAL`と`RATE`は変わり続ける測った値なので、それだけが変わったときは知らせない。ネットワーク設定の〈Ｗｉ－Ｆｉ〉は、この知らせで読み直し、〈状態〉を見ている間だけ電波の強さと速さを1秒ごとに読む(11.30)。ただし`SAVED`の行は、読んだプロセスの利用者のネットワークだけを出す(カーネルのタスクにはすべてを、行の終わりに持ち主のUUIDを付けて出す)。

```text
STATE connected			off、starting、nofirmware、idle、scanning、joining、handshake、connected
MAC 00:28:f8:xx:xx:xx
SSID <16進>
BSSID xx:xx:xx:xx:xx:xx
FREQ 2437			MHz
SIGNAL -52			dBm
RATE 54				Mb/s
SECURITY wpa2			open、wpa2、wpa3(その接続が使う方式。wpa2wpa3で保存したネットワークも、SAEでつないだらwpa3)
REASON password			前の接続が失敗した理由: notfound、unsupported、nowpa3、timeout、password、lost、refused、asked
SAE yes				カードがWPA3(SAE)でつなげるか: yes、no
SAVED <SSIDの16進> wpa2 auto	読んだプロセスの利用者が保存したネットワーク。セキュリティはopen、wpa2、wpa3、wpa2wpa3。鍵もパスワードも出さない
```

レコード1に書くと指示になる。`SCAN`(接続していないときに走査する)、`CONNECT <SSIDの16進>`(書いた利用者が保存したネットワークにつなぐ)、`CONNECT`(保存したネットワークに自動でつなぐのを再開する)、`DISCONNECT`(切断し、`CONNECT`か設定の書換えまで自分からはつながない)、上の`SAVE`と`FORGET`。だれでも書けるが、どれも書いた利用者のネットワークにだけ効く。レコード2は走査の結果で、1行が`BSS <BSSID> <MHz> <dBm> <open|wep|wpa|wpa2|wpa3|wpa2wpa3|8021x> <SSIDの16進>`である(`wpa2wpa3`はPSKとSAEの両方を出すアクセスポイント。`wpa2`はPSKだけ)。走査の結果の数にも上限は無い。

WPA3でつなげるかどうかは、機械の種類ではなくカードの能力で決める。チップのsupplicantがSAEを持つカード(`rump_tswifi_fw_caps`の`FW_IDSUP`と`FW_SAE`、Raspberry Pi 5)と、SAEのフレームをホストのSAE(`knl_wpa_sae_*`)に渡すOpenBSDの層(`WIFI_NET80211=obsd`、9.6.9)はつなげる。NetBSDのnet80211とiwmには認証のフレームを送る手段が無いので、つなげない。接続先を選ぶとき(`choose`)は、保存したセキュリティとアクセスポイントのセキュリティに、カードが扱える共通のものがあるアクセスポイントだけを候補にする。WPA3だけで保存したネットワークは、SAEを持たないカードでは候補にならず、名指しで接続を頼まれたときは`REASON nowpa3`で断る。WPA2/WPA3で保存したネットワークは、SAEを持たないカードではWPA2でつなぐ。ネットワーク設定は`SAE no`のとき、走査の一覧のWPA3だけのネットワークに「(未対応)」を添え、WPA2/WPA3のネットワークを「WPA2」と示す。rumpカーネルの受け(`rumpcomp/wifi/tswifi_if.c`の`rump_tswifi_results`)は、走査結果のioctl(長さが16ビットで、32KB弱しか返せない)を使わず、net80211の走査の表を直接たどる。用意された場所に入らなかったものも数えて答えるので、管理のタスクは場所をその数まで広げて受け取り直し、見つかったものを全部レコード2にする。ネットワーク設定も全部を一覧に出す。

### 9.6.7 試験

保存したネットワークと鍵は、群`wifikey`(`tests/ktest/ktest_wifikey.c`、`WIFI=1`のKTESTで入る。ARMは`make TARGET=_QEMU_VIRT_ KTEST=1 WIFI=1 KTONLY=wifikey`、x64は`make TARGET=_X64_ KTEST=1 KTONLY=wifikey sdimg`を`tools/x64/ktest64.sh`)で確かめる。カードの無いマシンには管理のタスクが無いので、依頼はカーネルのテストのタスクが管理のタスクと同じ関数で行う。利用者と、ログインしている利用者は設定の実身を読めず書けないこと、パスフレーズで保存すると設定に鍵(PBKDF2で求めた値と同じもの)が入り、パスフレーズも`$$WIFIPASS`も入らないこと、wlan0のレコード1に鍵もパスフレーズも出ないこと、パスフレーズを省いて保存し直しても鍵が変わらず、接続に使う鍵がそれであること、打ち直すと置き換わること、別の利用者からはそのネットワークがレコード1に見えず、鍵が使えず、消せず、同じSSIDを自分の鍵で別に持てること、自分から接続するのがログインしている利用者のネットワークだけで、別の利用者がログインすると前の利用者のネットワークは自分から接続されず(接続中なら切られ)新しい利用者のものが接続されること(`knl_ob_session`で利用者を替えて見る)、削除したネットワークだけが消えること、`$$WIFIPASS`の設定と、持ち主の無い行や`all`の行(同じSSIDが2度あるもの)が、ログインしている利用者のネットワークとして鍵に直されて書き直されることを見る。WPA3では、`wpa3`で保存すると設定にパスワード(16進)が入りPMKは入らないこと、参加の側に渡る(`net_secret`)のがそのパスワードと、それから求めたH2EのPTであること、wlan0のレコード1にパスワードもその16進も出ないこと、ほかの利用者には何も渡らないこと、短いもの、64桁の16進、印字できない文字のあるパスワードは断られて前のものが残ること、`wpa2wpa3`ではPMKとパスワードの両方を持ち、パスワードを省いてPMKの無いネットワークを`wpa2wpa3`にはできないこと、`wpa2`に戻すとPMKだけが残り、パスワードの無いまま`wpa3`にはできないことを見る。

画面は`tools/tests/ui_wifikey.steps`(ARM、`make TARGET=_QEMU_VIRT_ DESKTOP=1 UITEST=1 WIFI=1`)と`tools/x64/tests/ui_wifikey.steps`(x64)で確かめる。UIテストの`wifitest`の命令(`application/desktop/dtuitest.c`)が、カードの無いマシンにテスト用のwlan0を作る。テスト用のwlan0は、SAEを持つカード(`SAE yes`)として振る舞う。走査の結果は長い名前を含む決まった4つで、保存と削除は本物のカードと同じ管理の関数で行い、`CONNECT`は接続する代わりに、使う鍵(保存した鍵か、鍵が無いか)をコンソールに出す。手順は、走査の一覧で長いSSIDが「…」で省かれること、利用者の資格のネットワーク設定から何も尋ねられずにパスワードで保存でき、その利用者の接続として〈保存した接続〉に出ること、保存した接続を選ぶと伏せ字が8個出ること、伏せ字のまま〈接続〉を押すと保存せずに保存した鍵で接続を指示すること(`wifi: test: joining ... with the saved key`)、〈削除〉も尋ねずに消すこと、走査の一覧のWPA3のネットワークを選ぶと〈セキュリティ〉が「WPA3-Personal」になり、パスワードで保存して〈接続〉するとSAEで保存したパスワードを使うこと(`by SAE with the saved password`)、〈セキュリティ〉のポップアップに4つの選択肢が並び、「WPA2/WPA3-Personal」で保存し直すとPMKとパスワードの両方を使うこと、表示の倍率を150%にしても一覧の文字が欄からはみ出さないことである。

QEMUにはWi-Fiの装置が無い。QEMUでは、`WIFI=1`のビルドで、Wi-Fiの部分がカードの無いマシンで何もしないこと、有線とネットワークの試験が通ることを確かめる(`make TARGET=_X64_ KTEST=1 KTONLY=net,so,devob,pcdev,rump WIFI=1 sdimg`を`tools/x64/ktest64.sh`で`NET=user`)。アダプタの選択とWi-Fiの画面は`tools/x64/tests/ui_netadp.steps`を`tools/x64/ui_run64.py`で走らせて確かめる。virtio-netを選んで設定すると`NET_ADAPTER`が書かれてシステムが受け取り、自動に戻せること、ネットワーク設定の〈Ｗｉ－Ｆｉ〉がカードの無いことを示して部品を操作できなくすることを見る。

WPA2のハンドシェイクは、`tools/wpa/build.sh test`がホストで確かめる。カーネルと同じ`wpa_glue.c`とwpa_supplicantの状態機械を、同じリリースのhostapdの認証側(`src/ap/wpa_auth.c`)と組み、EAPOLのフレームを互いに渡して、ペアの鍵とグループの鍵がどちらもCCMPのもの、グループの鍵がTKIPのものの2通りで両側の鍵が一致すること、パスフレーズが違えばハンドシェイクが終わらないこと、PMKがIEEE 802.11の試験の値(パスフレーズ「password」、SSID「IEEE」)になることを見る。あわせて、接続の後の流れを見る。メッセージ1が失われたとき(アクセスポイントが送り直して終わる)、メッセージ4が失われたとき(メッセージ3がもう一度来て、答え直し、ペアの鍵は1回しか設定しない)、接続している間のグループの鍵の更新とペアの鍵の更新(2秒ごとに更新するアクセスポイントで、両側の新しい鍵が一致し、前の鍵と違う)、PMFを「使える」とするアクセスポイント(PMFなしで終わる)と「必須」とするアクセスポイント(始める前に断る)である。この試験で、2つ目のネットワークにつなぐとき前のネットワークの自分のRSNの要素が残る誤りを見つけて直した(`wpa_sm_set_assoc_wpa_ie`で先に消す)。M2の自分のRSNの要素が関連付けの要求のものと同じことは、hostapdの認証側がメッセージ2を受けたときに比べる(`wpa_auth.c`の`wpa_compare_rsn_ie`。違えばハンドシェイクを止める)ので、どの試験もハンドシェイクが終わることでそれを確かめている。

SAEとPMFに使う暗号とSAEそのものは、`tools/wpa/build.sh modtest`が、wpa_supplicant 2.11に入っている上流のmodule tests(`src/common/common_module_tests.c`と`src/crypto/crypto_module_tests.c`)を書き換えずに、カーネルと同じソースとMbed TLSで翻訳して走らせる。`sae_tests`はIEEE Std 802.11-2020のAnnex J.10の値で、hunting and peckingのCommit、KCK、PMK、PMKIDと、H2EのPTとPWE(群19と15)を確かめる。あわせて、802.11の要素の解析、GAS、RSNの要素の解析、OMAC1(BIP-CMAC-128が使うAES-CMAC)、AESの鍵の包み、MD5、SHA-1とPBKDF2、SHA-256、SHA-384、FIPS 186-2のPRF、HKDF、MS-CHAPv2の関数が通る。構成に無い群(SAE-PK、PASN、SIV、EAX、ECB、AES-CTR、HPKE)は飛ばされる。テストのリンクにだけ、上流の`gas.c`、`eloop.c`、`ms_funcs.c`と内部の`md4`、`des`、`fips_prf`、`sha1`の実装を足す(カーネルには入らない)。PMFのIGTKを扱う状態機械の流れ(`src/rsn_supp`)には上流のmodule testsが無い。

カードのドライバ(iwm、bwfm)とカードとのつなぎは実機でしか確かめられない。その上のWi-Fiの管理、net80211とのつなぎ、DHCPまでは、Wi-Fiのシミュレータ(9.6.12)でQEMUの中で確かめる。実機での確かめ方は`docs/x64-hw-test.md`にある。

### 9.6.8 Raspberry Pi 5のWi-Fi

Raspberry Pi 5のWi-Fi(CYW43455)は、BCM2712の2つ目のSDのホスト(`sdio2`、デバイスツリーの`/axi/mmc@1100000`)にSDIOでつながる。起動のディスクのSDカードのドライバ(`device/sd/sdhci.c`)は使わず、NetBSD 11.0のSD Host Controllerのドライバ`sdhc`とSD/SDIOの層`sdmmc`をrumpカーネルの中でこのホストに付け、チップをBroadcomのFullMACのドライバbwfm(4)で動かす。`sdhci.c`は1行も変えていない。Pi 5のビルドに既定で入り(`build_make/wifi_arm.mk`)、`make TARGET=_RPI5_ WIFI=0`で除ける。Pi 4とQEMU virtの既定のビルドには入らない。走査、接続(なし、WPA2-Personal)、DHCPは、x64と同じWi-Fiの管理(`device/net/wifi/wifi.c`、9.6.4、9.6.6)とWPA2の鍵の交換(`device/net/wifi/wpa/`、`tools/wpa/build.sh`の`ARCH=aarch64`で`~/tessronos-wpa-arm/wpasupp.o`)が行い、プロトコルスタックのカードはx64と同じカードの選択(`device/net/netsel.c`)とアダプタの管理(`device/net/netadp.c`)がボードのEthernetとWi-Fiから選ぶ(9.6.1)。Ethernetは機器の設定の`NET_ADAPTER`で`eth`と書く。システム環境設定の〈ネットワークアダプタ〉とネットワーク設定の〈Ｗｉ－Ｆｉ〉はx64と同じに使える。Wi-Fiの設定の実身「Ｗｉ－Ｆｉの設定」もPi 5のシステムボリュームに入る。

| 部分 | 置き場 | すること |
| --- | --- | --- |

ファームウェア、地域の規則(CLM)、基板の設定(NVRAM)は、linux-firmwareのタグ20260810から`tools/rpi5/wifi/fw.sh`が取り、SHA-256を確かめる。`tools/rpi5/wifi/mkobj.py`が次の3つの実身を作り、実身「システム」から結ぶ。

| --- | --- | --- |

| `cyfmac43455-sdio.clm_blob`(`SYSDEF_FW_BWFM43455_CLM`) | 同上 | 同上 |

基板の設定は、Wi-Fiの初期化が文章(xmlTAD)を読んで、bwfmが受け取る形のテキスト(`名前=値`の行)にして渡す(`knl_wifi_nvram`)。規則は次のとおりで、ホストの`tools/rpi5/wifi/nvram.py`と同じである。

- 段落(`<p>`)ごとに、その中の要素の文字も含めて文字を読む。文中の改行(`<br/>`)と段落の終わりが、どちらも行の終わり
- 「【注記】」で始まる段落は注記で、設定ではない

- 行の前後の空白を取り、空の行と`#`で始まる行は読み飛ばす。最初の`=`の前後の空白も取る
- それでもASCIIの印字できる文字以外が残る行と、`=`の無い行は、`wifi: nvram:`の行でコンソールに出して捨てる

bwfmは受け取ったテキストから空白とコメントを除き、チップに渡す形(NULで区切った並びと長さの語)にする。この変換は二重にしない。

1回の起動で、どこまで進んだかがコンソール(COM3)の`wifi:`の行で分かる。ホスト(レジスタ、割込み、クロック)、ピンの制御の段階(c0かd0か)と設定した後の値、チップの電源の前の状態と入れた後、cfgのレジスタの前後、オブジェクトの層が開いたこと、bwfmが求めた各ファイルの大きさ(基板の設定は取り出した設定の大きさと捨てた行の数)、`bwfm0`のMACアドレスと、そこまでとその10秒後のホストの割込みの数である。あわせて、rumpカーネルの装置の付き方(`tssdhc0 at mainbus0`、`sdmmc0 at tssdhc0`、`bwfm0 at sdmmc0`)と、bwfmとsdhcの言うこと(`aprint_verbose`の分も出す)が出る。

#### チップのsupplicant、PMF、WPA3、ローミング、速さ

CYW43455のファームウェア7.45.234は、自分のsupplicant(`idsup`)、管理フレームの保護(`mfp`)、WPA3のSAE(`sae`)、ローミング(`roamprof`、`okc`)を持つ。機能の文字列(`cap`のiovar)は`... mfp ... idsup idauth ... roamprof ... sae dpp sr okc ...`である。外部認証(`sae_ext`、SAEの認証フレームをホストが作る形)は持たない。そこで、鍵のあるネットワークへの参加は、ホストのwpa_supplicantの状態機械ではなく、チップのsupplicantに任せる。Linuxのbrcmfmacも、このファームウェアではチップのsupplicantでSAEとPMFを使う(`sae_ext`のあるファームウェアだけがホストのSAEを使う)。

- 管理のタスクは、カードを上げた後に`rump_tswifi_fw_caps`でチップの能力を1回読む。機械の種類ではなく、この能力で手順を選ぶ。チップのsupplicantを持つカード(`FW_IDSUP`)では、WPA2のネットワークへの参加のとき、ホストの状態機械を始めず、関連付けの要求のRSNの要素も渡さず(`rump_tswifi_optie(NULL, 0)`)、保存してある鍵(PMK)を`rump_tswifi_fw_keys`で渡す。SAEのパスワードを渡す口も同じ関数にある(このファームウェアはSAEにパスワードそのものを要るので、Pi 5ではWPA3のネットワークのパスワードを保存しておく必要がある。9.6.9)。
- 参加の直前に、bwfmの`bwfm_connect`が当て(9.6.2)で`tswifi_bwfm_join`を呼ぶ。そこで、走査のノードのアクセスポイントのRSNの要素から鍵の管理を選ぶ。アクセスポイントがSAEを出していて、パスワードがあればSAE、そうでなければPSK(無ければPSK-SHA256)である。PMFは、アクセスポイントが必須とするか、SAEなら「必須」、アクセスポイントが使えるとするなら「使う」とする。そのうえで、`wpaie`(自分のRSNの要素)、`wpa_auth`(PSKは0x80、PSK-SHA256は0x8000、SAEは0x40000)、`wsec`、`auth`(SAEは3)、`mfp`、鍵(PSKは`BWFM_C_SET_WSEC_PMK`でPMKそのもの、SAEは`sae_password`)、`sup_wpa`(1)の順に書く。書いた鍵とパスワードの写しは、書いたらすぐ0で消す。チップはSAEの交換、4ウェイとグループ鍵のハンドシェイク、鍵(BIPの完全性の鍵を含む)の設定を自分で行う。
- 管理のタスクは、ハンドシェイクの段階で0.5秒ごとに`rump_tswifi_fw_link`を読み、アクセスポイントの項目(`sta_info`)が「認可済み」(`BWFM_STA_AUTHO`)になったら接続済みとする。チップのsupplicantの間に来たEAPOLは、ホストの状態機械には渡さない。
- ローミングはチップが行う。チップのsupplicantで参加したときと暗号の無いネットワークでは`roam_off`を0にし、電波が-75 dBmより弱くなったら20 dB強いアクセスポイントへ移る(`BWFM_C_SET_ROAM_TRIGGER`、`BWFM_C_SET_ROAM_DELTA`。Linuxのbrcmfmacの既定と同じ値)。移った後のハンドシェイクもチップがやり直す。ホストの4ウェイで参加したときは、ホストの鍵がローミングについて行けないので`roam_off`を1にする。管理のタスクは接続している間2秒ごとにチップのBSSIDを読み、変わったら`wifi: roam: <前のBSSID> -> <新しいBSSID>, <dBm>, <MHz>`の行を出す。
- 速さは、チップのファームウェアが802.11nと802.11acの中から選ぶ。`wifi: link:`の行には、`sta_info`の送受の最後の速さ(Mb/s)と、802.11n、802.11acのどちらで関連付けたか、RSSI(`BWFM_C_GET_RSSI`)、周波数(`BWFM_C_GET_CHANNEL`)、鍵が入っているか、ローミングの回数を出す。チップのsupplicantでつないでいる間は、wlan0のレコード1の`SIGNAL`と`RATE`も、この2秒ごとに読むチップの値(RSSIと送信の速さ)にする。チップが自分で速さを選びローミングもするので、net80211の値は追いつかない。接続の直後でまだチップから読んでいないとき、またはチップが値を返さなかったとき(`sta_info`のバージョンが3より前)は、net80211の値を出す。
- チップのイベントのうち、参加と離脱(`set_ssid`、`auth`、`assoc`、`reassoc`、`deauth`、`disassoc`とその`_ind`)、`link`、`roam`、`psk_sup`(チップのsupplicantの状態。6で鍵が入った)は、当てで`tswifi_bwfm_event`がbwfmより先に受け、`bwfm: event`の行に状態、理由、相手のアドレスを出す。`psk_sup`と`roam`は、参加の直前にイベントのマスクに足す。

ホストの4ウェイの手順(9.6.4)は、チップのsupplicantを持たないカード(x64のiwm)と、能力を読めなかったときのためにそのまま残す。

#### 実機での確かめ方

QEMUにはチップが無いので、次のことはPi 5の実機で1回にまとめて確かめる。コンソールはCOM3(Debug Probe、115200)で、`C:\tmp\com3_read.ps1`を切り離して起こし、`[com3 opened]`が出てから電源を入れる。

1. 起動の後、`bwfm: firmware ...`、`bwfm: capabilities: ...`、`bwfm: the chip's supplicant yes, SAE yes, PMF yes`と、`wifi: the card's firmware: its own supplicant yes, ...`の行が出るか。
2. WPA2-Personalのアクセスポイントに〈接続〉し、`bwfm: join: the chip's supplicant, PSK (WPA2-Personal), group CCMP, PMF ...`の行の括弧の中の7つの数がすべて0か(それぞれの設定をチップが受けたか)、`bwfm: the chip's roaming on ...`の3つの数が0か、`bwfm: event psk_sup, status 6`と`wifi: the card's supplicant has the keys: connected`が出るか。DHCPでアドレスが取れて、外とつながるか。
3. PMFを「必須」にしたアクセスポイント(できればWPA3とWPA2の両方を受け付ける設定と、WPA3だけの設定の両方)で、`PMF required`で参加できるか。WPA3だけのアクセスポイントは、パスワードを保存する口ができてから(9.6.9)`SAE (WPA3-Personal)`で確かめる。
4. 3分以上つないだまま使い、1分ごとの`wifi: link:`の行に802.11nか802.11acと、54 Mb/sを超える速さが出るか。
5. 同じSSIDのアクセスポイントが2台あれば、一方の近くでつないでから他方の近くへ移り、`bwfm: event roam, status 0`と`wifi: roam: ... -> ...`が出て、つながったままか(`wifi: the network was lost`が出ないか)。
6. わざと違うパスワードで〈接続〉し、`bwfm: event psk_sup`の状態と、`wifi: the card's supplicant did not end the handshakes`の行が出て、「パスワードが違う可能性があります」になるか。
7. 失敗したときは、`bwfm: join:`の行の括弧の中の数(0でないものの位置。順に`wpaie`、`wpa_auth`、`wsec`、`auth`、`mfp`、鍵、`sup_wpa`)と、`bwfm: event`の行の状態と理由を持ち帰る。

試験。QEMU virtは`make TARGET=_QEMU_VIRT_ WIFI=1`でWi-Fiの部分を入れて走らせられる。ホストのノードが無いので`wifi: no Wi-Fi host`の1行だけを出して何も触らず、`net`、`so`、`rump`の群が通ることを確かめる。基板の設定の取り出しは、群`wifinv`(`tests/ktest/ktest_wifinv.c`、`WIFI=1`のときだけ入る)が、注記、コメント、空の行、全角、文中の改行、設定でない行、参照(`&amp;`)の文章と、システムボリュームの実身(79の設定)で確かめ、`tools/rpi5/wifi/test_nvram.py`がホストで同じ文章と元のテキストとの突き合わせを確かめる。アダプタの選択とWi-Fiの画面は、`make TARGET=_QEMU_VIRT_ DESKTOP=1 UITEST=1 WIFI=1`のカーネルと`KTEST=1 WIFI=1`の試験のディスクで`tools/tests/ui_netadp.steps`を`tools/ui_run.py`で走らせて確かめる(x64と同じ手順で、アダプタの名前が`eth`)。ホスト、チップ、ファームウェア、走査と接続は実機でしか確かめられない。

### 9.6.9 OpenBSDの802.11の層(`WIFI_NET80211=obsd`)

NetBSD 11.0のiwmとnet80211には、802.11n、PMF(802.11w)、接続している間の走査、より強いアクセスポイントへの移動の手段が無い(9.6.2、9.6.4の20.、`docs/private/wifi_flow_review.md`の5、14、19)。R1.200の前にこれを埋めるため、2026-10-23に次の3つを比べた。

#### 組み方

x64のPCの802.11の層とドライバは、OpenBSD 8.0のnet80211とiwmである(`WIFI_NET80211=obsd`、ただ一つの形)。前はNetBSDのもの(`WIFI_NET80211=nbsd`)が既定だったが、OpenBSDの層が実機でつながり(ThinkPad X1 Yoga 第3世代で802.11n MCS 15、144 Mb/sまで)、NetBSDの形は除いた(2026-10-23)。Raspberry Pi 5はNetBSDのbwfmのまま、PMF、SAE、ローミングをチップのファームウェアに頼む(9.6.8)。

| --- | --- | --- |

OpenBSDのコードをNetBSDのrumpカーネルの中に入れなかったのは、`struct ifnet`、`ifq`、mbuf、`spl`の作りが違い、同じ翻訳単位に両方のヘッダを入れられないからである。rumpカーネルから借りたかったPCI、DMA、割込み、ファームウェアの読込みは、もともとTessronOSのハイパーコールなので、層はそれを直接呼ぶ。

#### 層(`device/net/wifi/obsd/`)

層は、OpenBSDのカーネルがドライバとnet80211に与えるものを、TessronOSの上で用意する。

- 排他。OpenBSDのカーネルロックと同じく、層の関数はすべて1つのロック(`obsd_lock`、同じタスクなら重ねて取れる)を持って動く。管理のタスクの呼出し、カードの割込み、タイムアウト、タスクキューは、それぞれTessronOSのタスクで、そのロックを取って走る。`tsleep_nsec`はロックを手放して待ち、取り直す。iwmはファームウェアに命令を送ると、答えの割込みを眠って待つので、その間にほかのタスクが進む。割込みのレベル(`splnet`)とミューテックスは何もしない(ロックを持たずに動くものが無い)
- 眠りと目覚め(`tsleep_nsec`、`wakeup`)、タイムアウト(`timeout_*`、期限の順の1本の列と1つのタスク)、タスクキュー(`taskq_create`、`task_add`。キューごとに1つのタスク)、読み書きのロック(`rw_enter`。持ち主が眠っている間、ほかは眠って待つ)、参照の数(`refcnt_*`)
- メモリ。`malloc`はカーネルのヒープ。mbufのプール(`pool_get`)は、クラスタの大きさ(2048バイト)以上のものを、ページアロケータの物理的に続いた4GB未満のページから取る。カードはクラスタを1つの区切りとしてDMAで読み書きするためである
- `bus_dma`。カーネルの直写像のアドレスを、ページごとに`rumpcomp_pci_virt_to_mach`で物理アドレスにし、続いたページを1つの区切りにまとめる。`bus_dmamem_alloc`は`rumpcomp_pci_dmalloc`
- PCI。構成空間、能力のリスト、BARの写像(`pci_mapreg_map`)、MSIの割込み(1つのタスクが割込みを待ってドライバのハンドラを呼ぶ)。MSI-Xとピンの割込みは無いとする。iwxはMSI-Xが無ければMSIを使う(`iwx_intr`と割込みの原因の表)
- ネットワークのインタフェース。`iwm0`(iwxのカードでは`iwx0`)はどのスタックにも入らない。送信の列(`ifq`、256個)、`if_start`(すぐにドライバの送信を呼ぶ)、`if_input`(受けたEthernetのフレームを`rumpcomp_tswifi_input`、つまり管理のタスクの`knl_wifi_rx`に渡す)、1秒ごとの見張り(`if_timer`と`if_watchdog`、OpenBSDの`if_slowtimo`と同じ)
- ファームウェア(`loadfirmware`)。iwmの求める`iwm-8265-36`の名前で、システムボリュームの実身`SYSDEF_FW_IWM8265_36`を、iwxの求める`iwx-cc-a0-77`の名前で`SYSDEF_FW_IWXCC_77`を読む(9.6.5)
- コンソール。層の`printf`は行にまとめて出す。OpenBSDの`%b`も読む

#### 管理のタスクとのつなぎ(`tswifi_obsd.c`)

NetBSDの層では、管理のタスクがアクセスポイントのBSSIDまで選んで関連付けを頼み、ローミングを自分で決めていた(`IEEE80211_ROAMING_MANUAL`)。OpenBSDの層では、OpenBSDの`ifconfig join`と同じく、管理のタスクはネットワーク(SSID、セキュリティ、鍵)を名指すだけで、どのアクセスポイントにつなぐか、いつ移るかは層が決める。何も名指していない間、層は走査を続け、何にもつながない(望むSSIDが無いと`ieee80211_match_bss`がどれも選ばない)。

1. 走査。層が走査を終えるたび(`ieee80211_end_scan`をリンクの`--wrap`で包む)、数を1つ増やして管理のタスクを起こす。管理のタスクはその数が変わるたびに結果(`rump_tswifi_results`、net80211の木のノード)を取り、保存したネットワークを選ぶ(9.6.4の3.と同じ規則)。〈走査〉の指示は、接続している間は背景の走査(`ieee80211_begin_bgscan`)になる
2. 参加(`ob_join`、`rump_tswifi_join`)。SSID、RSNを使うか、許すAKM(WPA2はPSKとPSK-SHA256、WPA3はSAE、両方なら全部)、PMFを必須にするか(WPA3)、PMKを層に渡す
3. 認証の前。層がアクセスポイントを選び、認証のフレーム(シーケンス1)を送るところ(`ic_send_mgmt`を包む)で止め、知らせ(`TSW_EV_AUTH`とBSSID)を残す。管理のタスクは、そのアクセスポイントのRSNの要素とRSNXE(ビーコンとプローブ応答から層が控えたもの。`ic_recv_mgmt`を包む)で、`knl_wpa_choose`(9.6.6)にAKM、PMF、H2Eを決めさせる。合わなければ層に断らせ(`rump_tswifi_auth_fail`)、層は別のアクセスポイントを探す
4. PSK。`knl_wpa_start2`で関連付けの要求に入れる自分のRSNの要素を作り(`rump_tswifi_optie`)、止めていた開放の認証を出させる(`rump_tswifi_auth_go`)
5. SAE。`knl_wpa_sae_start`が作るコミットを、認証の方式3のフレームで送る(`rump_tswifi_auth_send`)。アクセスポイントのフレームは層には渡さず(層はSAEを知らない)知らせ(`TSW_EV_FRAME`)にし、`knl_wpa_sae_rx`の答えを送り返す。1秒答えが無ければ`knl_wpa_sae_resend`。受け入れられたら、SAEのPMKとPMKIDで`knl_wpa_start2`を呼び、層を関連付けに進める(`rump_tswifi_auth_done`)
6. 関連付けの要求。層が作る要求のRSNの要素を、管理のタスクの要素に差し替え、RSNXE(H2E)は最後に足す(`send_assoc`)。層はSAEのAKMもRSNXEも作れないためで、4ウェイハンドシェイクのメッセージ2の要素と同じバイト列でなければならない
7. 鍵の交換。EAPOLの鍵のフレームは、層の4ウェイハンドシェイク(`ieee80211_eapol_key_input`)に渡さず、リンクの`--wrap`で包んで管理のタスクに回す。状態機械はNetBSDの層と同じwpa_supplicantのもの(9.6.4の7.〜11.、9.6.7のホストのテスト)である。鍵は層のハンドシェイクと同じ形で設定する(`rump_tswifi_setkey`。ペアの鍵は送受の保護の印も立てる。グループの鍵、管理フレームの保護のIGTKはBIP、番号4か5)。終わったらポートを有効にする(`rump_tswifi_port`)
8. ローミング。接続している間、電波が弱くなると層は背景の走査をし、より良いアクセスポイントがあれば移る(iwm_bgscan、`ieee80211_node_switch_bss`)。移る先への認証の前に3.の知らせが来るので、管理のタスクは前と今のBSSIDを`wifi: roam:`の行に出し(Raspberry Pi 5と同じ形)、鍵の交換をやり直す。背景の走査を始める時は、層の`ic_bgscan_start`を包んで決める(`tsw_bgscan_start`)。層は、閾値(2.4GHzはカードの幅の60%、5GHzは50%。iwmでは2.4GHzで-59dBm)より弱い信号のフレームを受けてから500ミリ秒で走査を始める。そのため、接続の直後に走査が始まり、DHCPの答えを取りこぼしていた(X1 Yogaの実機。-71dBmのAPにつながった0.15秒後に走査が始まり、OFFERが来なかった)。走査の長さは上流と同じで、カードはチャネルを1回に120ミリ秒まで離れて120ミリ秒戻ることをくり返し、全部のチャネルで約10秒かかる(`iwm_umac_scan`の`max_out_time`と`suspend_time`)。Linuxのwpa_supplicantの背景の走査(`bgscan simple`、NetworkManagerは短い間隔30秒)は、接続の直後には走査せず、最初の走査は短い間隔の後で、信号が閾値より弱いときだけである。これに合わせて、ポートが開いてから30秒の間と、前の背景の走査から30秒の間は始めない。DHCPのDISCOVERかREQUESTが答えを待っている間(送ってから、クライアントが送り直すまでの最も長い待ちの33秒まで。REQUESTは4秒、8秒、16秒、32秒の待ちで送り直す(9.3.1)。1回りの問い合わせで最大60秒)も始めない。答えが全員宛てなら、APはDTIMのビーコンの後に送り、局がチャネルを離れていれば受け取れないからである。管理のタスクの〈走査〉の指示(利用者の走査)は待たせない。止めた理由は変わるたびに`wifi: background scan put off: ...`の行に出す。閾値と、空振りのたびに間隔を延ばす動き(`ic_bgscan_fail`)は層のままである
9. 切断。アクセスポイントに離脱させられるかビーコンを見失うと、層は自分で探し直す。管理のタスクは`wifi: the network was lost ... the layer looks for it again`を出して30秒待ち、それでもつながらなければあきらめて(`REASON lost`)走査の結果から選び直す
10. 離れること(〈切断〉、別のネットワーク、設定の`off`)は`rump_tswifi_deauth`で、認証の解除を送り、望むSSIDを消す

OpenBSDのソースへのパッチは、下の「送るデータのQoSとブロックACK」と「iwx」の2つだけである。層の関数で包む所は、`ic_send_mgmt`、`ic_recv_mgmt`、`ic_newstate`、`ic_bgscan_start`(関数のポインタ)と、`ieee80211_end_scan`、`ieee80211_eapol_key_input`、`ieee80211_inputm`、`ieee80211_encap`、`ieee80211_node_trigger_addba_req`(リンクの`--wrap`)だけである。iwmでは、ペアの鍵を、`iwm_set_key`と同じADD_STA_KEYの命令で、答えを待つ形で送る(`tsw_iwm.c`の`iwm_t_ptk_to_card`。下のログ)。

パスフレーズが違うと、APはメッセージ2のMICの誤りで局を離れさせ、層は自分からすぐに関連付け直す。前は管理のタスクが「handshake -> joining」をくり返すだけで、いつまでもつなぎ直していた(シミュレータで見つけた)。今はwpa_supplicantと同じ判定と時間で扱う。参加の最初の4ウェイハンドシェイクの途中で接続が切れ(層がRUNから離れたか、層が認証をやり直し始めた。`step_obsd`と`ob_auth`の`ob_wrong_key`)、鍵の管理がPSK(SAEでない)なら、鍵の誤りとして(`events.c`の`could_be_psk_mismatch`と同じ)`wifi: WPA: 4-Way Handshake failed - pre-shared key may be incorrect`を出し、そのネットワークの失敗を数えて一時的に外す(`wpa_supplicant.c`の`wpas_auth_failed`と同じ。1回目は10秒、2回目は20秒、3回目は30秒、4、5回目は60秒、6〜10回目は90秒、11〜50回目は120秒、それより多いと300秒。すでにそれより後まで外していればそのまま)。外したことは`wifi: "<SSID>" is left for N s (CTRL-EVENT-SSID-TEMP-DISABLED auth_failures=K reason=WRONG_KEY)`の行に出し、`REASON password`にする。自分から関連付け直す層の動きは、`rump_tswifi_deauth`で求めるESSIDを消して止め、外している間は接続先の選択(`choose`)がそのネットワークを選ばない。時間が過ぎると外すのをやめ(数は残す。`wpas_temp_disabled`)、接続まで進むと数も消す(`wpas_clear_temp_disabled`の`clear_failures`)。名指しの`CONNECT <SSID>`も、そのネットワークを外すのをやめ数を消す(`wpa_supplicant_select_network`)。ほかの失敗の待ち(`failed_at`、`RETRY_MS`)は、この場合には数えない。

#### 速さ、電源の節約

802.11nと802.11ac(8265はVHT80、2本の流れ、MCS 0〜9)は、iwmとnet80211がそのまま使う。速さの選び方はnet80211のMiRA(`ieee80211_ra.c`、`ieee80211_ra_vht.c`)。wlan0の`RATE`とアダプタの一覧の速さは、HTとVHTのMCS、流れの数、帯域の幅、ショートガードインターバルから求める。電源の節約はOpenBSDのiwmのまま(`iwm_power_update_device`)である。iwmは、装置の電源の命令(`IWM_POWER_TABLE_CMD`)とMACの電源の表(`IWM_MAC_PM_POWER_TABLE`)に`POWER_SAVE_ENA`だけを立て、`POWER_MANAGEMENT_ENA`は立てない(`iwm_power_build_cmd`)。Linuxのiwlmvmで、mac80211が省電力を許していない時(`vif->cfg.ps`が偽)と同じ形で、カードは起きたまま(CAM)である。層の省電力(`IEEE80211_F_PMGTON`)も切ってある。ポートが開いた時に`wifi: power:`の行に、層の省電力、関連付けの要求のlisten interval、APのビーコンの間隔、DTIMの周期、AIDを出す。その後の最初のビーコン5つと、局のAIDのビットが立ったビーコンを`wifi: beacon of ...`の行に出し(TIMの要素。APが局を眠っているとみて局宛てをためているか)、最初のデータフレーム4つを電源の管理のビットとともに`wifi: sent: ...`の行に出す(`ieee80211_encap`をリンクの`--wrap`で包む)。ARPの送りと、受けた答えと、DHCPが与えたアドレスへの問い合わせも`wifi: ARP ...`の行に出す(接続ごとに24行まで)。

#### ログ

各段階をコンソールと`KERNEL.TXT`に出す。`obsd: BAR`(カードの窓)、`iwm0 at pci2 dev 0 function 0, msi 1`、`iwm0: hw rev ..., fw ver 36..., address ...`(ファームウェアとNVMが読めた)、`wifi: joining "SSID" (...; the layer chooses its access point, ...)`、`wifi: authenticating with <BSSID>: PSK, PMF ...`か`SAE (H2E) ... commit sent`、`wifi: SAE in: commit/confirm ...`、`wifi: SAE done: associating`、EAPOLの鍵のフレームの送受(9.6.3と同じ)、`wifi: ... key set (CCMP/BIP ...)`、`wifi: roam: <前> -> <今>, <dBm>, <MHz>`、1分ごとの`wifi: link: <dBm>, <速さ> (802.11ac MCS 9, 2 streams, 80 MHz, short GI), <MHz>, PMF on, ..., background scans N, roams N`。ネットワークを名指している間(参加の途中と接続している間)は、層の言うこと(OpenBSDの`IFF_DEBUG`の出力。状態の移り、送った管理フレーム、走査の候補、`begin background scan`、`roaming from ... to ...`)も出す。何も名指していない間は、走査のたびに全部のネットワークを並べるので止める。

`wifi:`と`net:`で始まる行(Wi-Fiの管理、アダプタの管理、DHCP)と層の行(`iwm0:`など)には、起動からの秒(ミリ秒まで)を前に付ける(`12.345 wifi: ...`。`peripheral_kernel/network/netbsd/netlog.h`が、その3つのファイルの`tm_printf`と`tm_putstring`を、コンソールの鍵の中で時刻と行を一続きに出すものに替える)。接続の手順、背景の走査、DHCPのメッセージがどれだけ離れていたかを実機の記録から読むためである。あわせて、参加の1回ごとに、層が送ろうとした開いた認証を管理のタスクのために止めてから、RUNになるか参加が終わるまでを`wifi: join timed:`の行に出す。止めた時(iwmのセッションの保護の時間のイベントが張られているかと、その長さ。`iwm_auth`がビーコンの間隔の2倍で張る)、管理のタスクが送らせた時、層の状態の移り(APの答え)、時間のイベントが終わった時を、止めた時からのミリ秒と、そのとき時間のイベントが張られているかで出す。時間のイベントの終わりは、管理のタスクのループ(参加の間は20ミリ秒ごと)で見る(`rump_tswifi_trace`)。参加していない間は出さない。APの認証の答え(方式、シーケンス、状態の番号)と関連付けの答え(状態の番号)も、同じ行に出す。各行には、最後に送った管理フレーム(認証か関連付けの要求)がどうなったかを、iwmがカードの送信の結果から数えるもので添える。APのACKが来ずカードがあきらめた数(`if_oerrors`の増え)、速さの制御が送り直しと見た数(`amn_retrycnt`)、管理フレームのキューにまだ残っている数である。ACKがあってキューも空ならAPは聞いて答えなかった、ACKが無ければAPに届いていない、キューに残れば、カードが送っていない(チャネルやPHYのコンテキスト)。iwmが状態の番号そのものを数えないので、層の数から読む。認証の解除と関連付けの解除を受けたら、送り元、BSSID、理由の番号、そのときの層の状態を`wifi: deauthentication from ...`の行に出す。層の状態の移りの`AUTH -> AUTH`は、認証の途中で認証の解除を受けた時である(`ieee80211_recv_deauth`が`IEEE80211_FC0_SUBTYPE_DEAUTH`でAUTHに移し、AUTHからAUTHへの移りでは何も送らず、認証のタイムアウトを待って走査し直す)。ローミングでは、層が前のAPに認証の解除を送ってから新しいAPに認証を送る。

DHCPのメッセージは、両方向とも層のところで`wifi: DHCP in:`と`wifi: DHCP out:`の行に出す(`tsw_dhcp_frame`)。種類、トランザクションID、ブロードキャストの印、ciaddr、yiaddr、chaddr、求めたアドレス、サーバの識別子と、フレームの送り元と宛先、宛先が自分だけ(ペアの鍵で暗号化)か全員(グループの鍵)かである。スタックの手前で、何を頼み何が返ったかが分かる。接続している間は10秒ごとに、変わっていれば、受けたフレームの数と捨てた数を理由ごとに`wifi: receive:`の行に出す(`rxs_tick`)。iwmが層に渡したフレーム(`ieee80211_inputm`をリンクの`--wrap`で包み、層の検査の前に数える)の、局宛てのデータ(そのうち保護されたもの、カードが復号したもの)、全員宛てのデータ、局宛ての管理フレーム、スタックに渡した自分宛てと全員宛ての数、復号の失敗(カードのCCMPの復号の状態)、リプレイ(パケット番号が前より大きくない)、ポートが開いていない、ブロックACKの並べ直し(窓より前、失われた、すき間の時間切れ、合意の数)、重複、別のBSS、暗号化されていない、取り出しの失敗、mbufの不足、iwmの受信の誤り、送信の失敗である。自分宛てのフレームがスタックに届かなければ、どれかの数が増える。iwmが層に渡した局宛てのデータが増えなければ、フレームは層より下で捨てられている(カードのファームウェアのアドレスの選別か復号、`iwm_rx_mpdu`のCRCとオーバーランの状態の検査。後者は数えない)。そのため、カード自身の数(最後の統計の通知。iwmが`sc_stats`に持つ)も同じ時に出す。OFDM、CCK、HTの速さごとの正しく受けた数、CRCの誤り、PLCPの誤り、HTの扱えないMCSと集約、局宛てと見たデータ、選別で捨てた数、別のBSSIDの数、ビーコンとその見失い、送ったACKとブロックACKの答えである。ただし、この統計の構造体はOpenBSDのもの(通知の版8)で、版36のファームウェアの並びと合っている保証は無い。iwmが落とす前の受信のバッファも、iwmが読み始める時(`iwm_rx_pkt`がバッファを同期する`bus_dmamap_sync`。`obsd_pci.c`の`dm_sync`からドライバの`rx_peek`(iwmは`tsw_iwm.c`の`iwm_t_rx_peek`)を呼ぶ)に読む。カードが書いたMPDUごとに、802.11のヘッダと後ろのカードの状態(CRC、オーバーラン、ステーションが見つかったか、鍵が有効か、ICV、MIC、見つけた暗号、復号できたか、ステーションの番号)を見て、局宛てのものを数え、ポートが開いた後の保護された最初の6つを`wifi: the card received: ...`の行に出す(直前のPHYの情報の速さも)。iwmが`iwm_rx_mpdu`のCRCの検査で黙って捨てるものも、ここで分かる。接続のあと、カードが渡した局宛てのデータの最初の4つは、宛先、送り元、保護、カードの復号、受信の印、シーケンス番号を`wifi: from the card:`の行に出す。ペアの鍵をカードに入れた結果は`wifi: the card's pairwise key: ADD_STA_KEY ...`の行に出す(命令の版と大きさ、ステーションの番号、鍵の位置、鍵の印、番号、誤りとカードの状態の値、かかった時間)。カードは局宛てに来たものを自分の持つ鍵で復号し、局が送るものは送るたびに命令に添えた鍵で暗号化する(`iwm_tx`)ので、カードが鍵を受け取っていないと、受信にだけ表れる。グループの鍵は層のソフトウェアが持つ(`iwm_set_key`)。APのブロックACKの合意の要求、答え、終わりは`wifi: block ack: ...`の行に出す。層の行は510文字で切る(`obsd_kern.c`。前は254文字で、`wifi: receive:`の行が途中で切れていた)。

#### 送るデータのQoSとブロックACK

OpenBSDのnet80211は、送るデータのブロックACKの取り決めができるまで、そのTIDのデータをQoSの欄の無いフレームで送る(「QoSデータはアグリゲーションにだけ使う」)。そのフレームのシーケンス番号は、管理フレームと共用の数え方でカードのファームウェアが振る。取り決めの後の最初のQoSデータで、TIDの数え方が0から始まり、取り決めの始めの番号(ADDBAのSSN)も0になる。そのため、アクセスポイントから見た局のデータのシーケンス番号は、取り決めのところで0に戻る。ThinkPad X1 Yogaとメッシュのアクセスポイントf4:d5:80:31:fc:d0(hw11o)では、QoSの欄の無いフレームが3〜7、取り決めの後に集約の待ち行列で0、1、2…となった。それ以後、アクセスポイントはどのフレームにもACKを返したのに、ほとんどがネットワークに届かなかった(DHCPのREQUESTに30秒答えが無く、局宛てのフレームも1つも来なかった)。同じ形で通ったアクセスポイントac:44:f2:1e:7b:d8もあるので、QoSの欄の無いフレームとTID 0の受けた番号を1つの記録で持つアクセスポイントだと、この形で落ちる、という見込みである。

Linuxのmac80211は、QoSのピアへのデータを関連付けの直後からすべてQoSデータで送り(`ieee80211_build_hdr`、局のWMEの印)、TIDごとの数え方で番号を振り(`ieee80211_tx_h_sequence`)、EAPOLは優先度7で送る。iwlwifiは、取り決めをそのTIDの次の番号から始める(`iwl_mvm_sta_tx_agg_start`の`ssn`は`tid_data->seq_number`)。取り決めを求めている間のそのTIDのフレームは、mac80211が取っておく(`ieee80211_tx_prep_agg`)。TessronOSもこれに合わせた。

iwxでは、この形にしない。iwxのカード(AX200など)の送信の命令(`iwx_tx_cmd_gen2`、`_gen3`)は、ステーションもTIDも持たない。ファームウェアの待ち行列は、有効にする時(`iwx_enable_txq`、`iwx_tx_queue_cfg_cmd`)に1つのステーションと1つのTIDに結ばれる。TIDが自分の待ち行列を持つのは、取り決めのために`iwx_sta_tx_agg_start`が有効にしてからで、それまで`iwx_tx`はそのTIDのフレームを、管理のTID(`IWX_MGMT_TID`)に結ばれた最初のデータの待ち行列に積む。そこにTID 7や0のQoSデータを積む形は、リリースのiwxもiwlwifiも作らない(iwlwifiはこのファームウェアで、TIDの最初のQoSフレームの前にTIDの待ち行列を作る)。前はiwxにもパッチの形を当てていて、Surface Go 2のAX200は、iwmのつながるアクセスポイントf4:d5:80:31:fc:d0で、EAPOLのメッセージ2を4回送ってもアクセスポイントがメッセージ1を送り直し続け、4秒後に理由15(4ウェイハンドシェイクのタイムアウト)で離された(2026-10-28の実機のログ)。iwmは送信の命令にTIDを書く(`tid_tspec`)ので、この違いは無い。そこで、パッチは`IEEE80211_C_ADDBA_OFFLOAD`のときリリースの形に戻す。取り決めができるまでQoSの欄を付けず、EAPOLには付けない。取り決めを求める時期と取っておきは、iwmと同じである。

- `tools/openbsd/patches/ieee80211_output-qos-data.patch`: QoSのピアへのデータを、関連付けの直後からすべてQoSデータにする。EAPOLはTID 7で送り、取り決めは求めない。ただし、取り決めをカードのファームウェアが結ぶドライバ(`IEEE80211_C_ADDBA_OFFLOAD`、iwx)では、リリースの形のままにする(下の「iwx」)。
- 取り決めを求める時期(`tswifi_obsd.c`の`ieee80211_node_trigger_addba_req`の包み): ポートが開いた後に、そのTIDのフレームが1秒に10個以上になってから求める。iwlwifiの`rs_tl_turn_on_agg`(局が認証済み、`IWL_MVM_RS_AGG_START_THRESHOLD`の毎秒10フレーム)と同じで、接続の直後のDHCPの数フレームやEAPOLでは求めない。前は、データが1つあれば1秒後に求めていた。
- 取り決めを求めてから答えが来るまで、そのTIDのフレームを取っておき、答えが来たら(または失敗したら)順に送る(`rump_tswifi_send`、64個まで、2秒まで)。その間にも送ると、そのTIDの番号を使ってしまい、取り決めはSSNから始まる(net80211はTIDの数え方をSSNに戻し、iwmの集約の待ち行列もSSNから始まる)ので、同じ番号が二度出る。
- ログ: `wifi: block ack: an agreement for TID N to be asked for, after N frames in a second; the TID's next sequence number S`、`wifi: block ack: the agreement for what the station sends on TID N: status 0, starting at S, the TID's next sequence number S`(2つのSは同じになる)、`wifi: block ack: N frames of TID 0 held N ms while the agreement was asked for, sent`、カードの送信の答え`wifi: the card sent: queue Q, ..., TID T, sequence S, N ms after the port opened`(ポートが開いてから16個)。iwxでは、関連付けからポートが開くまで(4ウェイハンドシェイクのEAPOL)の答えも、`..., during the handshake`の形で接続ごとに8個まで出す。メッセージ2と4がアクセスポイントにACKされたか、送り直しの上限で失敗したか、カードが送らなかったかが分かる。

Wi-Fiのシミュレータは、両方の無線を802.11nとQoSとA-MPDUの送信つきにしたので、局が取り決めを求め、アクセスポイントのnet80211が取り決めの窓で並べ直し、窓より古いものと重複を捨てる(`ieee80211_input_ba`)。`seqshare on`で、アクセスポイントが、QoSの欄の無いデータとTID 0の受けた番号を1つの記録で持ち、その最後より後でないTID 0のQoSデータを捨てる形にできる。群`wifisim`の`agg`は、`seqshare on`のアクセスポイントで、DHCPでは取り決めを求めないこと、データが増えると取り決めができること、その始めの番号がTIDの次の番号と同じこと、アクセスポイントが古いとして捨てたものも1つの記録で捨てたものも0であることを確かめる。前の形(パッチなし)では、同じテストで取り決めが0から始まり、捨てられたものが14個、エコーは10個中0個だった。

#### 受けたフレームのPNの検査と並べ直しの順番

Linuxのiwlwifiとmac80211は、受けたフレームを、重複の検査(`iwl_mvm_is_dup`、`ieee80211_rx_h_check_dup`)、ブロックACKの並べ直し(`iwl_mvm_reorder`、`ieee80211_rx_reorder_ampdu`)、PNの検査(`iwl_mvm_check_pn`、`ieee80211_crypto_ccmp_decrypt`)の順に扱う。PNはTIDごとに持つ。OpenBSDのiwm(8265は待ち行列の多い受信を持たない)は、カードで復号したフレームのPNを、まずTIDごとの最後に受け取ったPNと比べ(`iwm_ccmp_decap`)、その後に`ieee80211_inputm`で重複の検査、並べ直し、PNの検査と更新(`ieee80211_input_hwdecrypt`)を行う。PNは並べ直しの後に受け取った順で更新するので、窓の中の順の入れ替わりで捨てることは無い。最初の検査で捨てるのは、PNが受け取り済みのPN以下のもの、つまりアクセスポイントが送り直した受け取り済みのフレームや、窓が先へ進んだ後に来た送り直しである。Linuxでも同じフレームを、重複か窓より古いものとして捨てる。届くデータは同じで、数え方だけが違う(iwmの`replay`に送り直しが入る)。x64の実機で2時間49分動かしたとき、`replay`は3006(局宛てのデータの約3%)で、並べ直しの時間切れ(gaps timed out)の増えた時と同じ時に増えていた。iwmの`if_ierrors`(3330)は、このreplayに、短すぎるフレーム、長すぎるフレーム、mbufの確保の失敗を足したものである。

これを次の実機で確かめるために、iwmが捨てるreplayを、カードの受信のバッファの段階で先に見て分ける(`rp_look`)。送り直しの印(Retry)の有無と、そのTIDで同じシーケンス番号を受けていたかで数え、`wifi: receive: the replays as seen ahead N: with the retry bit R, the sequence received before S, neither X; too short T; allocations failed A`の行に出す。どちらにも当たらない(X)ものは、最初の16個まで`wifi: a frame to the station iwm drops as a replay: TID, sequence, retry bit, the sequence received before, PN, the last PN taken for the TID, the TID's block-ack agreement`の行に出す。Xが0に近ければ、データは失われていない。Xが多ければ、PNの扱いを直す。カードの統計の知らせの大きさがiwmの読む構造体(`IWM_STATISTICS_NTFY_API_S_VER_8`)と違うときは、`wifi: the card's statistics notification: N bytes, iwm reads M ... not to be trusted`の行に出す。そのときは、カードの統計の行(PLCP errors、beacons、missedなど)は信用しない。OpenBSDの層のプールの確保の失敗(mbufとクラスタを含む)も数える(`obsd_pool_fails`)。

#### iwx(Surface Go 2のWi-Fi 6 AX200)

Surface Go 2のWi-Fiは、IntelのWi-Fi 6 AX200(PCI 8086:2723)である(検討書`docs/private/x64_surface_go2_study.md`の部品の表と、linux-surfaceのwikiのSurface Go 2の頁の「Intel WiFi 6 AX200 series」)。個体によって違わないかは、実機の`HW.TXT`のPCIの一覧で確かめる。AX200はiwmの次の世代で、OpenBSDではiwx(4)が扱う。OpenBSD 8.0の`if_iwx.c`、`if_iwxreg.h`、`if_iwxvar.h`をiwmと同じ層に足した。802.11axは使わず、iwxの扱う範囲(802.11nとac、VHT80、2本の流れ)で動かす。

層の中は、ドライバによらない部分と、ドライバごとの部分に分けた。

| ファイル | 内容 |
| --- | --- |
| `tswifi_obsd.c` | 管理のタスクの入口(`rump_tswifi_*`)、認証の止め、関連付けの要求の要素、鍵、走査、背景の走査の保留、ブロックACKの取り決めの時期と取っておき、DHCPとARPの記録、受けたフレームの数。カードのPCIのIDで、iwm、iwxの順にドライバの`match`(ドライバ自身の表、`pci_matchbyid`)に聞き、知っている方を取り付ける。インタフェースの名前は`iwm0`か`iwx0`で、管理のタスクは`rump_tswifi_ifname`で聞く |
| `tsw_drv.h` | ドライバに聞くことの表(`struct tsw_drv`)。取り付け、時間のイベント、送り直しの数、管理フレームの待ち行列、走査中か、ペアの鍵をカードに入れること、受信のバッファの読み、カードの統計、ポートが開いた時のカードの鍵 |
| `tsw_iwm.c` | iwmの分(iwmのヘッダで翻訳する)。前に`tswifi_obsd.c`にあったiwmの構造体を読む所を移した。ログは前と同じ |
| `tsw_iwx.c` | iwxの分(iwxのヘッダで翻訳する) |

カードの起動の側(`wifi_user.c`)は、iwmとiwxのPCIのIDの表を持ち、見つけたカードがどちらのものかで、記録に読むレジスタを分ける。iwxのカードには、iwmの命令のキューのスケジューラとFHの送信の通り道が無い(待ち行列はファームウェアのもの)ので、`wifi: cmdq:`の行はCSRと割込みの原因の表だけにする。

iwmとの違いと、その扱いは次のとおりである。

- 速さの制御。iwxはカードのファームウェアが速さを選ぶ(TLC)。ドライバに送り直しの数が無いので、`wifi: join timed:`の行は、ACKの無かった数と待ち行列の数だけを出す。wlan0の`RATE`は、ファームウェアの知らせでiwxが書くnet80211のMCSと流れの数から、iwmと同じく求める
- 鍵。iwxは、ペアの鍵、グループの鍵、IGTK(BIP)のどれもカードに入れる。`ic_set_key`はすぐEBUSYを返し、ドライバのタスク(`iwx_setkey_task`)がカードの答えを待って入れる。層の`rump_tswifi_setkey`はEBUSYを成功と扱う(iwmと同じ)。iwmのようにペアの鍵だけを層から答えを待って入れること(`ptk_to_card`)はしない。全部の鍵が入ると、iwx自身もポートを有効にする。ポートが開いた時に、カードが持つ鍵を`wifi: the card's keys: pairwise 1, group 1, integrity group 1, 0 still to be set`の行に出す。TKIPはソフトウェアのまま
- ブロックACK。送るデータの取り決めは、カードのファームウェアが求めて結ぶ(`IEEE80211_C_ADDBA_OFFLOAD`)。net80211は、取り決めを求める時に、ドライバのタスク(`iwx_ba_task`)にTIDの集約の待ち行列を有効にさせ、その時に取り決めができたとする。取り決めを求める時期(1秒に10フレーム、ポートが開いた後)とフレームの取っておきは、iwmと同じ`tswifi_obsd.c`の包みを通る。送るデータの形はリリースのままで、取り決めができるまでQoSの欄を付けず、EAPOLにも付けない(「送るデータのQoSとブロックACK」の「iwx」)。TIDのQoSデータは取り決めの下でしか出ないので、新しい待ち行列の取り決めを0から始めるリリースの`iwx_sta_tx_agg_start`は、TIDの次の番号から始めることになる。前は、パッチの形でTIDの番号が関連付けの直後から進むため、新しい待ち行列でもTIDの次の番号から始めるパッチ`if_iwx-agg-ssn.patch`を当てていたが、送る形をリリースに戻したので除いた
- 受けたフレームの並べ直し。iwxのカードは、ブロックACKの取り決めの下で来たフレームを自分で並べ直し、ドライバが重複を捨てる(`iwx_detect_duplicate`)。`wifi: receive:`の行の並べ直しの数は、iwmより少なく出る
- 受信のバッファ。カードは複数の待ち行列の受信で、MPDUごとに記述子(状態と速さ)の後に書く。`tsw_iwx.c`の`iwx_t_rx_peek`が記述子を読み、状態の印(iwmと同じ並び)を`tswifi_obsd.c`の`tsw_rx_mpdu`に渡す。`wifi: the card received:`、`wifi: the card sent:`(送信の答えと、まとめたブロックACKの答え)、リプレイの先見(`rp_look`)はiwmと同じ形で出る
- 統計。iwxの読む統計の構造体は通知のバージョン13(`STATISTICS_NTFY_API_S_VER_13`)で、大きさが違えば`wifi: the card's statistics notification: N bytes, iwx reads M ... not to be trusted`の行に出す
- 割込み。iwxはMSI-Xを先に求めるが、層はMSIだけを与える。iwxはMSIのとき割込みの原因の表(ICT)を使う
- ヘッダ。`if_iwxvar.h`はカードの設定の構造体を定義する(`static`でない)ので、2つのファイルから読むと二重の定義になる。`tools/openbsd/patches/if_iwxvar-static-cfg.patch`で`static`にした
- そのほか、iwxが使うOpenBSDのカーネルの関数で足りなかったのは、`bus_space_unmap`(`obsd_pci.c`。窓はカーネルの直写像なので何もしない)と`fls`(`lib/libkern/fls.c`を翻訳する)だけだった

ファームウェアは、iwxがAX200に求める`iwx-cc-a0-77`(APIのバージョン77)である(9.6.5)。AX200はPNVMを読まない(AX210以降だけ)。

実機で見るログは、iwmと同じ形である。`wifi: card 8086:2723 at ..., for iwx`、`obsd: the card 80862723 is iwx's`、`iwx0 at pci1 dev 0 function 0, msi 1`、`obsd: iwx0: firmware iwx-cc-a0-77, device family ..., HW_REV ..., RF ID ..., message (MSI) interrupt`、`iwx0: hw rev ..., fw ..., address ...`(ファームウェアとNVMが読めた)、`obsd: iwx0: firmware ... running its API (first data queue ...), the NVM read`、`wifi: iwx0 ready, address ...`、`wifi: iwx0 up (0): the runtime firmware loaded`、走査の数、`wifi: joining ...`から`wifi: DHCP in: ACK`まで(上の「ログ」)。

#### まだ確かめていないこと

- iwmの`replay`のうち、送り直しでないもの(上のX)があるかどうか。
- アクセスポイントf4:d5:80:31:fc:d0が、上の見込みのとおりにQoSの欄の無いフレームとTID 0の番号を1つの記録で持つかどうか。次の実機で、直した形でこのアクセスポイントにつないでDHCPとデータが通るかを見る。
- iwmは認証の前に、カードがその周波数に留まるよう時間を取る(`iwm_protect_session`、ビーコンの間隔の2倍)。管理のタスクが認証を止めている時間(PSKは数ミリ秒、SAEはコミットの計算の時間)がそれを超えると、カードが周波数を離れる見込みがある。`wifi: authenticating with ...`の行で確かめる
- SAEのアンチクロギングのトークン、グループの変更(19以外)、H2Eは、実機のアクセスポイントで確かめる
- iwx(AX200)は、カードの起動、ファームウェアの読込み、走査、接続、鍵、DHCP、ブロックACKの取り決め、背景の走査とローミングを、Surface Go 2の実機で確かめる。QEMUにはカードが無いので、層の共通の部分をシミュレータ(群`wifisim`)で、iwxの部分は翻訳とリンクだけを確かめた。4ウェイハンドシェイクのメッセージ2と4がACKされることは、`wifi: the card sent: ..., during the handshake`の行で見る。取り決めの後に、アクセスポイントf4:d5:80:31:fc:d0がデータを通すか(リリースの形では、QoSの欄の無いフレームの後に、取り決めの下のTID 0のQoSデータが0から始まる。上の見込みのアクセスポイントなら、iwmで見たように落ちる)は、DHCPの後に`wifi: block ack:`の行が出てからのデータで見る。落ちるなら、TIDごとの待ち行列を関連付けの時から持つ形を考える

### 9.6.10 暗号の実装

wpa_supplicantの暗号は、すべてMbed TLS 3.6.7(`lib/mbedtls`、ブラウザのHTTPSと同じもの、Apache-2.0、書き換えない)で行う。wpa_supplicantの`crypto.h`の口の下に、OpenWrt v24.10.0の`package/network/services/hostapd/patches/110-mbedtls-TLS-crypto-option-initial-port.patch`が足す`src/crypto/crypto_mbedtls.c`(BSD-3-Clause、書き換えない)を置く。`tools/wpa/build.sh`が、その当てを取ってきてSHA-256を確かめ、当ての中の新しいファイルの行だけを取り出して`crypto_mbedtls.c`にし、そのSHA-256も確かめる。Mbed TLSは`device/net/wifi/wpa/ts_wpa_mbedtls_config.h`の小さな構成(大きい整数、NISTの楕円曲線P-256、P-384、P-521、ECDH、ECDSA、DH、ハッシュ、AES、CMAC、鍵の包み、HKDF、PKCS#5)で、要る37のファイルだけを翻訳する。カーネルのWi-Fiの部分の大きさは、x64でtextが330,733バイト、ARMで266,538バイトである(bssは約12KB)。1つの関数のスタックで最も大きいのは`crypto_dh_derive_secret`の2,304バイトで、管理のタスクのスタック(32KB)の中に収まる。

比べた案と理由は次のとおりである。

| 案 | 内容 | 決め |
| --- | --- | --- |
| A すべてMbed TLS | WPA2もWPA3もMbed TLSの暗号で行う | 採る。暗号の実装が1つで済み、HTTPSと同じものを1か所で更新できる。Mbed TLSの楕円曲線の計算は、秘密の値によって時間が変わりにくい作りである。弱みは、`crypto_mbedtls.c`がhostapdの本流に無く、OpenWrtの当てにしか無いことである。WPA2の振る舞いが変わる危険は、WPA2のホストの試験(9.6.7)と上流のmodule testsで確かめる |
| B WPA2は内部の暗号、SAEだけMbed TLS | 今までの`CONFIG_CRYPTO_INTERNAL`をWPA2に残す | 採らない。wpa_supplicantは暗号の実装を1つ選ぶ作りで、2つを混ぜると同じ名前の関数がぶつかり、どちらを使うかの選り分けを自前で持つことになる |
| C OpenSSL | wpa_supplicantの本流の`crypto_openssl.c` | 採らない。TessronOSにOpenSSLは無く、大きい |

将来の候補はOpenSSLかBoringSSLである。BoringSSLはブラウザ(tessron-chromium)がすでに使っていて、wpa_supplicantの本流の`crypto_openssl.c`が`CONFIG_BORINGSSL`で対応している(Androidが使う形)。替えるときは`crypto.h`の下(`crypto_mbedtls.c`と乱数の源)を差し替えるだけで済むよう、TessronOSのつなぎはMbed TLSの関数を直接呼ばない形を保つ。`wpa_glue.c`はwpa_supplicantの関数(`crypto.h`、`sha1.h`、`sae.h`など)だけを呼ぶ。Mbed TLSに乱数を渡す`mbedtls_hardware_poll`(Wi-Fiの管理の`knl_wifi_random`を呼ぶ)は、別の小さなファイル`device/net/wifi/wpa/wpa_entropy.c`に分けてある。

プロセスの形(9.6.11)では、暗号をOpenSSL 3.5.9のlibcryptoで行い、wpa_supplicantの本流の`src/crypto/crypto_openssl.c`をパッチなしで使う。3.5はLTSで、2030年4月までサポートされる。ライセンスはApache-2.0である。BoringSSLと比べてOpenSSLを選んだ。BoringSSLはリリースもサポート期間も持たず、ソースはC++に移っている。OpenSSLはLTSを持ち、wpa_supplicantの本流が既定で使う暗号である。OpenSSLのソースは書き換えない。`tools/wpa/proc.sh`がGitHubのリリースから取り、SHA-256(openssl.orgの`.sha256`と同じ値)を確かめてWSLの`~/openssl`に展開し、ソースの外の置き場で構成する。lib/の下には置かない(展開すると50MBを超えるため)。構成は、アセンブラを使わず(`no-asm`)、使わない部分を外す(`no-module`、`no-engine`、`no-dso`、`no-sock`、`no-threads`、`no-autoload-config`、`no-legacy`など)。乱数の源は`getentropy`で、プロセスの側でTessronOSの乱数のシステムコールにつなぐ。プロセスは浮動小数点を使えるので、カーネルの中の形で問題になる`double`の使用(`params.c`など7つのファイル)はそのままでよい。

### 9.6.11 wpa_supplicantのプロセス(`WPA_MODE=proc`)

鍵の交換(4ウェイハンドシェイク、グループ鍵のハンドシェイク、SAE、PMFの鍵)とその暗号を、カーネルの外のプロセスで動かす形である(2026-10-23のユーザの決定)。LinuxとBSDと同じく、wpa_supplicantを利用者の側に置く。暗号はOpenSSL 3.5のlibcrypto(9.6.10)で、プロセスはnewlibと浮動小数点を使えるので、カーネル向けの制限を付けずに組む。ビルドの変数`WPA_MODE`で選び、既定は今までのカーネルの中の形(`kernel`)である。`WPA_MODE=proc`で確かめた後に既定を替え、その後でカーネルの中のwpa_supplicantとMbed TLSを外す。

#### 分担

| | カーネル(`device/net/wifi/wifi.c`) | プロセス「wpasupp」 |
| --- | --- | --- |
| 持つもの | net80211とドライバ(iwm、bwfm、OpenBSDの層)、カードの起動と始め直し、走査、接続先の選択、関連付けの要求、鍵をカードに入れること、Wi-Fiのオンとオフ、利用者の切替え、保存した接続とその秘密(設定の実身、9.6.6) | wpa_supplicant 2.11の状態機械(`src/rsn_supp`)、SAE(`sae.c`、`dragonfly.c`)、RSNの要素の解析、PBKDF2とSAEのPTの計算、OpenSSLのlibcrypto |
| 秘密 | 設定の実身に置き、接続のたびに要るものだけをプロセスに渡す | 渡された秘密を、その呼出しとハンドシェイクの間だけメモリに持つ。保存しない |
| 決めること | どこにいつつなぐか、失敗の扱い、休ませる時間、ローミング | 決めない。カーネルの呼出しに答え、EAPOLのフレームと鍵をカーネルに返すだけ |

カーネルの管理のタスクは、今の`knl_wpa_*`の関数(`wpa_glue.h`、17個と`knl_wpa_tick`)をそのまま呼ぶ。`WPA_MODE=proc`では、その関数を、wpa_supplicantの代わりに`device/net/wifi/wpaproc/wpaproc.c`が持つ。この関数は引数をメッセージにしてプロセスに送り、答えを待って戻る。プロセスの中では同じ`wpa_glue.c`が同じ関数を実行し、途中で呼ぶカーネルの関数(`knl_wifi_eapol_tx`、`knl_wifi_setkey`、`knl_wifi_delkey`、`knl_wifi_deauth`、`knl_wifi_say`)をメッセージにしてカーネルに返す。カーネルの側では、答えを待っている呼出し元のタスク(ふつうは管理のタスク)がそれを実行し、結果を返してまた待つ。呼び返しは、今までと同じタスクで同じ順に実行される。`wifi.c`は変えない。時刻と乱数は、プロセスが自分のシステムコール(単調時刻、乱数)で得る。

#### やりとり

やりとりには、専用のデバイスの実身「wpasup」(`knl_obdev_add`、`OB_S_NET`)のレコード1を使う。プロセスが読むと、カーネルからの次のメッセージ(呼出しか、呼び返しの結果)を受け取る(1秒で`E_TMOUT`)。書くと、答えか呼び返しを送る。メッセージは頭(魔法の語、種類、関数の番号、戻り値、呼出しの番号、長さ)と、引数を順に並べたもの(整数、長さ付きのバイト列、NULL)で、4KBまでである(`device/net/wifi/wpaproc/wpaproc.h`)。カーネルは`CALL`ごとに番号を付け、プロセスの`RET`と`CB`はそれを持ち帰る。時間切れであきらめた呼出しの答えが後から来ても、番号が違うので捨てる。

| 種類 | 向き | 中身 |
| --- | --- | --- |
| `HELLO` | プロセス→カーネル | 版。カーネルはこれを受けてからプロセスを使える状態とする |
| `CALL` | カーネル→プロセス | `knl_wpa_*`の呼出し。入力の引数(BSSID、SSID、アクセスポイントのRSNとRSNXE、PMK、SAEのパスワードやPT、受けたEAPOLとSAEの認証のフレーム) |
| `RET` | プロセス→カーネル | 戻り値と出力の引数(関連付けの要求に入れる自分のRSNの要素、送るSAEのフレームと番号と状態、PMKとPMKID、選んだ鍵の管理とPMF) |
| `CB` | プロセス→カーネル | 呼び返し。送るEAPOLのフレーム、カードに入れる鍵(種類、アドレス、番号、RSC、鍵)、鍵の削除、離脱、コンソールに出す行 |
| `CBRET` | カーネル→プロセス | 呼び返しの戻り値 |

出来事(関連付け、切断、ローミング)は、今と同じく管理のタスクが`knl_wpa_assoc`、`knl_wpa_disassoc`、`knl_wpa_sae_abort`として呼ぶ。呼出しは一度に1つで、カーネルの側はミューテックスで順番にする。

カーネルのタスクがプロセスを待つ所には、どこにも時間切れを置く。1つの呼出しの答え(途中の呼び返しを含む)の待ちは5秒である。最も重い呼出しはPBKDF2(SHA-1で4096回を2つ)とSAEのPTの計算で、Raspberry Pi 5でも0.1秒に届かない。5秒は、それより十分に長く、管理のタスクが止まっていても利用者に分かる前に戻れる長さとして決めた。5秒を過ぎたら、呼出しは失敗(`-1`、`WPAG_SAE_FAIL`、`WPAG_NONE`)で戻り、見張りのタスクが固まったプロセスを`ts_ter_prc`で終わらせて、下のとおり起こし直す。管理のタスクは、今のカーネルの中の形でハンドシェイクが終わらないときと同じように扱う(9.6.4の10.)。呼出しのミューテックスの待ちも同じ5秒で切る。プロセスの側の読出しは1秒ごとに戻り、カーネルが「wpasup」を消したら終わる。

秘密の守りは次のとおりである。

- 「wpasup」の実身は、所有者がシステム、グループが管理者、モード`rw-------`で、レコード1の読み書きは、カーネルが起こしたプロセス(覚えておいたプロセスID)からだけ受け付ける。ほかのプロセスは管理者でも`E_OACV`になる。秘密を含む`CALL`は、そのプロセスにしか渡らない。
- カーネルは、送ったメッセージと受けたメッセージの場所を、使い終えたら0で埋める。プロセスも、答えた後にメッセージの場所と秘密の写しを0で埋める(OpenSSLの中の値は`OPENSSL_cleanse`で消える)。
- プロセスはシステムのプロセス(`TS_PRC_SYSTEM`、5.5.1)で、利用者のShift+Pauseでは止められない。アドレス空間はほかのプロセスから見えない。
- 保存した秘密はカーネルの設定の実身にしか無い。プロセスは設定の実身を開かず、ファイルも持たない。

ほかのOSと比べると次のとおりである。

| | Linux(nl80211) | NetBSD(`driver_bsd.c`) | TessronOS(`WPA_MODE=proc`) |
| --- | --- | --- | --- |
| 動かす側 | wpa_supplicantが、nl80211で走査、参加(`NL80211_CMD_CONNECT`など)、鍵(`NEW_KEY`)をカーネルに頼む | wpa_supplicantが、`SIOCS80211`のioctlで鍵とMLMEを頼む | カーネルの管理のタスクが走査と参加を決め、プロセスに鍵の交換を頼む |
| EAPOL | `PF_PACKET`か、nl80211の制御のポート(`CONTROL_PORT_FRAME`) | BPF(`l2_packet`) | `CALL`と`CB`のメッセージ |
| 出来事 | nl80211のマルチキャスト(関連付け、切断、ローミング) | 経路のソケット(`RTM_IEEE80211_*`) | 管理のタスクが`knl_wpa_assoc`などを呼ぶ |
| 秘密 | `wpa_supplicant.conf`(rootだけが読む)。NetworkManagerはD-Busでその都度渡す | `wpa_supplicant.conf` | カーネルの設定の実身にだけ置き、接続のたびに渡す(NetworkManagerの秘密の渡し方に近い) |
| 外からの操作 | 制御のインタフェース(UNIXのソケット、`wpa_cli`) | 同じ | 無い。操作はwlan0への依頼だけ(9.6.6) |

方針(どこにつなぐか、秘密の持ち方、利用者ごとの接続)は今のカーネルの管理に残し、wpa_supplicantを「鍵の交換の係」として切り出した。Linuxのように方針ごとwpa_supplicantに移すと、9.6.4と9.6.6の流れを作り直すことになり、秘密をプロセスのファイルに置くことにもなる。この形では、生のフレームを送る口も鍵を入れる口も、ほかのプロセスに開かない。

主になる側も違う。Linuxのwpa_supplicantはプロセスが主で、カーネルの出来事(nl80211の走査の終わり、関連付け、切断)を受けて、自分で走査を頼み、接続先を選び、参加と鍵を決める。今回の形はカーネルの管理のタスクが主で、プロセスは呼ばれたときだけ動く。最初の移り方としてこの形にしたのは、9.6.4から9.6.8の流れ(Pi 5のチップのsupplicant、OpenBSDの層、利用者ごとの接続を含む)をそのまま残し、変わるのを暗号と状態機械の置き場だけにするためである。将来プロセスを主にする形へ進めることはできる。出来事(走査の結果、関連付け、切断、ローミング)を「wpasup」のメッセージでプロセスに知らせ、プロセスが接続先と鍵を決めて、参加と鍵の設定をカーネルに頼む形である。そのときは、方針と秘密の扱い(9.6.6)を一緒にプロセスに移すことになる。暗号と状態機械の置き場を確かめた後に、改めて決める。

#### 起こし方と見張り

`wpaproc.c`は、最初の`knl_wpa_*`の呼出しで見張りのカーネルのタスクを作る。見張りのタスクは、プログラム実身「wpasupp」(`SYSDEF_PROG_WPASUPP`、レコード1がELF)を`ts_cre_prc_obj`で`TS_PRC_SYSTEM`として起こし、引数に「wpasup」の実身のUUIDを渡す。カーネルのタスクが起こすので、プロセスはシステムの資格で動き、だれの子にもならない。プロセスが`HELLO`を送ると使える状態になる。システムが起動してから初めての起動の間は、呼出しはそれを10秒まで待つ(プログラムをディスクから読む時間)。起こし直しの間は待たない。12秒たっても`HELLO`の無いプロセスは、見張りが終わらせて起こし直す。

見張りのタスクは`ts_wai_prc`でプロセスの終わりを待つ。終わったら(落ちた、`abort`した)、待っている呼出しを失敗で戻し、`wpa: the supplicant ended (...), started again in N s`の行を出し、1秒、2秒、4秒と延ばして60秒までおいて起こし直す。起こし直すまでの呼出しは待たずに失敗で戻るので、管理のタスクの50ミリ秒ごとの`knl_wpa_tick`が止まることはない。状態機械の状態はプロセスとともに失われるので、ハンドシェイクの途中なら、管理のタスクは時間切れからつなぎ直す。保存した秘密はカーネルにあるので、つなぎ直しに困らない。

#### チップのsupplicantとOpenBSDの層

Raspberry Pi 5のチップのsupplicantの形(`FW_IDSUP`、9.6.8)では、ハンドシェイクもSAEもチップが行う。プロセスは、走査の結果の分類(`knl_wpa_classify`)、接続先の鍵の管理の選択(`knl_wpa_choose`)、保存のときのPBKDF2(`knl_wpa_psk`)とSAEのPT(`knl_wpa_sae_pt`)だけに答える。チップに渡すPMKとSAEのパスワードは、今と同じくカーネルが設定の実身から読んで渡し、プロセスを通らない。OpenBSDの層(`WIFI_NET80211=obsd`、9.6.9)とNetBSDのiwmでは、4ウェイとグループ鍵のハンドシェイク、OpenBSDの層ではSAEの認証のフレームも、プロセスが扱う。どの形でもカーネルとプロセスの間の口は同じ`knl_wpa_*`である。

#### ビルドとテスト

`tools/wpa/proc.sh`が、OpenSSL 3.5.9の取得とSHA-256の確認(`~/openssl`)、利用者のプログラムの旗でのlibcryptoの構成とビルド、wpa_supplicantのソース(`tools/wpa/build.sh fetch`と同じNetBSD 11.0のもの)と`crypto_openssl.c`、`wpa_glue.c`、答えの部分(`application/wpasupp/wps_serve.c`)の翻訳を行い、`wps_serve`から届く部分だけを`--gc-sections`で残した1つのオブジェクト`~/tessronos-wpaproc-x64/wpasupp_lib.o`(ARMは`~/tessronos-wpaproc-arm/`)にする。外から見える名前は`wps_serve`だけで、`wpa_glue.c`が持つ`strtol`などはnewlibのものとぶつからない。`build_make/wpaproc.mk`が、それとプロセスの本体(`wps_main.c`、newlibの下回りの`wps_libc.c`)をnewlibと結んで`wpasupp.elf`にし(textはx64で約2.4MB、ARMで約2.4MB)、stripしたものをプログラム実身のレコード1にして、メタデータとレコード0(`application/wpasupp/def`)と一緒に`WIFI=1 WPA_MODE=proc`のシステムボリュームに載せる。どの仮身からも結ばず、カーネルがUUIDで起動するので、システムボリュームの`--hold`にする。カーネルは`wpasupp.o`の代わりに`device/net/wifi/wpaproc/`の2つのファイルを結ぶ(`build_make/wpamode.mk`)。既定の`WPA_MODE=kernel`では、どれも足さない。

ホストのテストは、`tools/wpa/proc.sh test`と`modtest`が、`build.sh`の`test`、`modtest`と同じテスト(`test_wpa.c`、`modtest.c`、上流のmodule tests)を、OpenSSLのlibcryptoと`crypto_openssl.c`で走らせる。`test`は、テストが呼ぶ`knl_wpa_*`を`wpaproc.c`のメッセージの組立てと読取りに通し、プロセスの側の受け(`application/wpasupp/`)が同じプロセスの中でそれを読んで答える形にして、メッセージの形もあわせて確かめる。カーネルでは、群`wifikey`(9.6.7)が`WPA_MODE=proc`でも通ることと、群`wpaproc`(`tests/ktest/ktest_wpaproc.c`、`WPA_MODE=proc`のKTESTで入る)で、プロセスがIEEE 802.11の試験の値のPMK、ネットワークの種類、H2EのPTを答えること、カーネルのタスクからも「wpasup」のレコード1を読み書きできないこと(`E_OACV`)を確かめる。

### 9.6.12 Wi-Fiのシミュレータ(`WIFI_SIM=1`)

QEMUにはWi-Fiの装置が無く、Wi-Fiの管理(`wifi.c`)、カードの部品(`tswifi_if.c`)、カードの選択(`netsel.c`)、アダプタの管理(`netadp.c`)、DHCPのつなぎは、実機に載せるまで一度も動かなかった。そのため、バスマスタ、命令のキュー、接続の手順、パスワードの読み、M2の送信、切断、DHCPの誤りは、実機のテストで1つずつ見つかった。Wi-Fiのシミュレータは、LinuxのLinux mac80211_hwsimと同じ考え方で、カードの代わりに仮想の無線をrumpカーネルの中に置き、QEMUの中で走査からデータ、切断、再接続までを通しで流せるようにするものである。テストのためのビルドの変数`WIFI_SIM=1`(既定は0)のときだけ入り、既定のビルドの出力は変わらない。

#### 方式の選び方

次の3つを比べた。

| 方式 | TessronOSのつなぎを通せるか | x64とARM | KTESTとUIテスト | 決め手 |
| --- | --- | --- | --- | --- |
| (a) net80211の上の仮想の無線と、同じ仮想の電波の上のAP | `wifi.c`、`tswifi_if.c`、`netsel.c`、`netadp.c`、DHCP、ネットワーク設定がすべてそのまま動く。替わるのはドライバだけ | どちらもrumpカーネルの中で同じソース | どちらからも使える。APをテストから操作できる(電波から消す、パスワードを替える、DHCPを止める) | 採る |
| (b) QEMUの`usb-host`でUSBのWi-Fiのアダプタを渡す | 渡せれば実物だが、そのアダプタのドライバ(NetBSDのrumpカーネルに無いUSBのWi-Fiのドライバ)とUSBの部品を新しく要る。iwmやbwfmの経路は通らない | 機種ごとにドライバが要る | 実物のAPが要り、テストから操作できない | Windowsの公式のQEMUは`usb-host`をlibusbのドライバの入れ替え(WinUSB)無しでは使えず、アダプタをWindowsから取り上げることになる。確かめるだけにとどめる |
| (c) 802.11のフレームを作らず、`wifi.c`の下の関数を差し替える | net80211、鍵の設定、ポートの認可を通らない | どちらでも | 使える | 実機で起きた誤り(下の認可の誤りなど)はnet80211とのつなぎにあるので、見つけられない |

(b)は、ThinkPadなどにつないだUSBのアダプタをWindowsのQEMUへ渡すには、Zadigなどでその装置のドライバをWinUSBに替える必要があり、替えるとWindowsからはWi-Fiとして使えなくなる。また、渡せても、NetBSD 11.0のrumpカーネルにはUSBのWi-Fiのドライバ(`urtwn`、`run`など)の部品が無く、iwmやbwfmとは違う経路になる。そのため採らない。

`wifi.c`が`WIFI_SIM`で変わるのは、カードがあるかどうか(シミュレータのSTAは常にある)、アダプタの名前(「Simulated Wi-Fi (wifisim)」)、管理の開始でAPのタスクを起こすことの3つだけである。`netadp.c`は、KTESTのビルドではアダプタを替えたときとWi-Fiがつながり直したときにDHCPを問い合わせ直さない(テストがアドレスを自分で決めるため)が、`WIFI_SIM=1`では実機と同じに問い合わせ直す。

#### 仮想の電波

一方の無線が送ったフレームは写されて相手の待ち行列に入り、rumpカーネルのスレッド(`wsimair`)がカーネルのロックを取って相手のnet80211に渡す(`ieee80211_input`)。ドライバの受信の割込みと同じ形である。フレームが相手に届くのは、両方が動いていて、同じチャネルにいて、APが電波に出ているときだけである。暗号はnet80211のソフトウェアのCCMPがかける(`ieee80211_crypto_encap`、受ける側は`ieee80211_input`の中で外す)。同じスレッドが、100ミリ秒ごとにAPのビーコンを送り(`ieee80211_beacon_alloc`)、STAの走査を1つのチャネルに60ミリ秒いたら次へ進め(`ieee80211_next_scan`)、STAが接続しているAPから300ミリ秒何も聞かなければビーコンの欠けをnet80211に知らせ(`ieee80211_beacon_miss`、net80211は探査を送ってから走査に戻る)、1秒ごとにnet80211の見張り(`ieee80211_watchdog`)を呼ぶ。信号の強さは45 dBm(テストから替えられる)で、x64はiwmと同じく大きさを、ARMはbwfmと同じく符号付きのdBmを渡す。

APを電波から消すと、APが送るものも受けるものも捨て、APのネットワークを始め直す(電源を切ったAPと同じく、局を忘れる)。接続していたSTAはビーコンが来なくなり、届かないネットワークと同じく離れる。

#### APとそのネットワーク

APは、ネットワークを`rump_tswifisim_ap_config`で設定する。WPA2のときは、hostapdのBSD用の層(`driver_bsd.c`の`bsd_set_ieee8021x`、`bsd_configure_wpa`)と同じく、`IEEE80211_IOC_WPA`(2)、`MCASTCIPHER`(CCMP)、`UCASTCIPHERS`、`KEYMGTALGS`(PSK)、`RSNCAPS`、`AUTHMODE`(`IEEE80211_AUTH_WPA`)、`DROPUNENCRYPTED`を書く。APのタスクは20ミリ秒ごとに、関連付けている局をnet80211の局の表から読む。局が(関連付け直しも含めて)新しく関連付けたら、関連付けの要求のRSNの要素で認証側の状態機械を始める(`wpa_validate_wpa_ie`、`wpa_auth_sta_associated`)。認証側が送るEAPOLのフレームはAPのインタフェースから送り、ペアの鍵とグループの鍵は`IEEE80211_IOC_WPAKEY`で入れ、4ウェイハンドシェイクが終われば局のポートを開く(`IEEE80211_MLME_AUTHORIZE`)。表から消えた局は認証側から外す。

DHCPは、局ごとに192.168.77.100から1つずつアドレスを貸し、ルータとネームサーバに192.168.77.1、ドメインに`wifisim.test`を返す。OFFERとACKは、クライアントがブロードキャストの印を立てていればすべてに(グループ鍵で暗号化される)、立てていなければクライアントのアドレスに送る。テストから、常にすべてに送るようにもできる。DNSは、`wifisim.test`とその下の名前をすべて192.168.77.1と答え、ほかの名前は無いと答える。見たものは数え(`knl_wifisim_counts`)、DHCPのメッセージはコンソールに`wifisim: DHCP:`の行で出す。テストからは`knl_wifisim_ctl`で、APを電波から消す、戻す、信号の強さ、セキュリティ(なし、WPA2)、パスフレーズ、SSID、DHCPを止める、戻す、すべてに送る、貸出しの期間を替えられる。

#### OpenBSDの層の上のシミュレータ

x64の既定のOpenBSDの層(`WIFI_NET80211=obsd`、9.6.9)では、仮想の無線を層の中に置く(`device/net/wifi/sim/obsd_sim.c`、`tools/openbsd/build.sh`の`WIFI_SIM=1`で`~/tessronos-obsd-x64-wifisim/obsdwifi.o`)。iwmとそのPCIのバス(`if_iwm.c`、`obsd_pci.c`)は入れず、`tswifi_obsd.c`の`rump_tswifi_start`がiwmを取り付ける代わりに2つの無線を作る(`TSWIFI_SIM`)。STAは`iwm0`で、iwmと同じに動く。インタフェースの起動で走査を始め、走査はチャネルを順に回り、背景の走査(`ic_bgscan_start`。APの信号が閾値より弱いとき、net80211が自分から始める)ではAPのチャネルを離れてほかのチャネルを順に聞き、ビーコンが来なくなれば名指しの探査の要求を送る。信号の強さはiwmと同じく「dBmからIWM_MIN_DBMを引いた値」で、`ic_max_rssi`もiwmと同じ(IWM_MAX_DBMの-33から求めた67)にするので、背景の走査の閾値(2.4GHzで-59dBm相当)も同じに効く。前はシミュレータの上限を-10dBmにしていて閾値がiwmと違っていたので、iwmに合わせた。APは`wsimap0`で、層のHOSTAPのモードとその中の4ウェイの認証側(`ieee80211_pae_input.c`、`ieee80211_pae_output.c`)を使い、PSKを`ic_psk`に入れる。hostapdの写し(`wpaap.o`)は使わない(`WIFISIM_LAYER_AUTH=1`)。APが受けたEthernetのフレームは`obsd_net.c`の`if_input`から仮想のAP(`wifisim_ap.c`)へ行き、APのEAPOLは層の認証側に残す(`tswifi_obsd.c`の`ieee80211_eapol_key_input`の包み)。仮想の電波は層の10ミリ秒ごとのタイムアウトで、層の鍵を持って動く。背景の走査の間にAPのチャネルを離れていて失ったフレームは別に数える(`WSIM_AIR_LOST_BGSCAN`)ので、接続の直後の背景の走査とDHCPの取りこぼしの重なり(9.6.9)もこのシミュレータで見られる。rumpカーネルはWi-Fiの無いものを使う。iwmとカードの代わりなので、カードのファームウェアの道は通らない。鍵は層のソフトウェアが持ち(`ic_set_key`は層の`ieee80211_set_key`)、暗号と復号もソフトウェアで、フレームは`ieee80211_input`で層に渡す。ADD_STA_KEYでカードに入れるペアの鍵、カードの復号(`iwm_rx_hwdecrypt`)、`iwm_rx_mpdu`の検査、カードのブロックACKは、実機でしか確かめられない。

NetBSDの層の上のシミュレータ(上のとおりrumpカーネルの中)はARMのビルドで使う。x64のNetBSDの形(`WIFI_NET80211=nbsd`)を除く前は、x64でも同じものを使い、認可の誤り(9.6.3)を再現して直した。

WPA3-Personal(SAE)のAPは、このシミュレータでは確かめられない。NetBSDの802.11の層もOpenBSDの層もHOSTAPのモードにSAEの認証を持たず、hostapdのSAEの側を仮想のAPに組むことになるためである。WPA3のSTAの側は、SAEのホストのテスト(`tools/wpa/build.sh modtest`、9.6.7)と実機で確かめる。

APのインタフェース`wsimap0`自身のリンク層のアドレス(02:77:73:00:00:ff)は、APのBSSID(02:77:73:00:00:01、net80211が送るときに使う`ic_myaddr`)と別にしてある。STAのスタックとAPのインタフェースが同じrumpカーネルの中にあり、NetBSDのARPは自分のインタフェースのどれかが持つアドレスから来たARPを捨てる(`in_arpinput`の`if_get_bylla`)ので、同じにするとAPのARPの答えが捨てられる。

#### テスト

群`wifisim`(`tests/ktest/ktest_wifisim.c`、`WIFI_SIM=1`のKTESTで入る)。x64は`make TARGET=_X64_ KTEST=1 KTONLY=wifisim WIFI_SIM=1 BUILD_ID=simob sdimg`を`tools/x64/ktest64.sh`で、ARMは`make TARGET=_QEMU_VIRT_ KTEST=1 WIFI=1 WIFI_SIM=1 KTONLY=wifisim BUILD_ID=simka test`で流す(カーネルのELFの名前はBUILD_IDで決まるので、x64とARMで分ける)。x64のKTESTの機械にはvirtio-netがあり、起動のときは有線を使っている。群は機器の設定の`NET_ADAPTER`を`wifi`にしてWi-Fiに切り替えさせ、アドレスをDHCPから取るようにしてから、次を順に見る。終わったら設定を戻す。

1. 走査(`SCAN`)でAPが見え、WPA2と分かる。
2. パスフレーズで保存した接続(利用者のもの、自分から接続)で接続し、両側の4ウェイハンドシェイクが終わる。
3. DHCPでアドレス(192.168.77.100)、マスク、ゲートウェイ、ネームサーバが取れる。STAのポートが開いていなかったために捨てたデータのフレームが無い。
4. 有線からWi-Fiに移ったことで、DHCPの要求の送り元(イーサネットの送り元と`chaddr`)がSTAのアドレスになり、IPv6のリンクローカルのアドレスがSTAのアドレスから作られ(EUI-64)、有線のアドレスから作ったものが残っていない。
5. DNSで`wifisim.test`の下の名前が引け、ほかの名前は引けない。
6. 1〜1400バイトのUDPのデータグラム20個がAPのエコーから同じバイトで返る。数えるデータグラムを送る前に、数えない1バイトのデータグラムを1つ送り、返るのを待ってAPのリンクのアドレスを引いておく(最大3回)。アドレスを置き直した後のスタックはAPの項目を持たず、ARPで問い合わせている間に送ったデータグラムは保留される。NetBSDは問い合わせ中の隣ごとに1つだけ保留し(`net.inet.arp.maxqueuelen`が1、RFC 1122 2.3.2.2の求める最小)、新しいものが来ると古いものを捨てるので、その間にほかのタスクが同じ隣へ送ると(15秒ごとに問い直す時計のDNSの問合せ)、先に保留されたエコーが失われる。x64で`test_declined`が16/17になったのはこれで、問い合わせ中に続けて送った2つのデータグラムのうち後のものだけが返ることを確かめてある。
7. `DISCONNECT`で離れ、APもそれを見る(`REASON asked`)。
8. `CONNECT`でつなぎ直し、DHCPがまた答える。
9. APを電波から消すと、STAはネットワークを失い(`REASON lost`)、戻すと自分から接続し直し、DHCPとデータが通る。
10. APのパスフレーズを替えると、接続は`REASON password`で終わる。戻すとつながる。
11. DHCPの答えをすべてに送る(グループ鍵で暗号化)ときも取れる。
12. アドレスがまだ無いとき、局がブロードキャストを求めていてもACKを局だけに送る(ハードウェアのアドレスと与えるアドレス宛て、ペアの鍵で暗号化)サーバ(仮想のAPの`dhcp ackuni`)からも、アドレスが取れる。そのあとエコーが通る(アドレスを新しく置いたので、スタックがARPで重複を確かめ終わるのを待つ)。
13. APの信号を閾値より弱くして(`rssi 75`)接続し直すと、DHCPの間と、ポートが開いてから30秒の間は背景の走査が始まらず、その後に始まる(x64のOpenBSDの層だけ。ARMでは飛ばす)。
14. 同じ名前のなしのネットワークに接続でき、DHCPとデータが通る。
