# 第8章　実身

## 8.1 基本的な考え方

TessronOSでは、ファイル、共有メモリ、デバイス、プロセス、プロセス間の通信路、ネットワークのソケット、ウインドウとその部品を、すべて実身として同じ基本操作で扱う。実身は128bitのUUIDで識別され、レコードの列、属性(メタデータ)、保護情報を持つ。どの種類の実身も、開いてキーを取得し、レコードを読み書きし、イベントを受け取る、という同じ手順で使える。

この構造はBTRON2の設計にならっている。周辺核は実身の種類ごとのマネージャの集合で、名前マネージャがシステムコールを担当のマネージャへ振り分ける。

| タイプ | サブタイプ | 実体 | 例 |
| --- | --- | --- | --- |
| ストレージ`OB_T_STORAGE` | ファイル`OB_S_FILE` | ボリューム上のレコード(TSFS) | 文書、図形、プログラム、ユーザ |
| ストレージ | メモリ`OB_S_MEMORY` | 主記憶上のレコード。揮発性 | 共有メモリ、グローバル名 |
| デバイス`OB_T_DEVICE` | ディスク`OB_S_DISK`、キャラクタ`OB_S_CHAR`、時計`OB_S_CLOCK`、サウンド`OB_S_SOUND`、一覧`OB_S_DEVLIST`、システム`OB_S_SYSTEM`、入力`OB_S_INPUT`、画面`OB_S_DISPLAY`、GPIO`OB_S_GPIO`、USB`OB_S_USB` | ドライバ | SDカード、USBメモリ、時計、キーボード、画面、GPIOのバンク、乱数 |
| プロセス`OB_T_PROCESS` | | 実行中のプロセス | |
| 通信`OB_T_CHANNEL` | キュー`OB_S_QUEUE`、ソケット`OB_S_SOCKET` | 主記憶上のメッセージキュー、ネットワークのソケット | ウインドウのイベントの受信口、TCPの接続 |
| ウインドウ`OB_T_WINDOW` | ウインドウ、パネル、メニュー、部品 | ウインドウマネージャ | 文書のウインドウ、ボタン、テキストボックス |

## 8.2 基本操作

| 分類 | システムコール |
| --- | --- |
| 開く、閉じる | `ob_opn_obj`、`ob_cls_obj` |
| 作成、削除、複製 | `ob_cre_obj`、`ob_del_obj`、`ob_cpy_obj` |
| 参照、検索 | `ob_ref_obj`、`ob_lst_obj`、`ob_fnd_nam`、`ob_fnd_lnk`、`ob_lst_lnk` |
| レコード | `ob_rea_rec`、`ob_wri_rec`、`ob_apd_rec`、`ob_trn_rec`、`ob_del_rec`、`ob_lst_rec`、`ob_sch_rec`、`ob_trs_rec` |
| リソース | `ob_rea_res`、`ob_wri_res`、`ob_del_res`、`ob_lst_res` |
| 属性とアイコン | `ob_get_atr`、`ob_set_atr`、`ob_get_ico`、`ob_set_ico` |
| マッピング | `ob_map_rec`、`ob_unm_rec` |
| イベント | `ob_ntf_evt`、`ob_can_evt` |
| 保護 | `ob_get_prt`、`ob_set_prt`、`ob_dup_key` |
| ユーザ | `ob_login`、`ob_set_pwd`、`ob_get_crd` |
| ボリューム | `ob_att_vol`、`ob_det_vol`、`ob_ref_vol`、`ob_get_dom`、`ob_set_dom` |
| トランザクション | `ob_beg_trx`、`ob_end_trx` |

実身を開くと実身キーが返る。キーには所有プロセスと許可された操作が記録されており、以後の操作はキーの操作権限で判定する。所有プロセス以外がキーを使うと`E_OACV`になる。`ob_dup_key`で操作権限を絞ったキーを作り、別のプロセスに渡せる。プロセスが終了すると、そのプロセスのキーはすべて閉じられる。

## 8.3 ストレージの実身

ファイルの実身はTSFSに格納される(第7章)。レコードは型(RT)とサブタイプを持つ。主な型は次のとおりである。

| 型 | 内容 |
| --- | --- |
| 0 | リンク(ウインドウの実身では、パネルからその部品へのリンク) |
| 1 | xmlTAD。文書、図形、仮身一覧 |
| 7、8 | 付箋 |
| 9 | 実行ファイル(プログラムの実身) |
| 10 | データボックス |
| 11 | フォント |
| 12 | 辞書 |
| 15 | 型を定めていないバイト列(ウインドウの配置など) |

書体箱、壁紙箱、プログラム箱のような箱は、レコード0のxmlTADにリンク(`<link id="UUID_0.xtad">`)を並べた実身である。`ob_lst_lnk`は箱のリンク先を書かれた順にすべて返し、名前を指定すればその名前のものだけを返す。`ob_fnd_lnk`はその名前の最初のリンク先を返す。名前は実身名か、メタデータの`tessronos.file.name`(ファイルから取り込んだ実身の元のファイル名)と比べ、英字の大文字と小文字を区別せず、拡張子は省略できる(`NotoSansJP-Regular`は`NotoSansJP-Regular.otf`にも一致する)。箱は呼んだプロセスの資格で読み、メタデータを読めない実身は実身名だけで比べる。フォントの`ts_face_find`、`ts_face_list`、デスクトップの書体箱と壁紙箱の読込み、プログラム箱の一覧(デスクトップ、システム環境設定、パッケージの展開、ファイル変換)、`xf_find`は、これで箱を読む。

メモリの実身は揮発性で、共有メモリとグローバル名に使う。`OB_F_GLOBAL`を指定して作成した実身は、`ob_fnd_nam`で名前から検索できる。メモリの実身のレコードを`ob_map_rec`でプロセスの共有メモリ領域にマッピングすると、同じ物理ページが、マッピングしたすべてのプロセスから同じアドレスで見える。

## 8.4 デバイスの実身

デバイスの実身は、登録されたデバイスごとに存在する。レコードの読み書きがデバイスの読み書きになり、属性にはデバイスの種類、容量、マウントの状態が現れる。このほか、次の仮想デバイスがある。

| 実身 | 内容 |
| --- | --- |
| 時計 | 現在時刻 |
| デバイス一覧 | すべてのデバイスへの仮身を持つ。どのデバイスで起きたイベントもここに届くので、これ1つを監視すればすべてのデバイスの接続と切断が分かる |
| システム(`SYSDEF_SYSTEM`) | マシンそのもの。下表のレコードを持つ |

デバイス管理に登録しないデバイスも、デバイスマネージャが実身として見せる。デバイスを扱うモジュールが名前とレコードの読み書きの関数(`T_OBDVOPS`)を渡して実身を加え(`knl_obdev_add`)、デバイスマネージャがUUIDを与え、デバイス一覧に載せ、保護を付け、接続と切断を`OB_E_ATTACH`、`OB_E_DETACH`で知らせる。UUIDは名前ごとにデバイス箱に記録するので、同じポートに差し直したデバイスは同じ実身になる。どの実身もレコード0に説明のxmlTADを持ち、関係する実身への仮身をそこに置く。

| 実身 | サブタイプ | 名前とUUID | レコード |
| --- | --- | --- | --- |
| 乱数 | `OB_S_CHAR` | 固定のUUID(`ob_uuid_random`)、「乱数」 | 1　読むと乱数のバイト列、書くと生成器に混ぜる |
| 入力 | `OB_S_INPUT` | 固定のUUID(`ob_uuid_input`)、「入力」 | 1　イベント(`T_HIDEV`)、2　ポインタの位置と接続数、3　入力の属性(`T_HIDATTR`) |
| キーボード、ポインタ | `OB_S_INPUT` | HIDのインタフェースごと。「hid」とUSBのポート(`hid0-8.3`) | 1　そのデバイスのイベント、2　種類、ベンダとプロダクト、ポート、絶対座標か相対座標か |
| 画面 | `OB_S_DISPLAY` | 固定のUUID(`ob_uuid_display`)、「画面」 | 1　モード(`SIZE`、`DEPTH`、`MODES`、`DRIVER`など)、2　ピクセル |
| GPIOのバンク | `OB_S_GPIO` | Raspberry Pi 5だけ。`gpio-aon0`、`gpio-aon1`、`gpio-rp1-0`〜`gpio-rp1-2` | 1　ピンごとに「ピン 方向 値 プル」の行 |
| USBデバイス | `OB_S_USB` | ハブを含むデバイスごと。「usb」とコントローラ、ルートポート、経由するハブのポート(`usb0-8.3`) | 1　VID、PID、クラス、速度、ポート、製品名 |

入力の実身のレコード1は、読むと、そのキーで前回読んだ後に届いたイベントの写しを返す。ウインドウマネージャが受け取るイベントを奪わないので、何人が読んでもウインドウには全部が届く。書くと、デバイスが報告したのと同じようにイベントを入れる。試験とデスクトップの操作試験(`dtuitest.c`)は、この書込みで入力を与える。キーボードとポインタの実身は、それぞれ自分のUSBデバイスの実身と入力の実身への仮身を持つ。

画面の実身のレコード1に「幅x高さ」を書くと、画面のドライバを通して解像度を変える。QEMUでは`bochs-display`のモードを、Raspberry Pi 5ではファームウェアにその大きさのフレームバッファを求める(ファームウェアが断ったときは元の大きさのまま)。モードが変わると、画面の実身のレコード1とシステムの実身のレコード3に`OB_E_CHANGE`を知らせる。

GPIOのバンクのレコード1に「ピン 方向 値 プル」の行を書くと、そのピンを設定する(`-`の欄は変えない)。方向は`in`、`out`、チップの機能に渡したピンは`alt<番号>`で表す。カーネルのドライバが使うピン(SDカードの挿抜検出、EthernetのPHYのリセット、ヘッダのUART、サウンドが使うI2S)は行末に`kernel`と付き、書き込むと`E_BUSY`になる。入力のピンの値が変わると、レコード1に`OB_E_CHANGE`を知らせる。通知の`code`がピン、`x`が値である。基板のLEDも、実身ができた後はカーネルがこのバンクの実身を通して点灯させる。

USBデバイスの実身は、ぶら下がるハブの実身、提供する機能の実身(ディスク、サウンドデバイス`snda`、キーボードとポインタ)への仮身を持ち、ハブはその先のデバイスへの仮身を持つ。

システムの実身のレコードは「キー 値」の行からなるテキストである。読み出せばマシンの現在の状態が分かり、書き込めばマシンに指示できる。

| レコード | 読出し | 書込み |
| --- | --- | --- |
| 1　情報 | 名前、バージョン、ビルド日時、機種、プロセッサ、メモリ | |
| 2　電源 | 実行できる操作 | `OFF`で電源を切る、`RESTART`で再起動する |
| 3　画面 | 画面の実身のUUIDと、そのレコード1(解像度、色深度、選択できる解像度) | |
| 4 USB | USBデバイスの実身ごとに、そのレコード1から作る行と実身のUUID | |
| 5　配色 | 配色の一覧と現在の配色 | 番号で配色を切り替える |
| 6　壁紙 | 現在の壁紙 | 画像の実身のUUIDと配置方法で壁紙を変える |
| 7　ネットワーク | IPアドレス、サブネットマスク、ゲートウェイ、DNS、リンク状態、使用中のソケット数 | |
| 8　サウンド | 出力先、サンプリングレート、チャネル数 | |
| 9　ハードウェアの状態 | SoCの温度(`TEMPERATURE`、`TEMPERATURE_MC`)、ARMのクロック(`ARM_HZ`)、V3Dのクロック(`V3D_HZ`)。Raspberry Pi 5ではファームウェアにメールボックスのプロパティタグ(温度`0x00030006`、クロック`0x00030002`)で問い合わせ、QEMUでは`unknown`とする | |

## 8.5 プロセスと通信の実身

実行中のプロセスは実身として参照でき、`OB_E_EXIT`で終了を通知する。プロセスの実身のレコード0は状態を表すxmlTADで、実行しているプログラムの実身と、そのプロセスが開いているソケットの実身への仮身を持つ。

通信の実身には、メッセージキュー(`OB_S_QUEUE`)とソケット(`OB_S_SOCKET`)がある。メッセージキューはレコード0の書込みで1つのメッセージを送り、読出しで1つを受け取る。プロセスがウインドウのイベントを受け取る受信口にも使う。

ソケットは、`so_socket`か`so_accept`で作られてから、`so_close`かプロセスの終了で閉じられるまで実身である(9.2.1)。所有者は作ったプロセスが代理するユーザで、名前は`socket 3 (process 12)`のようになる。レコード0は説明のxmlTADで、所有するプロセスの実身への仮身を持つ。レコード1がデータで、読むと受信し、書くと送信する。メッセージキューのレコード0と同じく、データがないときや送れないときは待ち、キーを`OB_O_NOWAIT`で開いていれば`E_TMOUT`を返す。メタデータの`socket`に、番号、プロセス、ファミリ、種類、プロトコル、両端のアドレスとポート、状態が現れる。実身を削除するとソケットが閉じる。

## 8.6 保護

保護情報はすべての種類の実身に同じ形式で付く。

| 項目 | 内容 |
| --- | --- |
| 所有者、グループ | ユーザとグループのUUID |
| モード | 所有者、グループ、その他のそれぞれにr、w、x |
| 属性 | 書込み禁止、削除禁止 |
| ACL | ユーザかグループごとに許可する操作 |
| レコードマスク | レコードごとに許可する操作を制限する |

rwxは次の操作ビットに展開して判定する。

| ビット | 内容 | rwx |
| --- | --- | --- |
| `OB_OP_READ` | データレコードを読む | r |
| `OB_OP_ATRRD` | 属性を読む、レコードの一覧を取得する | r |
| `OB_OP_WRITE` | データレコードを書く、切り詰める | w |
| `OB_OP_RECORD` | レコードを追加する、削除する | w |
| `OB_OP_ATRWR` | 属性を書く | w |
| `OB_OP_LINK` | 参照数を増減する | w |
| `OB_OP_DELETE` | 実身を削除する、プロセスを終了させる | w |
| `OB_OP_EXEC` | プログラムを実行する、デバイスを制御する | x |
| `OB_OP_PROT` | 保護情報を変更する | 所有者には常に許可 |

判定は次の順で行う。管理者であればすべてを許可する。そうでなければ、所有者、グループ、その他のどれに該当するかでrwxを選び、ACLで許可された操作を加え、属性とレコードマスクで制限する。

レコードマスクに`OB_OP_EXEC`を含むレコードは、`OB_OP_EXEC`を持つキーでなければ読み書きできない。人が見ている画面のピクセルや、人が打ったキーのように、デバイスの制御に等しいレコードに使う。デバイスの実身の既定の保護では、xは管理者だけが持つ。

| 実身 | 所有者、グループ | モード | xが要るレコード |
| --- | --- | --- | --- |
| 乱数 | システム、管理者 | `rw-r--r--` | なし |
| 入力、キーボード、ポインタ | システム、管理者 | `rw-r--r--` | 1(イベントの読み書き) |
| 画面 | システム、管理者 | `rw-rw-r--` | 2(ピクセルの読出し) |
| GPIOのバンク | システム、管理者 | `rw-rw-r--` | なし(グループと管理者が書ける) |
| USBデバイス | システム、管理者 | `r--r--r--` | なし |
| ソケット | 作ったプロセスのユーザ、その最初のグループ(カーネルのソケットはシステム、管理者) | `rw-------`(変更できない) | なし |

ボリュームには保護ドメインを設定できる。ドメインの保護は、そのボリュームのすべての実身の保護に重ねて適用される。

TADjs Desktopから持ってきた実身は保護情報を持たない。その場合は所有者なしとし、メタデータの`readable`、`editable`、`deletable`からモードと属性を決める。

## 8.7 ユーザとログイン

ユーザとグループはファイルの実身で、メタデータの`tessronos.user`、`tessronos.group`で定義する。パスワードはPBKDF2-HMAC-SHA256のハッシュで保存し、平文は保存しない。プロセスは資格情報(ユーザと所属グループの一覧)を持ち、子プロセスは親の資格情報を継承する。`ob_login`で資格情報を別のユーザに切り替える。初期プロセスとカーネルのタスクは管理者である。

## 8.8 イベント通知

`ob_ntf_evt`で、ある実身の特定のレコードで起きたイベントを、通信の実身かストレージの実身へ通知させられる。ウインドウの入力、部品の操作、ストレージの実身の変更、デバイスの接続と切断は、すべてこの1つの仕組みで受け取る。

| イベント | 内容 | 発生する実身 |
| --- | --- | --- |
| `OB_E_PRESS`、`OB_E_RELEASE` | ボタンを押した、離した | ウインドウ、部品 |
| `OB_E_MOVE`、`OB_E_WHEEL` | ポインタが動いた、ホイールが回った | ウインドウ |
| `OB_E_KEY` | キー入力 | ウインドウ |
| `OB_E_ENTER`、`OB_E_LEAVE` | ポインタが入った、出た | ウインドウ |
| `OB_E_REDRAW` | ウインドウの再描画が必要 | ウインドウ |
| `OB_E_CLOSE` | ウインドウを閉じるよう要求された | ウインドウ |
| `OB_E_CHANGE` | レコードや部品の値が変わった | ストレージ、部品、パネル、デバイス(画面のモード、GPIOの入力、キーボードとポインタの数) |
| `OB_E_DELETE` | 実身が削除された | すべて |
| `OB_E_ATTACH`、`OB_E_DETACH` | メディアやデバイスが接続された、切断された | デバイス |
| `OB_E_EXIT` | プロセスが終了した | プロセス |
| `OB_E_DROP` | 仮身がドロップされた | ウインドウ |
| `OB_E_SCROLL` | スクロールバーが操作された(10.4) | ウインドウ |

通知は固定長の`T_OBNTM`で届き、要求の番号、発生元の実身のUUID、レコード番号、イベントの種類、キーやボタン、位置、時刻を含む。受信側のキューが満杯でも送信側は待たない。取りこぼした数は次に届く通知に記録される。

## 8.9 設定の実身

マシンの設定は、固定のUUIDを持つ設定用の実身のレコード1に「キー 値」の行として格納する。ネットワーク設定、デバイス設定、ユーザ情報の3つがある。カーネルはこれらのレコードの変更をイベントで監視しており、書き換えられるとすぐに反映する。設定の小物(第11章)は、設定用の実身を書き換えるだけで設定を変える。

## 8.10 デバイスの実身化の確認

デバイス管理に登録していなかった資源を実身にした。カーネルの関数を直接呼んでいた経路は実身を通すように改め、直接の関数は、呼ぶ回数が多くて実身を通すと遅くなる経路にだけ残した。そうした経路は実身のキーを1回開いて保持する。時間は`ktest_devob`の`test_measure`でQEMU上で測った1回あたりの値である。

| 資源 | 実身の種類とマネージャ | 名前とUUID | 操作 | 保護 | 事象 | 関係(仮身) | 定義 | 実身にしないものと理由 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |

## 8.11 ソケットの実身化の確認

ネットワークのソケットを通信の実身にした(9.2.1)。スタックは番号を割り当てるときと返すときだけ実身の層に知らせ、送受信の経路は変えていない。時間は`ktest_so`の`test_sockobj_rate`でQEMU上で測った1回あたりの値である。

| 資源 | 実身の種類とマネージャ | 名前とUUID | 操作 | 保護 | 事象 | 関係(仮身) | 定義 | 実身にしないものと理由 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| ソケット | 通信(`OB_S_SOCKET`)、ソケットマネージャ(`obsock.c`) | `socket 3 (process 12)`。UUIDは`so_socket`、`so_accept`のときに作り、`so_close`で消える。`so_getobj`で番号から引く | レコード0で説明を読む。レコード1を読むと受信、書くと送信。実身を削除するとソケットを閉じる | 作ったプロセスのユーザの所有、`rw-------`(変更できない)。カーネルのソケットはシステムの所有 | 閉じると`OB_E_DELETE` | 所有するプロセスの実身への仮身。プロセスの実身から各ソケットへの仮身 | 属性`socket`(`number`、`process`、`family`、`type`、`protocol`、`local`、`remote`、`state`、`waiting`) | 送受信、オプション、待ち合わせ(`so_send`、`so_recv`、`so_poll`など)と、POSIXの口は番号のまま(1回ごとに実身を探すと遅くなる)。ソケット番号とrumpカーネルのディスクリプタの対応は`so_api.c`に残す |

| 経路 | NetBSD | lwIP |
| --- | --- | --- |
| `so_socket`と`so_close`の1組 | 34〜55µs | 29µs |
| そのうち実身の作成と削除 | 2.5〜4.2µs | 5.8µs |
| 何もしない呼出し(`so_fcntl`) | 1.5〜2.4µs | 0.12µs |

`so_fcntl`と送受信の呼出しは実身に触れないので、時間は9.1.4の値と変わらない。実身の分が加わるのはソケットを作るときと閉じるときだけである。
